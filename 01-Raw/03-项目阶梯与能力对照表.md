# 项目阶梯与能力对照表

> **文件性质：** 能力标准与作品规划，**只增不改**。它回答三个问题：做什么、做到什么程度算过关、怎么讲给面试官听。
> **配套：** [[01-Raw/02-12周速通学习计划]]（什么时候做）· [[00-配置/进度看板]]（做到哪了）· [[04-Outputs/README]]（作品记录）

---

## 一、这个阶梯怎么用

**不要从最后一档开始。** 每一档的存在意义是让你在**刚好够得着**的难度上练一个具体能力。跳过 L1 直接做 L6 的结果通常是：代码能跑，但说不清为什么这么写。

**判断标准不是"跑通 Demo"**，而是能不能回答四个问题：

1. **为什么这样选？**（技术选型的依据，替代方案的代价）
2. **效果如何度量？**（指标是什么、数字是多少、怎么测的）
3. **失败如何恢复？**（出错了会怎样、有没有兜底）
4. **成本如何控制？**（一次多少钱、上限在哪、怎么降）

四个问题答不上来，这一档就没过关。

## 二、八级阶梯

### L1 · 计算器 Agent

| 项目 | 内容 |
|------|------|
| **一句话** | 能理解自然语言里的计算需求，调用计算工具算出结果 |
| **核心能力** | 最小 tool call loop、工具 schema 定义、错误处理 |
| **对应章节** | [[docs/第04章 工具调用]]、[[docs/第05章 ReAct最小Agent-Loop]] |
| **规模** | 100–150 行 |

**最低交付标准：**
- [ ] 至少 3 个工具（计算、时间、单位换算之类）
- [ ] 工具失败时程序**不崩溃**，错误被喂回模型
- [ ] 有最大步数限制
- [ ] 有 README 说明怎么跑

**验证方式：** 准备 10 个测试问题（含 2 个无法回答的），跑一遍记录通过数。

**面试会被问：** 模型是怎么选中工具的？工具描述写不好会怎样？

---

### L2 · 网页研究 Agent

| 项目 | 内容 |
|------|------|
| **一句话** | 输入一个主题，自动搜索、筛选、综合，输出**带可追溯引用**的报告 |
| **核心能力** | 任务拆解、多步规划、来源可信度判断、引用保真 |
| **对应章节** | [[docs/第06章 范式进阶]]、[[docs/第08章 RAG全链路]]、[[docs/第15章 综合实战]] |
| **规模** | 300–500 行 |

**最低交付标准：**
- [ ] 有明确的报告结构（不只是"一堆段落"）
- [ ] **引用可追溯**：每个引用能定位到原始来源，编造的引用会被拦截
- [ ] 有失败处理：抓取失败、搜索结果为空、内容过长
- [ ] 给出一次真实运行的产物（报告文件）

**验证方式：** 5 个不同主题各跑一次，人工检查引用准确率与编造率（编造率必须为 0）。

**面试会被问：** 怎么保证引用不造假？搜索结果矛盾时怎么处理？

---

### L3 · 文档问答 Agent

| 项目 | 内容 |
|------|------|
| **一句话** | 喂一批自己的文档，用自然语言提问，得到**带出处**的答案；文档里没有的会说"不知道" |
| **核心能力** | RAG 全链路、切片策略、混合检索、Rerank、拒答、评估 |
| **对应章节** | [[docs/第08章 RAG全链路]]、[[docs/第15章 综合实战]] |
| **规模** | 400–700 行 |

**最低交付标准：**
- [ ] 有**切片对比实验**（至少两种切法，给出召回率差异并解释原因）
- [ ] 混合检索（向量 + 关键词）且用了 RRF 之类的融合
- [ ] 有引用校验（编号存在 + 字面依据），不合格就拒答
- [ ] **30 条评测集**，报告三个指标：Recall@K / 忠实度 / 引用准确率
- [ ] bad case 分类统计（切片问题 / 检索没召回 / 召回了没用 / 模型瞎编）

**验证方式：** 评测集全跑一遍，指标可复现；把 bad case 列表给一个没参与的人看，他能照着改进。

**面试会被问：** 召回率多少？怎么测的？召回不够你怎么排查？

---

### L4 · 代码审查 Agent

| 项目 | 内容 |
|------|------|
| **一句话** | 读一个 git diff，按风险排序给出**可执行**的修改建议，而不是"这里可能有问题" |
| **核心能力** | 长上下文处理、风险分类、**误报控制**、结构化输出 |
| **对应章节** | [[docs/第09章 Skills能力包]]、[[docs/第11章 多智能体协作]]、[[docs/第15章 综合实战]] |
| **规模** | 300–600 行 |

**最低交付标准：**
- [ ] 大 diff 有降级策略（分块 / 摘要 / 只审查变更行附近），并**声明覆盖范围**
- [ ] 建议可执行：给出具体改法和示例代码，不只是描述问题
- [ ] **误报控制**：置信度阈值 + 条数上限 + 风格类过滤
- [ ] 20 个真实 diff 的测试结果：检出率 / 误报率 / Precision@3

**验证方式：** 用你自己或开源项目的真实 commit 测；宁可少报也别乱报 —— 误报率高会让工具被弃用。

**面试会被问：** 怎么控制误报？大 diff 塞不进去怎么办？

---

### L5 · 浏览器 Agent

| 项目 | 内容 |
|------|------|
| **一句话** | 只操作公开网页：打开、观察、提取信息、生成摘要 |
| **核心能力** | 页面理解、元素定位、失败恢复、安全边界 |
| **对应章节** | [[docs/第10章 MCP与通信协议]]、[[docs/第13章 部署成本与性能]] |
| **规模** | 300–500 行 |

**最低交付标准：**
- [ ] 能处理页面变化 / 弹窗 / 元素定位失败（每种都有降级路径）
- [ ] 有动作日志（截图或 DOM 快照），失败时能复盘
- [ ] **安全边界写进 README**：不登录敏感账号、不绕过平台规则、不越权
- [ ] 遵守目标站点的 robots 与访问频率

**验证方式：** 在 3 个公开网页上跑通；故意改一个选择器，验证降级路径生效。

**⚠️ 合规提醒：** 只操作公开页面，遵守平台规则与版权边界。不爬取需登录内容，不做批量抓取。

---

### L6 · Nano Coding Agent

| 项目 | 内容 |
|------|------|
| **一句话** | 一个能读写文件、执行命令、跑测试的编码 Agent —— 迷你版 Claude Code |
| **核心能力** | shell 工具、文件编辑、**权限门**、session、上下文压缩、trace |
| **对应章节** | [[docs/第14章 构建你自己的Agent框架]] |
| **规模** | 500–900 行 |

**最低交付标准：**
- [ ] 工具集：读文件 / 写文件 / 搜索 / 执行命令（**命令执行必须在白名单内**）
- [ ] **权限门**：危险操作（写、删、执行）需确认，确认界面展示完整参数
- [ ] **session 持久化**：能中断后恢复继续
- [ ] **上下文压缩**：长任务不撑爆窗口，压缩前后有对比数据
- [ ] 完整 trace，能导出并复盘一次失败运行

**验证方式：** 让它修一个真实的小 bug（含跑测试验证），全程记录 trace；中断一次再恢复。

**面试会被问：** 权限怎么设计的？上下文满了怎么办？怎么防止它删错文件？

---

### L7 · 可复用 Skill Pack

| 项目 | 内容 |
|------|------|
| **一句话** | 把一类任务的流程知识打包成可复用、可验证的能力包 |
| **核心能力** | SKILL.md 设计、渐进式加载、**效果验证** |
| **对应章节** | [[docs/第09章 Skills能力包]]、[[skills/README]] |
| **规模** | 3–5 个 skill，每个含 SKILL.md + 脚本/模板 |

**最低交付标准：**
- [ ] 每个 skill 有清晰 frontmatter（name / description / 触发条件）
- [ ] description 写明"做什么 + 什么时候用 + 什么时候别用"
- [ ] 每个 skill 有验收标准（否则模型不知道什么时候算做完）
- [ ] **smoke test**：固定任务集，带 skill 与不带 skill 各跑一遍，**给出成功率对比**
- [ ] 附带资源按需加载（不是一股脑塞进上下文）

**验证方式：** A/B 对比的成功率差异要能复现。说不出提升多少 = 没过关。

**面试会被问：** Skill 和 Prompt 有什么区别？怎么知道你的 Skill 真的有用？

---

### L8 · 生产级 Harness

| 项目 | 内容 |
|------|------|
| **一句话** | 一个能上线、可评估、可观测、有权限边界、成本可控的 Agent 运行时 |
| **核心能力** | 全部前七档 + 评估体系 + 可观测性 + 生产工程 |
| **对应章节** | [[docs/第12章 评估可观测性与安全]]、[[docs/第13章 部署成本与性能]]、[[docs/第14章 构建你自己的Agent框架]] |
| **规模** | 1000 行以上，多个模块 |

**最低交付标准：**
- [ ] **evals**：固定评测集 + 可复现的指标报告 + 回归测试进 CI
- [ ] **trace**：每次运行可导出，能按失败模式分类
- [ ] **权限**：危险动作白名单 + 人工确认 + 最小权限
- [ ] **成本**：单次/单用户/每日三级上限 + 熔断
- [ ] **可靠性**：分层超时 + 分类重试 + 降级链 + 幂等
- [ ] **可恢复**：可中断、可续跑、可回放
- [ ] 一份压测或容量报告（P50 / P95 / 成本曲线）

**验证方式：** 让别人 clone 下来，照着 README 能在 10 分钟内跑起来；给他一份指标报告，他能看懂你的取舍。

**面试会被问：** P99 怎么优化？成本怎么降了 80%？线上出问题你怎么定位？

## 四、简历怎么写

### 4.1 项目描述的公式

```
做了什么（动词开头） + 用了什么技术 + 解决到什么程度（数字） + 规模（可选）
```

**❌ 空话版本：**
> 深度参与企业知识库项目，负责 RAG 模块开发，大幅提升了检索效果。

问题：没有技术细节、没有数字、"深度参与"和"大幅提升"是填充词。

**✅ 可验证版本：**
> 独立搭建企业知识库问答系统（Python + 混合检索）：针对中文文档设计了父子切片策略，用 BM25 + 向量双路召回配合 RRF 融合，检索 Recall@5 从 0.74 提升到 0.88；实现三道引用校验把编造引用从 12% 降到 0；建 30 条评测集把迭代从"凭感觉"变成"看指标"。

**逐句拆解：**
| 句子成分 | 作用 |
|----------|------|
| 独立搭建…问答系统 | 明确范围和你的角色 |
| 中文文档 + 父子切片 | 体现一个具体的技术决策 |
| BM25 + 向量 + RRF | 体现方案完整度 |
| Recall@5 0.74 → 0.88 | 可验证的效果 |
| 编造引用 12% → 0 | 抓了一个具体问题 |
| 30 条评测集 | 体现工程规范 |

### 4.2 必须删掉的空话词

| 删掉 | 换成 |
|------|------|
| 精通 / 熟练掌握 | （直接写你做过什么） |
| 深度参与 | 我负责了 X 模块，做了 Y |
| 大幅提升 / 显著优化 | 从 A 提升到 B |
| 负责相关工作 | 具体做了什么 |
| 了解 / 熟悉 | 用过它做过什么 |
| 丰富的经验 | 做过 N 个项目，分别是…… |

**判据：删掉这个词之后，句子信息量没变 → 这个词就是废话。**

### 4.3 数字从哪来

| 场景 | 数据来源 |
|------|----------|
| 有真实用户 | 线上监控（要能说出统计口径和时间范围） |
| 没有真实用户 | **离线评测集**（要给出集子大小和判定方式） |
| 被问"这个数怎么来的" | "在 N 条离线评测集上测的，判定方式是 X，跑 K 次取平均" |

**⛔ 不要编数字。** 面试官一定会追问口径（怎么测的、样本多大、有没有置信区间）。答不上来比没有数字更糟。

### 4.4 三个项目怎么组合

写简历不是写得越多越好。建议：

| 位置 | 放什么 | 为什么 |
|------|--------|--------|
| 第一个 | **L8 或 L6**（最有分量的） | 体现工程完备度 |
| 第二个 | **L3 文档问答**（最贴业务的） | 大多数岗位需要 RAG 能力 |
| 第三个 | **L7 Skill Pack 或 L4 代码审查**（最能体现判断力的） | 区别于只会调 API 的候选人 |

**L1 / L2 不要写进简历** —— 它们是练习，不是作品。做完就归档到 [[04-Outputs/]]，别放简历。

## 五、面试追问预演

每个项目都会被问这几类问题。**面试前把你的项目的答案写下来。**

| 追问 | 应对框架 | 你的答案（面试前填） |
|------|----------|---------------------|
| 为什么不用 X 方案？ | 四维对比：成本 / 延迟 / 可靠性 / 团队成本 | |
| 流量涨 10 倍怎么办？ | 先算账（QPS、token、成本）再谈架构 | |
| 效果不好你怎么排查？ | 分段定位：检索层 → 上下文层 → 模型层 → 工具层 | |
| 最难的地方是什么？ | 说一个**真实的取舍**，不要堆技术名词 | |
| 你在里面具体做了什么？ | 严格区分"我做的"和"我们做的" | |
| 如果重做一次你会怎么改？ | 体现反思，要有具体的改动点 | |
| 你的方案有什么缺点？ | 主动暴露边界，比嘴硬得分高 | |

完整的追问应对示范见 [[02-Wiki/面试题库/03-项目表达与追问应对]]。

## 六、常见翻车点

| 翻车点 | 表现 | 怎么避免 |
|--------|------|----------|
| **做得太大** | 想做一个"通用 AI 助手"，结果什么都没做完 | 缩到一个具体场景、一类具体用户 |
| **没有指标** | 只能说"效果不错" | 建评测集，哪怕只有 20 条 |
| **只演示 happy path** | 面试官一问失败情况就露馅 | 准备一份失败案例清单 |
| **无法复现** | 别人 clone 下来跑不起来 | README 四问：怎么跑 / 怎么配 / 怎么扩展 / 已知限制 |
| **伪造数据** | 编了一个测不出来的指标 | 只写能说清口径的数字 |
| **过度包装** | 把教程项目说成"生产系统" | 诚实说明规模和限制，反而加分 |
