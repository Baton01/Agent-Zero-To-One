# Agent 学习路线调研报告

> **文件性质：** 调研与规划，**只增不改**。它记录的是"为什么这样排课"，不是学习内容本身。
> **什么时候看：** 开始之前看一遍建立全局观；学到一半迷茫时回来看；想调整计划时对照着改 [[01-Raw/02-12周速通学习计划]]。

## 一、为什么又做一份 Agent 学习路线

网上关于 AI Agent 的资料已经足够多，真正缺的是三样东西：

| 缺什么 | 具体表现 | 本项目的做法 |
|--------|----------|--------------|
| **缺顺序** | 收藏了 200 篇文章，不知道先看哪个；RAG 和 ReAct 哪个先学都说不清 | 17 章严格按**依赖关系**排序，每章的前置章节写在章首 |
| **缺动手** | 看完"什么是 ReAct"觉得自己懂了，一让写就写不出来 | 每章一个可运行脚本，且**没有 API Key 也能跑** |
| **缺反馈** | 学得对不对没人告诉你；卡住了没人可问 | 内嵌 AI 教练（[[学习中枢]]），带评测集和自我检验清单 |

还有第四个更隐蔽的问题：**大部分教程教你用框架，不教你判断**。学完 LangGraph 的人，往往答不出"这个任务到底该不该用 Agent"。所以本项目把"什么时候不该用"贯穿始终 —— 每一章都在讲边界。

## 二、先看清坐标：Agent 领域现在该学什么

Agent 领域变化极快，2023 年流行的东西到 2026 年很多已经成了历史。把精力投在正确的地方，比努力更重要。

### 2.1 优先级排序

| 优先级 | 学什么 | 为什么 | 对应章节 |
|:------:|--------|--------|----------|
| **1** | 编码类 Agent（Claude Code / Codex 形态） | 真实代码库、shell、文件编辑、测试、权限、上下文压缩 —— 这是**最好的 Agent 工程样本**，因为它把 Agent 的所有难点都暴露了 | 05 / 07 / 12 / 14 |
| **2** | Agent Harness 工程 | Agent 的能力很大一部分不来自模型，而来自 harness：工具协议、权限、状态、反馈、回放、CI、评测 | 12 / 13 / 14 |
| **3** | 上下文工程 | 长任务的胜负手。上下文怎么选、怎么压、怎么隔离，直接决定 Agent 能不能撑过 20 步 | 07 |
| **4** | 工具与协议（Function Calling / MCP / Skills） | 工具决定 Agent 的能力边界；MCP 决定接入成本；Skills 决定流程知识的复用效率 | 04 / 09 / 10 |
| **5** | 评估、可观测性与安全 | 没有 eval、trace、权限边界的 Agent 只能算 demo。这一项是"业余"和"专业"的分水岭 | 12 |
| **6** | 多智能体协作 | 有用，但**被严重高估**。多数任务单 Agent 就够。要学，但要先学会判断什么时候不用 | 11 |
| **7** | RAG | 仍然是企业落地最广的场景，但要理解它正在被长上下文和更好的检索方案重塑 | 08 |
| **8** | 微调 / Agentic RL | 应用开发者不必精通，但要知道它解决什么问题、什么时候该用它而不是 RAG | 02（对比）/ 速查表 |

### 2.2 不建议重押的方向

- **老式角色扮演多 Agent 框架**（crew / role-play 那一类）：它们的抽象已经被更强的 Coding Agent / Harness 形态覆盖。可以了解历史，不必当主线。
- **背 API 和框架用法**：框架每半年换一批。学**设计模式**（工具契约、停止条件、上下文治理）才保值。
- **只做 Demo 不做评估**：会写 10 个 demo 但说不出任何一个的指标，面试和实际工作都不加分。

## 三、学习路线对比：三种主流路径的取舍

在做这份规划前，对比了三条主流学习路径：

| 路径 | 代表形态 | 优点 | 缺点 | 本项目的取舍 |
|------|----------|------|------|--------------|
| **A. 从平台入手** | Dify / Coze / n8n 拖拽搭建 | 门槛最低，一小时能出成品，有成就感 | 学到的是"配置某一个工具"，换平台就归零；出问题无法排查；无法回答"为什么" | **不采用为主线**。第 05 章会提一下，帮助你形成判断，但不作为学习路径 |
| **B. 从框架入手** | 直接学 LangGraph / AutoGen / Agents SDK | 上手快，能快速做出复杂结构 | 抽象泄漏时你会束手无策；容易只会"调 API"不会"想设计"；面试一问原理就露馅 | **折中**：先手写（04/05/06），再对照框架（14），最后知道框架替你做了什么 |
| **C. 从原理入手** | 先读 Transformer 论文、学预训练 | 基础扎实，理解深刻 | 周期太长（几个月），学完还做不出一个能用的 Agent，容易中途放弃 | **只取够用的部分**：第 02 章讲清 Token / 上下文 / 采样，不深入数学 |

**最终方案：B 与 C 的折中，且明确"先手写、后框架"。**

具体来说 —— **前 14 章不依赖任何 Agent 框架**。你手写 ReAct 循环、手写工具注册表、手写切片和检索、手写 multi-agent 调度。第 14 章再把这些重构成一个自己的 mini harness，然后才去对比 LangGraph 这类真实框架。

理由：**框架的抽象是别人的判断结果。你没经历过它要解决的问题，就看不懂它为什么这么设计。**

## 四、为什么是 17 章这个顺序

课程顺序不是按"知识点分类"排的（那种排法看起来整齐，学起来断裂），而是按**能力依赖链**排的。

```
第 00 章  环境与第一次调用   ← 先有"能跑"的体感，再谈别的
   ↓
第 01 章  认识 Agent          ← 建立判断力：什么该用、什么不该用
   ↓
第 02 章  大模型基础          ← Token/成本/上下文 = 后面所有取舍的度量单位
   ↓
第 03 章  结构化输出          ← 从"会聊天"到"会开发"的分界线
   ↓
第 04 章  工具调用            ← Agent 的手
   ↓
第 05 章  ReAct 循环          ← 把 03 + 04 装进一个能自转的循环（核心章）
   ↓
第 06 章  范式进阶            ← 循环有了，再谈怎么规划、怎么反思
   ↓
第 07 章  记忆与上下文工程    ← 循环跑长了会撑爆上下文，必须解决
   ↓
第 08 章  RAG                 ← 外部知识接入（也是最大的单独场景）
   ↓
第 09 章  Skills              ← 流程知识可复用（为什么不是 prompt）
第 10 章  MCP                 ← 工具接入标准化
   ↓
第 11 章  多智能体            ← 单 Agent 能力到顶后的横向扩展
   ↓
第 12 章  评估与安全          ← 到这里才谈"能不能信"
第 13 章  部署与成本          ← 到这里才谈"能不能用"
第 14 章  自造框架            ← 抽象收束：把散落的能力结构化
   ↓
第 15 章  综合实战            ← 三个可交付项目
第 16 章  毕业设计与面试      ← 独立设计与表达
```

### 几个关键的顺序决策及理由

| 决策 | 理由 |
|------|------|
| **第 01 章就讲"什么时候不该用 Agent"** | 判断力应该在最开始建立，而不是最后补充。很多人的问题不是不会用 Agent，是到处乱用 |
| **第 02 章讲成本，放在很前面** | 成本是 Agent 工程最重要的约束之一，而且它是**可计算**的。早建立"这个设计要花多少钱"的直觉，能避免后面大量错误决策 |
| **第 03 章独立成章** | 结构化输出是一道真正的分界线。会写 prompt 聊天的人很多，能让模型稳定输出可解析结构的人少得多 |
| **第 05 章必须是高潮** | ReAct 是整个领域的心脏。这一章写不透，后面全是空中楼阁 |
| **第 07 章在 RAG 之前** | 上下文管理和检索是两件事，但上下文管理更基础 —— 它决定了检索结果怎么被消费 |
| **第 09/10 章放一起讲** | Skills（能力复用）和 MCP（接入标准化）解决的是同一类问题的两面：怎么让 Agent 的能力可扩展 |
| **第 11 章在多智能体之前先泼冷水** | 这一章的开篇就是"多智能体不是魔法，大多数任务单 Agent 就够"。先建立成本意识，再学怎么用 |
| **第 12 章（评估）在第 13 章（部署）之前** | 没有评估就部署，等于闭着眼睛上线 |
| **第 14 章自造框架放在最后** | 只有前面所有痛都痛过了，你才知道框架该抽象什么 |

## 五、12 周的时间分配依据

12 周（每周 6–8 小时）是怎么来的：

| 阶段 | 周次 | 内容 | 为什么占这么久 |
|------|:----:|------|----------------|
| 起步 | W1 | 00–02 章 | 需要熟悉新工具链，且第 02 章的概念多 |
| 核心 | W2–W4 | 03–07 章 | **ReAct 和上下文工程必须慢**，这两块是后面所有内容的地基 |
| 扩展 | W5–W7 | 08–10 章 | RAG 一条链路就值得两周；Skills/MCP 相对轻 |
| 工程 | W8–W10 | 11–13 章 | 评估和部署都是"做起来比听着慢"的工作 |
| 收束 | W11–W12 | 14–16 章 | 自造框架和综合实战是**整合**，不是新知识 |

**时间不够怎么办？** 优先级：`05 → 07 → 04 → 12 → 08 → 13 → 其余`。也就是说，如果只有 4 周，做第 04、05、07、12 章加一个项目。这四章能让你具备"能做出可用 Agent"的最小能力集。

**别跳过的三章：** 04（工具）、05（循环）、12（评估）。它们不是"某一类知识"，而是**方法论**。

## 六、学习方法上的四个结论

### 6.1 先跑通，再理解细节
每个脚本都支持 `AGENT_MOCK=1` 离线跑通。先看流程怎么走、每一步打印了什么，再回过头看代码。**不要一开始就逐行读代码** —— 在不知道它要解决什么问题之前，读懂的是语法不是设计。

### 6.2 「改一个地方」比「读完一章」重要
每章都有"动手改造"任务。改完要**先预测结果，再运行验证**。预测和实际不一致的地方，就是你理解错的地方 —— 这比读十遍正文都有用。

### 6.3 用「能讲清」检验掌握，而不是「跑通了」
每章的进度看板有三个勾：跑通代码 → 能讲清机制 → 能改能动。只打第一个勾的章节，三个月后基本等于没学。

### 6.4 建立自己的失败库
[[02-Wiki/速查表/03-报错排查手册]] 是公共的，但你遇到的坑是私有的。每次踩坑记进 [[03-学习笔记/]] 的「踩坑记录」，12 周后这就是你最有价值的资产 —— 因为面试和工作里，**判断力主要来自踩过的坑**。

## 七、每阶段的"过关标准"

学完一个阶段，用这个标准自检。达不到就回炉，不要往下走。

### 阶段一（第 00–02 章）· 起步
- [ ] 能在 5 分钟内从零配好环境并跑通一次真实调用
- [ ] 能画出"一次模型请求的完整链路"（从你的代码到模型再回来）
- [ ] 能计算一个具体设计要花多少钱
- [ ] 能说出三种情况下**不该**用 Agent，并说明理由

### 阶段二（第 03–06 章）· 单 Agent 核心
- [ ] 能写出稳定输出 JSON 的 prompt，并处理模型不听话的情况
- [ ] 能不看代码说出工具调用的五步流程
- [ ] 能白手写出一个 ReAct 循环，并给出五种停止条件
- [ ] 能说出 CoT / Plan-and-Execute / Reflection 各自的适用场景和代价

### 阶段三（第 07–10 章）· 能力扩展
- [ ] 能设计一个带压缩的上下文管理方案，并说明压缩丢了什么
- [ ] 能搭一条完整的 RAG 链路，并给出召回率指标
- [ ] 能写一个真的会被触发的 Skill，并证明它有效
- [ ] 能接上一个 MCP Server，并说清 MCP / A2A / ACP 的分工

### 阶段四（第 11–14 章）· 工程化
- [ ] 能设计多 Agent 的契约和停止条件，并能说出为什么这个任务需要（或不需要）多 Agent
- [ ] 能建评测集、跑出指标、对失败做分类
- [ ] 能量化成本、延迟，并给出优化清单
- [ ] 能画出自己的 harness 架构图，说明每个模块存在的理由

### 阶段五（第 15–16 章）· 实战
- [ ] 交付 1 个有指标、有 README、别人能跑起来的项目
- [ ] 完成毕业设计并做一次 3 分钟演示
- [ ] 能把项目按"业务问题 → 技术选型 → 系统设计 → 评估指标 → 故障与优化 → 最终结果"讲出来
