## 0. 开篇：三个"本地好好的"的事故

把 Agent 放到别人的浏览器里，第一天通常会出三件事，而且它们都不是模型的问题。我上周刚经历一次：一个内部助手在我自己机器上跑了半个月，稳得像老黄牛，于是我们开了 10 个人的灰度。

> 上线两个小时，群里有人问："是不是挂了？我这边转圈转了 4 分钟。"
>
> 我打开日志："不应该啊，我本地 8 秒就跑完了。"
>
> "你一个人跑当然 8 秒，"他说，"我们三个人同时点，全都报 429 了。"
>
> 那天晚上我又看了一眼账单：$47，是预期的 6 倍。我一开始以为是模型涨价，追了半天才想明白——失败后无限重试、循环没有预算上限，有一个任务自己跟自己死循环到天亮。
>
> "那超时呢？代码里没设超时吗？"
>
> "客户端有，"我说，"但工具卡住的时候，整个循环都在等。"
>
> 他忍不住问："可你自己不是跑了半个月吗？怎么一点征兆都没有？"
>
> "因为本地只有我一个人用，也不会有人同时点十次。"

| 事故 | 现场 | 真实原因 |
|---|---|---|
| **并发** | 本地单人跑 8 秒很流畅；3 个人同时用，全部报 429 | 代码是同步串行的，且没有并发上限与限流——3 个请求把上游配额打满 |
| **超时** | 某次任务卡住不动，用户等到 4 分钟自己关掉页面 | 只有客户端有超时，**每一层都没有**；工具卡住时整个循环在等 |
| **成本** | 一晚过去账单 $47，是预期的 6 倍 | 失败后无限重试 + 循环没有预算上限，任务本身还在死循环 |

三个事故的共同点：**它们都只在"多用户 + 长时间 + 真实网络"下出现**，而你的本地测试恰好一条都不满足。

另一个容易被忽略的差异是输入分布：本地你输入的是精心写的问题，线上用户输入的是"帮我看看那个东西怎么样了"。上下文长度、工具调用次数、重试率都会比本地高，**成本因此不是线性放大，而是成倍放大**。

所以这一章讲的是"给别人用"这件事的全部细节：延迟该看哪三个数、流式要流出什么、成本怎么一步步压下来、失败怎么兜住——最后给出一份可以逐项打勾的上线前检查清单。

### ⚠️ 常见坑

- **现象**：本地单测全绿，上线后 5% 的请求超时，日志里只有 `TimeoutError` 没有别的信息。**原因**：底层超时比上层长，外层先死，真正的错误被吃掉了。**怎么改**：内层超时必须短于外层（第 4 节的分层超时表）。
- **现象**：第一周成本很低，第二周突然翻倍。**原因**：用户开始问长问题、用上历史上下文（第 07 章），输入 token 涨了 3 倍而你没看 trace。**怎么改**：从第一天就统计"每任务成本"和"$/完成任务"（第 12 章），并设预算熔断。
- **现象**：加了流式输出，用户却说"还是卡"。**原因**：流式只改善了 TTFT，Agent 端到端要等 8 步跑完。**怎么改**：见第 2 节——Agent 的流式要输出"进度"而不只是"文字"。

## 1. 延迟的三个关键指标

用户说"慢"，可能指三件完全不同的事。分开量化，才谈得上优化。

| 指标 | 定义 | 用户感知 | 主要优化手段 |
|---|---|---|---|
| **TTFT**（Time To First Token，首字延迟）| 请求发出 → 第一个 token 到达 | "它到底有没有开始干活" | 流式输出、精简 prompt、**前缀缓存**（第 3 节）、更快的模型 |
| **TPOT**（Time Per Output Token，每 token 输出时间）| (总时长 - TTFT) / (输出 token 数 - 1) | "它一个字一个字往外蹦得有多慢" | 选更快的模型（小模型 TPOT 可差 3~5 倍）、控制输出长度 |
| **端到端 P95** | 从请求到**全部完成**的时间，取第 95 百分位 | "怎么还没好"（抱怨的都是这个）| 减少步数、并行工具调用、缓存、流式（缓解观感）|

它们的关系很简单：

```text
端到端 ≈ TTFT + TPOT × 输出 token 数          （单轮）
端到端 ≈ Σ(每步 TTFT + 该步输出 × TPOT) + Σ 工具耗时   （Agent，N 步）
```

**在 Agent 里，TTFT 每步都要付一次——这是最容易被忽略的一条。** 一个 8 步的任务，每步 TTFT 0.9 秒，光"等模型开口"就 7.2 秒；如果每步平均输出 120 token、TPOT 25 毫秒，再加 24 秒；工具 8 次共约 3 秒。合计约 34 秒——**而用户感知到的"卡"，40% 来自那 7.2 秒的 TTFT 累积。**

代入一组具体数字对比：

| 场景 | TTFT | TPOT | 输出 token | 端到端 |
|---|---|---|---|---|
| 单轮问答（大模型）| 0.9s | 45ms | 300 | 0.9 + 13.5 = **14.4s** |
| 单轮问答（小模型）| 0.3s | 12ms | 300 | 0.3 + 3.6 = **3.9s** |
| 8 步 Agent（大模型）| 8 × 0.9 | 25ms | 8 × 120 | 7.2 + 24 + 3 = **34.2s** |

两个结论直接可用：① **小模型不只是便宜，TPOT 常常快 3 倍以上**——简单的分类/抽取/摘要这类子任务交给小模型，端到端能省一半；② **Agent 的延迟是步数的函数**，把 8 步压到 5 步（更好的工具描述、更明确的收敛条件）比换模型更有效。

**为什么必须看 P95 而不是平均值？** 平均值 12 秒听上去还行，但如果 P50 是 8 秒、P95 是 45 秒，意味着**每 20 个用户就有 1 个等 45 秒**——他会在群里说"这玩意儿没法用"。优化顺序也是先看 P95：P95 长的原因通常是"少数请求走了异常路径"（重试、步数超限、大输入），而不是"整体慢"。

```python
def percentile(values, p):           # 不依赖 numpy，够用且能进 CI
    if not values:
        return 0.0
    data = sorted(values)
    idx = min(len(data) - 1, int(round((p / 100.0) * (len(data) - 1))))
    return data[idx]
```

### ⚠️ 常见坑

- **现象**：为了降延迟把 `max_tokens` 调到 256，结果模型被截断，任务完成率掉了 10 个点。**原因**：把"输出上限"当成了"性能开关"，忘了它也是质量开关。**怎么改**：`max_tokens` 按"这个任务最多需要多少字"设（例如 512~1024），别按"我想让它快点"设；先看 trace 里实际输出的 P95 长度再加 20% 余量。
- **现象**：把 system prompt 从 2000 token 精简到 800，TTFT 只降了 0.1 秒。**原因**：TTFT 主要由排队时间和 KV 计算的前几个 token 决定，**不是按输入长度线性增长**。**怎么改**：省 prompt 主要是省钱，不是省时间；要降 TTFT 优先看"首 token 前的排队/网络"和流式是否真的生效。
- **现象**：P95 忽高忽低，同一个改动两次跑的结果差一倍。**原因**：样本太少（几十次请求），P95 本身就是噪声。**怎么改**：至少几百次采样再谈 P95；样本不足时看 P90 + 最大值，并且记录"超时次数"这种计数型指标。

## 2. 流式输出：不只是"打字机效果"

### 2.1 为什么必须有

没有流式时，一个 14 秒的单轮回答，用户前 14 秒屏幕一片空白——**他分不清"在思考"和"已经挂了"**，会在第 8 秒刷新页面，于是你又多了一次请求、多一次成本，他还是没看到答案。流式把 TTFT 从 14 秒降到 0.9 秒，这是产品体验上最划算的一个改动。

实现上只有两种形态，原理都是"边生成边送出"：

```python
def stream_answer(messages, llm):
    """逐块 yield：服务端每收到一个 delta 就转发出去。"""
    for chunk in llm.stream_chat(messages):
        yield chunk                      # 上层可以是 SSE、WebSocket 或 CLI 的 print

# SSE（Server-Sent Events）格式：一条消息 = "data: <内容>\n\n"
def sse_format(text):
    return "data: %s\n\n" % text.replace("\n", "\\n")
```

HTTP 层用 SSE 就够了（`Content-Type: text/event-stream`），比 WebSocket 简单且能穿大多数代理。**关键工程细节**：关掉框架的响应缓冲（Flask 要 `Response(..., direct_passthrough=True)`，很多反向代理要 `X-Accel-Buffering: no`），否则你以为在流式，其实客户端等了 14 秒才一次性收到全文——**上线的第一件事就是拿 `curl -N` 验证流是真的在流**。

### 2.2 Agent 场景的特殊难点：工具调用时用户看到什么

普通对话应用流式很容易：把模型的话转出去即可。Agent 不行，因为它一半时间不在生成文字，而在调工具。**用户看到的是这样一段空白：**

```text
用户：帮我查一下杭州明天的天气，如果下雨提醒我带伞
[第 1 步：模型思考 1.2s] [工具 get_weather 1.8s] [第 2 步：模型思考 1.1s]
[工具 get_calendar 0.9s] [第 3 步：生成回答 3.4s]
→ 8.4 秒里，前 5 秒屏幕上什么都没有
```

**解法是流"状态"，而不只是流"文字"。** 把每一步的进展转成用户能读懂的一行：

```text
● 正在理解你的问题…
● 正在查询杭州天气（get_weather）…
● 明天有雨，正在检查你的日程…
● 正在整理建议…
```

具体做法有三种，可以叠加：

| 做法 | 实现 | 适合 | 注意 |
|---|---|---|---|
| **状态行** | 每步开始时 `yield` 一个事件（`{"type": "status", "text": "正在查询天气…"}`）| 所有 Agent | 状态文案要**面向用户**（"正在查询天气"），不要暴露工具名与参数 |
| **流式思考过程** | 把模型的 `content`（Thought）实时转出 | 开发工具、研究型 Agent | 用户看"我再想想…"会烦；建议折叠或默认收起 |
| **增量结果** | 把中间产物（已查到的 2 个来源）逐条推出去 | 检索/研究类 | 要保证"已推送的内容"不会被后续推翻（否则用户看到的是错的还看了 30 秒）|

事件流建议设计成一个统一的协议，客户端按 `type` 渲染：

```python
# 前端只需按 type 分支：status → 状态行；delta → 追加文字；tool → 折叠的工具卡
yield {"type": "status", "text": "正在查询天气…"}
yield {"type": "tool", "name": "get_weather", "ok": True, "summary": "杭州，明天中雨"}
yield {"type": "delta", "text": "明天杭州有中雨，"}
yield {"type": "done", "steps": 3, "cost_usd": 0.021, "elapsed_ms": 8420}
```

### 2.3 流式与结构化输出的冲突

**结构化输出（JSON）和流式天生矛盾**：JSON 只有在最后一个字符到达时才是合法 JSON，你没法把半个 JSON 解析出结果。三种务实做法：

1. **分阶段**：先流式输出自然语言部分（用户能读的那段），最后再输出一段结构化数据（用于程序处理）。用户等的是前者，程序等的是后者。
2. **工具调用不流式**：把结构化输出放进工具调用的参数里（第 03~04 章的 Function Calling），参数是完整返回的，天然不冲突。
3. **部分 JSON 解析**：只对"字段逐个完整"的场景做增量解析（如 `{"title": "...", "summary": "..."}` 中 `title` 一旦闭合就可用）。**不要为此自己写解析器**，除非确实需要——绝大多数场景用方案 1 就够。

**还有一个常见冲突**：你要在流式过程中做安全过滤或校验（第 12 章），但**一旦把 token 推给用户就收不回来了**。稳妥规则：**先流式的是"草稿态"内容，最终答案以 `done` 事件里携带的完整文本为准**；涉及危险动作（发邮件、付款）的确认，一律在非流式的独立步骤里做。

### ⚠️ 常见坑

- **现象**：本地流式正常，部署到 Nginx 后面变成"一次性返回"。**原因**：反向代理缓冲了响应。**怎么改**：`X-Accel-Buffering: no` + `proxy_buffering off`，并且用 `curl -N` 验证首字节时间（应该等于 TTFT，而不是端到端时间）。
- **现象**：用户在流式过程中关掉页面，服务端还在跑，白花钱。**怎么改**：监听连接断开（客户端取消），把取消信号传进 Agent 循环（每一步开始时检查 `cancelled`），并在 `finally` 里落 trace。**没有取消机制的流式接口，等于给用户一个免费的 DoS 按钮。**
- **现象**：工具调用时界面空白 5 秒，用户以为卡死狂点重试 → 并发翻倍 → 429。**怎么改**：状态行（2.2 节）+ 服务端幂等（第 4.4 节）+ 客户端按钮置灰。这三件事必须一起做，否则修一个漏一个。

## 3. 成本控制的七种手段

先看钱花在哪。一次典型的 Agent 任务（8 步、输入 12,000 token、输出 1,500 token，用大模型，价格按 2025–2026 年常见档位量级：输入 $3 / 1M、输出 $15 / 1M 计）：

```text
输入：12,000 token × $3 / 1M  = $0.036
输出： 1,500 token × $15 / 1M = $0.0225
单任务 ≈ $0.059  →  1000 任务/天 ≈ $58.5/天 ≈ $1,755/月
```

**输入占了 61%。** 这个比例决定了优化重点：**省输入比省输出重要，而省输入的第一手段是缓存和压缩，不是换模型。**

| # | 手段 | 怎么落到代码里 | 量级 | 代价 / 坑 |
|---|---|---|---|---|
| 1 | **模型分级路由**（routing）| 简单任务（分类、抽取、改写）走小模型，复杂推理走大模型 | 小模型输入/输出价可低 **10~25 倍** | 路由判错会把难题交给弱模型 → 完成率下降，必须用评测集验证 |
| 2 | **前缀缓存**（prompt caching）| system prompt + 工具 schema 放**最前面**且保持不变 | 命中部分输入按 **10%~50%** 计价 | 前缀必须**逐字节一致**；把时间戳/用户 ID 插到 system 开头会让缓存 100% 失效 |
| 3 | **历史压缩**（第 07 章）| 超过预算就把早期对话摘要成一段 | 20 轮对话 15k token → 摘要 1.5k，**降 90%** | 摘要会丢细节（数字、ID）；压缩后要用正则校验关键实体还在 |
| 4 | **输出长度限制** | `max_tokens` 按任务设（512~1024），并在 prompt 里说清"用要点回答" | 限制最坏情况；输出是最贵的一项（单价比输入贵 5 倍）| 设太小会截断 → 完成率掉 |
| 5 | **结果缓存** | 相同请求直接返回上次答案（第 5 节）| 客服/FAQ 场景命中率 **15%~40%**，成本直接归零 | 时效性与个性化问题不能缓存 |
| 6 | **批处理** | 离线任务走 Batch 接口（不要求实时）| 常见 **5 折**，且不占用在线配额 | 延迟以小时计，无法交互 |
| 7 | **预算熔断** | 单任务 / 单用户 / 每日总额三级上限，超限立刻停 | 把"最坏情况"从无限变成有界（如 $0.5 / $2 / $100）| 要防止误伤（正常任务被截断时要给用户可理解的提示）|

**为什么"前缀缓存"要求 system prompt 放在最前面？** 缓存是按"从第一个 token 开始的最长公共前缀"命中的——你的 messages 顺序是 `system → 历史 → 当前问题`，那么每一轮变化的部分都在最后，前面那一大段（system + 工具 schema，通常 1~3k token）就能被复用。反过来，如果你把 `当前时间：2026-09-20 10:03:21` 写进 system 的第一行，**整段前缀每次都不同，缓存命中率归零**。同理，工具 schema 的顺序要稳定（别用无序的 `set` 生成），用户 ID 要放在后面而不是 system 里。

**把七种手段叠加后看账单**（同一个日均 1000 任务的助手）：

```text
基线（全走大模型，无优化）                        $58.5/天
+ 分级路由：60% 简单任务走小模型（$0.002/次）      -$32.4  →  $26.1
+ 前缀缓存：命中的 30% 输入按 0.1 计价             -$4.9   →  $21.2
+ 历史压缩：复杂任务的输入从 12k 压到 6k           -$10.6  →  $10.6
+ 结果缓存：命中率 20%，直接返回                    -$2.1   →  $8.5
+ 离线任务走 batch（占 30%，5 折）                 -$1.3   →  $7.2
→ 从 $58.5/天 降到约 $7.2/天（-88%），且完成率不变（前提：每一步都用评测集验证过）
```

**注意最后一句话**：上面每一步都可能伤完成率。正确顺序是"**先用评测集把基线固定住，再逐项打开并复测**"，而不是一口气全开——否则你分不清是哪个手段导致了退化。

### ⚠️ 常见坑

- **现象**：加了语义/前缀缓存后，成本降了但用户开始收到过期答案（"昨天的价格"）。**原因**：缓存的 key 里没有版本与时间维度。**怎么改**：缓存 key 必须包含**模型版本 + prompt 版本 + 工具版本**，时效性内容单独设 TTL 或干脆不缓存（第 5 节）。
- **现象**：`max_tokens` 设了 4096，模型经常写 3000 字，成本比预期高 3 倍。**原因**：模型会"填满"给它的空间。**怎么改**：按任务设小上限 + prompt 明确格式（"用 5 条以内要点回答"）；在输出层做**截断+重试**而不是给大空间。
- **现象**：预算熔断设成"单任务 $0.1"，结果复杂任务跑到一半被砍，用户只看到"任务失败"。**怎么改**：熔断分级（单步/单任务/单用户/全局），并且**在接近上限前给提示**（"本次任务已达预算上限，已完成 70%"），而不是静默失败。

## 4. 可靠性：超时、重试、降级、幂等

### 4.1 每一层都要有超时

**原则：内层超时必须短于外层**，否则外层先死，你拿到的错误是"整个任务超时"，而真正的凶手（某个卡住的工具）藏在一层之下。

| 层 | 建议值 | 说明 |
|---|---|---|
| 客户端总超时（用户愿意等多久）| 60~120 秒（长任务用异步 + 轮询/SSE）| 超过就要有进度反馈，否则用户会刷新 |
| 单次 LLM 调用 | 30 秒（流式用 **空闲超时** 10 秒：只要还在出字就不算超时）| 流式的正确超时口径是"多久没有新 token"，不是"总共多久" |
| 工具调用 | 本地 5 秒 / 网络 15 秒 | 工具必须有超时，否则一次卡死拖垮整个任务 |
| 向量检索 / 数据库 | 2 秒 / 1 秒 | 这两层通常很快，慢了说明是故障不是慢 |
| 重试总预算 | 不超过客户端总超时的 1/3 | 否则重试还没跑完，用户已经走了 |

```python
import signal

def with_timeout(fn, seconds, *args, **kwargs):
    """POSIX 最小实现；生产建议用线程池或支持 timeout 的客户端（如 httpx）。"""
    def handler(signum, frame):
        raise TimeoutError("调用超过 %s 秒" % seconds)
    old = signal.signal(signal.SIGALRM, handler)   # Windows 上不可用，见下方说明
    signal.alarm(seconds)
    try:
        return fn(*args, **kwargs)
    finally:
        signal.alarm(0)
        signal.signal(signal.SIGALRM, old)
```

**Windows 兼容提醒**：`signal.SIGALRM` 在 Windows 上不存在（`AttributeError`）。跨平台做法是给每个调用配上支持 timeout 的客户端参数（`timeout=15`），或者用 `concurrent.futures.ThreadPoolExecutor` + `future.result(timeout=15)`——**代码里看到 `signal.alarm` 就要警觉**，这是最常见的"Linux 能跑、Windows 报错"来源。

### 4.2 重试：什么该重试，什么不该

| 该重试 | 不该重试 |
|---|---|
| 429（限流）、408（请求超时）| 400（参数错）、422（校验失败）|
| 500 / 502 / 503 / 504（服务端临时故障）| 401 / 403（认证、权限——**重试 100 次都一样**）|
| 网络连接超时、连接被重置 | 404（资源不存在）|
| 上游明确返回"稍后重试" | 内容审核拒绝（模型不会因为重试就同意）|
| | JSON 解析失败（同样输入会同样失败 → 该改 prompt/加 schema 校验）|

```python
import random, time
RETRYABLE = {408, 429, 500, 502, 503, 504}

def backoff_delay(attempt, base=0.5, cap=8.0):
    """指数退避 + 抖动：50%~100% 的随机化，避免同时重试把上游打死。"""
    return min(cap, base * (2 ** attempt)) * (0.5 + random.random() * 0.5)

def call_with_retry(fn, max_attempts=4):
    for attempt in range(max_attempts):
        try:
            return fn()
        except Exception as exc:
            code = getattr(exc, "status_code", None) or getattr(exc, "code", None)
            if code not in RETRYABLE or attempt == max_attempts - 1:
                raise
            time.sleep(backoff_delay(attempt))
```

**抖动（jitter）为什么是必须的？** 假设 1000 个客户端同时被限流，如果都老老实实"等 1 秒、2 秒、4 秒"，它们会在同一时刻再次一起冲上去（惊群 / thundering herd），把上游打死。加上 50%~100% 的随机抖动后，重试被打散到时间轴上——**这一行 `random.random()` 是可靠性工程里性价比最高的一行代码**。

### 4.3 降级：主模型挂了怎么办

降级链必须**提前设计并演练**，不能等出事再临时改：

```text
主模型（大） → 备用模型（另一家服务商） → 返回缓存答案（明确标注"可能是旧结果"）
           → 排队稍后重试（告知用户"当前繁忙，已加入队列"） → 明确失败（绝不静默编一个答案）
```

三条纪律：① **降级结果必须显式标记**（"当前为主模型不可用时的备用回答，质量可能下降"）——否则用户会把降级当正常，你的评测基线就废了；② **备用模型要提前跑过评测集**，否则你不知道它差在哪；③ **降级要记 trace 与指标**（降级率超过 1% 就该告警，说明主模型或你的容量有问题）。

### 4.4 幂等：重试不能重复扣款、重复发邮件

**这是 Agent 最容易造成真实损失的一类事故**：网络超时后重试，结果邮件发了两遍、订单下了两笔。核心做法是把"生成"和"执行"分开：

```python
def execute_once(action_id, arguments, do_it):
    """action_id = trace_id + 步骤序号，同一次任务里唯一。"""
    if done_actions.exists(action_id):        # 落库/落文件都行
        return done_actions.get(action_id)    # 已经执行过 → 直接返回上次结果
    result = do_it(**arguments)               # 真正的副作用只在这里发生一次
    done_actions.record(action_id, result)
    return result
```

配套规则：**写操作先落"意图"再执行**（`pending → done` 两态，崩溃后能判断该不该重发）；**给外部接口带上 `Idempotency-Key`**（多数支付/邮件 API 都支持）；**危险动作的重试一律改成人工确认**——重试按钮点两次就等于执行两次，这类"人肉触发"比代码重试更常见。

### ⚠️ 常见坑

- **现象**：日志里全是 `TimeoutError`，看不出是哪个环节慢。**原因**：超时错误没有携带层次信息。**怎么改**：**不要 raise 裸的 `TimeoutError`，要写清是谁超时**——`raise TimeoutError("工具 fetch_url 超过 15 秒")`；再配 trace 的 `latency_ms` 就能一眼定位。
- **现象**：上游返回 200 但 `body` 里是错误（很多网关这么干），重试逻辑完全没触发。**怎么改**：把"HTTP 状态码"和"业务错误码"分开判断，业务错误也要映射到可重试集合里。
- **现象**：重试把成本放大了 3 倍。**原因**：每次重试都付一次完整的 token 钱，而重试通常发生在最贵的路径上（长上下文）。**怎么改**：给重试设总预算（次数 + 金额），并把"重试率"当成核心指标监控；重试率超过 5% 应该去修根因，而不是加大重试次数。

## 5. 缓存的分层：从精确匹配到语义缓存

| 层 | 命中依据 | 命中率（经验）| 风险 | 建议 |
|---|---|---|---|---|
| **L1 精确匹配** | `hash(模型 + prompt 版本 + 工具版本 + messages 规范化)` | 客服/FAQ 类 15%~40%；工具类低于 10% | 几乎为零 | **无条件先上这一层** |
| **L2 语义缓存** | 问句 embedding 相似度 ≥ 阈值 | 在 L1 之上再加 10%~25% | **高**（见下）| 只对无状态、无个性化、非时效的问题开 |

**L1 的 key 必须包含什么？** 少了任何一项都会返回错误答案：

```python
def cache_key(model, prompt_version, tools_version, messages, temperature):
    material = "|".join([model, prompt_version, tools_version, str(temperature),
                         json.dumps(messages, ensure_ascii=False, sort_keys=True)])
    return hashlib.sha256(material.encode("utf-8")).hexdigest()
```

注意几个细节：`temperature > 0` 时严格说不该缓存（同样的输入本来就该有不同的输出），实务上按 `temperature == 0` 才缓存；`messages` 要 `sort_keys=True` 规范化（否则字段顺序变化会制造假 miss）；`prompt_version` / `tools_version` 是**改动后自动失效的开关**——改了 prompt 忘了清缓存，是"改了没生效"类 bug 的头号原因。

**L2 语义缓存的四个风险**，每一个都有真实翻车案例：

1. **问句相近但答案不同**："能不能退款" vs "能不能退货"（cos 相似度可能 0.94）——业务规则完全不同；
2. **时效性**：昨天的价格、上周的库存；
3. **个性化**："我的订单到哪了"——不同用户问句几乎一样，答案只属于提问者；
4. **阈值玄学**：阈值设 0.90 命中率高但错得多，设 0.98 几乎不命中；**没有评测集就不要调这个参数**。

所以规则是：**只对"知识型、无状态、无个人信息、非时效"的问句开语义缓存**（例如产品功能怎么用、政策是什么），阈值从 0.97 起步，命中后仍然要过一遍轻量校验（把缓存命中的原问题和当前问题一起给模型判断"是否同一个意思"，比直接返回便宜得多）。个性化问题（订单、余额、日程）永远不走语义缓存，只走 L1 或直接回源。

### ⚠️ 常见坑

- **现象**：缓存上线后"改了 prompt 却没生效"，排查半小时。**原因**：key 里没有 prompt 版本。**怎么改**：把 `prompt_version` 做成配置项，每次改 prompt 手动 +1（或者用 prompt 内容的 hash，自动且不会忘）。
- **现象**：缓存把"失败结果"也存了，用户接下来 10 分钟都收到同一个错误。**怎么改**：**只缓存成功结果**；错误结果可以短 TTL 缓存（如 10 秒）用来挡重试风暴，但要标记为错误。
- **现象**：语义缓存命中率很高但投诉变多。**原因**：阈值太低。**怎么改**：把命中的"原问题/新问题"记进 trace 抽样人工看 50 条——**这是唯一能发现"输错答案"的方法**，光看命中率只会让你越调越低。

## 6. 发布形态：CLI、Web API、后台任务、机器人

| 形态 | 适合 | 优点 | 特有的坑 |
|---|---|---|---|
| **CLI** | 自己用、运维脚本、批处理 | 零基础设施；`input()` 就是现成的确认界面（第 12 章）| 无并发概念；长任务要能中断（Ctrl+C 后要落 trace）|
| **Web API** | 给产品/前端集成 | 通用、可鉴权、可限流 | 长任务会撞网关超时 → 必须异步化 + 轮询/SSE；要限流、要鉴权、要 CORS |
| **后台任务** | 离线批处理、定时任务 | 能用 batch 接口省钱；失败可重跑 | 需要队列与重试（别自己写，用现成的）；任务状态要可查 |
| **机器人**（Slack / 飞书 / 企业微信）| 团队内部使用 | 触及率高，天然有身份与权限 | 消息长度限制（常见 4000 字符，需要分片）；确认交互靠卡片或"回复确认"；平台有审核与限速 |

**Web API 的最小骨架**（FastAPI 是可选依赖，离线跑 `ch13_deploy.py` 不需要它）：

```python
# pip install fastapi uvicorn —— 可选；没装也不影响 `python ch13_deploy.py` 跑通
try:
    from fastapi import FastAPI, HTTPException
    from fastapi.responses import StreamingResponse
    app = FastAPI()

    @app.post("/chat")
    def chat(req: dict):
        budget = Budget(limit_usd=0.5, per_user_usd=2.0)      # 第 3 节的预算熔断
        if not budget.allow(req.get("user_id")):
            raise HTTPException(status_code=429, detail="已达预算上限，请稍后再试")
        return StreamingResponse(stream_answer(req["messages"]), media_type="text/event-stream")
except ImportError:      # 没装 fastapi 时这段跳过，其余功能（缓存/重试/统计）照常可用
    app = None
```

三个骨架层面的必做项：**鉴权**（谁在调用）、**限流**（每分钟每用户多少次）、**异步化**（长任务返回 `task_id`，客户端轮询 `/tasks/{id}`）。短任务（<30 秒）可以直接同步 + SSE。

### ⚠️ 常见坑

- **现象**：API 上线后同一个用户连点 5 次，跑了 5 个任务花了 5 份钱。**怎么改**：客户端置灰 + 服务端幂等键（同一用户 + 同一输入在 30 秒内只跑一次）+ 每用户并发上限 1。
- **现象**：机器人里输出被平台截断成 3 条消息，用户看不懂。**怎么改**：按段落/语义分片（不要按字符数硬切），每片带序号；结构化结果改用卡片或文件附件。
- **现象**：后台任务失败后没人知道。**怎么改**：任务状态落库 + 失败告警（哪怕只是发一条消息给自己）；**没有告警的后台任务等于没有后台任务**。

一次示例输出（mock）：

```text
============ 部署自检报告（12 次任务）============
TTFT  P50 0.42s  P95 0.98s      端到端 P50 6.8s  P95 21.4s
缓存  L1 命中 3/12 (25.0%)  L2 命中 1/12  节省 $0.014
重试  2 次（均因 HTTP 503，退避 0.6s / 1.3s）  重试率 16.7% ⚠️
成本  $0.0186/任务  $/完成任务 $0.0216  累计 $0.223 / 预算 $5.00
熔断  触发 0 次；预算使用 4.5%
流式  首事件 0.42s，状态行 4 条，末事件 done（steps=3, cost=$0.019）
==============================================
```

**读这份报告的三个要点**：① **TTFT 和端到端必须分开看**——TTFT 0.42 秒说明流式生效，端到端 P95 21.4 秒说明任务本身重（步数/工具慢），两者的优化手段完全不同；② **重试率 16.7% 是危险信号**——说明上游不稳或你的超时设得太紧，这不是"重试机制在工作"，是根因没修；③ **预算用掉 4.5% 但缓存省下 $0.014**——缓存和熔断是两个方向的事：前者降均值，后者控尾部，都要有。

### ⚠️ 常见坑

- **现象**：脚本里 `Budget` 只在开头检查一次，任务跑到一半超支了。**怎么改**：在**每一步**（每次 LLM 调用前）检查累计花费，而不是只在入口检查一次。
- **现象**：mock 模式下流式的 `time.sleep` 让脚本跑得很慢。**怎么改**：mock 下的 sleep 要短（0.05 秒级）或跳过——测试的是**事件顺序与格式**，不是真实速度；真实延迟要在线测。

## 本章小结

1. **"本地好好的"骗人**：并发、超时、成本三件事只在多用户 + 长任务 + 真实网络下暴露；线上输入分布还会让成本成倍放大。
2. **延迟分三个指标**：TTFT（首字，靠流式 + 前缀缓存 + 精简 prompt）、TPOT（每 token，靠模型选择与输出长度）、端到端 P95（用户真正抱怨的）。**Agent 里 TTFT 每步都要付一次**，8 步就是 8 次。
3. **P95 才是体感**，平均值会骗人；样本太少时 P95 本身就是噪声，要几百次采样再谈。
4. **流式不只是打字机效果**：它把"14 秒空白"变成"0.9 秒有反应"。Agent 还要流**状态**（正在查天气…），否则用户卡在工具调用的那 5 秒里。上线的第一件事是用 `curl -N` 证明流是真的在流（反代缓冲是头号杀手）。
5. **流式与结构化输出天生冲突**：分阶段（先自然语言、后结构化）、放进工具参数、或做部分 JSON 解析；**推出去的内容收不回来**，所以危险动作的确认一定要放在非流式的独立步骤里。
6. **成本七手段**：模型分级路由、前缀缓存、历史压缩、输出限制、结果缓存、批量处理、预算熔断。输入通常占大头，**省输入靠缓存与压缩，不靠换模型**；前缀缓存的前提是 system prompt 在最前面且稳定。
7. **叠加后账单能降一个数量级**（示例 $58.5/天 → $7.2/天），但**每一步都可能伤完成率**，必须用评测集逐项验证。
8. **可靠性四件事**：每层超时（内层 < 外层）、重试只覆盖可重试错误（指数退避 + 抖动）、降级链显式标注、副作用操作幂等（生成与执行分离）。
9. **缓存分两层**：L1 精确匹配（key 必须含模型/prompt/工具版本）无条件先上；L2 语义缓存只对无状态、无个性化、非时效的问题开，阈值从 0.97 起。
10. **发布形态四选一**：CLI（自己用）、Web API（集成，注意长任务异步化）、后台任务（离线省钱）、机器人（团队，注意分片与确认交互）。
11. **上线前逐项打勾**：延迟、成本、可靠性、安全合规、运维五组清单——任何一项没有，就先别给别人用。
12. **关联阅读**：[[02-Wiki/专题总结/09-部署成本与性能]]、[[02-Wiki/速查表/02-Token与成本速查]]。

## 动手练习

**练习 1（量出你的 TTFT 与 TPOT）**：给 `ch13_deploy.py` 的流式函数加上计时，分别记录"发出请求 → 第一个 chunk"和"第一个 chunk → 结束"，输出 TTFT / TPOT / 端到端三个数。然后把 system prompt 从 1k token 加到 3k，再测一次，看三者各自变化多少。
*目标：亲手验证"prompt 变长主要影响成本，对 TTFT 影响有限"这条反直觉的结论。*

**练习 2（故意打死重试）**：把 mock 的失败率调高（模拟 50% 返回 503），先跑通"重试全部成功"，再把重试次数从 4 改成 1，对比两次的**完成率与总成本**；然后把抖动去掉（`random.random()` 换成固定 1.0），观察重试的时间分布。
*目标：理解"重试不是免费的"——它同时抬高成本、放大尾部延迟，抖动只是缓解不是解药。*

**练习 3（给任务加预算熔断并造一次超支）**：给 `Budget` 加上"单任务 $0.02"的限制，然后构造一个会跑很多步的任务，观察它在第几步被拦下、给出什么提示、trace 里记了什么。再把上限调到合理值，让任务跑完。
*目标：体验熔断的三个设计点——**在哪一层检查、超限时怎么告诉用户、trace 里怎么复盘**。*

## 自测题

**1. TTFT、TPOT、端到端 P95 分别是什么？各自的优化手段是什么？**

<details><summary>点击查看答案</summary>

**TTFT**（Time To First Token）：请求发出到第一个 token 到达，用户感知是"它有没有开始干活"；优化手段是流式输出、精简 prompt、**前缀缓存**、更快的模型。**TPOT**（Time Per Output Token）：生成阶段每个 token 的平均时间，靠选择更快的模型（小模型可快 3~5 倍）与控制输出长度来优化。**端到端 P95**：从请求到全部完成、取第 95 百分位——**用户抱怨的就是这个**；靠减少步数、并行工具调用、缓存来优化。

关系式：单轮 `端到端 ≈ TTFT + TPOT × 输出 token`；Agent 是 `Σ(每步 TTFT + 该步输出 × TPOT) + Σ 工具耗时`。**Agent 里 TTFT 每步都要付一次**，这是最容易被忽略的一点。

</details>

**2. 为什么必须看 P95 而不是平均值？**

<details><summary>点击查看答案</summary>

因为用户的抱怨来自尾部。平均值 12 秒听上去还行，但 P50 是 8 秒、P95 是 45 秒意味着**每 20 个用户就有 1 个等 45 秒**，他会在群里说"这玩意儿没法用"。

P95 长通常说明"少数请求走了异常路径"（重试、步数超限、超大输入），这和"整体慢"是两种完全不同的病：整体慢要优化每一步，尾部慢要找出那条异常路径（trace 能直接定位）。

注意**样本量**：几十次请求算出来的 P95 是噪声，至少要几百次采样；样本不足时看 P90 + 最大值，并单独统计超时次数这类计数指标。

</details>

**3. Agent 场景下流式输出的特殊难点是什么？**

<details><summary>点击查看答案</summary>

难点是**一半时间不在生成文字**：模型思考 + 工具执行期间没有文字可流，用户面对 5 秒空白，以为卡死而刷新或狂点重试，反而制造更多请求。解法是**流"状态"而不只是流"文字"**：每一步开始 yield 一个 `status` 事件（"正在查询天气…"），工具完成后 yield 一条可折叠的 `tool` 摘要，文字用 `delta`，最后 `done` 携带步数与成本——前端按 `type` 分支渲染。

另外三个坑：① **反向代理缓冲**会让流式退化成一次性返回，必须用 `curl -N` 验证首字节时间；② **结构化输出（JSON）与流式天生冲突**，务实做法是分阶段（先自然语言后结构化）或把结构化放进工具参数；③ **推出去的内容收不回来**，所以危险动作的确认必须在非流式的独立步骤里做，而且必须支持客户端取消（否则等于给用户一个免费的 DoS 按钮）。

</details>

**4. 哪些错误该重试，哪些不该？为什么必须加抖动？**

<details><summary>点击查看答案</summary>

**该重试**：429（限流）、408、500/502/503/504、网络连接超时/被重置。**不该重试**：400（参数错）、401/403（认证与权限——重试 100 次都一样）、404、422（校验失败）、内容审核拒绝（模型不会因为重试就同意）、JSON 解析失败（同样输入会同样失败，应该改 prompt 或加 schema 校验）。

**抖动（jitter）**：把退避时间乘上 50%~100% 的随机因子。原因是防止惊群——1000 个客户端同时被限流，若都严格等 1s/2s/4s，它们会在同一时刻再次一起冲上去把上游打死；随机化把重试打散在时间轴上。**这一行 `random.random()` 是可靠性工程里性价比最高的一行代码。**

补充：重试要设总预算（次数 + 金额），并把**重试率**当核心指标——重试率超过 5% 说明根因没修，而不是"重试机制在工作"。

</details>

**5. 语义缓存有什么风险？你会怎么设置它的使用边界？**

<details><summary>点击查看答案</summary>

**四个风险**：① **问句相近但答案不同**——"能不能退款" vs "能不能退货"（相似度可能 0.94），业务规则完全不同；② **时效性**——昨天的价格、上周的库存；③ **个性化**——"我的订单到哪了"几乎人人一样，但答案只属于提问者；④ **阈值玄学**——阈值低则错得多，高则几乎不命中，没评测集就不要调这个参数。

**使用边界**：只对**知识型、无状态、无个人信息、非时效**的问句开（产品功能怎么用、政策是什么）；阈值从 **0.97** 起步；命中后仍要过一遍轻量校验（把缓存命中的原问题与当前问题一起交给模型判断是否同义）；个性化问题（订单/余额/日程）永不走语义缓存，只走 L1 精确缓存。

另外：**L1 精确缓存的 key 必须包含模型 + prompt 版本 + 工具版本**（少一项就会返回错误答案），`temperature > 0` 时不该缓存，只缓存成功结果并定期抽样人工看命中日志——这是唯一能发现"输错答案"的方法。

</details>

## 结语与下一章

部署这件事，有点像把只在自家厨房里做过的菜端到饭店里卖：配方没变，但你得同时应付十桌客人、突然迟到的供应商和吃了一半要退单的人——**本地能跑只是及格线，能被别人用才算交付。**

但你会发现一个尴尬的事实：**这些能力在你的代码里是重复的**——第 05 章写过一遍 Agent 循环，第 11 章又写了一遍，本章的流式与预算逻辑还要再写一遍；工具注册、消息裁剪、trace 记录也在各处抄来抄去。

第 14 章 [[docs/第14章 构建你自己的Agent框架]] 是全书的技术收束：把这些散落的能力抽象成一个 400 行左右的 mini harness——LLM 客户端层、Tool Registry、Agent Loop、上下文管理、Memory、Session 持久化、Trace、Permission Gate、Sub-agent 九个模块；讲清每一个"没有它会怎样"、什么时候该抽象什么时候是过度设计、接口该窄还是宽、状态该放在哪；最后和 LangGraph / OpenAI Agents SDK 的真实抽象做对比，说明它们的取舍与你的差距。
