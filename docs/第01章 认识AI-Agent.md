# 第01章 认识AI-Agent

> **本章目标：** 分清 Chatbot / Workflow / Agent / Multi-Agent 四种形态，并知道什么时候**不该**用 Agent。
> **预计用时：** 2.5 小时　**前置章节：** 第00章　**配套代码：** `code/ch01_first_call.py`

## 0. 开篇：一个真实的问题

前段时间有个学员面试 AI 应用岗，简历上写了一个"智能客服 Agent"。那是他实习时做的项目，起因是客服主管的一句话："我们有 3 个人每天花 2 小时整理客户邮件 —— 看内容、查订单、写回复草稿。能不能用 AI 自动做掉？"

> **面试官：** 你这个 Agent 和普通客服机器人有什么区别？
>
> **他：** 我们用了更强的大模型，能理解客户邮件，还能多轮对话，还会自己查订单。
>
> **面试官（继续追问）：** 那它有没有自己决定下一步做什么？同一封邮件，今天是 3 步做完，还是明天绕了 7 步？如果步骤是你写死的，为什么要叫 Agent？如果真是它自己决定的，你又怎么验收、一封邮件多少钱？

这下就卡住了 —— 同样的问题，客服主管三周前刚问过他一遍。

他的经历是这样的：

- **第 1 周**：跑通了 Demo。给模型几个工具（查订单、查政策、写草稿），它能自己决定先查什么。演示时效果惊艳。
- **第 2 周**：开始出问题。同一封邮件，今天 3 步做完，明天绕了 7 步；有 12% 的邮件它反复调用同一个工具，直到你加的步数上限把它拦下来。
- **第 3 周**：主管问"准确率多少、一封邮件多少钱、出错怎么办"，他答不上来。项目被叫停，换成了一个"读邮件 → 分类 → 按模板生成草稿 → 人工确认"的固定流程，两天写完，准确率反而更高。

这类问题很常见。很多简历上写了 Agent，讲出来还是一个 ChatBot；很多团队上了 Agent，最后发现用 Workflow 两天就能写完，还更稳。

这里的问题不在于 Agent 不好，而在于**你跳过了一个判断**：这件事到底该用哪种形态来做？

所以这一章把这条边界讲清楚。本章要给你两样东西：一张能分清四种形态的图，和一份"什么时候不该用 Agent"的决策清单。**知道边界比会调 API 更值钱** —— 因为在真实项目里，选错架构的代价是几周时间，选错参数的代价是几块钱。

## 1. 四种形态：Chatbot / Workflow / Agent / Multi-Agent

### 1.1 一个业务，四种做法

我们用"每天整理客户邮件"这一个业务贯穿全章。任务背景：

```text
输入：一封客户邮件（可能包含订单号、退货诉求、物流催单、投诉）
输出：一封可以直接发给客户的回复草稿 + 处理建议
约束：每天约 300 封；出错要被人工拦下来；每封处理成本要低于 0.05 元
```

四种形态的差别，不在于用了什么模型，而在于 **"下一步做什么"这个决定由谁来下**：人、代码、还是模型。

### 1.2 形态一：Chatbot —— 模型只出文本，动作由人执行

```python
from common.llm import chat

email_text = "订单 DP1002 六天了还没发货，我要退款！"
answer = chat(
    "你是客服助手。请给出一封礼貌的回复草稿，并列出你需要核实的信息。\n\n" + email_text
)
print(answer)          # 人看完，自己决定怎么发
```

- **谁决定下一步**：人。模型只是把你的输入变成更可用的文本。
- **优点**：立刻能用，零集成风险。
- **缺点**：3 个人还是每天花 2 小时 —— 因为"查订单""翻政策""写进系统"全是人做的。
- **判断信号**：如果人愿意自己动手执行，且量不大，Chatbot 就够了，不要过度设计。

### 1.3 形态二：Workflow —— 流程写死在代码里，模型只做其中一步

```python
def daily_email_workflow(emails):
    result = {"total": len(emails), "drafted": 0, "to_human": 0}
    for mail in emails:
        label = chat(                       # 模型只负责"分类"这一步
            "只回答一个词：退款 / 物流 / 投诉 / 其他。\n邮件：" + mail["body"],
            temperature=0,
        ).strip()
        if label == "退款":
            draft = chat("按退款话术写回复草稿：\n" + mail["body"], temperature=0.3)
        elif label == "物流":
            draft = chat("按物流话术写回复草稿：\n" + mail["body"], temperature=0.3)
        else:
            draft = None                    # 认不出来的，交给人工
            result["to_human"] += 1
        if draft:
            save_draft(mail["id"], draft)   # 写回系统，这是普通代码
            result["drafted"] += 1
    return result
```

- **谁决定下一步**：代码。步骤、分支条件、结束条件全是 `if/elif/for` 写死的。
- **优点**：可预测、可测试、成本固定（每封信固定 2 次调用）、出错能复现。
- **缺点**：流程变复杂时会变成一大坨 `if`；遇到"这封信既问退款又问物流"这种交叉情况就抓瞎。
- **关键认识**：**Workflow 里也可以有模型，而且往往是性价比最高的用法** —— 模型只做它擅长的模糊判断（分类、改写），其余交给确定性的代码。

### 1.4 形态三：Agent —— 模型决定下一步

```python
from common.llm import get_llm
from common.tools import Tool, ToolRegistry

registry = ToolRegistry()
registry.register(Tool("search_order", "按订单号查询订单状态",
                       {"type": "object", "properties": {"order_id": {"type": "string"}},
                        "required": ["order_id"]}, search_order))
registry.register(Tool("get_policy", "查询售后政策",
                       {"type": "object", "properties": {"topic": {"type": "string"}},
                        "required": ["topic"]}, get_policy))
registry.register(Tool("save_draft", "把回复草稿写入工单系统",
                       {"type": "object", "properties": {"ticket_id": {"type": "string"},
                                                          "content": {"type": "string"}},
                        "required": ["ticket_id", "content"]}, save_draft,
                       requires_confirmation=True))          # 有副作用的工具要人工确认

def email_agent(mail, max_steps=8):
    llm = get_llm(temperature=0.2, system="你是客服处理助手。先查事实，再写草稿；查不到就转人工。")
    messages = [{"role": "user", "content": mail["body"]}]
    for _ in range(max_steps):
        resp = llm.chat(messages, tools=registry.to_openai_schema())     # think
        messages.append({"role": "assistant", "content": resp["content"],
                         "tool_calls": resp["tool_calls"]})
        if not resp["tool_calls"]:
            return resp["content"]                                       # 停止：不再请求工具
        for call in resp["tool_calls"]:                                  # act
            output = registry.execute(call["name"], call["arguments"])
            messages.append({"role": "tool", "tool_call_id": call["id"], "content": str(output)})
    return "达到步数上限，转人工处理"                                     # 停止：兜底
```

- **谁决定下一步**：模型。它自己判断"要不要先查订单""查到未发货 6 天后要不要去查政策""够不够写下草稿了"。
- **优点**：能处理事前枚举不完的分支 —— 这是 Workflow 做不到的。
- **缺点**：每次调用的轮数不定，成本、延迟、结果都不确定；调试要看完整轨迹。
- **判断信号**：只有"下一步取决于上一步的结果，而且这种依赖组合事先说不清"时，Agent 才划算。

> 上面这段代码用到的 `tools=` / `tool_calls` / `ToolRegistry` 是第 04、05 章的内容。现在你只需要看懂**结构**：一个 `for` 循环里，模型决定"要不要调工具、调哪个"，代码负责"真的去调"。

### 1.5 形态四：Multi-Agent —— 多个角色分工

当一封邮件里混杂多种诉求（退款 + 投诉 + 要求补偿），或者"写手"和"审核员"的目标天然冲突时，用一个 prompt 同时约束所有目标会互相打架。做法是拆成多个角色：

```text
分类员（temperature=0，只有分类工具）
   └→ 退款组：写手（语气亲和，负责写草稿）+ 审核员（检查合规：不能承诺具体到账时间）
   └→ 投诉组：写手 + 审核员（检查是否触发了升级条件）
   └→ 都拿不准 → 人工队列
```

- **谁决定下一步**：多个模型各管一段，用固定的编排代码串起来（所以它其实是 "Workflow + 多个 Agent"）。
- **代价**：调用次数是单 Agent 的 2–3 倍；角色之间会互相甩锅（"我按审核意见改了，审核又说不行"）；必须给每个角色设独立的停止条件。
- **判断信号**：只有当**职责边界真的冲突**（一方要写得让客户满意，另一方要拦合规风险）时，拆角色才有收益。为了"看起来高级"而拆，只会让系统更难调试。

### 1.6 四者对比

| 维度 | Chatbot | Workflow | Agent | Multi-Agent |
|------|---------|----------|-------|-------------|
| 谁决定下一步 | 人 | 代码 | 模型 | 多个模型各管一段 |
| 单封邮件调用次数 | 1 | 2（固定） | 3–10（不定） | 6–20 |
| 结果可预测性 | 低（人兜着） | 高 | 中 | 中低 |
| 典型出错方式 | 答得不好 | 分类错 → 草稿错 | 选错工具、绕圈、超预算 | 角色间循环、互相否决 |
| 调试方式 | 看输出 | 看日志 | 看完整 trace | 看 trace + 角色时序 |
| 开发成本 | 1 小时 | 1 天 | 3 天起 | 1 周起 |
| 什么时候选它 | 人愿意自己动手 | 步骤能画成流程图 | 分支说不清、依赖中间结果 | 职责真的冲突 |

**记住这一行：Agent 不是"更聪明的 Workflow"，而是把决策权交给了模型。** 交出去的是灵活性，换回来的是不确定性 —— 这笔交易只在特定场景下划算。

### ⚠️ 常见坑

- **现象：把一个 `if/elif` 写成 prompt，叫它"Agent"。** 比如"请判断这是退款还是物流，然后按对应模板回复" —— 这本质是 Workflow，用 prompt 实现反而更难测、更贵。改法：能写成 `if` 的就写 `if`，把模型用在模糊判断上。
- **现象：Workflow 稳定跑了一个月，突然某天分类结果全错。** 原因：服务商悄悄更新了模型版本，或你把 `temperature` 从 0 改成了 0.7。改法：生产环境固定模型名（别用 `latest` 之类的别名）、分类任务 `temperature=0`，并留一份固定的评测样本（第 12 章）。
- **现象（多智能体）：两个 Agent 互相"已阅，请修改"。** 原因：没有定义"谁有最终决定权"。改法：给审核员一票否决权，或者设最大往返轮数（2 轮），超过就转人工。
- **现象：Agent 用的工具里包含"直接发邮件给客户"。** 风险：模型判断失误就直接对外发信，无法撤回。改法：有副作用的工具加 `requires_confirmation=True`（第 12 章讲完整的权限门设计），默认只产出草稿。

## 2. Agent 的基本循环：observe → think → act → observe

### 2.1 手工模拟一个 Agent 循环

在写任何框架代码之前，我们先手工跑一遍循环 —— 用 `while`/`for` + 假数据，把每一步都打印出来。**这段代码里没有模型，但循环的形状和真实 Agent 完全一样。**

```python
"""手工模拟 Agent 循环：observe → think → act → observe。不用任何框架。"""

FAKE_ORDERS = {
    "DP1001": {"status": "已发货", "days": 2},
    "DP1002": {"status": "未发货", "days": 6},
}
FAKE_POLICY = {"未发货超过 5 天": "可以无条件退款，无需客户举证"}

def tool_search_order(order_id):
    """工具 1：查订单。真实项目里这是一次 HTTP 请求。"""
    return FAKE_ORDERS.get(order_id, {"error": "订单不存在"})

def tool_get_policy(topic):
    """工具 2：查政策。真实项目里这是知识库检索（第 08 章）。"""
    return FAKE_POLICY.get(topic, {"error": "未收录该政策"})

TOOLS = {"search_order": tool_search_order, "get_policy": tool_get_policy}

def fake_llm(messages):
    """假模型：用规则替我们"想"。真模型在这里是 llm.chat(messages, tools=...)。

    注意：它只看**工具返回的观察结果**（role == "tool" 的消息），不看用户原话 ——
    否则用户消息里恰好出现的关键词会让它"假装已经知道了"。
    返回一个决定：想干什么 + 要不要调工具（tool=None 表示可以收工）。
    """
    observed = "\n".join(m["content"] for m in messages if m["role"] == "tool")
    if "status" not in observed:
        return {"thought": "还不知道订单状态，先查订单", "tool": "search_order",
                "args": {"order_id": "DP1002"}}
    if "未发货" in observed and "退款" not in observed:
        return {"thought": "未发货已 6 天，需要确认退款政策", "tool": "get_policy",
                "args": {"topic": "未发货超过 5 天"}}
    return {"thought": "事实齐了，可以写答复", "tool": None, "args": {}}

def run_agent(user_message, max_steps=5):
    """Agent 循环的全部骨架 —— 就这么点东西。"""
    messages = [{"role": "user", "content": user_message}]
    for step in range(1, max_steps + 1):
        print("── 第 %d 轮 ─────────────────────────" % step)
        decision = fake_llm(messages)                                # think
        print("[think] " + decision["thought"])
        if decision["tool"] is None:                                 # 停止条件
            print("[done ] 模型不再需要工具，任务结束")
            return messages
        result = TOOLS[decision["tool"]](**decision["args"])          # act
        print("[act  ] %s(%s) → %s" % (decision["tool"], decision["args"], result))
        # observe：把行动结果作为新的观察，拼回上下文，进入下一轮
        messages.append({"role": "tool", "name": decision["tool"], "content": str(result)})
    print("[stop ] 达到 %d 轮上限，强制结束（防止无限循环）" % max_steps)
    return messages

run_agent("订单 DP1002 六天了还没发货，我要退款！")
```

运行输出：

```text
── 第 1 轮 ─────────────────────────
[think] 还不知道订单状态，先查订单
[act  ] search_order({'order_id': 'DP1002'}) → {'status': '未发货', 'days': 6}
── 第 2 轮 ─────────────────────────
[think] 未发货已 6 天，需要确认退款政策
[act  ] get_policy({'topic': '未发货超过 5 天'}) → 可以无条件退款，无需客户举证
── 第 3 轮 ─────────────────────────
[think] 事实齐了，可以写答复
[done ] 模型不再需要工具，任务结束
```

第 3 轮没有 `[act]`，因为模型说"不需要工具了" —— **这就是 Agent 最自然的停止方式**。

### 2.2 循环里每一步到底是谁在做决定

| 环节 | 谁负责 | 在代码里体现为 |
|------|--------|----------------|
| observe（观察） | **代码** | 把工具返回值拼成一条 `role: "tool"` 消息，追加到 `messages` |
| think（思考） | **模型** | `llm.chat(messages, tools=...)`，返回文本或 `tool_calls` |
| act（行动） | **代码** | 遍历 `tool_calls`，真的去执行函数（模型碰不到你的系统） |
| loop（循环） | **代码** | `for step in range(max_steps)` |
| stop（停止） | **代码 + 模型** | 模型不再请求工具（正常）／代码的步数上限（兜底） |

**这是本章最重要的一行结论：Agent = 模型只负责"想"，其余全部由代码负责。** 模型没有手，它的"行动"只是输出一个 JSON 说"我想调用 `search_order`"；真正执行的永远是你的代码。这既是安全边界（你可以拦下任何危险操作），也是调试的抓手（每一步都有日志）。

### ⚠️ 常见坑

- **现象：模型调了工具，但下一轮它好像"忘了"工具返回了什么。** 原因：你执行了工具，却没把结果追加回 `messages`。改法：每次 `act` 之后必须 observe 一次 —— 把结果作为 `role: "tool"` 消息追加，并且带上 `tool_call_id`（第 04 章）。
- **现象：同一个工具被连续调用了 4 次，参数一模一样。** 原因：工具返回错误（比如订单号不存在），模型看不到有效信息就重试。改法：① 让工具返回**结构化的错误信息**（`{"error": "订单不存在", "hint": "订单号格式应为 DP+4 位数字"}`），模型才知道该怎么改；② 加"重复动作检测"：连续两次相同工具 + 相同参数就跳出循环转人工。
- **现象：循环永远不结束。** 原因：模型每轮都返回一个 `tool_calls`，永远不说"够了"。改法：**必须有 `max_steps`**，并在达到上限时返回一句明确的话（"转人工"），而不是抛异常。

## 3. 一个 Agent 的最小解剖：五个部件，缺一不可

### 3.1 五个部件

```text
        ┌──────────── 停止条件（代码）────────────┐
        │                                        │
   [模型] ──决定──→ [工具] ──执行──→ [观察] ──→ [状态/上下文]
     ▲                                              │
     └──────────────── 循环 ────────────────────────┘
```

| 部件 | 它是什么 | 缺了会怎样（具体现象） |
|------|----------|----------------------|
| **模型** | 决策者，唯一"想"的部件 | 退化成固定脚本，就是 Workflow（不是坏事，但别叫它 Agent） |
| **工具** | 行动能力，一组有名字、有参数、有返回值的函数 | 只能说不能做 —— 它无法查订单，只能告诉你"应该去查订单"，等于 Chatbot |
| **循环** | `for`/`while` 反复执行 think-act-observe | 只调用一次就结束，需要两步以上的任务必然失败（比如"先查订单，再按政策写回复"） |
| **状态/上下文** | `messages` 数组，装着历史决策与观察 | 第 2 轮不知道第 1 轮做过什么：重复调用同一工具、反复问你要同一个信息、绕圈 |
| **停止条件** | 模型不再请求工具 + 步数/成本/时间上限 | 无限循环烧钱（见下面的真实模式）；或者过早结束（任务没做完就收工） |

### 3.2 停止条件值得单独讲一段

新手最容易省掉的就是它，因为"Demo 跑起来的时候没出问题"。但**你迟早会遇到这种轨迹**：

```text
轮 3: get_policy({"topic": "退款"})  → {"error": "未收录该政策"}
轮 4: search_order({"order_id": "DP1002"}) → {"status": "未发货"}
轮 5: get_policy({"topic": "退款"})  → {"error": "未收录该政策"}
轮 6: search_order({"order_id": "DP1002"}) → ...
```

模型在两个工具之间来回试，每一轮都要重发全部历史（第 02 章会算这笔账）。工程上至少要设四道闸门：

```python
STOP_RULES = {
    "max_steps": 8,              # 步数上限：最基本的一道
    "max_tokens": 20000,         # 累计 token 上限（用 resp["usage"] 累加）
    "max_seconds": 60,           # 墙钟时间上限，防止某次调用卡住
    "repeat_limit": 2,           # 相同工具+相同参数出现 2 次 → 判定为绕圈，退出
}
```

到达任何一道闸门时，**返回一个可用的兜底结果**（"已转人工处理"），而不是抛异常 —— 因为对业务来说，"转人工"是可以接受的；"整个批处理任务崩了"是不可接受的。

### ⚠️ 常见坑

- **现象：Agent 在本地跑得好好的，上线后某天账单暴涨 20 倍。** 原因：某类输入让模型进入了绕圈模式，而没有步数上限，一个请求就跑了上百轮。改法：四道闸门全上；给账户设置月度预算告警（第 13 章）。
- **现象：给了 Agent 10 个工具，它老是选错。** 原因：工具描述写得太模糊（"处理订单"），或者工具之间有重叠（`search_order` 和 `query_order` 两个都能查订单）。改法：① 工具名和描述里写清"什么时候用它、什么时候别用"；② 同一个能力只保留一个工具；③ 工具不要超过 7±2 个（这是第 04 章的核心话题）。
- **现象：工具报错后 Agent 直接崩了。** 原因：工具函数抛异常，而循环里没有 `try/except`。改法：工具执行层统一兜住异常，把错误当成**正常的观察结果**返回给模型 —— "工具失败了"是 Agent 世界里的常态，不是异常。
- **现象：把用户输入直接当成工具参数，导致越权。** 比如用户说"帮我删掉订单 DP1001"，模型就调了 `delete_order`。改法：危险工具必须 `requires_confirmation=True`；工具的权限边界要写死在代码里，不能靠 prompt 约束（第 12 章）。

## 4. 什么时候不该用 Agent

### 4.1 决策清单

按顺序问自己这六个问题，**任何一个命中，就不要上 Agent**：

| # | 问题 | 命中时该用什么 |
|---|------|---------------|
| 1 | 步骤能提前画成一张没有回头箭的流程图吗？ | **Workflow**（分支多也不怕，`dict` 路由即可） |
| 2 | 规则能写成 `if` / 正则 / SQL 吗？ | **普通代码**，别引入模型（又快又准又免费） |
| 3 | 需要 100% 一致吗？（对账、扣款、删数据、发通知） | **代码 + 人工确认**，模型最多做"建议" |
| 4 | 延迟必须小于 1 秒吗？ | **规则 / 缓存 / 小模型**，Agent 的多轮往返做不到 |
| 5 | 出错代价高且没有人工审核环节吗？ | **不要自动化**，或者只产出草稿 |
| 6 | 你说不清"什么算做完"吗？ | **先写验收标准**，再谈架构 |

再补一条反向判断：**如果这个任务的单次价值低于单次调用成本，就不该用 Agent。** 第 02 章会给出具体的成本算法 —— 一封邮件 0.017 元可以接受，但如果你每天要处理 10 万条日志、每条只值 0.0001 元，那就不行。

### 4.2 成本与体验对照

用第 02 章的价格模型（`deepseek-chat`，输入 ¥2/百万 token、输出 ¥8/百万 token）估算：

| 指标 | Workflow（2 次调用） | Agent（5 轮循环） |
|------|---------------------|------------------|
| 调用次数 | 2（固定） | 5（1–8 波动） |
| 输入 token（累计） | 约 700 | 约 4250 |
| 输出 token（累计） | 约 400 | 约 1000 |
| 单封成本 | 约 ¥0.0046 | 约 ¥0.0165（**3.6 倍**） |
| 单封延迟 | 约 2–4 秒 | 约 6–15 秒 |
| 结果方差 | 小 | 大 |
| 出错时能不能复现 | 能（同样的输入走同样的分支） | 不一定（采样有随机性） |

结论不是"Agent 太贵别用"，而是：**Agent 用不确定的额外成本，换来了处理不可预知分支的能力。这笔交易只在分支真的不可预知时才划算。**

### 4.3 Agent 真正适合的三类任务

1. **步骤取决于中间结果的探索型任务**：网页研究（搜到什么决定下一步搜什么）、代码排错（报错信息决定改哪里）。
2. **需要多工具协作、且组合方式不固定**：查数据库 → 调 API → 写文件，顺序随情况变。
3. **单次价值足够高、允许重试**：一份研究报告值 50 元，花 0.5 元和 3 分钟去生成，完全合理。

### ⚠️ 常见坑

- **现象：因为"Agent 更先进"而选了 Agent，最后花 3 周调优一个 Workflow 两天就能做完的事。** 改法：先用第 4.1 节的清单过一遍，把结论写在需求文档里 —— 面试时这也是加分项（"我评估后选择了 Workflow，因为步骤可枚举"）。
- **现象：把 Workflow 包装成 Agent 去汇报，演示时被追问就露馅。** 判断方法很简单：**把模型的工具全部拿走，如果流程还能跑（只是内容变差），那它是 Workflow。**
- **现象：Workerflow 里的 `dict` 路由分支爆炸（20 个 `elif`）。** 这其实是"该拆成两层"的信号：先用一次模型调用做**分类**（把 20 个分支压成 4 类），再对每一类走小的固定流程。不要因为分支多就直接跳到 Agent。

`code/ch01_first_call.py` 做了两件事，并把它们并排打印，让你看到"一次问答"和"一个循环"的差距：

```text
==================================================
第 01 章 · 一次问答 vs 一个循环
==================================================

【实验 A】一次问答（1 次模型调用）
问题：订单 DP1002 六天了还没发货，我要退款，该怎么回复？
回答：这是 Mock 模式生成的回答：我收到了你的问题「订单 DP1002 ...」，...
调用次数：1    输入 token：48    输出 token：39    耗时：0.00 秒

【实验 B】一个循环（模型自己决定查什么）
问题：同上
── 第 1 轮：model → tool_calls(search_order)
[act] search_order({'order_id': 'DP1002'}) → {'status': '未发货', 'days': 6}
── 第 2 轮：model → tool_calls(get_policy)
[act] get_policy({'topic': '未发货超过 5 天'}) → 可以无条件退款，无需客户举证
── 第 3 轮：model → 不再请求工具，输出最终答复
调用次数：3    累计输入 token：约 310（每轮都要重发历史）    输出 token：约 120

==================================================
对比结论：
  实验 A 只能"说"，它不知道 DP1002 的真实状态，回答里很可能编造一个。
  实验 B 先查事实再回答，代价是 3 倍调用次数和 3 倍 token。
  → 循环的价值 = 让模型能拿到它不知道的事实；循环的代价 = 成本与延迟成倍增加。
==================================================
```

Mock 模式下 `tool_calls` 的参数是按规则生成的（它看到问题里有 `DP1002` 就调 `search_order`）。**换成在线模式，这两步就是模型自己决定的** —— 这也正是你该亲眼看一次的差别：

```bash
python ch01_first_call.py        # 需要 code/.env 配好 key
```

## 本章小结

| 结论 | 关键细节 |
|------|----------|
| 四种形态的区别在于"谁决定下一步" | 人（Chatbot）／代码（Workflow）／模型（Agent）／多角色（Multi-Agent） |
| Workflow 里也可以有模型，而且常常最优 | 模型只做模糊判断，流程与分支交给代码 |
| Agent 不是更聪明的 Workflow | 它是把决策权交出去，换来灵活性，付出不确定性 |
| Agent 循环只有四步 | observe（代码）→ think（模型）→ act（代码）→ observe（代码） |
| 模型只负责"想" | 它没有手：所有副作用都发生在你的代码里，这是安全边界 |
| 五个部件缺一不可 | 模型、工具、循环、状态、停止条件；最常被省掉的是停止条件 |
| 停止条件至少四道 | 步数、累计 token、墙钟时间、重复动作 |
| 不该用 Agent 的信号 | 步骤可枚举、规则能写成代码、要求 100% 一致、延迟 < 1 秒、无人工审核、说不清验收标准 |
| 成本对照（示例价） | 单封邮件 Workflow 约 ¥0.0046，Agent 5 轮约 ¥0.0165 |

**一句话记住：** 先问"这件事需要模型做决定吗"，而不是"怎么把 Agent 做得更强"。

## 自测题

**第 1 题：** Workflow 和 Agent 最本质的区别是什么？如果一个流程用了 3 次模型调用，但它一定是"查订单 → 查政策 → 写回复"这个固定顺序，它属于哪一种？

**第 2 题：** Agent 循环的四个步骤里，哪一步是模型做的？为什么说"模型没有手"？

**第 3 题：** 一个 Agent 没有设置 `max_steps` 会怎样？请描述一种具体的失败轨迹。

**第 4 题：** 客服主管说"我们要 100% 准确，绝对不能给客户承诺错误的退款金额"，你该怎么设计这个系统？

**第 5 题：** 为什么说"把模型的工具全部拿走，如果流程还能跑，那它就是 Workflow"？这句话在判断架构时有什么用？

<details>
<summary>点击查看答案</summary>

**第 1 题：** 最本质的区别是**"下一步做什么"由谁决定**：Workflow 由代码（`if/elif/for`）决定，Agent 由模型决定。用了 3 次模型调用但顺序固定，仍然是 **Workflow** —— 调用次数和是否用模型都不是判据，**决策权的归属**才是。

**第 2 题：** 只有 `think`（思考）是模型做的：它读 `messages`（含历史观察），输出文本或 `tool_calls`。`observe`（把工具结果拼回上下文）、`act`（真正执行函数）、循环与停止条件都是代码做的。所谓"模型没有手"，指模型只能**输出一个调用请求**，真正碰你数据库/API 的永远是代码 —— 所以你可以拦下任何一步危险操作，也可以记录每一步日志。

**第 3 题：** 模型可能陷入"调工具 → 看到结果 → 再调同一个工具"的绕圈模式，直到把上下文撑爆或账单跑穿。典型轨迹：`get_policy("退款")` 返回"未收录该政策" → 模型改查订单 → 又回头 `get_policy("退款")` → 如此往复几十轮，每轮都把全部历史重发一遍（token 消耗近似平方级增长）。正确做法是四道闸门：步数、累计 token、墙钟时间、重复动作检测。

**第 4 题：** 不要把它做成一个"自主 Agent"。正确设计是：① 退款金额这类**可验证事实必须走代码查询**（订单 API / 规则表），不能让模型生成；② 模型只负责"写草稿 + 说明依据"；③ 有副作用的动作（发送、提交退款）加人工确认门（`requires_confirmation=True`），且确认界面必须显示模型引用的原始数据；④ 用固定评测集（第 12 章）量化"承诺金额错误"的比例，而不是靠感觉。核心原则：**模型可以建议，不可以执行。**

**第 5 题：** 因为"谁决定下一步"才是判据。把工具拿走后，Agent 就失去了行动能力，只能输出文字 —— 如果此时流程仍然能按预期推进（只是内容质量下降），说明步骤本来就是代码写死的，模型只是被叫来生成文案，那就是 Workflow。这句话的用处：**它能在 30 秒内戳破"伪 Agent"** —— 无论是评审别人的方案，还是在面试里被追问"你这个到底是不是 Agent"。

</details>

## 结语与下一章

这四种形态不是四个档位，而是四种"谁握方向盘"的分工：Chatbot 是你自己开，Workflow 是铺好的轨道，Agent 是把方向盘交出去 —— 换来灵活，也换来看不清的绕路。真实项目里最省钱的那次架构调整，往往不是换一个更强的模型，而是把方向盘收回来。

但收回来之后还有个问题没解决：方向盘要交出去，得先算清它每一步的成本和质量 —— 模型一步看到多少字、花多少钱、什么时候开始胡说，这些你不清楚，就不敢把它放进真实业务。

下一章是第 02 章《大模型基础》，回答"钱、时间和质量"三个工程问题：Token 到底怎么数（中文和英文差多少）、上下文窗口超了会怎样、`temperature` 调高调低各有什么现象、一笔真实业务要花多少钱（**并看清 Agent 循环为什么是平方级烧钱**）、幻觉的成因和五种工程缓解手段、以及流式输出为什么能让用户"感觉快"。
