# 第11章 多智能体协作

> **本章目标：** 知道什么时候**不该**上多智能体；真要用时，能用契约、协调模式和四道保险（轮次上限、目标复述、上下文隔离、交付清单）把它做成可控系统。
> **预计用时：** 4 小时　**前置章节：** 第05章（ReAct 最小 Agent Loop）、第07章（记忆与上下文工程）　**配套代码：** `code/ch11_multi_agent.py`

## 0. 开篇：先泼一盆冷水

"多智能体"是 AI Agent 领域最容易被过度使用的概念。但"多"从来不是免费的——三个月前有位同学很兴奋地跟我讲，他把"每周写周报"做成了流水线，5 个 Agent 各管一段。

> "收集事实一个、整理结构一个、起草一个、审查一个、润色一个，每个都有自己的 system prompt，看起来特别专业。"
>
> 我问他："拆之前跑过单 Agent 的基线吗？"
>
> "没有。单 Agent 我试过，感觉写得不够细致，所以就拆了。"
>
> "那拆完以后变好了吗？"
>
> "质量我说不好，但 token 涨了三倍多，延迟从 20 多秒变成 70 多秒。"
>
> 我又追了一句："审查和润色之间，会不会互相不服气？"
>
> 他愣了一下："你怎么知道？每周都要吵一次，最后跑到超时。"

他不是个例：**把"看起来更专业"当成了"确实更好"**——这次翻车没有别的原因，只是账没有先算过。

三周后的数据对比：

| 指标 | 单 Agent | 5 Agent 流水线 |
|---|---|---|
| 输入 token | 约 9k | 约 29k（**3.2 倍**）|
| 端到端延迟 | 约 22 秒 | 约 78 秒（**3.5 倍**）|
| 任务成功率 | 92% | 88% |
| 事故 | 无 | 每周一次"审查与润色互相不满意"，跑到超时 |

**他的任务并不需要多智能体。** 周报是"步骤固定 + 上下文不需要隔离 + 不需要对抗性检查"的典型任务，单 Agent 一个提示词就够了。多出来的 4 个 Agent 只贡献了成本、延迟和新的故障模式。

所以本章的正确读法是：**先学会判断"不该用"，再学"非用不可时怎么做好"。**

### 判断清单：四条同时不满足，就老老实实用单 Agent

| 需求 | 单 Agent 的具体症状 | 满足时才考虑多 Agent |
|---|---|---|
| **上下文需要隔离** | 一个上下文里塞了几万 token 资料，模型开始丢前面的内容、答非所问 | 检索的资料不该污染写作的思路 |
| **需要对抗性检查** | "作者"和"审稿人"在同一段上下文里，倾向于自我确认，挑不出自己的错 | 需要一个独立上下文来挑错 |
| **需要并行** | 5 个独立子任务串行跑，20 秒 × 5 = 100 秒 | 子任务彼此独立，可以同时跑 |
| **角色差异巨大** | 一个 system prompt 里塞两套矛盾要求（"严谨引用" vs "大胆发散"），模型两头不讨好 | 每个角色一份独立 system prompt 才合理 |

**反过来说，下面这些情况一律不要上多 Agent**：

- 任务步骤固定且短（3 步以内）——写一个清晰的 Skill 就够了；
- 对延迟敏感——多 Agent 的延迟通常按最慢的分支算；
- 预算小——多 Agent 的输入 token 常见是单 Agent 的 1.2–3 倍；
- **还没给单 Agent 建评测集**——本项目的学习原则是"先有评测，再加 Agent"。没有基线，你无法证明多 Agent 变好了（第 12 章）。

### ⚠️ 常见坑

- **现象**：一上来就画五个角色的架构图，代码写了 400 行还没有跑通一次完整任务。**原因**：把架构当成了产出。**怎么改**：先用单 Agent + 工具跑通，记录基线和失败样本；只有当失败样本里反复出现"上下文污染 / 缺少对抗 / 太慢"时，才动手拆 Agent。
- **现象**：拆完 Agent 后成功率没变，token 涨了三倍，团队质疑。**原因**：拆分没有解决任何单 Agent 的问题。**怎么改**：每个新增的 Agent 都要能回答"它替谁解决了哪一条判断清单上的需求"，答不出来就删掉。
- **现象**：多 Agent 之间靠"自由讨论"协作，结果经常跑题。**怎么改**：见第 3 节——协调方式必须结构化，Supervisor / Pipeline / Graph 三选一。

## 1. 常见角色模式与它们的输入输出契约

角色不是起的名字，是**契约**。同一个名字，输入输出不写清，等于没定义。

| 角色 | 输入 | 输出 | 停止条件 | 不许做什么 |
|---|---|---|---|---|
| **planner**（规划者） | 目标 + 约束（预算、时间、格式） | 有序任务列表，每项含验收标准 | 每个子任务都能独立执行且可判定 | 不许亲自执行任务 |
| **executor / worker**（执行者） | 单个子任务 + 必要的上下文片段 | 产物 + 自检结果 | 产物满足该子任务的验收标准 | 不许改目标、不许扩大范围 |
| **reviewer**（审查者） | 产物 + 验收标准 | 结论（pass / revise）+ 可定位的问题清单 | 明确给出 pass 或 revise | 不许重写产物（那是执行者的活） |
| **critic**（批评者） | 方案 + 评判维度 | 可验证的反对意见 + 替代方案 | 至少给出 N 条可验证的反驳 | 不许为反对而反对（每条必须可验证） |
| **router**（路由器） | 用户输入 | 目标 Agent + 理由 | 明确唯一去向 | 不许自己处理任务 |

区分 reviewer 和 critic：**reviewer 对照验收标准判"合不合格"，critic 不设标准、专找"有没有更好的做法"。** 前者收敛（要能终止），后者发散（必须限定条数）。

没有契约会发生什么，三个真实症状：

1. **planner 顺手把活干了** → 后面 executor 没活干，产出两份互相矛盾的稿子。
2. **reviewer 顺手把稿子重写了** → 版本号失控，writer 被架空，最终交付的到底是哪一版没人知道。
3. **worker 自己扩大了范围**（"既然改了这个文件，顺手把整个模块都重构了"）→ 这正是第 5 节要讲的"任务漂移"。

### ⚠️ 常见坑

- **现象**：给 worker 的输入是一整段对话历史，它不知道该关心什么。**原因**：输入契约没写清"你必须拿到哪些字段"。**怎么改**：输入只给必需字段（`objective` + `facts`），其余通过检索按需取；输入契约要在代码里校验，缺字段就报错而不是硬跑。
- **现象**：reviewer 说"整体还行"就通过了。**原因**：没给它验收标准，它只能凭感觉。**怎么改**：reviewer 的输入必须包含**可判定的验收标准**，输出必须是 `pass` / `revise` 二选一 + 问题清单。
- **现象**：critic 输出一堆"可以更好"，无法执行。**怎么改**：限定条数（≤3 条）并要求每条给出"可验证的方式"（比如"把 X 换成 Y，跑同一批任务对比成功率"）。

## 2. 三种协调方式（以及一种明确不推荐的）

角色定义了"谁干什么"，协调方式定义"怎么串起来"。**先在这张表里选，再写代码。**

| 方式 | 结构 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **Supervisor** | 一个主管调度多个 worker | 能全局控轮次、预算、交付清单 | 主管是瓶颈；主管上下文也有限 | 任务需要动态分发、需要兜底与裁决 |
| **Pipeline** | 固定顺序：research → write → review → revise | 可预测、易调试、每步有产物 | 不能回头，路径写死 | 流程稳定的生产任务（周报、审查、翻译） |
| **Graph** | 状态图：节点=步骤，边=条件 | **可恢复、可分支、可重试** | 实现复杂，要有状态存储 | 长任务、可能失败中断、需要断点续跑 |
| **自由对话式** ❌ | Agent 之间随便聊 | 无 | 跑题、上下文指数膨胀、无法终止 | **不推荐** |

**为什么明确不推荐"自由对话式"**，三个可验证的理由：

1. **容易跑题**：没有结构约束，两个 Agent 会在"什么算更好的文风"这种无法判定的问题上耗光预算。
2. **上下文爆炸**：每个 Agent 都要读别人的全部发言，消息数按 `n²` 增长（第 5 节有实测数据）。
3. **无法终止**：没有停止条件，系统只能靠"轮次上限"这种外部手段掐断——那说明它本来就不是一个可控系统。

补充一句 Graph 的独特价值：**可恢复**。一个跑 40 分钟的研究任务，如果在第 30 分钟崩了，Supervisor 和 Pipeline 通常要重跑，而 Graph 能从上一个检查点继续。这是它在生产环境里唯一的、也是决定性的优势。

### ⚠️ 常见坑

- **现象**：用 Supervisor 但主管把所有子 Agent 的完整输出都读进自己的上下文，主管反而最先撑爆。**怎么改**：子 Agent 只回传**压缩后的结论**（见第 6 节），主管的上下文预算要单独设上限。
- **现象**：Pipeline 跑中间某步失败，整条链路重跑，前面白干还花钱。**怎么改**：每步产物落盘（文件/trace），失败时从最近的产物继续；需要断点续跑就上 Graph。
- **现象**：明明只有两个角色，却写了一个"通用调度器"。**怎么改**：两个角色的场景，一个 `for` 循环足够（`ch11_multi_agent.py` 的 `run_rounds` 就是 20 行）；框架要跟着复杂度长，不要提前长。

## 3. 每个 Agent 都必须有明确契约

契约不是文档，是**要落到代码里的字段**。先写模板，再写实现：

```markdown
角色：researcher
职责：只收集事实与来源，不写结论、不写正文
输入：question (str)
输出：facts (list[str]，≥3 条)、sources (list[str])
停止条件：facts ≥3 且每条都能对应 sources 里的来源
失败回退：退化为最多 2 条事实 + 标注"证据不足"，并把不确定性写进输出
不许做：价值判断、给建议
```

这六项缺一项都会出事：没有"停止条件"就会无限干；没有"失败回退"就会卡死；没有"不许做"就会越界。

`ch11_multi_agent.py` 把契约写成了数据结构，并在**运行时校验输入与输出**：

```python
class Worker(object):
    """带契约的 worker：输入校验 → 干活 → 输出校验 → 失败回退。"""
    def __init__(self, contract, work, fallback=None):
        self.contract = contract
        self.work = work
        self.fallback = fallback
        self.calls = 0

    def run(self, payload, trace):
        self.calls += 1
        trace.log("worker_start", worker=self.contract.role, call=self.calls)
        missing = self.contract.check_input(payload)
        if missing:
            trace.log("input_contract_violation", worker=self.contract.role, missing=missing)
            print("  [!] %s 输入契约不满足，缺字段：%s" % (self.contract.role, missing))
        result = self.work(payload)
        bad = self.contract.check_output(result)
        if bad:
            trace.log("output_contract_violation", worker=self.contract.role, missing=bad)
            print("  [!] %s 输出契约不满足，缺字段：%s" % (self.contract.role, bad))
            if self.fallback:
                print("      → 触发失败回退：%s" % self.contract.on_failure)
                result = self.fallback(payload)
                trace.log("fallback_used", worker=self.contract.role)
        trace.log("worker_done", worker=self.contract.role)
        return result
```

三个设计要点：

1. **契约校验放在"跑之前"和"跑之后"**：输入缺字段就别让它瞎跑（省 token），输出缺字段就触发回退（保交付）。
2. **回退逻辑必须事先写好**：`on_failure` 不是一句描述，是一个真函数（`writer_fallback`）；没有回退的 Agent 等于没有错误处理。
3. **每次校验都写 trace**：`input_contract_violation` / `fallback_used` 这些事件是复盘时最重要的证据。

### ⚠️ 常见坑

- **现象**：worker 返回的 JSON 少了一个字段，主管直接用 `result["draft"]` 崩了。**原因**：只校验了"有没有返回"，没校验"字段全不全"。**怎么改**：用 `check_output` 逐一比对必填字段；在线模式下还要处理"模型返回的不是合法 JSON"（重试一次或走回退）。
- **现象**：所有 Agent 都用同一个 system prompt，只是任务不同。**原因**：把"角色"当成了"任务"。**怎么改**：角色差异要体现在 system prompt 里（职责、禁令、输出格式），否则拆了也不会有不同的行为。
- **现象**：失败回退写成了"重试一次"，模型第二次照样错。**怎么改**：回退要**降级**而不是重试——减少输出要求（只给大纲）、缩小范围（只做前半部分）、或明确上报"做不了，原因是 X"。

## 4. 四类典型故障：检测与处理（本章重点）

多 Agent 系统的故障不是随机 bug，而是**四种固定模式**。每一种都有对应的机械手段。

| 故障 | 现象 | 检测手段 | 处理手段 |
|---|---|---|---|
| **循环争论** | reviewer 每轮都说 revise，轮次一直涨 | 轮次计数 + 相邻两轮意见相似度 | 轮次上限 + 强制裁决，标注分歧交人工 |
| **任务漂移** | 做着做着偏离原目标 | 每轮强制复述目标 + 与原始目标做重合度检查 | 打回重述、缩小范围、重新下发目标 |
| **上下文膨胀** | 消息数 / token 指数增长 | trace 里的 token 与消息计数 | 上下文隔离 + 只回传压缩结论 + 超预算摘要 |
| **责任真空** | 交付时发现某项没人做 | 开工前定交付清单，收尾逐项打勾 | 每项必须有人认领；缺失项指派兜底 |

### 4.1 循环争论

**检测**：轮次计数最简单有效。`ch11_multi_agent.py` 里 `MAX_ROUNDS = 3`，跑到上限就停：

```python
            if round_no == self.max_rounds:
                print("  [!] 已达轮次上限 %d：强制停止修订，把分歧点交给人工" % self.max_rounds)
                self.trace.log("round_limit_hit", round=self.max_rounds)
                return draft, review, "limit"
```

**处理**：强制裁决规则必须**事先定义**：以原始目标的验收标准为准；无法判定时输出"未达成一致 + 分歧点 + 各自的理由"，交人工。实测输出（故意让 reviewer 永远不满意）：

```text
[轮次 3/3] reviewer 开始审查
  reviewer 判定：revise，问题：初稿语气不够正式；再改一版
  [!] 已达轮次上限 3：强制停止修订，把分歧点交给人工
裁决：强制停止，交人工（分歧点：初稿语气不够正式；再改一版）
证据：trace 里的 round_limit_hit 事件 = [{'event': 'round_limit_hit', 't': 0.001, 'round': 3}]
```

注意"初稿语气不够正式"这种**无法判定**的反对意见，正是循环争论的燃料。**reviewer 的每一条意见都必须是可判定的**（"缺少对比表"可判定，"语气不够正式"不可判定）——这条规则能从源头消灭大部分争论。

### 4.2 任务漂移

**检测**：要求每个 Agent 在输出里**复述目标**（`restated_goal` 字段），然后和原始目标做自动比对：

```python
    def check_drift(self, restated):
        score = overlap(restated, self.objective)
        self.trace.log("drift_check", restated=restated[:40], score=round(score, 2))
        if score < DRIFT_THRESHOLD:
            print("  [!] 检测到任务漂移：复述目标“%s”" % restated[:24])
            print("      与原始目标重合度只有 %.2f（阈值 %.2f）→ 打回，要求重新复述并缩小范围"
                  % (score, DRIFT_THRESHOLD))
            self.trace.log("drift_detected", score=round(score, 2))
            return True
        return False
```

实测输出（writer 把目标写成"顺便把整个项目重构一遍"）：

```text
[!] 检测到任务漂移：复述目标“对比一下向量数据库，顺便把整个项目重构一遍并向老”
    与原始目标重合度只有 0.20（阈值 0.45）→ 打回，要求重新复述并缩小范围
处理：重新下发目标 + 缩小范围（只做选型对比，不许碰代码）
```

**关键点**：漂移不是靠"人看一眼"发现的，而是靠**每轮强制复述 + 自动比对**。这个机制还有一个副作用好处：目标和约束被反复强调，模型更不容易忘。

### 4.3 上下文膨胀

**检测**：数 token。共享一份上下文的系统，消息数按 `n²` 涨——每个 Agent 都要读别人的全部输出。实测对比（同样 5 轮）：

```text
轮次   共享上下文的 token   隔离 + 压缩后的主管 token
----------------------------------------------------------
1      420                    244
2      1260                   488
3      2940                   732
4      6300                   976
5      13020                  1220
----------------------------------------------------------
第 5 轮时差 10.7 倍。处理：子 Agent 独立上下文 + 只回传压缩结论 + 超预算就摘要。
```

**处理**：三件事一起做——子 Agent 独立上下文、只回传压缩结论、接近预算时主动摘要（第 07 章的上下文压缩在这里直接复用）。

### 4.4 责任真空

**检测**：开工前把交付清单定好，收尾时逐项打勾：

```python
    def check_deliverables(self, collected):
        missing = [item for item in self.deliverables if not collected.get(item)]
        self.trace.log("deliverable_check", missing=missing)
        if missing:
            print("\n[!] 责任真空检查：交付清单里还没有人产出的项 → %s" % "、".join(missing))
            print("    → 指派给 reviewer 兜底补齐（每项都必须有人认领，否则不算完成）")
            self.trace.log("reassign", to="reviewer", items=missing)
```

典型输出："草稿写了、稿也审了，但没人给测试建议"，收尾时才发现：

```text
[!] 责任真空检查：交付清单里还没有人产出的项 → sources、verdict
    → 指派给 reviewer 兜底补齐（每项都必须有人认领，否则不算完成）
```

**处理**：清单在开工前定、收尾时逐项核对；发现空缺就显式指派（而不是"大家应该都做了"）。这条规则的本质是：**在终点做一次存在性检查，比在过程中祈祷有效得多。**

### ⚠️ 常见坑

- **现象**：轮次上限设得很大（10 轮），成本失控。**原因**：把上限当成"质量保障"。**怎么改**：默认 2–3 轮；超过就要有人工介入环节，或者说明任务本身无法判定（先改验收标准）。
- **现象**：漂移检测把正常的范围收窄也判成漂移。**原因**：阈值定得太高，或者目标表述本身太模糊。**怎么改**：先记录几轮的 `score`，看正常复述的分值分布（通常 0.7+）再定阈值；目标本身要写成可判定的句子。
- **现象**：交付清单里有一项谁都没做，最后靠"临时加一轮"补救，超时。**怎么改**：清单项必须和某个角色的 `produces` 字段对应；定清单时就检查"这一项由谁产出"，产不出来就砍掉这项要求。

## 5. 上下文隔离才是多 Agent 的核心价值

上面四类故障里有三类的解法都指向同一个词：**上下文隔离**。而它带来的收益是双向的：

| | 单 Agent（共享上下文） | 多 Agent（隔离 + 压缩回传） |
|---|---|---|
| **质量** | 检索来的 5 万 token 资料和写作要求混在一起，注意力被稀释 | 写作 Agent 只看到"结论 + 3 条事实"，噪音少 |
| **成本** | 每轮都要重发全部历史 | 子 Agent 各自的中间过程不进主管上下文 |
| **故障面** | 一处跑偏全盘污染 | 单个子 Agent 跑偏可被隔离、可重跑 |

**关键动作是"压缩回传"**：子 Agent 只把结论摘要交回主管，细节留在自己的上下文里：

```python
def compress(items, budget=120):
    """把子 Agent 的一堆结论压成一句话，再回传给主管（上下文隔离的关键动作）。"""
    joined = "；".join(items)
    if len(joined) <= budget:
        return joined
    return joined[:budget] + "……（已压缩，细节留在子 Agent 自己的上下文里）"
```

实跑输出：`researcher 的 3 条事实已压缩为 41 字后回传（子上下文已隔离）`。

两点必须注意：

1. **压缩要留"指针"**：摘要里必须保留可回查的信息（文件路径、来源 id、行号），否则主管想问细节时只能重新跑一遍。
2. **压缩会丢信息**：这是有意的取舍。判断标准是"主管下一步决策需不需要它"——不需要就丢，需要就留在产物文件里（落盘），而不是留在上下文里。

### ⚠️ 常见坑

- **现象**：隔离之后子 Agent 开始"自作主张"，产出和整体目标不一致。**原因**：只隔离了上下文，没传递目标与约束。**怎么改**：给子 Agent 的输入里，目标与验收标准永远完整保留，只压缩"过程性内容"。
- **现象**：压缩太狠，主管拿到一句话无法判断质量。**怎么改**：压缩保留"结论 + 依据数量 + 不确定性"，例如"3 条事实（2 个来源，未验证冷启动延迟）"——数量和缺口比文字长度更重要。
- **现象**：所有子 Agent 共用一份 system prompt，隔离了等于没隔离。**怎么改**：隔离包括提示词、工具集、上下文三层；只隔离上下文时收益有限。

## 6. 成本对比：先算账，再决定要不要上多 Agent

同一任务的量级估计（`ch11_multi_agent.py` 打印这张表）：

| 方案 | 输入 token | 输出 token | 延迟 | 说明 |
|---|---|---|---|---|
| 单 Agent 一路到底 | 9200 | 1800 | 26s | 上下文从头累积，第 6 轮时还带着前 5 轮的全部历史 |
| Supervisor + 2 worker | 11400 | 2100 | 34s | 总 token 更高，但主管上下文只保留压缩结论 |
| Supervisor + 2 worker（并行） | 11400 | 2100 | 19s | 两个 worker 同时开工，延迟按最慢的那个算 |

三条规律：

1. **多 Agent 的输入 token 通常比单 Agent 高 20%~200%**——每个子 Agent 都要重复带自己的系统提示和背景。
2. **唯一能降延迟的手段是并行**：串行分工只会让延迟更高（34s > 26s）。
3. **收益买的是"上下文更干净 + 可对抗检查 + 可并行"**，不是"更聪明"。买不到这三样，就是纯亏。

所以判断顺序永远是：**单 Agent 能到 90% → 先用 Skill 补流程 → 还不够，再拆 Agent。**

### ⚠️ 常见坑

- **现象**：统计成本时只看 token，没算失败重跑。**怎么改**：把 trace 里的失败率算进去（失败任务的 token 是全损）；多 Agent 的失败成本比单 Agent 高，因为它每次都要跑好几个子 Agent。
- **现象**：为了省 token 把子 Agent 的 system prompt 砍到极简，结果输出质量下降、重试变多，总成本反而上升。**怎么改**：优化目标是"完成任务的总成本"，不是"单次调用的 token"。
- **现象**：拿"并行"当默认。**怎么改**：只有子任务之间**无依赖**时才能并行；有先后依赖的任务强行并行，只会得到互相矛盾的产物。

## 7. 配套代码走读：`code/ch11_multi_agent.py`

脚本五段输出对应本章五节：**契约 → 一次完整协作 → 四类故障 → 上下文与成本 → trace 落盘**。全部在 `AGENT_MOCK=1` 下跑通。

**第一段：契约就是数据**。三个角色的契约打印出来是这样（每行都对应本章第 3 节的模板）：

```text
researcher  职责=只收集事实与来源，不写结论、不写正文
           输入=question
           输出=facts,sources
           停止条件=facts 至少 3 条且每条都能对应 sources 中的来源
           失败回退=退化为“最多 2 条事实 + 标注证据不足”，并把不确定性写进输出
           不许做=不许做价值判断，不许给出建议
```

**第二段：一次完整协作**（Supervisor 模式，含三道保险）：

```text
主管：目标 = 对比向量数据库的检索方案，给出选型建议
主管：轮次上限 = 3，漂移阈值 = 0.45，交付清单 = draft、facts、sources、verdict
主管：researcher 的 3 条事实已压缩为 41 字后回传（子上下文已隔离）

[轮次 1/3] reviewer 开始审查
  reviewer 判定：revise，问题：缺少对比表
[轮次 2/3] reviewer 开始审查
  reviewer 判定：pass（停止修订）
交付清单检查：全部有主，可以收尾
最终状态：pass　产出：草稿 73 字，事实 3 条，来源 2 个，未解决项 0 个
```

**第三段：四类故障各跑一遍**（第 4 节的输出即来自这里）。**第五段：trace 落盘**：

```text
已写入 traces/ch11_multi_agent.json（真实项目里这是复盘与评估的唯一依据，别省）
```

trace 里的事件统计（JSON 打印的一部分）：`worker_start: 5`、`worker_done: 5`、`drift_check: 1`、`deliverable_check: 1`。**有了它你才能回答"这一轮到底谁干了什么、为什么停下"。**

**跑一遍**：

```bash
cd code
AGENT_MOCK=1 python ch11_multi_agent.py        # Windows: set AGENT_MOCK=1
```

离线模式下，三个 worker 的产出由脚本内的规则函数提供（`researcher_work` / `writer_work` / `reviewer_work`），**框架、契约校验、漂移检测、轮次上限、交付清单检查全部真实执行**；接上真模型后只需把 `ask_json` 里的分支换成 `chat()` 调用，控制流的代码一行都不用改。

### ⚠️ 常见坑

- **现象**：把 `MAX_ROUNDS` 改成 10 想看"能不能改得更好"，结果只是多烧了三倍的 token，产出没变。**怎么改**：上限的作用是止损，不是提质；要提质应该改验收标准或拆任务。
- **现象**：手工删掉 `check_deliverables` 让流程"顺畅"，结果交付时缺件。**怎么改**：这三道保险都不是可选项——它们是多 Agent 系统与"一群 Agent 瞎聊"的唯一区别。
- **现象**：在 mock 模式下看到"全部 pass"就以为系统没问题。**怎么改**：mock 模式验证的是控制流，真实效果要在线跑；离线跑通只是"脚手架没搭错"。

## 本章小结

1. **先泼冷水**：多数任务单 Agent 就够。判断清单四条（上下文隔离 / 对抗检查 / 并行 / 角色差异）不满足就不要拆。
2. **角色是契约不是名字**：planner / executor / reviewer / critic / router 各有输入、输出、停止条件与禁令；reviewer 收敛、critic 发散、router 只路由。
3. **协调方式三选一**：Supervisor（可控）、Pipeline（可预测）、Graph（可恢复）；**自由对话式不推荐**——跑题、上下文爆炸、无法终止。
4. **四类故障都有机械解法**：轮次上限治循环争论、目标复述治漂移、隔离 + 压缩治膨胀、交付清单治责任真空。
5. **上下文隔离是核心价值**：独立上下文提升质量的同时降低 token；回传时压缩，但保留指针与不确定性。
6. **成本要算总账**：多 Agent 输入 token 高 20%~200%，只有并行能降延迟；买的是上下文干净与对抗检查。
7. **关联阅读**：[[02-Wiki/专题总结/06-多智能体协作]]。

## 动手练习

**练习 1（给契约加一条禁令）**：给 `CONTRACTS["writer"]` 加一条 `must_not_do`（比如"不许编造 facts 之外的数据"），并在 `writer_work` 里故意返回一条不在 `facts` 里的数据，然后写 5 行代码检测它、打印"越界警告"并让该条失效。
*目标：把"禁令"从文档变成能拦人的检查。*

**练习 2（把轮次上限换成"相似度熔断"）**：现在的循环争论靠 `MAX_ROUNDS` 掐断。改成：比较相邻两轮 reviewer 的 `issues`，如果重合度 > 0.8 就立即判定"无进展"并停止（提前于轮次上限）。用 `code/ch11_multi_agent.py` 里的 `overlap` 函数即可，跑出来对比两种停止方式的轮次与 token。
*目标：学会用"无进展"而不是"到次数"来终止循环。*

**练习 3（加一个 router）**：给系统加第四个角色 `router`：输入用户请求，输出 `{"target": "researcher|writer", "reason": "..."}`，并给主管加上"如果 router 指向不存在的角色就回退到默认流程"的兜底。契约、校验、trace 事件三样都要补齐。
*目标：完整体验"新增一个 Agent"的全部工作量（契约 + 校验 + 回退 + 可观测），并自己判断它值不值得。*

## 自测题

**1. 什么情况下才该考虑多智能体？**

<details><summary>点击查看答案</summary>

四条判断标准，满足其中一条且有明确收益才考虑：① 上下文需要隔离（资料污染思路）；② 需要对抗性检查（同一上下文里挑不出自己的错）；③ 需要并行（子任务独立、对延迟敏感）；④ 角色差异巨大（一个 system prompt 塞不下两套矛盾要求）。

反例：步骤固定且短、延迟敏感、预算小、单 Agent 评测集还没建——这些情况一律先用单 Agent + Skill。

</details>

**2. reviewer 和 critic 的区别是什么？为什么 reviewer 的输出必须是 pass/revise？**

<details><summary>点击查看答案</summary>

reviewer 对照**验收标准**判断合不合格，输出必须收敛（pass / revise 二选一 + 可定位的问题清单），否则循环无法终止；critic 不设标准、专门找"有没有更好的做法"，输出发散，因此必须限定条数（如 ≤3 条）并要求每条可验证。两者混用（比如让 reviewer 提"语气可以更好"）会直接导致循环争论。

</details>

**3. 为什么明确不推荐"自由对话式"多智能体？**

<details><summary>点击查看答案</summary>

三个理由：① 容易跑题——没有结构约束，会在无法判定的问题（"什么算更好的文风"）上耗光预算；② 上下文爆炸——每个 Agent 都要读别人全部发言，消息数按 n² 增长（实测 5 轮差 10.7 倍）；③ 无法终止——没有停止条件，只能靠轮次上限这种外部手段掐断，说明它本来就不是可控系统。替代方案：Supervisor / Pipeline / Graph。

</details>

**4. 四类典型故障分别怎么检测、怎么处理？**

<details><summary>点击查看答案</summary>

① 循环争论：检测=轮次计数 + 意见相似度；处理=轮次上限 + 强制裁决（以原始验收标准为准，无法判定就交人工）。② 任务漂移：检测=每轮强制复述目标 + 与原始目标做重合度比对（实测 0.20 < 阈值 0.45 即判漂移）；处理=打回、缩小范围、重新下发目标。③ 上下文膨胀：检测=trace 里的 token/消息计数；处理=子 Agent 独立上下文 + 只回传压缩结论 + 超预算摘要。④ 责任真空：检测=开工前定交付清单、收尾逐项打勾；处理=每项必须有人认领，缺失项显式指派兜底。

</details>

**5. 多 Agent 的输入 token 更高，为什么还值得？（或者说：什么时候不值得？）**

<details><summary>点击查看答案</summary>

值得的情况：买到三样东西之一——上下文更干净（子 Agent 不被无关历史稀释）、可对抗检查（独立上下文能挑错）、可并行（延迟下降）。量级上输入 token 常见高 20%~200%，串行分工还会让延迟更高，只有并行能降延迟。

不值得的情况：任务不需要这三样、对延迟敏感、预算小、单 Agent 还有明显可优化的地方（提示词、Skill、工具设计）。判断顺序：单 Agent → 加 Skill → 再拆 Agent。

</details>

## 结语与下一章

拆 Agent 不像给系统装插件，更像给一个团队加人：多一个人就多一套上下文、多一份沟通成本、多一种"谁都不认账"的可能——只有当活确实需要分工时，加人才划算。

但这一切都还没有**度量**：成功率是多少？成本花了多少？哪一步最慢？危险动作有没有人把关？prompt 注入有没有防住？

第 12 章讲**评估、可观测性与安全**：怎么建一套 20 条规模、可以天天跑的固定评测集；怎么看 trace 定位"到底是提示词的问题还是工具的问题"；怎么给危险工具加人工确认门；以及 prompt 注入的实战防御写法。
