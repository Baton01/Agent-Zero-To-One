## 0. 开篇：一个真实的问题

上周和做内部工具的老周吃饭，他说他把第 05 章的 ReAct 循环接进了**所有**任务——"多想想总没坏处"。

> 我：效果怎么样？
> 老周：分三类，每一类都让我怀疑人生。第一类，一个水池有两个进水管，A 管单独注满要 6 小时、B 管要 4 小时，底部还有个出水口 12 小时排空，多久注满——它调用 calculator 算了 8 步、烧了 1.1 万 token、等了 21 秒。
> 我：直接问一次模型呢？
> 老周：5 秒，答案还对。这类任务不需要外部信息，只需要想清楚，ReAct 让它绕了一大圈。
> 我：第二类呢？
> 老周：调研 2026 年 AI Agent 的三个主流技术方向，各写 200 字，最后给我一份对比表。它第 1 步查方向 A，第 2 步查 A 的细节，第 3 步觉得 A 更重要就一头扎进去了，第 4 步才查 B……跑了 14 步、4 万 token，方向 C 完全没查。
> 我：它哪一步做错了？
> 老周：单看每一步都没错，都是在做"当前看起来最合理"的选择。
> 我：那错在哪？
> 老周：……它从来没抬头看过全局。这类任务本该先出一份计划：A、B、C 各查什么、最后怎么汇总。
> 我：第三类呢？
> 老周：我让它把一段说明改成给非技术同事看的版本。第一版带了三处内部术语，我说"还有术语没解释"，它改掉那三处、又引入两个新术语……这样来回 5 次，最后一版还不如第一版。
> 我：那你为什么不停？
> 老周：因为它每一轮都说得特别有道理，而且越改越自信。

最后这句话才是重点：**没有外部信号时，模型会越改越自信，但并没有变好。**

三个问题指向三种不同的范式：**CoT** 解决"要推理没推理"，**Plan-and-Execute** 解决"缺全局规划"，**Reflection** 解决"输出需要迭代打磨"。本章把三种都实现一遍，最后给你一张决策表 —— 因为**真正的工程能力，是知道什么时候不该用那个更强的东西。**

## 1. CoT：先想再答

### 1.1 它为什么有效

**Chain of Thought（思维链，CoT）** 出自 Wei 等人 2022 年的论文 *Chain-of-Thought Prompting Elicits Reasoning in Large Language Models*。做法简单到有点荒唐：**别让模型直接给答案，先让它把推理步骤写出来。**

为什么这样有用？因为大模型是**逐 token 生成的**，而每一个新 token 都能"看到"前面所有 token。模型的"计算"就发生在生成的过程中：

- 你让它直接输出答案，它必须在**第一个 token** 里就把全部推理算完 —— 相当于让你心算 47×89 直接报结果；
- 你让它先写步骤，它就有了"草稿纸"：每一步的中间结果都变成了后续计算的输入。

对比效果（论文报告的数据，PaLM-540B，GSM8K 小学数学应用题）：

| 方法 | 准确率 |
|---|---|
| 标准提示（直接给答案） | 约 18% |
| CoT（8 个带步骤的示例） | 约 57% |
| CoT + Self-Consistency（采样 40 次投票） | 约 74% |

**从 18% 到 57%，只改了一句提示词。** 这是提示词工程里性价比最高的一招。

### 1.2 什么时候有效，什么时候无效

这一节比上一节重要得多 —— **CoT 用错地方会主动伤害效果。**

| 任务类型 | CoT 有效吗 | 原因 |
|---|---|---|
| 多步算术、应用题 | **非常有效** | 中间结果需要被"记住"并参与后续计算 |
| 逻辑推理（谁比谁高、排列组合） | **有效** | 约束需要逐步消解 |
| 需要组合多个条件做判断 | **有效** | 每一步只处理一个约束，负担被摊开 |
| 事实检索（"珠峰多高"） | **基本无效** | 答案在参数里，推理过程只是给幻觉加戏 |
| 简单分类（情感正负） | **无效甚至有害** | 先写"因为……"会强化模型最初的偏见 |
| 格式严格的结构化输出 | **有害** | 推理文字会污染 JSON，解析失败率上升 |
| 模型完全不知道答案的领域 | **有害** | 它会编出一段**看起来很严谨**的错误推理，比直接说错更可信 |

**最后一行要特别记住：CoT 不产生知识，它只整理知识。** 如果模型压根不知道某个事实，CoT 不会让它知道，只会让它的错误披上"推理"的外衣。这也是第 08 章要上 RAG 的原因 —— 知识的问题要用检索解决，不能用提示词解决。

还有一个常被忽略的上限：**CoT 是"涌现"能力。** 论文里的提升主要出现在百亿参数以上的模型上，小模型写出的推理链往往"流畅但不合逻辑"，收益很小甚至为负。**用小模型 + CoT 去替代大模型直接答，通常不划算。**

### 1.3 三种实现

```python
from common.llm import chat, get_llm

# ① Zero-shot CoT：一句魔法咒语（Kojima 等，2022）
def cot_zero_shot(question):
    return chat("请一步一步思考，然后给出最终答案。\n\n问题：%s" % question,
                system="你是严谨的推理助手。最后一行用「答案：」开头给出结论。")

# ② Few-shot CoT：给 1–3 个带步骤的示例（效果通常比 zero-shot 更稳）
COT_EXAMPLES = """问题：小明有 5 个苹果，吃了 2 个，又买了 3 倍于剩下的苹果，现在有几个？
思考：剩下 5-2=3 个。3 倍于剩下的是 3×3=9 个。总共 3+9=12 个。
答案：12

问题：一本书 240 页，第一天读了 1/4，第二天读了剩下的 1/3，还剩多少页？
思考：第一天读 240×1/4=60 页，剩 180 页。第二天读 180×1/3=60 页，剩 120 页。
答案：120
"""

def cot_few_shot(question):
    return chat(COT_EXAMPLES + "\n问题：%s" % question, system="照示例的格式回答。")

# ③ Self-Consistency：采样多次，对最终答案投票（Wang 等，2022）
def cot_self_consistency(question, n=3):
    llm = get_llm(temperature=0.7)          # ← 这里要开温度，否则 n 次结果一样
    answers = []
    for _ in range(n):
        text = llm.chat([{"role": "user", "content":
                          "请一步一步思考，最后一行用「答案：」开头。\n\n" + question}])["content"]
        answers.append(extract_final_answer(text))     # 从"答案："那行取结果
    return majority_vote(answers)                     # 多数票胜出
```

`cot_self_consistency` 的关键细节：**温度必须大于 0**（否则 n 次采样完全相同，投票毫无意义），而 `cot_zero_shot` / `cot_few_shot` 应该用 `temperature=0`（要稳定复现）。这个"温度按用途设置"的习惯，比记住任何提示词模板都有用。

> Self-Consistency 的本质是**用钱换稳定性**：n 次采样、n 倍成本，换来的是方差下降。n=3 通常就能明显改善，n=40 是论文里的配置（对普通项目太贵了）。

### ⚠️ 常见坑

- **现象**：加了"请一步一步思考"之后，模型给的答案反而更长更自信，但错得更离谱。**原因**：这是事实检索类问题，模型本来不知道答案，CoT 让它把幻觉组织成了推理链。**怎么改**：涉及具体事实、数字、时效信息时，**上工具或 RAG，不要上 CoT**。
- **现象**：要求模型输出 JSON，加了 CoT 之后 `json.loads` 频繁失败。**原因**：推理文字混进了 JSON 里（或在 JSON 前后各写了一段）。**怎么改**：把两件事拆开 —— 先用 CoT 让模型推理，**再用一次单独的请求**（或严格的 schema 约束）把它转成 JSON。不要指望一次输出里既有自由推理又有严格结构。
- **现象**：用 7B 级别的小模型 + CoT，效果还不如直接问。**原因**：CoT 是规模涌现能力，小模型写的推理链不合逻辑，反而干扰答案。**怎么改**：小模型直接答 + 用更大模型做校验，或者换更大的模型做推理。
- **现象**：`cot_self_consistency` 跑 5 次结果完全一样，投票没意义。**原因**：忘了设 `temperature`，默认 0.7 的封装里可能被覆盖成 0。**怎么改**：显式传 `temperature=0.7` 给 `get_llm()`；并在投票前检查 `len(set(answers)) > 1`，否则直接打印警告。

## 2. Plan-and-Solve / Plan-and-Execute

### 2.1 走一步看一步 vs 先看全局

ReAct 是**贪心策略**：每一步都问"现在最该做什么"，只看得到眼前。它天然适合**步骤间强依赖**的任务（下一步做什么，取决于这一步看到了什么）。

但有一类任务恰恰相反：**步骤是事先就能列清楚的，只是数量多。** 这时候贪心策略有两个毛病：

1. **会迷路**：第 3 步觉得方向 A 有意思，就一头扎进去了，忘了还有 B 和 C（就是开篇那个例子）。
2. **很贵**：ReAct 每一步都要把全部历史重发一遍。10 步任务的 token 是平方级增长（第 05 章第 7 节）。

**Plan-and-Execute** 换个顺序：**先一次性把计划列出来，再逐步执行。**

```text
Plan-and-Solve（一步到位）        Plan-and-Execute（计划 + 执行分离）
─────────────────────────        ────────────────────────────────────
planner + executor 合并            planner 出结构化计划（可存下来、可人工审核、可改）
在一个 prompt 里做完                 → 每一步独立执行（可以并行、可以换不同模型/工具）
简单，但没有中间检查点              → 全部执行完后汇总（可选 replan）
```

学术版本叫 **Plan-and-Solve Prompting**（Wang 等，2023），工程版本就是各大框架里的 **Plan-and-Execute Agent**。我们实现后者，因为它更贴近真实项目。

### 2.2 实现：planner → executor → replan

**第一步：Planner 输出结构化计划。**

```python
PLANNER_PROMPT = """你是任务规划专家。把用户的复杂任务拆成 2–6 个可独立执行的步骤。

要求：
1. 每一步必须是"一次具体动作"，不能是"继续研究"这类空话。
2. 每一步要能独立执行，尽量少依赖其他步骤的结果（这样能并行、能重试）。
3. 每一步都要写清"完成标准"：做完之后应该得到什么。

只输出 JSON，格式：
{"steps": [{"id": 1, "goal": "查 2026 年 Agent 的三大技术方向", "done_when": "列出 3 个方向名"}]}

用户任务：%s"""

def make_plan(task):
    raw = chat(PLANNER_PROMPT % task, system="你只输出 JSON，不要任何解释。")
    plan = json.loads(extract_json(raw))          # 容错：模型可能包了代码块
    return plan["steps"]
```

**第二步：Executor 逐步执行。**

```python
EXECUTOR_PROMPT = """你在执行一个大任务的一个步骤。只做这一步，不要扩展范围。

大任务：%s
已完成的步骤与结果：
%s
当前步骤：%s
完成标准：%s

请执行并给出这一步的产出（不超过 200 字）。"""

def execute_step(task, step, done):
    context = "\n".join("- 步骤 %s：%s → %s" % (s["id"], s["goal"], s["result"][:120])
                        for s in done) or "（无）"
    return chat(EXECUTOR_PROMPT % (task, context, step["goal"], step["done_when"]),
                system="你只输出这一步的结果，不要复述任务、不要写总结。")
```

**第三步（可选但重要）：Replan。**

```python
REPLAN_PROMPT = """原任务：%s
原计划：%s
已完成：
%s
剩余步骤：%s

执行过程中发现新信息，需要判断：原计划是否还成立？
- 如果成立，只输出 {"action": "continue"}
- 如果需要调整，输出 {"action": "replan", "steps": [...]}
- 如果任务已能回答，输出 {"action": "done"}"""
```

**为什么 replan 不能省？** 因为**计划的错误会被完整地执行下去**。这是 Plan 范式的结构性风险：ReAct 走错一步马上能看到 Observation 并回头，Plan 一旦第 2 步的前提就是错的，后面 4 步全在错误的地基上盖楼。**加了 replan，风险才从"灾难"降到"多花一次请求"。**

`code/ch06_paradigms.py` 里的完整实现长这样：

```text
plan_and_execute(task, enable_replan=True)
  ├─ ① make_plan(task)                    1 次请求 → steps[]
  ├─ ② for step in steps:
  │      result = execute_step(...)       每步 1 次请求
  │      done.append({..., "result": result})
  │      if enable_replan and step_index % 2 == 1:   ← 每 2 步检查一次，控制成本
  │          decision = replan(...)
  │          if decision == "replan": 替换剩余 steps
  │          if decision == "done":   提前跳出
  └─ ③ final = summarize(task, done)      1 次请求 → 汇总成最终答案
```

### 2.3 什么样的计划是"可执行"的

计划质量决定一切。看两份真实输出的对比：

```json
// ❌ 不可执行：每一条都无法判断"做完了没有"
{"steps": [{"goal": "研究 AI Agent 现状"}, {"goal": "继续深入分析"}, {"goal": "总结"}]}

// ✅ 可执行：目标具体、有完成标准、步骤之间依赖弱
{"steps": [
  {"id": 1, "goal": "查 2026 年 Agent 领域的 3 个主流技术方向", "done_when": "列出方向名 + 每个方向一句话定义"},
  {"id": 2, "goal": "查每个方向的一个代表项目", "done_when": "每个方向至少 1 个项目名和它的核心能力"},
  {"id": 3, "goal": "查每个方向的一个局限或争议", "done_when": "每个方向至少 1 条负面评价"},
  {"id": 4, "goal": "汇总成对比表", "done_when": "3 行 × 4 列（方向/代表项目/核心能力/局限）"}
]}
```

四个可执行的要素：**单一动作**（不含"和"）、**具体对象**（查什么、查几个）、**可验证的完成标准**（`done_when`）、**弱依赖**（步骤 1/2/3 可以并行）。

`done_when` 这一栏是很多人会漏的关键设计：它既约束了模型"做到什么程度算完"，也让你的代码可以在执行后**自动判断这一步是否合格**（把 `done_when` 和 `result` 一起喂给一个小模型做判定即可），从而知道什么时候该 replan。

### 2.4 该用 Plan 还是 ReAct

| 判断维度 | 用 ReAct | 用 Plan-and-Execute |
|---|---|---|
| 步骤数量 | 少（2–4 步） | 多（≥ 4 步） |
| 步骤间依赖 | **强**（下一步取决于这一步的结果） | **弱**（步骤可以独立做） |
| 能否事先列清 | 不能（要看了才知道） | 能 |
| 典型任务 | 调试报错、定位文件、多跳检索 | 调研报告、批量处理、多文件重构 |
| 成本特征 | 步数多时平方增长 | 线性增长（每步不带全部历史） |
| 人的参与点 | 几乎没有 | **可以审核/修改计划**（这是产品优势） |

**一个实用的分界线：问自己"第 2 步的输入是不是第 1 步的输出？"** 如果是（强依赖），用 ReAct；如果各步都只需要原始任务信息（弱依赖），用 Plan —— 而且可以并行执行，速度提升是线性的。

### ⚠️ 常见坑

- **现象**：planner 返回的 JSON 被包在 markdown 代码块里（前后各有一行三反引号，还标着 json），`json.loads` 直接抛 `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`。**原因**：模型习惯把 JSON 包起来。**怎么改**：写一个 `extract_json()`：先找第一个 `{` 和最后一个 `}` 截取，再 `json.loads`；失败则重试一次并把错误告诉模型（第 03 章讲过结构化输出的完整做法）。
- **现象**：计划第 1 步是"调研 A"，模型在 execute 里把 A、B、C 全调研完了，后面几步变成重复劳动。**原因**：executor 的提示词没有限定范围。**怎么改**：在 executor 提示词里加硬约束："**只做这一步，不要扩展范围；如果你认为还需要别的步骤，请在结果末尾用「建议：」注明**"。
- **现象**：任务跑完，最后的汇总答案很水，像是把各步结果拼了一遍。**原因**：缺了最后的 `summarize` 步骤，或者汇总提示词没给任何要求。**怎么改**：汇总必须是一次**独立的请求**，提示词里写清输出形态（"对比表 + 三点结论 + 数据来源"），而不是让 executor 顺带总结。
- **现象**：开了 replan 之后，Agent 每步都想 replan，把计划改得面目全非。**原因**：replan 提示词太宽松，或者检查频率太高。**怎么改**：① 提示词里明确"**只在原计划出现明显错误或已完成时才改**"；② 降低检查频率（每 2–3 步一次）；③ 限制 replan 次数上限（如 2 次），超了就照原计划执行完。

## 3. Reflection：让模型批判自己

### 3.1 两个层次，效果差一个数量级

**Reflection（反思）** 的思路：让模型检查自己的输出，然后改进。听起来很美，但**它的效果几乎完全取决于批判来自哪里**。

| 层次 | 谁来批判 | 效果 | 例子 |
|---|---|---|---|
| **L1 自我批判** | 模型自己（"你觉得这段写得怎么样？"） | **不稳定**，经常原地打转甚至越改越差 | 让模型"再检查一遍这篇文案" |
| **L2 带外部信号的批判** | 外部客观信号：测试结果、编译错误、检索到的证据、rubric 打分器 | **可靠**，这是 Reflexion 论文真正的贡献 | 用单元测试的失败信息指导修 bug |

Reflexion 论文（Shinn 等，2023）在代码生成任务上做的事很清楚：**跑单元测试 → 把失败的测试信息作为反馈 → 让模型根据具体错误修改 → 把"这次学到了什么"存进记忆**。HumanEval 上的 pass@1 从基线提升到了 91%。注意：**让模型变强的不是"反思"这个动作，而是"外部信号"这个东西。**

### 3.2 陷阱：没有外部信号时，它会越改越自信但没变好

这个现象值得单独讲，因为它反直觉、且很多人踩过。

你写一个"自我批判 → 修改 → 再批判"的循环，跑 5 轮。观察会发生什么：

```text
第 1 轮：模型说"我觉得内容不错，但可以更简洁"→ 删掉了一些细节
第 2 轮：模型说"论证还不够有力"→ 加了两段套话
第 3 轮：模型说"语言可以更专业"→ 把"帮你"改成"为您提供支持"
第 4 轮：模型说"结构可以更清晰"→ 加小标题、加过渡句
第 5 轮：模型说"已经是一份高质量的回答了"（自我评分 9/10）
```

真实情况是：**第 1 版最有用，第 5 版最啰嗦。** 三个原因：

1. **模型对自己的错误判断力弱**：它对"什么算好"的判断和它对"什么是答案"的判断一样，都是概率生成 —— 不是评估。它能写出"这段存在逻辑跳跃"这种话，但这句话本身可能是编的。
2. **没有外部锚点，修改方向就是随机的**：每轮"改进"都是重新采样一次，**改动 ≠ 改善**，累积下来往往是漂移。
3. **任务本身没有唯一正确答案时更糟**：创作、文案、开放式建议，任何改动都能自圆其说，所以循环永远不会"满意"，只会越来越大（`over-editing`，过度修改 —— 把本来对的地方改错，是反思循环最常见的副作用）。

**结论：没有外部信号的反思，最多做一轮；有外部信号的反思，值得做多轮。** 这不是保守，这是工程判断。

### 3.3 实现：带 rubric 的批判 + 明确的停止条件

正确的反思实现要抓住三点：**给批判者一个具体的检查清单（rubric）、只接受可验证的问题、限制轮数并保留最好的版本**。

```python
CRITIC_PROMPT = """你是严格的审稿人。按下面的检查清单，逐条判断这份回答是否合格。

检查清单：
1. 是否直接回答了用户的问题？（有没有跑题）
2. 有没有出现用户没有提供过的具体数字、日期、文件名？（警惕编造）
3. 有没有无法验证的绝对化表述？（"所有""一定""从来不"）
4. 是否包含了用户明确要求的信息？（逐项对照需求）

只输出 JSON：
{"issues": [{"item": 2, "quote": "原文片段", "problem": "问题描述", "fix": "具体怎么改"}],
 "verdict": "pass 或 revise"}

若没有任何问题，输出 {"issues": [], "verdict": "pass"}。

用户需求：%s
回答全文：%s"""

def reflect(question, answer, rubric=None, max_rounds=2):
    """带 rubric 的反思循环：只改被指出问题的部分，最多 max_rounds 轮。"""
    best, best_issues = answer, None
    for round_no in range(1, max_rounds + 1):
        raw = chat(CRITIC_PROMPT % (question, best), system="你只输出 JSON。")
        review = json.loads(extract_json(raw))

        if review["verdict"] == "pass" or not review["issues"]:
            break                                   # ← 没有问题就停，不要硬改

        if best_issues is not None and len(review["issues"]) >= len(best_issues):
            break                                   # ← 问题没变少 → 停止（越改越差的信号）

        best_issues = review["issues"]
        fixes = "\n".join("- 第 %s 条（%s）：%s" % (i["item"], i["quote"], i["fix"])
                          for i in review["issues"])
        revised = chat(
            "下面是原回答，以及审稿人指出的具体问题。**只修改被指出的部分**，"
            "其他内容保持原样，不要新增无关内容。\n\n原回答：\n%s\n\n需要修复的问题：\n%s"
            % (best, fixes), system="你只输出修改后的全文。")
        if revised.strip() == best.strip():
            break                                   # ← 模型没改动 → 停止
        best = revised
    return best
```

**四个值得照抄的设计：**

1. **rubric 是具体的、可验证的**（"有没有出现用户没提供的数字"），而不是"你觉得好不好"。可验证的问题才可能被真的修复。
2. **`issues` 必须包含 `quote`（原文片段）**：强制批判者定位到具体位置。只说"论证不够有力"的批判一律不采信 —— 那种"问题"改起来就是重新写一遍，等于随机漂移。
3. **`len(review["issues"]) >= len(best_issues)` 就停**：问题数量没减少，说明这轮修改没有实际收益。**这是"越改越差"最实用的早期信号。**
4. **返回 `best` 而不是最后一版**：不要默认"最新的就是最好的"。工程上应该保留每一版并对比，甚至用外部指标（测试通过率、用户反馈）选最终版。

### ⚠️ 常见坑

- **现象**：反思 3 轮后，回答变成了套话堆砌，比第 1 版还长一倍。**原因**：L1 自我批判 + 无 rubric + 轮数太多，典型的 over-editing。**怎么改**：加 rubric，`max_rounds=1`，并且提示词里写明"**不要新增无关内容**"。
- **现象**：每次反思都说"pass"，什么都不改。**原因**：批判提示词太客气（"请温和地指出问题"），模型倾向于给好评。**怎么改**：把批判者的角色写硬（"你是严格的审稿人"），并给出**必查清单**；还可以让批判者带上"如果通过，请说明每一条为什么通过"。
- **现象**：反思把正确答案改错了。**原因**：这是无外部信号反思的固有问题 —— 模型把"对的"当成"不够好"来改。**怎么改**：**先给个基准**。任何反思流程上线前，先拿 10 个有标准答案的样本测一下"反思前 vs 反思后的准确率"。如果没提升，就别开反思（第 12 章会讲怎么建这种评测集）。
- **现象**：`max_rounds` 设成 5，成本翻了 5 倍，效果没变。**原因**：反思的收益通常在第 1 轮就吃完了。**怎么改**：默认 1 轮，只有存在**外部信号**（测试、编译、检索结果）时才放宽到 2–3 轮。

## 4. 三者组合：Plan → Execute(ReAct) → Reflect

三种范式不是互斥的，真实项目里的常见组合是这样一条流水线：

```text
        用户任务
           │
           ▼
 ① Plan（Planner）───────────────────────► 产出：结构化步骤列表（可人工审核）
           │
           ▼
 ② Execute（每步用 ReAct + 工具）─────────► 产出：每步的结果 + trace
     · 步骤间弱依赖 → 可并行
     · 单步内部需要工具 → 用第 05 章的 ReAct 循环
     · 执行中发现计划不成立 → replan（回①）
           │
           ▼
 ③ Reflect（带外部信号）─────────────────► 产出：修订后的最终答案
     · 有测试/检索证据 → L2 反思，最多 2 轮
     · 纯创作类 → L1 一轮，或干脆不反思
           │
           ▼
       最终答案 + 成本报告
```

**每一层解决一个问题，也各自带来一份成本**：Plan 带来"全局视野"，代价是"计划错了会一路错"（靠 replan 兜）；Execute 用 ReAct 带来"能看环境反馈"，代价是走一步看一步的 token 开销；Reflect 带来"质量提升的机会"，代价是"没有外部信号时可能反而变差"。

`code/ch06_paradigms.py` 里的 `pipeline()` 就是这个组合的最小实现（约 60 行），三个开关分别控制要不要上哪一层 —— 你可以用它做"逐层加上去，看效果和成本怎么变"的实验。

### ⚠️ 常见坑

- **现象**：三层串起来后，最终答案比只跑 ReAct 还差。**原因**：planner 的计划不完整 → executor 缺了关键信息 → reflect 只能对着残缺的输入"润色"，把问题掩盖过去。**怎么改**：**逐层验证**。先只跑 plan（打印步骤看合不合理），再开 executor，最后才开 reflect。任何一层输出不对，不要指望下一层能救回来。
- **现象**：流水线跑一次要 25 秒，用户以为程序死了。**原因**：所有请求串行，且没有中间反馈。**怎么改**：把每一步的进展流式打出来（"正在规划…"、"正在执行第 2/4 步…"），弱依赖的步骤并行执行（见动手练习 3），必要时把 planner 换成更快的小模型。

## 5. 决策表：拿到任务该选哪个

**这是本章最该记住的一页。** 按从上到下的顺序问自己：

| 任务特征 | 推荐范式 | 理由 | 别用它 |
|---|---|---|---|
| 一次问答就能答，或答案在模型知识里 | **直接调用** | 加任何范式都是浪费 | 别加 CoT，事实类问题加重幻觉 |
| 需要精确计算、实时数据、私有文件 | **ReAct + 工具** | 推理解决不了数据问题 | 别用纯 CoT 硬算 |
| 一次性的多步推理（算术、逻辑、约束） | **CoT**（可加 Self-Consistency） | 无外部信息，全靠推理链 | 事实检索、严格 JSON 输出 |
| 步骤 ≥ 4 且步骤间依赖弱、能事先列清 | **Plan-and-Execute** | 线性成本、可并行、计划可人工审核 | 强依赖任务会一路错到底 |
| 步骤间强依赖 / 要看环境反馈才知道下一步 | **ReAct** | 走一步看一步是它的强项 | 步数多时成本平方增长 |
| 有客观验收标准（测试、编译、检索证据） | **ReAct + Reflection(L2)** | 外部信号让反思真正有效 | 没有外部信号别硬上 L2 |
| 创作类、主观评价类 | **Reflection(L1) 最多一轮** | 提升可读性、补充遗漏 | 多轮会啰嗦、漂移、同质化 |
| 对可靠性要求高（关键决策） | **Self-Consistency / 多路投票 + 人工复核** | 用钱换方差下降 | 成本 ×N，不能无脑用 |

**决策口诀：先问"有没有外部信息"（没有 → CoT 系列；有 → ReAct / RAG），再问"能不能事先规划"（能 → Plan；不能 → ReAct），最后问"有没有客观验收标准"（有 → 可以反思；没有 → 最多一轮）。**

### ⚠️ 常见坑

- **现象**：照着决策表选了"最强"的那一档，上线后成本超预算 5 倍。**原因**：决策表选的是"能力上限"，不是"成本上限"。同一行里"够用"的做法可能便宜一个数量级。**怎么改**：从表的**最上面一行往下试**，第一个能达标的就是答案；不要把决策表当成"越往下越好"的排行榜。
- **现象**：任务一开始是"多步调研"（适合 Plan），跑到一半发现有强依赖（该用 ReAct），但代码已经写死成 Plan 了。**原因**：范式的**切换成本**没有被提前考虑。**怎么改**：把范式做成可配置项（`mode="react" / "plan"`），并在计划里标出"哪一步可能变成强依赖"；真遇到混合型任务时，**外层用 Plan、内层单步用 ReAct**（第 4 节那条流水线就是为这个场景准备的）。

## 6. 范式不是越多越好

### 6.1 同一个任务，五种做法的成本账

任务：**"写一个函数，把嵌套 JSON 里的所有键名拍平成点分路径（如 `a.b.c`），并通过给定测试。"**

| 做法 | 请求次数 | token（约） | 耗时（约） | 测试通过率（量级参考） |
|---|---|---|---|---|
| 直接调用 | 1 | 900 | 3s | 40% |
| CoT | 1 | 1300 | 5s | 55% |
| ReAct + 工具（跑测试） | 5 | 8000 | 12s | 75% |
| Plan-and-Execute | 5 | 6000 | 14s | 70% |
| ReAct + Reflection(L2，2 轮) | 7 | 11000 | 20s | 85% |

> 表里的数字是**量级参考**，不是基准测试结果。请把它当"直觉校准"，而不是"事实"。你自己的任务必须自己测（第 12 章）。

看这张表要读出三个结论：

1. **范式能提效果，但价格差是 10 倍量级**（900 token → 11000 token）。
2. **并不是每一步都在赚钱**：这个任务上 ReAct 的 5 次请求比 Plan 的 5 次更值（75% vs 70%），因为**跑测试的反馈比规划更有价值**；而 Plan 更适合那种"没有可执行反馈、纯粹步骤多"的任务。
3. **最高配置不等于最优配置**：85% 的通过率如果已经达到产品要求，就没必要再往上加。**"够用"是一个工程判断，不是技术炫耀。**

### 6.2 范式税

每加一层范式，你都要多付这些：

- **调试成本**：出问题时，可能是 planner 错、executor 错、critic 错，还是它们之间的交接错？三层结构的问题定位难度是线性的，而组合出来的失败模式是接近指数的。
- **失败模式变多**：Plan 会"计划错 + 执行偏"，Reflect 会"越改越差"，Self-Consistency 会"多数票投出一个自信的错"。
- **延迟**：串行请求次数直接变成用户等待时间。20 秒的响应，用户已经会开始怀疑程序卡死了。
- **可评估性下降**：单次调用只有"对/错"，三层流水线要分别评估每层的贡献 —— 没有 trace，你根本不知道是哪一层在拖后腿。

**经验法则（三条）：**

1. **先用能过的最简单方案。** 直接调用 → CoT → ReAct → Plan → Reflect，按这个顺序试。
2. **每加一层，必须有一次评测数据支撑。** 说不出"加了之后指标从 X 涨到 Y"，就不该加。
3. **给每一层都留一个"关掉它"的开关。** `enable_plan`、`enable_reflection` 之类的参数，让你能随时做 A/B 对比 —— 这也是 `ch06_paradigms.py` 里所有函数都带开关的原因。

### ⚠️ 常见坑

- **现象**：把三种范式全串起来，效果还不如只有 ReAct。**原因**：每一层都有各自的失败模式，层数多了以后"某一层出错"的概率累积上去了；而且 replay/replan 会互相干扰。**怎么改**：一次只加一层，测完再加下一层；每层都要能单独关掉。
- **现象**：Plan 出来的步骤有 12 步，执行到第 5 步就超时了。**原因**：planner 提示词没有限制步骤数量。**怎么改**：在 planner 提示词里写死"**2–6 步**"，超过就在代码里截断或让它重新规划。
- **现象**：用 Self-Consistency 投票，5 次里 4 次给出同一个错误答案。**原因**：多数投票只能降低**随机**错误，对**系统性**错误（模型根本不知道这个知识）完全无效。**怎么改**：多路投票之前先确认"模型有足够的信息"，信息不足就该上 RAG 或工具，投票解决不了。

## 本章小结

1. **CoT 有效，但只对"需要推理且模型知道相关知识"的任务有效。** 事实检索类用 CoT 只会给幻觉加戏；小模型上收益很小；严格 JSON 输出别混 CoT。
2. **Plan-and-Execute 用"先规划"换全局视野和线性成本**，代价是"计划错了会一路错" —— 所以 **replan 不能省**。判断分界线：第 2 步的输入是不是第 1 步的输出？不是就用 Plan。
3. **Reflection 的效果几乎完全取决于批判的来源。** L2（外部信号：测试、编译、检索证据）可靠；L1（自我批判）不稳定，**没有外部信号时模型会越改越自信但没变好** —— 所以最多一轮。
4. **反思循环的四个保命设计**：具体 rubric、要求定位到原文片段、问题没变少就停、返回"最好的一版"而不是"最新的一版"。
5. **范式组合（Plan → Execute(ReAct) → Reflect）是真实项目的常见形态**，每一层解决一个问题，也各自带来一份成本和失败模式。
6. **范式不是越多越好。** 同一任务从"直接调用"到"ReAct + 反思"，token 差 10 倍量级 —— 先上最简单的，每一层都要有评测数据支撑，并且永远留一个关掉它的开关。

## 自测题

**Q1. 为什么 CoT 对"珠峰多高"这类问题无效，甚至有害？**

<details><summary>点击查看答案</summary>

因为这类问题的答案在模型的参数里，**不需要推理，只需要检索**。CoT 不会产生新知识，它只是把已有知识整理成步骤。当模型不知道答案时，CoT 会让它编出一段"看起来很严谨"的推理链 —— 这比直接说错更危险，因为**推理的形式让人更愿意相信它**。正确做法是上工具或 RAG。

</details>

**Q2. Plan-and-Execute 的最大风险是什么？为什么 replan 不能省？**

<details><summary>点击查看答案</summary>

最大风险是**计划一旦错了会被完整地执行下去**。ReAct 走错一步能立刻在 Observation 里发现并回头；Plan 是"先规划再执行"，如果第 2 步的前提就错了，后面的步骤全部建立在错误地基上，最后产出一份"每一步都执行得挺认真、但整体是错的"结果。replan 在每个检查点重新判断"原计划还成立吗"，把风险从"整体失败"降到"多花一次请求"。

</details>

**Q3. 为什么"让模型检查自己的输出并改进"经常会越改越差？**

<details><summary>点击查看答案</summary>

因为批判者也是模型，它判断"什么算好"和它生成答案一样是概率性的，**它对自己错误的判断力很弱**。没有外部锚点时，每轮"改进"其实是一次重新采样 —— **改动不等于改善**，累积多轮就是随机漂移。典型后果是 over-editing：把本来对的地方改错、内容越改越长越空。解决办法是给批判者一份具体可验证的 rubric、要求定位到原文片段、问题没变少就停，并且**返回最好的一版而不是最新的一版**。

</details>

**Q4. Reflection 的 L1 和 L2 有什么区别，为什么说"效果差一个数量级"？**

<details><summary>点击查看答案</summary>

L1 是模型自我批判（"你觉得这段怎么样"），L2 是带**外部客观信号**的批判（单元测试结果、编译错误、检索到的证据、rubric 打分器）。Reflexion 论文的贡献正是 L2：把测试失败的**具体信息**作为反馈，让模型知道"错在哪、为什么错"，并把这个教训存进记忆。L1 因为没有外部锚点，模型只能凭感觉改，改对了是运气。所以 L2 值得做多轮，L1 最多一轮。

</details>

**Q5. 同一个任务，"直接调用"和"ReAct + 反思"的 token 可能差 10 倍。那你应该在什么时候上复杂范式？**

<details><summary>点击查看答案</summary>

只有当**简单方案确实过不了**，并且**有评测数据证明复杂一层能带来可衡量的提升**时才上。顺序是：直接调用 → CoT → ReAct → Plan → Reflection，每加一层都记录指标（准确率、通过率、用户反馈）和成本（token、延迟）。三条工程纪律：一次只加一层、每层都留开关可 A/B 对比、说不出"指标从 X 涨到 Y"就不该加。**最高配置不等于最优配置 —— 够用是工程判断，不是技术炫耀。**

</details>

## 结语与下一章

范式选型很像出门选交通工具：两百米的路，走路比叫车快；十公里，地铁比共享单车稳；要去机场赶飞机，才值得叫专车。CoT、Plan-and-Execute、Reflection 都不是"更聪明的模型"，而是三种不同形态的**钞能力**——用对了省时间，用错了只是把账单拉长。

但……不管选哪个范式，你的 Agent 都有一个共同的死穴：**它什么都记不住。** 每次对话开始都是一张白纸；上下文一长就爆；上一轮说过的话，下一轮就"忘了"。本章讲的这些范式能帮它选对"怎么做"，却帮不了它"记住做过什么"。

下一章是第 07 章《记忆与上下文工程》——短期记忆 / 会话记忆 / 长期记忆怎么分层，上下文超限时怎么压缩，token 预算怎么分配。学完那一章，你的 Agent 才真正能"持续工作"。
