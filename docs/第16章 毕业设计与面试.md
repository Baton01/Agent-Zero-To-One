# 第16章 毕业设计与面试

> **本章目标：** 独立设计并交付一个**多智能体应用**（毕业设计），并把它翻译成面试答案：六段式项目表达、追问应对框架、简历公式与反问清单。
> **预计用时：** 16 小时（毕设 10 小时 + 面试准备 6 小时；毕设的实际开发是课后 2~4 周）　**前置章节：** 第15章（综合实战）　**配套代码：** `code/ch16_graduation.py`

---

## 0. 开篇：从"照着做"到"自己定题目"

上个月一次模拟面试，学员把第 15 章那三个项目讲得很顺，指标、失败案例、降级策略一样不缺。面试官合上简历，换了个问法：

> 面试官：「这三个项目如果让你自己定题目，你会做什么？为什么这么定？」
>
> 他：「我可能会做一个企业知识库助手……」
>
> 面试官追问：「那它和你在第 15 章做的文档问答有什么不同？你打算怎么证明它做完了——评测集谁来标？数据从哪来？」
>
> 他：「这些我还没想过，教程里是把题目和指标都写好了的。」

面试官最后说了一句他记了很久的话："跟着教程做完，说明你能执行；能自己出题并证明它有效，才说明你能判断。我花钱买的是判断力。"

**问题不在于你做得少，而在于"题目不是你自己定的"。** 跟着配方走，你练的是执行力；自己定题目并证明它有效，练的是判断力——而面试官花钱买的是判断力。

**先排除两个错误做法：** ① **把第 15 章的项目换个皮当毕设**——面试官两句就能问出来（"你这个和标准 RAG 有什么不同？"），而且你会失去唯一一次练"从需求到交付"全流程的机会；② **一上来选一个宏大题目**（"企业级 AI 中台"）——三周后你会有 8 个半成品模块和 0 个可验证结果，评审第一句就是"这东西怎么算做完了"。

十七章到这里就是最后一章了，所以它分两部分：**第一部分**教你选题、写需求与技术方案、排四个里程碑、做评估、交付（约 2~4 周）；**第二部分**把这三个月的学习翻译成面试官能听懂、能追问、能记住的答案。

## 第一部分：毕业设计

## 1. 毕业设计的定位：不是把第 15 章再做一遍

**一句话定位：** 独立完成一次"从模糊需求到可验证交付"的完整闭环，产出一个**多智能体应用**，并且能用数据说明它好不好。

| 维度 | 第 15 章（练习） | 毕业设计（项目） |
|---|---|---|
| 题目 | 给定三个，照做 | **自己选**，并说明为什么选它 |
| 需求 | 已写好，含指标 | **自己写**，指标自己定并解释依据 |
| 方案 | 已给出配方 | **自己做取舍**，至少 2 个关键决策要写替代方案对比 |
| 评估 | 已给出评测集配方 | **自己建 ≥20 条评测集**，含反指标 |
| 交付 | 跑通 + trace | 别人照 README 10 分钟能跑通 + 3 分钟演示 |
| 失败 | 记录 5 个 bad case | **失败分类**（按环节归类）+ 每类的处理策略 |

**三条硬要求（评审会直接按这三条打分）：**
1. **多智能体不是装饰**：至少两个角色，且**必须能说清为什么单 Agent 不够**（第 11 章的四条判断清单）；
2. **有可量化的评估**：≥20 条评测集、≥3 个指标、其中至少 1 个反指标（误报率/误拒率/编造率）；
3. **有真实取舍**：至少 2 个关键决策写了"替代方案 + 为什么没选 + 代价是什么"。

### ⚠️ 常见坑

- **现象**：把"用了多 Agent"当成目标，硬拆三个角色，结果单 Agent 版本效果更好。**怎么改**：毕设允许你**用数据证明不该拆**——写一版单 Agent 基线，把"多 Agent 提升 X 个点、成本上升 Y%"作为结论，这比硬拆更有说服力。
- **现象**：题目太大，做完 60% 就到期了。**怎么改**：选题时先写"明确不做什么"（≥3 条），把范围砍到"能在 2~4 周内交出完整闭环"。
- **现象**：只在最后一周做评估，发现指标没法算（标注数据没留、评测集没建）。**怎么改**：评测集是**里程碑 1 就要建的**，哪怕只有 5 条——它决定你后面每一步能不能判断"变好了没有"。

## 2. 选题指南：8 个方向 + 评分预估

评分口径（满分 100，评审就是按这个结构打分的）：

```
选题与需求 15　技术方案与取舍 20　实现与代码质量 20　评估与失败分析 25　交付与演示 10　文档与可复现 10
```

| # | 方向 | 核心能力点 | 难度·工时 | 评分预估 | 最容易被扣分的地方 |
|---|---|---|---|---|---|
| 1 | **个人知识助理** | RAG 全链路 + 增量索引 + 引用校验 + 多轮追问 | ★★☆ · 20–25h | 85–92 | 退化成"第 08 章作业"：没有增量更新、没有评测集 |
| 2 | **自动化周报生成** | 多源聚合（commit/issue/文档）+ 时间窗 + 去重 + 模板化输出 | ★★☆ · 18–22h | 82–90 | 数据源权限拿不到；先做离线样例数据版本 |
| 3 | **竞品监控分析** | 定时抓取 + 变更检测（diff）+ 变更摘要 + 分流通知 | ★★★ · 25–30h | 80–88 | 合规与反爬边界不写清；"抓不到"没有降级方案 |
| 4 | **招聘简历筛选** | 简历解析 → 结构化抽取 → 打分 → 排序 + 理由 | ★★★ · 25–30h | 78–88 | 偏见与隐私；必须写脱敏方案与"不做自动拒绝"的边界 |
| 5 | **智能客服工单分流** | 分类 + 优先级 + 路由 + 转人工（拒答）+ 混淆矩阵 | ★★★ · 25–32h | 85–93 | 类别不均衡时只报准确率；要报每类召回 |
| 6 | **内容审核流水线** | 规则 + 模型两级过滤 + 阈值 + 人工复核队列 + 审计日志 | ★★★★ · 30–36h | 82–90 | 只做模型不做规则（成本爆炸）；漏杀/误杀指标要分开 |
| 7 | **数据分析助手** | 自然语言 → SQL → 只读执行 → 图表 + 结论 + 失败重试 | ★★★★ · 32–40h | 84–93 | SQL 不校验就执行（重大扣分）；必须只读 + 行数上限 |
| 8 | **你自己的选题** | 自己定 | ? | ? | 过不了下面四问就别选 |

**四步选题法（四问全过才动手）：**

1. **数据能不能拿到？** 具体到"我能拿到 30 条可比对的样本"。拿不到真实数据的，先用样例数据把链路跑通，并写清"接入真实数据的接口在哪"。
2. **效果能不能验证？** 有没有客观指标（准确率/召回率/延迟/成本）。纯主观题（"生成的文章好不好"）要降级为"一致性 + 人工评分（3 人打分取均值）"，并提前说明评分标准。
3. **有没有真实取舍？** 能不能写出至少两组"方案 A vs 方案 B，为什么选 A"。写不出来说明这题没有技术含量。
4. **四个里程碑能不能跑完？** 用第 5 节的标准估时，总工时超过 40 小时的题目，砍到 30 小时以内。

**⚠️ 一个反直觉的建议：选题偏向"脏数据 + 有验证"的方向。** 数据干净、验证不了的题目（比如"做一个聊天机器人"）看上去好做，实际最难拿分——因为没有失败、没有指标、没有故事。

## 3. 需求文档模板

**为什么要写？** 因为不写你会**在开发中途换需求**（第 10 天突然觉得"应该加个前端"），最后交出来的东西什么都有、什么都不完整。需求文档的作用是**把范围钉住**。

```markdown
# 需求文档：<项目名>
## 1. 用户是谁
<一个具体角色 + 一个具体场景。不要写"所有需要 XX 的人"。>
## 2. 解决什么问题
<他们现在怎么做？成本是多少（分钟/次、错误率）？>
## 3. 成功标准（可量化，3~5 条，含至少 1 个反指标）
| 指标 | 目标 | 怎么测 |
## 4. 明确不做什么（≥3 条）
## 5. 边界与约束
<数据范围（哪些数据可用/不可用）、成本上限、延迟要求、合规要求>
```

**填好的示例（节选，方向 5 智能客服工单分流）：**

| 项 | 内容 |
|---|---|
| 用户是谁 | 客服组 6 人，每天处理约 300 张工单，早班高峰集中在 9:00–11:00 |
| 解决什么问题 | 目前全靠人工看标题分流，平均每张 40 秒，高峰积压；错分到错误组要转两次，用户等待翻倍 |
| 成功标准 | ① 分流准确率 ≥ 85%（人工抽检 100 张）；② **错分率 ≤ 5%**（反指标：宁可转人工也不许错分）；③ 转人工比例 ≤ 15%；④ P95 延迟 ≤ 3 秒；⑤ 单张成本 ≤ 0.01 元 |
| 明确不做什么 | 不自动回复用户、不做情感分析与质检、不做知识库问答、不替代人工结单 |
| 边界与约束 | 只用近 90 天的历史工单做训练/评估；用户手机号、订单号入库前脱敏；每月成本上限 200 元 |

**检查清单（写完逐条打勾）：**
- [ ] 成功标准里每个数字都有"怎么测"，否则它不是标准，是愿望。
- [ ] 有反指标（更低的更好），防止主指标被刷。
- [ ] "不做什么" ≥ 3 条，且每条都对应一个你**本来想做**的功能。
- [ ] 用户是具体角色，不是"所有用户"。

## 4. 技术方案模板

**架构图（文字描述就够，评审看的是数据流不是配色）：**

```text
┌──────────────────────────────────────────────────────┐
│ 入口层   CLI / 定时任务 / 一个 HTTP 接口（三选一即可）   │
└───────────────────────┬──────────────────────────────┘
┌───────────────────────▼──────────────────────────────┐
│ 编排层   Supervisor（分派 + 轮次上限 + 交付清单检查）    │
└──────┬────────────────┬─────────────────┬────────────┘
┌──────▼──────┐  ┌──────▼──────┐  ┌───────▼───────────┐
│ 角色 A      │  │ 角色 B      │  │ 角色 C            │
│ 解析/检索   │  │ 判断/生成   │  │ 校验/复核          │
└──────┬──────┘  └──────┬──────┘  └───────┬───────────┘
┌──────▼────────────────▼─────────────────▼───────────┐
│ 基础设施   证据表 / 索引 / 工具注册表 / Trace / 评测集 │
└──────────────────────────────────────────────────────┘
```

**模块划分表（每个模块都要能独立测）：**

| 模块 | 职责 | 输入 → 输出 | 复用前 15 章的哪一块 |
|---|---|---|---|
| 编排器 | 分派任务、控制轮次、检查交付清单 | 用户请求 → 最终产出 | 第 11 章 Supervisor |
| 角色 A | 解析与检索 | 请求 → 证据/候选 | 第 04、05、08 章 |
| 角色 B | 判断与生成 | 证据 → 结构化结论 | 第 03、06 章 |
| 校验器 | 引用校验、拒答、格式校验 | 结论 → 通过/打回 | 第 08、12 章 |
| 基础设施 | 工具、trace、成本统计 | — | 第 04、12、13 章 |
| 评测 | 评测集跑分与报告 | 评测集 → 指标 | 第 12 章 |

**为什么这样选（每个关键决策写一句话理由 + 依据）：** 例如"选 Supervisor 而不是 Graph：任务分支只有 3 种且不需要断点恢复，Supervisor 的实现与调试成本更低（第 11 章的判断清单）"。

**替代方案对比（至少 2 个关键决策，这是评审最看重的部分）：**

| 决策点 | 选择 | 替代方案 | 为什么没选 | 代价 |
|---|---|---|---|---|
| 编排方式 | Supervisor | Graph / 自由对话 | 分支少、无需断点恢复；自由对话无法终止 | 无法做复杂回滚 |
| 检索 | 混合检索 + RRF | 纯向量 | 18% 的查询含编号/数字，纯向量 Recall 掉 12 个点 | 多一路索引要维护 |
| 校验 | 规则校验 + 二次证伪 | 只靠 prompt | prompt 拦不住幻觉引用（实测漏 3/20） | 成本上升约 35% |

## 5. 实现路径：四个里程碑

**别一口气写完。** 每个里程碑都要有**可运行的产出**，做完就能演示给同学看，也能立刻发现问题。工时为参考值（按每天 2 小时估算）。

| 里程碑 | 可运行产出 | 验收问句 | 参考工时 |
|---|---|---|---|
| **M1 骨架跑通** | 一条命令跑通端到端（可离线 mock），打印中间结果与最终产出 | 换一台机器 10 分钟内能跑出结果吗？ | 6–8h |
| **M2 接真实数据与模型** | 真实数据 + 真模型跑通，落 trace（token/延迟/成本） | 单次成本与 P95 延迟是多少？ | 8–10h |
| **M3 评估闭环** | ≥20 条评测集 + 一键跑分 + 指标报告 + 5 条 bad case | 你能说出最难过的 3 条是哪条、为什么吗？ | 8–10h |
| **M4 交付打磨** | README 四问齐全 + 已知限制 ≥3 条 + 3 分钟演示脚本 | 陌生人照 README 能复现你的指标吗？ | 4–6h |

**每个里程碑的常见卡点：**
- **M1**：卡在"想先把架构设计完美"。→ 先让数据流跑通，**丑陋但完整**胜过"优雅但跑不起来"。
- **M2**：卡在数据清洗（占掉 60% 时间）。→ 给自己设硬上限（清洗不超过 1 天），剩余脏数据处理写成"已知限制"。
- **M3**：卡在标注（20 条标注看起来很轻松，实际要 3 小时）。→ 评测集**边开发边攒**，每遇到一个失败案例就补一条。
- **M4**：卡在"再改一个功能"。→ 冻结功能，只修 bug 与补文档；演示脚本要**照着念两遍**。

## 6. 评估要求：20 条评测集 + 指标报告 + 失败分类

**评测集配方（按你的项目类型调整比例，但四类都要有）：**

| 类型 | 占比 | 作用 | 例子（工单分流项目） |
|---|---|---|---|
| 常规样本 | 50% | 主指标 | 典型退款工单 |
| 边界样本 | 20% | 暴露真实难度 | 一句话里有两个诉求 |
| 拒绝样本 | 15% | 考"该说不" | 与工单无关的闲聊 |
| 对抗样本 | 15% | 考鲁棒性 | 含错别字、含指令注入（"忽略以上规则"） |

**指标报告模板（一页，含系统信息与反指标）：**

```markdown
# 评估报告 v3
系统：model=deepseek-chat, temperature=0.2, index=v3, 日期=2026-09-20
主指标：分流准确率 0.87（n=20）｜ 转人工率 0.12
反指标：错分率 0.04 ｜ 编造率 0（引用校验拦截 2 处）
工程指标：P95 延迟 2.4s ｜ 单张成本 0.006 元
5 条 bad case：
  1. #07 混合诉求（退款+改地址）→ 错分到售后 → 分类标签设计问题，非模型问题
  ...
改动记录：v3 加了"双诉求优先转人工"规则，错分率 0.09 → 0.04，转人工率 +3%
```

**失败分类（比 bad case 列表更有说服力）：** 把每个失败归到**环节**上，而不是写成"模型不行"：

| 环节 | 表现 | 归因 | 处理策略 |
|---|---|---|---|
| 输入解析 | 数据字段缺失、格式怪 | 数据质量 | 清洗 + 缺字段走默认分支 |
| 检索/召回 | 正确的材料没进候选 | 切片/检索 | 调切片、加混合检索 |
| 工具调用 | 参数错、超时、返回异常 | 工具契约 | 严格 schema + 重试 + 降级 |
| 推理/判断 | 材料在，结论错 | 提示词/模型 | 拆步、加对比示例、换模型 |
| 输出格式 | JSON 解析失败、字段缺失 | 约束不足 | schema 校验 + 一次重试 |
| 拒答 | 该拒没拒 / 不该拒拒了 | 阈值 | 用评测集扫阈值，双指标一起看 |

**结论要落到"归因分布"上**："20 条失败里，检索类 9 条、推理类 6 条、格式类 3 条、拒答类 2 条；因此下一步优先改切片（影响面最大）。"——这句话是评审最喜欢听到的。

## 7. 交付清单

**这一节的结构不用手搭**：配套代码 `code/ch16_graduation.py` 会直接生成项目骨架（目录结构 + README 模板 + 评测集模板 + 配置模板），你只需要往里填自己的东西：

```bash
cd code
AGENT_MOCK=1 python ch16_graduation.py --name my-agent --out ../04-Outputs/my-agent   # 生成骨架
AGENT_MOCK=1 python ch16_graduation.py --name my-agent --out ../04-Outputs/my-agent --dry-run  # 只看会生成什么，不落盘
```

生成的 README 里"怎么跑/怎么配/怎么扩展/已知限制"四节都是**待填空位**（带 `TODO` 标记），`evals/cases.jsonl` 里有 3 条示例样题和字段说明，`config.json` 里预置了模型名、温度、阈值等可调参数——**改造成自己的项目，比重搭一遍省半天**。

**仓库结构（照这个搭，评审一眼就能找到东西）：**

```text
<项目名>/
├── README.md            # 给陌生人的唯一入口
├── requirements.txt     # 依赖（能少则少）
├── .env.example         # 配置模板（key 用占位符，绝不提交真 key）
├── config.json          # 模型、阈值、路径等可调参数
├── src/                 # 代码（入口一个文件：main.py）
├── evals/
│   ├── cases.jsonl      # ≥20 条评测集
│   ├── run_eval.py      # 一键跑分
│   └── report.md        # 指标报告
├── traces/              # 每次重要运行的 trace
└── docs/
    ├── requirements.md  # 需求文档（第 3 节模板）
    ├── design.md        # 技术方案 + 替代方案对比（第 4 节模板）
    └── failures.md      # 失败分类与处理（第 6 节）
```

**README 必须包含四件事（顺序照抄）：**
1. **怎么跑**：三条命令以内，含离线模式（`AGENT_MOCK=1`）与在线模式；
2. **怎么配**：`cp .env.example .env`，填哪个字段，没有 key 会怎样；
3. **怎么扩展**：加一个工具/换一个模型/换一批数据分别要改哪个文件（写文件路径，不要写"详见代码"）；
4. **已知限制**：≥3 条，含一条"我知道但这次没做"和一条"数据/环境导致的边界"。

**演示方式（三选一，都要有备份）：**
- **一条命令**：`python src/main.py --demo` 输出完整过程（最稳，网络挂了也能演）；
- **3 分钟视频**：0:00–0:30 业务问题 → 0:30–1:30 现场跑一次 → 1:30–2:30 指标与失败 → 2:30–3:00 已知限制与下一步；
- **一页纸指标卡**：主指标 + 反指标 + 成本延迟 + 2 条 bad case（面试时截图用）。

## 8. 优秀毕业设计的共同点 / 常见翻车点

| 优秀毕设的共同点 | 反面 |
|---|---|
| 范围小但闭环完整（能跑、能测、能复现） | 功能多但没一条能验证 |
| 指标真实，主动报反指标与失败 | 只挑好看的数字说 |
| 有 2 组以上替代方案对比，代价写清楚 | 只有"我用了 X"，没有"为什么不是 Y" |
| 失败有分类、有归因分布、有下一步 | 失败列表 = "模型能力有限" |
| 陌生人照 README 能复现 | 只有作者本人的电脑能跑 |
| 能用 60 秒说清"给谁用、解决什么、指标多少" | 讲 5 分钟还在介绍背景 |

| 翻车点 | 后果 | 事前怎么防 |
|---|---|---|
| **做得太大** | 每块都半成品，无人能验证 | 需求文档的"不做什么"写满 3 条 |
| **没有指标只有感觉** | 评审问"好多少"答不上 | 里程碑 1 就建评测集（哪怕 5 条） |
| **无法复现** | 演示当天环境不对，全废 | 离线模式 + `requirements.txt` + 固定随机种子 |
| **只演示 happy path** | 一问失败场景就崩 | 准备 2 个"故意失败"的演示分支 |
| **多智能体是装饰** | 被追问"为什么不用单 Agent"答不上 | 做一版单 Agent 基线，用数据说明 |
| **引用/来源说不清** | 结论不可信 | 证据表 + 引用校验（第 15 章项目 A） |

## 9. 先搞清楚岗位差异

**同一套知识，不同岗位的问法完全不同。** 投递前先看 JD 里的关键词，反推它属于哪一类：

| 岗位 | 主要考什么 | 次要考什么 | 典型问题 | 你该突出的项目 |
|---|---|---|---|---|
| **AI 应用开发** | Prompt 工程、Function Calling、业务落地、成本控制 | 模型原理、工程规范 | "怎么让输出稳定？""怎么把成本降下来？" | L2 研究助手、L3 问答 |
| **Agent 工程师** | Agent loop、工具设计、上下文工程、失败恢复、多智能体 | 评估体系、协议 | "工具调用失败怎么恢复？""什么时候不该用多 Agent？" | L4 审查、L6 Nano Coding Agent |
| **RAG 工程师** | 切片、混合检索、重排、embedding 选型、评估 | 数据工程、向量库运维 | "召回不到怎么排查？""怎么评估 RAG？" | L3 文档问答 |
| **AI 后端** | 服务化、并发、缓存、限流、可观测性、成本 | 模型细节 | "流量涨 10 倍怎么办？""怎么做灰度与回滚？" | L8 生产级 Harness |

**一句话策略：** 面 Agent 岗就把"失败恢复与停止条件"讲深；面 RAG 岗就把"切片实验与评估指标"讲细；面 AI 后端就把"成本、延迟、降级"讲实。**同一段经历，按岗位换重点。**

**面试通常分四关，每关考的东西不一样：**

| 环节 | 时长 | 考什么 | 你该怎么准备 |
|---|---|---|---|
| 电话/视频初筛 | 20–30 min | 简历真实性、表达是否清楚、动机 | 90 秒自我介绍 + 一个项目的六段式（能讲顺就过关） |
| 技术基础面 | 45–60 min | 知识广度与深度（第 11 节那张表） | 每个高频考点 30 秒口述一遍 |
| 项目/系统设计面 | 45–60 min | 取舍、评估、故障排查（本章重点） | 三个项目的追问各准备 5 问 + 两个追问框架 |
| HR / 主管面 | 30 min | 稳定性、协作、预期管理 | 准备好反问清单与"为什么选我们" |

## 11. 高频题分类：每类一个"开门句"

**注意：下面给的是"示范开头"，不是完整答案**——开头的作用是让面试官知道你有结构，后面顺着讲就行。完整答案在题库里。

**① Agent 基础**（什么是 Agent / ReAct / 和 workflow 的区别）
> 开门句："我的理解是，Agent 和 workflow 的分界不在用不用模型，而在**控制权归谁**：workflow 的步骤是人写死的，Agent 是模型自己决定下一步调什么工具、什么时候停。所以判断要不要用 Agent，我一般先问三件事：步骤是否固定、能不能穷举分支、错了要不要能自己纠。"

**② 工具与协议**（Function Calling / MCP / Skills）
> 开门句："工具能不能被用对，八成决定于描述和 schema，而不是模型。我自己踩过的坑是：参数名含糊、错误返回不明确，模型就会乱传参；所以我会要求每个工具写清'什么时候用、什么时候不用、失败了返回什么'。MCP 解决的是另一件事——把 M×N 的适配问题变成 M+N。"

**③ RAG**（切片 / 召回 / Rerank / 评估 / 幻觉）
> 开门句："RAG 的效果上限由召回决定，所以我会把'召回'和'生成'分开评估。切片我会做对比实验——同一批问题跑三档参数看 Recall@5，我自己的数据上 400 字结构切比 800 字高 17 个点，因为块太大语义被稀释。"

**④ 记忆与上下文**（上下文工程 / 压缩 / 长期记忆）
> 开门句："上下文管理的目标是'在预算内保住最该保的信息'。我的做法是分层：system 里放规则，近期消息保原文，早期历史压成结构化摘要，长期事实写进外部存储按需检索回来。压缩会丢信息，所以压缩后我会补一条'不确定项'字段。"

**⑤ 多智能体**（协作 / 故障 / 什么时候不用）
> 开门句："我一般先默认不用多 Agent。只有在命中四条之一时才拆：上下文必须隔离、需要对抗检查、能并行、角色要求冲突。我做过一次拆分，收益是上下文干净带来的准确率提升，代价是输入 token 高 40%，所以我会用数据说明值不值。"

**⑥ 工程与生产**（成本 / 延迟 / 可靠性 / 安全）
> 开门句："生产上我盯四个数：P95 延迟、单次成本、任务成功率、危险动作拦截率。手段分三层：便宜的先做（缓存、减少无效调用、缩短上下文），再做降级（超时返回缓存结果、模型降级到小模型），最后才是扩容。"

## 12. 项目题的回答结构（本章重点）

**面试官问"讲讲你的项目"时，他要的不是功能列表，而是判断力。** 用固定六段式，每段控制在 30~60 秒：

| 段落 | 时长 | 面试官在考什么 | 常见失误 |
|---|---|---|---|
| ① 业务问题 | 30s | 你是从需求出发，还是从技术出发 | 上来就讲"我用了 LangChain" |
| ② 技术选型 | 45s | 有没有对比与取舍 | 只说我用了 X，说不出为什么不用 Y |
| ③ 系统设计 | 60s | 能不能画清模块与数据流 | 只会说"调 API"，说不清中间那几步 |
| ④ 评估指标 | 45s | 有没有量化意识与反指标 | 只有"效果不错""用户反馈好" |
| ⑤ 故障与优化 | 45s | 有没有踩过真实的坑 | 说"没遇到什么问题" |
| ⑥ 最终结果 | 30s | 能不能收敛到业务价值 | 没有数字，或数字没有口径 |

**完整示范回答（L4 代码审查助手，可直接背结构，数字换成你自己的）：**

> **① 业务问题**：我们组每天 20 多个 PR，reviewer 平均要花 40 分钟看一个中等规模的 PR，而且经常漏掉安全类问题——一次漏审的硬编码密钥进了仓库，回滚花了半天。我的目标是把"明显问题"在提交前拦掉，让人只看架构和业务逻辑。
>
> **② 技术选型**：市面上有纯规则方案（lint/Semgrep，误报可控但只认模式）和纯模型方案（覆盖广但爱乱报）。我选了**规则过滤 + 模型审查 + 独立证伪**的组合：规则层零成本过滤 lock 文件和生成代码，模型层负责语义问题，证伪层专门推翻候选意见。选这个组合的原因是我的场景里**误报比漏报更贵**——一份 20 条里 15 条是废话的 review，人会直接关掉。
>
> **③ 系统设计**：四层。第一层解析 diff 并按 hunk 分片，单次不超过 8k token，超大 PR 降级为"函数签名 + 改动摘要"并显式声明覆盖范围；第二层生成候选意见，输出强 schema 的 JSON（文件、行号、级别、类别、证据片段、建议 diff、置信度）；第三层独立证伪，置信度低于 0.6 直接丢弃，并校验行号必须落在改动行内；第四层合并去重、按风险排序，最多 5 条。
>
> **④ 评估指标**：20 个真实 diff，10 个含人工标注的 bug、10 个干净样本。检出率 0.73、高危问题 0.86、误报 0.6 条/PR、建议可用率 0.62、Precision@3 0.8。我特意把**误报率作为反指标**盯着，因为它是这个工具能不能活下去的关键。
>
> **⑤ 故障与优化**：第一版误报 2.1 条/PR，同事反馈"连 import 顺序都管"。我查出两个原因：prompt 里没有禁止风格意见，以及单次调用时模型倾向多报。改法是硬过滤风格类意见（代码里过滤，不是靠 prompt 求它）、加双阶段证伪、置信度阈值 0.6、条数上限 5。误报降到 0.6，检出率从 0.78 掉到 0.73——这个取舍是刻意的。另一个坑是大 PR 会漏审，我加了"本次仅审查 12/47 个文件"的显式声明。
>
> **⑥ 最终结果**：现在 20 个 PR/天里平均拦下 2.4 个高危问题，单 PR 成本 0.03 元、11 秒出结果；reviewer 的第一遍粗筛时间从 40 分钟降到 25 分钟左右。已知不足：跨文件的架构级问题它审不了，那部分我明确写进了 README 的限制里。

**练法：** 把这段话录音，听一遍；删掉所有形容词，只留数字和动作；再录一遍。**能背下来结构，但不要背原句**——背原句会在追问时露馅。

**三个必考的变体问题（准备一句话答案）：**
- **"你在这个项目里最大的贡献是什么？"** → 指向一个**具体决策**而不是"我全做的"："证伪阶段是我加的，因为它把误报从 2.1 降到 0.6，代价是检出率掉 5 个点——这个取舍是我定的。"
- **"如果重做，你会改哪里？"** → 体现复盘能力，答"顺序"而不是"技术"："我会把评测集提到第一周就建，当时拖到第三周，导致前两周的改动都没有基线可比。"
- **"团队协作中你和别人怎么分工？"** → 说实话 + 说清接口："我负责 Agent 与评估，另一位负责数据清洗；我们把接口定成 `cases.jsonl` 的字段格式，各自能独立测。"

## 13. 追问应对：三个框架

**框架 1："为什么不用 X 方案？"**

四步：**承认适用场景 → 说清我的约束 → 给数据或机制 → 说明何时我会改选 X**。

> 例（被问"为什么不用微调"）："微调在学风格和固定格式上确实更强。我的约束是文档每周都在改（一周 3~5 处），微调要重训、成本高、周期长，而且说不清'这句话是哪来的'——我的场景要求每条结论可追溯到原文。实测上 RAG 方案在 30 条评测集上忠实度 0.91、引用准确率 0.93，已经够用。如果哪天我的需求变成'统一输出风格'并且文档半年不变，我会优先考虑微调。"

**要点：绝不贬低 X**（面试官可能就是 X 的作者），**也绝不硬撑**（说"如果…我会改选 X"反而显得成熟）。

**框架 2："如果流量涨 10 倍怎么办？"**

四步：**先算账 → 找瓶颈 → 三种手段 → 排序与代价**。

> 例："先算：现在 300 次/天、P95 2.4 秒、单次 0.006 元。涨 10 倍是 3000 次/天，按早高峰 30% 集中在 2 小时算，约 0.13 QPS——**这个量级根本不需要扩容，先别慌**。真正的瓶颈是单次的外部 API 调用：串行 3 次调用让 P95 卡在 2.4 秒。手段按性价比排：① 缓存（同问题命中率约 20%，直接省掉五分之一成本）；② 把'分类 + 抽取'两个调用合并成一个，延迟和成本各降约三分之一；③ 加并发与限流兜底，超时返回缓存结果并标记'待人工'。真到 100 倍再考虑批处理与自建小模型做前置分流。"

**关键是把"10 倍"换算成绝对数字**——大多数面试里的"10 倍"其实还没到需要重构的量级，能算清这一点本身就是加分项。

**框架 3："效果不好你怎么排查？"**

五步：**定位环节 → 二分缩小 → 看 trace → 最小复现 → 改一处再测**。

> 例："引用准确率从 0.93 掉到 0.71，我先分段测：检索层 Recall@5 从 0.88 掉到 0.62，说明问题在检索不在生成。接着二分：换成上一版索引（index=v2）指标恢复，说明是索引构建环节。查 trace 发现新文档里有 3 份是扫描件 PDF，解析出来全是乱码，污染了向量空间。最小复现：单独用那份 PDF 建索引，复现出 0.61。处理：解析失败的文件在索引阶段直接进'排除清单'并告警，不静默入索引——重跑后 0.92。之后我在评估报告里加了一列'索引排除文件数'。"

**这个框架的核心是"分段评估"**：能把系统拆成可分别测量的几段，你就能把"效果不好"变成"第 3 段的第 2 小步退化"，而不是靠猜。

## 14. 简历怎么写

**公式：** `动词 + 系统名 + 三个关键技术点 + 可量化结果（含口径）`

| 不合格 | 合格 |
|---|---|
| 负责大模型相关功能的开发与优化，提升了系统效果 | 独立实现文档问答系统（混合检索 + RRF 融合 + 重排 + 引用校验），在 30 条自建评测集上 Recall@5 0.88、引用准确率 0.93，P95 延迟 4.2 秒 |
| 参与 Agent 项目，熟悉 LangChain 等主流框架 | 实现代码审查 Agent（diff 分片 + 双阶段证伪 + JSON 强校验），20 个真实 diff 检出率 0.73、误报 0.6 条/PR，单 PR 成本 0.03 元 |
| 深入研究 RAG 技术，效果显著提升 | 通过切片实验（固定长度 3 档 vs 结构切）把 Recall@5 从 0.74 提到 0.88；用评测集扫出拒答阈值 0.35，误拒率 ≤ 5% |

**空话词清单（见面就删）：** 负责、参与、赋能、闭环、一站式、大幅提升、显著优化、深入理解、熟练掌握、各类、相关、等主流技术。**删完之后如果这条描述没有任何数字或文件名，说明它不该出现在简历上。**

**数据怎么摆：**
1. **位置**：数字放在每条 bullet 的后半段（前半段说做了什么，后半段说结果）；
2. **口径**：每个数字都要能答"怎么测的"——"准确率 0.88（30 条评测集，人工核对 10 条抽样校准）"胜过"准确率 88%"；
3. **反指标要有**：写"误报 0.6 条/PR"比只写"检出率 0.73"更让人信服；
4. **规模也要**：320 页文档 / 1800 chunk / 20 个 diff / 20 个主题——规模说明你真的跑过。

**整份简历的排布：** 一页为限（校招/转行都适用）；顺序是"技能条（只写你真能答的）→ 项目（**最相关的放最前**，每条 3~4 行）→ 教育/经历 → 其他"。项目描述里**同一件事只出现一次**，别在技能条写"熟悉 RAG"又在项目里讲 RAG——前者是声明，后者才是证据。**投不同岗位时调换项目顺序**，RAG 岗把文档问答放第一位，Agent 岗把代码审查放第一位。

## 15. 反问环节

**反问不是客套，它是你判断"这家公司值不值得去"的唯一机会。** 准备 3 个，问 2 个。

| 该问 | 你想获取什么信息 |
|---|---|
| 这个岗位现在最核心的目标是什么？半年内做成什么样算成功？ | 判断团队有没有清晰目标，还是"试试 AI" |
| 现在有评测集吗？谁来维护？ | 没有评测 = 全靠感觉，你会天天背锅 |
| 从需求到上线大概走什么流程？有灰度与回滚吗？ | 判断工程成熟度 |
| 模型选型是团队自己定还是公司统一？能换吗？ | 判断你还有没有技术自主权 |
| 团队现在几个人？我进来主要负责哪一块？ | 判断你是第 1 个还是第 5 个做 AI 的人（差别巨大） |

| 不该问 | 为什么 |
|---|---|
| 加班多不多 / 能不能远程 / 涨薪幅度 | 这些问 HR，别问技术面试官（还容易留下坏印象） |
| "你们用什么模型？"（作为唯一问题） | 显得你只关心工具，不关心问题 |
| 官网能查到的信息 | 暴露你没做功课 |
| "我有机会吗？" | 把判断权交出去，显得没底气 |

## 17. 长期成长：这个领域变化快，怎么不被甩下

**看什么（按可信度排序）：**
1. **官方文档与 changelog**（模型厂商、SDK、协议规范）——第一手，最有信息量；
2. **可运行的开源项目**（能 clone 下来跑的那种）——看得见工程细节；
3. **有实验数据的论文/技术报告**——注意看它的评测条件，别只看结论；
4. **一线工程博客**（讲清"我们踩了什么坑"的那种）——最有共鸣，也最容易迁移。

**避开什么：**
- 只讲观点不给数据的自媒体（"某模型吊打某模型"）；
- 追新名词（今天 AgentOps、明天 AI Native），名词换得比工具快；
- 收藏夹式学习（收藏 200 篇，一篇没跑过）；
- 只换框架不动脑子（把 LangChain 换成另一个框架，能力没涨）。

**节奏（可持续 > 高强度）：**
- **每周 1 小时**固定读上面第 1、2 类，只记"能跑的一个新东西"；
- **每月一个小实验**：把新东西接到你第 15/16 章的项目里，用评测集量一次（有对比才知道值不值）；
- **每季度回头改一次旧项目**：半年后你回头看自己的代码，能看出 5 个可改的地方，这就是成长；
- **写下来**：每个结论写进 `03-学习笔记/`，形成自己的判断库——面试时你讲的就是这些真实的取舍。

## 本章小结

1. **毕设不是把第 15 章再做一遍**：题目自己定、指标自己定并给依据、至少 2 组替代方案对比、≥20 条评测集、失败要按环节分类。
2. **选题四问**：数据拿得到吗、效果验证得了吗、有没有真实取舍、四个里程碑跑得完吗。偏向"脏数据 + 可验证"的题目。
3. **先写需求文档把范围钉住**：具体角色、可量化的成功标准（含反指标）、≥3 条"不做什么"、边界与约束。
4. **技术方案的价值在替代方案对比表**：选择 / 替代方案 / 为什么没选 / 代价——这张表是评审与面试官最认的东西。
5. **四个里程碑，每个都有可运行产出**：骨架跑通 → 接真实数据与模型 → 评估闭环 → 交付打磨；评测集从 M1 就开始攒。
6. **交付看四件事**：README 四问（怎么跑/怎么配/怎么扩展/已知限制）、一键复现、离线演示、失败分类归因。
7. **面试按岗位换重点**，项目题用六段式：业务问题 → 技术选型 → 系统设计 → 评估指标 → 故障与优化 → 最终结果。
8. **追问三框架**：承认 X 的适用场景再讲取舍；把"10 倍"换算成绝对数字；用分段评估把"效果不好"定位到具体环节。
9. **简历只留数字与文件名**，空话词见面就删；每个数字都要能答"怎么测的"。
10. **关联阅读**：[[02-Wiki/面试题库/01-Agent高频面试题]]、[[02-Wiki/面试题库/02-RAG高频面试题]]、[[02-Wiki/面试题库/03-项目表达与追问应对]]、[[01-Raw/03-项目阶梯与能力对照表]]，产出放进 [[04-Outputs/README]]。

## 自测题

**1. 为什么毕业设计必须有反指标？举两个例子。**

<details><summary>点击查看答案</summary>

因为主指标可以靠"更激进"刷高，但没有代价意识。例：文档问答只报"回答率 100%"，只要从不拒答就能拿到——加上"编造率"就刷不了了；代码审查只报"检出率 0.9"，只要狂报就能拿到——加上"误报率"（≤1 条/干净 diff）就刷不了了；工单分流只报"准确率"，加上"错分率 ≤5%"才控制住了代价。反指标的作用是**把"我愿意付出多大代价"写进评估里**，这恰恰是面试官判断你有没有工程意识的地方。

</details>

**2. 面试官问"为什么不用 X 方案"，最好的回答结构是什么？**

<details><summary>点击查看答案</summary>

四步：① 先承认 X 的适用场景（显示你懂 X，且不贬低）；② 说清我当时的约束（数据更新频率、成本上限、可追溯要求等）；③ 给出数据或机制层面的依据（"实测纯向量在这类含编号的查询上 Recall 掉 12 个点"）；④ 说明什么时候我会改选 X（"如果文档半年不变且要求统一风格，我会优先微调"）。最差的回答是"X 不好"——那既暴露了你不了解 X，也暴露了你不做取舍。

</details>

**3. "如果流量涨 10 倍怎么办？"答题的第一步应该是什么？**

<details><summary>点击查看答案</summary>

**先算账，再谈方案。** 把 10 倍换算成绝对值：现在 300 次/天、P95 2.4 秒、单次 0.006 元，涨 10 倍是 3000 次/天，按早高峰 30% 集中在 2 小时算约 0.13 QPS——很多场景这个量级根本不需要扩容，瓶颈是单次调用的串行结构而不是并发。算完账再按性价比给手段：缓存 → 合并调用 → 并发与限流 → 批处理/小模型分流。跳过算账直接说"加机器/上 Kubernetes"是典型的答非所问。

</details>

**4. "效果不好你怎么排查？"为什么必须先分段评估？**

<details><summary>点击查看答案</summary>

因为"效果不好"是个**症状**，不是一个可修的问题。系统由多段组成（检索、生成、校验、拒答），只有分段测量才能把症状定位到环节：引用准确率从 0.93 掉到 0.71，先测检索层 Recall@5（0.88 → 0.62），确定问题在检索；再用"换回上一版索引指标恢复"缩小到索引构建；再看 trace 发现扫描件 PDF 被解析成乱码入了索引。**没有分段评估，你只能重跑、改 prompt、凭感觉**——三段拆开测，十分钟就能定位。

</details>

**5. 简历上"负责大模型相关功能开发，效果显著提升"这句话的三个问题是什么？**

<details><summary>点击查看答案</summary>

① **没有动作**："负责/参与"是角色不是贡献，看不出你做了什么；② **没有数字**："效果显著提升"没有口径（提升多少、怎么测、基线是多少）；③ **没有技术名词**：看不出技术深度，也看不出你解决的是哪一类问题。改法：`动词 + 系统名 + 三个关键技术点 + 可量化结果（含口径）`，例如"实现文档问答系统（混合检索 + RRF + 重排 + 引用校验），在 30 条自建评测集上 Recall@5 0.88、引用准确率 0.93"。

</details>

## 结语

学车时教练教的是打方向盘、看后视镜、踩离合，但拿到驾照那天你并不会开车——你只是在没人的路上把动作做对了；真正让你会开车的，是第一次自己决定走哪条路、什么时候并线、错过路口怎么办的那种紧张。这十六章就是那张驾照：它给了你动作和判断标准，路得你自己挑。

所以真正开始的地方不在教程里，在你自己的题目里——挑一个你每天都会遇到的小麻烦，写清需求、做取舍、建评测、记失败，做完一个，你就从"学 AI Agent 的人"变成了"做过 AI Agent 的人"。
