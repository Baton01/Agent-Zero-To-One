## 0. 开篇：一个真实的问题

周一早会，产品经理问了一个所有人都愣住的问题。

> **产品：** 这个"自动回复客户邮件"的功能，一次多少钱？
>
> **你：** 模型按量计费，应该……很便宜，几分钱一封吧。
>
> **产品：** 那按每天 300 封算，一个月多少钱？我们要拿去给客户报价的。
>
> **你：** 我回去算一下。

你没算出来 —— 因为你自己心里也没底。当天晚上，你把"批量处理 300 封客户邮件"的脚本挂上跑，想第二天拿真实数字交差。

第二天早上看到的是三件事：

1. **账单 87 元**。你心里预估的是"几分钱一封"，实际是 0.29 元一封 —— 差了 60 倍。
2. **脚本在第 41 封时崩了**，报错：`This model's maximum context length is 65536 tokens. However, you requested 70000 tokens.`
3. **生成的回复里有 3 封提到了不存在的订单号**（比如 `DP9999`），客户根本查不到这单。

这三个问题分别对应本章的三块内容：**成本怎么算**、**上下文窗口是什么**、**幻觉怎么缓解**。它们都不是"调 API 的技巧"，而是工程判断力 —— 决定你能不能把一个 Demo 做成一个能交给业务用的东西。

这类问题很常见：能把 Demo 跑起来的人很多，能当场说出"这个功能一次多少钱、什么时候会崩、它胡说的时候怎么办"的人很少。

所以这一章把这三笔账算清楚。先记住本章的一句总纲：**大模型按 Token 计费、按窗口限制、按概率生成，这三件事决定了它所有工程上的取舍。**

## 1. Token：模型眼里的"字"

### 1.1 为什么不能按"字数"计费

模型看不到字符，它看到的是 **Token**（词元）—— 由分词器（Tokenizer）把文本切成的片段。切法不是"一个字一个 Token"，也不是"一个词一个 Token"，而是**按出现频率切**：常见的词整块保留，生僻词被拆成更小的碎片。

这就是为什么：

- `Python` 可能是 1 个 Token，而 `zqxwj` 这样的生造词会变成 4 个 Token（每个字母或字母对一块）。
- `12345` 和 `1234567890` 的 Token 数不一样 —— 数字也是按频率切的。
- 同一个句子，换一家模型，Token 数可能差 20%。

**结论：Token 数只跟"这个模型的分词器"有关，不要用字数直接代替。** 但工程上必须有一个能算的数，所以我们用近似公式。

### 1.2 具体换算数字（够用的经验值）

| 内容类型 | 经验换算 | 例子 |
|----------|----------|------|
| 中文（汉字） | **1 个汉字 ≈ 0.6–1 Token**（保守估算按 1） | 500 字的客户邮件 ≈ 300–500 Token |
| 英文 | 1 Token ≈ 4 个字符 ≈ 0.75 个单词 | 1000 词的英文文章 ≈ 1300 Token |
| 代码 / JSON | 1 Token ≈ 3 个字符（符号多，切得碎） | 200 行 Python（约 8000 字符）≈ 2600 Token |
| 标点、空格、换行 | **一样的，全都要算** | 一段 30 行的日志，光换行和缩进就值 60+ Token |
| emoji / 特殊符号 | 1 个 emoji ≈ 1–3 Token | 一排 10 个 emoji 可能比一句话还贵 |

同一段意思，中文和英文的 Token 数差多少？看一个具体例子（按上面的保守规则数）：

```text
中文：请帮我查一下订单 DP1002 的物流状态，谢谢。        25 个字符 → 约 18 Token
英文：Please check the shipping status of order DP1002. 49 个字符 → 约 13 Token
```

信息量一样，中文只用了 25 个字符（英文要 49 个），但 Token 数反而多 38%。**原因是中文每个字几乎都要占 1 个 Token，而英文 4 个字符才占 1 个。** 所以同样的业务逻辑，中文 prompt 通常比英文贵 1.4–2 倍（真实分词器下的差距更大）。这个差价在你按"百万 Token"计费、每天跑几万次时是真实存在的。工程上的折中：面向用户的内容用中文，**内部指令和 Schema 尽可能用英文/短标识符**。

### 1.3 亲手估算：`count_tokens_approx`

本项目不装分词器（第 08 章会用到真正的分词，那时再装），先用一个 5 行的近似函数。**它刻意"宁可高估"，因为你按它做预算不会算穿：**

```python
def count_tokens_approx(text):
    """粗估 Token 数（宁可高估，不低估）。

    规则：中日韩字符按 1 字 = 1 Token，其余字符按 4 字符 = 1 Token。
    实测偏差通常在 -30% ~ +10%（不同模型的分词器不同），够用来做预算。
    """
    cjk = 0
    for ch in text:
        if "\u4e00" <= ch <= "\u9fff":      # 常用汉字区间
            cjk += 1
    other = len(text) - cjk
    return int(cjk + other / 4) + 1
```

用的时候注意两点：**① 它算的是"文本"，而每次请求的总输入 = system + 全部历史消息；② 多轮对话里历史越长，这个数字增长越快**（第 4 节会算这笔账）。

### ⚠️ 常见坑

- **现象：预算按"字数 = Token"算，实际账单是这个数的 1.5 倍。** 原因：中文 1 字往往多于 1 Token（尤其数字、英文混排、标点密集时），加上历史的 Token 没算进去。改法：预算时按"估算值 × 1.3"留余量，并在代码里累加真实 `usage`（`chat()` 的返回值里带）。
- **现象：以为"删掉一个空格就能省钱"。** 事实：一个空格 1 个 Token 都不到，无所谓。真正花在哪要打印出来看：把 system、历史、当前输入分别估算一次，通常会发现**历史占了 70% 以上**。
- **现象：把长 JSON 直接塞进 prompt，Token 数爆炸。** 原因：JSON 的引号、括号、逗号都是独立 Token。改法：能只传必要字段就别传整个对象；键名尽量短（`{"n": "A123"}` 而不是 `{"customer_order_number": "A123"}`）。

## 2. 上下文窗口与 max_tokens

### 2.1 上下文窗口 = 输入 + 输出

**上下文窗口（Context Window）** 是一次请求里模型能"看到"的 Token 总数上限：`system + 历史 messages + 本次输入 + 模型输出` 全都算在里面。

常见档位（不同服务商/模型差异很大，以官网为准）：

| 档位 | 典型模型 | 大致能装多少 |
|------|----------|-------------|
| 8K | 早期模型 / 小模型 | 约 5000–8000 汉字 |
| 32K | 常见中档 | 约 2 万字 |
| 64K | `deepseek-chat` | 约 4–6 万字 |
| 128K–200K | 长文本模型 | 约 10 万字以上 |

输出侧还有单独的限制：`max_tokens`（单次回答最多生成多少 Token），常见默认 4K、上限 8K。

### 2.2 超限的报错长什么样

超限是**客户端的责任**：请求发出去之前你就该知道会超。报错通常是 400：

```text
HTTP 400: This model's maximum context length is 65536 tokens.
However, you requested 70000 tokens (65000 in the messages, 5000 in the completion).
Please reduce the length of the messages or completion.
```

注意报错里已经把账算给你看了（消息 65000 + 预留输出 5000）。**看到这个报错不要改 prompt 里的措辞，要做的是减历史或切片。**

### 2.3 `max_tokens` 设太小会截断输出

`max_tokens` 是输出预算。设小了会**静默截断** —— 不报错，只是内容突然断在半路：

```python
resp = llm.chat(messages, max_tokens=50)
print(resp["content"])      # 可能是一段完整的话，也可能是 "客户您好，关于您的订单 DP1"
print(resp["usage"]["completion_tokens"])   # 恰好等于 50 → 就是被截断了
```

判断依据是 `finish_reason`：

| `finish_reason` | 含义 | 你该做什么 |
|-----------------|------|-----------|
| `stop` | 模型自然说完 | 正常 |
| `length` | 达到 `max_tokens` 被截断 | 调大 `max_tokens`，或简化任务 |
| `tool_calls` | 模型要调工具 | 第 04 章处理 |
| `content_filter` | 被内容安全策略拦住 | 检查输入是否违规 |

**最危险的组合：要求输出 JSON + `max_tokens` 太小。** 结果是拿到半个 JSON（`{"order_id": "A12`），`json.loads` 直接报 `Expecting value: line 1 column 15`。第 03 章会给出完整的校验与重试方案。

### ⚠️ 常见坑

- **现象：`max_tokens` 不填就报错，或者填了 `0` 报错。** 原因：部分服务商要求该字段必须 > 0 且不超过上限。改法：抽取类任务填 512–1024 就够；长文写作填 2048–4096；不确定就不传（用服务端默认）。
- **现象：输入 60K + 输出想要 8K，超了 64K 窗口。** 原因：窗口是输入输出的**总和**。改法：预留出输出空间（`输入预算 = 窗口 − max_tokens − 安全余量`），让代码算出"历史能留多少"（第 07 章的上下文预算管理）。
- **现象：模型答到一半断了，但 `finish_reason` 是 `stop`。** 可能是服务端对输出另有更小限制，或者你用了 `stop` 参数（遇见指定字符串就停）。改法：检查请求参数里是否传了 `stop`；这类参数在输出 JSON 时尤其危险（模型写到 `"status": "stop"` 就被自己截断）。

## 3. 采样参数：调高会怎样，调低会怎样

模型每生成一个 Token，都是从"候选词的概率分布"里抽样。采样参数控制的是这个抽样过程的松紧。

### 3.1 对照表

| 参数 | 控制什么 | 调高 | 调低 | 建议起点 |
|------|----------|------|------|----------|
| `temperature` | 随机性/多样性 | 输出多样、有创意，但容易跑题、编造、格式不稳 | 稳定、保守、可复现，但可能死板、重复 | 通用 0.7；抽取/分类/JSON **0–0.3** |
| `top_p` | 只从累计概率前 p 的候选里抽 | 同 temperature 调高 | 同 temperature 调低 | 0.9–1.0，**一般不动** |
| `top_k` | 只从概率最高的 K 个候选里抽 | 更发散 | 更保守 | 多数 API 不暴露此参数，忽略 |
| `frequency_penalty` | 按"出现过多少次"惩罚 | 减少重复用词，过度时语句不通顺 | 允许重复 | 0；复读严重时试 0.3 |
| `presence_penalty` | 按"出现过没有"惩罚 | 鼓励说新话题，容易跑题 | 允许复读 | 0 |
| `stop` | 遇到指定字符串立即停止 | — | — | **少用**，容易把 JSON 截断 |
| `seed` | 尽量固定随机种子 | — | — | 需要复现实验时用；不保证跨版本一致 |
| `n` | 一次生成几个候选 | 更贵 | — | 除非做采样投票（第 06 章），否则 1 |

**`temperature` 和 `top_p` 一般只调一个** —— 它们控制的是同一件事（分布的松紧），同时动会让效果难以归因。

### 3.2 `temperature=0` 为什么不等于"确定性"

`temperature=0` 表示"总选概率最高的那个 Token"。但同一个请求跑两次，输出仍可能不同，原因有五类：

1. **浮点误差的累加顺序**不同（批处理时同一批次里其它请求的矩阵形状影响计算路径）。
2. **服务端为了吞吐做动态批处理（dynamic batching）**，批次组成不同 → 计算路径不同。
3. **MoE（混合专家）模型的专家路由**可能有随机性。
4. **负载均衡到不同副本**，副本的推理框架/量化版本不同。
5. **服务商更新了模型版本**（最容易忽略、也最常见）。

工程含义：**不要把"两次输出不一致"当成代码有 bug**；反过来，需要严格复现时（比如评测、回归测试），要固定 `seed` + 固定模型名 + 接受近似。第 12 章建评测集时会用到这一条。

### 3.3 什么时候该调、调多少

| 任务 | 推荐值 | 理由 |
|------|--------|------|
| 分类 / 抽取 / 输出 JSON | `0`–`0.3` | 要的是稳定，任何随机性都是风险 |
| 结构化改写（翻译、润色、摘要） | `0.3`–`0.6` | 需要一点灵活性，但不能改意思 |
| 客户回复 / 文案 | `0.7`–`1.0` | 要自然、不重复 |
| 头脑风暴 / 起标题 | `1.0`–`1.3` | 要的就是多样性，后面人工挑 |
| Agent 的工具选择 | `0`–`0.3` | 选错工具是灾难，宁可死板 |

### ⚠️ 常见坑

- **现象：明明设了 `temperature=0`，抽取结果还是每次不一样。** 原因见 3.2 节（浮点/批处理/版本）。改法：① 用**代码校验 + 重试**兜住不一致（第 03 章）；② 评测时用"多次运行取一致率"而不是"断言输出相等"。
- **现象：把 `temperature` 设成 2.0 想"更有创意"，结果输出乱码式跑题。** 原因：分布被压平过头，低概率词也能被选中。改法：上限 1.3（有些 API 限制 ≤ 2.0，但超 1.3 基本不可用）。
- **现象：`frequency_penalty=1.0` 之后模型开始胡言乱语。** 原因：惩罚过强，模型被迫避开正常用词。改法：这类惩罚项一次只加 0.2–0.3，并且**先确认问题真的是"重复"**（很多时候重复是因为 prompt 里给了重复的示例）。
- **现象：以为 `temperature` 调低能消除幻觉。** 事实：温度低只能减少"发散型胡说"，**不能解决"没有知识硬答"**。幻觉的主战场在第 5 节。

## 4. 成本：怎么算、怎么省

### 4.1 输入和输出分开计价

几乎所有服务商都是**输入比输出便宜，输出是输入的 3–4 倍**：

```text
示例价格表（单位：元 / 百万 Token；价格会变，务必以服务商官网为准）
┌────────────────────┬─────────┬─────────┬──────────────┐
│ 模型                │ 输入     │ 输出     │ 缓存命中输入  │
├────────────────────┼─────────┼─────────┼──────────────┤
│ deepseek-chat      │ 2.0     │ 8.0     │ 0.5          │
│ qwen-plus          │ 0.8     │ 2.0     │ —            │
│ glm-4-flash        │ 免费档   │ 免费档   │ —            │
│ gpt-4o-mini        │ 约 1.1  │ 约 4.3  │ 约 0.55      │
└────────────────────┴─────────┴─────────┴──────────────┘
```

对应的工具函数：

```python
from common.llm import estimate_cost

# 参数是"输入 Token 数、输出 Token 数"，返回人民币元（按示例价表估算）
cost = estimate_cost(4250, 1000)          # 0.0165 元
print("本次调用约 %.4f 元" % cost)
```

### 4.2 一个真实业务的成本估算

回到第 01 章的邮件场景。假设：system 300 Token、用户邮件 50 Token、每轮回答 200 Token。

| 方案 | 计算过程 | 单封成本 |
|------|----------|----------|
| 一次问答（Workflow 里的分类步骤） | `(350 × 2 + 200 × 8) / 1e6` | ¥0.0023 |
| Workflow（分类 + 写草稿，2 次调用） | 输入 700、输出 400 | ¥0.0046 |
| Agent（5 轮） | 输入 4250、输出 1000 | ¥0.0165 |

放大到业务量：**每天 300 封 × Agent 方案 ≈ 5 元/天 ≈ 150 元/月**，看起来不多；但如果是**每天 10 万条日志分类**，Workflow 方案是 230 元/天（7000 元/月），Agent 方案就是 1650 元/天（5 万元/月）—— **架构选型直接决定成本能不能活下来**。

### 4.3 Agent 循环为什么是"平方级"烧钱

关键机制：**每一轮请求都要把全部历史重新发一遍**（模型没有记忆，见第 00 章）。

```text
轮 1：输入 350                              → 累计 350
轮 2：输入 350 + (上一轮回答 200 + 工具结果 50) = 600   → 累计 950
轮 3：输入 600 + 250 = 850                  → 累计 1800
轮 4：输入 1100                             → 累计 2900
轮 5：输入 1350                             → 累计 4250
```

公式：`N 轮累计输入 ≈ N × 首轮 + 每轮增量 × N(N−1)/2` —— **随轮数平方增长**。用 20 轮算一遍：`20 × 350 + 250 × 190 = 54500` Token，是 5 轮版（4250 Token）的 **12.8 倍**；成本约 ¥0.141，是 5 轮版（¥0.0165）的 8.5 倍。

**这就是"给 Agent 设步数上限"的经济学理由**：上限不是防死循环的补丁，而是成本控制的闸门。

### 4.4 五种省钱手段

| 手段 | 具体做法 | 大致省多少 |
|------|----------|-----------|
| ① 缓存命中 | 让**固定前缀**保持一致（system 放在最前，不要插时间戳/随机 ID） | 输入单价降到 1/4 左右 |
| ② 截断/压缩历史 | 只保留最近 N 轮 + 更早的摘要（第 07 章） | 长对话下省 50%–90% |
| ③ 小模型打前站 | 分类/初筛用小模型，只有疑难才升级到大模型 | 常见 5–20 倍 |
| ④ 控制输出 | "不要解释、只输出 JSON"、合理设置 `max_tokens` | 输出单价是输入 4 倍，收益明显 |
| ⑤ 缩减输入 | 只传必要字段、删掉冗余示例、键名用短名 | 视情况 20%–60% |

**第 ① 条最容易被忽略、也最容易踩坑**：前缀缓存要求"请求的前缀逐字节相同"。所以如果你在 system prompt 开头写了 `当前时间：2026-09-20 14:03:22`，那么每一秒的缓存都不同 —— **所有缓存全部失效，输入成本变成 4 倍**。正确做法是把动态内容放到**消息的最后**。

### ⚠️ 常见坑

- **现象：成本估算和账单差 3 倍以上。** 常见原因：① 只算了最后一轮的 Token，忘了历史；② 忘了输出单价更高；③ 没算重试（失败重试也是钱）；④ 服务商有"最低计费量"或按量取整。改法：在代码里**累加每次响应的 `usage`**，打印真实总量，别靠心算。
- **现象：缓存命中率一直是 0。** 原因：前缀里有变化的内容（时间戳、请求 ID、每次不同的示例），或每次请求的 system 有细微差异（比如空格）。改法：把 system 做成模板常量；把动态内容放最后。
- **现象：为了省钱把 `max_tokens` 设成 200，结果 JSON 老是被截断，重试两次反而更贵。** 教训：**省 Token 的前提是不破坏正确性**。抽取任务的 `max_tokens` 按实测输出的 1.5 倍来设，别抠。

## 5. 幻觉：成因与工程缓解

### 5.1 为什么会编

模型的训练目标是"预测下一个最可能的 Token"，**不是"说真话"**。所以：

- **知识缺失或过时**：训练数据里没有这个订单、这家公司的政策、上周的会议记录。
- **上下文里没有答案，但你没给它"不回答"的出口**：它会用"最像答案的内容"补全。这是最常见的工程性幻觉 —— **不是模型坏，是 prompt 没给台阶**。
- **问题本身诱导**：问"订单 DP9999 为什么延迟了"，模型会顺着你的假设编出一个原因（这个模式叫"前提假设被接受"）。
- **长上下文里的信息被稀释**：材料太长时中间部分容易被忽略（见第 6 节）。

### 5.2 五种工程缓解手段

**① 给它材料（RAG，第 08 章）。** 幻觉最有效的解药是"把答案放进上下文"。检索到相关片段再问，模型就从"回忆"变成了"阅读"。

**② 要求引用，并且让代码校验引用。**

```python
import re

# prompt 里要求：[1] [2] 这样的编号必须来自给定材料
# 代码里检查：引用的编号是否真的存在于候选材料里
def check_citations(answer, num_candidates):
    used = {int(n) for n in re.findall(r"\[(\d+)\]", answer)}
    bad = {n for n in used if n < 1 or n > num_candidates}
    return {"ok": not bad, "invalid": sorted(bad)}     # invalid 非空 = 有引用是编的
```

**③ 可验证事实一律走工具，不许模型"背"。** 订单号、金额、日期、库存这类东西必须调 API 或查库：

```python
import re
ORDER_RE = re.compile(r"^DP\d{4}$")

def validate_order_id(text):
    """格式校验 + 真值校验：格式不对直接判失败，格式对也要去库里确认存在。"""
    match = ORDER_RE.search(text)
    if not match:
        return {"ok": False, "reason": "订单号格式不合法"}
    order_id = match.group(0)
    if order_id not in FAKE_ORDERS:            # 真实项目里是查订单服务
        return {"ok": False, "reason": "系统里不存在该订单", "order_id": order_id}
    return {"ok": True, "order_id": order_id}
```

**④ 给它"不知道"的出口。** 在 prompt 里显式写：`材料中没有提及的，回答"材料未提及"，不要推测。` 这一句话的收益在实测里通常比换模型更明显。

**⑤ 后校验 + 降级。** 输出必须过一遍代码规则（枚举值、数值范围、字段完整性），不通过就重试（把错误回灌给模型，第 03 章），仍失败就降级到"转人工"。

### 5.3 无效或低效的做法

| 做法 | 为什么没用 |
|------|-----------|
| 写"请确保回答准确，不要编造" | 模型没有"真假"内部状态可以自查；这句话不提供任何新信息 |
| 换一个"更强的模型" | 知识缺失导致的幻觉，任何模型都会编；材料缺失才是根因 |
| 把 `temperature` 调到 0 | 只减少发散，不阻止"没有知识硬答" |
| 让模型"再检查一遍自己的答案" | 有一定效果（Reflection，第 06 章），但自查同样缺乏外部真值，容易"确认自己的错误" |
| 加重罚：`frequency_penalty` 等 | 与幻觉无关，纯粹是采样层参数 |

### ⚠️ 常见坑

- **现象：模型给出的订单号"格式正确但不存在"。** 这类幻觉最危险，因为它看起来太合理。改法：**结构校验（正则）+ 存在性校验（查库）两层都要有**，缺一层就等于没校验。
- **现象：加了 RAG 之后幻觉变少了，但模型开始把材料外的常识混进来。** 改法：prompt 里限制"只能依据材料回答"，并要求每句结论后带引用编号；引用校验不过就重试。
- **现象：模型说"根据政策，可以退 500 元"，但政策里根本没写金额。** 原因：你没规定"材料未提及"的表达方式。改法：明确出口措辞 + 代码检查关键字段是否为空（`null` 比例异常升高往往说明材料覆盖不足）。

## 6. 上下文窗口的工程含义：为什么长文档必须切片

这条是第 08 章 RAG 的伏笔，但你现在就该明白它的三个理由：

**① 装不下。** 一本 12 万字的书 ≈ 12 万 Token（保守估），已经超过 64K 窗口。想塞进 200K 模型？可以，但看第 ② 条。

**② 成本和延迟都不划算。** 每次提问都把 12 万 Token 发一遍：输入成本 `120000 × 2 / 1e6 = 0.24 元/次`，而且首字延迟会明显上升（第 7 节）。换成"检索出 2000 Token 的相关片段"，成本降到 `0.004 元/次` —— **60 倍差距**，而且回答更准。

**③ 长上下文不等于长记忆。** 研究（[Lost in the Middle, Liu et al. 2023](https://arxiv.org/abs/2307.03172)）发现：相关信息放在长上下文**中间**位置时，模型的表现明显低于放在开头或结尾时。也就是说，把 50 页文档一次性丢进去，不代表模型都能用上。

正确姿势（第 08 章展开）：**切片（chunk）→ 向量化 → 按问题检索 top-k → 只把相关片段放进上下文**。

```text
不切片：文档 120000 Token ──→ 每次全发 ──→ 0.24 元/次，慢，中段信息可能被忽略
切片后：文档切 120 片 ──→ 检索出 2 片（约 2000 Token）──→ 0.004 元/次，快，相关度更高
```

### ⚠️ 常见坑

- **现象：以为"模型支持 200K，就不用管切片了"。** 代价是每次请求都贵 60 倍，而且中间部分的信息可能被漏掉。改法：**能用检索解决的，不要用长上下文硬塞**。
- **现象：切片时按固定 500 字硬切，把一句话切成两半。** 后果：语义被破坏，检索到的一半片段答不上问题。改法：按段落/标题切，并让相邻片段有重叠（overlap），第 08 章给具体参数。

## 7. 流式输出与首字延迟（TTFT）

### 7.1 两个延迟指标

| 指标 | 含义 | 用户感受 |
|------|------|----------|
| **TTFT**（Time To First Token，首字延迟） | 从发出请求到看见**第一个字** | 决定"这个系统卡不卡" |
| **总延迟** | 到最后一个字出现 | 决定"读完要多久" |

一段 800 Token 的回复，非流式与流式的对比：

```text
非流式：0.0s ────────── 8.2s 一次性出现在屏幕上（用户盯着空白屏等了 8.2 秒）
流式：  0.0s ─ 0.6s 出现第一个字 ──────── 8.2s 最后一个字（用户 0.6 秒后就"开始读"了）
```

**总时长没变，但主观等待从 8.2 秒变成了 0.6 秒。** 这就是流式输出存在的唯一理由 —— 它不省钱、不提速，只改变感知。

### 7.2 流式的数据长什么样

开启 `stream=True` 后，服务端用 SSE（Server-Sent Events）逐块推送，每一块都是一个独立的 JSON：

```text
data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: {"choices":[{"delta":{},"finish_reason":"stop"}]}

data: [DONE]
```

三个要点：

- 字段是 **`delta`**（增量），不是非流式的 `message`（完整消息）。你要把 `delta.content` 一段段拼起来。
- 分块**不对齐字/词**：一个中文字可能被拆在相邻两块里，别假设"每块一个字"。
- 流式响应里 `usage` 常常**不返回**（因为还没算完）。OpenAI 兼容接口可以加 `stream_options={"include_usage": True}` 让最后一块带上 usage。

本项目的接口是 `LLM.stream_chat(messages, **kw)`，返回一个迭代器：

```python
llm = get_llm(temperature=0.7)
collected = []
for piece in llm.stream_chat([{"role": "user", "content": "用三句话介绍 Python。"}]):
    collected.append(piece)
    print(piece, end="", flush=True)        # 打字机效果
print("\n总字数：", len("".join(collected)))
```

### ⚠️ 常见坑

- **现象：流式输出打印时一卡一卡地成块出现。** 原因：忘了 `flush=True`，或者终端/中间层（比如某些 Web 框架的缓冲）攒够了才发。改法：`print(..., end="", flush=True)`；Web 场景要关掉中间层的响应缓冲（第 13 章）。
- **现象：流式模式下 `usage` 是 `None`，成本统计全丢了。** 原因：见上。改法：加 `stream_options={"include_usage": True}`；不支持的话就退回 `count_tokens_approx()` 估算，并在日志里标明"估算值"。
- **现象：流式请求中途报错，已经打印了一半的内容收不回来。** 这是流式的固有特性。改法：先缓冲到变量，成功后再整体渲染；或者把"已收到的部分"当降级结果处理（并记录 trace，第 12 章）。

## 本章小结

| 结论 | 关键细节 |
|------|----------|
| 按 Token 计费，不按字数 | 中文 1 字 ≈ 0.6–1 Token（保守按 1）；英文 1 Token ≈ 4 字符；代码 1 Token ≈ 3 字符 |
| 上下文窗口 = 输入 + 输出 | `输入预算 = 窗口 − max_tokens − 安全余量`，超了报 400 |
| `finish_reason` 必须看 | `length` = 被截断（JSON 会残缺），`stop` = 正常结束 |
| 采样参数只调一个 | 抽取/分类 `temperature=0`；文案 0.7–1.0；`top_p` 一般不动 |
| `temperature=0` 不等于确定 | 浮点、批处理、MoE 路由、副本差异、模型版本都会引入变化 |
| 输出单价是输入的 3–4 倍 | 让模型"少说废话"是真省钱 |
| Agent 循环接近平方级烧钱 | 每轮重发历史：5 轮成本 ≈ 单轮的 7.2 倍，20 轮 ≈ 单轮的 61 倍 |
| 幻觉的根因是"知识缺失 + 没有出口" | 五种手段：给材料、要求引用并校验、事实走工具、给"不知道"的出口、后校验降级 |
| 长文档必须切片 | 装不下、贵 60 倍、中段信息会被忽略（Lost in the Middle） |
| 流式只改感知 | TTFT 从 8.2s 降到 0.6s，总时长不变，费用不变 |

## 自测题

**第 1 题：** 一段 800 字的中文说明文，大概是多少 Token？为什么不能直接按"字数"给客户报价？

**第 2 题：** 模型输出到一半停住了，`finish_reason` 是 `length`。列出两种可能的修法，并说明各自的代价。

**第 3 题：** `temperature` 设成 0，同一个请求两次调用结果不同，可能是哪些原因？（至少说出三个）

**第 4 题：** 一个 Agent 循环跑 10 轮，为什么成本远高于"10 轮单次调用"？请用"每轮重发历史"解释。

**第 5 题：** 模型回答里出现了"订单 DP9999，退款 500 元"，但系统里没有这个订单、政策里也没有金额。请给出至少三种工程手段来防止这类问题。

<details>
<summary>点击查看答案</summary>

**第 1 题：** 按保守估算（1 汉字 ≈ 1 Token）约 800 Token；如果模型分词器对中文效率高（约 0.6–0.7 Token/字），实际约 500–600 Token。不能按字数报价的原因：① 不同模型/不同服务商分词器不同，差 20% 很常见；② 计费含输入和输出两侧，且**历史消息每轮都要重发**；③ 数字、英文、标点、换行、emoji 都另算。正确做法是打印真实的 `usage` 并累加。

**第 2 题：** ① **调大 `max_tokens`**（比如从 512 到 2048）—— 代价是单次最多能生成的量增加，极端情况下更贵更慢；② **让模型输出更短**（prompt 里限制"只输出 JSON、不要解释"）—— 代价是可能需要重写 prompt 并重测格式稳定性。补充：如果输入已经接近窗口上限，还要同时缩减历史，否则调大 `max_tokens` 会直接触发 400 超限。

**第 3 题：** ① 浮点累加顺序/批处理组成不同；② 服务端动态批处理与并行 kernel 的差异；③ MoE 专家路由的随机性；④ 多副本负载均衡到不同推理框架或量化版本；⑤ 服务商更新了模型版本（不知不觉就变了）。工程含义：需要可复现时固定 `seed` + 固定具体模型名 + 用"多次运行一致率"做指标。

**第 4 题：** 因为大模型没有跨请求的记忆，每一轮都要把 `system + 全部历史 + 新输入` 重新发一遍。第 2 轮的输入 = 第 1 轮输入 + 第 1 轮输出 + 工具结果；第 3 轮又在这基础上继续叠加。设首轮输入 350、每轮增量 250，10 轮的累计输入 = `10×350 + 250×(0+1+…+9) = 3500 + 11250 = 14750` Token，而"10 次独立单轮"只要 `10×350 = 3500` Token —— **差 4 倍以上**，轮数越多差距越大（接近平方增长）。这也是必须设步数上限的经济理由。

**第 5 题：** ① **结构校验 + 存在性校验**：订单号先用正则校验格式，再调订单服务确认真实存在，任一步失败就丢弃该字段（不是丢弃整个回答）；② **事实走工具**：金额、日期、库存这类可验证事实**不允许模型生成**，必须由代码从系统查出后填入模板；③ **给"不知道"的出口**：prompt 里明确要求"材料未提及的信息写 null / 说『材料未提及』"，并统计 `null` 比例作为材料覆盖率的指标；④ 要求引用编号并**用代码校验编号是否落在候选材料范围内**；⑤ 后校验失败就把错误回灌给模型重试（第 03 章），仍失败降级为"转人工"。

## 结语与下一章

Token 是模型的口粮，窗口是它一次能摊开的工作台，概率是它的性格。你要把它当成一个临时工来用，就得先接受这三件事：按口粮付钱、按工作台的大小限活、按性格防它随口乱说。这一章留下的不是三个知识点，而是一张能拿去报价、也能拿去验收的账本。

但账算清了只解决了"花多少"；还有一件事没解决 —— 它说出来的话，你的程序不一定接得住。

下一章是第 03 章《Prompt 工程与结构化输出》，解决一个分水岭问题：**怎么让模型输出程序能解析的东西。** 我们会讲六段式 prompt（角色/任务/约束/输入/输出格式/示例）、让模型稳定输出 JSON 的完整套路、必须写的那层代码校验（`safe_parse_json` + 把报错回灌给模型的重试）、三种结构化输出方案（纯 Prompt / JSON mode / Function Calling）的取舍，以及 9 个真实踩坑现场 —— 从 ` ```json ` 包裹到中文引号，从数字变字符串到输出被截断。
