# 第09章 Skills 能力包

> **本章目标：** 把"每次都往 prompt 里粘"的流程，沉淀成能被自动触发、按需加载的 `SKILL.md`，并用 A/B 对比证明它真的提升了成功率。
> **预计用时：** 3 小时　**前置章节：** 第05章（ReAct 最小 Agent Loop）、第07章（记忆与上下文工程）　**配套代码：** `code/ch09_skills.py`　**配套文件：** `skills/example-skill/SKILL.md`

## 0. 开篇：一个真实的问题

上个月有位同学来找我，说他给团队做的"代码审查助手"已经跑通了——第 05 章的 ReAct 循环，加第 08 章的知识库，功能一个不少——但他快被这套东西烦死了。

我让他把屏幕共享打开，于是看到了这样的对话：

> "你看，每次开新会话我都得把同一段 30 行的审查清单粘进去。上个月粘漏了一条，那个 PR 上线就出事了。"
>
> 我问他："那为什么不把它固定下来，写进代码里？"
>
> "试过。我把清单写成常量 `REVIEW_CHECKLIST`，结果改一次清单就要改代码、重启服务，业务同学没法自己维护。"
>
> "那就写成技能文件，让模型按需加载？"
>
> "写了，`SKILL.md` 放在那儿三个月，从来没触发过。而且两个项目要两套规则——一个查并发、一个查 SQL 注入——我把两套都塞进 prompt，模型开始串味：审 Java 项目的时候给我讲 Python 的 GIL。"
>
> 我最后问了一句："那这段清单到底有没有用？"
>
> 他愣了一下："……感觉好像认真了一点。"

**"感觉好像认真了一点"——这就是问题所在。** 这段清单 800 token，每天 200 次调用就是 16 万 token/天，全是重复的老话；而它有没有让审查质量真的变好，你手上没有任何证据。

这类问题很常见，而且它不是"你写得不好"，更不是模型太笨——**问题出在承载方式上。**

这里的本质问题是：**流程知识（Procedural Knowledge）被当成了本次对话的临时指令。**

流程知识有三个特点，而 prompt 一个都满足不了：

| 流程知识的特点 | 塞进 prompt 的后果 |
|---|---|
| 会被反复使用 | 每次都要重发，token 白烧 |
| 需要独立更新 | 改流程 = 改代码 = 重新部署 |
| 只在特定任务才需要 | 无关任务也带着，互相干扰 |

把它抽出来的那份东西就是本章的主角：**Skill（技能包）**；支撑它落地的机制叫**渐进式加载（Progressive Disclosure）**——平时只让模型看到"技能目录"，命中任务时才把正文注入上下文。

所以这一章就干三件事：把 Skill 的结构拆开看（尤其是决定它会不会被触发的 `description`）、把渐进式加载的成本账算清、最后用一次 A/B 对比拿到数字——证明这个技能到底值不值得留在你的仓库里。

### ⚠️ 常见坑

- **现象**：把产品文档、接口手册整本粘进 `SKILL.md`，结果技能又长又没人看。**原因**：混淆了"流程知识"（怎么做一类任务）与"领域资料"（事实与数据）——后者属于第 08 章的 RAG。**怎么改**：Skill 只写"怎么做"，资料在运行时检索注入。
- **现象**：写了 5 个技能，一个月后自己都忘了用，更别说让别人用。**原因**：技能没进版本管理，也没有触发场景。**怎么改**：技能和代码一样进 Git，改一次就跑一次 A/B（第 6 节），把结果记在笔记里。
- **现象**：想写一个"什么都能干"的万能技能。**怎么改**：一个技能一个任务类型（见第 2 节），多了就拆——描述越具体，触发越准。

## 1. 先把四个概念分清：Tool / Prompt / Skill / MCP

0 基础读者最容易在这里糊成一团：这四个词都会在"让 Agent 变强"的语境里出现，看起来像同义词。**它们不是竞品，是四个不同层次的东西。**

| 概念 | 是什么 | 解决什么 | 例子 |
|---|---|---|---|
| **Tool**（工具） | 一个可调用的接口 | 让模型**能做**一件事 | `read_file(path)`、`search_web(query)` |
| **Prompt**（提示） | 一次性的指令 | 控制**这一次**的输出 | "把下面内容总结成 3 点" |
| **Skill**（技能包） | 可复用的流程知识包 | 让模型知道**一类任务该怎么做** | "代码审查该按什么顺序、查哪些项" |
| **MCP**（模型上下文协议） | 连接外部工具/数据源的标准协议 | 不用为每个工具写一遍适配 | 文件系统 MCP Server |

用"代码审查"这一件事把四者串起来，你就能看出它们是**叠加关系**，不是**替代关系**：

- Prompt 说：**"这次重点看并发安全"**（本次的特殊要求）
- Tool 让模型：**真的把 `order_service.py` 读进来**（能力）
- Skill 告诉模型：**审查要按"正确性 → 边界 → 错误处理 → 并发 → 安全 → 性能 → 可测性"的顺序过，每个问题标风险等级，最后必须给测试建议**（流程）
- MCP 负责：**让"读文件"这个能力在 Cursor、Claude Desktop、你自己的脚本里都能用同一份实现**（接入标准化，第 10 章细讲）

一次真实的审查任务长这样：

```text
用户：帮我审一下这个 PR（Prompt：本次意图）
  ↓
Agent 加载 code-review 技能（Skill：流程与验收标准）
  ↓
调用 read_file / run_tests（Tool：真正干活，由某个 MCP Server 提供）
  ↓
输出：问题清单 + 风险等级 + 测试建议（Skill 规定的验收形状）
```

**判断口诀**：模型"不能做"某件事 → 缺 **Tool**；模型"做得不对、不按套路" → 缺 **Skill**；每个应用都要重写一遍工具适配 → 缺 **MCP**；只有这一次有特殊要求 → 用 **Prompt**，别建成 Skill。

### ⚠️ 常见坑

- **现象**：把 Skill 写成一篇 2000 字的"操作手册"，指望它提升效果，结果模型照样跳步骤。**原因**：Skill 是"按需加载的流程文件"，不是"更长的 prompt"；一次注入太多要求，模型会挑好做的做。**怎么改**：正文控制在 7±2 个步骤，细节挪到附带资源（`reference.md` / `scripts/`），正文里只写"什么时候调用它"。
- **现象**：在 Skill 里写"用 read_file 读取代码"，以为工具就接上了，结果运行时报 `tool not found`。**原因**：Skill 只是一段文字，不能注册任何工具。**怎么改**：工具必须真的注册进 `ToolRegistry`（第 04 章）并暴露 schema；Skill 只负责"什么时候该用哪个工具"。
- **现象**：把"总结成 3 点"这种一次性要求也写成 Skill。**原因**：混淆了"本次指令"和"一类流程"。**怎么改**：判断标准是"下个月还会不会再用一次"——不会，就别建 Skill。

## 2. Skill 的解剖：一个 `SKILL.md` 里到底有什么

一个 Skill 就是一个目录，核心是 `SKILL.md`：

```text
skills/
└── example-skill/
    ├── SKILL.md          ← 必需：frontmatter（元信息）+ 正文（流程）
    ├── templates/        ← 可选：输出模板，用到才读
    └── scripts/          ← 可选：确定性脚本，用到才执行
```

### 2.1 frontmatter：给"加载器"看的部分

```markdown
---
name: example-skill
description: >-
  一句话说清"做什么 + 什么时候用 + 什么时候别用"。
  当用户说"xxx / yyy"时使用；只是 zzz 时不要使用。
---

# 技能标题

## 何时使用
...
## 步骤
1. ...
## 验收标准
- [ ] ...
```

字段说明：

| 字段 | 必需 | 作用 | 写错会怎样 |
|---|---|---|---|
| `name` | 是 | 技能标识，要求 kebab-case，与目录名一致 | 加载器找不到 / 调用时对不上号 |
| `description` | 是 | **唯一常驻上下文的内容**，负责"被找到" | 技能永远不触发，或到处乱触发（见第 3 节） |
| `version` / `license` 等 | 否 | 团队协作时的版本信息 | 无直接影响 |

### 2.2 正文：给"模型"看的部分

正文是五个固定小节，缺一个都会出问题：

1. **何时使用** —— 正向触发场景，写具体动作（"用户给出 diff 并要求找问题时"）。
2. **不适用** —— 反向边界。**这一节最容易被省，也最容易出事**：没有它，模型会把技能往所有相近任务上套。
3. **步骤** —— 编号、祈使句、每步说清产物。这是 Skill 的主体价值。
4. **验收标准** —— 可判定的完成条件（checklist）。**没有它，模型不知道什么时候算做完**，于是"再补充一点点"停不下来；配一个正例加一个反例，比十句描述都管用。

### 2.3 附带资源：给"执行"看的部分

- `scripts/`：能确定性完成的事，别让模型"想"。比如统计 diff 行数、格式化输出、跑 lint。
- `templates/`：输出形状固定的东西（报告模板、审查表格）。
- `reference.md`：长清单、长表格、接口文档——**只在需要时读，不要抄进正文**。

规则一句话：**正文写"什么时候用脚本"，不写"脚本里是什么"。**

### ⚠️ 常见坑

- **现象**：`name: 代码审查`（中文 + 空格）导致加载失败。**原因**：多数加载器按文件系统友好的标识处理名字，且要求与目录名一致。**怎么改**：统一小写 kebab-case，`name` 与目录名逐字符相同。
- **现象**：解析 frontmatter 时报 `mapping values are not allowed here`。**原因**：YAML 里 `description: 审查代码: 检查并发` 出现了第二个冒号，被当成新的键值对。**怎么改**：整句用引号包住，或改写成 `description: >-` 折叠块（推荐）。
- **现象**：把 5 个场景塞进一个 Skill，触发后上下文里一半是无关内容。**原因**：一个 Skill 想覆盖太多任务类型，description 只能写得很宽泛。**怎么改**：**一个 Skill 一个任务类型**；子场景用参数区分（比如 `path` 参数），而不是靠描述区分。

## 3. description 是 Skill 的生死线

模型的"技能选择"是一次**语义匹配**，不是正则匹配。它唯一能看到的常驻信息就是 `name` + `description`。所以：**描述写得不对，正文写得再好也永远不触发。**

两种典型死法：

| 死法 | 描述 | 后果 |
|---|---|---|
| **太不具体** | `description: 帮助处理代码` | 模型不知道什么时候该用 → 永远不触发 |
| **太宽泛** | `description: 代码相关的一切任务，包括审查、编写、重构、解释、补全` | 聊什么都能命中 → 每次都注入，上下文被污染，还挤掉了真正该用的技能 |

正反例对照（可直接照抄的结构）：

```markdown
# ❌ 反例 1：太虚
description: 一个帮助审查代码的技能

# ❌ 反例 2：太宽（审查、编写、重构、解释、补全全都命中）
description: 处理代码相关任务，提供专业的代码建议

# ✅ 正例：做什么 + 什么时候用 + 什么时候别用
description: >-
  审查代码改动（git diff、单个文件或一段代码），按风险从高到低输出问题清单、
  修复建议和测试建议。当用户说"审查代码 / 审一下 / review / 看看有没有问题 /
  有没有 bug / 帮我看看这个 PR"时使用。只是解释代码在做什么、或者补全代码时不要用。
```

正例里三个成分缺一不可：**做什么**（审查代码改动，输出问题清单 + 修复建议 + 测试建议）、**什么时候用**（把用户**真实会说的话**列出来，含中文口语、英文单词、同义词）、**什么时候别用**（排除最容易混淆的两个邻居：解释代码、补全代码）。

**触发词从哪来？** 不要凭想象编。翻你自己的历史对话，把原话抄进去。真用户说的是"审一下"、"看看有没有坑"、"这个 PR 有啥问题"，而不是"请执行代码审查流程"。**描述里没有用户的原话，就不会在用户说那句话时被触发。**

> 触发词决定了技能的**召回**，边界句决定了技能的**准确率**。这两个指标，第 6 节的 A/B 会分别量出来。

### ⚠️ 常见坑

- **现象**：技能写完了，测试时怎么问都不触发。**原因**：description 只写了"是什么"（"一个代码审查技能"），没写"什么时候用"。**怎么改**：补上触发条件句 + 用户原话清单，然后跑 `code/ch09_skills.py` 看匹配分数——低于阈值就是描述的问题，不是模型的问题。
- **现象**：闲聊一句"这个 bug 真烦"也被注入审查技能。**原因**：描述过泛，`bug` 这种高频词把无关请求也拉进来了。**怎么改**：加边界句（"只是讨论技术概念时不要使用"），把阈值从 0.30 提到 0.40 以上再观察。
- **现象**：两个技能同时命中，指令互相矛盾。**原因**：职责有重叠，比如 `code-review` 和 `security-review` 都写了"检查安全问题"。**怎么改**：在各自的 description 里写清互斥条件（"若任务是专项安全审计，请改用 security-review"），或让上层加载器只注入 top-1。

## 4. 渐进式加载：为什么不能一次全塞进上下文

假设你攒了 20 个技能，每个正文 400 token。**全量注入 = 每次请求 8000+ token 起步**，而且每次请求都带着 19 份用不上的流程——这既烧钱，又干扰模型判断（无关规则会挤占注意力）。

**渐进式加载（Progressive Disclosure）** 把它拆成三层，按需展开：

| 层级 | 内容 | 何时进入上下文 | 量级 |
|---|---|---|---|
| **Level 0 · 目录** | 所有技能的 `name` + `description` | 常驻 | 每个 40–100 token |
| **Level 1 · 正文** | 命中技能的步骤 + 验收标准 | 任务命中时 | 每个 100–500 token |
| **Level 2 · 资源** | `scripts/`、`templates/`、`reference.md` | 正文里让模型"需要时再读" | 可能上千 token，但通常不读 |

关键实现只有两件事：**一个索引**，和**一个匹配函数**。

```python
# 节选自 code/ch09_skills.py —— 目录常驻，正文只注入命中的那一份
class SkillIndex(object):
    def catalog(self):
        """技能目录：只有 name + description，token 成本很低。"""
        return "\n".join(s.index_line() for s in self.skills)

    def match(self, task):
        """返回 [(分数, Skill), ...]，最多 top_k 个；低于阈值一律不返回。"""
        return [(score, skill) for score, skill in self.score_all(task)
                if score >= self.threshold][: self.top_k]

    def progressive_prompt(self, picked):
        """正确做法：目录常驻 + 只注入命中技能的正文（资源只给路径）。"""
        parts = ["你是 Agent。可用技能目录（命中才需要执行）：", self.catalog()]
        if picked:
            parts.append("\n本次任务请按以下技能执行：")
            for _score, skill in picked:
                hint = ""
                if skill.resources:
                    hint = "（附带资源，需要时再读取：%s）" % ", ".join(skill.resources)
                parts.append("\n## 技能：%s\n%s\n%s" % (skill.name, skill.body, hint))
        return "\n".join(parts)
```

配套代码 `ch09_skills.py` 的实测输出（5 个技能的演示集，`AGENT_MOCK=1` 跑出来的真实数字）：

```text
全量注入（每次请求都带上全部 5 个技能正文）：723 token

审查一下这个 PR 的改动…      渐进式 660 token   节省 9%
帮我写一份关于向量数据库的…  渐进式 560 token   节省 23%
解释一下 def foo(x): …       渐进式 376 token   节省 48%

技能越多，差距越大：如果有 20 个技能、每个正文 400 token，全量注入约 8000+ token/次；
而渐进式只要"目录 20 个 × 60 token + 命中 1 个正文 400 token" ≈ 1600 token，差 5 倍以上。
```

注意第一行：**技能只有 5 个时"省"得并不明显（9%）**——渐进式加载的收益随技能数量增长，所以两三个技能不值得搭，二十个时它是刚需。

三个实现细节，缺一个都会翻车：

1. **索引只建一次**：扫描目录 → 解析 frontmatter → 缓存在内存里。别在每次请求时遍历磁盘。
2. **必须设 `top_k` 上限并留痕**："全部命中"等于没做渐进式加载（默认注入 1–2 个）；把"任务 → 命中技能 → 分数"写进 trace，调阈值时你唯一能依赖的就是这份记录。

### ⚠️ 常见坑

- **现象**：跑了几天发现上下文里永远有 5 个技能正文。**原因**：阈值设得低（0.20）又没设 `top_k`。**怎么改**：先跑一遍全部任务，打印每个技能的匹配分数，找一条明显的分界线（命中通常 0.45+，误命中通常 0.35 以下），把阈值放在缝里。
- **现象**：离线模式触发正常，接上真模型后技能不再被使用。**原因**：离线是关键词/字符重合度匹配，在线可能是模型自己"挑技能"；两套逻辑的判据不同。**怎么改**：把"选择了哪个技能"和"匹配分数"都记进 trace，对比两套逻辑的分歧样本，别同时改两个变量。
- **现象**：`description` 写得很好但技能还是不用。**原因**：注入位置不对——技能正文被塞进了 user 消息里，模型把它当成"用户提供的背景资料"而不是"必须执行的规范"。**怎么改**：注入到 system prompt 末尾，并在前面加一句角色说明（"本次任务请按以下技能执行"）。

## 5. 怎么写一个好的 Skill：从一次成功的任务里"抽"出来

**不要设想一个流程再写下来——那是纸上谈兵。** 正确做法是四步反推：

| 步骤 | 做什么 | 判断标准 |
|---|---|---|
| 1. 先成功一次 | 手工把这类任务做成功一次（允许试错、允许查资料） | 有可交付的产出 |
| 2. 记录动作 | 把"你脑子里默认做的事"写出来，包括你自己都没意识到的检查项 | 能列出 5–10 条动作 |
| 3. 固定顺序 | 排成编号步骤，每步写清输入、产物、如何验证 | 每步都能被外人照做 |
| 4. 补验收标准 | 写 checklist + 一个正例一个反例 | 判据可机械判定 |

第 2 步最容易被跳过。真正的流程知识藏在"我顺手看了一眼"里：看依赖有没有改、配置有没有跟着改、错误处理是不是裸 `except`。**这些"顺手"才是 Skill 的价值，而不是"要仔细审查"这种正确的废话。**

```markdown
# ❌ 含糊，模型只能自由发挥
2. 检查代码质量，注意错误处理和安全问题。

# ✅ 可执行，每条都能判定
2. 逐项检查，顺序固定：
   - 每个 except 是否指定了具体异常类型（裸 except / except Exception 记为中风险）
   - 每个外部输入（HTTP 参数、文件、环境变量）是否有校验
   - 每个资源（文件、锁、连接）是否有释放路径
   - 是否存在把用户输入拼进 SQL / shell 的写法（记为高风险）
```

还要写**越界禁令**。比如审查技能必须写"不要顺手重写代码"——否则模型会给你一份重构后的版本，而你要的是问题清单。约束的反面同样是契约的一部分。

### ⚠️ 常见坑

- **现象**：模型绕着步骤走，只做最容易的两步。**原因**：步骤用了商量语气（"可以考虑检查……"），模型把它当建议。**怎么改**：全部改成祈使句 + 编号，每步写明产物（"输出：问题清单表格"）。有产物才有验收。
- **现象**：模型做完还在"再补充一点"，输出越来越长。**原因**：没写验收标准，模型不知道终点在哪。**怎么改**：加 `## 验收标准` checklist，并在末尾写一句"满足以上全部条件即停止，不要额外扩写"。
- **现象**：技能在你手上好用，同事用同一个技能却触发不了。**原因**：你的 description 里写的是你的说话习惯。**怎么改**：收集 3 个以上同事的真实提问原话，全部塞进触发词清单；把这条写进团队的 Skill 评审清单。

## 6. 验证 Skill 真的有用：A/B smoke test

凭感觉说"好像变好了"是 0 基础学习者最容易养成的坏习惯。**验证只有一个办法：同一批任务，跑两遍，用代码判定。**

设计要点（少一个结论就不可信）：

1. **任务集固定**：6–10 条，从真实历史里挑，覆盖典型 + 边界 + 一条"不该触发"的。
2. **成功判据可机械判定**：每条任务写出"必须出现哪些要素"，交给代码检查，不靠人眼看。
3. **重复 3 次，除技能外全部一致**：模型有随机性，单次结果不可信；同一模型、同一 temperature、同一提问模板。
5. **必须有等长基线**：A 组不能是"空白 prompt"——那证明的只是"上下文变长了有用"。正确做法是给 A 组塞**等量的无关文本**，这样才分离出"技能内容有用"这个变量。
6. **指标一起看**：成功率提升 ≥ 20 个百分点，**且** token 增幅 < 50%，才算这个技能值得留。

判定器就这么简单，关键是能自动跑：

```python
# 节选自 code/ch09_skills.py
def judge(answer, checks):
    """判定器：返回命中了几条判据。真项目里应换成更严格的断言或模型评审。"""
    return sum(1 for word in checks if word in answer)
```

`ch09_skills.py` 的实测输出（离线 Mock 模式下，答案由脚本内的固定答案提供）：

```text

--------------------------------------------------------------------------
审查一下这个 PR 的改动…       code-review     3/9 (33%)     9/9 (100%)
帮我写一份关于向量数据库的…   research-report 3/9 (33%)     9/9 (100%)
解释一下 def foo(x): …        -               0/9 (0%)      0/9 (0%)
--------------------------------------------------------------------------
判据命中率：不带 skill 15/54（28%）　带 skill 45/54（83%）
system prompt token 合计：不带 skill 108　带 skill 9870
```

**看清这段输出的性质**：离线时"带 skill 就全对"来自脚本里的固定答案，只能验证**判定器与统计口径能跑通**。真实结论要去掉 `AGENT_MOCK` 重跑，数字会难看很多（经验值：提升 10–30 个百分点算好结果，翻倍提升通常说明判据太松）。最后一行提醒代价：**带技能时 system prompt 涨到 9870 token**——判据与成本必须一起看。

### ⚠️ 常见坑

- **现象**：A/B 显示"带技能成功率从 40% 涨到 90%"，上线后毫无感觉。**原因**：判据写成了关键词命中，而技能正文里本来就含这些关键词，等于自己给自己打分。**怎么改**：判据要写成"可验证的内容要求"（必须包含对比表、必须给出可复现的测试步骤），并且让一个**没读过技能**的人来写判据。
- **现象**：改了 3 个地方（description、步骤、模型）后一起测，效果提升但不知道是谁的功劳。**怎么改**：一次只改一个变量，其余保持不变；改完重跑同一批任务，把三组数字都记进 `03-学习笔记/`。
- **现象**：离线全绿就以为通过了。**原因**：把"代码能跑"当成了"效果变好"。**怎么改**：把离线跑当作"检查器自检"，把在线跑当作"效果验收"，两步都写进本章的交付标准。

````markdown
# 代码审查

## 何时使用
用户给出改动、文件或 PR，要求找问题。

## 不适用
- 只是问"这段代码在做什么" → 直接解释，不要走审查流程。
- 要求"帮我写完这个函数" → 这是编码任务，不是审查任务。
- 要求做整体架构评审 → 超出本技能范围，应改用专门的架构评审技能。

## 步骤
1. 先确定改动范围：改了哪些文件、新增还是修改（需要时运行 `scripts/count_diff.py`）。
2. 按固定顺序检查：正确性 → 边界条件 → 错误处理 → 并发与资源 → 安全 → 性能 → 可测性。
3. 每个问题标注风险等级：高（会出错/丢数据）、中（易踩坑）、低（风格）。
4. 输出问题清单表格：文件:行 / 风险等级 / 问题 / 修复建议。
5. 给测试建议：每个高风险问题至少一条能复现的用例。

## 验收标准
- [ ] 输出含问题清单表格，每行都有风险等级
- [ ] 至少给出一条测试建议
- [ ] 没问题也要写明"未发现高风险问题"，不能空着

## 输出格式
见 `templates/review.md`。
````

逐段讲解：

| 部分 | 为什么这么写 |
|---|---|
| `name: example-skill` | kebab-case，与目录名严格一致；加载器据此建立索引 |
| `description: >-` | 用折叠块避免 YAML 冒号陷阱；三句话分别覆盖"做什么 / 什么时候用 / 什么时候别用" |
| `version: 1` | 技能也要有版本，改了流程就升版本，A/B 对比时才分得清"哪一版" |
| `## 何时使用` | 正向场景，一句话说清触发条件 |
| `## 不适用` | **防乱触发**。三个邻居场景逐个排除，比在 description 里堆形容词有效 |
| `## 步骤` 第 1 步 | 把"确定性的事交给脚本"：数 diff 行数不需要模型推理，跑脚本更便宜也更准 |
| `## 步骤` 第 2–3 步 | 顺序固定 → 结果可对比；风险分级 → 输出能排序、能筛选 |
| `## 验收标准` | 三条全是**可判定**的：表格、测试建议、空结果声明。没有"质量要高"这种空话 |
| `## 输出格式` | 只给模板**路径**，不抄模板内容——这就是前面说的"正文写什么时候用，不写里面是什么" |

### ⚠️ 常见坑

- **现象**：技能里引用了 `scripts/count_diff.py`，模型去读时发现文件不存在，于是开始编造脚本内容。**原因**：写文档时顺手写了个路径，但没有真的建文件。**怎么改**：技能里出现的每个路径都必须存在，且脚本要能独立跑；在正文里给一行用法（`python scripts/count_diff.py --diff a.patch`），模型就不会猜。
- **现象**：验收标准写成"输出要专业、要全面"。**原因**：把愿景当标准。**怎么改**：逐条问"这条能不能用代码判定？"——不能就重写。
- **现象**：技能维护半年后没人知道哪版好用。**原因**：没有版本和变更记录。**怎么改**：`version` 字段 + 在 `03-学习笔记/` 里记录每次改动对应的 A/B 结果。

## 8. 配套代码走读：`code/ch09_skills.py`

脚本干三件事：**扫描目录建索引 → 按任务匹配技能 → 跑 A/B 对比**；不依赖第三方库（frontmatter 自己解析），`AGENT_MOCK=1` 直接跑通。

**片段 1：解析 frontmatter**（`code/ch09_skills.py:65`）。项目坚持"最小依赖"，所以不引入 PyYAML，30 行手写解析足够覆盖 `key: value` 和 `key: >-` 两种写法：

```python
def parse_frontmatter(text):
    """把 SKILL.md 拆成 (meta 字典, 正文)。支持 key: value 与 key: >- 折叠块。"""
    lines = text.splitlines()
    if not lines or lines[0].strip() != "---":
        return {}, text
    meta, key, i = {}, None, 1
    while i < len(lines) and lines[i].strip() != "---":
        line = lines[i]
        stripped = line.strip()
        if key and line[:1] in (" ", "\t") and stripped:
            meta[key] = (meta[key] + " " + stripped).strip()      # 折叠块的续行
        elif ":" in line:
            key, value = line.split(":", 1)
            key, value = key.strip(), value.strip()
            if value in (">-", ">", "|", "|-"):
                meta[key] = ""                                     # 下面几行才是内容
            else:
                meta[key] = value.strip("\"'")
        i += 1
    return meta, "\n".join(lines[i + 1:]).strip()
```

**片段 2：匹配打分**（`code/ch09_skills.py:93`）。用**字符二元组（bigram）重合度**代替分词——中文不需要装分词器，英文单词也能自然匹配（`bug` 会切出 `bu`、`ug`）：

```python
def bigrams(text):
    """取字符二元组并去掉标点：'审查代码' -> {'审查','查代','代码'}"""
    chars = [c for c in text.lower() if c not in PUNCT]
    return set(chars[i] + chars[i + 1] for i in range(len(chars) - 1))


def overlap(task, description):
    """任务文本的二元组里，有多大比例能在 description 中找到。"""
    task_bg = bigrams(task)
    if not task_bg:
        return 0.0
    return len(task_bg & bigrams(description)) / float(len(task_bg))
```

实测分数（阈值 0.40）：`审查一下这个 PR……` → `code-review=0.72` 命中；`解释一下 def foo(x)……` → 最高分只有 `0.32`，不注入任何技能。**这就是"该触发的触发、不该触发的不触发"能被量化的样子**。

**片段 3：A/B 对比**（`code/ch09_skills.py:326`）。核心是"两组只差一个变量"：

```python
for _round in range(ROUNDS):
    prompt_a = "你是 Agent。"                       # A 组：不给技能
    prompt_b = index.progressive_prompt(picked)     # B 组：渐进式注入
    answer_a = FAKE_WITHOUT_SKILL.get(skill_name, GENERIC_ANSWER) if is_mock_mode() \
        else chat(task, system=prompt_a, temperature=0.2)     # 离线用固定答案，在线走真模型
    answer_b = FAKE_WITH_SKILL.get(skill_name, GENERIC_ANSWER) if is_mock_mode() \
        else chat(task, system=prompt_b, temperature=0.2)
    row_a += judge(answer_a, checks)
    row_b += judge(answer_b, checks)
```

## 本章小结

1. **四个概念各就各位**：Tool 让它能做，Prompt 管这一次，Skill 管一类任务的流程，MCP 管工具怎么被复用接入。它们叠加使用，不是四选一。
2. **Skill = 一个目录 + 一份 `SKILL.md`**：frontmatter 负责"被找到"，正文负责"怎么做"，附带资源负责"确定性执行"。
3. **`description` 是生死线**：写清"做什么 + 什么时候用 + 什么时候别用"，并把用户真实说过的话抄进去。
4. **渐进式加载是成本与效果的平衡术**：目录常驻、正文按需、资源最后。技能越多收益越大，两三个技能不值得搭。
5. **写技能靠反推，不靠想象**：先成功做一次 → 记录动作 → 固定顺序 → 补验收标准与越界禁令。
6. **效果必须测**：固定任务集 + 等长基线 + 重复 3 次 + 代码判定 + 同时看成功率与 token。
7. **关联阅读**：[[02-Wiki/专题总结/07-Skills与MCP协议]]、`skills/example-skill/SKILL.md`。

## 自测题

**1. Tool、Prompt、Skill、MCP 分别在什么情况下是"正确答案"？**

<details><summary>点击查看答案</summary>

- 模型**不能做**某件事（读文件、发请求）→ 缺 **Tool**，注册工具并暴露 schema。
- 只有**这一次**有特殊要求（"总结成 3 点"）→ 用 **Prompt**。
- 模型**做得不规范**、每次都漏步骤、流程需要复用和迭代 → 写 **Skill**。
- 同一个工具要被**多个应用**复用，不想为每个应用写适配 → 用 **MCP** 接入。

判断顺序：先看是不是"只有这一次"，再看是不是"没这个能力"，再看是不是"流程问题"，最后看是不是"接入重复"。

</details>

**2. 为什么 Skill 的 `description` 比正文更重要？**

<details><summary>点击查看答案</summary>

因为模型在选择技能时，上下文里**只有 `name` + `description`**（Level 0 目录）。正文只有在命中之后才会被加载。描述不具体 → 永远不触发；描述太宽泛 → 到处触发、污染上下文。正文写得再好，没被选中就等于不存在。

</details>

**3. 渐进式加载的三层各是什么？为什么不能一次全塞进上下文？**

<details><summary>点击查看答案</summary>

Level 0 目录（name + description，常驻）、Level 1 正文（命中后注入）、Level 2 资源（脚本/模板/参考文档，需要时才读）。

不能全塞的原因有两个：一是 token 成本线性增长（20 个技能 × 400 token = 8000+ token/次，且每次调用都重复付），二是无关规则会干扰模型判断，反而降低效果。

</details>

**4. 一个 Skill 的验收标准应该怎么写？举一个反例和改法。**

<details><summary>点击查看答案</summary>

要写成**可机械判定**的条件。反例："输出要专业、要全面、质量要高"——无法判定，模型不知道什么时候算完成。改法示例：`- [ ] 输出含问题清单表格，每行都有风险等级`、`- [ ] 至少给出一条测试建议`、`- [ ] 没有发现问题时写明"未发现高风险问题"`。判断方法：逐条问"这条能不能用代码或明确的清单核对？"

</details>

**5. A/B smoke test 里，为什么 A 组不能是空白 prompt？**

<details><summary>点击查看答案</summary>

因为那样你无法区分"技能内容有用"和"上下文变长有用"。正确做法是给 A 组塞**等量的无关文本**作为基线，两组只差"内容是否为技能规范"这一个变量。另外还需要：固定任务集、每条跑 3 次、判据由代码执行、成功率和 token 一起看。

</details>

- [ ] 一个可用的 `skills/example-skill/SKILL.md`：frontmatter 完整（name/description），正文含"何时使用 / 不适用 / 步骤 / 验收标准"，至少 1 个附带资源；跑一次离线脚本验证它能被扫到。
- [ ] 一次 `AGENT_MOCK=1 python code/ch09_skills.py` 的完整输出，能指着它讲清四段内容；以及一次**在线模式**的 A/B 结果（6 条以上任务、每任务 3 次、记录成功率与 token 变化）。
- [ ] 一条明确的结论：这个 Skill 值得留还是该改（给出数字，不给感觉）。如果该改，说明改哪里（description？步骤？阈值？）。
- [ ] 记进 `03-学习笔记/`：改动前后对比、踩到的坑、"如果重来我会怎么写"。

**验收问句**（能答上来才算过关）：为什么这个技能会在用户说那句话时被触发？不触发时你从哪里看出是哪一环出的问题？

## 结语与下一章

Skill 不是一个更长的 prompt，而是一个带目录、按需翻页的工具箱：模型平时只看见书架上的一排标签，真正动手时才把那一页翻开——流程知识从此和对话历史分了家。

但流程的复用被解决之后，另一份重复劳动还在原地：工具本身仍然硬编码在你的项目里，同一套文件操作能力要接到 Cursor、Claude Desktop 和自己的脚本上，就得写三遍适配。

第 10 章 [[docs/第10章 MCP与通信协议]] 讲 **MCP（Model Context Protocol）与通信协议**：Server / Client / Host 三方角色、Tools / Resources / Prompts 三种能力、stdio 与 HTTP 两种传输，并亲自动手写一个最小 MCP Server，最后把 MCP / A2A / ACP 三个协议放在一起讲清各自的定位。
