# 第14章 构建你自己的Agent框架

> **本章目标：** 把前面 13 章散落的能力抽象成一个 400 行左右、能跑通完整任务的 mini harness（九大模块），并掌握抽象设计的五个关键取舍——知道什么时候该抽象、什么时候是过度设计。
> **预计用时：** 6 小时　**前置章节：** 第05章（ReAct 最小 Agent Loop）、第07章（记忆与上下文工程）、第11章（多智能体协作）、第13章（部署成本与性能）　**配套代码：** `code/ch14_mini_harness.py`

## 0. 开篇：你已经在重复写同一段代码

把第 05 章到第 13 章的配套代码摊开，数一下同一个逻辑出现了几次：

| 逻辑 | 出现过的章节 | 次数 |
|---|---|---|
| Agent 主循环（模型 → 工具 → 回灌 → 再循环）| 05 / 06 / 09 / 11 / 12 | **5 次** |
| 工具注册与 schema 生成 | 04 / 05 / 09 / 11 | **4 次** |
| 消息裁剪 / 上下文预算 | 07 / 08 / 11 | **3 次** |
| trace 记录（每步的输入输出耗时）| 11 / 12 / 13 | **3 次** |
| 重试与超时包装 | 04 / 12 / 13 | **3 次** |

上周有个学员在模拟面试里，就被这张表背后的东西问住了：

> 面试官：「你这个 Agent 项目为什么不用 LangGraph？自己写循环，图什么？」
>
> 他：「我想把底层搞明白。」
>
> 面试官：「那你搞明白了吗——你的框架支持断点恢复吗？状态存在哪？并行任务的上下文怎么隔离？」
>
> 他：「这几个我还没做，但它能跑通一个完整任务。」
>
> 面试官追问：「所以你是判断过自己的需求不需要这些能力，还是不知道 LangGraph 解决的恰好就是这些？」

他答不上来。这类问题很常见：**自己写一份框架不难，说不清"为什么要写、写到哪一层"才致命。** 而你手上其实早有答案——一个真实症状：某位同学在 `ch11_multi_agent.py` 里修好了"工具参数校验失败时要把可用参数一并返回给模型"这个 bug，但他忘了 `ch09_skills.py` 里有一份几乎一样的工具执行代码。三周后他在 Skill 场景里又踩了同一个坑，排查了两小时才发现"这个 bug 我修过啊"。

**这就是"该抽一层了"的信号**：同一段代码在三个以上地方各有一份，且改动需要同步修改多处。本章要做两件事：把这五类重复逻辑（循环、注册、上下文、trace、重试）收敛到**一个**地方；把"什么时候该抽象、什么时候是过度设计"的判断标准交到你手里。

先说清楚目标：**你要造的不是"一个能替代 LangGraph 的框架"，而是一个你完全理解的小工具**。标准是"每一行都能解释为什么存在"，不是"功能多"。`code/ch14_mini_harness.py` 约 400 行，能跑一个带工具、带记忆、带预算、带权限门、能导出 trace 的完整任务。

### ⚠️ 常见坑

- **现象**：为了"以后能复用"，先花两周造框架，结果业务需求变了，框架白造。**原因**：抽象从想象的需求出发，而不是从**已经重复了三次**的代码出发。**怎么改**：规则是"**第三次**抄同一段代码时才抽象"（Rule of Three）；只出现一两次的逻辑留在原地。
- **现象**：框架造好了，但每个新任务都要改框架才能跑。**原因**：把业务逻辑写进了框架层（比如 `if task_type == "翻译"`）。**怎么改**：框架只提供机制（循环、注册、记录），业务只提供配置与函数；**框架里出现业务名词就是分层漏了**。

## 1. 为什么要自己造一个（而不是直接用 LangGraph）

先说反面：**大多数生产项目应该直接用成熟框架**。这一章让你自己造，有三个明确的理由。

**理由一：理解每个模块存在的理由。** 用过 LangGraph 的人常说不清"checkpointer 到底解决什么问题"、"为什么要有 state 而不是 messages"。自己写一遍之后，你会知道 checkpointer 的存在是因为**Agent 会在第 30 分钟崩溃**，而你不想重跑前 29 分钟（第 11 章的 Graph 模式讲的就是这件事）。抽象只有在你亲手感受到它解决的那个痛点之后，才真正属于你。

**理由二：框架的抽象一定会泄漏。** 三个具体例子：

| 泄漏现象 | 真实原因 | 你得自己补什么 |
|---|---|---|
| 想拿到"第 3 步调用了什么工具"，框架只给你最终答案 | 框架把中间状态封装了 | 自己挂 trace 回调，或读它的内部 state |
| 想给某个工具加"必须人工确认"，框架说工具调用是自动的 | 权限门不是它的核心抽象 | 在工具函数内部实现确认（第 12 章）|
| 想限制"每个任务最多 $0.05"，框架只支持 max_iterations | 预算是钱，框架按步数计 | 自己包一层成本统计与熔断（第 13 章）|

**理由三：你的需求比框架的通用能力窄得多。** 一个 8 步、3 个工具、单用户的内部助手，用不上图状态机、并行分支、检查点恢复。窄需求配窄实现，代码量差 10 倍、排查时间差 10 倍。

**那什么时候不该自己造？** 下面任一条成立，请直接用框架：

| 信号 | 为什么 |
|---|---|
| 需要**断点续跑**（任务跑 40 分钟，崩了要接着跑）| 检查点/持久化状态机是框架的强项，自己写要一周 |
| 需要**复杂的条件分支与并行**（DAG 形状的流程）| 状态图 + 可视化调试省下大量时间 |
| 团队 5 个人以上协作 | 统一抽象比"每个人一套"重要得多 |
| 需要**可观测性平台**（自动接入 tracing 后端）| 框架的生态集成已经做好了 |
| 你只是想尽快上线，不在意长期维护 | 时间成本优先 |

### ⚠️ 常见坑

- **现象**：造完框架的第一天就加上了"插件系统""多后端适配""YAML 定义流程"，代码 1500 行，自己都不想读。**原因**：**为想象中的需求抽象**。**怎么改**：每加一个抽象，先问"现在有哪个具体场景需要它"；答不上来就不加——**框架的代码量和它解决的问题数应该成正比**。
- **现象**：一直用框架，遇到"框架不支持"时改用 hack 绕过去（比如把确认逻辑塞进工具函数内部）。**原因**：没有判断"框架该不该换"的标准。**怎么改**：用上面的表格对照；如果连续两次因为同一个缺口绕路，就说明它和你的需求不匹配。

## 2. 框架的九个模块（每块都要能回答"没有它会怎样"）

**先讲没有它会出的问题，再讲它是什么。** 这是本章的核心方法——如果一个模块的存在理由你说不出一句"没有它就会出现 XX 现象"，那它就是过度设计。

| # | 模块 | 职责 | **没有它会怎样**（具体症状）|
|---|---|---|---|
| 1 | **LLM 客户端层** | 统一多服务商、重试、流式、用量统计 | 换模型的成本是改十几个文件；token 统计各写各的、对不上；重试逻辑抄了 3 份且行为不一致 |
| 2 | **Tool Registry** | 注册、schema 生成、执行、错误包装、权限标记、超时 | 加一个工具要改 4 处（函数、schema、分发、文档）；模型拿到的是 `KeyError` 而不是"参数 city 必填"；工具名写错直接 500 |
| 3 | **Agent Loop** | ReAct 主循环、停止条件、步数/成本预算 | 主循环在 5 个文件里各一份；"为什么停了"永远说不清（是输出了答案、还是步数用完了、还是报错了）|
| 4 | **Message / Context 管理** | 消息结构、裁剪、压缩、system prompt 组装 | 上下文越跑越长直到 400 报错；system prompt 各任务拼得不一样；压缩后数字/ID 丢了（第 07 章）|
| 5 | **Memory** | 短期（本轮）/ 会话（本次）/ 长期（跨会话）| 用户说"我不是说过我喜欢简洁吗"——每一轮都是从零开始；长期记忆写进上下文却没有任何约束（记忆投毒，第 07 章）|
| 6 | **Session 持久化** | 会话怎么存、怎么恢复、怎么重放 | 服务重启后所有人的对话丢失；用户刷新页面等于开新会话；出问题无法重放那一次对话 |
| 7 | **Trace / 可观测** | 每步记录、导出 | 线上失败只能看最终答案，中间 12 次调用全是黑盒（第 12 章）；成本归因不到步 |
| 8 | **Permission Gate** | 危险工具确认、白名单 | Agent 半夜自己删了目录、给客户发了邮件（第 12 章）|
| 9 | **Sub-agent** | 子任务隔离（独立上下文 + 独立预算）| 主 Agent 的上下文被检索资料撑爆；没法并行；子任务失败污染整个任务（第 11 章）|

**依赖方向（谁可以调用谁）**——这张图决定了代码会不会变成一团泥：

```text
        ┌──────────────────────────────────────────────┐
        │            Agent Loop（唯一的编排者）          │
        └───┬────────┬─────────┬──────────┬────────────┘
            ↓        ↓         ↓          ↓
      ┌────────┐ ┌────────┐ ┌────────┐ ┌──────────────┐
      │Context │ │  Tool  │ │Memory/ │ │  Permission  │
      │管理     │ │Registry│ │Session │ │   Gate       │
      └───┬────┘ └───┬────┘ └───┬────┘ └──────┬───────┘
          │          │          │             │
          └──────────┴────┬─────┴─────────────┘
                          ↓
                 ┌──────────────────┐
                 │ LLM 客户端层      │  ← 只有它知道是哪家服务商
                 └────────┬─────────┘
                          ↓
                 ┌──────────────────┐
                 │  Trace（横切所有层）│  ← 每一层都能写，但没人依赖它
                 └──────────────────┘
```

**三条铁律**：① **依赖只能向下**（Context 不调用 Tool Registry，Registry 不调用 Agent Loop）；② **LLM 客户端是唯一的服务商边界**，别的模块不许 import 任何 `openai` / `anthropic` 之类的包——这样换服务商只改一个文件；③ **Trace 是横切的观察者**，所有模块都可以往里写，但没有任何模块依赖它（否则日志出问题会拖垮主流程）。

最小接口设计（**接口窄、参数少、显式依赖**，每个都能一屏读完）：

```python
class LLMClient:                     # 1. 唯一的服务商边界
    def chat(self, messages, tools=None, **kw): ...
    def stream(self, messages, **kw): ...

class ToolRegistry:                  # 2. 注册 → schema → 执行，闭环
    def register(self, name, fn, schema, risk="low", timeout=10): ...
    def to_openai_schema(self): ...
    def execute(self, name, arguments): ...      # 统一错误包装＋超时＋权限

class ContextManager:                # 4. 只做两件事：装、裁
    def build(self, system, history, user_input): ...
    def maybe_compress(self, messages, budget_tokens): ...

class Session:                       # 6. 会话状态：内存 + 落盘
    def append(self, role, content): ...
    def save(self, path=None): ...
    @classmethod
    def load(cls, path): ...

class PermissionGate:                # 8. 复用第 12 章的实现
    def check(self, name, arguments): ...

class Budget:                        # 3. 每步检查，超限立刻停
    def spend(self, usage, step): ...
    def exceeded(self): ...
```

### ⚠️ 常见坑

- **现象**：写着写着，`ContextManager` 里出现了"如果工具名是搜索就多留点历史"这类判断。**原因**：模块边界被业务逻辑污染。**怎么改**：模块只接受参数（`budget_tokens`、`protect_patterns`），不接受业务名词；需要区分行为就**传参数进来**，不要在模块里 `if tool_name == ...`。
- **现象**：Trace 的写入失败（磁盘满）导致整个任务崩溃。**原因**：观察者变成了依赖。**怎么改**：Trace 的所有写入都 `try/except` 吞掉异常并降级为打印——**日志系统不能成为单点故障**。
- **现象**：Memory 模块直接读环境变量、直接连数据库，换环境就要改代码。**怎么改**：把外部依赖通过构造函数注入（`Memory(store=...)`），模块内不出现 `os.environ` / 全局连接。

## 3. 抽象设计的关键取舍（本章最有价值的部分）

前面是"造什么"，这一节是"怎么判断"。这五个取舍，值一年的踩坑经验。

### 3.1 什么时候该抽象，什么时候是过度设计

**判断标准只有一条：抽象之后的代码，是不是比抽象之前更容易改。** 用三个具体测试：

| 测试 | 通过 | 不通过（过度设计）|
|---|---|---|
| **三次法则**：同一段逻辑出现过几次？| ≥3 次，且每次都在改同一处 | 1~2 次，只是"看起来以后可能复用" |
| **改动测试**：换个需求要改几个文件？| 从 5 个文件改成 1 个 | 从 1 个文件变成 3 个文件（多了间接层）|
| **解释测试**：能一句话说清它做什么吗？| "把工具调用统一成带超时和错误包装的一次调用" | "这是一个可插拔的工具执行策略工厂"（说不清）|

**反例（三行代码的抽象不如不抽象）**：

```python
# ❌ 抽象前：清楚、直白，一眼看懂
total = sum(item["price"] for item in items)
# ❌ 抽象后：多了一层，没有任何收益
class PriceAggregator:
    def __init__(self, strategy=None):
        self.strategy = strategy or DefaultSumStrategy()
    def aggregate(self, items): return self.strategy.run(items)
```

```python
# ✅ 值得抽象：三处重复 + 每处都要改同一件事
def execute_with_guard(registry, name, arguments):     # 只在框架里写一次
    if not registry.has(name):
        return {"ok": False, "error": "没有名为 %s 的工具，可用：%s" % (name, registry.names())}
    if not gate.check(name, arguments)[0]:
        return {"ok": False, "error": "用户拒绝执行"}
    return registry.execute(name, arguments)           # ← 超时/错误包装都在里面
```

### 3.2 接口该窄还是宽

| | 窄接口 | 宽接口 |
|---|---|---|
| 例 | `chat(messages, tools=None)` | `run(prompt, tools, memory, trace, budget, gate, retry, model, ...)` |
| 优点 | 好组合、好测试、依赖清晰 | 调用方少写代码，一个函数搞定 |
| 缺点 | 调用方要自己拼装（多写几行）| **参数 10+ 个，没人记得住顺序；加一个参数就破坏所有调用** |
| 建议 | 内部模块之间**一律用窄接口** | 最外层入口可以用宽接口，但**参数必须收进配置对象** |

```python
class AgentConfig:
    """宽接口的正确形态：一个配置对象，加字段不破坏调用方。"""
    def __init__(self, model=None, max_steps=8, max_cost_usd=0.5, temperature=0.0,
                 system=None, tools=None, compress_at_tokens=6000):
        self.model, self.max_steps, self.max_cost_usd = model, max_steps, max_cost_usd
        self.temperature, self.system, self.tools = temperature, system, tools
        self.compress_at_tokens = compress_at_tokens

agent = Agent(config=AgentConfig(max_steps=6))     # 加新配置项不影响已有调用
```

**经验法则**：函数参数超过 **4 个**就该考虑收进配置对象；模块之间的依赖用**构造注入**而不是方法参数（`Agent(llm, registry, gate)` 而不是 `agent.run(..., llm=..., registry=...)`）。

### 3.3 配置 vs 代码：什么该写成配置

**判断标准：这个变化是"数据变化"还是"控制流变化"？** 数据变化可以配置化，控制流必须写代码。

| 该做成配置 | 必须写代码 |
|---|---|
| 模型名、温度、`max_steps`、预算上限 | "如果工具返回为空就换一个工具重试"（这是控制流）|
| system prompt 文案、工具白名单 | "检索结果少于 3 条时降级到联网搜索" |
| 超时时间、重试次数、缓存 TTL | 任何 `if/else` 分支、循环、异常处理 |
| 工具列表（哪个任务开哪些工具）| 自定义的解析、校验、格式化逻辑 |

**为什么不能把控制流配置化？** 因为你最终会造出一门编程语言，而且是很难调试的那种——用 YAML 写的 `if` 既没有类型检查、也没有堆栈信息，出错时你只能看到"第 42 行配置无效"。**配置描述"用什么"，代码描述"怎么做"**；一旦发现配置里出现了"当…时…否则…"，就该停手了。

一个反例（真实见过）：有人把"先检索再总结，如果检索为空就只总结问题本身"写成了 YAML 的 `steps` 列表加 `on_empty` 字段，结果排查一个分支问题花了半天。**这三行代码写成 `if` 是 30 秒的事。**

### 3.4 同步 vs 异步：什么时候必须上 async

**先说不该上的**：纯串行、单用户、没有并发的场景，用同步代码更简单也更好调试——`async` 会污染整条调用链（一个函数变 `async`，它的所有调用者都得变）。

**必须上 async 的三种情况**：

1. **要并行做多件独立的事**：3 个独立工具各 2 秒，串行 6 秒，`asyncio.gather` 后 2 秒——**这是 Agent 里最常见的收益**（第 11 章的并行子 Agent 也靠它）；
2. **要同时处理多个用户请求**（Web 服务）：同步框架下每个请求占一个线程，几十个并发就打满；
3. **流式 + 其他工作并行**（边推状态边执行下一步）。

```python
# 并行工具调用：3 个独立查询，2 秒而不是 6 秒
import asyncio

async def run_tools_parallel(tool_calls, registry):
    tasks = [asyncio.create_task(registry.execute_async(c["name"], c["arguments"]))
             for c in tool_calls]
    return await asyncio.gather(*tasks, return_exceptions=True)   # 一个失败不拖垮全部
```

**最大的坑：把同步的 SDK 调用放进 async 函数里。** `async def chat(): return client.chat(...)` 里的同步 HTTP 调用会**阻塞整个事件循环**——其他并发请求全部排队，你以为并发度提高了，实际吞吐反而下降。要么用服务商提供的 async 客户端（`AsyncOpenAI`、`httpx.AsyncClient`），要么用 `await asyncio.to_thread(client.chat, ...)` 把它挪到线程池。

**工程建议**：核心逻辑（Loop、Registry、Context）写成**同步**的，把并发留在最外层（Web 层或多任务调度层）。这样 90% 的代码好调试，需要并发时包一层即可。

### 3.5 状态放在哪：全局单例是万恶之源

```python
# ❌ 全局单例：两个请求互相覆盖，且测不出来
_CURRENT_SESSION = {}
_CURRENT_TRACE = None

def handle(user_input):
    _CURRENT_SESSION["history"].append(user_input)     # 另一个用户的对话也在这里
    ...
```

```python
# ✅ 每个 Agent 实例持有自己的状态，构造时注入
class Agent:
    def __init__(self, llm, registry, gate, session=None, trace=None, config=None):
        self.llm, self.registry, self.gate = llm, registry, gate
        self.session = session or Session()            # ← 状态属于实例
        self.trace = trace or Trace("agent")
        self.config = config or AgentConfig()
```

三个真实事故，都来自全局状态：

| 事故 | 现场 | 原因 |
|---|---|---|
| 用户 A 看到用户 B 的答案 | 两个请求都往同一个 `_CURRENT_SESSION` 里写 | 会话状态是全局的 |
| 单元测试互相污染 | 单独跑通过，一起跑就失败 | 测试共享了全局的 registry / trace |
| 并发下 trace 串行错乱 | 一次 run 的 trace 里混进了另一条的步骤 | trace 是全局的，`step` 计数互相覆盖 |

**判断方法**：如果你在模块里看到 `global`、模块级可变变量（`SESSION = {}`）、或者"先 reset 再 run"的写法，那就有状态放错了地方。**状态应该在实例里，随实例的生命周期生灭**；确实需要跨实例共享的东西（配置、连接池、注册表）应当是**只读或线程安全**的。

### ⚠️ 常见坑

- **现象**：为了"灵活"把工具列表、模型、步数全做成 YAML 配置，结果改一个流程要写三层配置加一次代码改动。**怎么改**：用 3.3 的表格自检——**配置里出现条件分支就是信号**。
- **现象**：一个函数改成 `async` 之后，半个项目都变成了 `async`，测试也要用 `pytest-asyncio`。**怎么改**：只在最外层上 async（3.4 节）；核心逻辑保持同步，用 `run_in_executor` / `to_thread` 包一层。
- **现象**：框架跑得好好的，加了一个"并行执行子任务"的功能后开始随机出错、结果串台。**原因**：并行共享了可变状态（同一个 `Session` / `Trace` 实例）。**怎么改**：**并行任务必须各自持有独立的状态对象**（第 11 章的上下文隔离，在框架层体现为"每个子 Agent 一个 session"）。

## 4. 逐步构建：四个阶段，每阶段都能跑

**不要一次写完 400 行。** 分成四个阶段，每个阶段结束时脚本都能跑通一个完整任务——这样出问题时你知道是刚加的哪一层引起的。

| 阶段 | 加什么 | 累计代码量 | 新解决什么问题 | 怎么验证 |
|---|---|---|---|---|
| **S1** | Agent Loop 类化 | ~60 行 | 主循环从 5 处收敛到 1 处；停止原因显式化 | 跑一个 2 步任务，打印 `stop_reason` |
| **S2** | Tool Registry + Trace | ~160 行 | 加工具只改一行；每步有记录可复盘 | 加一个工具，确认没改 Loop |
| **S3** | Context 管理 + Budget | ~260 行 | 上下文不再无限增长；成本有上限 | 造一个长对话，看它压缩；把预算调小看它熔断 |
| **S4** | Permission Gate + Session + Sub-agent | ~400 行 | 危险动作有人把关；会话可恢复；子任务隔离 | 拒绝一次危险动作；重启进程后恢复会话 |

**S1：把循环变成一个类**（关键是让"为什么停"变成返回值，而不是靠猜）：

```python
class StopReason:                      # 停止原因必须是枚举，不是字符串魔法
    FINISH = "finish"                  # 模型给出最终答案（唯一正常出口）
    MAX_STEPS = "max_steps"            # 步数上限
    BUDGET = "budget"                  # 成本超限
    REPEAT = "repeat_action"           # 同一动作重复（无进展）
    ERROR = "error"

class Agent:
    def run(self, user_input):
        for step in range(1, self.config.max_steps + 1):
            messages = self.context.build(self.system, self.session.history, user_input)
            reply = self.llm.chat(messages, tools=self.registry.to_openai_schema())
            self.trace.log("llm_call", step=step, usage=reply.get("usage"), **reply)
            if reply.get("tool_calls"):
                self._dispatch(reply, step)
                continue
            return {"answer": reply["content"], "stop_reason": StopReason.FINISH, "steps": step}
        return {"answer": None, "stop_reason": StopReason.MAX_STEPS, "steps": self.config.max_steps}
```

**S2 的 Registry 关键在"执行"这一个方法**——所有超时、错误包装、权限标记都在这里，模型看到的是人话：

```python
    def execute(self, name, arguments):
        tool = self._tools.get(name)
        if tool is None:
            return {"ok": False, "error": "没有名为 %s 的工具。可用工具：%s"
                    % (name, ", ".join(sorted(self._tools)))}
        try:
            data = tool.fn(**arguments)                 # 参数校验交给签名与 schema
        except TypeError as exc:                        # 缺参数/多参数
            return {"ok": False, "error": "参数不合法：%s。该工具的必填参数：%s"
                    % (exc, tool.required)}
        except Exception as exc:
            return {"ok": False, "error": "%s: %s（可尝试其他方式）" % (type(exc).__name__, exc)}
        return {"ok": True, "data": data}
```

**S3 的 Context 只做两件事**（`build` 与 `maybe_compress`），压缩时**保护约束类消息**（第 07 章：用户偏好、规则、关键实体）。Budget 在**每一步之前**检查，而不是在入口检查一次：

```python
class Budget:
    def __init__(self, max_cost_usd=0.5):
        self.max_cost_usd, self.spent = max_cost_usd, 0.0
    def spend(self, usage):
        self.spent += estimate_cost(usage.get("prompt_tokens", 0),
                                    usage.get("completion_tokens", 0))
        return self.spent
    def exceeded(self):
        return self.spent >= self.max_cost_usd
```

**S4 的 Session 与 Sub-agent**：Session 落盘成 JSONL（每行一条消息，追加写，崩溃不丢），Sub-agent 用**同一个类**新实例化，只是注入**独立的 Session、Trace、Budget**——这就是第 11 章"上下文隔离"在框架层的实现，一共不到 20 行：

```python
def spawn_subagent(parent, task, max_steps=4, max_cost_usd=0.1):
    """子 Agent = 同一个 Agent 类 + 独立的状态对象（复用第 11 章的隔离思路）。"""
    return Agent(llm=parent.llm, registry=parent.registry, gate=parent.gate,
                 session=Session(), trace=Trace("sub", parent_id=parent.trace.run_id),
                 config=AgentConfig(max_steps=max_steps, max_cost_usd=max_cost_usd))
```

### ⚠️ 常见坑

- **现象**：想一次把九个模块都写上，写到 200 行时已经跑不通了，也不知道哪里错了。**怎么改**：按 S1→S4 递增，**每阶段跑一次**；任何阶段跑不通就不进入下一阶段。
- **现象**：加了 Registry 之后反而更啰嗦（原来 `TOOLS[name](args)` 一行，现在要 `registry.execute(...)` 一行）。**原因**：抽象只有在"统一处理错误/超时/权限/记录"时才有收益，如果这些你都不需要，那就**不该抽象**（回到 3.1）。**怎么改**：确认你真的需要那四项统一处理，否则删掉这层。
- **现象**：子 Agent 复用父 Agent 的 `Budget`，结果一个子任务把预算吃光。**怎么改**：子 Agent 有独立预算，同时父级要能汇总（`parent.budget.spend(sub.budget.spent)`），否则总额失控。

## 5. 框架的"最后一公里"

功能跑通了不等于好用。最后这一公里是区分"能跑的 demo"和"能维护的工具"的地方。

### 5.1 错误信息要能指导行动

**错误信息的三个要素：发生了什么 + 你传了什么 + 下一步该怎么做。** 而且——**给模型的错误信息要给"可用选项"**，因为模型看不到你的代码。

```text
❌ 给模型：ToolError: invalid arguments
❌ 给人看：KeyError: 'city'

✅ 给模型：
   工具 get_weather 参数校验失败：缺少必填参数 'city'。
   必填：city（城市中文名，如"杭州"）、unit（枚举：c/f，默认 c）。
   你传的是：{'unit': 'c'}。
   建议：如果不知道城市，先调用 get_location() 拿到城市名再重试。

✅ 给人看（trace 里）：
   step 3 工具调用失败 | get_weather | 缺参数 city | 建议：先调 get_location
```

实测差别很大：把工具错误信息从 `KeyError: 'city'` 改成上面那段之后，模型在**下一轮自己改对**的比例从约 40% 提到 80% 以上——**这不是模型变聪明了，是你终于把话说明白了。**

### 5.2 调试开关

三个开关，成本极低但省下大量时间：

| 开关 | 行为 | 什么时候用 |
|---|---|---|
| `AGENT_DEBUG=1` | 每步打印：步号、messages 摘要与长度、模型输出前 200 字、工具名与参数、耗时 | 本地调试 |
| `AGENT_TRACE=<path>` | 落盘完整 trace（第 12 章的 JSONL 格式）| 复盘线上失败 |
| `AGENT_DRY_RUN=1` | 工具**只返回模拟结果**，不产生任何副作用（`"DRY-RUN: 将执行 send_email(to='a@b.com', subject='报销')"`）| 开发期、评测、演示 |

**`dry-run` 是本章最被低估的一个开关**：它让你能安全地跑通全流程（包括危险动作），不担心"调试时真的发了一封邮件"。实现只需在 `execute` 里加三行：

```python
if os.environ.get("AGENT_DRY_RUN") == "1":
    return {"ok": True, "data": "DRY-RUN: 将执行 %s(%s)" % (name, arguments), "dry_run": True}
```

### ⚠️ 常见坑

- **现象**：报错信息是 `Exception: error`，排查靠猜。**怎么改**：所有 `raise` / `return error` 的地方都按"三要素"写；**写错误信息的时间，永远少于排查它的时间**。
- **现象**：`dry-run` 模式下工具返回假数据，模型的后续推理因此跑偏，测试不出真实效果。**怎么改**：假数据要**仿真**（`get_weather` 返回一个合理的天气，而不是 `"mock"`）；或者用录制好的真实响应回放。
- **现象**：调试开关写成了全局变量，并发时互相影响。**怎么改**：开关从**环境变量读进配置对象**（`AgentConfig(debug=...)`），不要写模块级全局变量（回到 3.5）。

## 6. 对比真实框架：LangGraph 与 OpenAI Agents SDK

自己造完之后，看真实框架的抽象会更清楚。这张表的用法是：**当你的 mini 版开始缺右边的能力时，就该考虑迁移。**

| 维度 | 你的 mini harness（~400 行）| LangGraph | OpenAI Agents SDK |
|---|---|---|---|
| **核心抽象** | Agent（循环 + 工具 + 上下文）| 状态图：节点 = 步骤，边 = 条件 | Agent + Handoff（转交）+ Guardrail |
| **状态** | 显式存在 `Session` 里，自己管 | 统一 state 对象，图执行为它负责 | 交给运行上下文（context）|
| **持久化 / 断点续跑** | ❌ 只有 JSONL 会话，**不能从第 5 步恢复** | ✅ checkpointer，天然可恢复（最大的优势）| 部分（会话级）|
| **并行与分支** | ❌ 手工 `spawn_subagent` | ✅ 图上的分支与并行节点 | ✅ handoff 与并行 tool calls |
| **人工确认** | ✅ 自己写的 `PermissionGate`（完全可控）| 需自己接 interrupt 机制 | ✅ 内置 tool approval 流程 |
| **可观测** | ✅ 自己的 JSONL trace（够用但不通用）| ✅ 可接主流 tracing 后端 + 图可视化 | ✅ 内置 tracing，能看每一步 |
| **学习曲线** | 你写的，你最懂 | 高（图、state、reducer 概念多）| 中（概念少，但受实现约束）|
| **适合谁** | 单用户/小团队、流程简单、想完全掌控 | 长任务、需要恢复、复杂分支、多人协作 | 快速搭多 Agent 交互、需要内置 guardrail |

**三个真实的取舍差异**（这就是"框架的抽象泄漏"）：① **可恢复性不是免费的**——LangGraph 的 checkpointer 要求你把所有状态放进它管理的 state 里，于是**你不能随意用闭包、全局缓存或本地变量**存东西；自己造时随意，但崩了就得从头跑。② **人工确认的位置不同**——框架通常把确认放在"工具层或运行层"，而第 12 章的做法（展示完整参数 + 风险评估）需要你自己接进去。③ **成本控制通常不是框架的核心**——它们更关心"步数/迭代次数"，钱要靠你自己统计（第 13 章）。

**迁移的判断标准**（出现任一条就迁移，不要提前）：任务需要**从中间恢复**（跑 30 分钟以上）；流程出现**两个以上的条件分支且要可视化**；**三人以上**协作开发；需要接公司统一的**可观测性平台**。

### ⚠️ 常见坑

- **现象**：把 mini harness 硬改成"支持任意流程"的小型框架，最后写出了一个更难用的 LangGraph。**怎么改**：**框架的边界要跟着真实需求长**（回到 3.1 的三次法则）；需要通用能力时就迁移到成熟框架，不要重复造它的坑。
- **现象**：迁移到框架后，原有的权限门和成本统计失效了。**怎么改**：迁移前列一张"我依赖的四个能力"清单（权限门、成本熔断、trace 格式、缓存），逐项确认框架怎么支持；**先跑评测集对比，再切换**（第 12 章）。

## 7. 配套代码走读：`code/ch14_mini_harness.py`

```bash
AGENT_MOCK=1 python code/ch14_mini_harness.py
```

约 400 行，模块与第 2 节的九块一一对应：

| 行数区间 | 内容 |
|---|---|
| `LLMClient` | 统一 chat / stream / 用量统计，mock 模式下返回确定性假响应（不联网、不需要 Key）|
| `Tool` / `ToolRegistry` | 装饰器与显式两种注册方式、schema 生成、`execute` 的错误包装 + 超时 + 权限检查 |
| `ContextManager` | `build`（system + 历史 + 当前输入）与 `maybe_compress`（保护约束类消息）|
| `Memory` / `Session` | 三层记忆的最小实现；会话落盘 JSONL、`load` 可恢复 |
| `Budget` / `PermissionGate` | 每步成本检查 + 三级预算；危险动作确认门（复用第 12 章）|
| `Agent` | Loop、停止原因枚举、`spawn_subagent`、`dry_run` |
| `Trace` | 每步事件 + 导出 `code/traces/ch14_harness.json` |
| `main()` | 跑一个完整任务（多步 + 工具 + 一次被拒绝的危险动作），打印摘要并导出 trace |

一次示例运行（mock）：

```text
==================== mini harness 运行摘要 ====================
任务：查一下杭州明天天气，如果是雨天就给我的邮箱发一封提醒
步骤 1  llm_call   0.4s  → 调用 get_weather(city='杭州')
步骤 2  tool_call  0.1s  → ok: 明天中雨，18~24℃
步骤 3  llm_call   0.5s  → 请求调用 send_email(to='me@example.com', ...)
步骤 4  gate       ×     → 高风险动作：展示完整参数 → 用户拒绝
步骤 5  llm_call   0.4s  → 改为把提醒内容直接输出给用户
结果：stop_reason=finish  steps=5  cost=$0.0186  预算使用 3.7%
Trace: code/traces/ch14_harness.json（12 个事件，失败可复盘）
==============================================================
```

**看这份摘要要注意三件事**：① **`stop_reason=finish` 是唯一正常出口**——如果打印的是 `max_steps` 或 `budget`，说明任务没完成，要看 trace 找原因；② **第 4 步的拒绝没有让任务失败**——权限门拒绝后，Loop 把"用户拒绝"作为一条观察结果回灌给模型，它自己换了方案，**这是"拒绝"应该有的行为**；③ **12 个事件能完整复现这次运行**——满足第 12 章的判断标准"只看 trace 就能复现一次失败"。

### ⚠️ 常见坑

- **现象**：读到 400 行代码觉得"太长"，于是删掉 trace 和错误包装。**怎么改**：先删**抽象**而不是删能力——比如 `ContextManager` 只有一个 `build` 时可以直接合并进 `Agent`；**但 trace、超时、错误包装属于能力，删了会在线上以更贵的方式还回来**。
- **现象**：框架跑通了，但每个新任务都要复制 `main()` 改一遍。**怎么改**：任务只应该由"配置 + 几个工具函数"定义；如果新任务要改框架代码，说明分层还没做对（回到 3.3 的配置 vs 代码）。

## 本章小结

1. **该抽象的时机是"第三次抄同一段代码"**（Rule of Three），不是"以后可能会复用"。第 05~13 章里主循环抄了 5 次、工具注册抄了 4 次——这就是信号。
2. **自己造框架的三个理由**：理解每个模块存在的理由（比如 checkpointer 对应"崩了不想重跑 30 分钟"）、框架的抽象一定会泄漏、你的需求比通用框架窄得多。**同时要知道什么时候该直接用框架**（需要断点续跑、复杂分支、多人协作、接统一可观测平台）。
3. **九个模块，每一块都要能回答"没有它会怎样"**：LLM 客户端层、Tool Registry、Agent Loop、Context 管理、Memory、Session 持久化、Trace、Permission Gate、Sub-agent。答不出来的模块就是过度设计。
4. **三条架构铁律**：依赖只能向下、LLM 客户端是唯一的服务商边界、Trace 是横切观察者且不能被依赖（日志系统不能成为单点故障）。
5. **抽象设计的五个取舍**：① 三次法则 + 改动测试 + 解释测试；② 模块间用窄接口，最外层入口用配置对象（参数 >4 个就该收进 `AgentConfig`）；③ 配置描述"用什么"、代码描述"怎么做"——**配置里出现 if/else 就该停手**；④ 只在"并行、多用户、流式并行"时上 async，核心逻辑保持同步；⑤ **状态放在实例里**，全局单例是并发事故、测试污染、trace 串台的共同来源。
6. **分四阶段构建，每阶段都能跑**：S1 Loop 类化（显式 `stop_reason`）→ S2 Registry + Trace → S3 Context + Budget → S4 Permission + Session + Sub-agent。子 Agent = 同一个类 + 独立的状态对象（第 11 章隔离思路的框架化）。
7. **最后一公里决定它好不好用**：错误信息三要素（发生了什么 + 传了什么 + 下一步怎么做），**给模型的错误要带"可用选项"**——实测能让模型下一轮自己改对的比例从 40% 提到 80%；三个开关（`AGENT_DEBUG` / `AGENT_TRACE` / `AGENT_DRY_RUN`），其中 dry-run 让你能安全跑通危险动作。
8. **迁移到真实框架的判断标准是"缺什么"**：需要从中间恢复、两个以上条件分支、三人以上协作、接公司可观测平台——出现任一条再迁移，**不要提前**；迁移前先列"我依赖的能力清单"并跑评测集对比。
9. **关联阅读**：[[02-Wiki/专题总结/01-Agent是什么]]、[[02-Wiki/专题总结/05-记忆与上下文工程]]。

## 动手练习

**练习 1（做一次"删抽象"实验）**：把 `ch14_mini_harness.py` 里的 `ContextManager` 合并回 `Agent`（删掉这一层），跑一遍确认功能不变；再加回一个"每次 build 都要记 trace"的需求，看看合并后的代码要改几处。
*目标：亲手体验"抽象的价值来自它统一处理的那件事"——没有统一处理需求时，这一层就是纯成本。*

**练习 2（给框架加一个"无进展熔断"）**：现在的停止条件是 `max_steps` / `budget` / 用户拒绝。加一个新的 `StopReason.NO_PROGRESS`：当连续两次工具调用的 `(name, arguments)` 相同时，立刻停止并在 trace 里记录。然后用一个会重复调同一工具的任务验证它。
*目标：把第 12 章"反复调同一个工具"这条失败模式，变成框架层的一道保险。*

**练习 3（把框架的一个能力换成真实实现）**：选一个模块做真实版——推荐 `LLMClient`（接真实服务商，用第 00 章的 `common/llm.py`）或 `Session`（从 JSONL 换成 SQLite/Redis）。要求：**只改这一个文件**，其余代码一行不动。改完在线跑一次完整任务，对比 mock 与真实的两份 trace。
*目标：验证你的分层是否真的成立——**如果改一个模块需要动别处，说明边界划错了**。*

## 自测题

**1. 什么时候该抽象、什么时候是过度设计？给出三个可操作的测试。**

<details><summary>点击查看答案</summary>

三个测试：① **三次法则**——同一段逻辑出现过 ≥3 次且每次都在改同一处，才值得抽象；只出现 1~2 次、只是"以后可能复用"的，不抽。② **改动测试**——抽象后"换一个需求要改几个文件"应当**变少**；如果从 1 个文件变成 3 个文件（多了间接层），就是过度设计。③ **解释测试**——能用一句话说清它做什么（"把工具调用统一成带超时和错误包装的一次调用"）；说不清（"这是一个可插拔的工具执行策略工厂"）就是过度设计。

配套原则：**先删抽象再删能力**——`ContextManager` 只有一个 `build` 时可以合并回 `Agent`，但 trace、超时、错误包装属于能力，删了会在线上以更贵的方式还回来。

</details>

**2. 九个模块分别解决什么问题？为什么"没有它会怎样"是判断模块该不该存在的标准？**

<details><summary>点击查看答案</summary>

九个模块与它们解决的问题：**LLM 客户端层**（换服务商只改一处、统一用量统计与重试）、**Tool Registry**（加工具只改一行、统一 schema/错误包装/超时/权限）、**Agent Loop**（循环收敛到一处、停止原因显式）、**Context 管理**（上下文不无限增长、压缩不丢关键实体）、**Memory**（跨轮次记住用户，且写入有约束防投毒）、**Session 持久化**（重启不丢会话、可恢复、可重放）、**Trace**（失败可复盘、成本可归因到步）、**Permission Gate**（危险动作有人把关）、**Sub-agent**（上下文隔离 + 独立预算 + 可并行）。

用"没有它会怎样"作为标准，是因为**抽象的唯一正当理由是消除一个真实存在的痛点**。说不出现象（比如"没有它会导致 XX 报错/事故"），说明这个模块是为想象中的需求服务的——那就是过度设计，应当删掉。

</details>

**3. 接口该窄还是宽？"参数超过 4 个就收进配置对象"解决的是什么问题？**

<details><summary>点击查看答案</summary>

**模块之间一律用窄接口**（如 `chat(messages, tools=None)`）：好组合、好测试、依赖清晰；缺点是调用方要自己拼装。**最外层入口可以用宽接口**（一个函数干完所有事、上手快），但宽接口的问题是**参数 10+ 个没人记得住顺序，加一个参数就破坏所有调用方**。

解法是把宽接口的参数收进**配置对象**（`AgentConfig`）：加字段不破坏已有调用，且配置能集中做校验和默认值，还能整体传给子 Agent。配套原则：模块之间的依赖用**构造注入**（`Agent(llm, registry, gate)`），而不是把它们塞进方法参数（`agent.run(..., llm=..., registry=...)`）。

</details>

**4. 为什么"把流程写成配置"通常是错的？举一个反例。**

<details><summary>点击查看答案</summary>

因为**配置描述"用什么"，代码描述"怎么做"**。判断标准是：这个变化是**数据变化**还是**控制流变化**——模型名、温度、`max_steps`、超时、工具白名单属于数据，可以配置化；"如果工具返回为空就换一个工具重试""检索少于 3 条就降级到联网搜索"属于控制流，必须写代码。

**反例**：有人把"先检索再总结，如果检索为空就只总结问题本身"写成了 YAML 的 `steps` 列表加 `on_empty` 字段。结果排查一个分支问题花了半天——因为 YAML 写的 `if` 没有类型检查、没有堆栈信息，出错只能看到"第 42 行配置无效"。而这写成 `if` 是 30 秒的事。

**信号**：一旦配置里出现"当…时…否则…"，就说明你在造一门没有调试器的编程语言。

</details>

**5. 为什么"状态放在实例里"这么重要？全局状态会导致哪些具体事故？**

<details><summary>点击查看答案</summary>

全局状态（模块级可变变量、`global`、"先 reset 再 run"）会让**并发实例互写**，而且这类 bug 在单线程测试里几乎不出现。三个具体事故：① **用户 A 看到用户 B 的答案**——两个请求都往同一个 `_CURRENT_SESSION` 里写；② **单元测试互相污染**——单独跑通过、一起跑失败，因为共享了全局 registry / trace；③ **并发下 trace 串台**——两条 run 的 `step` 计数互相覆盖，trace 里混进了别的一次运行的事件，线上复盘直接失效。

正确做法：状态属于实例，随实例生命周期生灭，构造时注入（`Agent(llm, registry, session, trace, config)`）；确实需要共享的东西（配置、连接池、注册表）应当是**只读或线程安全**的。并行任务必须各自持有独立的状态对象——这就是第 11 章"上下文隔离"在框架层的落地。

</details>

## 结语与下一章

造框架和盖房子是一回事：你不会因为"以后也许要加两层"就把地基挖到十米深，但你一定会在地基里留好承重的位置。**抽象的价值不在于它多通用，而在于它的每一块都对应着一个你说得出来的痛点**——说不出"没有它会怎样"的模块，就是白挖的那十米。这一章真正的产出不是那 400 行代码，而是你以后看任何框架时，都能指着它的每个模块说出它替谁挡了哪一刀。

但这套东西现在还是一个"你完全理解的小工具"，不是"别人能用的东西"：它没有需求边界、没有评估、没有失败记录，也还没有一个能拿出去演示的完成品。下一章是第 15 章 [[docs/第15章 综合实战]]，也是阶段五的开始：用你亲手造的这套东西，从零交付三个可以拿出去给人看的项目——**网页研究助手**（多步检索 + 引用 + 报告）、**文档问答系统**（切片实验 + 混合检索 + 拒答）、**代码审查助手**（读 diff + 定位 + 给可执行的修改建议）。每个项目都会给出需求拆解、技术选型、关键实现，以及"怎么衡量它做好了"的验收标准——你会第一次体验"从需求到上线"的完整工程流程，而不只是跑通一个 demo。
