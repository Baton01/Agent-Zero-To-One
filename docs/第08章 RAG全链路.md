# 第08章 RAG全链路

> **本章目标：** 打通检索增强生成（RAG）的完整链路——加载 → 清洗 → 切片 → 向量化 → 检索 → 融合 → 重排 → 带引用回答 → 评估，每一环都知道"为什么这样选"和"怎么判断好坏"。

## 0. 开篇：一个真实的问题

第 07 章的助手终于记得住用户了，有个读者趁热把它接上公司内部文档，做成问答入口挂在 OA 里。上线第三天，财务的同事截图找过来：

> 财务：这个 AI 说我们出差住宿报销上限是"一线城市每晚 500～800 元"，哪份文件里写的？
> 读者：模型答的，我们只是把内部文档都接进去了……
> 财务：那它这句话是从哪份文件、哪一页看来的？我要出处。
> 读者：（翻了半天，员工手册、差旅制度、产品 FAQ 里都没有这句话。差旅制度里写的是：海外差旅单晚不超过等值 8000 日元，国内一线城市 600 元、其他城市 400 元。）
> 我：它不知道这个数字，也没检索到，于是编了一个"听起来对"的。

这不是模型不够强，而是**你的私有文档从来不在它的知识里**，而它又不会说"我不知道"。

**先排除两个错误方案：** ① **把文档拼进 system prompt**——员工手册 + 产品文档 + 接口文档可能 30 万字（≈ 45 万 token）：每次提问都付费、随时超窗口、关键段落还会淹没在中间（第 07 章的 U 形曲线），文档到 300 万字时彻底不可行；② **微调（Fine-tuning）让它记住**——微调擅长学**风格、格式、判断方式**，不擅长**记事实**；制度每年改一次就要重训一次，成本高、周期长，还说不清"这个答案是哪来的"。

**RAG（Retrieval-Augmented Generation，检索增强生成）** 走的是第三条路：**不改模型，改上下文。** 提问时先去你的文档里捞出相关片段，把片段和问题一起交给模型，并让它**标注答案来自哪一段**。文档更新只需重建索引。

本章要回答：切片怎么切才不丢信息？没有 embedding API 能不能检索？Top-K 怎么定？为什么需要重排？怎么让答案带可核验的引用？以及最重要的一条——**怎么知道你的 RAG 到底做得好不好**。配套代码 `code/ch08_rag.py` 内置 3 篇示例文档，离线就能跑完整链路。配合这两篇一起看：[[02-Wiki/专题总结/04-RAG全链路]]、[[02-Wiki/面试题库/02-RAG高频面试题]]。

## 1. RAG 的完整链路

RAG 分两阶段：**索引阶段（离线，文档变了才跑）** 和 **查询阶段（在线，每次提问都跑）**。很多人只做了中间几步，就以为 RAG 做完了。

```
【索引阶段 · 离线 · 文档变更时执行】
① 加载 Load      读入 md / txt / pdf                      → 原始文档
② 清洗 Clean     去页眉页脚、广告、多余空行、统一标点        → 干净文本
③ 切片 Chunk     按标题/段落切，再用长度兜底                → chunk 列表 + 元数据
④ 向量化 Embed   TF-IDF / embedding 模型（两条路本章都写）   → 向量矩阵
⑤ 存储 Store     JSON + npy 文件 / 向量数据库               → 可检索索引
【查询阶段 · 在线 · 每次提问】
⑥ 查询改写 Rewrite  口语化问题 → 检索友好的关键词/多路查询
⑦ 召回 Retrieve     向量 top-20 + BM25 top-20              → 候选 40 条
⑧ 融合 Fuse         RRF 合并两路排名                        → 候选 20 条
⑨ 重排 Rerank       cross-encoder / 词面重排                → top 4
⑩ 组装 Assemble    编号 + 来源标题，写进 prompt              → 带资料的 prompt
⑪ 生成 Generate     「只依据资料回答」+ 强制引用              → 答案 + [n]
⑫ 校验 Verify       引用编号存在？引用原文可查？              → 通过 / 重试 / 拒答
⑬ 评估 Evaluate     离线跑评测集，量化好坏                    → 指标 + bad case
```

每个环节都有自己的失败方式，**排错时必须先定位是哪一环坏了**：

| 环节 | 典型失败表现 | 排查动作 |
|---|---|---|
| 加载 / 清洗 | 文档读进来是乱码、页眉页码混进正文 | 打印前 500 字人工看一眼 |
| 切片 | 答案被切断在两块中间，或一个 chunk 混了 3 个主题 | 看命中的 chunk 原文 |
| 向量化 | 语义相近的句子相似度却很低 | 换模型；确认文档和查询用**同一个**模型 |
| 召回 | 正确的 chunk 根本没进候选集 | 查 Recall@K（第 8 节），调 K 或加 BM25 |
| 融合 / 重排 | 正确 chunk 召回了，但排在第 15 位被截掉 | 看排序位置，加 Rerank |
| 组装 / 生成 | 资料在里面模型却不用，或引用了不存在的编号 | 改 prompt 顺序；加引用校验 |

**先记住一条铁律：RAG 的效果上限由召回决定。** 检索没召回的内容，再好的模型也变不出来——所以第 8 节的评估必须把"召回"和"生成"分开测。

## 2. 文档加载与清洗

**为什么：** 真实文档不是干净纯文本。PDF 转出来带页眉页脚和断行，网页复制来带导航栏和广告，Markdown 里有 HTML 注释。**脏数据进 RAG，就是脏答案出 RAG**——而且这类错误最隐蔽，因为它不报错。

```python
import io, os, re
def load_documents(root):
    """加载 md / txt。返回 [{"id","title","path","text"}]，不引入任何第三方依赖。"""
    docs = []
    for dirpath, _, names in os.walk(root):
        for name in sorted(names):
            if name.lower().endswith((".md", ".txt")):
                path = os.path.join(dirpath, name)
                with io.open(path, encoding="utf-8") as f:
                    docs.append({"id": name, "title": name, "path": path, "text": clean_text(f.read())})
    return docs
def clean_text(text):
    """清洗四件事：统一换行 → 去页眉页脚 → 压空行 → 去零宽字符。"""
    text = text.replace("\r\n", "\n").replace("\r", "\n")
    text = re.sub(r"^\s*(第\s*\d+\s*页|-\s*\d+\s*-|Page\s+\d+)\s*$", "", text, flags=re.M)
    text = re.sub(r"[ \t\u00a0\u200b]+", " ", text)
    return re.sub(r"\n{3,}", "\n\n", text).strip()
```

**PDF 怎么办？** 本章只用 md/txt 是为了"零依赖可跑"，但生产里 PDF 很常见，选型思路是：
工具选型：`pypdf` 适合纯文本型 PDF（Word 导出），速度快，但扫描件和双栏排版会乱；`pdfplumber` 能保留表格与坐标，但慢且吃内存；`unstructured` 支持 PDF/HTML/PPT 混合一把梭，代价是依赖重；商用文档解析 API 能处理扫描件与复杂版面（要 OCR），但要钱、要联网、数据出域。
**关键判断：先花 10 分钟人工看一页解析结果。** 如果 PDF 是扫描件（整页是图），任何纯文本库都提不出文字，必须先 OCR；如果是双栏论文，要先按坐标分区再拼，否则左右两栏的文字会交错混在一起——这种错误的切片再怎么优化都救不回来。
### ⚠️ 常见坑

**坑 1：把页眉页脚一起切进 chunk。** 现象：每个 chunk 里都有"XX公司员工手册 第 3 页"，检索"员工手册"时所有块得分都很高，排名被污染。原因：没做清洗，页眉页脚是全文重复的高频文本。→ 怎么改：清洗阶段用正则删掉页码/页眉行，或统计"出现在超过 30% 块里的相同句子"并自动剔除。
**坑 2：把 Markdown 的井号标题当普通字符。** 现象：chunk 里全是"## 3.2 报销标准"，模型把标题符号也当内容编码。原因：向量化时没区分"结构"和"内容"。→ 怎么改：标题别删，但要把它变成语义的一部分——在第一行拼上标题路径（`差旅制度 > 3.2 报销标准 > 住宿`），检索时就有"面包屑"可用。

## 3. 切片（Chunking）：本章第一个重点

切片是 RAG 里**最便宜也最有效的优化点**：换一种切法就能让召回率涨十几个百分点，不用花一分钱 API 费。
### 3.1 固定长度切片的三个参数

```python
def chunk_fixed(text, chunk_size=400, chunk_overlap=60, separators=("\n\n", "\n", "。")):
    """固定长度：按 chunk_size 切，相邻块重叠 chunk_overlap，尽量在分隔符处断开。"""
    chunks, start = [], 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        if end < len(text):                                  # 不在结尾时，往前找分隔符断开
            for sep in separators:
                cut = text.rfind(sep, start + chunk_size // 2, end)
                if cut != -1:
                    end = cut + len(sep)
                    break
        if text[start:end].strip():
            chunks.append(text[start:end].strip())
        if end >= len(text):
            break
        start = max(end - chunk_overlap, start + 1)          # 回退 overlap，且保证不原地打转
    return chunks
```

三个参数作用完全不同，别混着调：

| 参数 | 决定什么 | 调大的后果 | 调小的后果 |
|---|---|---|---|
| `chunk_size` | 一个块装多少字 | 噪声变多、检索变糊、token 变贵 | 语义不完整、答案被切断 |
| `chunk_overlap` | 相邻块共享多少 | 冗余、结果重复、成本上升 | 边界处的信息仍然丢失 |
| `separators` | 优先在哪断开 | 断点更自然，但块长不均 | 句子/段落被硬切 |

**经验起点：`chunk_size` 300~500 字（中文）、`chunk_overlap` 取 15%~20%（50~80 字）、分隔符优先级 `\n\n` > `\n` > `。` > 硬切。**
### 3.2 中文的 chunk_size 不能照搬英文经验

网上的"chunk_size=500、overlap=50"是**英文语料**的经验，直接抄到中文上会踩两个坑：
1. **单位不一样。** 英文经验里 500 通常指 **token**，而 1 token ≈ 4 个英文字符，所以 500 token ≈ 2000 字符 ≈ 375 个英文单词。中文如果单位是**字符**，500 字符 ≈ 350~800 token（不同分词器差一倍）；如果单位是 token，500 token 只有约 **350~800 个汉字**——**同一个数字，中英文承载的信息量差 2~4 倍**。
2. **信息密度不一样。** 汉字单字信息量高，500 个汉字往往已是一整节内容。用英文的块长去装中文，很容易把两个不相关的主题塞进一块，这段向量就成了"什么都像、什么都不准"的中间态。
**所以中文的实操建议：以"一个完整语义单元"为准，用字数（不是 token）当参数，从 300~500 字起调，再用第 8 节的评测集验证。**

```python
from common.llm import count_tokens_approx
for size in (200, 400, 800):                       # 打印块数、平均与最大 token，看块长是否均匀
    cs = chunk_fixed(doc["text"], chunk_size=size)
    toks = [count_tokens_approx(c) for c in cs]
    print("size=%-4d 块数=%-4d 平均 %d token，最大 %d token" % (size, len(cs), sum(toks) / len(toks), max(toks)))
```
### 3.3 按语义结构切：比按字符切好得多

**为什么：** 作者已经帮你分好段了——标题、小节、列表就是天然的语义边界。按字符切是"无视这些边界"的做法，所以才会出现"答案被切成两半"。

```python
def chunk_by_heading(text, max_chars=600):
    """按 Markdown 标题层级切：一个标题下的内容为一块；过长则按段落再切。"""
    chunks, level_path = [], []
    for block in re.split(r"\n(?=#{1,3}\s)", text):               # 在每个标题前断开
        m = re.match(r"(#{1,3})\s+(.+)", block.strip())
        if m:
            level = len(m.group(1))
            level_path = [p for p in level_path if p[0] < level] + [(level, m.group(2).strip())]
        path = " > ".join(t for _, t in level_path)              # 标题路径：既是检索特征，也是引用来源
        body = block.strip()
        if len(body) <= max_chars:
            chunks.append({"text": body, "path": path})
        else:                                                    # 太长的节按段落二次切分
            chunks += [{"text": sub, "path": path}
                       for sub in chunk_fixed(body, chunk_size=max_chars, chunk_overlap=60)]
    return chunks
```

`path`（标题路径）一定要留着，它有两个用处：**拼进 chunk 提高检索准确率**，以及**给用户看引用来源**（"《差旅制度》> 3.2 报销标准"比"chunk_17"有用得多）。
### 3.4 四种切片策略对比

| 策略 | 做法 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **固定长度** | 按字数切 + 重叠 | 实现零成本、块长均匀 | 无视语义边界，答案易被切断 | 结构混乱的文本（聊天记录、OCR 结果） |
| **递归字符** | 按 `\n\n` → `\n` → `。` → 硬切的优先级递归切 | 尽量保住段落，块长可控 | 仍是字符视角，不认识标题层级 | **默认首选**，80% 场景够用 |
| **按语义/结构** | 按标题、段落、代码块切 | 每块语义完整，可带标题路径 | 块长不均，超长节仍要二次切 | 结构清晰的文档（手册、规范、API 文档） |
| **父子切片** | 小块（200 字）**检索**，命中后把父块（800 字 + 标题）喂模型 | 检索准 + 上下文全，效果通常最好 | 实现复杂，token 成本上升 | 对答案完整性要求高的场景 |

**父子切片值得多说一句**，它解的是"检索粒度"和"生成粒度"的矛盾：小块向量更聚焦、匹配更准，但模型看不到上下文；大块上下文完整，但向量被稀释。父子切片让两者各干各的活——**用小块找，用大块答**：

```python
def chunk_parent_child(text, child_size=200, parent_size=800):
    pairs = []
    for p_idx, parent in enumerate(chunk_fixed(text, chunk_size=parent_size, chunk_overlap=0)):
        for child in chunk_fixed(parent, chunk_size=child_size, chunk_overlap=40):
            pairs.append({"child": child, "parent": parent, "parent_id": p_idx})
    return pairs        # 只索引 child；命中后把 parent 交给模型
```
### 3.5 切片好坏怎么判断：一次真实对比

**不要凭感觉说"这样切更好"。做法是：同一份文档、同一批判测问题，跑两种切法，看检索排名的差异。**
示例文档里有这么一段：

```
## 3.2 报销标准
国内出差住宿：一线城市每晚不超过 600 元，其他城市不超过 400 元。
海外出差住宿：按当地货币结算，单晚不超过等值 8000 日元。
```

问题：**"海外出差住宿上限是多少？"**

| 切法 | 命中的块 | 排名 | 结果 |
|---|---|---|---|
| 固定 200 字切 | "…其他城市不超过 400 元。海外出差住宿：按当地货币结算，单晚不超" + "过等值 8000 日元。" | 第 7 位（Top-5 之外，**没召回**） | 答不出，或编一个数字 |
| 按标题切 | "## 3.2 报销标准 / 国内… / 海外… 8000 日元"（整节 312 字） | 第 1 位 | 答案完整 |

原因很直白：固定切法把"8000 日元"和它所在的语义单元（"报销标准"）切散了，而"过等值 8000 日元"这个块单独看根本看不出在讲什么；按标题切保留了完整语义，向量自然更聚焦。
**判断切片好坏的三个可操作指标：** ① **Recall@K**（第 8 节代码）：同一批判测问题下正确块被召回的比例，最硬的指标；② **块语义完整率**（抽 20 块人工读）：单独看能看懂的块占比，低于 80% 就该改切法；③ **块长分布**：打印 `min/平均/max`，若 max 是最小值的 10 倍以上（80 字和 1200 字并存），检索质量会很不稳定。
### ⚠️ 常见坑

**坑 1：chunk_size 直接抄英文的 1000 token。** 现象：中文语料每块装了 3~4 个主题，检索出的块"沾一点边但都不对"。原因：中文信息密度高，同样 token 数装的内容更多。→ 怎么改：中文从 300~500 字起调，用召回率验证，而不是抄数字。
**坑 2：只调 overlap 想解决"答案被切断"。** 现象：overlap 从 50 加到 400，召回率没涨，成本翻倍，结果里开始出现大量重复块。原因：答案被切断是**切点位置**的问题，不是重叠多少的问题。→ 怎么改：先改成按标题/段落切，overlap 保持 15%~20%。
**坑 3：把表格和代码当普通文本切。** 现象：表格被切成两半，模型读到半张表，答案错位。原因：表格的"行"是原子的。→ 怎么改：表格整块保留（或转成 Markdown 表格后按行切）；代码块用三个反引号的围栏整体保留，超长再按函数边界切。

## 4. 向量化（Embedding）
### 4.1 embedding 是什么：把"意思"变成坐标

**为什么需要它：** 关键词检索解决不了同义改写——用户问"出差住酒店最多能花多少"，文档里写的是"住宿标准"，一个共同关键词都没有，但意思完全一致。
**embedding 就是给每段文字在高维空间里定一个坐标**：意思相近的文字坐标靠得近，于是"找相关内容"变成了"找最近的点"——一次点积就能算出两段文字有多像，不需要共享任何字词。
余弦相似度的公式是**点积除以两个向量模长的乘积**，纯数学库就能算：`dot / (||a|| * ||b|| + 1e-9)`（加 1e-9 防止除零）。不需要 numpy，几千条向量时手写循环完全够快。
### 4.2 中文常用 embedding 模型选型

| 模型 | 维度 | 部署 | 大致成本 | 适合 |
|---|---|---|---|---|
| `text-embedding-3-small` | 1536 | API | $0.02 / 百万 token | 通用、便宜、中英混合 |
| `text-embedding-v3`（通义） | 1024 | API | 按量计费，国内可直连 | 中文为主、要国内合规 |
| `bge-small-zh-v1.5` | 512 | 本地 | 免费（约 100MB） | 中文、离线、CPU 可跑 |
| `bge-m3` | 1024 | 本地 | 免费（约 2GB） | 多语言 + 长文本，效果好但吃资源 |

**算一笔账：** 30 万字中文 ≈ 45 万 token，用 `text-embedding-3-small` 全量编码一次约 **$0.009（约 7 分钱）**。索引成本可以忽略，**真正贵的是每次查询的生成调用**——所以别为了省 embedding 的钱牺牲检索质量。
**铁律：文档和查询必须用同一个模型（同一版本）编码。** 不同模型的向量空间不可比——两个 1536 维向量算出的余弦可能只有 0.2，你会以为"完全没有相关内容"。**换了 embedding 模型，必须全量重建索引。**
### 4.3 零依赖降级方案：TF-IDF 与 BM25

**为什么要有这条路：** 很多人的第一个 RAG 卡在"没配 embedding API"。而且即使有 API，关键词方法在某些场景（专有名词、型号、错误码）本来就比向量强——**所以这套代码不是玩具，它是混合检索的一半。**

```python
import math
from collections import Counter
def tokenize(text):
    """中文分词：有 jieba 就用（pip install jieba），没有就退回字符二元组。"""
    try:
        import jieba
        return [w for w in jieba.lcut(text.lower()) if w.strip()]
    except ImportError:
        t = re.sub(r"\s+", "", text.lower())
        return [t[i:i + 2] for i in range(max(len(t) - 1, 1))]     # 二元组：无需词典
class BM25:
    """BM25：k1 控制词频饱和，b 控制长度归一化。手写 25 行，比调库更讲得清。"""
    def __init__(self, docs, k1=1.5, b=0.75):
        self.k1, self.b, self.docs = k1, b, [tokenize(d) for d in docs]
        self.avgdl = sum(len(d) for d in self.docs) / max(len(self.docs), 1)
        self.freqs = [Counter(d) for d in self.docs]
        df = Counter(w for d in self.docs for w in set(d))
        self.idf = {w: math.log((len(self.docs) - c + 0.5) / (c + 0.5) + 1) for w, c in df.items()}
    def score(self, query, i):
        dl, s = len(self.docs[i]), 0.0
        for w in tokenize(query):
            f = self.freqs[i].get(w, 0)
            if f:
                s += self.idf.get(w, 0) * f * (self.k1 + 1) / (f + self.k1 * (1 - self.b + self.b * dl / self.avgdl))
        return s
    def search(self, query, top_k=20):
        ranked = sorted(range(len(self.docs)), key=lambda i: -self.score(query, i))
        return [(i, self.score(query, i)) for i in ranked[:top_k] if self.score(query, i) > 0]
```

**BM25 比"数关键词个数"强在哪？** 两点：**IDF** 让"的、是、在"这类到处都有的词几乎不计分，让"报销、日元"这类稀有词权重变高；**长度归一化（b）** 避免长文档靠"字多"占便宜。这也是它至今仍是工业界检索基线的原因。纯 TF-IDF 与它同源，只是没有词频饱和与长度归一化，检索质量通常略差。
### ⚠️ 常见坑

**坑 1：文档用 A 模型、查询用 B 模型。** 现象：文档里明明有答案，相似度却普遍只有 0.1~0.3，阈值怎么调都不对。原因：两个模型的向量空间不通用。→ 怎么改：把模型名与维度写进索引元数据（`{"model": "...", "dim": 1536}`），启动时校验，不一致直接报错。
**坑 2：忘归一化却用点积当余弦。** 现象：长文档永远排第一，短小精准的块排不上。原因：未归一化时模长大的向量天然占优。→ 怎么改：编码后统一 L2 归一化（`v / ||v||`），之后点积就等于余弦。
**坑 3：拿 BM25 分数当相似度阈值。** 现象：想设"分数 < 0.3 丢弃"，结果 BM25 分数是 0~20 的任意范围，阈值完全失效。原因：BM25 没有固定上界，和余弦不是一回事。→ 怎么改：BM25 只用**排名**，不用分数——这正是 RRF 要解决的问题。

## 5. 向量数据库：什么时候需要，什么时候不需要

**先破除一个误区：几千到几万条 chunk，完全不需要向量数据库。** 算一下规模：1 万个 768 维 float32 向量 = 10000 × 768 × 4 字节 ≈ **30 MB**；一次查询 = 1 万次点积 ≈ 768 万次乘加，纯 Python 几十到几百毫秒，numpy 只要 **5~20 毫秒**。这点开销完全撑得住一个内部知识库。

```python
class VectorIndex:
    """极简向量索引：内存矩阵 + 暴力余弦检索。几千条 chunk 用它就够了。"""

    def __init__(self, model_name="tfidf-fallback"):
        self.model_name = model_name      # 必须与查询侧一致（见 4.3 的铁律）
        self.vectors, self.metas = [], []

    def add(self, vector, meta):
        norm = math.sqrt(sum(x * x for x in vector)) + 1e-9
        self.vectors.append([x / norm for x in vector])     # 进来就归一化，检索时点积即余弦
        self.metas.append(meta)

    def search(self, qvec, top_k=20):
        q = [x / (math.sqrt(sum(y * y for y in qvec)) + 1e-9) for x in qvec]
        scored = sorted(((sum(a * b for a, b in zip(q, v)), i) for i, v in enumerate(self.vectors)),
                        reverse=True)
        return [(i, sc) for sc, i in scored[:top_k]]
```

**那什么时候真的需要向量数据库？** 满足任一条再上：**① 向量数超过 10 万**（暴力检索变成几百毫秒~秒级）→ HNSW / IVF；**② 要按元数据过滤**（只搜 2025 年、产品线=A 这类条件）→ Qdrant / Milvus / pgvector；**③ 多进程共享、要持久化与增量更新** → 独立服务或交给数据库；**④ 千万级向量、内存放不下** → IVF-PQ（有损压缩，用召回率换内存）。
常见组合：**本地小项目用文件（JSON + npy）就够；单机生产用 FAISS 或 Chroma；要多租户、要过滤、要扩缩容再上 Milvus / Qdrant / pgvector。** 索引不是越重越好——**先让链路跑通，再按规模换零件**。
### ⚠️ 常见坑

**坑 1：索引只存向量不存原文。** 现象：换台机器，检索能跑，但组装上下文时找不到原文，只能返回一串 id。原因：向量和原文分开存且没做同步。→ 怎么改：一条记录同时存 `{id, text, path, source, model}`，向量与元数据同批写入。

## 6. 检索质量优化
### 6.1 Top-K 与相似度阈值

**Top-K 由"给模型多少 token"决定，不是拍脑袋：** 可用 token ≈ 预算里"检索文档"那一栏（第 07 章的表，比如 3,000），K ≈ 3,000 / 平均块长（比如 350 token）≈ 8。实践区间是 **K=3~8**：K 太小明显漏召回；K 太大会引入噪声，而且中间位置的块会被模型忽略（U 形曲线），等于白花钱。
**阈值不要用绝对值。** 不同 embedding 模型的余弦分布完全不同（有的模型"所有文本相似度都在 0.6 以上"），照抄一个 0.7 只会让检索永久失联。两种稳妥做法：**① 相对阈值**——只保留 `score >= 0.85 * top1_score` 的块；**② 重排分数阈值**——用 Rerank 分数做截断（同一模型的分数可比），比向量分数可靠得多。

```python
def trim_by_relative_score(hits, ratio=0.85):
    """相对阈值：以最高分为基准，砍掉明显掉队的块。hits: [(id, score)] 已按分数降序"""
    if not hits:
        return []
    return [h for h in hits if h[1] >= ratio * hits[0][1]]
```
### 6.2 混合检索：向量 + 关键词，用 RRF 融合

**为什么需要混合：** 向量擅长同义改写，但对**精确字符串**很弱——型号 `XR-2000`、错误码 `E1042`、人名、版本号，向量会把"看着都差不多"的东西搞混；BM25 恰好相反。两者互补，所以生产系统的检索通常是混合的。
难点是**分数不可比**：余弦是 0~1，BM25 是 0~∞，min-max 归一化又会因每次查询的分布不同而抖动。**RRF（Reciprocal Rank Fusion，倒数排名融合）** 绕开分数，只用**排名**：

```python
def rrf_fuse(rank_lists, k=60, top_k=20):
    """RRF：score(d) = Σ 1 / (k + rank_i(d))。只用排名，天然免疫分数量纲问题。"""
    fused = {}
    for ranks in rank_lists:            # ranks 形如 [(doc_id, score), ...]，已按相关性降序
        for pos, (doc_id, _score) in enumerate(ranks):
            fused[doc_id] = fused.get(doc_id, 0.0) + 1.0 / (k + pos + 1)
    return sorted(fused.items(), key=lambda kv: -kv[1])[:top_k]
```

**为什么 RRF 比"归一化后加权求和"稳？** 看一个具体例子（k=60）：

| 文档 | 向量排名 | BM25 排名 | RRF 分数 |
|---|---|---|---|
| A | 第 1 名 | 第 9 名 | 1/61 + 1/69 = **0.0309** |
| B | 第 4 名 | 第 5 名 | 1/64 + 1/65 = **0.0310** |

**B 反超了 A。** 这就是 RRF 的价值观：**在两路里都稳定靠前，胜过在一路里当冠军、另一路里失踪**——语义相关且关键词也命中，才算真的相关。
### 6.3 Rerank 重排：为什么两阶段检索有效

**先理解为什么需要它。** 向量检索用的是 **bi-encoder（双塔）**：查询和文档**各自**编码成向量，直到最后一步点积才"见面"，信息被压成固定长度的向量（信息瓶颈），所以它快（向量可预先算好、建索引）但不够准。**cross-encoder（交叉编码器）** 让查询和文档**拼在一起**送进模型，每一层都在做交叉注意力，能看出"这段到底有没有回答这个问题"，精度高得多——但每个候选都要跑一次模型，无法预先建索引，不能用来做全量检索。
**两阶段检索就是把两者组合：**

```
① 召回（快、粗）：向量 top-20 + BM25 top-20 → RRF 融合 → 候选 20 条
② 重排（慢、准）：cross-encoder 对 20 条逐个打分 → 取 top 4 交给模型
```

代价可算：20 条候选 × 每条约 400 token = 8,000 token 的重排输入；本地 reranker（如 `bge-reranker-base`）CPU 上约 0.5~2 秒、GPU 上几十毫秒，商用 Rerank API 按次计费。**换来的是排序质量提升——公开评测与多数工程实践里 nDCG@5 常涨 5~15 个点，但具体数字必须在你自己的语料上测。**
**没有 rerank 模型怎么办？** 零依赖的替代品是**词面重排**：用查询词覆盖度 + 标题命中 + 长度惩罚重新打分，比 cross-encoder 弱，但比不做强：

```python
def lexical_rerank(query, candidates, w_title=2.0):
    """零依赖重排：查询词覆盖率 + 标题命中加权 + 长度惩罚。candidates: [(chunk, meta, score)]"""
    q_terms = set(tokenize(query))
    rescored = []
    for chunk, meta, _score in candidates:
        cover = len(q_terms & set(tokenize(chunk))) / max(len(q_terms), 1)      # 覆盖率
        title_hit = len(q_terms & set(tokenize(meta.get("path", "")))) > 0
        penalty = 1.0 if len(chunk) < 1200 else 0.8                            # 过长的块降权
        rescored.append((cover + (w_title if title_hit else 0) * 0.5, chunk, meta))
    return sorted(rescored, key=lambda x: -x[0])
```
### ⚠️ 常见坑

**坑 1：Top-K 从 5 拉到 50，以为"多给点总没错"。** 现象：成本涨 5 倍，质量反而下降（模型被无关内容带偏，中间位置的关键块被忽略）。原因：把 K 当"越多越好"的旋钮。→ 怎么改：先按 token 预算定 K（3~8），不够就用**重排**提精度，而不是加数量。
**坑 2：RRF 之后又去乘原始分数。** 现象：融合白写了，结果和纯向量检索几乎一样。原因：忘了 RRF 的前提是"只用排名"。→ 怎么改：RRF 输出只用于排序；要加权就把权重加在**每一路的 RRF 贡献**上，而不是乘原始分数。
**坑 3：重排模型输入被静默截断。** 现象：长块的重排分数永远偏低。原因：cross-encoder 有最大长度（常见 512 token），超长部分被截掉，"答案在块的后半段"就看不见了。→ 怎么改：重排前把块截到模型上限（取前 512 token 或块内最相关的窗口），或用父子切片让小块参与重排。

## 7. 让答案带引用（防幻觉引用）

**为什么必须带引用：** 企业场景里"答案对不对"没法靠人一眼判断，必须能追溯到原文。引用还会**反向约束模型**——当它必须指出出处时，编造概率会明显下降。
**Prompt 的四个要点**（缺一不可）：① 只用资料（否则模型混入自己的知识，答案无法追溯）；② 明确拒答（无答案问题必须能说"不知道"）；③ 编号受限（防止造 `[7]`）；④ **要求回抄原文片段**——这是校验的抓手。

```python
RAG_PROMPT = """你是资料问答助手。只能依据下面的【资料】回答，不允许使用资料之外的知识。
规则：1. 每个事实性结论后必须标注来源编号，格式 [1]、[2]；一句话用到两段资料就写 [1][3]。
2. 【资料】里没有足够信息时，必须直接回答"资料中没有找到相关内容"，禁止推测、禁止编造。
3. 引用编号只能来自【资料】里出现过的编号，不要创造新编号。
4. 中文回答，先给结论，再给依据。

【资料】
{context}

【问题】{question}
输出格式：<答案>（正文，含 [编号] 引用）</答案>  <引用>（每行一条：编号 | 逐字摘自资料的原文片段）</引用>
"""
```

**校验：模型输出的引用必须能在检索结果里找到，而且要能对上原文。**

```python
def validate_citations(answer, cited_ids, retrieved, min_overlap=0.8):
    """校验三件事：编号存在 → 编号在检索结果里 → 引用的原文确实出自对应块。"""
    problems, by_id = [], {m["cite_id"]: m for m in retrieved}
    for cid in cited_ids:
        if cid not in by_id:                                   # ① 编号可能是编的
            problems.append("引用了不存在的编号 [%s]" % cid)
            continue
        quoted = extract_quote(answer, cid)                    # 从答案里抽出该编号对应的片段
        if quoted and ratio_in(quoted, by_id[cid]["text"]) < min_overlap:
            problems.append("编号 [%s] 的引用内容在原块里找不到" % cid)   # ② 片段对不上原文
    return problems

def must_refuse(answer):
    """判断模型是否正确地拒答了。"""
    return any(k in answer for k in ("没有找到", "无法回答", "资料中未提及"))
```

`ratio_in(quote, source)` 用集合近似算"引用里有多少字符能在原文找到"，避免 difflib 在大文本上的慢匹配；重合度 ≥ 0.8 视为引用有效。
**校验失败怎么办？** 三种处理，按严重程度递增：① 记进 bad case 报告（**最少要做这一步**）；② 把问题抛回模型，要求"只使用 [1][2] 回答"再生成一次；③ 直接返回"资料中没有找到相关内容"——**宁可拒答，也不要给出无法追溯的答案**。
### ⚠️ 常见坑

**坑 1：只要求"标注引用"不校验。** 现象：答案带着 `[3]` 很有说服力，但 `[3]` 指向的块根本没被检索回来。原因：把"有引用"当成了"引用正确"。→ 怎么改：必须做机械校验——编号存在、且引用字符与原文重合度 ≥ 0.8。
**坑 2：资料编号和用户可见的文档名混在一起。** 现象：模型写出 `[《差旅制度》]`，校验器只认数字编号，全部判非法。原因：编号格式没约束死。→ 怎么改：prompt 里明确"只能用 [1] [2] 这样的数字编号"，组装时另存"编号 → 文档名 + 标题路径"的映射表给前端展示。

## 8. RAG 评估：本章第二个重点

**没有评估的 RAG 不算做完。** 你会改切片、换模型、加 Rerank——每次改动都需要一个数字告诉你"是变好还是变坏"。凭感觉调参的典型结局是：改到最后自己也不知道哪版更好。
### 8.1 五个指标

| 指标 | 衡量什么 | 怎么算 | 需要标注吗 |
|---|---|---|---|
| **召回率 Recall@K** | 相关的块有多少被召回 | 命中的相关块数 / 全部相关块数 | 需要（标注相关块） |
| **命中率 Hit Rate@K** | Top-K 里是否至少有一个相关块 | 命中为 1 否则 0，取平均 | 需要（或只标答案关键词） |
| **MRR** | 第一个相关块排得有多靠前 | 1 / 第一个相关块的排名 | 需要 |
| **答案正确性** | 答案对不对 | 人工判定，或 LLM 打分（1~5） | 需要标准答案 |
| **忠实度 Faithfulness** | 答案是否**只**由检索内容支撑 | 拆句后逐句判定"能否在资料里找到依据" | 不需要（需模型或人工判定） |
| **引用准确率** | 引用是否真的支撑结论 | 第 7 节的校验通过率 | 不需要 |

**最重要的两个是 Recall@K 和 Faithfulness**：前者决定上限（召回没有的，模型变不出来），后者决定可信度（答案是不是在编）。**很多"看起来效果不错"的 RAG 其实是 Recall@5 高、Faithfulness 低——答案听着对，但一半内容来自模型自己的知识，一换文档就错。**
### 8.2 怎么建评测集（20~50 条就够）

不需要 1000 条。**20~50 条精心设计的问答对就能发现 80% 的问题**，关键是覆盖类型：

| 类型 | 占比 | 例子 | 考什么 |
|---|---|---|---|
| 事实型（单跳） | 约 50% | "住宿报销上限是多少？" | 基本召回与引用 |
| 跨段拼接（多跳） | 约 20% | "我周五出差三天能报多少？"（查标准 + 天数规则） | 多块召回 + 组合 |
| 无答案（negative） | 约 15% | "公司的团建预算是多少？"（文档里没有） | **能否正确拒答** |
| 易混淆 | 约 15% | "海外住宿上限" vs "国内住宿上限" | 区分度、是否混淆相近条款 |

```python
EVAL_SET = [
    {"q": "员工出差住宿报销上限是多少？", "expect": ["600", "400"], "must_refuse": False,
     "gold_chunk_keywords": ["报销标准", "一线城市"]},
    {"q": "海外出差的住宿上限是多少？", "expect": ["8000"], "must_refuse": False,
     "gold_chunk_keywords": ["海外", "当地货币"]},
    {"q": "公司的团建预算是多少？", "expect": [], "must_refuse": True, "gold_chunk_keywords": []},
    # … 建议 20~50 条，写在一个 JSON 文件里，别硬编码进代码
]
```

**标注要求：** 每条至少有"标准答案 + 期望命中的关键词或块 id"；无答案的题必须标 `must_refuse=True`。**只测"能答对的题"的评测集是自欺欺人**——上线后 80% 的投诉来自"文档里没有却编了一个"。
### 8.3 mini 评估函数

```python
def mini_eval(rag, eval_set, top_k=5):
    """离线可跑的最小评估：检索指标 + 关键词答案率 + 引用准确率 + 拒答准确率。"""
    stat = {"n": 0, "hit@k": 0, "mrr": 0.0, "answer_ok": 0, "cite_ok": 0, "cite_total": 0,
            "refuse_ok": 0, "refuse_total": 0}
    bad_cases = []
    for item in eval_set:
        stat["n"] += 1
        hits = rag.retrieve(item["q"], top_k=top_k)                       # ① 只测检索
        texts = [h["text"] for h in hits]
        if item["gold_chunk_keywords"]:                                   # 命中率与 MRR
            ranks = [i for i, t in enumerate(texts) if any(k in t for k in item["gold_chunk_keywords"])]
            stat["hit@k"] += 1 if ranks else 0
            stat["mrr"] += (1.0 / (ranks[0] + 1)) if ranks else 0.0
            if not ranks:
                bad_cases.append(("检索未召回", item["q"], []))
        result = rag.answer(item["q"], hits)                              # ② 再测生成
        ans, cited = result["answer"], result["cited_ids"]
        stat["cite_total"] += 1
        problems = validate_citations(ans, cited, hits)                   # ③ 引用可核验？
        stat["cite_ok"] += 1 if not problems else 0
        if problems:
            bad_cases.append(("引用不可核验", item["q"], problems))
        if item["must_refuse"]:                                           # ④ 拒答能力
            stat["refuse_total"] += 1
            stat["refuse_ok"] += 1 if must_refuse(ans) else 0
            if not must_refuse(ans):
                bad_cases.append(("该拒答却硬答", item["q"], []))
        elif item["expect"]:
            miss = [e for e in item["expect"] if e not in ans]
            stat["answer_ok"] += 1 if not miss else 0
            if miss:
                bad_cases.append(("答案缺关键内容", item["q"], miss))
    n = max(stat["n"], 1)
    return {"hit@k": stat["hit@k"] / n, "mrr": stat["mrr"] / n, "answer_ok": stat["answer_ok"] / n,
            "cite_ok": stat["cite_ok"] / max(stat["cite_total"], 1),
            "refuse_ok": stat["refuse_ok"] / max(stat["refuse_total"], 1), "bad_cases": bad_cases}
```

**注意：离线 Mock 模式下模型回答是模板化的，所以 `answer_ok` 只能当"链路是否打通"的信号；`hit@k`、`mrr`、`cite_ok` 完全可测，它们才是离线调试的主战场。** 接上真模型后 `answer_ok` 才有意义，Faithfulness 也可以再用一次模型来判（"下面这句话能否被资料支撑？能/不能"）。
### 8.4 错误分析：把 bad case 分成四类

跑完评估拿到 bad case 列表后，**逐条归类**，因为四类的修法完全不同：

| 类型 | 判断依据 | 修法 |
|---|---|---|
| **切片问题** | 命中的块明显不完整（答案被切断、混了别的主题） | 改切法：按标题/递归切、调 size 与 overlap、父子切片 |
| **检索没召回** | 正确的块根本不在 Top-K 里 | 加 BM25 混合检索、查询改写、换 embedding、调 K |
| **召回了但模型没用** | 正确块在结果里、排位不低，答案却没用它 | 改 prompt 顺序（最相关的块放最前）、加"必须引用"、降 K 去噪 |
| **模型瞎编** | 检索结果里没有该事实，答案却给出了具体数字 | 强化"无资料必须拒答"、加引用校验、降 temperature、换更强模型 |

**这张表是本章最实用的产出：bad case 报告里每条都应落在某一格，并附上"我打算怎么修"。没有分类的"效果不好"是无法行动的。**
### ⚠️ 常见坑

**坑 1：没有评测集，靠"我问几个问题感觉还行"判断效果。** 现象：改了切片，自己试 3 个问题都觉得更好，上线后投诉变多。原因：3 个问题覆盖不到多跳、无答案、易混淆。→ 怎么改：先花 1 小时建 20 条评测集（含 3 条无答案），每次改动都跑一遍，指标记进 `Trace` 形成对比。
**坑 2：把 Recall 和 Faithfulness 合成一个"总分"。** 现象：总分从 0.7 涨到 0.75，但你不知道该修检索还是修生成。原因：两个指标衡量链路的不同阶段。→ 怎么改：分开看、分开记，做成"检索指标"和"生成指标"两张表。

## 9. RAG vs 微调 vs 长上下文

三种方案不是"谁取代谁"，而是各有适用面：

| 维度 | RAG | 微调（Fine-tuning / LoRA） | 长上下文直塞 |
|---|---|---|---|
| 解决什么 | 私有/易变的知识 | 风格、格式、固定判断模式 | 小规模文档的即时问答 |
| 知识更新 | 重建索引（分钟级） | 重新训练（小时~天级） | 换文档即可 |
| 成本结构 | 查询时 token + 索引 | 一次性训练 + 推理 | 每次提问都塞全部文档 |
| 可解释性 | 高（能给出处） | 低（说不清"哪来的"） | 中（能指出在哪一段） |
| 适用规模 | 万页以上没问题 | 与规模无关 | 约 5 万 token 以内（3~5 万字） |
| 主要失败模式 | 召回不准、引用错 | 学到"口吻"不是"事实"，且会过时 | 成本高、关键信息被淹没 |

**选择建议（按顺序问自己三个问题）：** ① **知识会变吗？** 会变 → RAG（制度、产品文档、代码库都是这一类）；② **需求是"记住事实"还是"改变行为"？** 改变行为（输出格式、语气、领域术语习惯）→ 微调或 few-shot，记事实 → RAG；③ **文档总量小于 5 万 token 吗？** 是 → 长上下文直塞也可以，链路最短；超过 → 必须走 RAG。
**生产中最常见的组合是 RAG + 少量微调：** RAG 负责"知道什么"，微调负责"怎么做"（比如始终按公司格式输出、稳定调用某几个工具）。**先有 RAG 和评测，再考虑微调**——评估体系是共用的，而且 RAG 上线快得多。

## 本章小结

- **RAG 的定位：不改模型，改上下文。** 它解决"私有 + 易变 + 要出处"的知识问题；微调解决"风格与行为"，长上下文只适合 5 万 token 以内的小文档。
- **链路不能只做一半。** 加载 → 清洗 → 切片 → 向量化 → 存储 → 改写 → 召回 → 融合 → 重排 → 组装 → 生成 → 校验 → 评估，每一步都有自己的失败模式，排错要**先定位环节**。
- **切片是最便宜的优化点。** 中文别照搬英文的 chunk_size（单位与信息密度都不同），300~500 字起调；按标题/段落切优于按字符切；小块检索 + 大块喂模型（父子切片）通常效果最好；判断标准是 Recall@K 与"块语义完整率"。
- **向量不是唯一答案。** BM25 在精确字符串上更强且零依赖；向量擅长同义改写。**RRF 只用排名做融合**，天然免疫分数量纲——"两路都靠前"胜过"一路冠军、一路失踪"。
- **两阶段检索（召回 → 重排）是精度与成本的平衡。** bi-encoder 快但粗，cross-encoder 准但慢；先用便宜的召回把候选缩到 20 条，再精排到 4 条。
- **引用必须可校验。** 只要求模型"标注引用"不够，要机械校验：编号存在、引用片段能在原文对上。**宁可拒答，也不要无法追溯的答案。**
- **没有评估的 RAG 不算做完。** `Recall@K` 决定上限，`Faithfulness` 决定可信度，两者必须分开测；评测集 20~50 条、覆盖四类问题（含无答案）；bad case 必须归到"切片 / 检索 / 生成 / 瞎编"四类里，否则无法行动。

## 自测题

**Q1：为什么 chunk 不能太大也不能太小？分别会出什么问题？**

<details><summary>点击查看答案</summary>

**太大**：① 一个块混进多个主题，向量被"平均化"，语义不聚焦，检索精度下降；② token 成本上升，关键信息还会被挤到中间的"低注意力区"。
**太小**：① 语义不完整，"过等值 8000 日元"这种块单独看不知在说什么，检索和生成都会出错；② 块数暴涨，索引与检索开销变大，还容易产生大量近似重复块。
判断标准不是"多大最好"，而是**"这个块单独看能不能看懂在讲什么"**——所以中文推荐 300~500 字起调，再用 Recall@K 验证。

</details>

**Q2：中文的 chunk_size 为什么不能照搬英文经验？**

<details><summary>点击查看答案</summary>

两个原因：**① 单位不同。** 英文经验里的 500 通常指 token，1 token ≈ 4 个英文字符，约合 2000 字符；中文若把参数理解成字符，500 字符 ≈ 350~800 token（取决于分词器），同一数字承载的信息量差 2~4 倍。**② 信息密度不同。** 汉字单字信息量高，500 个汉字往往已是一整节，用它当块长容易把两个主题塞进一块。
实操建议：中文以"一个完整语义单元"为准，用**字数**当参数，从 300~500 字起调，overlap 取 15%~20%，并且必须用评测集验证而不是抄数字。

</details>

**Q3：向量检索和 BM25 各自擅长什么？RRF 为什么比分数归一化更稳？**

<details><summary>点击查看答案</summary>

**向量**擅长同义改写与语义匹配（"住酒店最多花多少" ↔ "住宿标准"），但对精确字符串（型号 `XR-2000`、错误码 `E1042`）容易混淆；**BM25** 正相反，精确词匹配极强、同义改写完全无能。两者互补，所以常见做法是混合检索。
**RRF 稳的原因**：余弦是 0~1、BM25 是 0~∞，量纲不可比；min-max 归一化会因每次查询的分数分布不同而抖动。RRF 只用**排名**：`score(d) = Σ 1/(k + rank_i(d))`，k 常取 60。例：A 在第 1 和第 9 名 → 1/61+1/69 = 0.0309；B 在第 4 和第 5 名 → 1/64+1/65 = 0.0310，**B 反超**——"两路都稳定靠前"胜过"一路冠军、一路失踪"。

</details>

**Q4：Rerank 为什么有效？为什么不能只用 cross-encoder 做检索？**

<details><summary>点击查看答案</summary>

**有效的原因**：向量检索用 bi-encoder，查询和文档**各自**编码，直到最后点积才"见面"，信息被压成固定长度向量（信息瓶颈），快但粗；cross-encoder 把查询与文档拼在一起过模型，每层都有交叉注意力，能判断"这段有没有回答问题"，精度明显更高。
**不能只用它的原因**：cross-encoder 必须对每个候选跑一次模型，无法预先编码建索引——对上万块做全量打分，延迟和成本都不可接受。所以用两阶段：便宜的召回（向量 + BM25 → RRF）把候选缩到 20 条，再用 cross-encoder 精排到 4 条。实践中 Rerank 常带来 nDCG@5 提升 5~15 个点，但必须在自己语料上测。

</details>

**Q5：Recall@5 = 0.95 但 Faithfulness = 0.4，最可能的问题在哪？**

<details><summary>点击查看答案</summary>

**问题不在检索，在生成。** Recall 高说明相关块已经召回，Faithfulness 低说明答案里有一半内容**不是**由检索内容支撑的，典型原因有三种：① prompt 没强约束"只依据资料回答"，模型用自己的先验知识补内容；② 资料被放在 prompt 中段（U 形曲线），模型没真正用上；③ 块里噪声太多（K 太大），模型抓错重点。
修法对应：强化"只用资料 + 无资料必须拒答"、把最相关的块放到资料区最前面、把 K 从 8 降到 4、加引用校验并记录失败率。**这也是为什么 Recall 和 Faithfulness 必须分开测**——合成一个总分就无法定位到环节。

</details>

## 结语与下一章

RAG 不是给模型换一个更大的脑子，而是允许它在答题时**翻书**：书是你自己的（私有文档），页码是你编的（索引），答案必须写上"第几页"（引用），翻完还得有人检查它有没有真的翻到那一页（校验与评估）。所以决定 RAG 效果的从来不是模型多强，而是**你递给它的那几页纸对不对、全不全**——检索决定上限，忠实度决定可信度，这两件事必须分开量。

但……你的 Agent 现在能记住用户（第 07 章）、能查你的私有文档（第 08 章），能力却仍然**写死在代码里**——每加一个能力就要改一次 Python，改完还得重新评测、重新上线。

下一章是第 09 章 [[docs/第09章 Skills能力包]]，它换一种扩展方式：用一份 `SKILL.md` 描述"什么时候用、怎么用、有哪些脚本"，让 Agent 在不改代码的前提下学会新技能。你会写一个能被真正触发的 Skill（而不是写了却从不被调用），并用评测集量化它带来的成功率提升。本章的检索评估方法会直接复用——**验证 Skill 是否有效，靠的也是评测集，不是感觉。**
