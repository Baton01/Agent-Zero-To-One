# 第15章 综合实战

> **本章目标：** 把前 14 章散落的能力组装成**三个能拿出去给人看的项目**：网页研究助手（L2）、文档问答系统（L3）、代码审查助手（L4）。每个项目都走完整流程：需求 → 设计 → 实现 → 评估 → 复盘。
> **预计用时：** 12 小时（每个项目 4 小时；建议一次只做一个，做完一个再开下一个）　**前置章节：** 第04–14章（工具、ReAct、记忆、RAG、Skills、多智能体、评估、部署）　**配套代码：** `code/ch15_agent_app.py`

---

## 0. 开篇：能跑通 ≠ 能交付

上个月有个学员去面一家做 AI 应用的团队，简历上写着"完成 14 章 Agent 教程，实现检索、记忆、多智能体等多个 demo"。面试官翻了两页，问了一句：

> 面试官：「这些里面，有哪个是别人现在能用的？」
>
> 他：「都能跑，我本地都演示过。」
>
> 面试官：「那我 clone 下来 10 分钟能跑起来吗？它的准确率是多少？」
>
> 他：「key 得换成我自己的……准确率没统计过，但效果还行。」
>
> 面试官追问：「'还行'是几成？答不上来，我这边就没法判断这东西做没做完。」

他卡住了。回来打开自己的 `code/` 目录，三个问题一个都答不上来：

- **问题 1**：别人 clone 下来，能在 10 分钟内跑起来吗？→ 不能。你的 key 写在代码第 12 行，路径写死了 `C:\Users\你\Desktop`。
- **问题 2**：你能说出它的准确率是多少吗？→ 不能。你只记得"跑起来效果还行"，但"还行"是几次？几条？
- **问题 3**：它昨天和今天的表现一样吗？→ 不知道。同一段 prompt 两次结果不同，而你没有任何记录。

这就是**能跑通的 Demo** 和**能交付的项目**之间的差距。面试官、导师、同事判断你做没做过真东西，看的就是这三条：**跑得起来、说得清效果、复现得了**。

**先排除两个错误做法：** ① **一上来就做"大而全"的平台**（带前端、带多用户、带权限、带计费）——你会花 80% 时间在 Web 框架上，Agent 部分还是最粗糙的那块，最后什么也讲不清；② **把第 05 章的 ReAct 循环换个数据集当项目**——那不是项目，那是练习，它没有需求边界、没有评估、没有失败记录。

本章走第三条路：**用同一套骨架做三个不同的小项目**，每个都完整回答"给谁用、解决什么、效果多少、失败怎么办"。三个项目对应 [[01-Raw/03-项目阶梯与能力对照表]] 里的 L2 / L3 / L4，是简历上最容易被追问、也最容易讲出深度的一档；三者共用一份代码 `code/ch15_agent_app.py`，用 `--mode research / qa / review` 切换，离线也能跑（详见第 5 节）。

## 1. 从 demo 到项目：五个差距

这五条是"看起来能跑"和"敢拿去演示"的分界线。**每一条都能在半小时内补上**，但没补的状态下，你会在演示现场被问穿。

| # | 差距 | Demo 的样子 | 项目的要求 | 最小补法（今天就做） |
|---|---|---|---|---|
| 1 | **配置管理** | Key 写在代码第 12 行；模型名、路径、阈值全是字面量 | 密钥不落代码、参数可改、换个模型不用改代码 | 全部走 `.env`（`load_env()`），启动时校验必填项，缺失**直接报错退出** |
| 2 | **错误处理** | 一次超时就崩；一个来源抓不到整条任务就废 | 局部失败不拖垮整体，且失败要看得见 | 三类错误分开：可重试（超时/429/5xx，退避 1s→3s，最多 2 次）、不可重试（400/401/403，立刻抛）、可降级（跳过并计入 `failures`） |
| 3 | **日志与可观测** | 只有 `print`，出事只能重跑 | 能事后回答"这一步花了多少 token、为什么选了这条来源" | 结构化事件：`Trace("ch15_research").log("retrieve", candidates=12, kept=8)`，收尾 `.summary().save()` |
| 4 | **文档** | 只有代码，靠口头讲 | README 回答四个问题：怎么跑、怎么配、怎么扩展、**已知限制** | 四小节标题照抄，每节写 5 行；"已知限制"写满 3 条才算合格 |
| 5 | **可复现性** | 两次结果不同，无法比较 | 固定输入 + 固定参数 + 可离线，指标能对上 | 内置示例数据、`AGENT_MOCK=1` 离线跑、trace 记录模型名与温度；同一评测集跑两遍差异 > 5% 就要查原因 |

**为什么把"已知限制"单列出来？** 因为它是最省时间的加分项。面试官问"你这个系统什么问题解决不了"，你答"表格跨页时切片会丢表头、超过 8k token 的 diff 我只审高危文件、模型版本换了指标会漂 3~5 个点"——这三句话传递的信息量，比十句"效果挺好的"大得多。**说不清限制的人，通常也没做过评估。**

## 2. 项目 A：网页研究助手（对应 L2）

### 2.1 需求与边界

**一句话需求：** 输入一个主题，自动完成 **搜索 → 抓取 → 筛选 → 综合 → 输出带引用的报告**。

**用户是谁：** 需要快速了解一个陌生话题的人（技术选型调研、竞品了解、课程作业背景调研）。

**成功标准（可量化）：**

| 指标 | 含义 | 目标 |
|---|---|---|
| 来源数量 | 最终报告实际引用的独立来源数 | 6~12 个 |
| 引用准确率 | 抽检引用，原文确实支持该句的比例 | ≥ 90% |
| 编造率 | 报告中断言无法在证据里找到支撑的比例 | **0**（出现即 P0） |
| 任务成功率 | 一次运行能正常产出报告的比例 | ≥ 95% |
| 单次成本 | 一次研究的总 token 花费 | ≤ 0.2 元（deepseek-chat 量级） |

**明确不做什么：** 不做多轮对话（一次一主题）、不做全文翻译、不追求实时（允许 5 分钟出结果）、**不承诺"全面"**（明确输出 800~1500 字的要点式报告，不是综述）。

### 2.2 设计：先出大纲还是先搜？

这是本项目第一个真实取舍，两条路都有人走，结果差别很大：

| 做法 | 怎么做 | 优点 | 致命问题 |
|---|---|---|---|
| 先出大纲 | 让模型直接列 5 个子问题，再逐个搜 | 结构漂亮、成本低 | 模型**不知道你的库和互联网上有什么**，大纲全是空泛的常识框架（"背景/现状/挑战/展望"），搜出来的东西也是空的 |
| 先搜再出大纲 | 先用主题做一轮粗搜，看真实材料，再定子问题 | 大纲贴着材料长，问题具体可答 | 多一轮搜索成本；粗搜偏了会带偏方向 |
| **两阶段（推荐）** | ① 粗搜 8~12 条，只读标题+摘要；② 生成 3~5 个子问题；③ 每个子问题精确搜 3~5 条 | 结构由证据决定，且每步都能验收 | 需要多花 20% token |

**结论：采用两阶段。** 理由很简单——**大纲是"关于材料的问题清单"，不是"关于主题的作文提纲"**。判断标准：一个子问题如果搜不到材料，它就是错的，必须重写。

### 2.3 四个关键难点

**难点 1：搜索结果质量参差。** 省钱的顺序是"先筛后读"——用标题+摘要做粗筛（几乎不花钱），再抓正文（贵）。一次典型的漏斗：

```
搜索结果 20 条  →  去重后 16 条  →  粗筛保留 8 条  →  抓取成功 5~6 条  →  引用 4~6 条
```

**抓取成功 30%~40% 失败是常态**（403、付费墙、JS 渲染），设计时就要按"抓 8 条能成 5 条"来规划，而不是指望 8 条全成。

**难点 2：来源可信度排序。** 不要用"模型觉得靠不靠谱"，用可解释的规则打分：

| 层级 | 来源类型 | 分数 | 处理方式 |
|---|---|---|---|
| T0 | 官方文档、规范、原始论文、官方仓库 | 1.0 | 关键结论优先引用 |
| T1 | 一线工程博客、技术社区高赞长文、知名媒体 | 0.7 | 正常引用 |
| T2 | 问答站、论坛、教程转载 | 0.4 | 只用于交叉验证，不单独支撑结论 |
| T3 | 内容农场、聚合站、无署名文章 | 0.1 | 直接丢弃 |

`score = 0.5×tier + 0.2×时效(近 2 年=1.0) + 0.2×标题匹配度 + 0.1×有代码/数据`。
**再加一条硬规则：同一条事实至少有 2 个独立来源才写进报告。** 只有一个来源时，要么标注"单一来源，待核实"，要么不写——这条规则能挡掉大部分编造。

**难点 3：内容过长需要压缩。** 一页正文 3000~8000 字，十几页就能撑爆上下文。三段式压缩，**每一步都要保留原文定位**：

1. **段级筛选**：按与子问题的词面相关度（BM25 思路）只留前 30% 的段落；
2. **抽成事实卡**：每段抽 1~3 条"事实 + 原文片段"，每条 ≤ 60 字，**必须带原文片段**；
3. **预算截断**：超过 token 预算时，按来源 tier 从低到高丢弃（而不是按顺序砍）。

**难点 4：引用必须可追溯——本项目的灵魂。** 核心设计是**证据表（evidence table）**：抓取阶段就把证据固化下来，生成阶段只允许"用证据说话"。

```python
# 抓取阶段：每条证据都是一个可回查的对象，quote 是原文，不是模型改写的
ev = {"sid": "S3",              # 证据编号，报告里必须写成 [S3]
      "url": "https://...",     # 来源
      "title": "MCP 规范概览",
      "tier": 0,                # 可信度分层
      "quote": "MCP 基于 JSON-RPC 2.0 ...",   # 原文片段（保真关键）
      "span": (1240, 1310),     # 在原文中的字符偏移，可自动复核
      "fetched_at": "2026-09-20"}

def check_citations(report, evidence):
    """三道闸的最后一道：报告里每个 [Sn] 必须存在于证据表，且句子与原文有词面重叠。"""
    problems = []
    for sid, sentence in extract_citations(report):          # 正则抓 [S3] 与所在句
        if sid not in evidence:
            problems.append("引用了不存在的来源 %s：%s" % (sid, sentence[:30]))
            continue
        overlap = keyword_overlap(sentence, evidence[sid]["quote"])   # 关键词覆盖率
        if overlap < 0.35:
            problems.append("引用 %s 与原文不符（覆盖率 %.2f）：%s" % (sid, overlap, sentence[:30]))
    return problems
```

**三条硬约束，缺一条引用就会失真：**
1. **URL 只能来自证据表**，禁止模型自己写 URL（模型编 URL 是高频幻觉）；
2. **`quote` 必须是原文切片**，不许模型改写后再存；
3. **生成后必过校验**：发现的每条问题要么删除该句，要么把那句话降级为"（单一来源，待核实）"。

### 2.4 评估：怎么判断一份研究报告是好的

**先写标准要点表，再看报告。** 做法：拿到主题后先自己查一遍，列出 8~12 条"一份合格报告必须覆盖的要点"，存成 `evals/research_gold.json`——这就是你的评测基线。

| 指标 | 怎么算 | 目标 | 怎么测 |
|---|---|---|---|
| **信息覆盖度** | 命中的要点数 / 应有要点数 | ≥ 0.7 | 对照标准要点表逐条打勾 |
| **引用准确率** | 抽 10 条引用打开原文核对，`(支持 + 0.5×部分支持) / 10` | ≥ 0.9 | 人工 20 分钟，或让模型判 + 抽 3 条人工校准 |
| **编造率** | 无证据支撑的断言数 / 断言总数 | 0 | 逐句回溯证据表 |
| **来源质量** | T0+T1 引用数 / 总引用数 | ≥ 0.6 | 统计证据表 tier |
| **失败可见性** | `failures` 里被记录且被说明的失败数 / 实际失败数 | 1.0 | 看 trace，看有没有"静默失败" |

**最容易被忽略的是最后一个。** "抓取失败"不算事故，"抓取失败了但报告里假装没这回事"才是事故。

### ⚠️ 常见坑

- **现象**：报告很流畅，但引用编号对不上原文。**原因**：证据用模型摘要而不是原文，摘要过程中信息被改写。**怎么改**：`quote` 只存原文切片，摘要另存字段，引用校验比对的是原文。
- **现象**：为了让报告"丰富"，让模型自由发挥补充背景知识，结果一半内容查不到来源。**怎么改**：prompt 里写死"只允许使用编号证据中的信息，无法支撑的句子删掉"，并在校验环节真的删。
- **现象**：抓取用 `requests.get` 没有超时，一个慢站把整次运行拖到 10 分钟。**怎么改**：超时 10 秒、正文上限 200KB、整体任务上限 5 分钟；超时的一律记入 `failures` 继续往下走。
- **现象**：子问题写得像作文提纲（"发展现状与未来展望"），搜出来的东西全是营销文。**怎么改**：子问题必须能直接当搜索词用，验收问句是"这个词搜出来的是不是我想要的东西"。

### 2.5 交付标准清单

- [ ] `README.md`：一句话介绍、怎么跑（含离线模式）、一次完整运行的输出样例、已知限制 ≥ 3 条。
- [ ] `python ch15_agent_app.py --mode research` 离线可跑，无 key 无网络，产出报告 + `traces/ch15_research.json`。
- [ ] 证据表落盘（`evidence.json`）：每条含 `sid / url / title / tier / quote / span / fetched_at`。
- [ ] 引用校验可独立运行：`check_citations()` 能对任意一份报告输出问题清单。
- [ ] 评测数据：一份标准要点表（8~12 条）+ 5 个主题的实际跑分（含 1 个跑砸的）。
- [ ] 失败记录：`failures.md` 写清每个失败来源、失败类型（超时/403/解析失败）、当时的降级动作。
- [ ] 真实运行一次在线版本，记录 token 与费用。

**验收问句**：随机挑报告里的一句话，你能在 30 秒内说出它来自哪条证据的哪句原文吗？（答不上来说明证据表是摆设。）

### 2.6 简历写法

**一句话：** 独立实现网页研究助手：输入主题自动完成检索—抓取—交叉验证—成文，输出带来源编号的研究报告，引用准确率 \_\_%（抽检 50 条），编造率为 0。

**三个技术亮点：**
1. **证据表驱动的引用机制**：抓取阶段固化原文片段与字符偏移，生成后逐条校验（编号存在性 + 词面覆盖 ≥ 0.35），把"引用可信"变成可自动检查的工程约束。
2. **两阶段问题拆解**：先粗搜再定子问题，让子问题贴着真实材料生长；配合来源分层（T0~T3）与"单一事实至少 2 个独立来源"的硬规则，把幻觉挡在成文之前。
3. **失败可见的降级设计**：按"抓 8 条成 5 条"规划漏斗，超时/403/解析失败全部记录并降级（改用搜索摘要），任务成功率从 \_\_% 提到 \_\_%。

**可量化结果（填你自己的实测值）：** 20 个主题上，平均 8.4 个来源、平均单次 0.11 元、平均耗时 92 秒、引用准确率 92%。

### 2.7 面试追问预演

**Q1：你的报告怎么保证不编造？**
要点：三道闸——① 生成前只给编号证据，prompt 明确"无证据不写"；② 生成后跑 `check_citations()`，编号不存在或与原文不符的句子直接删；③ 发布前人工抽检 10 条引用回查原文。另外把"单一来源"的结论显式标注，而不是让读者以为是共识。

**Q2：搜索质量很差（全是营销文/过期内容）怎么办？**
要点：分层打分 + 交叉验证 + 宁缺毋滥。具体动作：T3 直接丢；同一条事实要 2 个独立来源；报告里显式写"该结论证据不足"。**关键是承认"查不到"也是结果**，不要用看起来像答案的废话填空。

**Q3：主题特别宽泛（比如"讲讲 RAG"）怎么办？**
要点：先收窄再动手。做法是粗搜一轮后，把主题改写成 3~5 个可回答的子问题，并**明确写出不覆盖什么**。报告开头直接声明范围与时间边界（"截至 2026-09，仅覆盖开源方案"），这样"覆盖度"才有可衡量的基准。

## 3. 项目 B：文档问答系统（对应 L3）

### 3.1 需求与边界

**一句话需求：** 喂一批自己的文档，用自然语言提问，得到**带出处的答案**；答不出来时必须说"不知道"。

**用户是谁：** 团队内部成员（查制度、查接口、查产品文档）。**与第 08 章的区别：** 第 08 章你跑通了链路，这里你要把每一环**做完整并量化**——切片有对比实验、检索有混合与重排、答案有引用校验、范围外问题有拒答。

**成功标准：**

| 指标 | 目标 |
|---|---|
| Recall@5（检索层面） | ≥ 0.85 |
| 忠实度（答案被上下文支持的比例） | ≥ 0.90 |
| 引用准确率 | ≥ 0.90 |
| 范围外问题拒答正确率 | ≥ 0.90（误拒率 ≤ 5%） |
| P95 延迟 | ≤ 6 秒 |

**明确不做什么：** 不做跨语言检索、不做图片/扫描件 OCR、不做多用户权限、不做"帮我改文档"的写操作。

### 3.2 设计：把第 08 章的链路补完整

| 环节 | 第 08 章的做法 | 本项目要做的完整版 | 为什么必须补 |
|---|---|---|---|
| 切片 | 固定长度 / 按标题 | **结构切 + 三类特殊块规则**（表格、代码、跨页） | 表格和代码被腰斩后检索必错 |
| 召回 | 单路向量或单路 BM25 | **混合检索**：向量 + BM25，RRF 融合（k=60） | 向量对数字/编号/专有名词差，BM25 对同义改写差 |
| 重排 | 可选 | **必做**：粗排 top-20 → 重排 top-4 | 正确块排在第 15 位等于没召回 |
| 引用 | 让模型标 [n] | **生成后校验 + 伪引用过滤** | 模型会引用不存在的编号 |
| 拒答 | 没做 | **阈值 + 冲突 + 越界** 三种触发 | 不知道时说"不知道"是功能，不是缺陷 |

**切片策略怎么选（要有对比数据，不要凭感觉）：** 同一批文档、同一批 30 条问题，跑三档参数，看 Recall@5：

| 切片方式 | 参数 | Recall@5 | 平均块 token | 结论 |
|---|---|---|---|---|
| 固定长度 | 200 字 / overlap 40 | 0.62 | 145 | 块太碎，答案被切断 |
| 固定长度 | 400 字 / overlap 60 | 0.74 | 290 | 一般 |
| 固定长度 | 800 字 / overlap 100 | 0.71 | 580 | 噪声变多，成本翻倍 |
| **结构切 + 特殊块规则** | 标题层级 / 400 字兜底 | **0.88** | 330 | **采用** |

**这张表就是你面试时的"我做过实验"的证据。** 数字换成你实测的，但**必须真的跑过**——面试官只要问一句"800 字为什么反而降了"，编的人是答不上来的（答案通常是：块变大后，一个向量混了多个主题，语义被稀释）。

### 3.3 三个关键难点

**难点 1：多文档信息冲突。** 冲突有三种，处理方式完全不同：

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| **时效冲突** | 2023 版制度说 500 元，2025 版说 600 元 | 按元数据（版本/生效日期）取新的，并在答案里说明"依据 2025 版" |
| **范围冲突** | 国内差旅 600 元，海外按当地货币 | 先问清适用范围（或按问题里的地点线索过滤），两个都给出并标注适用场景 |
| **真冲突** | 两份文档对同一件事说法不一致 | **并列呈现 + 标注来源**，明确说"两份文档不一致，以 XX 为准请与文档负责人确认" |

**绝对不能静默选一个。** 静默选择等于让用户以为文中有共识，这是最危险的失败模式。实现上，让模型输出的结构多一个字段：`{"conflict": true, "sources": ["[1]", "[4]"], "note": "..."}`。

**难点 2：表格和代码块怎么办。** 这两类内容用同一套切片规则必错：

- **表格**：按行切，**每行都要重复表头**（`列名: 值 | 列名: 值` 的扁平化写法），并保留表格标题作为上下文前缀。这样"海外单晚上限是多少"才能在单行里找到答案。跨页表格要按表头做续接。
- **代码块**：**当成不可分的原子单元**，整块保留；切片时优先在函数/类边界断开；在 chunk 前缀里写明语言与函数名（`Python > def chunk_fixed`），检索时以词面为主（函数名、报错信息这类查询向量检索很弱）。
- 一个具体判断标准：如果一个 chunk 拿给人看，人看不出它属于哪个文档的哪一节，这个 chunk 就是不合格的。

**难点 3：问题超出文档范围时要说"不知道"。** 三种触发条件，写死在代码里而不是交给模型自由发挥：

```python
def should_refuse(question, hits, conflict):
    """拒答的三个机械触发条件。阈值要用评测集扫出来，不是拍脑袋。"""
    if not hits or hits[0]["score"] < 0.35:      # ① 检索最高分太低：根本没有相关内容
        return True, "文档中未找到相关内容"
    if conflict:                                  # ② 检索结果互相矛盾
        return False, "两份文档说法不一致"          # 不拒答，但要并列呈现
    if not is_in_scope(question):                 # ③ 问题类型越界（如"帮我写代码""今天天气"）
        return True, "我只回答本知识库范围内的问题"
    return False, ""
```

**阈值怎么定（这是本题的评估重点）：** 拿评测集里的 6 条范围外问题 + 20 条正常问题，把阈值从 0.20 扫到 0.50：

| 阈值 | 该拒的拒了 | 不该拒的拒了（误拒） | 结论 |
|---|---|---|---|
| 0.25 | 3/6 | 0/20 | 太松，编答案 |
| **0.35** | **6/6** | **1/20** | **采用** |
| 0.45 | 6/6 | 5/20 | 太严，用户体验崩了 |

**误报的代价是用户不再信任你，编答案的代价是用户被误导。** 两者都严重，所以要在评测集上同时看两个数字，选择平衡点。

### 3.4 评估：30 条评测集

**评测集构成（这是可复用的模板）：**

```json
{"id": "q01", "question": "海外出差住宿单晚上限是多少？", "type": "可答-单跳",
 "gold_docs": ["差旅制度.md"], "gold_chunks": ["差旅制度.md#3.2"],
 "gold_answer": "单晚不超过等值 8000 日元", "must_refuse": false}
```

| 题型 | 条数 | 考什么 |
|---|---|---|
| 可答 · 单跳 | 12 | 基础召回与引用 |
| 可答 · 跨文档 | 5 | 混合检索与融合是否有效 |
| 可答 · 含数字/编号 | 3 | BM25 是否在起作用（纯向量往往这里翻车） |
| 冲突题 | 4 | 是否并列呈现而不是静默选一个 |
| 范围外 | 6 | 是否拒答、误拒率 |

**三个必报指标（计算方式要写进 `evals/report.md`）：**

| 指标 | 公式 | 目标 |
|---|---|---|
| 召回率 Recall@5 | 检索 top-5 里含 `gold_chunks` 的问题数 / 可答题数 | ≥ 0.85 |
| 忠实度 Faithfulness | 答案句子中被上下文支持的比例（模型判定 + 抽 10 条人工校准） | ≥ 0.90 |
| 引用准确率 | 引用编号存在 **且** 指向 chunk 确实支持该句的比例 | ≥ 0.90 |

**加一个反指标防止自欺：** 拒答正确率与误拒率必须一起报。只报"拒答正确率 100%"（把所有问题都拒答）是刷分行为，加上误拒率就刷不了了。

### ⚠️ 常见坑

- **现象**：评测集是"我自己想的问题"，全是文档里的原句改写，指标漂亮但一上线就废。**怎么改**：问题必须写**口语化版本 + 真实用户会问的错别字版本**，并至少包含 5 条跨文档问题。
- **现象**：忠实度用模型自己判，分数虚高。**怎么改**：抽 10 条人工校准模型的判定，一致率 < 80% 就换判定 prompt 或改为人工。
- **现象**：文档更新后指标掉了，但不知道是哪一步。**怎么改**：索引带版本号，评测报告里记录 `index_version` 与 `model`，每次重跑留档（这正是第 12 章 trace 的用法）。
- **现象**：为了指标好看，把 chunk_size 调到 1500 让"答案总在里面"。**怎么改**：块越大检索越糊；要看的是**检索排名的位置**，不是"答案在不在上下文里"。

### 3.5 交付标准清单

- [ ] 索引构建脚本可重复执行：删库重跑，同一批文档产出同一份索引（块数、向量数一致）。
- [ ] 切片对比实验记录（上表四行，含真实数字与结论）。
- [ ] 混合检索 + RRF 融合 + 重排，每一步都能单独开关（用于做消融实验）。
- [ ] 30 条评测集 `evals/cases.jsonl` + 一键跑分脚本 + `evals/report.md`（含三个指标与 bad case 列表）。
- [ ] 拒答阈值扫描记录（0.25 / 0.35 / 0.45 三档，报拒答正确率与误拒率）。
- [ ] 5 条 bad case 的逐条分析：错在哪一环（加载/切片/召回/重排/生成），你改了什么，指标变化多少。
- [ ] README 的"已知限制"里写清表格跨页、扫描件、超范围问题的处理边界。

**验收问句**：你能否指出评测集里哪 3 条最难过？为什么难过？改了什么之后它们过了？

### 3.6 简历写法

**一句话：** 构建团队文档问答系统（混合检索 + 重排 + 引用校验 + 拒答策略），在 30 条自建评测集上 Recall@5 \_\_%、忠实度 \_\_%、引用准确率 \_\_%，范围外问题拒答率 100% 且误拒率 ≤ 5%。

**三个技术亮点：**
1. **切片策略经过实验对比**：固定长度三档 vs 结构切 + 表格/代码特殊规则，Recall@5 从 0.74 提到 0.88，并说明 800 字反而下降的原因（语义稀释）。
2. **混合检索 + RRF + 重排的三级漏斗**：向量 top-20 与 BM25 top-20 融合后重排到 top-4，解决"数字/编号类查询向量检索失效"的问题。
3. **可量化的拒答策略**：用评测集扫出 0.35 的阈值，在"该拒的拒了 6/6"与"误拒 1/20"之间取平衡，而不是凭感觉。

**可量化结果：** 320 页文档、1800 个 chunk、P95 延迟 4.2 秒、单次问答成本 0.004 元。

### 3.7 面试追问预演

**Q1：已经有向量检索了，为什么还要 BM25？**
要点：两者失败模式不同。向量擅长同义改写（"住宿上限"↔"单晚不超过"），但对数字、编号、专有名词常常失效（"8000 日元"和"6000 元"在向量空间里很近）；BM25 恰好相反。**要有证据**：评测集里"含数字/编号"那 3 条，用纯向量 Recall@5 明显低于混合检索。

**Q2：文档更新了怎么办？**
要点：分三步——① 增量索引（按文档 hash 判断是否重切，只重建变化的文档）；② 版本留存（旧 chunk 标记 `deprecated` 而不是立刻删，便于回查历史答案）；③ 更新后**重跑评测集**，防止"改了切片参数忘了同步"。如果允许,再补一句"冲突类问题在新旧版本共存期间用生效日期过滤"。

**Q3：幻觉怎么治？**
要点：分层面答——检索层（混合 + 重排，确保材料在里面）、生成层（prompt 强制"只依据资料回答 + 每句带引用"）、校验层（引用存在性 + 与原文的词面覆盖）、交互层（不确定就拒答或标注）。**别只说 prompt**，工程手段才是可复制的。

## 4. 项目 C：代码审查助手（对应 L4）

### 4.1 需求与边界

**一句话需求：** 读一个 git diff（或一段代码），**按风险排序**给出审查意见，每条都要有可执行的修改建议。

**用户是谁：** 提交 PR 的开发者（作为"提交前自查"）和 reviewer（作为"第一遍粗筛"）。**定位必须说清楚：辅助而非替代**——它的价值是把"明显的问题"提前拦掉，让人的注意力花在架构和业务逻辑上。

**成功标准：**

| 指标 | 目标 | 说明 |
|---|---|---|
| 检出率（真 bug） | ≥ 0.70（高危 ≥ 0.85） | 20 个 diff 里人工标注的真问题 |
| 误报率 | ≤ 1 条 / 每个干净 diff | 宁可少报也别乱报 |
| 建议可用率 | ≥ 0.60 | 建议能直接采纳（含 diff 或代码片段） |
| 排序质量 Precision@3 | ≥ 0.80 | 前 3 条里都是真问题 |
| 输出可解析率 | 100% | JSON 结构稳定，字段齐全 |

**明确不做什么：** 不做整体重构建议、不做风格/命名审查（那是 linter 的活）、不给"更好的架构方案"、不评价业务逻辑对错（它不知道需求）。

### 4.2 设计：大 diff 怎么喂、风险怎么分、废话怎么避免

**① diff 怎么喂进去——三层降级，先规则后模型：**

```
L0 规则过滤（不花 token）：跳过 lock 文件、生成代码、vendor/、二进制、
                          纯注释改动、纯格式改动（行尾空白/缩进）
L1 正常审查：单文件 hunk 级送入（改动行 + 上下文 3 行），单次 ≤ 8k token
L2 降级审查：diff > 2000 行或单文件 > 800 行时——
             ① 只审代码文件（.py/.js/.ts/.go/.sql/.java），跳过文档与配置
             ② 超限文件只送"函数签名 + 改动摘要"
             ③ 输出里显式声明"该 PR 过大，仅审查了 X 个文件的改动部分"
```

**关键判断：不要试图把整个 diff 塞进去。** 一次送 5000 行，模型会在中间部分"睡着"（第 07 章的 U 形曲线），而且 token 成本会失控。**按文件切分、并行审、最后合并排序**，比一次梭哈既便宜又准。合并时把同一文件同一行的意见去重，再按风险级别排序。

**② 风险分类——四类 + 每条意见的固定字段：**

| 类别 | 典型问题 | 例子 |
|---|---|---|
| **安全 Security** | 注入、硬编码密钥、越权、不安全反序列化、日志泄露敏感信息 | `cursor.execute("... " + user_id)`、`api_key = "sk-..."` |
| **正确性 Correctness** | 边界、空值、异常被吞、并发、off-by-one、资源未关闭 | `for i in range(len(a) - 1)` 漏最后一个；`except: pass` |
| **性能 Performance** | N+1 查询、循环内 IO、无界缓存、缺索引的全表扫描 | 循环里 `db.query(...)` |
| **可维护性 Maintainability** | 重复逻辑、魔法数、超长函数、无测试的高危改动 | 同一段校验逻辑抄了 3 遍 |

**每条意见必须是这个结构（缺字段直接判不合格）：**

```json
{"file": "app/order.py", "line": 42, "severity": "high", "category": "correctness",
 "evidence": "except: pass",                       // 原文片段，必须能在 diff 里找到
 "problem": "支付失败被静默吞掉，调用方以为下单成功",
 "suggestion": "-        except:\n-            pass\n+        except PaymentError as e:\n+            logger.warning(...)\n+            raise",
 "confidence": 0.82, "verify": "看 order_service.create 的调用方是否处理异常"}
```

**③ 怎么避免"什么都夸一遍"的废话输出——三条硬规则：**

1. **只报能指出具体行、能说清后果的问题。** 说不出"会怎样出错"的，一律不报。
2. **禁止风格意见**（命名、缩进、注释多少、有没有用列表推导式），除非项目里有明确的 lint 规则文件。
3. **条数上限 + 允许零结果。** 每份 diff 最多 5 条，按 `severity` 排序；没有真问题就输出 `"issues": []` 并附一句"未发现高危问题"。

**为什么这三条是硬规则？** 因为审查工具的成本不在生成本身，而在**人的注意力**。一份 20 条评论里有 15 条是废话的 review，人会直接关掉——那 5 条真问题也一起被忽略了。**误报率比检出率更能决定工具活不活得下去。**

### 4.3 三个关键难点

**难点 1：控制误报率。** 单靠"请谨慎判断"是没用的，要靠机制：

```
生成候选（一次调用，temperature=0.2）
    ↓
独立证伪（第二次调用，换个 system prompt：给你这条意见和代码，
         请试着证明它是错的；找不到反例才保留）
    ↓
置信度过滤（confidence < 0.6 直接丢弃）
    ↓
行号校验（line 必须落在 diff 的改动行范围内，否则丢弃）
```

四道筛子下来，误报通常能降一半以上。**多花的那次调用比"被人骂乱报"便宜得多。**

**难点 2：给可执行的修改建议，而不是"这里有问题"。**

| 不合格 | 合格 |
|---|---|
| "这里可能有并发问题" | "`self.count += 1` 在多线程下会丢更新；改用 `threading.Lock`，或换成 `itertools.count()`：`+        self.lock = threading.Lock()`" |
| "建议加错误处理" | "给出 try/except 的具体代码，并说明要捕获哪个异常、失败后返回什么" |
| "这个 SQL 可能有注入" | "把字符串拼接改成参数化查询，给出改后的 2 行代码" |

判断标准：**这条建议能不能直接复制粘贴到编辑器里？** 不能就重写。

**难点 3：输出要稳定可解析。** 做法：强制 JSON schema（字段名与枚举值写死在 prompt 里）+ 解析失败重试一次（附上报错信息）+ 校验通过才返回，失败则返回空结果并记录到 trace。**永远不要让下游收到半结构化文本。**

### 4.4 评估：20 个真实 diff

**测试集构建（这是本项目最费时间也最值钱的部分）：**

```
10 个含已知问题的 diff：从自己的仓库历史里挑（每个含 1~3 个真实 bug）
                       + 人工注入的漏洞（SQL 注入、硬编码密钥、吞异常）
10 个干净 diff：真实的小改动（重命名、加日志、补测试、文档更新）
标注：每行标注 bug 类型与严重级别 → evals/review_gold.jsonl
```

**指标计算：**

| 指标 | 公式 | 目标 |
|---|---|---|
| 检出率 | 命中的标注 bug 数 / 标注 bug 总数 | ≥ 0.70 |
| 误报率 | 干净 diff 上的意见条数 / 干净 diff 数 | ≤ 1.0 |
| 建议可用率 | 可直接采纳的建议数 / 建议总数（人工判） | ≥ 0.60 |
| Precision@3 | 前 3 条里真问题的比例 | ≥ 0.80 |
| 可解析率 | JSON 解析成功次数 / 运行次数 | 1.00 |

**三个必须记录的对比实验（面试的加分点）：** ① 单次调用 vs 双阶段（生成 + 证伪）：检出率降了多少、误报率降了多少（通常检出降 3~5 个点、误报降 40%+）；② 排序 vs 不排序：Precision@3 的变化；③ 大 diff 分片 vs 整块塞：成本与检出率对比（分片通常更便宜且更准）。

### ⚠️ 常见坑

- **现象**：助手满屏"建议增加注释""变量名可以更清晰"，用户三分钟后再也不看。**怎么改**：把风格类意见在代码里**硬过滤掉**（不是靠 prompt 求它别说），并加上条数上限。
- **现象**：误报太多，被同事吐槽"它连 `import` 顺序都要管"。**怎么改**：上双阶段证伪 + 置信度阈值；把过滤前后的误报率都记进报告，用数据说话。
- **现象**：审大 PR 时超时或漏审，输出里却看不出来。**怎么改**：降级时必须**显式声明**（"本次仅审查 12/47 个文件"），否则等于骗人。
- **现象**：模型引用了 diff 里不存在的行号，建议驴唇不对马嘴。**怎么改**：校验 `line` 落在改动行集合内，越界直接丢弃；`evidence` 片段必须在 diff 里能搜到。

### 4.5 交付标准清单

- [ ] `--mode review` 离线可跑：内置 1 个含 3 处真问题的 diff + 1 个干净 diff，跑完能对比两次输出。
- [ ] 规则过滤层独立可测：给定一个 diff，能列出被跳过的文件及原因。
- [ ] 输出 schema 固化 + 解析失败重试 + 行号/证据校验，三者都有对应代码。
- [ ] 20 个 diff 的测试集与标注文件，一键跑分输出检出率/误报率/Precision@3。
- [ ] 三个对比实验的结论（双阶段、排序、分片）写进 `evals/report.md`。
- [ ] 失败记录：至少 3 个漏报案例，逐个分析漏在哪一步（分片丢了？证伪阶段误杀？）。
- [ ] README 明确写"不审风格、不做架构建议、不评价业务逻辑"的边界。

**验收问句**：拿一个你自己写过的、含已知 bug 的历史 commit 喂进去，它找到了吗？没找到的话，你能说清是分片丢的、还是证伪阶段误杀的吗？

### 4.6 简历写法

**一句话：** 实现代码审查助手：解析 git diff 后按安全/正确性/性能/可维护性四类输出**可执行建议**，在 20 个真实 diff 上检出率 \_\_%、误报 0.6 条/PR、建议可用率 \_\_%。

**三个技术亮点：**
1. **双阶段审查（生成 + 独立证伪）**：第二次调用专门尝试推翻候选意见，配合置信度阈值（< 0.6 丢弃）把误报率降低约一半，代价是检出率下降 3~5 个点——这个取舍是有意为之。
2. **diff 的三层降级策略**：规则层零成本过滤（lock/生成代码/vendor），hunk 级分片审查，超大 PR 降级为"函数签名 + 改动摘要"并显式声明覆盖范围。
3. **结构化输出的强校验**：JSON schema + 行号必须落在改动行内 + `evidence` 必须能在 diff 中检索到，把"幻觉意见"挡在输出之前。

**可量化结果：** 20 个真实 diff（含 10 个干净样本），检出率 0.73、误报 0.6 条/PR、单 PR 成本 0.03 元、平均 11 秒出结果。

### 4.7 面试追问预演

**Q1：误报和漏报只能二选一，你选哪个？**
要点：**选"少误报"**，理由要讲成本结构——误报消耗的是人的注意力且会被迅速失去信任，漏报至少还有人工 review 兜底。然后是具体取舍：置信度阈值 0.6、双阶段证伪、条数上限 5、风格类硬过滤。**同时给出反指标**：只报误报会滑向"什么都不报"，所以检出率必须一起报（0.73），高风险问题单独要求 ≥ 0.85。

**Q2：怎么保证建议是可执行的？**
要点：结构化输出 + 硬校验。每条建议要么给 unified diff，要么给 ≥ 3 行可粘贴代码；写不出具体代码的候选意见必须降级为"待确认"或不报。再加人工抽检：从 20 个 diff 的输出里抽 20 条建议，逐条判断"能不能直接采纳"，把比例作为可用率指标。

**Q3：一个 3000 行的 PR 怎么办？**
要点：先过滤（跳过 lock/生成代码/vendor/纯格式改动），再按文件分片并行审，单文件超 800 行只送函数签名与改动摘要。**核心是显式降级与声明覆盖范围**，同时把"这次没审到什么"写进输出。更大规模时应该引导用户拆 PR——工具可以顺便提示"该 PR 建议拆分"。

## 5. 一份代码，三种模式

三个项目在工程上是**同一套骨架的三个配方**，所以做成了同一份代码（`AGENT_MOCK=1` 时无需 key、无需联网）：

```bash
cd code
AGENT_MOCK=1 python ch15_agent_app.py --mode research   # 项目 A
AGENT_MOCK=1 python ch15_agent_app.py --mode qa         # 项目 B
AGENT_MOCK=1 python ch15_agent_app.py --mode review     # 项目 C
AGENT_MOCK=1 python ch15_agent_app.py --mode all        # 三个都跑，打印横向对比表
```

**三种模式共用同一条流水线**：`输入 → 检索/解析 → 证据表 → 生成 → 校验 → 指标 → 输出 + trace`，只是每步的实现不同。底层统一复用 `code/common/`：`llm.py` 的 `load_env()` / `is_mock_mode()` / `chat()` / `count_tokens_approx()` / `estimate_cost()`，`tools.py` 的 `Tool` / `ToolRegistry`，`trace.py` 的 `Trace`——**接真模型只改 `chat()` 一处，控制流代码一行不动**。

| 模式 | 内置示例数据（离线可跑） | 校验环节 | 收尾指标 |
|---|---|---|---|
| `research` | 12 条假搜索结果 + 8 篇假页面（含 2 篇抓取失败） | 引用编号存在性 + 词面覆盖 | 来源数 / 引用准确率 / 编造率 |
| `qa` | 3 篇示例文档（含 1 张表、1 段代码、1 处跨文档冲突） | 引用校验 + 拒答触发 | Recall@5 / 忠实度 / 拒答正确率 |
| `review` | 1 个含 3 处真问题的 diff + 1 个干净 diff | 行号落在改动行 + 证据可检索 | 检出率 / 误报数 / 可用率 |

一次 `research` 模式的输出长这样（真实运行时数字来自你的数据）：

```text
========== [1/6] 主题解析 ==========
主题：MCP 协议解决了什么问题
子问题：3 个（先粗搜 8 条 → 生成大纲）

========== [2/6] 检索与去重 ==========
候选 12 条 → 去重掉 4 条（3 条 URL 重复、1 条正文相似度 0.87）
来源分层：T0=2  T1=4  T2=2  T3=0

========== [3/6] 抓取 ==========
成功 6 条，失败 2 条（403 Forbidden：example-blog.com；超时：slow-blog.io）→ 已记入 failures

========== [4/6] 证据抽取 ==========
抽出 14 条事实卡，平均每条 52 字，全部带原文片段与字符偏移

========== [5/6] 生成与校验 ==========
报告 936 字，引用 7 处
校验：编号存在性 7/7；词面覆盖不足 1 处 → 该句已删除

========== [6/6] 指标 ==========
来源数 6 / 引用准确率 6/6 = 1.00 / 编造率 0 处 / token 2841 / 估算成本 0.0031 元
已写入 traces/ch15_research.json
```

**跑通之后要做的三件事**（这才是"做过项目"的证据）：① 把 `chat()` 从 mock 切到真模型（脚本里只有一处分支），跑同一个主题对比两份输出；② 故意制造失败（断网、不存在的主题、3000 行假 diff），看降级与记录是否生效；③ 把任意一个指标改好 5 个百分点，**写下你改了什么、为什么**——这就是面试里"故障与优化"那段的内容。

## 本章小结

1. **Demo 与项目的差距是五件事**：配置管理、错误处理、日志、文档（含已知限制）、可复现性。每一项半小时就能补，不补就会在演示现场被问穿。
2. **项目 A 的灵魂是引用可追溯**：证据表存原文片段 + 字符偏移，生成后逐条校验（编号存在 + 词面覆盖 ≥ 0.35），禁止模型自己写 URL；"单一事实至少 2 个独立来源"。
3. **项目 B 的关键是把链路做完整并量化**：切片要有对比实验（0.74 → 0.88），检索要混合 + 重排，拒答阈值要用评测集扫（0.25/0.35/0.45），冲突要并列呈现而不是静默选择。
4. **项目 C 的核心是控制误报**：双阶段（生成 + 证伪）+ 置信度阈值 + 条数上限 + 风格类硬过滤；建议必须可直接粘贴；大 diff 走三层降级并显式声明覆盖范围。
5. **三个项目共用一个模式**：输入 → 证据 → 生成 → 校验 → 指标 → trace。**"校验 + 指标"这两步是练习与项目的分界线**，没有它们的系统只能叫 Demo。
6. **三个项目对应 L2/L3/L4**，简历写法、追问预演见 [[01-Raw/03-项目阶梯与能力对照表]] 与 [[02-Wiki/面试题库/03-项目表达与追问应对]]。

## 自测题

**1. 为什么研究助手里必须用"原文片段"做证据，而不是模型摘要？**

<details><summary>点击查看答案</summary>

因为引用校验要比对的是**原文**。如果证据存的是模型摘要，摘要过程中信息已经被改写，校验时"句子与证据的词面覆盖"就失去了意义——你比的是"模型的两次改写"，永远都像。正确做法：`quote` 字段只存原文切片（配 `span` 字符偏移便于回查），摘要另存一个字段给生成阶段用。

</details>

**2. 文档问答系统里，拒答阈值为什么必须用评测集扫出来？**

<details><summary>点击查看答案</summary>

因为拒答是**双目标**问题：阈值调高，范围外问题拒得干净但误拒正常问题；阈值调低则相反。实测中 0.25 时 6 条范围外只拒掉 3 条（在编答案），0.35 时 6/6 拒掉且只误拒 1/20，0.45 时误拒升到 5/20。这个平衡点依赖你的文档、切片、embedding 模型，**任何经验值都不能直接照搬**，只能在自己的评测集上扫。同时必须两个数字一起报，否则"全部拒答"也能拿满分。

</details>

**3. 代码审查助手为什么要加"证伪"这一步？代价是什么？**

<details><summary>点击查看答案</summary>

因为模型生成候选意见时倾向于"多报"（漏报不会被骂，误报会显得很努力），而误报消耗的是人的注意力——一份 20 条里 15 条是废话的 review 会被直接关掉。证伪是换一个独立上下文，专门尝试推翻候选意见（找不到反例才保留），配合置信度阈值过滤，实测能砍掉约一半误报。代价是多一次调用（成本上升）且检出率会掉 3~5 个点——这个取舍是刻意的：**少报好过乱报**，漏掉的高危问题还有人工 review 兜底。

</details>

**4. "从 demo 到项目"的五个差距里，哪一个最容易被跳过、后果最严重？**

<details><summary>点击查看答案</summary>

"已知限制"与"可复现性"最容易被跳过，后果也最严重。前者让使用者（和面试官）无法判断系统的适用边界，把工具用在它不该用的场景；后者让所有指标失去意义——同一评测集跑两遍结果差 10 个点，你就无法判断"这次改动到底有没有变好"。最小补救：README 里写满 3 条已知限制；评测脚本记录模型名、温度、索引版本，两遍差异 > 5% 就必须查原因。

</details>

**5. 三个项目共用"输入 → 证据 → 生成 → 校验 → 指标 → trace"这一条流水线，这条流水线的哪一步最能体现工程能力？**

<details><summary>点击查看答案</summary>

**证据与校验两步**。证据决定系统"能不能被追溯"（每条结论指向可回查的原文），校验决定系统"会不会骗人"（编号存在性、词面覆盖、行号范围、拒答触发）。生成只体现"会用 API"，证据与校验体现的是对失败模式的预判；指标与 trace 则把这两步的效果变成可比较的数字——没有它们，前两步做得好不好只能靠感觉。

</details>

## 结语与下一章

做这三个项目的过程，很像第一次把家里的电路接上配电箱：单独拉一根线点亮一盏灯不难，难的是让它们共用一个总闸、各自有保险丝、跳闸时你能马上知道是哪一路。**"输入 → 证据 → 生成 → 校验 → 指标 → trace"就是那条总闸**——三个项目换了三批数据和工具，但闸门的位置没变，所以出问题时你总有一个固定的地方可以先去看。能跑通靠的是把每一步写出来，能交付靠的是每一步都留下了可以复查的痕迹。

但请注意：这三个项目的题目是本章给你的，配方也是本章给你的。面试官的下一个问题通常是："如果让你自己定题目，你会做什么？为什么这么定？"——这考的就不是执行力，而是独立设计与取舍了。下一章是第 16 章 [[docs/第16章 毕业设计与面试]]：怎么用四步选题法从 8 个方向里挑一个能做完、能验证、能讲深的题目；怎么写出可量化的需求文档与技术方案（含替代方案对比）；四个里程碑怎么排；20 条评测集、失败分类、演示方式怎么准备；以及把这一切翻译成面试答案的六段式结构、追问应对框架与简历公式。配套代码 `code/ch16_graduation.py` 会直接生成你的毕设骨架——目录结构、README 模板、评测集模板、配置模板一次到位。
