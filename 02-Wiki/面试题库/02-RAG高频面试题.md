## 一、考什么：面试官的知识地图

RAG 是"看起来最简单、实际上最容易做成八股"的方向。面试官的分值分布如下——**最后两行决定你能不能拿到 offer**：

| 层次 | 大致占比 | 考察方式 | 典型问法 | 满分信号 |
|---|---|---|---|---|
| **基础认知** | 20% | 直接问概念与边界 | "为什么要 RAG？上限由什么决定？" | 说出"不改模型只改上下文"与"上限由召回决定" |
| **工程实现** | 30% | 问"你会怎么做" | "怎么切？Top-K 怎么定？怎么防引用幻觉？" | 报出具体参数区间（300–500 汉字 / Top-4~6） |
| **取舍判断** | 20% | 问"为什么不用 X" | "为什么不上微调 / 不用长上下文直塞？" | 说清被放弃方案的代价与适用条件 |
| **评估与故障** | 20% | 给现象问怎么查 | "召回了模型没用怎么办？" | 检索层与生成层**分开测量** |
| **生产问题** | 10% | 问运维与合规 | "文档更新了怎么办？多租户怎么隔离？" | 提到 pre-filter 与索引一致性监控 |

**RAG 面试的唯一分水岭：你会不会把"召回"和"生成"分开评估。** 做不到这一点的人，所有回答都只能停在"调调参数试试"。

## 二、概念题（Q1–Q14）

### Q1. "为什么需要 RAG？它到底改了什么？"

**考什么：** 是不是把 RAG 当成"更高级的搜索"。

**30 秒骨架：** ① RAG **不改模型，只改送进模型的上下文**——所以知识更新只需重建索引（分钟级），不需要训练；② 它解决三件事：知识的时效性、私有数据的接入、以及**可溯源**（能标出"这句话出自哪一段"）；③ 代价是每次提问都要付检索与拼接的成本，而且引入了新的失败面：召回错了，再强的模型也救不回来。

**加分点：** 指出"可溯源"这一条是微调给不了的——微调模型的答案说不清来源。 **⚠️ 扣分回答：** "RAG 就是让模型能查资料"——没有说明它改的是上下文，也没提代价。

### Q2. "RAG、微调、长上下文直塞，你怎么选？"

**考什么：** 三条路线的适用条件，这是 RAG 方向的第一道分水岭题。

**30 秒骨架：** ① 三条判据：知识**会变**且需要**引用** → RAG；需求是**稳定输出风格/格式**且标注数据充足 → 微调；材料少（< 5 万字）、变化少、延迟不敏感 → 长上下文直塞；② 关键澄清：**微调不擅长记事实**——会过时、不可溯源，它学的是风格、格式与判断方式；③ 三者不互斥，生产里最常见的是"RAG 供事实 + 少量示例或微调固定输出格式"；④ 决策依据是数据特征与更新频率，不是模型能力。

**加分点：** 说"知识更新频率是硬判据：文档每周改 3–5 处，微调就要重训，成本和周期都不成立"。 **⚠️ 扣分回答：** "微调效果更好"或"长上下文以后会取代 RAG"——两个都是没算账的结论。

### Q3. "RAG 的效果上限由什么决定？"

**考什么：** 知不知道优化的主战场在哪。

**30 秒骨架：** ① **上限由召回决定**——没被检索出来的内容，再强的模型也变不出来，这是 RAG 的第一性事实；② 可信度由**引用与拒答**决定，这两件事在链条的两端，必须**分开测量**；③ 工程上最容易翻车的反而是看起来最不"智能"的两处：**索引一致性**（文档改了索引没改）与**权限过滤**（越权检索）；④ 所以排错时第一动作是"定位坏在哪一环"，而不是凭感觉调参数。

**加分点：** 收尾一句"凭感觉调参的典型结局是：改到最后自己也不知道哪一版更好"。 **⚠️ 扣分回答：** "换个更强的 embedding 模型"——把上限问题窄化成模型选型。

### Q4. "embedding 的原理是什么？为什么它能表示语义？"

**考什么：** 是不是只会调 API 而不知道自己在用什么。

**30 秒骨架：** ① embedding 把文本映射成**稠密向量**，训练目标是让语义相近的文本在向量空间里距离更近（对比学习：正样本拉近、负样本推远）；② 因为是**学出来的相似度**而不是字面重合，所以"住宿能报多少"能匹配到"住宿标准"——这是它相对关键词检索的核心优势；③ 但它是**有限的压缩**：维度固定、有容量上限，所以会丢失精确符号（订单号、型号、缩写），这正是必须配 BM25 的原因；④ 选型时必须用**自己的评测集**对比，榜单任务的分布和你不同。

**加分点：** 提"有的模型要求给 query / passage 加不同前缀（`query:` / `passage:`），漏了会明显掉点"——这是只有真跑过的人才知道的坑。 **⚠️ 扣分回答：** "embedding 就是把文本变成向量，相似度高的就是相关的"——同义反复，没解释它为什么有效、以及为什么一定会漏。

### Q5. "为什么文档和查询必须用同一个 embedding 模型？"

**考什么：** 知不知道这条铁律，以及它的故障表现。

**30 秒骨架：** ① 不同模型的向量空间**不可比**——用 A 的坐标系查 B 的向量，结果全是噪声；② **最危险的是它不报错**，只表现为"效果突然变差"，很容易被误判成"模型变笨了"；③ 推论：模型名与版本必须写进**索引元数据**，并在 trace 里记录；换模型一定要重建索引；④ 顺带一条：模型与相似度度量必须匹配——用余弦就全库归一化，换内积或 L2 时索引参数与代码要同步改。

**加分点：** 把它归到"三种必须监控的漂移"里说（文档更新没重建、换模型没重建、权限变更没同步），显得你有体系。 **⚠️ 扣分回答：** "理论上要一致，实际影响不大"——这是会直接导致线上事故的误判。

### Q6. "相似度度量怎么选？余弦、内积、L2 有什么区别？"

**考什么：** 知不知道这三者不是"随便选一个"。

**30 秒骨架：** ① 余弦看**方向**（不受模长影响），内积同时受方向与模长影响，L2 看**欧氏距离**；② 归一化之后，余弦与内积、L2 的排序等价——所以"选哪个"很多时候取决于你的库与模型约定；③ 关键是**模型与度量要匹配**：模型训练时用什么度量，检索就跟着用什么；④ 实践建议：把向量归一化后统一用余弦，能省掉一大类"分数不可比"的麻烦。

**加分点：** 说"分数不可比是做混合检索时要面对的问题——向量相似度在 0–1，BM25 可能是 0–30，所以要归一化，而归一化本身就是一堆调参（这也是 RRF 的好处）"。 **⚠️ 扣分回答：** "都用余弦，大家都用余弦"——没回答"什么时候不该用"。

### Q7. "混合检索为什么有效？纯向量一定会漏什么？"

**考什么：** 知不知道向量检索的结构性缺陷。

**30 秒骨架：** ① 向量擅长**语义相近**，但会漏掉**精确符号**：订单号 `DP1002`、型号 `XPS-9370`、缩写、人名、专业术语——这些在向量空间里没有区分度；② BM25 恰好相反：字面精确匹配强、语义泛化弱；③ 两路并用几乎总是赚的，典型配比是**向量 Top-30 + BM25 Top-30 → 融合 → Top-10~20 → Rerank → Top-4~6 进 prompt**；④ 中文 BM25 要分词（`jieba` 等），零依赖兜底可以用 bigram（"报销标准"切成"报销/销标/标准"）。

**加分点：** 举那个经典反例：问"海外住宿上限"却召回"国内住宿标准"——语义很像、数字完全不同，纯向量分不出来，加 BM25 才能用"海外"这个精确词区分。 **⚠️ 扣分回答：** "向量检索已经够了，BM25 是旧技术"——不理解两者的互补关系。

### Q8. "RRF 的原理是什么？为什么不做加权融合？"

**考什么：** 知不知道 RRF 的价值在于"免调参"。

**30 秒骨架：** ① RRF（reciprocal rank fusion）= 对每个文档累加 `1 / (k + rank)`，`k` 常取 60，**只用排名不用分数**；② 为什么不做加权：向量相似度（0–1）与 BM25 分数（可能 0–30）**不可比**，加权前要先归一化，而归一化方案本身又是一堆要调的参数；③ RRF 的价值是**鲁棒**——换个模型、换批数据都不用重调权重；④ 代价是它丢掉了分数里的"置信度信息"（排第 1 是很确定还是勉强第 1，RRF 不区分）。

**加分点：** 说"我手写过 RRF，20 行不到，这也是我敢说'不需要引入库'的底气"。 **⚠️ 扣分回答：** "两个分数加起来除以二"——没意识到量纲不同，这是最常见的技术型扣分。

### Q9. "Rerank 为什么有效？"

**考什么：** bi-encoder 与 cross-encoder 的结构差异。

**30 秒骨架：** ① 召回阶段是 **bi-encoder**（query 与 doc 各自编码）——**能预计算**所以快，但两者没有交互，精度受限；② 重排阶段是 **cross-encoder**（query + doc 拼在一起编码）——**能看到两者的交互**所以精度高，但**不能预计算**，每条 5–50ms；③ 所以用两阶段：从万级里用便宜的召回挑出几十条，再用贵的重排挑出 5 条；④ **Rerank 救不回没召回的内容**——它只在候选集内重新排序，所以召回阶段的 K 要给足（常见 20–50）。

**加分点：** 指出"收益通常是三处里最立竿见影的——把'正确块排第 9'变成'排第 2'，直接改善生成质量"。 **⚠️ 扣分回答：** "Rerank 就是把结果重新排序"——没回答"为什么它能排得更准"。

### Q10. "为什么要做两阶段检索？只做一步不行吗？"

**考什么：** 成本与精度的取舍意识。

**30 秒骨架：** ① 一步精排意味着对全库做 cross-encoder——计算量不可接受；② 一步粗排意味着没有精细排序，正确块容易被 Top-K 截掉；③ 两阶段的本质是**用小成本拿到接近精排的效果**；④ 代价要算清：延迟从 1× 变成 1.5–2.5×，而且候选集大小直接决定延迟——**50 条 vs 20 条延迟差 2.5 倍**，所以要先测延迟预算再定 K。

**加分点：** 给出四档配置的量级：单路向量 Top-5（1×）→ 向量+BM25+RRF（1.2×）→ 加 Rerank（1.5–2.5×）→ 加三路查询改写（2–4×）。 **⚠️ 扣分回答：** "两阶段更准"——没提延迟成本，面试官会认为你没在线上跑过。

### Q11. "什么叫引用幻觉？"

**考什么：** 知不知道"看起来有引用"和"引用是真的"是两件事。

**30 秒骨架：** ① 两种形态：**编号越界**（答案里出现 `[7]` 但只给了 5 条资料）、**来源编造**（写"根据《员工手册》第 12 条"，资料里根本没有这句话）；② 关键点是这是**不需要人工标注就能测的指标**——校验编号是否存在、是否在范围内即可，比"答案对不对"便宜得多；③ 还有一个隐性形态：编号存在，但该句结论与所引块**没有字面依据**（张冠李戴），这个要做句子级校验才能发现。

**加分点：** 说"模型很爱写'根据《XX 制度》'——这是编造，不是引用；所以 prompt 里要明确只能引用资料编号，禁止提及外部来源名，并在校验层过滤"。 **⚠️ 扣分回答：** "加了引用就不算幻觉了"——把"有编号"当成"可信"。

### Q12. "什么情况下不需要向量数据库？"

**考什么：** 会不会为了上技术而上技术。

**30 秒骨架：** ① 规模 < 1 万块、单机、只读 → **内存 + NumPy 余弦**就够了（无持久化、无过滤、重启重建，但零依赖）；② 1 万–100 万且有过滤需求 → FAISS / Chroma / Qdrant 本地模式；③ 已有 PostgreSQL → **pgvector**（性能不如专用库，但复用现有备份与权限体系）；④ 亿级、多租户、强过滤 → Milvus / Qdrant 集群 / Elasticsearch。

**加分点：** 强调选型时最容易被忽略的一项是**过滤能力**——能否在检索时做 **pre-filter**（`tenant_id = X AND updated_at > Y`）；很多实现是"先取 Top-K 再过滤"，结果是"过滤后只剩 2 条"，**召回率被过滤层吃掉了**。 **⚠️ 扣分回答：** "直接上 Milvus，专业的事交给专业的库"——没有规模判断，成本意识为零。

### Q13. "什么情况下根本不该上 RAG？"

**考什么：** 这是比"怎么优化 RAG"更能体现判断力的一题。

**30 秒骨架：** ① 五类症状：问题是**聚合型**的（趋势、对比、总计）→ 该做 map-reduce 摘要或走长上下文；数据是**结构化表且能写 SQL** → Text-to-SQL，别把表格塞进向量库；知识库 **< 20 页且极少变** → 直接进 system prompt（配 prompt caching 更划算）；**没有评测集** → 先花 1 小时建 20 条，否则你无法判断 RAG 是否有效；用户期望**精确数字/计算** → 检索 + 工具计算，纯 RAG 会给一个"看起来对"的数；② 一句话：**RAG 擅长"在大量会变的知识里定位"，不擅长"通读与聚合"。**

**加分点：** 提"先花 1 小时建 20 条评测集"这个动作——它说明你的决策流程里评测在技术选型之前。 **⚠️ 扣分回答：** "所有知识问答都该上 RAG"——没有边界条件。

### Q14. "RAG 有哪些环节？哪一环最容易翻车？"

**考什么：** 有没有全链路视角，而不是只盯着向量库。

**30 秒骨架：** ① 两段串联：**离线索引**（加载 → 清洗 → 切片 → 向量化 → 存）与**在线查询**（改写 → 召回 → 融合 → 重排 → 组装 → 生成 → 校验）；② 最难的环节不是向量库，是**切片 + 召回**——它决定上限；③ 其次是**评估**（没有指标就无法优化）与**无答案时的拒答**（决定可信度）；④ 工程上最容易翻车的是**索引一致性**与**权限过滤**——两者都属于"不报错但后果严重"的类型。

**加分点：** 说"每一环都有独立的失败模式，所以排错必须先定位坏在哪一环——我会把 Hit@K 和 Faithfulness 分开测"。 **⚠️ 扣分回答：** "主要就是向量检索和生成两步"——把链条压缩到看不见故障点。

## 三、实现题（Q15–Q27）

### Q15. "中文文档怎么切？和英文的差别在哪？"

**考什么：** 知不知道英文的经验值不能照搬。

**30 秒骨架：** ① 中文经验值：`chunk_size` 取 **300–500 汉字**（约 200–500 token，视分词器而定），overlap **50–80 字**；英文那套 512 token 的经验**不要直接照搬**——中文字符的信息密度不同；② 默认起手式是**结构切分（按标题）+ 长度兜底（超长小节按递归切）+ 10%–15% overlap**；③ 目标是"**检索单元自足**"：块被单独送进模型时必须能读懂它是关于什么的，所以要把文档名 + 标题路径拼进块首；④ overlap 不是越多越好——它按比例放大索引体积与检索噪声。

**加分点：** 说"我是用评测集选的参数：400 字结构切比 800 字在 Recall@5 上高 17 个点，因为块太大语义被稀释"。 **⚠️ 扣分回答：** "按 1000 字切，简单省事"——没有依据，也没做过对比。

### Q16. "怎么判断切片质量好不好？"

**考什么：** 有没有可量化的判断方法，而不是肉眼看两块。

**30 秒骨架：** ① 最直接的方式：用评测集看 **Hit@K / Recall@K**，切片改了指标有没有动；② 看**命中的块是否完整**——打印 gold chunk 原文，看答案是被切在块尾还是块首（跨块就是切坏了）；③ 看**块是否混主题**——一个块里塞了两件事，检索到它反而干扰生成；④ 检查关键结构是否被破坏：表格有没有表头、代码有没有缩进与上下文、块首有没有带上它所属的标题路径。

**加分点：** 说"我会固定 20–50 条样本，做'只改切片'的单变量对比——一次只改一个变量，不然涨了也不知道是谁的功劳"。 **⚠️ 扣分回答：** "看一下块的长度是不是均匀"——长度均匀不代表语义自足。

### Q17. "表格和代码块怎么处理？"

**考什么：** 知不知道这两类是检索垃圾的重灾区。

**30 秒骨架：** ① **表格必须整块保留**，并补一行表头说明（"下表为国内差旅住宿标准，单位：元/晚"）——被切碎的表格是检索垃圾，模型会拿没有表头的数字乱配对；② 超长表格按行切，但**每块都要带表头**；③ **代码按语法单元切**（函数/类），块首带上文件路径与依赖导入信息；④ 结构化数据能查库就别进向量库——Text-to-SQL 比把表塞进向量库准得多。

**加分点：** 提"表格还可以额外建一路'表格专用检索'——把表格转成行级自然语言再索引，查数值型问题命中率明显更高"。 **⚠️ 扣分回答：** "统一按字符数切，表格也算文本"——这是最容易导致"答案数字正确但对应关系错"的做法。

### Q18. "向量库怎么选？"

**考什么：** 会不会按"你真正会遇到的约束"来排，而不是按名气。

**30 秒骨架：** ① 按规模与过滤需求排序：< 1 万块用内存 + NumPy；1 万–100 万用 FAISS / Chroma / Qdrant；已有 Postgres 用 pgvector；亿级、多租户、强过滤用 Milvus / Qdrant 集群；关键词与向量同等重要用 Elasticsearch；② **过滤能力是最容易被忽略的一项**——确认你的库支持 pre-filter（或分区索引），否则"先取 Top-K 再过滤"会把召回率吃掉；③ 混合检索能力也要看：ES 原生 BM25 + 向量，是最省事的混合方案；④ 选型结论要写清"为什么不选另一个"。

**加分点：** 说"我有一次就是因为库不支持 pre-filter，多租户场景下过滤后只剩 2 条，最后换库才解决"。 **⚠️ 扣分回答：** "用 Milvus / 用 Pinecone，因为它最火"——没有约束分析。

### Q19. "召回不足怎么排查？按什么顺序动手？"

**考什么：** **这是 RAG 最核心的一道实现题**，考你的动手顺序。

**30 秒骨架：** ① **先建评测集测 Recall@K**——没有基线你无法判断任何改动是否有效；② 查切片对不对（命中的块是否完整、是否混主题）；③ 加**混合检索**（向量 + BM25 + RRF）——这是性价比最高的一步；④ **查询改写**（多查询 / HyDE）跨越"用户口语"与"文档术语"的鸿沟；⑤ 上 **Rerank** 并调 K；⑥ 换 embedding（**务必重建索引**）；⑦ 元数据过滤与分区。

**加分点：** 强调"顺序很重要——先切片后检索再重排，因为 Rerank 救不回没召回的，换 embedding 是最贵的一步要放最后"。 **⚠️ 扣分回答：** "把 Top-K 调大"——先不说它会让噪声进上下文，它根本没解决"没被召回"这件事。

### Q20. "Top-K 怎么定？"

**考什么：** 知不知道 Top-K 本质是上下文预算问题。

**30 秒骨架：** ① 没有通用最优值，必须用评测集自测；② 预算公式：`Top-K × 平均块长度 + prompt 模板 ≤ 上下文预算 × 0.5`——**留一半给历史与输出**；③ K 太小会漏（正确块在 Top-10 之外），K 太大会让噪声进上下文，反而降低生成质量（"召回了但模型没用"常常就是 K 太大导致的）；④ 生产常用分层：召回 K 给足（20–30），Rerank 后只留 **Top-4~6** 进 prompt。

**加分点：** 说"Rerank 候选集从 50 降到 20 是延迟优化的常规动作，但降之前要先测召回有没有掉"。 **⚠️ 扣分回答：** "K=5，论文里都是 5"——没有预算计算，也没提噪声问题。

### Q21. "查询改写怎么做？HyDE 和多查询怎么选？"

**考什么：** 知不知道改写的适用场景与代价。

**30 秒骨架：** ① 改写的目的是跨越"用户口语 ↔ 文档术语"的鸿沟（用户说"住宿能报多少"，文档写"住宿标准"）；② **多查询**：生成 3–5 个不同角度的查询各自检索再 RRF 融合，适合表述模糊、单一措辞召回不稳；③ **HyDE**：先生成"假想答案"再用它检索，适合短查询与术语密集型文档，**风险是假答案跑偏会把检索带偏**；④ **退步提问**：把具体问题抽象成更一般的问题（"周五出差三天能报多少" → "差旅报销规则"），常与原查询合并检索；⑤ 别忘了一条更省的：**改写结果按 query 哈希缓存**——同类问题在客服场景重复率高。

**加分点：** 说"改写是检索次数 ×N，但检索远比生成便宜，所以这笔账通常划算"。 **⚠️ 扣分回答：** "让模型把问题改写得更清楚一点"——没有具体手法，也没提代价。

### Q22. "怎么让回答带引用？"

**考什么：** 引用是设计出来的，不是求模型求出来的。

**30 秒骨架：** ① 组装时给每条资料编号，格式为 `[编号] + 来源标题 + 元数据`，**资料在前、问题在后**；② prompt 里要求"每个结论必须带编号引用"，并明确**只能引用资料编号，禁止提及外部来源名**；③ 引用粒度越细越可信：块级 → 句子级，代价是校验成本（客服/法务类场景值得做句子级）；④ 展示层要做二次校验（防止跨租户的块 id 被拼进上下文）。

**加分点：** 提"去重（同一文档相邻块重复）与去噪（相似度过低的块宁可不给）也是引用质量的一部分——把不相关的资料喂进去，等于让模型从噪声里挑真相"。 **⚠️ 扣分回答：** "prompt 里让它标注来源就行"——模型会编来源，没有校验层等于没做。

### Q23. "怎么防引用幻觉？"

**考什么：** 有没有可执行的校验机制。

**30 秒骨架：** ① 三道校验：**编号存在 → 编号在本次范围内 → 被引原文能在块里找到依据**；② 前两道是纯代码断言（越界即判失败并重试一次），第三道做**句子级**校验：把答案拆句，检查每句能否在被引块中找到词面依据（关键词重合，离线可跑零依赖）；③ 校验不通过时的降级：重试一次，仍不通过就降级为"未收录"；④ 把"**引用不可核验率**"作为可监控指标——它不需要人工标注就能统计。

**加分点：** 直接给出可运行的实现思路：`validate_citations(answer, cited_ids, hits)` 返回问题列表，这个函数就是你的护栏。 **⚠️ 扣分回答：** "让模型自己检查引用是否正确"——用同一个概率模型检查自己的幻觉，不构成防线。

### Q24. "怎么让模型在该说'不知道'的时候说'不知道'？"

**考什么：** 拒答是一个路径设计，不是一个愿望。

**30 秒骨架：** ① **最可靠的做法是短路**：最高相似度低于阈值时直接回"未收录"，**不调用生成模型**——比让模型自己判断更可靠也更便宜；② prompt 里给拒答 few-shot，并明确输出格式（"资料中未收录，已检索范围：XX"）；③ 生成后校验：答案中的数字/事实有没有资料依据；④ 评测集必须包含 `must_refuse` 用例，把"该拒答率"作为上线门槛指标。

**加分点：** 说"我会同时盯着两个方向——'该拒答却硬答'是可信度事故，'能答却误拒'是可用性事故，阈值要在这两者之间选，我自己的数据上阈值 0.35 时误拒率 ≤ 5%"。 **⚠️ 扣分回答：** "在 system prompt 里写'如果不知道就说不知道'"——模型不知道"自己不知道"，它只有相似度分数。

### Q25. "多文档冲突（新旧制度同时被召回）怎么办？"

**考什么：** 数据治理意识，而不只是检索技巧。

**30 秒骨架：** ① 现象：答案给出"600 元"（旧版）或摇摆不定地列出两个数字；② 定位：检查召回结果里是否有同一主题的多份文档，比较 `updated_at` / 版本号；③ 解决分两层——**检索层**用元数据按"生效中"过滤，**生成层**在 prompt 里明确"以最新版本为准（按 updated_at）"并要求标注适用版本；④ 从源头治理：旧文档下线或打 `deprecated` 标记——**别把冲突留给模型去猜**。

**加分点：** 说"冲突无法过滤时，我会在答案里显式呈现差异并注明各自版本，而不是替用户选一个"。 **⚠️ 扣分回答：** "让模型自己判断哪个新"——模型看不到时间戳的语义，除非你把它放进上下文。

### Q26. "怎么评估 RAG？"

**考什么：** **是否把检索与生成分开测**——这是 RAG 面试的核心分水岭。

**30 秒骨架：** ① **分层测**：检索指标（Recall@K / Hit@K / MRR）与生成指标（Faithfulness 忠实度 / 引用准确率 / 拒答准确率）**分开测量**；② 分开的理由是可以立刻定位问题：`Hit@K` 正常而 `Faithfulness` 低 → 问题在组装或生成，不在检索；③ 评测集 20–50 条，覆盖**事实型、多跳、无答案、易混淆**四类；④ bad case 四类归因（切片坏 / 未召回 / 召回未用 / 瞎编）；⑤ 上线后把线上 bad case 回流，改一次跑一次，指标存下来形成对比。

**加分点：** 说"'答案听起来对'是幻觉的重灾区，不是质量指标——所以我要的是可核验的指标，而不是感觉"。 **⚠️ 扣分回答：** "人工看几十个问题，觉得答得不错"——没有指标，也没有分层。

### Q27. "怎么建 RAG 评测集？bad case 怎么分类？"

**考什么：** 评测集的来源与维护方式。

**30 秒骨架：** ① 从**真实问题**里抄，不要自己编——自己编的题带着你的偏见，且分布与真实请求不一致；② 四类必须覆盖：事实型（单块能找到）、多跳（需要两块拼）、无答案（`must_refuse`）、易混淆（近义条款）；③ 每条要有**可机械判定的判据**（标准答案要点 / 必须引用的块 id），并由没参与设计的人来写判据，防自证；④ bad case 四类归因：**切片坏**（gold chunk 被切断）、**未召回**（gold 不在 Top-K）、**召回未用**（gold 在 Top-K 但答案没采纳）、**瞎编**（资料里根本没有）；⑤ 每次修好的失败样本固化为回归样本。

**加分点：** 说"20 条的作用是回归与归因，不是统计显著性——它能在改动时立刻告诉你变差了没有"。 **⚠️ 扣分回答：** "用公开数据集就行"——公开数据集的分布和你的业务不同，且不覆盖你的私有术语。

## 四、取舍题（Q28–Q35）

### Q28. "四种切片策略怎么选？"

**考什么：** 会不会按文档结构选，而不是一档参数打天下。

**30 秒骨架：** ① 四档对照：**固定长度**（保真度低、成本最低，适合无结构纯文本与快速验证）、**递归切分**（按 `\n\n` → `\n` → 句号逐级回退，通用默认）、**结构/语义切分**（按 Markdown 标题 / HTML 标签 / 代码函数，保真度高，适合有层级的文档）、**父子切片**（小块检索、大块喂模型，保真度最高但存两份）；② 默认起手式：结构切分 + 长度兜底 + 10%–15% overlap；③ 父子切片专治"答案依赖上下文"的场景，代价是存储与 token 成本上升；④ 选完必须用评测集验证。

**加分点：** 说"最关键的动作是**给 chunk 补上下文**——把文档名与标题路径拼进块首，让孤立的块自解释"。 **⚠️ 扣分回答：** "用递归切分，这是最佳实践"——没有文档形态判断。

### Q29. "向量检索、BM25、混合检索，怎么选？"

**考什么：** 知不知道什么时候纯向量够用。

**30 秒骨架：** ① 纯向量适合：知识库是自然语言叙述、没有大量编号与专有名词；② 出现以下任一信号就该上混合：查询里有订单号/型号/人名/缩写、用户会用文档里的精确术语、召回过"语义很像但答案是另一个"的块；③ 混合的代价主要是工程复杂度（要多维护一路索引、要处理分词、要做融合），延迟只增加约 20%；④ 中文场景记得加分词或 bigram 兜底。

**加分点：** 说"混合检索几乎总是赚的——因为它补的是向量的结构性缺陷，不是调参能解决的"。 **⚠️ 扣分回答：** "上混合检索，越多路越好"——路数多了融合噪声也大，且没算延迟与维护成本。

### Q30. "要不要上 Rerank？"

**考什么：** 收益与延迟的量化取舍。

**30 秒骨架：** ① 收益：把"正确块排第 9"变成"排第 2"，直接改善生成质量，是三处优化里最立竿见影的；② 代价：自建 cross-encoder 吃 GPU/CPU 与延迟，API 版按 token 计费，延迟从 1× 涨到 1.5–2.5×；③ 判断依据：**先测延迟预算再决定候选集大小**——50 条 vs 20 条延迟差 2.5 倍；④ 不要上的场景：知识库很小（几百块）、延迟要求极严（< 1s）、召回 K 本来就小到没有重排空间。

**加分点：** 说"Rerank 救不回没召回的——如果 recall 本身就低，先把混合检索做上，别急着加重排"。 **⚠️ 扣分回答：** "Rerank 效果好，直接加上"——没提延迟与计费。

### Q31. "查询改写要做几种？"

**考什么：** 会不会克制——改写是拿钱和时间换召回。

**30 秒骨架：** ① 按场景选：**多查询**适合表述模糊（检索次数 ×N）；**HyDE** 适合短查询与术语密集型文档；**退步提问**适合"具体→一般"的抽象需求；**关键词抽取**最简单，常与向量路并联；② 常见组合是"原查询 + 2 路改写"共三条检索线，延迟 2–4×；③ **先上缓存**：同类问题在客服场景重复出现，改写结果按 query 哈希缓存命中率高得惊人；④ 改写的副作用要说清：改过头会丢关键限定词（"海外"被"概括"掉，召回就跑到国内标准上去了）。

**加分点：** 说"改写时我会显式要求保留限定词，而不是让模型自由'概括'"。 **⚠️ 扣分回答：** "把所有改写手法都上"——延迟 4×、成本翻倍，收益递减。

### Q32. "chunk_size 到底取 300 还是 800？"

**考什么：** 有没有做实验的习惯。

**30 秒骨架：** ① 没有通用最优值，必须用评测集自测——**这也是这道题唯一正确的开场**；② 中文常见起点是 300–500 汉字 + 10%–15% overlap；③ 用"答案要求的最小上下文"倒推：FAQ 短、手册长，同一系统里不同文档类型可以不同参数；④ 经验方向：块太大 → 语义被稀释、噪声增多、命中位置不精确；块太小 → 上下文不完整、跨块答案拿不到。

**加分点：** 给一组自己的数字："我用同一批 30 条问题扫了三档参数，400 字结构切 Recall@5 比 800 字高 17 个点，比 200 字高 9 个点。" **⚠️ 扣分回答：** "500 是经验值"——经验值不是你的数据，面试官要的是你的方法。

### Q33. "语义缓存该不该开？"

**考什么：** 知不知道语义缓存的答错风险。

**30 秒骨架：** ① 它能显著提高命中率，但**有答错的风险**——相似但答案相反的问题会命中（"如何开启自动续费" vs "如何关闭自动续费"）；② 时效性问题（股价、库存、订单状态）**禁止**走语义缓存；个性化问题必须把用户/租户标识放进 key；③ 命中后要**标注**（"这是 3 分钟前的相同问题答案"），不能静默；④ 结论：只在"答案稳定、错了代价小、可标注"的场景开；**会执行动作的入口不该用它**。

**加分点：** 对比说"前缀缓存与工具结果缓存是必做且无正确性风险，语义缓存是唯一需要权衡正确性的那一层"（前缀缓存命中部分输入费降 5–10 倍）。 **⚠️ 扣分回答：** "开啊，能省很多钱"——没提答错风险，这在客服/法务场景是致命回答。

### Q34. "拒答用'相似度阈值短路'还是'让模型自己判断'？"

**考什么：** 知不知道哪一层做决策更可靠。

**30 秒骨架：** ① 推荐**阈值短路优先**：最高分低于阈值直接回"未收录"，不调用生成模型——更可靠、更便宜、延迟更低；② 让模型自己判断的问题：模型只能看到你给的资料，它没有"资料库里还有没有别的"这个信息，容易过度自信；③ 但阈值不能只用一个数：可以组合"最高相似度 + 命中块数量 + 是否有 BM25 精确命中"；④ 阈值要靠评测集扫出来，两个方向都要看——**该拒答率**与**误拒率**。

**加分点：** 说"我把阈值扫出 0.35，误拒率 ≤ 5%；这个数和样本量有关，换数据要重扫"。 **⚠️ 扣分回答：** "模型更智能，让它自己判断就行"——把可靠性与成本一起交出去。

### Q35. "文档更新用增量还是全量重建？"

**考什么：** 索引运维意识。

**30 秒骨架：** ① 常规更新走**增量**：以 `doc_id` 为单位"删旧块 + 写新块"（delete by metadata），用内容哈希（`sha1(text)`）判断是否需要重算向量——全量重建在大库上期间不可用且成本高；② **切块规则一旦变更**（chunk_size、切分方式），所有块 id 都会变，这类变更要当成一次全量重建来发布：**双索引 + 切换**；③ 权限/租户元数据变更也必须同步到索引，否则会越权；④ 加监控：**文档变更事件数与索引变更事件数的比值应接近 1:1**。

**加分点：** 说出三种必须监控的漂移：文档更新没重建（答案引用旧制度）、换 embedding 没重建（检索整体退化且不报错）、权限变更没同步（越权检索，最严重）。 **⚠️ 扣分回答：** "每天凌晨全量重建一次"——没算成本，也没处理切块规则变更与权限同步。

## 五、故障排查题（Q36–Q43）

### Q36. "召回了但模型没用，怎么排查？"

**考什么：** 会不会把"检索指标"和"生成指标"分开看。

**30 秒骨架：** ① 定位动作：`Hit@K` 正常而 `Faithfulness` 低 → 问题在**组装或生成**，不在检索；② 打印实际送进模型的 prompt 片段，确认资料没有被截断或被 history 挤掉（**这是最常见的原因**）；③ 常见修法：最相关的块放**最前面**并加显式标注（"以下资料与问题最相关"）、要求每个结论带编号引用、**降 K**（把噪声块去掉，模型更容易专注）、prompt 里加"若资料与问题无关就忽略它"；④ 别忘了查 Lost in the Middle——资料在中间位置时利用率会下降。

**加分点：** 说"我会做一次 5 分钟就能验证的对照实验：把同一条资料分别放开头/中间/结尾，看答案是否变化"。 **⚠️ 扣分回答：** "换个更强的模型"——先用大炮解决一个组装问题。

### Q37. "答案跨块被切断（切片切坏了）怎么定位？"

**考什么：** 有没有从 gold chunk 的边界入手。

**30 秒骨架：** ① 现象："我周五出差三天能报多少"需要"住宿标准"+"天数规则"两块，但两块各含一半信息；② 定位：看 gold chunk 的原文边界——答案被切断在块尾还是块首；对比不同切片参数的 `Hit@K`；③ 修法：增大 overlap（50–80 字）、按标题/段落切而不是按字符硬切、**父子切片**（小块检索、命中后把父块即完整小节喂给模型）、检索命中后**拼接相邻块**（`position ± 1`）再送模型；④ 修完重跑同一批评测样本确认。

**加分点：** 说"'拼接相邻块'是成本最低的一招——不改索引，只在组装阶段加逻辑"。 **⚠️ 扣分回答：** "把 chunk_size 调大"——掩盖问题且引入语义稀释。

### Q38. "表格被切碎，模型读出错的数据，怎么办？"

**考什么：** 认不认得"检索垃圾"这个类别。

**30 秒骨架：** ① 现象：检索到的是"金额（元）| 城市"这种没有表头的残片，模型据此给出错误的对照关系；② 定位：打印命中的 chunk 原文，看表格是否缺表头、代码是否缺缩进与上下文；③ 修法：表格做成**一个块**（超长按行切但每块都带表头）、块首加自然语言描述（"下表是海外差旅住宿标准，单位为当地货币/晚"）、代码按函数/类切并带文件路径；④ 结构化数据额外建一路"表格专用检索"（把表格转成行级自然语言）。

**加分点：** 说"这类问题在评估里表现为'数字对但配错行'——比完全答错更难发现，所以我会专门为表格类文档建一组评测样本"。 **⚠️ 扣分回答：** "把表格转成 markdown"——转了格式但没解决"块被切开"这个根因。

### Q39. "相似但错误的召回（问海外住宿却召回国内标准）怎么办？"

**考什么：** 知不知道这是 embedding 的分辨率极限。

**30 秒骨架：** ① 定位：看 Top-K 的相似度分布——如果正确块与错误块分数接近（差距 < 0.02），说明 embedding 分辨不出这个维度，**需要外部信号**；② 三个修法：加 **BM25 混合**（"海外"是精确词，词面检索能区分）、上 **Rerank**（cross-encoder 对这种细粒度差异更敏感）、加元数据过滤器（地域/产品线）；③ 检查查询改写有没有把限定词"概括"掉——改写时要求显式保留关键区分词；④ 验证：改完看这类样本的 Hit@1 有没有提升。

**加分点：** 用"分数差距 < 0.02"这个具体判据说明你不是靠感觉判断的。 **⚠️ 扣分回答：** "换个大模型/换个 embedding"——没先确认问题出在分辨率还是出在缺少精确匹配通道。

### Q40. "制度昨天改成了 800，今天答的还是 600，怎么查？"

**考什么：** 索引一致性的排查能力。

**30 秒骨架：** ① 定位：对比文档 `updated_at` 与索引构建时间，检查更新流程有没有真的触发重建；② 检查三种漂移之一：文档更新了索引没重建（答案引用旧制度）；③ 修法：内容哈希（`sha1(text)`）判断是否需要重算向量、更新走"删旧块 + 写新块"的增量路径、加监控（文档变更事件与索引变更事件的比值应接近 1:1）；④ 变更较大时双索引发布 + 切换。

**加分点：** 说"我会在评测集里保留一条'版本敏感'的样本（问同一个数字），这样下次索引没更新，回归测试就会红"。 **⚠️ 扣分回答：** "重新建一次索引"——治标，且没解释为什么没触发更新。

### Q41. "越权检索（A 部门问到 B 部门文档）怎么防？"

**考什么：** **这是 RAG 里最严重也最常考的安全题。**

**30 秒骨架：** ① 原则：权限过滤必须在**检索层**用元数据 **pre-filter 强制注入**（`tenant_id` / `acl`），**绝不能靠 prompt 约束**——这是数据隔离，不是提示工程；② 索引元数据必须与权限系统同步，包括权限变更的增量更新；③ 引用与结果展示做二次校验（防止跨租户的块 id 被拼进上下文）；④ 把"用低权限账号构造敏感查询"的对抗测试纳入回归；⑤ 越权属于事故级别，必须有审计日志。

**加分点：** 强调"很多实现是'先取 Top-K 再过滤'，这不仅是召回率问题，还可能把不该看到的块带进日志——所以 pre-filter 是安全要求，不只是性能要求"。 **⚠️ 扣分回答：** "在 system prompt 里说明用户只能看自己部门的数据"——一句话就会被面试官问穿。

### Q42. "加了 Rerank 之后延迟到 3–5 秒，怎么优化？"

**考什么：** 分段计时与延迟预算意识。

**30 秒骨架：** ① 先**分段计时**（改写 / 向量召回 / BM25 / 融合 / Rerank / 生成），找出最大头——不定位就优化等于猜；② 常规动作：两路召回**并行**执行、改写结果缓存、Rerank 候选集从 50 降到 20（延迟差 2.5 倍）、embedding 批量与本地化（避免跨网调用）；③ 感知层面的动作：首屏流式输出生成结果、检索阶段给"正在检索…"的反馈——**这一步不减少时间但显著改善体感**；④ 最后才考虑换模型或上更快的索引。

**加分点：** 说"我会先看它是 TTFT 慢还是整体慢——Agent 侧的 P99 由最慢一步 × 步数决定，RAG 侧主要是检索链条的长度"。 **⚠️ 扣分回答：** "把 K 调小"——可能直接伤到召回，且没做分段计时。

### Q43. "知识库里没有的问题，模型硬答，怎么办？"

**考什么：** 拒答路径的设计，与 Q24 是同一机制的不同问法。

**30 秒骨架：** ① 现象：问"公司团建预算"，文档里没有，模型按"一般公司做法"编了个数字；② 定位：看评测集里 `must_refuse` 用例的通过率，线上统计"无资料问句"的答案率；③ 修法按优先级：相似度阈值短路（不调用生成）→ prompt 里给拒答 few-shot → 生成后校验答案中的数字/事实有没有资料依据；④ 把线上"该拒答却硬答"的样本回流评测集。

**加分点：** 说"拒答要输出**已检索的来源范围**（'已检索：差旅制度、报销手册，未收录团建相关内容'）——用户知道系统真的找过了，而不是敷衍"。 **⚠️ 扣分回答：** "在 prompt 里加一句'不确定就不要回答'"——没有阈值、没有校验、没有指标。

## 六、压力题（Q44–Q45）

> RAG 方向的压力题几乎都围绕"RAG 会不会被取代"。**答法只有一条：不要防守，要把问题重新定义成"它解决什么、长上下文解决什么"。**

### Q44. "我们直接用长上下文替代 RAG 了，你怎么看？"

**考什么：** 会不会为了捍卫 RAG 而硬撑；以及有没有算过账。

**30 秒骨架：** ① 先承认它对的部分："材料少、变化少、延迟不敏感的场景，长上下文直塞确实更简单——知识库不到 20 页、配 prompt caching 也很划算，这种情况我不会上 RAG"；② 再指出它不解决的：**100 万字知识库每次全塞的成本随长度线性上涨**、知识每天更新就要重新组织输入、**"这句话出自哪"的溯源成本高**、多租户权限靠应用层裁剪而 RAG 有成熟的元数据过滤；③ 给对照结论：长上下文解决"一次读懂少量材料"，RAG 解决"在大量会变的知识里定位"——**两者组合是常态**（RAG 定位 + 大窗口读完整章节）；④ 最后给判据：**看你的知识是"会变的大量知识"还是"固定的少量材料"**。

**加分点：** 补一句"长上下文在**全局聚合**（总结整份年报趋势）上确实比 RAG 强——因为召回是局部视角，这一点我会主动承认"。 **⚠️ 扣分回答：** "长上下文成本太高，所以还是 RAG"——只谈成本不谈能力边界，显得在保卫自己的技术栈。

### Q45. "模型能力越来越强，RAG 是不是快被淘汰了？"

**考什么：** 判断力与行业视角，不是知识点。

**30 秒骨架：** ① 模型变强改变的是**生成质量的下限**，改变不了两件事：**私有数据模型不知道**、**答案必须可溯源**——这两件恰好是 RAG 的核心价值；② 反过来，模型变强确实在削弱 RAG 的一部分价值：召回容错变高（块切得糙一点模型也能读懂）、不需要那么激进的 Rerank——所以 RAG 的重心在从"检索技巧"往"数据治理与评估"移动；③ 真正的趋势是**职责重组**：模型负责理解与生成，检索负责"在会变的知识里定位 + 权限 + 溯源"；④ 收尾给一个判断依据："只要企业数据在增长、在变化、且需要审计，这几件事就必须由检索层承担。"

**加分点：** 说"我不赌某个技术栈不会被淘汰，我只关注'定位会变的知识 + 权限 + 溯源'这三件事谁来做——这三件事不会消失"。 **⚠️ 扣分回答：** 要么"RAG 永远不会被取代"，要么"RAG 已经过时了"——两个都是表态而不是分析。

## 七、反问面试官

RAG 岗位的反问有一个特殊价值：**你能问出这个团队的 RAG 到底是"调过参的 demo"还是"跑过评测的系统"**。

| 该问 | 你在获取什么信息 |
|---|---|
| 现在有 RAG 的评测集吗？分不分检索指标和生成指标？ | **最关键的一问**——不分层测的团队，优化全靠感觉 |
| 知识库现在多大？更新频率是多少？谁负责索引重建？ | 判断运维成熟度，以及你会不会兼职做数据工程 |
| 召回效果不好时，你们一般先动哪一环？ | 听答案就知道对方是不是真排查过 |
| 多租户和权限是怎么做的？过滤在检索层还是应用层？ | **这一问能立刻暴露团队的安全水位** |
| 现在用的是什么 embedding 和向量库？换过一次吗？ | 换过的团队才踩过"没重建索引"的坑 |

**不该问的：** "你们用什么模型做 embedding？"当唯一问题（显得只关心工具）；能不能远程、加班多不多（找 HR）；"你们的效果怎么样？"（问法太空，对方只会答"还不错"）。

**三个能展示水平的反问：**

1. "你们的 bad case 一般归到哪一类？切片、未召回、召回未用、还是瞎编？"——说明你有归因框架。
2. "线上**该拒答却硬答**的比例你们会监控吗？"——问出这个，面试官知道你想过可信度问题。
3. "如果明天要换 embedding 模型，你们的重建流程需要多久？"——一个很具体、只有真运维过的人才会问的问题。

**收尾：** 如果你有项目，用一句话把反问接回自己的经历——"我之前的项目里这个问题是靠 X 解决的，很好奇你们是怎么处理的"。反问也是一次汇报。
