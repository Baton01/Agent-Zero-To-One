# 项目表达与追问应对

> **这份文件不是题库，是方法。** [[02-Wiki/面试题库/01-Agent高频面试题]] 与 [[02-Wiki/面试题库/02-RAG高频面试题]] 负责让你"答得对"，这一份负责让你"**在面试官追问三层之后还站得住**"。
> **配套：** [[docs/第16章 毕业设计与面试]]（岗位差异与知识地图）· [[docs/第12章 评估可观测性与安全]]（指标与 trace 的来源）· [[docs/第15章 综合实战]]（三个可讲的项目）
> **一句话：** 面试官不考核你的项目有多少功能，他考核**你对这个项目的理解有多深**——而深度的唯一证据是数字、取舍和踩过的坑。

## 一、面试官听项目时在听什么

表面上他在听你做了什么，实际他在四个维度上打分。**每一维都有"一票加分"和"一票起疑"的信号**：

| 维度 | 他在听什么 | 什么信号让他信 | 什么信号让他起疑 |
|---|---|---|---|
| **真实性** | 这件事你真的做过吗 | 说得出别人不知道的细节（某次故障、某个参数为什么是这个值） | 全程只有架构名词，没有任何"操作层面的刺" |
| **判断力** | 你会不会在正确的层做决策 | 说得出**放弃的方案与它的代价** | 只讲用了什么，讲不出为什么不用另一个 |
| **数据意识** | 你怎么知道它变好了 | 主动给口径、给反指标、给基线 | 只有"效果不错""用户反馈好" |
| **工程完备度** | 上线之后的事你想过吗 | 主动讲失败路径、降级、成本、护栏 | 问到"上线后"才开始想 |

**一句话总结这张表：** 前三十分钟靠真实性，最后十分钟靠判断力。**功能列表谁都能背，取舍和故障只有做过的人才有。**

## 二、项目陈述的六段式结构（本章核心）

面试官说"讲讲你的项目"时，用这个固定顺序，**总长控制在 4 分钟以内**。乱序讲（先讲架构再讲问题）会让面试官抓不住重点，然后开始随机追问。

| 段 | 时长 | 一句话任务 | 面试官在这一段考什么 |
|---|---|---|---|
| ① 业务问题 | 30s | 说清"谁的什么痛，值多少钱" | 你是从需求出发还是从技术出发 |
| ② 技术选型 | 45s | 说清"为什么是这条路，不是那条" | 有没有对比与取舍 |
| ③ 系统设计 | 60s | 说清模块与数据流 | 能不能画出中间那几步 |
| ④ 评估指标 | 45s | 说清"怎么知道它行" | 有没有量化意识与反指标 |
| ⑤ 故障与优化 | 45s | 说清一个真实的坑与修法 | 有没有踩过、有没有归因能力 |
| ⑥ 最终结果 | 30s | 收敛到业务价值与已知限制 | 能不能落到价值，而不是自我表扬 |

### ① 业务问题（30 秒）

- **说什么：** 谁（角色）+ 现在怎么做的（现状与耗时）+ 痛在哪（出错/慢/贵）+ 规模（多少文档、多少请求、多少人）。**不要先说技术。**
- **说多少秒：** 30 秒。超过 1 分钟说明你在铺垫，面试官会开始走神。
- **面试官在考什么：** 你是否理解需求的**价值来源**——是省钱、省时间，还是减少事故。
- **常见讲砸方式：** 上来就说"我用了 LangChain + 向量库做了个 Agent"——面试官此时还不知道问题是什么，后面所有的取舍都听不懂。

### ② 技术选型（45 秒）

- **说什么：** 至少给两条候选路线 + 各自的代价 + 你的约束条件 + 为什么选了这条 + **什么情况下你会改选另一条**。
- **说多少秒：** 45 秒。这一段是判断力的主战场，宁可多花 10 秒。
- **面试官在考什么：** 你的选型依据是约束还是偏好。**"我们团队没有 GPU"是约束，"我觉得 RAG 更先进"是偏好。**
- **常见讲砸方式：** 只报技术栈（"用了 RAG、向量库、Rerank"），或者贬低另一条路线（"微调太贵了"）——面试官可能就是微调方案的支持者。

### ③ 系统设计（60 秒）

- **说什么：** 按数据流讲 3–5 个模块，每个模块说"输入什么、做什么、输出什么、失败了怎么办"。**能画图就画图**，共享屏幕画比口述省 30 秒。
- **说多少秒：** 60 秒。这是最长的一段，因为它是后面所有追问的靶子。
- **面试官在考什么：** 你是在"调 API"还是在"设计系统"——差别就在有没有中间层（清洗、校验、降级、缓存）。
- **常见讲砸方式：** 只讲主路径不讲失败路径；模块粒度不一致（一层是"解析"一层是整个"Agent"）；报了一堆技术名词但说不清数据长什么样。

### ④ 评估指标（45 秒）

- **说什么：** 评测集规模与来源 + 主指标（含口径）+ **一个反指标** + 成本与延迟 + 与基线的对比。
- **说多少秒：** 45 秒。这一段是数据意识的唯一证据，**如果你有反指标，面试官会明显高看你一眼**。
- **面试官在考什么：** 你怎么知道它变好了，以及你会不会为了主指标牺牲体验。
- **常见讲砸方式：** "准确率 90%"但说不清怎么测的；只有主指标（检出率涨了）没有反指标（误报涨了多少）；用"用户觉得还行"代替指标。

### ⑤ 故障与优化（45 秒）

- **说什么：** 一个具体的故障：**现象 → 怎么定位 → 根因 → 修法 → 修完的数字 → 这次之后加了什么机制**。注意最后一项：面试官要的是"你现在有了什么防呆机制"，而不是"我修好了"。
- **说多少秒：** 45 秒。这是整场面试最有价值的一段——**判断一个候选人是否真做过项目，就看这一段讲不讲得具体。**
- **面试官在考什么：** 归因能力（是分段定位出来的，还是猜出来的）+ 有没有从个案沉淀出机制。
- **常见讲砸方式：** 说"没遇到什么问题"（面试官会认为你没上过线）；或者把故障讲成"模型不行，后来换了个模型"（没有定位过程）。

### ⑥ 最终结果（30 秒）

- **说什么：** 上线状态（谁在用、用了多久）+ 业务侧的变化（时间/成本/事故率）+ 明确的不足（哪一类问题它做不了，你写在哪了）。
- **说多少秒：** 30 秒。**主动说不足是加分项**，因为它证明你知道边界。
- **面试官在考什么：** 收敛能力——你能不能把技术工作翻译成业务价值，同时不吹。
- **常见讲砸方式：** "效果非常好，领导很满意"；或者把已知不足藏起来（一被追问就崩）。

## 三、完整示范回答（2 个）

> **怎么用：** 不要背原句，背**结构 + 数字 + 那个坑**。把数字换成你自己的，句子换成你自己的语速。两篇都请录音听一遍——你会发现口头讲出来比读起来长 30%。

### 3.1 示范一：企业文档问答系统（RAG 方向）

> **① 业务问题（30 秒）：** "公司有 320 页制度文档散在 6 个手册里，客服每天答约 200 次制度问题，一次要翻 8 分钟，还按作废的报销标准答错过一次、被投诉过。"
> ↳ **作用：** 30 秒内把角色（客服）、痛（8 分钟）、事故（一次投诉）、规模（320 页 / 200 次/天）全给出来。**"一次投诉"是这段的钩子**——它让后面所有的技术选择都有了理由。

> **② 技术选型（45 秒）：** "三条路：微调、长上下文直塞、RAG。微调排除——制度每周改 3–5 处，重训不成立，而且说不清'这句话出自哪一页'，客服必须能指回原文。320 页全塞进上下文的成本是 RAG 的十几倍，延迟也顶不住。选 RAG，并接受它的代价：召回错了模型救不回来，所以最多时间花在检索上。"
> ↳ **作用：** 两条路线各给一个**否定理由**（更新频率、成本与延迟），再给一句"我接受它的代价"——这句话是整段的加分点，说明你不是选完就忘。

> **③ 系统设计（60 秒）：** "四层。索引：按标题切，块 400 字、overlap 60 字，块首拼'文档名 > 标题路径'让块自解释，表格整块保留，共 1800 块。召回：向量 Top-30 加 BM25 Top-30，RRF 融合到 20，再 cross-encoder 重排到 Top-5。生成：只许引用资料编号，跑编号越界与被引块字面依据两道校验，不过就降级'未收录'；权限过滤强制注入在检索层。"
> ↳ **作用：** 按数据流说，每层给一个具体参数（400 字 / 60 字 / 1800 块 / Top-30 / Top-5）。最后一句主动提权限——**这是安全意识的证据，也是面试官最容易忽略、你最容易得分的地方。**

> **④ 评估指标（45 秒）：** "30 条评测集，来自真实客服问题，覆盖单块、跨块、无答案、易混淆四类。检索和生成**分开测**：Recall@5 从 0.74 提到 0.88，引用准确率 0.93，拒答准确率 0.91，P95 4.2 秒。反指标我盯**误拒率**，必须 ≤ 5%——客服问不到答案会转人工，等于把成本转移回去。"
> ↳ **作用：** 来源（真实问题）、分层（检索/生成）、四类覆盖、四个数字、一个反指标。**"误拒率 ≤ 5%"这句话的作用是**：证明你知道指标之间会互相打架。

> **⑤ 故障与优化（45 秒）：** "上线第一周引用准确率从 0.93 掉到 0.71。分段测得检索层 Recall@5 也从 0.88 掉到 0.62，问题在检索不在生成。查 trace：3 份扫描件 PDF 解析成乱码污染了向量空间。修法是解析失败的文件进排除清单并告警、不静默入索引，重跑回到 0.92。之后我加了一列'索引排除文件数'和一条扫描件回归样本。"
> ↳ **作用：** 现象带数字、有分段定位过程、根因具体（扫描件）、有修法、有回访数字，**最后一句是机制沉淀**——面试官从这里判断你是不是"修完就算"的人。

> **⑥ 最终结果（30 秒）：** "每天 200 次咨询约 130 次由它直接答，客服处理时间从 8 分钟降到 3 分钟，两个月无版本错误。已知不足：跨制度的对比类问题答不好——召回是局部视角，这是结构性问题，那条走人工，我写进了 README。"
> ↳ **作用：** 收敛到业务价值（8 分钟→3 分钟）、给使用率（130/200）、给出一个**技术根因层面的限制**（不是"以后会优化"，而是"这类问题召回解决不了"）。**主动划边界是这一段最值钱的动作。**

### 3.2 示范二：行业调研报告多 Agent 系统（Agent 方向）

> **① 业务问题（30 秒）：** "售前每周要出 3–5 份竞品调研报告，一份一个人查两天，结构还不统一；客户经常追问'这个数据哪来的'，我们答不上来。"
> ↳ **作用：** 给频率（3–5 份/周）、人力成本（两天/份）、质量痛点（结构不一致、不可溯源）。

> **② 技术选型（45 秒）：** "先写单 Agent 基线：一个 ReAct 循环加 4 个工具，一次成稿成功率 92%。两个缺口明显：资料量大稀释写作注意力；自己写的稿自己审、挑不出错——命中四条门槛里的一条半。所以加 researcher 和 reviewer 两个角色。代价算过：输入 token 涨 24%，串行延迟从 26 秒变 34 秒，所以让两个 researcher 并行，最终 19 秒。"
> ↳ **作用：** **先有基线再谈升级**——这是这段的骨架。给出 92% 基线、"一条半门槛"这种诚实的措辞、以及 +24% token / 26s→19s 的成本账。**注意"只命中一条半"比"四条全命中"可信得多。**

> **③ 系统设计（60 秒）：** "Supervisor 模式。主管只调度与裁决，不读子 Agent 全文，只收压缩结论。researcher 的契约：输出 facts 至少 3 条和 sources，不许做价值判断。reviewer 的输出固定为 verdict 二选一、每条 issue 带 how_to_verify，必须可判定。四道保险：MAX_ROUNDS=3、相邻两轮意见重合度超 0.8 即停、每轮复述目标跟原目标比对、收尾按交付清单打勾。"
> ↳ **作用：** 说清"谁只做什么"（Supervisor 不读全文、researcher 不许判断）、给出可判定的机制（verdict 二选一、重合度阈值）。**这一段专治"多 Agent 就是几个角色聊天"的质疑。**

> **④ 评估指标（45 秒）：** "25 条历史任务。主指标'可直接交付率'：单 Agent 92%，加 reviewer 后 88%——**降了 4 个点**。拆开看：事实性错误从 6.2% 降到 2.4%，结构合规率从 0.71 提到 0.94。契约违规率 3%、平均轮次 2.3、每成功一次成本 1.2 元、并行后 P95 19 秒。"
> ↳ **作用：** **主指标下降还如实报出来，这是整份示范里最能体现诚信与判断力的一段。** 然后用分项指标解释"总成功率降了但交付质量升了"——这才叫分层评估。

> **⑤ 故障与优化（45 秒）：** "第一版 reviewer 永远说 revise，跑到第 5 轮，成本翻三倍。定位发现两条：意见大量是'不够全面''语气再正式点'这种**不可判定**的，且相邻两轮重合度 0.85 以上，在绕圈。修三件：意见必须带 how_to_verify、加重合度熔断、MAX_ROUNDS 从 5 砍到 3。平均轮次从 4.1 降到 2.3。之后定了一条纪律：verdict 只能二选一。"
> ↳ **作用：** 一个典型的"循环争论"故障，有现象、有定位手段（意见可判定性 + 重合度）、有修法、有前后数字，最后一句是**机制沉淀**。

> **⑥ 最终结果（30 秒）：** "每周 3–5 份报告从两天降到 12 分钟出初稿，人只做事实抽查。已知不足：擅长广度收集、不擅长需要交叉验证的深度结论；另外多 Agent 成功率比单 Agent 低 4 个点，这是用质量换的，不是没发现。"
> ↳ **作用：** 业务价值（两天→12 分钟）+ 使用方式（人做抽查）+ 两条边界，其中第二条主动认领了"成功率下降"这个不利数字。**主动认领比被问出来强十倍。**

**练法：** 把每篇录音，听一遍，删掉所有形容词，只留**数字、机制、动词**，再录一遍。背结构不背原句——**背原句的人在追问第二层时会露馅，因为他不知道那句话为什么在那儿。**

## 四、量化数据的来源与口径

面试里 90% 的"数字翻车"不是因为编，而是因为**说不出口径**。这一节解决三件事。

### 4.1 没有真实流量，数据从哪来

| 数据 | 合法来源 | 注意 |
|---|---|---|
| 效果指标（准确率/召回率） | **自建离线评测集**（20–50 条，从真实问题抄） | 必须说明条数、来源、判据由谁写 |
| 延迟 | 本地跑 20 次取 P95 | 说明机器环境与是否含网络 |
| 成本 | 按真实 `usage` 的 token 数 × 官方价目表折算 | 说明单价与输入输出分开计价 |
| 业务收益 | **耗时对比**（人工做要多久 vs 系统要多久）**+ 假设的请求量** | 必须把假设说出来，别直接报月省多少钱 |
| 规模 | 文档页数、块数、工具数、评测条数 | 这是最容易说真话也最容易被忽略的一类 |
| 对照 | **自己的基线**（上一版 / 单 Agent / 纯规则） | 没有基线的提升不能称之为提升 |

**核心方法：离线评测集是你唯一需要的"流量"。** 20–50 条来自真实历史的问题，能在半天内判断一次改造是否有效——这也是 [[02-Wiki/专题总结/08-评估可观测性与安全]] 里反复强调的"先有评测再加功能"。没有真实用户时，就用它。

### 4.2 哪些数字可以说，哪些不能编

- **可以说：** 你自己跑出来的每一个数（评测集指标、延迟、token 成本、规模）；有明确假设的推算（"按日 1 万次请求估算月成本约 XX 元"）。
- **不能说：** 你没测过的线上数据（"线上准确率 95%""DAU 5000"）；别人项目的数据；把"假设"说成"事实"（"每月省 3 万元"——除非真有人付过这笔钱）。
- **可以模糊：** 商业敏感的具体金额与客户名（"月成本从五位数降到四位数"是合规的说法）。
- **一条底线：** 任何一个数字，如果被追问"这个数怎么测的"你答不上来，就把这个数字删掉——**它带来的风险远大于它带来的加分。**

### 4.3 被追问"这个数怎么来的"怎么答

**三段式：** 口径 → 样本 → 局限。

> "引用准确率 0.93 是这么算的：**口径**上，我统计的是'答案里出现的引用编号能在本次资料范围内找到、且该句结论与被引块有词面依据'的比例，不需要人工标注；**样本**是 30 条自建评测集，跑 3 次取一致的结果，其中 10 条我人工核对过作为校准；**局限**是这 30 条来自我们自己的客服场景，换一批文档绝对值会变，所以我看的是改动前后的相对变化，不是绝对水平。"

这段话之所以有效，是因为它同时展示了口径、样本量、校准方式和**你对局限的自觉**。被追问到第三层还答得住，面试官基本就信了。

**如果确实没测过：** "这块我没有量化过，只有主观感受——如果要测，我会用 X 方法、在 Y 条样本上做。"**承认没有数字，比编一个数字安全一百倍。**

## 五、简历怎么写

### 5.1 项目 description 公式

> **做了什么（系统名 + 三个关键技术点）+ 效果如何（指标 + 口径）+ 规模多大（文档/请求/数据量）**

| 不合格 | 合格 |
|---|---|
| 负责大模型相关功能的开发与优化，提升了系统效果 | 独立实现企业文档问答系统（混合检索 + RRF 融合 + Rerank + 引用校验），30 条自建评测集上 Recall@5 0.88、引用准确率 0.93，P95 4.2 秒，覆盖 320 页 / 1800 个块 |
| 参与 Agent 项目，熟悉 LangChain 等主流框架 | 实现多 Agent 调研系统（Supervisor + 契约校验 + 漂移检测 + 轮次熔断），25 条评测集上结构合规率 0.94、契约违规率 3%、单份成本 1.2 元，P95 19 秒 |
| 深入研究 RAG 技术，效果显著提升 | 通过切片对比实验（固定长度三档 vs 结构切）把 Recall@5 从 0.74 提到 0.88；扫出拒答阈值 0.35，误拒率 ≤ 5% |

### 5.2 空话词清单（见到就删）

> 负责、参与、赋能、闭环、一站式、大幅提升、显著优化、深入理解、熟练掌握、各类、相关、等主流技术、丰富的经验、独立完成、全方位。

**删完之后如果这条描述没有任何数字或文件名，说明它不该出现在简历上。** 一个可执行的判据：**每条项目 bullet 至少包含一个数字或一个具体机制名**（`RRF`、`契约校验`、`MAX_ROUNDS`），否则它就是形容词的堆叠。

### 5.3 数据摆放位置

1. **位置：** 数字放在每条 bullet 的**后半段**——前半段说做了什么，后半段说结果。
2. **口径：** 每个数字都要能答"怎么测的"。"准确率 0.88（30 条评测集，人工核对 10 条校准）"胜过裸的"准确率 88%"。
3. **反指标要有：** 写"误报 0.6 条/PR"比只写"检出率 0.73"更让人信服——**它证明你在盯着副作用**。
4. **规模也要：** 320 页文档 / 1800 个块 / 25 条评测 / 4 个工具——规模说明你真的跑过，而不只是读过。
5. **同一件事只出现一次：** 别在技能条写"熟悉 RAG"又在项目里讲 RAG——前者是声明，后者才是证据。

### 5.4 同一段经历，按岗位改写

同一份 RAG 项目，投不同岗位时的第一条 bullet 应该不一样：

| 岗位 | 第一条 bullet 突出 | 一句话原则 |
|---|---|---|
| AI 应用开发 | 输出稳定性 + 成本（结构化输出与校验、单次成本） | 讲"怎么让它稳定好用" |
| Agent 工程师 | 失败恢复 + 停止条件 + 工具设计 | 讲"它出错了会怎么样" |
| RAG 工程师 | 切片实验 + 检索链路 + 评估指标 | 讲"你怎么知道召回够不够" |
| AI 后端 | 并发 + 缓存 + 限流 + 降级 | 讲"流量涨了会怎么样" |

**操作方式：** 简历准备一版为主，投递时**调换项目顺序 + 改写每条 bullet 的前半段**，把该岗位最关心的三件事顶到最前面。**别为每个岗位写一份全新简历——改 5 行就够，改多了你会记不住自己写了什么。**

## 六、追问应对框架（7 个）

> 追问的通用结构是：**先接住 → 再给结构 → 最后给一个数字或一个边界**。所有框架都遵守这三步，只是内容不同。

### 6.1 "为什么不用 X 方案？"

**框架（四步）：承认 X 的适用场景 → 说清我的约束 → 给数据或机制 → 说明什么时候我会改选 X。**

**示范 1（被问"为什么不用微调"）：**
> "微调在学风格和固定格式上确实更强，这是它的主场。我的约束是文档每周改 3–5 处，微调要重训、周期长、成本高；更关键的是我的场景要求每条结论可追溯到原文，微调说不清来源。实测 RAG 方案在 30 条评测集上引用准确率 0.93、拒答准确率 0.91，已经够用。如果哪天需求变成'统一输出风格'并且文档半年不变，我会优先考虑微调。"

**示范 2（被问"为什么不用多 Agent"）：**
> "多 Agent 我在另一个项目里用过，它买到的是上下文隔离和对抗检查。这个项目里我算过账：单 Agent 基线的输入 token 是 9200，拆成 Supervisor 加两个 worker 后是 11400、涨 24%，串行还会更慢；而我的失败样本里没有一条是'上下文被污染'或'自己挑不出自己的错'——四条门槛一条都不命中。所以我用单 Agent 加一个独立 reviewer 就够了。如果失败样本开始集中在'资料太多看不过来'，我会重新算这笔账。"

**示范 3（被问"为什么不用现成框架"）：**
> "我评估过图框架，它的强项是断点续跑和多分支，代价是概念多、调试要穿过框架层。我这个任务最长 20 秒、没有中断恢复需求，两个角色一个 `for` 循环 20 行就够。我先手写跑通，把契约校验、漂移检测、轮次上限写成自己的组件——这样出问题时我能直接看 trace，不用穿过框架。等任务出现断点续跑需求我再引入。"

### 6.2 "如果流量涨 10 倍怎么办？"

**框架（四步）：先算账 → 找瓶颈 → 三种手段 → 排序与代价。**

**关键动作：把"10 倍"换算成绝对数字。** 大多数面试里的 10 倍，其实还没到需要重构的量级——**能算清这一点本身就是加分项。**

**示范 1（RAG 问答）：**
> "先算：现在 300 次/天、P95 4.2 秒、单次 0.006 元。涨 10 倍是 3000 次/天，按早高峰 30% 集中在 2 小时算，大约 0.13 QPS——**这个量级不需要扩容，先别慌**。真正的瓶颈是单次的外部调用串行：向量召回、BM25、Rerank 串起来让 P95 卡在 4.2 秒。手段按性价比排：① 两路召回并行 + 改写结果缓存，延迟能砍掉接近一半；② Rerank 候选集从 50 降到 20，延迟再降；③ 加并发上限与限流兜底。真到 100 倍再考虑把 embedding 本地化和批处理。"

**示范 2（Agent 服务）：**
> "先算：现在 5000 次/天、平均 4.2 步、P95 12 秒。涨 10 倍是 5 万次/天，约 0.58 QPS——**QPS 不高，但 Agent 的并发占用时长很长**（一次请求要占十几秒），所以要按并发连接数算而不是 QPS，大概需要 7–8 个并发槽位，现在的架构够。真正会先爆的是**成本**：5 万次 × 0.0198 元 / 次 ≈ 990 元/天。所以我先做三件事：模型分级（循环推进一步用小模型）、前缀缓存、历史压缩——这三件事能把单次成本压到 0.011 元。"

### 6.3 "效果不好你怎么排查？"

**框架（五步）：分段定位 → 二分缩小 → 看 trace → 最小复现 → 改一处再测。**

**核心是"分段评估"**：能把系统拆成可分别测量的几段，你就能把"效果不好"变成"第 3 段的第 2 小步退化"，而不是靠猜。

**示范 1（RAG）：**
> "引用准确率从 0.93 掉到 0.71，我先分段测：检索层 Recall@5 从 0.88 掉到 0.62，说明问题在检索不在生成。接着二分：换回上一版索引指标恢复，说明是索引构建环节。查 trace 发现新导入的 3 份扫描件 PDF 解析出来全是乱码，污染了向量空间。最小复现：单独用那份 PDF 建索引，复现出 0.61。处理：解析失败的文件在索引阶段直接进排除清单并告警，不静默入索引；重跑后 0.92。之后我在评估报告里加了一列'索引排除文件数'。"

**示范 2（Agent）：**
> "先看 `stop_reason` 分布——这是 Agent 的体检报告。我发现 `repeat_action` 的比例从 4% 涨到 17%，说明模型在绕圈。拉出长尾 trace 一看：同一个 `get_policy` 用相同参数调了 4 次，而工具返回的是 `{'error': '未收录该政策'}`——模型不知道下一步能干什么，只能重试。修法是把错误信息写成说明书：'未收录该政策，可用主题：退款/换货/发票；或调用 list_policies 查看全部'。改完 `repeat_action` 回到 3%，平均步数从 5.2 降到 3.8。"

**示范 3（通用兜底，当你没有 trace 时）：**
> "如果手上没有 trace，我会先做三件事：把失败样本按同一批输入并排跑两次对比 pass/fail；给每条失败打一个标签看分布；然后按分布决定先修哪一类。分布是最有用的信号——失败集中在同一类输入说明是提示词或判据问题，分散且跟工具相关说明是工具设计问题，同一步骤反复出错说明那一步的观察结果有问题。"

### 6.4 "这个项目最难的地方是什么？"

**框架：说一个真实的取舍，不要说一个技术名词。** 技术名词（"最难的是向量检索调优"）等于没答；取舍（"最难的是决定要不要牺牲检出率换误报率"）才是有判断力的答法。

**示范 1：**
> "最难的不是技术实现，是**定误报率与检出率的平衡点**。我第一版误报 2.1 条/PR，同事的反馈是'连 import 顺序都管'，很快就没人看了。但把阈值调高、意见变少之后，检出率从 0.78 掉到 0.73。这个取舍不是调参调出来的，是要跟使用方谈出来的——我最后选了'误报 0.6 条/PR、检出率 0.73'，理由是这个工具的价值在于**让人愿意看**，被关掉的工具检出率再高也是零。"

**示范 2：**
> "最难的是**说服自己砍掉多出来的那个 Agent**。我一开始设计了三个角色（planner、executor、reviewer），后来看失败样本发现 planner 的存在反而让任务容易漂移——它会自作主张扩大范围。最后我把 planner 砍掉，用一句可判定的目标描述加漂移检测替代它，成功率从 88% 回到 91%。这个过程让我接受了一件事：**每多一个 Agent，我就要能说出它替谁解决了哪一条门槛需求，说不出来就删掉。**"

### 6.5 "你在里面具体做了什么？"（团队项目必被问）

**框架：先说清边界（我做的 / 我参与的 / 别人做的），再指着具体的一个决策说"这是我定的"。** 面试官问这题不是要查你有没有偷懒，是要确认**你对自己做的事有掌控感**。

**示范 1：**
> "整个系统是三个人做的：一位做数据清洗与索引流水线，一位做前端接入，我负责检索链路与评估。具体到我自己：混合检索的 RRF 融合、Rerank 的候选集选型、引用校验与拒答阈值都是我从零写的；评测集 30 条是我采的，判据我请产品同学写（避免自证）。**最能说明我作用的是一个决策**：拒绝方案一开始是让模型自己判断，我改成相似度阈值短路，因为它更便宜也更可靠——这个改动把拒答准确率从 0.83 提到 0.91，误拒率控制在 5% 以内。"

**示范 2（如果项目是你主导的）：**
> "项目是我提的，我负责从需求到上线的全部技术部分。但我要说清一件事：**'评估指标的口径'是和业务方一起定的**——一开始我报的是'回答准确率'，业务方说他们真正关心的是'客服少转人工的次数'，所以我们最后把主指标改成了'可直接使用率'。这件事教我的比技术部分多。"

### 6.6 "如果重做一次你会怎么改？"

**框架：答"顺序"而不是"技术"——顺序类反思显得你真的复盘过，技术类反思听起来像"我当时学得不够"。**

**示范 1：**
> "我会把**评测集提到第一周就建**。我当时拖到第三周才建，结果前两周所有改动都没有基线可比，只能靠感觉——后来回头看，那两周里有两次改动其实是负收益，但当时没人发现。现在我给自己的纪律是：**先有评测再加功能**。"

**示范 2：**
> "我会**先写 Workflow 版本做基线**。这个项目里我直接上了 Agent 循环，后来复盘才发现，其实有 60% 的请求是可以写成固定流程的，只有 40% 需要模型现场决策。如果先写 Workflow 基线，我会更早看到这一点，也许会把 60% 的流量分流到便宜路径上。**没有基线就没有架构决策，只有偏好**——这是我这次最贵的教训。"

### 6.7 "你的方案有什么缺点？"

**框架：主动暴露边界比嘴硬得分高。** 但要注意：**缺点必须是"技术根因导致的"，不能是"我没做好"。** 前者是判断力，后者是失职。

| 说这个（对） | 不要说这个（错） |
|---|---|
| "跨制度的聚合类问题它答不好——召回是局部视角，这是 RAG 的结构性问题" | "检索这块我还不太熟，可能还有优化空间" |
| "多 Agent 的成功率比单 Agent 低 4 个点，这是我们用质量换回来的" | "多 Agent 我没调好，效果不太理想" |
| "它只在我们的客服场景验证过，换一批文档绝对值会变" | "数据量比较小，效果可能不太准" |

**示范：**
> "三个已知不足：一是**聚合型问题做不了**——'总结这份年报的趋势'需要通读，而召回是局部视角，这类问题我做的是显式降级到长上下文或者转人工；二是**多 Agent 的成功率比单 Agent 低 4 个点**，这是我们主动用质量换的，因为结构合规率和事实准确率都提升了；三是**评测集只有 30 条**，它的作用是回归与归因，不是统计显著性——所以我只看改动前后的相对变化，不对外宣称绝对水平。这三条我都写进了 README。"

## 七、压力面试应对

压力题考的不是知识，是**心态**。三种典型情形，各有固定接法。

| 情形 | 错误反应 | 正确接法 |
|---|---|---|
| **被否定**（"你这个方案有问题"） | 辩解、硬撑、"不是的，因为……" | **先接住再区分**："你说得对，如果是 XX 条件，这个方案确实不成立。我的场景里区别在于 YY，所以选了它；如果换成 XX，我会改成 ZZ。" |
| **被连续追问**（一层套一层） | 越答越虚、开始编 | **主动降级成不确定**："这个层面我没有实测过，我的理解是……要验证的话我会先做 XX。"**主动说停比被问穿强。** |
| **被问不会的** | 沉默、硬编、转移话题 | **三段式**："这块我没做过 → 我的理解是（给一个可证伪的猜测）→ 如果要验证我会先做什么。" |

**三条纪律：**

1. **不辩解。** 面试官的质疑通常有一部分是对的，先把对的那部分承认下来，再划出你不同意的部分。**"你说得对"这四个字不会让你失分，硬撑会。**
2. **不认领你没做的事。** 被问到没做过的部分，直接说"这部分不是我做的，我负责的是 X"——**模糊归属比明确边界危险得多**，追问两层就会自相矛盾。
3. **不赌。** 任何"模型不会被骗""这样绝对不会出错"的绝对表述都会被追问。改成"我保证它被骗了也做不了坏事"这种**机制层面的表述**。

**最后一句忠告：** 压力面试里最容易崩的不是不会，而是**假装会**。面试官一天见 5 个人，他能听出来你在背；但你诚实说"这块没做过"，他反而会往下问你会的部分——**你只需要一个领域足够深。**

## 八、反问环节

反问是你**判断这家公司值不值得去**的唯一机会，也是最后一次展示水平的机会。准备 5 个，问 2–3 个。

| 该问 | 你在获取什么信息 |
|---|---|
| 这个岗位现在最核心的目标是什么？半年内做成什么样算成功？ | 团队有没有清晰目标，还是"领导让我们试试 AI" |
| 现在有评测集吗？谁来维护？多久跑一次？ | **最关键的一问**——没有评测就是全靠感觉，你会天天背锅 |
| 从需求到上线大概走什么流程？有灰度和回滚吗？ | 工程成熟度，以及你要不要兼做运维 |
| 线上成本现在怎么控？有预算上限吗？ | 判断团队是否已被账单教育过 |
| 模型选型是团队自己定还是公司统一？能换吗？ | 你还剩多少技术自主权 |

**不该问：** 加班多不多、能不能远程、涨薪幅度（这些问 HR）；"你们用什么模型？"当唯一问题（显得只关心工具）；官网能查到的信息（暴露没做功课）；"我有机会吗？"（把判断权交出去）。

**三个能展示水平的反问**（把问题问成"我在关心你的工程问题"）：

1. "你们 Agent 的**失败率怎么统计**？看 pass@k 还是 pass^k ？"——一句话说明你知道生产要看稳定性。
2. "线上跑起来之后，你们**怎么发现某个改动让它变差了**？"——直接指向评测集与 trace，最能问出团队真实水平。
3. "你们接入的工具里，**危险动作的确认门放在哪一层**——Host 侧还是提示词里？"——问出这个，面试官立刻知道你懂权限边界。

**收尾话术：** 面试结束时问一句"如果我有机会加入，你希望我**第一个月先把哪件事做起来**"，比问任何待遇问题都更留印象——它说明你已经在想怎么干活了。

## 九、面试前一晚的检查清单

**材料**
- [ ] 每个项目一页卡片：六段式的**关键词** + 指标数字 + 一个失败故事（写关键词，别写完整句子）。
- [ ] 两张架构图（截图或手画拍照），能在 30 秒内讲清数据流。
- [ ] 指标数字表：主指标 / **反指标** / 成本 / 延迟 / 规模，口径也写上。
- [ ] 每个项目准备 5 个追问的答案（为什么不用 X / 流量 10 倍 / 效果不好怎么查 / 最难的地方 / 你做了什么）。
- [ ] 每个项目准备一个"**最难的地方**"和一个"**已知缺点**"——这两题几乎必问，且必须提前想过。
- [ ] 简历打印一份，标记出可能被追问的三个点。

**演示**
- [ ] 离线模式确认可跑（**网络挂了也能演**）。
- [ ] 录一段 3 分钟备份视频。
- [ ] 环境变量与 key 检查一遍，演示前不清空日志。
- [ ] 准备一个"演示失败时"的兜底话术（"我用日志里的结果讲一下"）。

**口述**
- [ ] 90 秒自我介绍录音听一遍：`我是谁 → 两个项目 + 指标 → 我想做的方向`。
- [ ] 每道高频题的 **30 秒版本**口述一遍，卡壳的标红。
- [ ] 把自己的项目按六段式完整讲一遍并计时，**超过 4 分钟就删内容**（删的是铺垫，不是数字）。
- [ ] 准备"不会"的标准答法："这块我没做过，我的理解是……要验证我会先……"
- [ ] 三个反问写在纸上，放在手边。

**状态**
- [ ] 提前 10 分钟进会议；耳机、摄像头、屏幕共享提前测一次。
- [ ] 水放在手边（说 40 分钟话真的会渴）。
- [ ] 简历上的每个数字都能答"怎么测的"——**这是最后的自检**。
- [ ] 想清楚"我为什么投这家"的一句话答案。
- [ ] 睡够 7 小时。**状态比多做一道题重要。**

## 十、岗位差异

同一套知识，不同岗位的问法完全不同。投递前先看 JD 里的关键词反推类型，**然后按类型调简历顺序与讲述重点**。

| 岗位 | 主要考什么 | 次要考什么 | 典型问题 | 简历该突出什么 | 你该把哪段讲最深 |
|---|---|---|---|---|---|
| **AI 应用开发** | Prompt 工程、Function Calling、业务落地、成本控制 | 模型原理、工程规范 | "怎么让输出稳定？""成本怎么降？" | 结构化输出与校验、单次成本、业务指标 | 技术选型 + 评估指标 |
| **Agent 工程师** | Agent loop、工具设计、上下文工程、失败恢复、多智能体 | 评估体系、协议 | "工具失败怎么恢复？""什么时候不该用多 Agent？" | 停止条件、契约校验、trace、pass^k | 故障与优化 + 系统设计 |
| **RAG 工程师** | 切片、混合检索、重排、embedding 选型、评估 | 数据工程、向量库运维 | "召回不到怎么排查？""怎么评估 RAG？" | 切片对比实验、Recall@K、引用准确率 | 系统设计 + 评估指标 |
| **AI 后端** | 服务化、并发、缓存、限流、可观测性、成本 | 模型细节 | "流量涨 10 倍怎么办？""怎么做灰度与回滚？" | 分层超时、重试退避、成本看板、降级演练 | 故障与优化 + 技术选型 |

**一句话策略：** 面 Agent 岗就把"失败恢复与停止条件"讲深；面 RAG 岗就把"切片实验与评估指标"讲细；面 AI 后端就把"成本、延迟、降级"讲实。**同一段经历，按岗位换重点——但绝对不能换数字。** 数字一旦为了迎合岗位而变形，你会在追问里露馅。

**四个岗位的共同底线：** 无论投哪个方向，面试官都会问"**你怎么知道它有效**"。能答出评测集、判定器、主指标与反指标的人，在任何岗位的面试里都是安全区。

> **最后：** 这份方法论要和两份题库一起练——[[02-Wiki/面试题库/01-Agent高频面试题]] 给你"答得对"的骨架，[[02-Wiki/面试题库/02-RAG高频面试题]] 给你"答得细"的数字，这一份给你"**答完还站得住**"的结构。项目讲完的那一刻，面试官心里的判断其实只有一句话：**这个人是不是真的做过、想过、并且知道自己在做什么。**
