## 一、Token 估算规则（中文对照）

| 内容 | 经验换算 | 例子 |
|---|---|---|
| 中文（CJK 字符） | **1 字 ≈ 1 token**（偏多时 1.2–1.5） | "你好世界" ≈ 4 token |
| 英文/拉丁字母 | **4 字符 ≈ 1 token**；约 **0.75 词 = 1 token** | `hello world` ≈ 3 token |
| 数字 | 1–3 位一组 ≈ 1 token | `2025` ≈ 1–2 token |
| 代码 | 约 **3 字符 = 1 token**（符号多） | 100 行 Python ≈ 800–1500 token |
| JSON | 引号、括号、逗号**各算独立 token** | 见下方"键名长度"提醒 |
| 标点（中英混排） | 中文标点 ≈ 1 token/个 | 密集标点会显著抬高估算 |
| 空格/换行 | 很少（<1 token） | 删空格不省钱 |
| 整体偏差 | 实测通常在 **−30% ~ +10%** | 做预算时按估算值 **×1.3** 留余量 |

```python
def estimate_tokens(text):
    """零依赖估算：中文 1 字 ≈ 1 token，其余 4 字符 ≈ 1 token。
    用途是预算与上限保护，不是对账依据。"""
    cjk = 0
    for ch in text:
        if "\u4e00" <= ch <= "\u9fff":
            cjk += 1
    return int(cjk + (len(text) - cjk) / 4) + 1
```

**三条容易算错的地方**：

1. 每次请求的总输入 = **system + 全部历史 messages + 本次输入**，不是只有本次输入；
2. 多轮对话里**历史占大头**（常达 70% 以上），估算时别只看当前那句；
3. **键名越长越贵**：`{"customer_order_number":"A123"}` 比 `{"n":"A123"}` 多好几个 token，长 JSON 塞进 prompt 会明显膨胀。

## 二、常见内容的 token 量级参考

| 内容 | 大致 token | 说明 |
|---|---|---|
| 一句话（20 汉字） | 20–30 | 用户提问的常见量级 |
| 一段系统提示词 | 300–600 | 本书示例的 Agent 系统提示 |
| 一个 Skill 正文 | 100–500 | 命中后才注入 |
| 一个 Skill 的 `name + description`（目录项） | 40–100 | 常驻上下文，20 个技能 ≈ 1200–2000 |
| 一个 MCP 工具 schema | 约 200 字节 ≈ 50–80 token | 4 个工具 ≈ 200–300 token，**每次请求都带** |
| 一篇 1000 字中文文档 | 1000–1500 | RAG 切片前的原始量 |
| 一个 RAG chunk（300 字） | 300–450 | Top-5 检索 ≈ 1500–2200 token |
| 1000 行 Python 文件 | 8000–15000 | 别整文件塞进去，用检索/摘要 |
| 一次工具返回（网页正文） | 500–5000+ | **必须截断**，这是最容易被忽略的大头 |
| 一段 500 字模型回答 | 500–750 | 输出单价是输入的 3–4 倍 |

## 三、成本计算公式（含算好的例子）

```text
单次调用成本 = prompt_tokens × 输入单价 + completion_tokens × 输出单价
单次任务成本 = Σ 该任务所有调用的成本
每成功一次的成本 = 总成本 ÷ 成功次数            ← 含失败重跑的"真实成本"
月成本      = 每成功一次的成本 × 日请求量 × 30
```

示例价表（**仅作口径示例，价格会变，务必以服务商官网为准**；单位：元 / 百万 token）：

| 模型 | 输入 | 输出 | 缓存命中输入 |
|---|---|---|---|
| `deepseek-chat` | 2.0 | 8.0 | 0.5 |
| `qwen-plus` | 0.8 | 2.0 | — |
| `glm-4-flash` | 免费档 | 免费档 | — |
| `gpt-4o-mini` | 约 1.1 | 约 4.3 | 约 0.55 |

**算例 1（一次问答）**：system 300 + 用户 50 = 输入 350，输出 200
`350 × 2 / 1e6 + 200 × 8 / 1e6 = 0.0007 + 0.0016 = ¥0.0023`

**算例 2（5 步 Agent）**：输入累计 7380、输出累计 630
`7380 × 2 / 1e6 + 630 × 8 / 1e6 = 0.01476 + 0.00504 = ¥0.0198`（**约 8.6 倍**）

**算例 3（月成本）**：每天 1 万次、每次 ¥0.0198、成功率 90%
`0.0198 × 10000 ÷ 0.9 × 30 = ¥6,600/月`
→ 若把每成功成本降到 ¥0.011：`¥3,667/月`，直接省 44%。

## 四、Agent 循环的 token 放大规律

前提：system 600 token、每步输出 80、每次观察 100（第 05 章口径）。

| 步数 | 本轮 prompt | 本轮输出 | 累计输入 | 累计输出 | 相对 1 次问答 |
|---|---|---|---|---|---|
| 1（一次问答，无循环） | 600 + 180 = 780 | 150 | 780 | 150 | 1× |
| 3 | — | 80 | 1,800 | 240 | 约 2.3× |
| 5 | 600 + 900 = 1,500 | 80 | 3,600 | 400 | 约 4.6× |
| 6（5 步 + 收尾） | 1,680 | 150 | 7,380 | 630 | **约 8.6×** |
| 10 | — | — | 约 25,000 | 约 950 | 约 30× |

**三条必须记住的规律**：

1. **prompt 随步数线性增长**（第 n 次 ≈ 600 + 180n），**总 token 是平方级**；
2. **重复率约 80%**：每次都要把历史重发一遍（模型没有记忆，不发它就不知道）；
3. **步数从 5 涨到 10，token 不是翻倍而是约 3 倍** —— 所以"砍步数"永远是最强杠杆。

**延迟同理**：单次请求 1.2–2.5 秒 × 6 次串行 ≈ 9–15 秒。多智能体串行分工只会更慢；只有并行无依赖子任务才能降延迟。

## 五、省钱清单（10 条，按收益排序）

1. **模型分级**：路由/抽取/循环用便宜模型，强模型只留给最终写作与评测判定 —— 收益可达数量级。
2. **砍步数**：工具 description 写清楚、给出"优先用哪个工具"的提示、观察结果截断，5 步压到 3 步。
3. **启用前缀缓存**：system 与固定资料放在请求最前面且**逐字节稳定**，命中部分输入费降 5–10 倍。
4. **历史压缩 + 工具结果截断**：超阈值改摘要、只留最近 N 轮；工具层限制返回长度（常砍掉最大的一块）。
5. **限制输出**：明确"3 条以内/表格形式"，设 `max_tokens` 上限 —— 输出单价是输入的 3–4 倍。
6. **结果缓存**：相同请求精确缓存 + 工具结果带 TTL 缓存（外部 API 常常是瓶颈）。
7. **批量/异步**：非实时任务走批量通道、错峰跑，单价常见 5 折。
8. **预算熔断**：单次任务（步数 + 金额）、单日、单用户三层上限，超限即停或降级。
9. **调试用小模型**：调流程一律 `AGENT_MOCK=1` 或小模型，最终验收才用强模型。
10. **统计口径修正**：算 **每成功一次的成本**（含失败重跑），并按"总 prompt token"而不是"步数"做优化判断。

**反向提醒（省过头的三个信号）**：

- 为了省 token 砍系统提示 → 输出变差 → 重试变多 → 总成本反而上升；
- 只优化"单次调用 token"而忽略失败重跑 → 账单和估算对不上；
- 步数降了但总 token 涨了（某一步的观察结果特别长）→ 要看 total prompt tokens。
