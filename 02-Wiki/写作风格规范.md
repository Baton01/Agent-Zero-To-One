# 写作风格规范

> **这份文件是给"写内容的人"看的**，包括你、AI 教练、以及任何给本项目贡献内容的人。
> 它规定的是**叙事方式**，不是内容本身。内容对不对看正文，读起来像不像样看这里。
>
> 风格来源：卡码笔记 [LLM-Master](https://github.com/youngyangyang04/llm-master)（MIT）。
> 本项目所有学习内容的叙事方式向它对齐。

## 一、核心差别：讲稿，不是手册

同样讲"什么是 Agent"，两种写法：

**❌ 手册式（本项目早期写法）**

> Agent 是把"下一步做什么"的决策权交给模型。它的五个组成部分是模型、工具、循环、状态、停止条件。判据如下表……
> 读完你能回答：1. 什么是 Agent……

问题：对，但干。读者不知道**为什么要关心这件事**，也不知道**别人会怎么挑他**。

**✅ 讲稿式（本规范要求）**

> 前段时间有个学员面试 AI 应用岗，简历上写了一个"智能客服 Agent"。
>
> 面试官问他：「你这个 Agent 和普通客服机器人有什么区别？」
>
> 他回答：「我们用了更强的大模型，能理解用户问题，还能多轮对话。」
>
> 面试官继续追问：「那它有没有自己决定下一步做什么？有没有调用工具？有没有根据工具结果调整动作？如果只是用户问一句、它答一句，为什么叫 Agent？」
>
> 这下就卡住了。
>
> 这类问题很常见。很多简历上写了 Agent，但讲出来还是一个 ChatBot。所以这篇先把最基础的问题讲清楚：**Agent 到底是什么？**

差别在哪：**读者先看到一个具体的人在一个具体的场合被问住，才会想知道答案。**

## 二、标准结构（七段）

### 第 0 段 · frontmatter（必写）

```yaml
---
title: Agent到底是什么？和普通大模型问答、ChatBot、Workflow有什么区别
description: Agent到底是什么，为什么它不只是更聪明的大模型问答？本文从普通问答、ChatBot、Workflow和Agent的边界讲起，拆解规划、工具调用、反馈迭代和任务闭环，帮助准备AI Agent岗位面试的同学建立清晰认知。
keywords: ["Agent是什么", "AI Agent", "Agent和Workflow区别", "Function Calling", "ReAct", "大模型面试"]
tags: ["AI Agent", "Agent入门", "大模型面试"]
---
```

要点：
- **title 是一句真问题**，不是名词短语。把主要关键词塞进去，长度可以到 30 字。
- **description 说清三件事**：本文讲什么、从哪讲起、帮谁解决什么。它是别人在搜索结果里唯一会读完的一段。
- keywords 要包含**长尾词**（"Agent和Workflow区别"），不只是主题词。

### 第 1 段 · 开篇：一个真实的人和真实的对话

**必须包含**：

1. **一个具体的人**（"一个学员"、"我同事"、"上周有个读者"）在**一个具体场合**（面试、评审、上线出事）
2. **一段对话**，用引用块排版。对话里要有人**追问**，把问题的尖锐性暴露出来
3. **一句共鸣式判断**："这类问题很常见"、"很多人都卡在这一步"
4. **一句全文承诺**："所以这篇把 X 讲清楚"

**禁止**：以"随着大模型技术的发展……"开头，或以定义开头。

### 第 2 段 · 先讲读者已经会的那部分

> 先别急着定义 Agent，我们从最熟的普通问答说起。

从读者**已经懂的东西**切入，再引出新概念。不要一上来就抛新名词。

### 第 3–N 段 · 主体：编号小节，标题是判断句

- 用 `## 一、` `## 二、` 编号（中文数字）
- **小节标题写成一句判断，不写名词**
  - ✅ `## 四、RAG 不是万能的：什么场景适合，什么场景不适合`
  - ❌ `## 四、RAG 的适用场景`
- 每节**先给结论，再解释机制**
- **讲机制，不只讲现象**：
  - ❌ "模型会产生幻觉，所以要用 RAG"
  - ✅ "大模型的本质是一个概率语言模型，它生成每个 token 时做的是'预测下一个最可能的词'，而不是'从知识库里查答案'。这意味着它不知道答案时不会说'我不知道'，而是生成一个听起来最合理的答案"
- **主动标注边界**："有了事实依据的约束，幻觉概率大幅降低——**但注意，不是归零**，这个后面会讲"
- **预判并回答读者的反驳**："有人会想：那把文档全部放进 Prompt 里呢？对于少量文档这是可行的，但当文档量达到几百份时……"
- 关键判断句用 `**加粗**`，放在段首或段尾
- 用「你」和「你们公司」拉近距离

### 第 N+1 段 · 面试可能怎么问

```markdown
## 五、面试可能怎么问

**Q：为什么有了大模型还需要 RAG？**

参考思路：大模型有几个局限性——幻觉、私有知识盲区、知识时效性、无法溯源。RAG 通过在回答前先检索外部知识库，把相关文档片段注入上下文，让模型"看资料回答"，从而有针对性地缓解以上问题。

**Q：RAG 能解决幻觉问题吗？**

参考思路：能显著缓解，但无法根治。……
```

要点：
- **Q 用面试官的原话**，不要改写成人话
- **参考思路写成一段可以直接背下来的话**，不是要点罗列
- 每题的回答里**必须有一个转折**（"但……"/"注意……"/"代价是……"），体现判断力
- 3–5 题

### 最后一段 · 结语：一句比喻收尾

> RAG 不是大模型能力的升级，而是大模型的外置数据库——让模型在回答时能检索自己的 cheat sheet，从而有据可依。

- **一段话，一个比喻，不重复前文**
- 不要写"综上所述"、"希望对你有帮助"

## 三、排版细节

| 项目 | 规范 |
|------|------|
| 小节编号 | `## 一、` `## 二、`（中文数字 + 顿号） |
| 分隔线 | 用 `------`（六个短横），不用 `---` |
| 术语首次出现 | 中英并列：幻觉问题（Hallucination） |
| 对话/示例 | 用引用块 `>`，一问一答分块 |
| 图示 | 图片 alt 写完整说明句，图片放在相关小节开头 |
| 表格 | 只用于枚举事实，不把解释塞进表格 |
| 代码块 | 必须标语言；代码前一句话说清这段在干什么 |
| 加粗 | **只加粗判断句**，不加粗名词 |

## 四、禁止清单

- ❌ 以定义开头（"X 是一种……的技术"）
- ❌ 空话（"X 非常重要"、"随着技术发展"、"在当今时代"）
- ❌ 只讲现象不讲机制（"模型会幻觉" 而不说为什么）
- ❌ 只有清单没有取舍（列 10 个优缺点，不说该选哪个）
- ❌ 结论没有边界（说"用 X 就行"，不说"什么时候不能用 X"）
- ❌ 结尾"综上所述"、"希望对你有帮助"
- ❌ 表格里塞大段解释文字
- ❌ 为了显得客观而两边都说好话——**要给出明确推荐**

## 五、本项目的补充要求

在 llm-master 风格之上，本项目额外要求：

1. **每个概念必须落到可运行的代码。** llm-master 是文章，本项目是课程——讲完机制要给代码或命令。
2. **要写"什么时候不该用"。** 每章都要有边界讨论，这是本项目的立身之本。
3. **要有可验证的数字。** 不说"性能大幅提升"，说"从 0.74 提升到 0.88，测法是……"。
4. **章节保持既有的骨架**：`本章目标 / 预计用时 / 前置章节 / 配套代码` 四行头 + `## 0. 开篇` + 主体 + `本章小结` + `动手练习` + `自测题` + `交付标准` + `下一章预告`。
   本规范改变的是**这些部分怎么写**，不是**有哪些部分**。
注意章节末尾那节的标题现在统一叫 `## 结语与下一章`（第 16 章是 `## 结语`），写法按本规范第 2 段最后一条。

## 六、自检清单

写完一段内容，用这五条过一遍：

- [ ] 开篇有没有一个具体的人在一个具体的场合说了具体的话？
- [ ] 有没有至少一处"但注意……"式的边界标注？
- [ ] 有没有预判并回答读者可能的反驳？
- [ ] 面试问答里的答案，能不能直接背下来用？
- [ ] 结语有没有一个比喻，而不是"综上所述"？
