# 专题：Agent 是什么

> **一句话** · Agent 与 Workflow 的唯一分界线，是**"下一步做什么"的决定权在模型手里还是在代码里**；把决定权交出去，就同时把成本、延迟、失败模式一起交了出去。
>
> **本专题对应：** `docs/第01章 认识AI-Agent`、`docs/第05章 ReAct最小Agent-Loop`、`docs/第06章 范式进阶`、`docs/第11章 多智能体协作`、`docs/第14章 构建你自己的Agent框架`
>
> **读完你能回答：**
> 1. 拿到一个需求，怎么在 5 分钟内判断它该做成 Chatbot、Workflow、Agent 还是 Multi-Agent？
> 2. Agent 的五个部件（模型/工具/循环/状态/停止条件）里，哪一个缺了最容易在 Demo 里看不出问题、上线后爆炸？
> 3. ReAct / Plan-and-Execute / Reflection 三种范式各自的**失败模式**是什么？什么信号出现时该把它们拆掉？

---

## 一、本质

需求评审会上，有个同学说"这块我们准备做成 Agent"。项目经理追问："它下一步做什么，是模型决定的，还是你代码里写好的？"他愣了一下："应该都有一点吧。"——接下来的成本怎么算、失败怎么兜，就都聊不下去了。

Workflow 的控制流写死在代码里（`if 金额 > 5000: 走主管审批`），Agent 的控制流交给模型——它每一步现场决定调哪个工具、传什么参数、什么时候停。**所以判断一个系统是不是 Agent，只问两句话：下一次迭代由谁决定？循环何时结束由谁决定？** 两个答案都是"模型"就是 Agent；有一个是"代码"，那就是 Workflow 里嵌了一个会思考的节点——**决定权交出去，成本和失败模式就一起交出去了**。**本文把这四种形态的工程取舍讲清楚。**

## 二、决策表

### 2.1 四选一的判断顺序

**从上往下问，第一个命中"否"的地方就是你的答案。**

| 顺序 | 问题 | 是 | 否 → 该用什么 |
|---|---|---|---|
| 1 | 任务能不能拆成**步骤固定**的流水线（哪怕有分支）？ | 继续问 2 | **Workflow**（`dict` 路由 / 责任链 / DAG） |
| 2 | 每一步的**输入输出契约**能不能事先定死？ | 继续问 3 | **Workflow + 单步 agent**（只在最难那一步放开） |
| 3 | 是否存在 2 个以上**角色不同、上下文应该隔离**的子任务？ | 继续问 4 | **单 Agent**（多角色往往是提示词问题，不是架构问题） |
| 4 | 子任务的**数量**是否事先未知、且可以并行铺开？ | **Multi-Agent** | **单 Agent** |

### 2.2 更硬的三条量化判据

架构选择最终要落到数字上。下面三条任意一条不满足，就不要上 Agent：

| 判据 | 合格线 | 不达标时怎么办 |
|---|---|---|
| **分支不可预测性** | 你写不出流程图，或者写出来有 ≥ 3 条"看情况"的回边 | 写成 Workflow，把"看情况"拆成规则 |
| **单次价值 / 单次成本** | 单次业务价值 ≥ 单次 Agent 成本的 50 倍（留足失控余量） | 降价：用小模型做决策 + 缓存；或改用规则 |
| **错误可容忍度** | 出错可被人工审核、可重试、可回滚 | 只让 Agent 产出**草稿或建议**，执行仍由代码/人做 |

### 2.3 四种形态的工程量对照

| 维度 | Chatbot | Workflow | Agent | Multi-Agent |
|---|---|---|---|---|
| 决定下一步 | 人（读完自己去做） | 代码 | 模型 | 模型 + 协调者 |
| 典型请求数/任务 | 1 | 2–5（固定） | 3–15（波动） | 15–60（波动更大） |
| 延迟 | 2–5s | 3–10s | 6–30s | 30s–10min |
| 结果方差 | 低 | 极低 | **高** | 极高 |
| 调试难度 | 低 | 低 | 中（要 trace） | 高（要 trace + 契约） |
| 主要失败模式 | 答错 | 分支漏写 | 绕圈、跑题、提前收工 | 循环争论、责任真空、上下文膨胀 |
| 何时选它 | 只是问答 | 流程确定 | 路径不可预测 | 子任务可并行且数量未知 |

### 2.4 三类真正适合 Agent 的任务

1. **探索型**：下一步取决于上一步看到了什么（网页调研、日志排障、代码定位）。
2. **工具组合不固定**：查库 → 调 API → 写文件，顺序随中间结果变。
3. **单次价值高且可重试**：一份尽调报告值 100 元，花 1 元和 2 分钟去生成完全划算。

反例（看起来像 Agent，其实不该做）：客服 FAQ（Workflow + RAG）、固定字段的发票抽取（1 次调用 + 结构化输出）、每日固定报表（定时任务 + 代码）。

## 三、工程实现要点

### 3.1 循环：把 `while` 写成有限状态机，而不是"让模型随便跑"

```python
# Python 3.9 兼容
MAX_STEPS = 8

def run_agent(llm, tools, goal, max_steps=MAX_STEPS):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": goal}]
    trace = []
    for step in range(1, max_steps + 1):
        reply = llm.chat(messages, tools=tools, temperature=0)   # Agent 一律 temperature=0
        calls = reply.get("tool_calls") or []                    # 永远不要假设字段存在
        if not calls:                                            # 模型不再要工具 = 收工
            return {"answer": reply.get("content", ""), "steps": step, "trace": trace}
        # 顺序很重要：带 tool_calls 的 assistant 消息必须在所有 tool 结果之前
        messages.append({"role": "assistant", "content": reply.get("content", ""), "tool_calls": calls})
        for call in calls:                                       # 一轮可能返回多个工具调用
            result = execute_tool(call)                          # 内部已吞异常，永不抛
            trace.append({"step": step, "tool": call["name"], "args": call["args"], "ok": result["ok"]})
            messages.append({"role": "tool", "tool_call_id": call["id"],
                             "content": trim(json.dumps(result, ensure_ascii=False), 2000)})
    return {"answer": FALLBACK, "steps": max_steps, "stop_reason": "max_steps", "trace": trace}
```

**关键决定：循环的骨架必须由代码拥有（步数、顺序、状态写入），模型只拥有一条能力——选择调用哪个工具、传什么参数。** 把整段控制逻辑交给模型（"你自己决定要不要继续"）是新手最常见的失控来源：模型会礼貌地说"任务完成了"，而你没有任何地方能拦住它。

### 3.2 状态：模型的记忆就是你写进 `messages` 的东西

- **每轮重发全部历史**：这不是配置问题，是 API 的工作方式。所以第 N 轮的输入 token ≈ 前 N−1 轮的总和，20 轮任务的累计输入是 5 轮版的 10 倍以上（`docs/第02章` 有算式）。
- **观察结果要裁剪后再入上下文**：一次返回 40KB 的 API 响应塞进上下文，不只是贵——它会**挤掉**真正重要的早期指令，让模型开始忽略约束。
- **大对象用引用而不是内容**：把 8 万字文档落盘成 `doc_id`，上下文里只留 `{"doc_id": "d17", "chars": 82000, "summary": "..."}`，需要时再分页读。这是所有长任务 Agent（Claude Code 一类）的通用做法。
- **工具结果要能被"重新读一遍"**：幂等工具（查询类）失败后可重放；非幂等工具（下单、转账）失败后只能查状态，绝不能重放——见 3.4。

### 3.3 停止条件：四道闸门 + 一条软性条件 + 一个兜底结果

| 闸门 | 拦住什么 | 推荐值 | 误杀风险 |
|---|---|---|---|
| `max_steps` | 一切失控的兜底 | 8（简单任务 5，调研类 15–20） | 极低 |
| 重复动作（同工具+同参数签名） | 卡在同一个调用 | 同签名第 2 次警告，第 3 次终止 | 中（会拦住合法重试） |
| 无进展（观察归一化后连续相同） | 换汤不换药地绕 | 连续 3 次 | 中（轮询类任务会误伤，需归一化时间戳） |
| 预算（token/金额/墙钟） | 烧钱、挂死 | 单任务成本的 2 倍；墙钟 120s | 低 |
| （软性）连续 N 轮无工具调用也无答案 | 模型在 Thought 里空转 | 追加一次提醒，再犯即终止 | — |

**到达任何闸门时返回兜底结果（"已转人工"），不要抛异常。** 对业务而言 5% 的任务转人工是可接受的，整个批处理崩掉不可接受。这一条决定了你的 Agent 能不能上线。

### 3.4 工具：Agent 的能力边界 = 工具边界，越权防线也在工具里

- **模型只能做你给过工具的事**。它说要"发邮件"但你没有 `send_email`，它就只能输出一段"建议你发邮件"——所以想让 Agent 干什么，先给工具。
- **权限必须写在代码里，不能写在 prompt 里**。`delete_order` 这种工具要么不注册，要么加 `requires_confirmation=True` 走人工确认；靠系统提示词写"请不要删除数据"迟早会被绕开（工具描述和用户输入都是不可信输入）。
- **非幂等工具必须带幂等键**。超时重试是常态：`POST /refund` 超时后 Agent 会重试，没有幂等键就退两次款。做法是让模型传 `request_id`（或由执行层按 `会话id+工具+参数哈希` 生成）。

### 3.5 可观测：没有 trace，就没有 Agent 工程

最低限度要记录每条：

| 字段 | 用途 |
|---|---|
| `task_id` / `goal` | 归因到具体任务，算成本与成功率 |
| 每步 `tool` + `args` + `ok` + 耗时 | 定位选错工具 / 参数错 / 工具慢 |
| 每步 `prompt_tokens` / `completion_tokens` / `cost` | 成本曲线，找"哪一步开始变贵" |
| `stop_reason` | 区分"正常收工"与"被闸门拦下"，这是最重要的单一指标 |
| 最终答案 + 是否通过验收 | 唯一能算成功率的字段 |

`stop_reason` 的分布是 Agent 健康度的体检报告：`finished` 应占多数；`max_steps` 高说明任务被低估或提示词太弱；`repeat_action` 高说明工具返回值让模型无法决策；`budget` 高说明该降模型档位或缓存。

## 四、横向对比

### 4.1 四种范式的代价与失败模式

| 维度 | Workflow | ReAct | Plan-and-Execute | Reflection |
|---|---|---|---|---|
| 谁决定路径 | 代码 | 模型逐步决定 | 模型先定计划，再逐步执行 | 模型执行后自我批判 |
| 请求数（同任务量级） | 2 | 5 | 5 | 7（含 2 轮反思） |
| token 量级（`docs/第06章` 实测口径） | ~900 | ~8000 | ~6000 | ~11000 |
| 主要收益 | 确定、便宜、可复现 | 能应对不可预知的分支 | 线性成本、计划可人工审核、可并行 | 在有客观信号时显著提质量 |
| **主要失败模式** | 分支漏写、新情况直接失败 | 绕圈、步数爆炸、成本平方增长 | **计划错则一路错到底** | **没有外部信号时越改越自信但没变好** |
| 什么时候该拆掉它 | 分支多到 maintain 不动 | 平均步数 > 15 或 P95 超过闸门 | 执行中偏离率 > 30% | 两轮反思后指标不升 |

**Anthropic 的量化参照**：在其多智能体研究系统的工程总结里，单个 agent 的 token 消耗约为普通对话的 **4 倍**，多智能体系统约为 **15 倍**；并且 token 消耗量本身解释了性能差异的绝大部分（约 80%）。结论不是"贵所以别用"，而是**"加范式之前先证明它买到了什么"**。

### 4.2 选型口诀（背下来）

> **先问有没有外部信息**（没有 → CoT 系列；有 → ReAct/RAG），
> **再问能不能事先规划**（能 → Plan；不能 → ReAct），
> **最后问有没有客观验收标准**（有 → 可以反思；没有 → 反思最多一轮）。

### 4.3 Agent 框架对比（"要不要用框架"）

| 方案 | 适合 | 代价 |
|---|---|---|
| 手写 while 循环（`code/ch05_react_loop.py` 那种） | 学习、单一路径、需要完全掌控 | 要自己写重试、并发、trace |
| 轻量封装（自己抽 `common/llm.py` + `common/tools.py`） | 生产项目的多数场景 | 需要自己维护一点基础设施 |
| LangGraph / 同类图框架 | 多分支、需要持久化与人工介入（human-in-the-loop） | 概念多、版本变动快、调试要穿过框架层 |
| 全托管 Agent 平台 | 快速验证、非核心业务 | 可观测性与成本控制受平台限制，迁移成本高 |

**建议：先用 SDK 手写一版跑通（第 05 章），确认需求真的存在后再引入框架。** "先学框架再看原理"的人，在排查"为什么这一步没执行"时会无从下手。

## 五、常见故障与排查

### 故障 1：绕圈（两个工具来回试，永不收工）

- **现象**：trace 里 `get_policy` → `search_order` → `get_policy` → `search_order`，参数完全相同。
- **定位**：把每步的 `工具名 + 参数 JSON 排序后` 拼成签名，统计签名重复次数；看返回给模型的观察结果是不是**无法决策的空话**（如 `{"error": "未收录该政策"}`——模型不知道下一步该干什么）。
- **解决**：① 重复签名第 2 次警告、第 3 次终止；② **把错误信息写成说明书**："未收录该政策，可用主题：退款/换货/发票；或调用 `list_policies` 查看全部"；③ 给一次"换思路"的提示后仍未变则终止。

### 故障 2：提前收工（第 1 步就交答案）

- **现象**：`steps=1`、`stop_reason=finished`，但答案明显没有依据（常见于需要先查数据的任务）。
- **定位**：trace 里工具调用数为 0，或调用数远小于任务所需。
- **解决**：① 在提示词里写**验收标准**（"必须包含从工具获取的订单号与状态，否则不算完成"）；② 强制"先取证再作答"——把"调用工具获取 X"列为完成条件；③ 用 Plan 前置一步生成检查清单，执行层逐项打勾；④ 加一个轻量 critic 在收工前核对"答案里的每个事实是否有对应工具结果"。

### 故障 3：跑题（越走越远，最后答了别的问题）

- **现象**：目标是"查订单 DP1002 的退款状态"，最后写成一篇关于退款政策的说明文。
- **定位**：trace 的 `goal` 与最终答案做语义比对；看第 4 步以后是否还出现与目标直接相关的工具调用。
- **解决**：① **原始目标每轮都重述**（做成固定的 user 消息或 system 末尾一行，不要只出现在第 1 条消息里）；② 收窄工具集合（跑题常常是因为模型发现了一个"更有意思"的工具）；③ 把大任务拆成有明确契约的子任务（`docs/第11章`）。

### 故障 4：步数爆炸（均值健康、P95 灾难）

- **现象**：平均 6 步，但 P95 是 34 步；成本被少数请求吃掉。
- **定位**：**统计步数分布而不是均值**，把 P95/P99 的长尾 trace 拉出来逐条看。
- **解决**：① 观察结果裁剪与摘要（大返回值是长尾主因）；② 把"连续多次单条查询"合并成一个批量工具（`get_orders(ids=[...])`）；③ 提示词里给出"最多允许 3 次查询"的预算感；④ 对长尾任务转人工或降级。

### 故障 5：成本失控（账单无故涨 20 倍）

- **现象**：同一个功能，上线后某天账单翻倍甚至更多，代码没有改动。
- **定位**：按 `task_id` 聚合 token，看是**请求数变多**（绕圈）还是**单请求变长**（观察结果变长/历史压缩失效）；同时检查是否有输入触发了解析失败→重试的循环（第 03 章的重试路径也会放大成本）。
- **解决**：① 四道闸门全上；② 模型分级：决策用小模型、最终生成用大模型；③ 命中率高的固定前缀开 **prompt caching**（缓存命中的输入价格通常低一个数量级）；④ 输出侧 `max_tokens` 设上限；⑤ 账户级预算告警。

### 故障 6：过度使用 Agent（能用 Workflow 的做成了 Agent）

- **现象**：一个"每天汇总 3 个固定报表"的任务做成了 7 轮 Agent，成本 10 倍、延迟 5 倍、偶发失败。
- **定位**：对照 2.1 的四问——如果第 1 问能通过（步骤固定），你根本不该继续问下去。
- **解决**：**写一个 Workflow 版本作为基线（baseline）**，再用数据证明 Agent 版本值得那多出来的成本。没有基线就没有架构决策，只有偏好。

### 故障 7：同一输入结果不同（线上无法复现用户投诉）

- **现象**：用户说"它昨天答对了今天答错了"，你本地重跑复现不了。
- **定位**：检查 `temperature`（Agent 场景必须为 0 或接近 0）、工具输出里是否含时间戳/随机 id、模型版本是否被服务商静默升级。
- **解决**：① `temperature=0`；② 工具输出稳定化（排序、去时间戳、固定精度）；③ trace 里记录模型名与版本、prompt 版本号；④ 保留可重放的工具快照（录制—回放模式）。

### 故障 8：工具都成功了，但模型不知道发生了什么

- **现象**：`ok=true` 的一串调用，最终答案却与数据无关。
- **定位**：检查工具返回值——是不是只返回 `{"ok": true}` 而没有可用内容？或者返回被截断到关键字段之外？
- **解决**：① 工具返回值按"模型要用来决策的最小充分信息"设计：成功时也要带上业务关键字段（订单状态、金额、单号）；② 截断要在**语义边界**上做并显式标记 `"truncated": true`；③ 失败永远不用空值表示（`{"ok": false, "error": "..."}`），否则模型会把"没有"当成"是空的"。

## 六、面试要点

**1. 什么算 Agent？**
骨架：① 唯一分界是控制流决定权（模型 vs 代码）；② 五部件（模型/工具/循环/状态/停止条件）；③ 不看有没有 `Thought`，看下一次迭代和终止由谁定；④ 举例：Workflow 里嵌一次 LLM 分类不算 Agent。

**2. Agent 和 Workflow 怎么选？**
骨架：① 步骤能否事先画清 → 能就是 Workflow；② 分支是否不可预测（有回边/看情况）→ 才是 Agent；③ 成本方差是代价：常数 → 分布；④ 先上 Workflow 做基线，用数据证明要升级。

**3. 为什么"不该用 Agent"是更重要的问题？**
骨架：① Agent 的代价是成本、延迟、方差三件事同时变差；② 可复现性差，线上排障成本高；③ 已有成熟判据：规则能写、需要 100% 一致、延迟 <1s、无人工审核 → 别用；④ 单次价值必须远超单次成本。

**4. Agent 五部件里哪个最容易被忽略，后果是什么？**
骨架：① 停止条件——Demo 阶段看不出，上线后账单爆炸；② 状态——表现为重复调用和绕圈；③ 工具——能力边界，缺了就只能"建议"不能"做"；④ 模型——决定了上限但不是架构；⑤ 循环——没有 for/while 就只能一次性回答。

**5. 怎么判断一个任务适合 Agent？**
骨架：① 三轴：分支不可预测性、单次价值/成本比、错误可容忍度；② 三类适合：探索型、工具组合不固定、高价值可重试；③ 反例：固定字段抽取、FAQ、定时报表；④ 给一个自己的场景并说清判据。

**6. ReAct 的核心贡献是什么？Thought 为什么有用？**
骨架：① 论文名与年份（Yao 等，2022，arXiv:2210.03629）；② 把推理与行动写进同一文本流，让中间结果成为后续决策的上下文；③ 相比纯 Act，多步任务的成功率提升来自"看到上一步再决定下一步"；④ 需要注意：Thought 只是上下文，**想对了不代表做对了**，执行层护栏（工具描述、参数校验）不能省。

**7. Plan-and-Execute 适合什么？replan 什么时候触发？**
骨架：① 适合步骤多、依赖弱、能事先列清的任务；② 收益：线性成本、可并行、计划可人工审核；③ 代价：计划错则一路错到底；④ replan 触发：步骤失败、连续偏离、预算消耗过半、外部状态变化；⑤ 混合用法：外层 Plan、内层单步 ReAct。

**8. Reflection 什么时候有效？**
骨架：① 必须有**外部信号**（测试、编译、检索证据、schema 校验），否则模型只会在自己的错误里打转；② 论文依据 Reflexion（Shinn 等，2023，arXiv:2303.11366）；③ 两个层次：L1 润色（主观任务，最多一轮）、L2 带 rubric 的批判 + 明确的停止条件；④ 停止条件：指标不再提升、预算耗尽、轮数上限；⑤ 创作类任务多轮反思会啰嗦、同质化。

**9. 怎么防止 Agent 死循环 / 失控？**
骨架：① 四道闸门：步数、重复动作、无进展、预算/超时；② 触发时返回**兜底结果**而非抛异常；③ 错误信息写成说明书，让模型知道下一步能干什么；④ 监控 `stop_reason` 分布；⑤ 具体参数：8 步、同签名 3 次、连续 3 次相同观察、120 秒。

**10. 多智能体到底买到了什么？**
骨架：① 核心价值是**上下文隔离**，不是"人多力量大"；② 适合子任务数量未知且可并行的广度探索（研究类），不适合强耦合任务（多数编码任务）；③ 成本参照：多智能体 token 约为普通对话的 15 倍（Anthropic 工程总结）；④ 代价：循环争论、任务漂移、上下文膨胀、责任真空；⑤ 上之前先算账，四条判据不满足就用单 Agent。

**11. 你会怎么观测和调试一个 Agent？**
骨架：① trace 字段：goal、每步工具/参数/结果/耗时、token 与成本、stop_reason、最终是否通过验收；② 四个核心指标：任务成功率、平均步数 + P95、单任务成本、stop_reason 分布；③ 调试顺序：先看 stop_reason，再看长尾 trace，最后才怀疑提示词；④ 用 trace 做 A/B：改提示词/换模型前后对比同一批任务的指标。

**12. 上线前你会做哪些防护？**
骨架：① 预算与闸门（成本上限、超时）；② 权限最小化 + 危险工具人工确认（参数要展示给人看）；③ 非幂等操作加幂等键；④ 降级路径（转人工、缓存答案、只出草稿）；⑤ 可观测与告警（成本异常、失败率、闸门触发率）；⑥ 灰度发布与回滚方案。
