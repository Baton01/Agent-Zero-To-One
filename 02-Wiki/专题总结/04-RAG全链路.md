# 专题：RAG 全链路

> **一句话** · RAG 不改模型，只改**送进模型的上下文**；因此它的效果上限由**召回**决定——没被检索出来的内容，再强的模型也变不出来。
>
> **本专题对应：** `docs/第08章 RAG全链路`、`docs/第07章 记忆与上下文工程`（上下文预算与压缩）、`docs/第02章 大模型基础`（token 与成本）、`docs/第12章 评估可观测性与安全`（评测与越权）
>
> **读完你能回答：**
> 1. 用户问"海外出差住宿能报多少"，正确条款排在 Top-20 的第 9 位却被 Top-5 截掉——你该先动切片、动检索、还是动 Rerank？
> 2. 什么情况下你**不需要**向量数据库，甚至**不该用 RAG**？
> 3. 怎么用 20–50 条评测数据，在半天内判断一次"切片 + 混合检索 + Rerank"的改造是否真的有效？

---

## 一、本质

有同学在评测里遇到过这一幕：用户问"海外出差住宿能报多少"，制度里明明写着 8000 日元，系统却答了 6000 元。翻出检索日志才发现——正确条款排在 Top-20 的第 9 位，被 Top-5 截掉了。**答案没错，是材料根本没送到。**

RAG 是一条**两段串联**的流水线：离线索引（加载 → 清洗 → 切片 → 向量化 → 存）与在线查询（改写 → 召回 → 融合 → 重排 → 组装 → 生成 → 校验）。背下三句话，本专题其余内容都是它们的展开：**不改模型，只改上下文**；**上限由召回决定，可信度由引用与拒答决定**（这两件事在链条两端，必须**分开测量**）；**每一环都有独立的失败模式**，排错必须先定位坏在哪一环。**本文把这条链上每一环的工程取舍讲清楚。**

## 二、决策表

### 2.1 RAG / 微调 / 长上下文 / 混合方案怎么选

| 维度 | RAG | 微调（SFT / LoRA） | 长上下文直塞 | RAG + 微调 |
|---|---|---|---|---|
| 解决什么 | **记事实**（会变的知识） | **学风格、格式、判断方式** | 一次性理解少量材料 | 事实靠检索、表达靠模型 |
| 知识更新 | 重建索引（分钟级） | 重训（小时～天级） | 无需更新（材料现取现用） | 索引更新即可 |
| 可溯源 | **强**（可标引用） | 弱（说不清来源） | 中（能指回原文） | 强 |
| 成本结构 | 每次查询付检索 + 拼接 | 一次性训练 + 推理省 token | 每次输入全量 token（贵且随长度线性增长） | 较高 |
| 数据量适用 | 10 万字～千万字 | 需要几百～几万条标注样本 | < 5 万字、材料固定 | 大知识库 + 高要求场景 |
| 典型不适用的任务 | 需要全局聚合推理（"总结整份年报趋势"） | 事实类问答（会过时、不可溯源） | 文档持续增长、多用户共享 | — |

**三条判据**：① 知识**会变**且需要**引用** → RAG；② 需求是**稳定输出风格/格式**、且标注数据充足 → 微调；③ 材料少、变化少、延迟不敏感 → 长上下文直塞。**三者不互斥**：生产里最常见的是"RAG 供事实 + 少量示例/微调固定输出格式"。

### 2.2 什么时候**不该**上 RAG

| 症状 | 真正该做的 |
|---|---|
| 问题是聚合型的（趋势、对比、总计） | 先把文档做 map-reduce 摘要，或走长上下文 |
| 数据是结构化表且能写 SQL | Text-to-SQL / 直接查库，别把表格塞进向量库 |
| 知识库 < 20 页且极少变 | 直接进 system prompt（配合 prompt caching 更划算） |
| 没有评测集 | 先花 1 小时建 20 条评测集，否则你无法判断 RAG 是否有效 |
| 用户期望"精确数字/计算" | 检索 + 工具计算，纯 RAG 会给一个"看起来对"的数 |

### 2.3 四种切片策略怎么选

| 策略 | 做法 | 保真度 | 成本 | 适合 | 主要风险 |
|---|---|---|---|---|---|
| **固定长度** | 每 N 字符切，带 overlap | 低 | 最低 | 无结构的纯文本、快速验证 | 句子/表格被切断 |
| **递归切分** | 按 `\n\n` → `\n` → 句号 逐级回退 | 中 | 低 | 通用文档（默认选择） | 层级混乱时切点仍不理想 |
| **结构/语义切分** | 按 Markdown 标题、HTML 标签、代码函数 | **高** | 中（要解析） | 有明确层级的文档（手册、API 文档、代码） | 小节过长仍需二次切 |
| **父子切片** | 小块检索、大块（父块）喂模型 | **高** | 高（存两份） | 答案依赖上下文（"该条适用于哪些人"） | 存储与 token 成本上升 |

**默认起手式**：结构切分（按标题）+ 长度兜底（超长小节按递归切）+ 10%–15% overlap。**中文经验值**：`chunk_size` 取 300–500 汉字（约 200–500 token，视分词器而定），overlap 50–80 字；英文的 512 token 经验不要直接照搬到中文。

## 三、工程实现要点

### 3.1 切片：目标是"检索单元自足"

一个 chunk 被单独送进模型时，必须能读懂**它是关于什么的**。所以关键动作是**给 chunk 补上下文**：

```python
# Python 3.9 兼容：把标题路径拼进块首，让孤立的块自解释
def build_chunk(text, heading_path, source, position, updated_at):
    header = "【%s】%s\n" % (source, " > ".join(heading_path))     # 文档 + 标题路径
    return {
        "id": "%s#%d" % (source, position),                        # 稳定 id：便于引用与增量更新
        "text": header + text,
        "meta": {"source": source, "heading_path": heading_path,
                 "position": position, "updated_at": updated_at},
    }
```

- **表格必须整块保留**，并补一行表头说明（"下表为国内差旅住宿标准，单位：元/晚"）——被切碎的表格是检索垃圾。
- **代码按语法单元切**（函数/类），并在块首带上文件路径与依赖导入信息。
- **overlap 不是越多越好**：它按比例放大索引体积与检索噪声；10%–15% 是常见起点。
- **元数据是刚需，不是可选项**：`source / heading_path / position / updated_at / tenant_id / acl` 里，最后两个决定了你能不能安全地做多租户检索。

### 3.2 Embedding：三条铁律

1. **文档与查询必须用同一个模型、同一个版本**。换模型不重建索引 = 用 A 的坐标系查 B 的向量，结果全是噪声（这类故障不报错，只表现为"效果突然变差"）。
2. **模型与相似度度量必须匹配**。用余弦就全库归一化；换成内积（dot）或 L2 时，索引参数与代码要同步改。有的模型要求给 query / passage 加不同前缀（如 `query:` / `passage:`），漏了会明显掉点。
3. **中文优先看中文评测**。选型时用**你自己的 20 条评测集**对比，而不是只看通用榜单（榜单任务的分布和你不同）。

### 3.3 向量库：先问"需不需要"

| 规模 / 需求 | 方案 | 代价 |
|---|---|---|
| < 1 万块，单机、只读 | **内存 + NumPy 余弦**（`docs/第08章` 的做法） | 无持久化、无过滤、重启要重建 |
| 1 万–100 万，单机、要过滤 | FAISS / Chroma / Qdrant（本地模式） | 运维与版本管理 |
| 已有 PostgreSQL | **pgvector** | 性能不如专用库，但复用现有备份/权限体系 |
| 亿级、多租户、强过滤 | Milvus / Qdrant 集群 / Elasticsearch | 集群运维、成本、调参 |
| 关键词检索是刚需 | Elasticsearch / OpenSearch（原生 BM25 + 向量） | 配置复杂 |

**选型时最容易被忽略的一项是"过滤"**：能否在检索时做**前置过滤**（`tenant_id = X AND updated_at > Y`）。很多实现是先取 Top-K 再过滤，结果是"过滤后只剩 2 条"——**召回率被过滤层吃掉了**。确认你的库支持 pre-filter（或分区索引）再决定。

### 3.4 混合检索与 RRF：为什么纯向量一定会漏

向量擅长语义相近，**但会漏掉精确符号**：订单号 `DP1002`、型号 `XPS-9370`、缩写、人名、专业术语。BM25 恰好相反。两路并用几乎总是赚的。

```python
def rrf_fuse(rank_lists, k=60, top_n=20):
    """reciprocal rank fusion：只用排名，不需要两路分数可比。"""
    scores = {}
    for ranks in rank_lists:                       # ranks: [(doc_id, ...), ...]
        for rank, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return [d for d, _ in sorted(scores.items(), key=lambda kv: -kv[1])][:top_n]
```

- **RRF 的价值在于"免调参"**：向量相似度（0–1）与 BM25 分数（可能 0–30）不可比，做加权前要先归一化，而归一化本身又是一堆调参；RRF 只看排名，鲁棒。
- **中文 BM25 要分词**（`jieba` 等），或用 **bigram** 做零依赖兜底（查"报销标准"时切成"报销/销标/标准"）。
- **典型配比**：向量 Top-30 + BM25 Top-30 → RRF → Top-10~20 → Rerank → Top-4~6 进 prompt。

### 3.5 Rerank：两阶段检索的收益与代价

| 阶段 | 模型结构 | 能否预计算 | 精度 | 延迟 | 用在哪 |
|---|---|---|---|---|---|
| 召回（bi-encoder） | query 与 doc 各自编码 | **能**（doc 向量离线算好） | 中 | 毫秒级（ANN） | 从万级里挑出几十条 |
| 重排（cross-encoder） | query + doc 拼在一起编码 | 不能 | **高** | 每条 5–50ms | 从几十条里挑出 5 条 |

- **Rerank 救不回没召回的内容**：它只在候选集内重新排序，所以召回阶段的 K 要给足（常见 20–50）。
- **收益通常是三处里最立竿见影的**：把"正确块排第 9"变成"排第 2"，直接改善生成质量；Anthropic 的 contextual retrieval 报告也指出，"上下文补全 + BM25 + 重排"的组合比单一手段的检索失败率下降幅度更大。
- **代价**：自建 cross-encoder 要吃 GPU/CPU 与延迟，API 版按 token 计费；**先测延迟预算**再决定候选集大小（50 条 vs 20 条的延迟差是 2.5 倍）。

### 3.6 查询改写：跨越"用户口语"与"文档术语"的鸿沟

用户说"住宿能报多少"，文档写的是"住宿标准"；用户说"我的包裹到哪了"，文档写的是"物流轨迹"。改写是补这条鸿沟最便宜的手段。

| 手法 | 做法 | 适合 | 代价 / 风险 |
|---|---|---|---|
| **多查询（Multi-Query）** | 让模型生成 3–5 个不同角度的查询，各自检索后 RRF 融合 | 问题表述模糊、单一措辞召回不稳 | 检索次数 ×N（但检索远比生成便宜） |
| **HyDE** | 先生成"假想答案"，再用它去检索 | 短查询、术语密集型文档 | 假答案跑偏会把检索带偏；有额外模型调用 |
| **退步提问（Step-back）** | 把具体问题抽象成更一般的问题再检索 | "我周五出差三天能报多少"→"差旅报销规则" | 抽象过头会丢细节，通常与原查询合并检索 |
| **关键词抽取** | 从口语问题里抽实体/术语做 BM25 查询 | 含编号、型号、人名的查询 | 实现简单，常与向量路并联 |

**别忘了一条更省的：缓存改写结果**。同一类问题在客服场景会重复出现，改写结果按 query 哈希缓存，命中率高得惊人。

### 3.7 组装：顺序、编号、预算

- **资料在前、问题在后**（长上下文场景的常见经验），每条资料带 `[编号] + 来源标题 + 元数据`。
- **去重**（同一文档相邻块重复）与**去噪**（相似度过低的块宁可不给）：把不相关的资料喂进去，等于让模型从噪声里挑真相。
- **预算公式**：`Top-K × 平均块长度 + prompt 模板 ≤ 上下文预算 × 0.5`，留一半给历史与输出（`docs/第07章` 的预算分配）。
- **给出"资料不足"的出路**：prompt 里明确"若资料中没有答案，输出 `未收录`，并说明已检索的来源范围"。

### 3.8 引用与拒答：可信度的两个开关

```python
def validate_citations(answer, cited_ids, hits):
    """三道校验：编号存在 → 编号范围内 → 被引原文能在块里找到依据。"""
    problems = []
    valid = {h["cid"] for h in hits}
    for cid in cited_ids:
        if cid not in valid:
            problems.append("引用了不存在的资料编号 %s" % cid)
    for cid, claim in extract_claims(answer):          # 句子级：把答案拆句，逐句找引用
        chunk = next((h["text"] for h in hits if h["cid"] == cid), None)
        if chunk is None:
            continue
        if not keyword_overlap(claim, chunk):          # 词面依据检查（离线可跑，零依赖）
            problems.append("引用 [%s] 与结论无字面依据" % cid)
    return problems
```

- **只允许引用资料编号，禁止引用外部来源名**。模型很爱写"根据《员工手册》第 12 条"——这是编造，不是引用；在 prompt 里明确"只能引用资料编号"，并在校验层过滤。
- **拒答要设计成一条路径，不是一个愿望**：相似度阈值以下直接短路（不调用生成模型，回"未收录"），比让模型自己判断更可靠、也更便宜。
- **引用粒度越细越可信**（块级 → 句子级），代价是校验成本；客服/法务类场景值得做句子级。

### 3.9 索引一致性：三种必须监控的漂移

| 漂移 | 后果 | 检测 | 处理 |
|---|---|---|---|
| 文档更新了、索引没重建 | 答案引用旧制度 | 对比文档 `updated_at` 与索引构建时间 | 内容哈希判断是否需要重算；增量重建 |
| 换 embedding 模型没重建 | 检索整体退化，且不报错 | 记录索引用的模型名 + 版本 | 重建，并把模型名写进索引元数据 |
| 权限/租户变更没同步 | **越权检索**（最严重） | 审计检索结果的所有者字段 | 检索层强制注入 `tenant_id` 过滤，绝不靠 prompt 约束 |

**增量更新的正确做法**：以 `doc_id` 为单位删除旧块（`delete by metadata`）再写入新块，而不是"全量重建"（大库重建期间不可用，且成本高）。切块规则一旦变更，所有块 id 都会变，这类变更要当成一次"全量重建"来发布（双索引 + 切换）。

## 四、横向对比

### 4.1 两阶段检索的收益与成本（为什么要 Rerank）

| 配置 | 候选集 | 精度（相对） | 延迟（相对） | 成本 | 适用 |
|---|---|---|---|---|---|
| 单路向量 Top-5 | 5 | 低（易漏、易偏） | 1× | 最低 | 演示、小知识库 |
| 向量 + BM25 + RRF → Top-5 | 60 → 5 | 中 | 1.2× | 低 | 含编号/术语的场景 |
| 上述 + Rerank → Top-5 | 60 → 20 → 5 | **高** | 1.5–2.5× | 中 | **生产默认** |
| 上述 + 查询改写（3 路） | 3×60 → 20 → 5 | 高（对模糊查询更稳） | 2–4× | 中高 | 客服问答、术语鸿沟明显 |

### 4.2 常见向量库对比（按"你真正会遇到的约束"排）

| 方案 | 部署 | 过滤能力 | 混合检索 | 运维成本 | 什么时候选 |
|---|---|---|---|---|---|
| NumPy + JSON | 零依赖 | 自己写 | 自己写 | 0 | < 1 万块、教学、单机离线 |
| FAISS | 库（非服务） | 弱（需自建映射） | 无 | 低 | 单机高性能、能接受自管 id 映射 |
| Chroma | 单机/服务 | 中 | 弱 | 低 | 原型到小规模生产 |
| Qdrant | 单机/集群 | 强（pre-filter） | 中 | 中 | 多租户、需要强过滤 |
| pgvector | 复用 PG | **强（SQL）** | 中（PG 全文） | 低（已有 PG） | 已有 Postgres、规模中等 |
| Milvus | 集群 | 强 | 中 | 高 | 亿级、多租户、专用团队 |
| Elasticsearch | 集群 | 强 | **强（原生 BM25 + 向量）** | 高 | 关键词与向量同等重要 |

### 4.3 长上下文会取代 RAG 吗

| 问题 | 长上下文直塞 | RAG |
|---|---|---|
| 100 万字知识库每次全塞 | 成本随长度线性上涨，延迟高 | 只送 Top-K |
| 知识每天更新 | 每次要重新组织输入 | 增量重建索引 |
| 需要"这句话出自哪" | 能定位但成本高 | 引用是原生能力 |
| 全局聚合（总结全部） | **更擅长** | 不擅长（召回是局部视角） |
| 多租户/权限 | 靠应用层裁剪 | 元数据过滤（成熟） |

**结论**：长上下文解决"一次读懂少量材料"，RAG 解决"在大量会变的知识里定位"。两者组合是常态：RAG 定位 + 大窗口读完整章节。

## 五、常见故障与排查

### 故障 1：召回了，但模型没用

- **现象**：正确块在 Top-3 里，答案却是模型自己编的，或只用了第 5 条不相关的块。
- **定位**：把"检索指标"和"生成指标"分开——`Hit@K` 正常而 `Faithfulness` 低，说明问题在组装/生成，不在检索。打印实际送进模型的 prompt 片段，确认资料没有被截断或被 history 挤掉。
- **解决**：① 最相关的块放**最前面**并加显式标注（"以下资料与问题最相关"）；② 要求"每个结论必须带编号引用"；③ 降 K（把噪声块去掉，模型更容易专注）；④ prompt 里加"若资料与问题无关就忽略它"。

### 故障 2：切片把上下文切断（答案跨块）

- **现象**："我周五出差三天能报多少"需要"住宿标准"+"天数规则"两块，但两块各含一半信息，模型只看到一半。
- **定位**：看 gold chunk 的原文边界——答案被切断在块尾还是块首；对比不同切片参数的 `Hit@K`。
- **解决**：① 增大 overlap（50–80 字）；② 按标题/段落切，别按字符硬切；③ **父子切片**：小块用于检索，命中后把父块（完整小节）喂给模型；④ 检索命中后**拼接相邻块**（`position ± 1`）再送模型。

### 故障 3：表格与代码块被切碎

- **现象**：检索到的是"金额（元）| 城市"这种没有表头的残片，模型据此给出错误的对照关系。
- **定位**：打印命中的 chunk 原文，看表格是否缺表头、代码是否缺缩进与上下文。
- **解决**：① 表格做成**一个块**（超长表格按行切但**每块都带表头**）；② 在块首加自然语言描述（"下表是海外差旅住宿标准，单位为当地货币/晚"）；③ 代码按函数/类切并带上文件路径；④ 结构化数据也可以额外建一路"表格专用检索"（把表格转成自然语言行）。

### 故障 4：多文档冲突（新旧制度同时被召回）

- **现象**：答案给出"600 元"（旧版）或摇摆不定地列出两个数字。
- **定位**：检查召回结果里是否存在同一主题的多份文档，比较它们的 `updated_at` / 版本号。
- **解决**：① 元数据带版本与生效日期，检索时按"生效中"过滤；② 冲突无法过滤时，prompt 明确"以最新版本为准（按 updated_at）"；③ 生成时要求标注适用版本；④ 从源头治理：旧文档下线或打上 `deprecated`。

### 故障 5：相似但错误的召回（近义条款混淆）

- **现象**：问"海外住宿上限"，召回"国内住宿标准"（语义很像、数字完全不同）。
- **定位**：看 Top-K 的相似度分布——如果正确块与错误块分数接近（差距 < 0.02），说明 embedding 分辨不出这个维度，需要外部信号。
- **解决**：① 加 **BM25 混合**（"海外"是精确词，词面检索能区分）；② 上 **Rerank**（cross-encoder 对这种细粒度差异更敏感）；③ 元数据过滤器（地域/产品线）；④ 查询改写时显式保留限定词（"海外 住宿 标准"），别让模型"概括"掉关键区分词。

### 故障 6：引用幻觉（编号不存在、来源编造）

- **现象**：答案里出现 `[7]` 但只给了 5 条资料；或写"根据《财务制度》第 3 章"（资料里根本没有这句话）。
- **定位**：引用校验器（编号范围 + 字面依据）跑一遍，统计"引用不可核验率"；这是**不需要人工标注**就能测的指标。
- **解决**：① 校验编号是否在本次资料范围内，越界即判失败并重试一次；② 要求"只能引用编号，禁止提及外部文件名"；③ 句子级校验：把答案拆句，检查每句能否在被引块中找到词面依据；④ 校验不通过时降级为"未收录"。

### 故障 7：超出知识库范围却硬答

- **现象**：问"公司团建预算"，文档里没有，模型按"一般公司做法"编了一个数字。
- **定位**：评测集里的 `must_refuse` 用例通过率；线上统计"无资料问句"的答案率。
- **解决**：① **相似度阈值短路**：最高分低于阈值时直接回"未收录"，不调用生成；② prompt 里给拒答 few-shot；③ 生成后校验"答案中的数字/事实是否有资料依据"；④ 把线上"该拒答却硬答"的样本回流评测集。

### 故障 8：文档更新了，答案没变

- **现象**：制度昨天改成了 800 元，今天答的还是 600 元。
- **定位**：对比文档 `updated_at` 与索引构建时间；检查更新流程有没有真的触发重建。
- **解决**：① 内容哈希（`sha1(text)`）判断是否需要重算向量；② 更新走"删旧块 + 写新块"的增量路径；③ 加监控：文档变更事件与索引变更事件的比值应接近 1:1；④ 变更较大时双索引发布 + 切换。

### 故障 9：越权检索（最严重）

- **现象**：A 部门用户问出来的答案引用了 B 部门的内部文档。
- **定位**：审计日志里检查检索结果的所有者字段；做一次"用低权限账号构造敏感查询"的对抗测试。
- **解决**：① 检索层**强制注入** `tenant_id` / `acl` 过滤（pre-filter），不依赖 prompt；② 索引元数据必须与权限系统同步；③ 引用展示时做二次校验（防止跨租户的块 id 被拼进上下文）；④ 把"越权尝试"作为安全测试用例纳入回归。

### 故障 10：延迟高（尤其加了 Rerank 之后）

- **现象**：端到端 3–5 秒，用户体感卡顿。
- **定位**：分段计时（改写 / 向量召回 / BM25 / 融合 / Rerank / 生成），找出最大头。
- **解决**：① 两路召回**并行**执行；② 改写结果缓存；③ Rerank 候选集从 50 降到 20；④ embedding 批量与本地化（避免跨网调用）；⑤ 首屏流式输出生成结果，检索阶段给"正在检索…"的反馈。

## 六、面试要点

**1. RAG 里最难的环节是什么？**
骨架：① 不是向量库，是**切片 + 召回**（决定上限）；② 其次是**评估**（没有指标就无法优化）；③ 再其次是"无答案时的拒答"（决定可信度）；④ 工程上最容易翻车的是索引一致性与权限过滤。

**2. 怎么优化召回？按什么顺序动手？**
骨架：① 先建评测集，测 `Recall@K`；② 切片对不对（看命中的块是否完整、是否混主题）；③ 加混合检索（向量 + BM25 + RRF）；④ 查询改写（多查询 / HyDE）；⑤ 上 Rerank 并调 K；⑥ 换 embedding（务必重建索引）；⑦ 元数据过滤/分区。

**3. 怎么评估 RAG？**
骨架：① 分层：检索指标（Recall@K / Hit@K / MRR）与生成指标（Faithfulness / 引用准确率 / 拒答准确率）；② 评测集 20–50 条，覆盖事实型、多跳、无答案、易混淆四类；③ bad case 四类归因（切片 / 未召回 / 召回未用 / 瞎编）；④ 改一次跑一次，指标存下来形成对比；⑤ 上线后把线上 bad case 回流。

**4. 文档里没有答案时你希望系统怎么做？**
骨架：① 明确输出"未收录"并说明检索范围，而不是编；② 用相似度阈值短路，避免把噪声喂给模型；③ prompt 里给拒答 few-shot；④ 评测集必须包含 `must_refuse` 用例；⑤ 统计"该拒答率"作为上线门槛指标。

**5. RAG 和微调怎么选？**
骨架：① 事实类、会变、要溯源 → RAG；② 风格/格式/判断方式、标注数据足 → 微调；③ 微调不擅长记事实（过时、不可溯源）；④ 两者常组合：检索供事实 + 微调固定输出；⑤ 决策依据是数据特征与更新频率，不是模型能力。

**6. 为什么要两阶段检索？**
骨架：① bi-encoder 可预计算 → 快，用于万级召回；② cross-encoder 精度高但只能对候选集算 → 慢，用于几十条精排；③ 组合用小成本拿到接近精排的效果；④ Rerank 救不回没召回的，所以召回 K 要给足；⑤ 代价是延迟与成本，要按预算定 K。

**7. `chunk_size` 怎么定？**
骨架：① 没有通用最优值，必须用评测集自测；② 中文常见起点 300–500 汉字 + 10%–15% overlap（英文经验不要照搬）；③ 结构清晰的文档优先按标题切，长度只做兜底；④ 表格/代码整体保留；⑤ 用"答案要求的最小上下文"倒推块大小（FAQ 短、手册长）。

**8. 长上下文会取代 RAG 吗？**
骨架：① 不会，两者解决不同问题（定位 vs 通读）；② 全量直塞的成本随长度线性增长、延迟高，且知识更新要重来；③ RAG 的优势是可溯源、增量更新、权限过滤；④ 组合最佳：RAG 选块 + 大窗口读整章；⑤ 小知识库（< 20 页）+ prompt caching 确实可以直接塞。

**9. 引用怎么做到不幻觉？**
骨架：① 只允许引用资料编号，禁止外部来源名；② 生成后校验编号存在性与范围；③ 句子级依据校验（拆句 + 词面重合）；④ 校验失败降级为"未收录"或重试一次；⑤ 引用准确率作为可监控指标（不需要人工标注）。

**10. 多租户场景的权限怎么做？**
骨架：① 权限过滤必须在**检索层**用元数据 pre-filter 强制注入，不能靠 prompt；② 索引元数据与权限系统同步（含权限变更的增量更新）；③ 引用与结果展示做二次校验；④ 对抗测试（低权限账号构造敏感查询）纳入回归；⑤ 越权属于事故级别，要有审计日志。

**11. 表格、代码、扫描件这些难啃的文档怎么办？**
骨架：① 表格：整体保留 + 每块带表头 + 自然语言描述；必要时把表格转成"行级自然语言"再索引；② 代码：按语法单元切 + 带文件路径与导入；③ 扫描件/图片：先 OCR（保留版面信息），OCR 质量决定上限；④ 结构化数据能查库就别进向量库；⑤ 都要用评测集验证"这类文档的问题能不能被召回"。

**12. 索引更新策略怎么设计？**
骨架：① 内容哈希判断是否需要重算；② 以 `doc_id` 为单位增量替换（删旧块 + 写新块）；③ 切块规则变更 = 全量重建 + 双索引切换；④ 权限变更同步到元数据；⑤ 监控"文档变更事件数 ≈ 索引变更事件数"。

- [RAG 原始论文（Lewis 等，2020）](https://arxiv.org/abs/2005.11401) —— **看什么**：RAG 的原始定义与训练方式；**看到什么程度**：知道"现代 RAG 大多只借用了它的推理形态（检索 + 生成），并未训练"，避免概念混淆。
- [Dense Passage Retrieval（Karpukhin 等，2020）](https://arxiv.org/abs/2004.04906) —— **看什么**：为什么双塔（bi-encoder）能预计算、以及它的精度损失来自哪里；**看到什么程度**：能与 cross-encoder 的取舍对上。

- [Reciprocal Rank Fusion（Cormack 等，2009）](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf) —— **看什么**：RRF 的公式与"免归一化、免调参"的动机；**看到什么程度**：能手写 RRF 并解释 k=60 这个经验常数的角色。
- [MTEB 榜单](https://huggingface.co/spaces/mteb/leaderboard) —— **看什么**：中文/多语言检索任务的排名与维度、成本；**看到什么程度**：把它当候选池，最终用**自己的评测集**决定选谁。
- [Lost in the Middle: How Language Models Use Long Contexts](https://arxiv.org/abs/2307.03172) —— **看什么**：长上下文里位置对利用率的影响；**看到什么程度**：理解它解释了"资料放前面还是放后面"的经验，并据此做自测。
