# 专题：部署、成本与性能（Deployment, Cost & Performance）

> **一句话** · 把 demo 变成"别人能用的服务"，要同时处理三件事：**延迟**（用户等不等得住）、**成本**（单位经济学成不成立）、**可靠性**（挂一次要付多大代价）。
> **本专题对应 `docs/第13章 部署成本与性能`**，配套代码 `code/ch13_deploy.py`；前置：[[docs/第02章 大模型基础]]（token 与计价）、[[docs/第05章 ReAct最小Agent-Loop]]（循环的放大效应）。
> **读完你能回答：**
> 1. 用户说"卡"，你怎么区分是 TTFT 慢还是 TPOT 慢？分别怎么优化？
> 2. 一个 5 步 Agent 的月成本怎么估、怎么降到 1/3？哪些手段的收益最大？
> 3. 超时、重试、降级、幂等这四件事在你系统里的具体参数是什么？为什么"无限重试"比"直接失败"更糟？

## 一、本质：从"能跑"到"能被人用"

上线第三天，有用户反馈"点一下就转圈"，他打开账单发现单日成本 400 元——而系统一天只有 200 次调用。**问题不在模型慢，也不在模型贵，在他自己的架构里**：5 步 Agent 要发 6 次请求，每次都重发全部历史。

Demo 和服务之间隔着四道门：**延迟**（用户 3 秒无反馈就关了）、**成本**（每天 10 万次就是 2 万/天，必须有预算上限与单位经济学）、**可靠性**（超时、重试、降级、幂等、可观测、可回滚）、**形态**（CLI / Web / Bot / API，别人能自己跑起来）。**核心认知**：Agent 的性能问题大多不是"模型慢"，而是**你自己的架构造成的**——循环把 token 变成**平方级**、延迟变成**串行累加**。**一句话原则**：**先测、再改、再谈优化**——没有 TTFT / TPOT / P95 / 每成功一次的成本这四个数，任何"优化"都是猜测。**本文把这四道门背后的工程取舍讲清楚。**

## 二、决策表

### 2.1 发布形态选型

| 形态 | 适合 | 代价 | 什么时候选它 |
|---|---|---|---|
| **CLI 脚本** | 自己用、团队内部、批处理 | 没有界面、要会命令行 | 第一次交付、验证价值（最快） |
| **本地 Web（FastAPI + 简单前端）** | 给非技术用户试用 | 要处理并发与超时、要做流式 | 有 3–5 个真实用户开始反馈 |
| **Bot（钉钉/飞书/Slack）** | 团队日常使用 | 平台限制（超时、消息长度、消息频率） | 嵌入既有工作流，零学习成本 |
| **HTTP API（给别人调）** | 被其他系统集成 | 要鉴权、限流、配额、版本管理、SLA | 成为别人依赖的上游 |
| **批量任务（离线跑）** | 日报、回归评测、数据加工 | 无交互，结果要落盘与通知 | 时效要求以小时/天计 |

**选型口诀**：**先 CLI 验证价值 → 有真人用户再 Web/Bot → 被系统依赖才做 API。** 过早做 API 会先把鉴权、限流、配额这些"没人用"的工程做完。

### 2.2 缓存层级选择

| 层级 | 命中条件 | 收益 | 风险 | 实现成本 |
|---|---|---|---|---|
| **前缀缓存（Prompt Caching）** | 请求前缀（system + 固定文档）逐字节相同 | 命中部分输入费降 5–10 倍 | 前缀里插入变内容就全部失效 | 低（多数服务商自动或一个参数） |
| **精确结果缓存** | 请求（含参数、模型、版本）完全一致 | 100%（零成本） | 命中率通常很低；**参数不同不能复用** | 低 |
| **语义缓存** | 语义相似度 > 阈值 | 命中率显著提高 | **答错的风险**（相似问题答案相反） | 中（要向量检索 + 阈值调优） |
| **工具结果缓存** | 同一个工具 + 同一参数 | 高（外部 API 调用常是瓶颈） | 数据过期（要 TTL） | 低 |

**选型规则**：**前缀缓存与工具缓存是"必做"**；精确缓存顺手做；**语义缓存只在低风险场景开**（FAQ、文档问答），且必须带 TTL、相似度阈值、以及"命中后仍要带来源标注"。

### 2.3 哪类错误该重试

| 错误类型 | 例子 | 重试？ | 理由 |
|---|---|---|---|
| **限流（429 rate_limit）** | 请求太密 | ✅ 指数退避 + 抖动 | 等待有效 |
| **服务端 5xx** | 502 / 503 / 504 | ✅ 有限次 + 退避 | 对方临时故障 |
| **超时** | 读超时 | ⚠️ 只在幂等操作上重试 | 不确定对方是否已执行 |
| **网络抖动** | 连接重置 | ✅ 少量次数 | 通常瞬时 |
| **余额/配额不足（429 insufficient_quota）** | 没钱了 | ❌ | 重试一万次也没用 |
| **401 / 403** | key 错、权限不足 | ❌ | 配置问题，重试固定失败 |
| **400 参数错误** | 上下文超限、类型错 | ❌ | 要改输入，不是重发 |
| **模型不存在 404** | 名字写错 | ❌ | 配置问题 |
| **业务校验失败** | 工具说参数不合法 | ❌（要把错误喂回模型） | 让模型改参数，不是重发请求 |

**铁律**：**重试必须带"最大次数 + 退避 + 抖动 + 总预算"四件套。** 无上限重试在故障时会把对方打垮，也把自己的成本打爆（重试风暴）。

### 2.4 降级策略选择

| 触发 | 降级动作 | 用户看到什么 |
|---|---|---|
| 主模型超时/不可用 | 换小模型（质量降级但可用） | "本次由快速模型回答" |
| 工具不可用 | 跳过该工具，用已有信息作答 + 标注 | "未能获取实时数据" |
| 检索为空 | 明确说"没找到依据"而不是硬答 | "知识库中未找到相关内容" |
| 预算耗尽 | 排队/次日处理/只做简易模式 | "今日额度已用完" |
| 上下文超限 | 压缩历史后重试一次 | 无感知（尽量） |

**降级设计原则**：**降级路径必须事先写好并可测试**（不是"出事了再想"）；**降级要可见**（trace 记录 + 必要时告知用户）；**不可降级的动作宁可失败**（转账、删除不能"降级执行"）。

### 2.5 模型分级的分配规则

| 环节 | 用什么模型 | 理由 |
|---|---|---|
| 意图分类 / 路由 / 参数抽取 | 便宜小模型（temperature 0–0.3） | 任务简单、量大、要稳定 |
| 工具选择与循环推进 | 中小模型 | 这是成本大头（每步都调用） |
| 最终写作 / 复杂推理 | 强模型 | 只调用 1 次，值这个钱 |
| 评测的模型评审（judge） | 强模型 | 判定器要准，否则评测不可信 |
| 离线批处理 | 便宜的批量通道 | 时效要求低就换价格 |

## 三、工程实现要点

### 3.1 三个延迟指标：先分清，再优化

| 指标 | 定义 | 用户感受 | 优化手段 |
|---|---|---|---|
| **TTFT**（Time To First Token） | 从发请求到收到**第一个 token** | "点了之后多久有反应" | 流式输出、缩短输入（前缀缓存）、减少首步工作量、模型/服务商选择、就近部署 |
| **TPOT**（Time Per Output Token） | 首 token 之后**每个 token 的平均生成时间** | "字出得快不快" | 减少输出长度（输出限制）、换更快的模型、避免长输出重试 |
| **P95 / P99（端到端）** | 95%/99% 的请求在多少时间内完成 | "最慢的那批有多慢" | 分层超时、并行化、减少步数、排队与限流、缓存 |

**四个必须知道的结论**：

1. **平均值骗人**：100 个请求里 95 个 1 秒、5 个 30 秒，平均 2.5 秒很好看，但那 5 个用户已经在投诉了。**报 P95/P99，不报平均。**
2. **P95 由最慢的那一步决定**：Agent 6 次串行请求，若每步 P95 是 3 秒，整体 P95 可能到 18 秒 —— **先砍步数，再谈单步优化。**
3. **TTFT 与 TPOT 的优化方向相反**：TTFT 想让"第一句话快出来"（流式、短输入），TPOT 想让"整体吐字快"（短输出、快模型）。**先确定用户在抱怨哪一个。**
4. **超时值要按分位数设，不按平均设**：`超时 = P99 × 1.5` 起步，再按业务容忍度调整。设成平均值会砍掉一大批本可成功的请求。

### 3.2 流式输出：Agent 场景下用户看到什么

流式（streaming）在 Agent 场景不是"更酷"，而是**感知延迟的唯一解**：把 15 秒的等待变成"1 秒内看到它在动"。

| 阶段 | 有流式 | 无流式 |
|---|---|---|
| 首个 token | 1–2 秒内有反馈 | 全程空白 |
| 模型决定调工具（`tool_calls` 分片到达） | 可以显示"正在查询知识库…" | 空白 |
| 工具执行期间 | 显示"已调用 X，等待结果…"（**这是纯等待，必须给文案**） | 空白 |
| 最终答案 | 逐字输出 | 一次性出现 |

**必须做的三件事**：

1. **工具调用阶段要有明确状态文案**（"正在检索…"），因为这段时间是**纯等待**，没有任何 token 可显示；
2. **不要边流式边做会失败的副作用**（用户已经看到一半答案，后面崩了体验更差）—— 危险动作等确认后再执行；
3. **流式的成本要单独看**：流式不减少 token，但会**占用连接更久**（并发能力下降），要按"并发连接数"而不是"QPS"做容量规划。

**分片解析的坑**：`tool_calls` 的 `arguments` 是**分片拼接**的，必须累积完再 `json.loads`；对每个分片解析 JSON 必然失败。

### 3.3 成本七种手段（按收益/成本比排序）

| # | 手段 | 怎么落地 | 典型收益 | 代价/风险 |
|---|---|---|---|---|
| 1 | **模型分级** | 路由/抽取/循环用小模型，写作与 judge 用强模型 | **最高**（数量级差异） | 效果可能下降，需评测验证 |
| 2 | **前缀缓存** | system + 固定文档逐字节固定，放在请求最前面 | 命中部分输入费降 5–10 倍 | 前缀里插入动态内容就全失效 |
| 3 | **历史压缩** | 超阈值摘要 + 只留最近 N 轮 + 工具结果截断 | 输入 token 降 30%–70% | 丢信息（要保留指针与关键约束） |
| 4 | **输出限制** | 明确要求"3 条以内""表格形式"；设 `max_tokens` | 输出费（单价是输入 3–4 倍） | 设太小会截断（`finish_reason=length`） |
| 5 | **结果缓存** | 精确缓存（相同请求）+ 工具结果缓存（TTL） | 重复请求零成本 | 命中率依赖场景；语义缓存有答错风险 |
| 6 | **批量/异步** | 非实时任务走批量通道、错峰跑 | 单价常见 5 折 | 有时效损失，要改架构 |
| 7 | **预算熔断** | 单次/单日/单用户上限，超限即停或降级 | 防止"一晚烧光" | 要在正常请求里也留余量 |

**两条纪律**：优化的是"**每成功一次的成本**"（含失败重跑），不是单次调用的 token；别为省 token 砍掉必要的系统提示 —— 输出变差 → 重试变多 → 总成本反而上升。

### 3.4 可靠性五件套：超时、重试、降级、幂等、限流

```text
分层超时（每层都要有，且内层 < 外层）
  连接超时 3–5s  <  单次模型调用超时 30–60s  < 单步工具超时 10–30s  <  整个 Agent 运行 120–300s  <  用户侧请求 网关 300s
```

**为什么必须分层**：只有最外层超时，内层会继续跑（继续烧钱），用户已经走了你还在算；内层超时可以让 Agent **换条路走**（换个工具、降级回答），外层的超时是最后一道闸。

**指数退避 + 抖动（jitter）**：

```python
def backoff(attempt, base=0.5, cap=8.0):
    """attempt 从 0 开始：0.5s、1s、2s、4s、8s（封顶）+ 抖动，避免重试同时打过去。"""
    return min(cap, base * (2 ** attempt)) * (0.5 + random.random() * 0.5)
```

**幂等**：每个会改状态的调用都带幂等键（`run_id + step_id + 动作hash`），重试时服务端识别到重复键就返回上次结果。**没有幂等键的重试是危险的** —— 可能重复发信、重复扣款、重复建单。

**限流与排队**：并发上限（信号量）+ 队列长度上限 + 超限返回 429 或排队提示。**没有并发上限的服务，在流量峰值时会自己把自己打死**（每个请求都在重试，成本与延迟双爆）。

### 3.5 缓存分层：从精确匹配到语义缓存

```text
L0 前缀缓存   → 逐字节相同的请求前缀（system + 固定资料），服务商侧自动生效
L1 精确结果缓存 → key = hash(model + 版本 + 参数 + 完整输入)，本地 KV / Redis
L2 工具结果缓存 → key = hash(工具名 + 参数)，带 TTL
L3 语义缓存   → 向量检索 + 相似度阈值，命中后返回缓存答案（风险最高）
```

**语义缓存的四个风险与对策**：

| 风险 | 例子 | 对策 |
|---|---|---|
| 相似但答案相反 | "如何开启自动续费" vs "如何关闭自动续费" | 阈值调高 + 反问句/否定词检测 |
| 时效性 | 缓存的股价、库存、订单状态 | 带时效类问题禁止走语义缓存 |
| 个性化 | 不同用户的"我的订单" | key 里必须带用户/租户标识 |
| 静默错误 | 用户不知道拿的是缓存答案 | 标注来源与时间（"3 分钟前的相同问题答案"） |

**判断标准**：**语义缓存只用于"答案稳定、错了代价小、可标注"的场景。** 一个会执行动作的 Agent（下单、改配置）**不该**用语义缓存做入口。

### 3.6 成本估算模板（可直接算）

```text
单次任务成本 = Σ(每次调用的 prompt_tokens × 输入单价 + completion_tokens × 输出单价)
月成本       = 单次任务成本 × 日请求量 × 30 ÷ 成功率        ← 成功率把失败重跑算进来
```

算例（按 [[02-Wiki/速查表/02-Token与成本速查]] 的示例价表 `deepseek-chat`：输入 ¥2/百万、输出 ¥8/百万）：

| 方案 | 输入 token | 输出 token | 单次成本 | 日 1 万次 | 说明 |
|---|---|---|---|---|---|
| 一次问答 | 350 | 200 | ¥0.0023 | ¥23 | 无循环 |
| 3 步 Agent | 1,800 | 450 | ¥0.0072 | ¥72 | 历史重发 |
| 6 步 Agent | 7,380 | 630 | ¥0.0198 | ¥198 | 步数翻倍，成本近 3 倍 |
| 6 步 Agent + 前缀缓存 + 历史压缩 | ~3,000 | 630 | ¥0.0110 | ¥110 | 输入侧省 ~45% |

**看这张表要得到两个结论**：① **步数是最强的成本杠杆**（6 步比 3 步贵 2.7 倍）；② **输入侧永远是主要战场**（历史重发占大头）。

### 3.7 上线检查清单（发布前逐条过）

- [ ] **超时**：连接/单次调用/工具/整体/网关五层都设了，且内层 < 外层；
- [ ] **重试**：次数上限（建议 ≤3）+ 指数退避 + 抖动 + 只对可重试错误生效；
- [ ] **幂等**：所有会改状态的调用都有幂等键；
- [ ] **降级**：至少两条降级路径（换小模型、跳过工具），且被测试过；
- [ ] **限流**：并发上限 + 队列上限 + 超限时的用户可见提示；
- [ ] **预算熔断**：单次 / 单日 / 单用户三层上限，超限行为明确（停 or 降级）；
- [ ] **成本可观测**：每次结束打印 `steps / tokens / cost / elapsed`，累计到日志或看板；
- [ ] **trace 落盘**：出问题能复盘（见 [[02-Wiki/专题总结/08-评估可观测性与安全]]）；
- [ ] **流式**：工具执行阶段有状态文案；`tool_calls` 分片按累积解析；
- [ ] **缓存与脱敏**：前缀缓存已启用（固定内容在最前）、工具结果缓存带 TTL、日志与 trace 已脱敏；
- [ ] **密钥**：从环境变量读，未进代码仓库、未进 trace、未进提示词；
- [ ] **评测与回滚**：回归测试能跑（`AGENT_MOCK=1` 最快）、改坏了能一键回到上一版（代码 + 提示词 + 模型名都算配置）。

## 四、横向对比

### 4.1 发布形态对比

| 维度 | CLI | 本地 Web | Bot | HTTP API | 批量 |
|---|---|---|---|---|---|
| 上手速度 | 最快 | 中 | 中 | 慢 | 快 |
| 并发支持 | 无（单次） | 中（要自己管） | 受平台限制 | 高（要限流） | 高 |
| 鉴权/配额 | 不需要 | 需要 | 平台代管 | **必须自己实现** | 视场景 |
| 超时约束 | 无 | 网关/浏览器 | **平台超时最严** | 调用方定 | 无 |
| 最适合的验证目标 | 价值验证 | 用户反馈 | 嵌入工作流 | 被系统集成 | 数据加工 |

### 4.2 缓存层级对比

| 维度 | 前缀缓存 | 精确结果缓存 | 工具结果缓存 | 语义缓存 |
|---|---|---|---|---|
| 命中率 | 高（稳定前缀） | 低 | 中–高 | 高 |
| 单次收益 | 输入费 ×5–10 降 | 100% | 100%（含外部调用） | 100% |
| 正确性风险 | 无 | 无（key 严格） | 数据过期 | **有（答错）** |
| 实现成本 | 极低 | 低 | 低 | 中 |
| 建议 | **必做** | 顺手做 | **必做** | 谨慎，限低风险场景 |

### 4.3 延迟优化手段的收益对比

| 手段 | 影响 TTFT | 影响 TPOT | 影响 P95 | 代价 |
|---|---|---|---|---|
| 流式输出 | **显著改善**（感知） | 无 | 无（总时长不变） | 要处理分片与状态文案 |
| 减少步数（更好的提示词/工具） | 改善 | — | **显著改善** | 需要工具与提示词设计功力 |
| 前缀缓存 | 改善（服务端少算） | — | 改善 | 前缀要稳定 |
| 并行无依赖子任务 | 改善 | — | **显著改善**（按最慢分支算） | 只适用于无依赖任务 |
| 换更快的模型 | 改善 | 改善 | 改善 | 质量与成本取舍 |

**排序建议**：**先砍步数（收益最大）→ 再上流式（改善感知）→ 再前缀缓存（省钱又提速）→ 最后才换模型。**

## 五、常见故障与排查（8 条）

### 故障 1：并发上来后 token 与成本爆炸

- **现象**：低并发时成本正常，一到 20 并发，账单翻十几倍，且延迟飙升。
- **定位**：看 trace 里的步数与重试次数；看是否有"每个请求都在重试"；统计 QPS × 平均步数 × 平均 prompt 大小。
- **解决**：设并发上限（信号量）与队列上限；限制单请求最大步数；限制重试总预算（次数 + 时间 + 金额）；对超出部分快速失败而不是无限排队。

### 故障 2：缓存击穿 / 缓存雪崩

- **现象**：缓存刚过期的一瞬间大量请求同时打到下游（或模型），延迟尖刺、成本陡增。
- **定位**：看缓存过期时间的分布（是否同一时刻批量过期）；看尖刺时刻的下游 QPS。
- **解决**：TTL 加随机抖动（±10%–20%）；热点 key 用"单飞"（single-flight，同一 key 只允许一个请求回源，其余等待）；预热常用 key；对回源做并发限制。

### 故障 3：重试风暴

- **现象**：下游一开始变慢，你的重试让它彻底崩掉；成本同时翻倍。
- **定位**：统计重试次数分布与"重试贡献的请求量占比"；看是否所有重试同时到达。
- **解决**：指数退避 + **抖动**；最大次数（≤3）；熔断（连续失败 N 次后暂停调用一段时间，直接走降级）；区分"可重试/不可重试"错误（见 §2.3，429 insufficient_quota 重试毫无意义）。

### 故障 4：超时没设或设错，请求堆积

- **现象**：并发一高，请求全卡住，内存/连接数持续上涨，最后整体不可用。
- **定位**：检查每一层是否都有超时；检查内层超时是否大于外层（顺序错了等于没设）。
- **解决**：五层超时全补齐（连接/单次调用/工具/整体/网关）；内层必须小于外层；超时后必须**释放资源并写 trace**（否则你不知道有多少请求是这样死的）。

### 故障 5：成本没有上限，一晚烧光预算

- **现象**：某个死循环 + 没有熔断，一夜之间跑出几百块。
- **定位**：统计单请求最大 token 与最大步数；检查是否有 `max_steps` 与金额上限。
- **解决**：三层熔断（单次任务 / 单日 / 单用户）；单请求步数上限（Agent 必备）；超限行为明确（停 + 告警，或降级为小模型）；把成本写进日志并在看板上展示趋势。

### 故障 6：流式下内容重复或 JSON 解析失败

- **现象**：前端出现重复文字；或工具参数解析报 `Expecting value`。
- **定位**：检查是否对每个分片都做了渲染/解析；检查 `tool_calls` 的 `arguments` 是否是分片累积后再解析。
- **解决**：按 `delta` 增量拼接、只在 `finish_reason` 到达后做完整校验；工具参数必须**累积**再 `json.loads`；重连/重试时要带上已接收内容的偏移，避免重复渲染。

### 故障 7：降级路径从没被执行过，出事时才发现是坏的

- **现象**：主模型一挂，降级逻辑报错或输出空结果。
- **定位**：搜 trace 里的降级事件（有没有出现过）；检查降级分支是否有测试。
- **解决**：把降级当功能测试（定期强制触发一次，或在评测集里加"主模型不可用"的用例）；降级必须可见（trace + 日志 + 必要时告知用户）。

### 故障 8：密钥或用户数据进了日志/提示词

- **现象**：日志里出现完整 API Key；或 trace 里带着用户的身份证号。
- **定位**：全文搜索日志与 trace 文件里的 `sk-`、手机号、邮箱等模式。
- **解决**：日志脱敏（正则替换 + 白名单字段）；密钥只从环境变量读、**永不进提示词与 trace**；`observation` 与用户输入统一截断与脱敏；把"日志脱敏"写进上线检查清单。

## 六、面试要点（11 题，回答骨架）

**1. P99 延迟怎么优化？**
- 先归因：是 TTFT（首字节）慢、TPOT（吐字）慢，还是步数多导致的总时长长；
- Agent 的 P99 主要由**最慢的一步 × 步数**决定 → 先砍步数、再并行化无依赖步骤；
- 分层超时 + 熔断，把"慢请求"变成"快速失败的降级请求"，避免拖垮整体；
- 缓存（前缀/结果/工具）+ 就近部署 + 换更快模型；
- 收尾：**P99 是排队与尾部问题，必须看分位数，且要在压测下验证。**

**2. TTFT 怎么优化？**
- TTFT 由"输入长度 + 首步工作量 + 排队"决定；
- 手段：流式输出（感知层面立刻改善）、缩短输入（前缀缓存、历史压缩）、减少工具/技能目录的常驻体积、选 TTFT 更优的模型与服务商；
- 注意：**TTFT 与 TPOT 的优化方向可能相反**（短输入利于 TTFT，短输出利于 TPOT）；

**3. 成本怎么降？（要给排序，不要罗列）**
- 第 1 位 **模型分级**（路由/抽取/循环用便宜模型，写作与 judge 用强模型），数量级差异；
- 第 2 位 **减步数**（工具与提示词优化，顺带降延迟）；
- 第 3 位 **前缀缓存 + 历史压缩 + 观察结果截断**（输入侧是主战场，历史重发常占 70%+）；
- 第 4 位 结果/工具缓存、批量通道、输出限制；
- 纪律：算 **每成功一次的成本**（含失败重跑）+ 三层预算熔断。

**4. 怎么保证可用性？**
- 五件套：分层超时、有限重试（退避 + 抖动）、降级路径、幂等、限流排队；
- 熔断：下游连续失败就暂停调用走降级，别把对方与自己一起打死；降级必须可测可见（定期演练 + trace 记录）；
- 幂等键保证重试安全（不重复扣款/发信/建单）；

**5. 怎么做容量规划？**
- 先测单请求画像：平均/P95 的 TTFT、总时长、token 数、并发占用时长（流式会显著拉长）；
- 按并发算：`所需并发 ≈ 峰值 QPS × 平均端到端时长`；流式还要看**连接数**而不是 QPS；
- 留余量：按峰值的 2 倍配置并发上限，用队列 + 限流兜住超出部分；
- 成本侧按 `月请求量 × 每成功一次的成本` 估算，并设熔断；

**6. 什么错误该重试？**
- 该重试：429 rate_limit（退避）、5xx、网络抖动；不该重试：401/403、404、400 参数错误、**429 insufficient_quota（没钱）**、业务校验失败（要把错误喂回模型改参数）；
- 超时只在幂等操作上重试（不确定对方是否已执行）；
- 重试四件套：最大次数、指数退避、抖动、总预算（时间 + 金额）。

**7. 语义缓存的风险是什么？**
- 相似但答案相反的问题（"如何开启/关闭自动续费"）会命中缓存；时效性问题（股价、库存、订单状态）不能走语义缓存；
- 个性化问题必须把用户/租户标识放进 key；命中后要标注"这是 X 分钟前的相同问题答案"，不能静默；
- 结论：**只在答案稳定、错了代价小、可标注的场景开语义缓存**；会执行动作的入口不该用它。

**8. 流式输出在 Agent 场景要注意什么？**
- 工具执行阶段是纯等待，**必须有状态文案**（"正在检索…"），否则用户又以为卡死了；
- `tool_calls.arguments` 是**分片**到达的，必须累积后统一解析；不要在流式过程中执行不可回滚的副作用；
- 容量规划按**并发连接数**算，不按 QPS；

**9. 前缀缓存怎么用才有效？**
- 前缀必须**逐字节稳定**：system + 固定文档放在最前面，动态内容（用户输入、时间戳、随机 id）放最后；
- 凡是"每次都在变"的内容插进前缀，就会导致整段缓存失效（这是最常见的失效原因）；
- 缓存命中价常见是输入价的 1/5–1/10，且能顺带改善 TTFT；

**10. 预算熔断怎么设计？**
- 三层：单次任务（步数 + 金额）、单日（总额）、单用户（配额）；
- 超限行为要明确（硬停 + 告警，或降级为小模型/简易模式）；阈值要能在 trace 里复盘（谁触发的、当时花了多少）；

**11. 面试官追问："你的服务上线后最怕什么？"**
- "看起来正常但一直在烧钱"（死循环、无限重试、缓存全不命中）；
- "尾部延迟拖垮整体"（没有分层超时与限流，慢请求堆积把服务拖死）；
- "降级路径是坏的"（从没跑过，出事才发现）与"危险动作被自动执行"（护栏，见 [[02-Wiki/专题总结/08-评估可观测性与安全]]）；
- 对应的四件事：**成本看板 + 分位数延迟 + 降级演练 + 权限门** —— 这是我理解的"生产就绪"。
