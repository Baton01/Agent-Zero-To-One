# 专题：记忆与上下文工程

> **一句话** · 模型没有状态，**上下文窗口是唯一的工作台，也是稀缺资源**；记忆管理的本质是"什么信息、在什么时候、以什么形式进入上下文"的取舍，而这场取舍永远发生在成本、注意力、可控性三者之间。
>
> **本专题对应：** `docs/第07章 记忆与上下文工程`、`docs/第02章 大模型基础`（窗口与成本）、`docs/第05章 ReAct最小Agent-Loop`（循环中的状态）、`docs/第11章 多智能体协作`（上下文隔离）、`docs/第14章 构建你自己的Agent框架`
>
> **读完你能回答：**
> 1. 一段 20 轮的任务型对话，哪些信息必须**逐字**保留、哪些可以压成摘要、哪些应该被抽成结构化槽位？
> 2. 你的摘要器把"订单号 DP1002 已确认退款"压成了"用户咨询退款"——怎么在架构上**防止这类丢失再次发生**？
> 3. 同一个问题，20 轮会话的 token 成本是 5 轮会话的多少倍？从哪三个地方能把它降下来？

---

## 一、本质

有位同学的摘要器把"订单号 DP1002 已确认退款"压成了"用户咨询退款"，第二天客服拿着这句话去查系统，什么也查不到——**摘要丢了 ID，链路就断了**。

先接受两条硬约束，后面所有设计都是它们的推论：**成本与注意力都随上下文长度恶化**——API 无状态意味着每一轮都要重发全部历史，累计输入是平方级；长上下文里模型对**中间位置**信息的利用率还会下降。**上下文里没有的信息，模型永远不会知道**——所以"忘记"是一个必须被设计的行为，而不是可以交给模型的好运。记忆系统因此由四个动作组成，缺一不可：**选择（Select）**、**压缩（Compress）**、**隔离（Isolate）**、**编排（Orchestrate）**；判断方案优劣的唯一标准是**在给定预算下，关键信息的保真度是否够用，且成本可控。本文把这个标准落到每一次取舍上。**

## 二、决策表

### 2.1 什么信息放哪里（核心表，背下来）

| 信息类型 | 放哪一层 | 为什么 | 生命周期 | 失效/更新策略 |
|---|---|---|---|---|
| 角色、规则、输出格式、安全约束 | **system（每轮固定前缀）** | 每轮都要遵守；固定前缀可被 prompt caching 覆盖 | 全程 | 版本化，改动能回归测试 |
| 工具说明（schema） | **请求的 tools 字段** | 模型选工具的唯一依据 | 全程 | 工具裁剪；数量大时分层加载 |
| 最近 3–5 轮对话原文 | **messages 历史** | 精确措辞与指代（"那个订单"）只在这里可解析 | 滚动 | 超出条数即进入压缩 |
| 更早的对话 | **摘要 + 结构化槽位** | 保留脉络与关键实体，丢弃寒暄与重复 | 会话级 | 每次压缩重新生成，保留原槽位 |
| 用户长期偏好/事实（住址、口味、身份） | **外部存储（键值/文档）** | 跨会话、体积小、按需注入 | 长期 | TTL + 用户可查看/删除 |
| 任务中间产物（长文档、日志、抓取结果） | **外部文件 + `doc_id` 引用** | 体积大，一次用不完 | 任务级 | 任务结束清理 |
| 知识型资料 | **RAG 检索结果** | 与用户无关、随时更新（`docs/第08章`） | 每次查询 | 索引重建 |
| 大体积工具返回值 | **截断摘要 + 资源引用** | 全文塞进去会挤掉指令 | 单步 | 按需分页重读 |

### 2.2 压缩策略怎么选

| 策略 | 保真度 | 成本 | 可控性 | 适用 | 主要风险 |
|---|---|---|---|---|---|
| **滑动窗口**（丢最早的） | 低 | 0 | 高 | 短任务、闲聊 | 丢掉早期的关键约束（用户第 1 轮说的订单号） |
| **摘要（LLM 生成）** | 中 | 每次压缩 1 次调用 | 中 | 长对话的通用方案 | **丢关键信息**（最常见事故）；多次压缩后失真累积 |
| **结构化抽取（槽位）** | **高** | 1 次调用（可与摘要合并） | **高** | 任务型对话（订单、工单、预约） | 槽位设计不全就会漏；灵活性低 |
| **滑动窗口 + 摘要 + 槽位（推荐组合）** | 高 | 1 次调用 | 高 | 生产默认 | 实现稍复杂 |

### 2.3 该不该"记住"这条信息

| 判断 | 记 | 不记 |
|---|---|---|
| 来源 | **用户明确陈述**（"我的地址是…"） | 模型推断（"用户可能住在上海"） |
| 时效 | 有明确时效或用 TTL 兜底 | 一次性的临时状态（"我正在查第 3 页"） |
| 复用 | 跨会话仍成立（偏好、身份、长期约束） | 只在本任务内有意义（中间结果） |
| 敏感度 | 用户已授权、且确有需要 | 密码、证件号、健康信息（默认不落盘） |
| 冲突 | 能与旧条目比较并覆盖 | 与既有条目冲突且无法判定（应**问用户**而不是二选一） |

## 三、工程实现要点

### 3.1 三层记忆的存储与职责

| 层 | 载体 | 写什么 | 谁负责压缩 | 典型容量 |
|---|---|---|---|---|
| **短期（short-term）** | `messages` 数组 | 最近几轮原文 + 本轮工具结果 | 达到水位时触发压缩 | 占预算 20%–30% |
| **会话（session）** | 摘要文本 + 结构化槽位（dict） | 目标、已确认事实、待办、结论 | 压缩器（每次压缩重写） | 占预算 5%–10% |
| **长期（long-term）** | 落盘存储（JSON/SQLite/向量库） | 用户偏好、稳定事实 | 写入时过滤 + 定期清理 | 不占预算，按需检索注入 |

```python
# Python 3.9 兼容：三层协作的最小形状（节选，完整实现在 code/ch07_memory.py）
class Memory:
    def __init__(self, llm, budgets):
        self.short_term = []          # [{"role": ..., "content": ...}]
        self.slots = {}               # 结构化事实：{"order_id": "DP1002", "goal": "退款"}
        self.long_term = LongTermStore("memory.json")
        self.budgets = budgets        # {"system": 800, "history": 2000, "retrieval": 2500, "output": 800}

    def build(self, user_input, retrieved=None):
        """每轮重新组装，而不是 append-only 一路堆积。"""
        system = render_system(self.slots)                 # 槽位渲染进 system
        history = compress_if_needed(self.short_term, self.budgets["history"])
        memory_block = self.long_term.render(user_input, top_k=3)   # 只注入命中的记忆
        return [{"role": "system", "content": system + memory_block}] + history + \
               [{"role": "user", "content": user_input}]
```

**关键决定：`build()` 每轮重新组装**。append-only 的实现（把一切堆进 `messages`）在 10 轮内就会失控；动态组装让你能随时"把某类信息降权或剔除"。

### 3.2 压缩：三件套一起做，缺一件就会丢信息

一次合格的压缩同时产出三样东西：

```text
① 摘要（脉络）：用户在处理订单 DP1002 的退款，已确认商品未拆封，等待退款到账。
② 关键实体（逐字）：订单号 DP1002；金额 ¥128.50；承诺时效 3 个工作日；用户手机号尾号 8899。
③ 待办与结论：已提交退款申请（单号 RF-2031）；待确认：退款到账时间。
```

- **②必须逐字保留**，不能被"二次概括"（摘要器最爱把数字和编号写模糊）。做法：把关键实体外置到 `self.slots`，压缩只动摘要文本，**槽位永不被摘要覆盖**。
- **压缩要触发在"水位"而不是"轮数"**：按 token 占用达到预算的 70%–80% 触发，而不是"每 5 轮压一次"——因为每轮的 token 消耗差异极大（一次工具返回可能顶十轮对话）。
- **压缩本身是一次模型调用**，要计入成本与延迟预算；压缩失败（超时）时应有降级路径：退回滑动窗口 + 保留槽位。
- **防止"摘要的摘要"级联失真**：每次压缩时把"上一次的摘要 + 新增对话"一起输入，并且**始终携带原始槽位**，让关键事实不经过多级转述。

### 3.3 防丢关键信息的三道保险

| 保险 | 机制 | 检测方式 |
|---|---|---|
| **验证清单（must_keep）** | 压缩前记录必须保留的实体（订单号、金额、承诺、用户明确要求），压缩后逐个检查是否还在 | 缺失即判压缩失败并重试（或直接保留原文一段） |
| **外置槽位** | 关键事实存在 `slots` 里，不参与文本压缩 | 槽位是结构化数据，天然不会被改写 |
| **原文回查** | 压缩后的对话仍保留"原始消息的 id"，需要时可按 id 取回原文 | 关键场景（金额、法律条款）可回查原文再作答 |

```python
MUST_KEEP = ["order_id", "amount", "deadline", "user_requirement"]

def verify_compression(summary, slots, must_keep):
    """压缩后的自检：所有 must_keep 字段必须能在槽位或摘要中找到。"""
    missing = [k for k in must_keep if not slots.get(k) and str(slots.get(k)) not in summary]
    return missing          # 非空 → 压缩失败，保留原文 + 告警
```

### 3.4 隔离：上下文工程里最被低估的动作

- **子任务独立上下文**：让一个子 Agent/子调用去读 8 万字的原始材料，只回传 200 字的结论。父上下文的 token 成本与注意力负担都降一个数量级（`docs/第11章` 的 `run_isolated`）。
- **工具的中间过程不该进主上下文**：一个工具内部调了 5 个 API，只需把**最终结论**作为 tool 消息回填，不要把中间结果拼进去。
- **不同角色的记忆不该混用**：写作 Agent 的草稿细节对审稿 Agent 是噪声（也是偏见来源）；审稿应该拿到**产物 + 验收标准**，而不是作者的思考过程。
- **多用户/多租户隔离**：长期记忆在检索时必须强制按 `tenant_id / user_id` 过滤，且**不能依赖 prompt 约束**——这是数据隔离，不是提示工程。

### 3.5 预算分配：把上下文当成一张要分账的账单

| 部分 | 建议占比 | 超支时的处理 |
|---|---|---|
| system + 槽位 | 10%–15% | 精简规则、把长示例改成短示例 |
| 工具定义 | 5%–20% | **这是最容易被忽略的一块**：几十个 MCP 工具的定义可以吃掉上万 token；按需分层加载 |
| 检索资料 | 25%–40% | 降 K、块裁剪、Rerank 后只留 top-4 |
| 历史（原文 + 摘要） | 20%–30% | 触发压缩、滑动窗口 |
| 输出预留 | 15%–25% | **必须预留**，否则 `finish_reason=length` 会截断结构化输出 |

**做一件小事就能省很多**：每轮打印 `prompt_tokens` 与各部分估算占比，把"预算"从口头承诺变成可观测的数字。

### 3.6 长期记忆的读写与生命周期

**写入（Write）**：抽取 → 过滤（是否为用户明确陈述、是否可复用、是否敏感）→ 去重（与既有条目语义比对）→ 落盘（带来源、时间戳、置信度）。

**读取（Read）**：按当前输入检索（关键词/向量）→ **时间衰减排序**（如半衰期 90 天，`score = 相似度 × 0.5 ** (age_days / half_life)`）→ 只注入 Top-3 → 在 prompt 中明确标注"以下为历史记忆，可能与当前情况不同"。

**生命周期**：

| 动作 | 触发条件 | 例 |
|---|---|---|
| **覆盖更新** | 同类事实出现新值 | 用户改地址 → 覆盖旧值，保留 `previous` 字段备查 |
| **TTL 过期** | 有时效的条目 | "本周出差中"7 天后失效 |
| **显式删除** | 用户要求（合规要求） | "忘掉我的地址" → 物理删除 + 检索层确认不可见 |
| **冲突挂起** | 新旧冲突且无法判定 | 存两条并标记冲突 → **下次对话问用户** |

### 3.7 记忆失效与冲突：能问就别猜

冲突的三种来源：**时间**（用户改主意了）、**来源**（用户说的 vs 你推断的）、**粒度**（"我不喜欢辣" vs "今天想吃川菜"）。

处理优先级：① **有明确时间戳时用新的**；② **来源可靠度优先于时间**（用户陈述 > 模型推断）；③ 无法判定时**在回复里问一句**（"你上次提到地址是 A，这次要用 B 吗？"）——一次澄清的成本远低于长期用错信息。

## 四、横向对比

### 4.1 三种记忆方案的工程对照

| 维度 | 摘要压缩 | 向量检索记忆 | 结构化状态抽取 |
|---|---|---|---|
| 保真度 | 中（细节丢失） | 中（召回决定） | **高**（字段精确） |
| token 成本 | 低（每次注入一段） | 中（检索 + 注入命中项） | **最低**（注入 dict） |
| 写入成本 | 每次压缩 1 次调用 | 每条记录 1 次 embedding | 每次抽取 1 次调用 |
| 可控性 | 中（黑盒文本） | 中（依赖召回质量） | **高**（字段可审计） |
| 可解释性 | 低 | 中（能看到命中了什么） | **高**（键值即真相） |
| 主要失败模式 | 丢关键信息、级联失真 | 召回错条目、旧信息污染 | 槽位设计不全、无法容纳意外信息 |
| 适合 | 长闲谈、探索型对话 | 跨会话的事实/偏好（量大、模糊） | **任务型对话（订单、工单、流程）** |

**生产建议：三者组合**——结构化槽位承载关键事实（必选），摘要承载脉络，向量检索承载"量大而模糊"的长期偏好。

### 4.2 记忆放在哪里：存储选型

| 方案 | 部署 | 适合 | 代价 |
|---|---|---|---|
| 内存 dict | 单进程 | 单机 demo、单会话 | 重启即失、无法多实例 |
| JSON/SQLite 文件 | 单机 | 中小规模、可审计（`code/ch07_memory.py` 的做法） | 并发写要加锁、无检索能力 |
| Redis | 有服务 | 多实例共享的会话记忆、TTL 原生支持 | 要做持久化配置 |
| PostgreSQL / pgvector | 有 DB | 长期记忆 + 结构化查询 + 向量检索一套搞定 | 需要 schema 设计与迁移 |
| 专用记忆层（如 Mem0/Zep 一类） | 依赖 | 想要现成的抽取/去重/冲突处理 | 引入外部依赖与数据合规评估 |

### 4.3 "上下文工程"与"Prompt 工程"的区别

| 维度 | Prompt 工程 | 上下文工程 |
|---|---|---|
| 关注点 | 单次输入的措辞与结构 | 整个窗口的**内容组成**与生命周期 |
| 时间尺度 | 一次调用 | 多轮、跨会话 |
| 主要手段 | 结构、示例、约束、格式 | 选择、压缩、隔离、编排 |
| 典型失败 | 格式错、理解偏 | 丢信息、成本失控、被旧信息污染 |
| 关系 | 是上下文工程的一个局部 | 包含 prompt 工程 + 记忆管理 + 检索注入 |

## 五、常见故障与排查

### 故障 1：摘要丢关键信息

- **现象**：用户在第 2 轮给的订单号在第 12 轮"消失"，模型开始问"请提供订单号"；或金额被写成"约 100 多元"。
- **定位**：对比压缩前后的原文与摘要，逐个核对 must_keep 字段；统计"压缩后关键实体命中率"（可离线跑，用固定对话样本）。
- **解决**：① 关键实体**外置到槽位**，不参与文本压缩；② 压缩后跑 `verify_compression`，缺失即失败重试；③ 保留原始消息 id 支持回查；④ 压缩 prompt 里明确"数字、编号、日期、承诺必须逐字保留"。

### 故障 2：中间内容被忽略（Lost in the Middle）

- **现象**：资料明明在上下文里（第 3 条检索块），模型却回答"没有找到相关信息"。
- **定位**：做一次对照实验——把同一条资料分别放在开头/中间/结尾，看答案是否变化；这是 5 分钟就能验证的。
- **解决**：① **最相关的资料放最前面**（并在文本里显式标注"最重要"）；② 关键指令在 system 与末尾各出现一次；③ 减少无关内容（去噪比加料有效）；④ 用引用编号强制模型"指认"用的是哪一条。

### 故障 3：旧信息污染（用户改了信息，模型还用旧的）

- **现象**：用户已改用新地址，回复里仍是旧地址；或长期记忆里两条地址同时存在被随机命中。
- **定位**：打印命中的长期记忆条目及其时间戳/来源；检查写入时有没有做**覆盖**与**去重**。
- **解决**：① 同类事实**覆盖式写入**（保留 `previous` 备查）；② 检索排序加入时间衰减；③ prompt 中标注记忆的时间与来源，并声明"若与本次对话冲突，以本次为准"；④ 冲突无法判定时在回复里问用户。

### 故障 4：错误被记忆固化

- **现象**：模型早期推断"用户想退货"，写进长期记忆后，之后每次对话都先入为主地按退货引导。
- **定位**：审计长期记忆的**来源字段**——区分"用户陈述"与"模型推断"；统计有多少条是推断写入的。
- **解决**：① **只写入用户明确陈述**（推断结果只放在会话级，不落盘）；② 每条记忆带 `source`（user/assistant/tool）与 `confidence`；③ 提供用户可查看、可删除的入口（也是合规要求）；④ 定期清理低置信度条目。

### 故障 5：上下文超限（400 / `context_length_exceeded`）

- **现象**：跑到第 N 轮突然报错，重放同一请求也失败。
- **定位**：把预算拆开算——system + 槽位 + **工具定义** + 检索资料 + 历史 + 输出预留，找出超出预期的部分（工具定义和单条大工具返回是两个最常见的"隐形大户"）。
- **解决**：① 补齐预算分配并每轮打印占用；② 工具定义分层加载、裁剪到必要工具；③ 大工具结果落盘 + 引用；④ 触发压缩的水位下调（70%）；⑤ 输出 `max_tokens` 显式设置并预留空间。

### 故障 6：token 成本非线性增长（成本失控）

- **现象**：会话从 5 轮变成 20 轮，账单不是 4 倍而是 10 倍以上。
- **定位**：用 `N × 首轮 + 每轮增量 × N(N−1)/2` 估算，与真实 `usage` 对比；看是否有**单条超长消息**（一次工具返回全文）把每轮增量抬高。
- **解决**：① 固定前缀（system + 工具定义）开启 **prompt caching**（命中部分的价格通常低一个数量级）；② 压缩 + 槽位化，让历史稳定在一个小体积；③ 工具结果裁剪；④ 模型分级（历史摘要用小模型、最终回答用大模型）；⑤ 给单会话设 token 上限（第 05 章的预算闸门）。

### 故障 7：早期指令被稀释（指令漂移）

- **现象**：第 1 轮明确要求"输出 JSON"，到第 15 轮模型开始输出 Markdown。
- **定位**：检查输出格式约束是不是只写在**第 1 轮的 user 消息**里（那它早被淹没在中间位置）。
- **解决**：① 规则放 **system**（每轮固定前缀，位置稳定）；② 目标与关键约束做成"每轮重述"（在 system 末尾或本轮 user 消息里）；③ 结构化输出用 schema 级约束（`docs/第03章`），别依赖文本记忆。

### 故障 8：多实例部署下会话记忆不共享

- **现象**：用户第二轮请求被路由到另一个实例，模型"失忆"。
- **定位**：确认会话状态是存在**进程内存**里还是外部存储里；用两个实例做一次连续对话即可复现。
- **解决**：① 会话记忆外置（Redis / DB），按 `session_id` 读写；② 写入时加锁/版本号（防止并发覆盖）；③ 无状态化 Web 层，把 `session_id` 显式传给每个请求；④ 压缩结果也落盘（否则每个实例各压一遍，结论不一致）。

### 故障 9：跨用户记忆错配（严重）

- **现象**：A 用户看到了 B 用户的偏好或订单信息。
- **定位**：审计长期记忆的键设计——是不是只有 `user` 一个维度？检索时有没有强制过滤？
- **解决**：① 键必须包含 `tenant_id + user_id`（+ 会话维度）；② 检索层**强制注入**过滤条件，绝不依赖 prompt；③ 写一条"用低权限账号构造查询"的对抗测试进回归；④ 记忆的删除要能级联到所有索引副本。

### 故障 10：压缩成了新的成本与延迟来源

- **现象**：加了"智能压缩"后，每次对话多花 1–2 秒、成本反而升高。
- **定位**：单列一项"压缩调用"的耗时与成本占比；看触发频率是否过高（每轮都触发说明水位设置不合理）。
- **解决**：① 水位调到 70%–80% 再触发；② 压缩用**小模型**（这是典型的"不需要大模型"的任务）；③ 压缩结果缓存（相同的历史片段不必重复压缩）；④ 压缩失败时快速降级（滑动窗口 + 槽位）。

## 六、面试要点

**1. 上下文工程是什么？和 Prompt 工程什么关系？**
骨架：① 关注整个窗口的**内容组成与生命周期**，而非单次措辞；② 四个动作：选择、压缩、隔离、编排；③ prompt 工程是它的一个局部；④ 目标：在预算内保证关键信息的保真度；⑤ 为什么重要：模型无状态，上下文是唯一工作台。

**2. 上下文窗口为什么是稀缺资源？**
骨架：① 成本随长度增长，且历史每轮重发导致平方级累计；② 注意力会被稀释（长上下文里中间内容利用率下降）；③ 超过窗口直接报错；④ 大体积工具返回/资料会挤掉关键指令；⑤ 所以要有预算分配与压缩。

**3. 怎么压缩历史而不丢关键信息？**
骨架：① 三件套：摘要（脉络）+ 关键实体逐字（槽位）+ 待办结论；② 槽位外置，永不被摘要覆盖；③ must_keep 验证清单 + 压缩后自检失败重试；④ 按 token 水位触发而非轮数；⑤ 保留原文引用以便回查。

**4. 长期记忆怎么实现？**
骨架：① 写入：抽取 → 过滤（用户明确陈述/可复用/非敏感）→ 去重 → 落盘（带来源与时间）；② 读取：检索 + 时间衰减排序 → 只注入 Top-3；③ 生命周期：覆盖更新 / TTL / 显式删除 / 冲突挂起；④ 隔离：按租户与用户强制过滤；⑤ 可审计、可删除（合规）。

**5. 为什么历史要每轮重发？这对设计有什么影响？**
骨架：① API 无状态，模型不保留上一次请求的任何东西；② 于是成本随轮数平方增长；③ 影响：固定前缀要做缓存、历史要压缩、大对象要外置引用；④ 也意味着"模型记住了"永远是错觉，记忆必须由你的代码管理。

**6. Lost in the Middle 是什么？怎么缓解？**
骨架：① 长上下文里模型对中间位置信息利用率下降（U 形）；② 缓解：最相关的放最前/最后、关键指令重复出现、减少无关内容、用引用编号定位；③ 与模型和任务相关，必须自测；④ 它解释了"资料塞进去不等于用得上"。

**7. 记忆冲突怎么处理？**
骨架：① 三类来源：时间、来源可靠度、粒度差异；② 优先时间戳新的，用户陈述优先于模型推断；③ 检索排序加时间衰减；④ 无法判定就**问用户**；⑤ 冲突事件要记录（长期记忆质量的指标）。

**8. 什么时候该做上下文隔离？**
骨架：① 子任务读大量原始材料时（只回传结论）；② 多角色协同时（作者与审稿人不共享草稿思路）；③ 工具内部的中间过程；④ 多租户数据；⑤ 收益：父上下文 token 降一个数量级、减少偏见与污染。

**9. 怎么防止记忆污染？**
骨架：① 只写用户明确陈述，推断不落盘；② 每条带来源与置信度；③ 去重与覆盖式更新；④ 支持查看与删除；⑤ 定期审计（有多少条被用户纠正过）。

**10. 怎么评估记忆系统的效果？**
骨架：① 任务侧：多轮任务成功率、用户纠正率、重复提问率；② 记忆侧：关键实体保留率（压缩前后对比）、记忆命中率、冲突率；③ 成本侧：平均每轮 token、压缩调用占比、P95 延迟；④ 用固定对话集离线回归；⑤ A/B：开/关某策略对比。

**11. 上下文超限了，你的排查顺序？**
骨架：① 拆预算算各部分占用（system/工具定义/资料/历史/输出）；② 找隐形大户（工具定义、单条大工具返回）；③ 缩短历史（压缩/窗口）；④ 裁剪工具与资料；⑤ 输出预留；⑥ 加监控，下次在超限前就发现。

**12. 会话状态在多实例部署下怎么存？**
骨架：① 外置存储（Redis/DB）按 `session_id` 读写；② 无状态 Web 层，显式传 `session_id`；③ 并发写用锁或版本号；④ 压缩结果也要落盘（避免多实例各压一遍导致不一致）；⑤ 设 TTL 与清理策略。
