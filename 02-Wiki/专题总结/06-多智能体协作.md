# 专题：多智能体协作（Multi-Agent Collaboration）

> **一句话** · 多智能体是**协作问题**不是智能问题 —— 拆角色买到的是"上下文隔离 + 对抗性检查 + 可并行 + 可恢复"，买不到"更聪明"。
> **本专题对应 `docs/第11章 多智能体协作`**，前置阅读：[[docs/第05章 ReAct最小Agent-Loop]]、[[docs/第07章 记忆与上下文工程]]；配套代码 `code/ch11_multi_agent.py`。
> **读完你能回答：**
> 1. 给定一个任务，你怎么**当场论证**该用单 Agent 还是多 Agent？（要能说出不是"感觉"的依据）
> 2. Supervisor / Pipeline / Graph 三种协调模式，你的任务该选哪一种，另外两种为什么不选？
> 3. reviewer 每轮都说"再改改"，你的系统在第几轮、靠哪个机制停下来？停止后剩下的分歧谁负责？

---

## 一、本质：多智能体解决的是协作，不是智能

有同学把写作 Agent 拆成"研究员 + 写手 + 审稿人"，跑了一周发现质量没变、成本翻了 1.4 倍，审稿人每轮都说"再改改"，最后靠轮次上限才停下来。

一个必须先建立的认知：**拆成 5 个 Agent，不会让系统"变聪明"**——它们用的是同一个模型、同一份知识、同一套工具，你能买到的只有四样东西：**上下文隔离、对抗性检查、可并行、可恢复**。**代价是四种固定的新故障**，而且它们是系统性的、不是偶发 bug：循环争论、任务漂移、上下文膨胀、责任真空。**一句话判断**：如果这四样收益里你一样都不需要，多 Agent 就是纯亏 —— 成本涨、延迟涨、故障面扩大、成功率往往还降几个点。**本文把这套判断的工程取舍讲清楚。**

## 二、决策表：什么时候用 / 什么时候不用

### 2.1 先过"该不该拆"的四条硬门槛

| 需求 | 单 Agent 的具体症状（命中才算） | 满足时才考虑多 Agent |
|---|---|---|
| **上下文需要隔离** | 一个上下文塞几万 token 资料，模型开始丢前面的内容、答非所问 | 检索资料不该污染写作思路 |
| **需要对抗性检查** | "作者"和"审稿人"在同一段上下文里，倾向于自我确认，挑不出自己的错 | 需要一个独立上下文挑错 |
| **需要并行** | 5 个独立子任务串行跑，20 秒 × 5 = 100 秒 | 子任务彼此无依赖，且延迟是痛点 |
| **角色差异巨大** | 一个 system prompt 里塞两套矛盾要求（"严谨引用" vs "大胆发散"），模型两头不讨好 | 每个角色一份独立 system prompt 才合理 |

**四条全不满足 → 一律单 Agent。** 下面这些情况同样不要上多 Agent：

- 步骤固定且短（≤3 步）→ 写一个清晰的 Skill（[[02-Wiki/专题总结/07-Skills与MCP协议]]）就够；
- 对延迟敏感 → 多 Agent 的端到端延迟按最慢的分支算，串行分工只会更慢；
- 预算小 → 输入 token 常见是单 Agent 的 1.2–3 倍；
- **还没给单 Agent 建评测集** → 没有基线，你无法证明"拆完变好了"，只会得到一句"好像差不多"。

### 2.2 协调模式选择（先选表，再写代码）

| 模式 | 结构 | 优点 | 代价 | 适合 | 典型反例 |
|---|---|---|---|---|---|
| **Supervisor** | 一个主管调度多个 worker | 能全局控轮次/预算/交付清单，可兜底裁决 | 主管是瓶颈，主管上下文也会满 | 任务需要动态分发、需要裁决与兜底 | 主管把子 Agent 全部原文读进自己上下文 |
| **Pipeline** | 固定顺序 research → write → review → revise | 可预测、易调试、每步有产物 | 不能回头，路径写死 | 流程稳定的生产任务（周报、审查、翻译） | 中间一步失败，整条链路重跑 |
| **Graph** | 状态图：节点=步骤，边=条件 | **可恢复、可分支、可重试** | 实现复杂，要状态存储 | 长任务、可能中断、需要断点续跑 | 20 分钟的任务为了"先进"上 Graph，调试成本吃不消 |
| **自由对话式** ❌ | Agent 之间随便聊 | 无 | 跑题、消息数按 n² 涨、无法终止 | **不推荐（永远）** | 两个 Agent 在"什么算更好的文风"上耗光预算 |

### 2.3 单 Agent → Skill → 多 Agent 的升级时机

```
单 Agent 成功率 < 目标
  ├─ 失败样本是"漏步骤 / 不按流程"      → 加 Skill（第 09 章），别拆 Agent
  ├─ 失败样本是"资料太多看不过来"        → 上下文工程（第 07 章）+ RAG（第 08 章）
  ├─ 失败样本是"自己挑不出自己的错"      → 加一个独立 reviewer（最小多 Agent）
  ├─ 失败样本是"太慢"且子任务无依赖      → 并行 worker（不改角色，只改调度）
  └─ 失败样本是"长任务中断要重跑"        → Graph 化，落盘检查点
```

**升级顺序不可颠倒**：单 Agent → 加 Skill → 加工具 → 加评测 → 最后才拆 Agent。

## 三、工程实现要点

### 3.1 角色契约的六个要素

契约不是文档，是**要落到代码里的字段**。缺一项就出对应的故障：

| 要素 | 写什么 | 缺了会怎样 |
|---|---|---|
| **职责**（role/responsibility） | 这个角色只负责哪一段 | 职责重叠，同一步被两个角色做两遍 |
| **输入**（input schema） | 必须拿到哪些字段，逐项校验 | 拿到一整段对话历史，不知道关心什么 |
| **输出**（output schema） | 输出形状 + 必填字段 | 主管 `result["draft"]` 直接 KeyError |
| **停止条件**（stop condition） | 什么状态算干完（可判定） | 无限干下去 |
| **失败回退**（on_failure） | **真函数**：降级而不是重试 | 卡死；或者"重试一次"照样错 |
| **禁令**（must_not_do） | 明确不许做什么 | 越界（planner 顺手把活干了、reviewer 顺手重写稿子） |

模板（可直接抄进你的项目）：

```markdown
角色：researcher
职责：只收集事实与来源，不写结论、不写正文
输入：question (str)
输出：facts (list[str]，≥3 条)、sources (list[str])
停止条件：facts ≥3 且每条都能对应 sources 里的来源
失败回退：退化为最多 2 条事实 + 标注"证据不足"，并把不确定性写进输出
不许做：价值判断、给建议
```

### 3.2 契约校验必须放在"跑之前"和"跑之后"

```python
class Worker(object):
    """带契约的 worker：输入校验 → 干活 → 输出校验 → 失败回退。"""
    def run(self, payload, trace):
        self.calls += 1
        missing = self.contract.check_input(payload)     # 跑之前：省 token
        if missing:
            trace.log("input_contract_violation", worker=self.contract.role, missing=missing)
        result = self.work(payload)
        bad = self.contract.check_output(result)         # 跑之后：保交付
        if bad and self.fallback:
            result = self.fallback(payload)              # 降级，不是重试
            trace.log("fallback_used", worker=self.contract.role)
        return result
```

三个要点：**输入缺字段就别让它瞎跑**（省 token）；**输出缺字段就走回退**（保交付）；**每次校验都写 trace**（复盘时最重要的证据）。

### 3.3 四道保险的推荐参数

| 保险 | 治什么 | 推荐配置 | 超限时的动作 |
|---|---|---|---|
| **轮次上限** | 循环争论 | `MAX_ROUNDS = 2~3` | 强制停止 + 输出"未达成一致 + 分歧点 + 各方理由"，交人工 |
| **无进展熔断** | 循环争论（更早停） | 相邻两轮意见重合度 > 0.8 立即停 | 判定"无进展"，不必等上限 |
| **目标复述 + 重合度** | 任务漂移 | 每轮强制输出 `restated_goal`；阈值先记录 3 轮分布再定（常见 0.45–0.6） | 打回、缩小范围、重新下发目标 |
| **压缩回传** | 上下文膨胀 | 子 Agent 只回传"结论 + 依据数量 + 不确定性"，保留指针（路径/id/行号） | 超预算就摘要，细节落盘而非留在上下文 |
| **交付清单** | 责任真空 | 开工前定清单，每项对应某个角色的 `produces` 字段 | 收尾逐项打勾，缺失项显式指派兜底 |

### 3.4 让 reviewer 的每条意见"可判定"

这是从源头消灭一半循环争论的规则。意见必须能被机械核对：

- ✅ 可判定："缺少对比表"、"未给测试建议"、"结论未引用来源"；
- ❌ 不可判定："语气不够正式"、"再写好一点"、"不够全面"。

**实现方式**：reviewer 的输出 schema 强制为 `{verdict: pass|revise, issues: [{item, evidence, how_to_verify}]}`，`verdict` 只能是二选一字符串，不给第三个选项。

### 3.5 trace 是多 Agent 系统唯一的复盘依据

最少要记的事件（`code/common/trace.py` 的 `Trace` 直接可用）：

```text
worker_start / worker_done          # 谁在第几轮干了什么
input_contract_violation            # 契约违规（输入）
output_contract_violation           # 契约违规（输出）
fallback_used                       # 走了降级
drift_check / drift_detected        # 每轮漂移分数
round_limit_hit                     # 撞了轮次上限
deliverable_check / reassign        # 交付清单与兜底指派
```

**判断标准**：只看 trace，你能不能回答"这一轮到底谁干了什么、为什么停下"。答不出来说明 trace 记少了。

## 四、横向对比

### 4.1 单 Agent vs 多 Agent（同一任务的量级）

| 指标 | 单 Agent 一路到底 | Supervisor + 2 worker | Supervisor + 2 worker（并行） |
|---|---|---|---|
| 输入 token | ~9200 | ~11400（**+24%**） | ~11400（**+24%**） |
| 输出 token | ~1800 | ~2100 | ~2100 |
| 端到端延迟 | ~26s | ~34s（**更慢**） | ~19s（**更快**） |
| 主管上下文 | 从头累积全部历史 | 只保留压缩结论 | 只保留压缩结论 |
| 新增故障面 | — | 4 类协作故障 | 4 类 + 并行一致性 |

三条规律必须记住：

1. **输入 token 通常高 20%~200%** —— 每个子 Agent 都要重复带上自己的系统提示与背景；
2. **串行分工让延迟更高**，唯一能降延迟的手段是**并行**（且子任务必须无依赖）；
3. **真实业务里成功率常常下降几个点**（例：单 Agent 92% → 5 Agent 流水线 88%），因为多了协作故障。

### 4.2 共享上下文 vs 隔离 + 压缩回传（同样 5 轮）

```text
轮次   共享上下文的 token   隔离 + 压缩后的主管 token
----------------------------------------------------------
1      420                    244
2      1260                   488
3      2940                   732
4      6300                   976
5      13020                  1220
----------------------------------------------------------
第 5 轮时差约 10.7 倍。原因：共享上下文里每个 Agent 都要读别人的全部输出，消息数按 n² 涨。
```

**结论**：上下文隔离不是"省一点 token"，而是把增长曲线从平方压到线性。

### 4.3 三种协调模式的能力对比

| 能力 | Supervisor | Pipeline | Graph |
|---|---|---|---|
| 动态分发任务 | ✅ | ❌ | ✅（条件边） |
| 全局预算/轮次控制 | ✅（集中） | ⚠️（每步自己控） | ✅（图上控） |
| 断点续跑 | ❌ | ❌ | ✅ **唯一优势** |
| 调试难度 | 中 | 低 | 高 |
| 状态存储 | 可无 | 可无 | **必需** |

选型口诀：**能 Pipeline 就 Pipeline；要动态分发用 Supervisor；要断点续跑才上 Graph。** 两个角色的场景，一个 `for` 循环（20 行）就够 —— 框架要跟着复杂度长，不要提前长。

## 五、常见故障与排查（8 条）

### 故障 1：循环争论（reviewer 永远说 revise）

- **现象**：轮次一直涨，成本线性上涨，产出没有变化。
- **定位**：打印每轮的 `issues` 列表与轮次计数；看意见是否**可判定**、相邻两轮是否高度重复。
- **解决**：① `MAX_ROUNDS = 2~3`，撞上限就强制停止；② 意见必须"可判定 + 附验证方式"；③ 加"无进展熔断"（相邻两轮 `issues` 重合度 > 0.8 立即停）；④ 停止时输出"未达成一致 + 分歧点"交人工，而不是静默丢弃。

### 故障 2：任务漂移

- **现象**：产出越来越长、范围越来越大（"对比向量数据库" → "顺手把整个项目重构一遍"）。
- **定位**：看 trace 里的 `drift_check` 分数分布；比对子 Agent 输出的 `restated_goal` 与原始目标的重合度。
- **解决**：每轮强制复述目标 + 自动比对（实测 0.20 < 阈值 0.45 即判漂移）；打回并要求"缩小范围重述"；把目标写成可判定的句子（模糊目标必然漂移）。

### 故障 3：上下文膨胀

- **现象**：token 数指数增长，主管最先撑爆，后期报上下文超限或答非所问。
- **定位**：trace 里的 token / 消息计数；算"第 n 轮 prompt 大小"是否呈 n² 趋势。
- **解决**：子 Agent 独立上下文 + 只回传压缩结论（保留指针与不确定性）+ 接近预算主动摘要（复用 [[docs/第07章 记忆与上下文工程]] 的压缩器）+ 主管上下文单独设上限。

### 故障 4：责任真空

- **现象**："草稿写了、稿也审了，但没人给测试建议"，收尾时才发现。
- **定位**：开工前定的交付清单，收尾逐项打勾（`deliverable_check` 打印 missing 项）。
- **解决**：清单项必须与某个角色的 `produces` 字段一一对应；产不出来的项直接砍掉需求；缺失项显式指派兜底（不许"大家应该都做了"）。

### 故障 5：子 Agent 各自为政（隔离的副作用）

- **现象**：隔离之后子 Agent 自作主张，产出与整体目标不一致；合并时两份产物互相矛盾。
- **定位**：对比各子 Agent 的输入里是否包含完整目标与验收标准。
- **解决**：隔离的是**过程性内容**，目标与验收标准必须完整传递；只压缩细节，不压缩约束。

### 故障 6：mock 全绿、上线全崩

- **现象**：`AGENT_MOCK=1` 下"全部 pass"，接真模型后技能不触发、契约频繁违规。
- **定位**：对比离线/在线两套逻辑的判据差异（离线常是关键字匹配，在线是模型自主判断）。
- **解决**：mock 只验证**控制流**（契约校验、轮次上限、漂移检测、交付清单是否真的执行）；真实效果必须在线跑，并把"选择了哪个角色/哪个技能/匹配分数"记进 trace。

### 故障 7：并行子任务互相踩踏

- **现象**：并行后产出互相覆盖（同一个文件被两个 worker 写）、或结论互相矛盾。
- **定位**：检查子任务之间是否存在**隐含依赖**（共享的可写资源、同一份事实来源）。
- **解决**：只并行无依赖任务；写操作**按资源串行化**（同一文件只允许一个写者）；冲突时以"验收标准"裁决，而不是让两个 Agent 继续协商。

### 故障 8：成本统计漏了失败重跑

- **现象**：按成功样本算账很便宜，月底账单差一倍以上。
- **定位**：把 trace 里的失败率乘进成本（失败任务的 token 是全损）。
- **解决**：报告里给出"每成功一次的平均成本 = 总成本 / 成功次数"，而不是"每次调用的 token"；多 Agent 的失败成本更高（一次失败要跑好几个子 Agent）。

## 六、面试要点（12 题，回答骨架）

**1. 为什么说多智能体往往不如单 Agent？**
- 拆 Agent 不改变模型能力，只买到四样：上下文隔离、对抗检查、可并行、可恢复；
- 代价是成本 +20%~200%、延迟按最慢分支算、新增四类协作故障；
- 真实案例：同一任务单 Agent 92% 成功率 → 5 Agent 流水线 88%，延迟 3.5 倍；
- **判断依据**：四条硬门槛（隔离/对抗/并行/角色差异）一条不命中就别拆；
- 没建评测基线前拆分，等于无法证明收益。

**2. 那什么时候必须上多 Agent？**
- 上下文被资料污染（检索结果稀释写作注意力）；
- 需要独立视角挑错（同一上下文里模型挑不出自己的错）；
- 子任务无依赖且延迟是痛点（并行是唯一降延迟手段）；
- 长任务需要断点续跑（Graph 的可恢复是决定性优势）；
- 每个新增 Agent 都要能回答"它替谁解决了哪一条门槛"。

**3. 怎么保证协作能收敛、不无限循环？**
- 三层停止：意见可判定（源头）→ 无进展熔断（相似度）→ 轮次上限（兜底）；
- `MAX_ROUNDS = 2~3`，上限是止损不是提质；调大只会多烧 token；
- 强制裁决规则**事先定义**：以原始验收标准为准，判不了就交人工；
- 停了要产出"分歧点 + 各方理由"，不能静默丢弃；
- 所有停止原因写 trace（`round_limit_hit`）。

**4. 角色怎么划分？划分依据是什么？**
- 按**契约**分，不按名字分：职责/输入/输出/停止条件/失败回退/禁令六要素；
- reviewer（对照标准判合格，收敛）与 critic（找更好做法，发散，限条数）必须区分；
- planner 不许执行、executor 不许改目标、reviewer 不许重写、critic 每条要可验证；
- 角色差异必须体现在 system prompt 里，否则拆了也不会有不同行为；
- 角色数量由失败样本决定，不由架构图决定。

**5. 多 Agent 的 token 怎么控制？**
- 上下文隔离 + 压缩回传（子 Agent 只回传结论摘要，把 n² 增长压成线性）；
- 输入侧只给必需字段（`objective` + `facts`），其余按需检索；
- 工具观察结果在工具层限长；
- 主管上下文单独设预算上限；
- 把失败重跑算进成本，看"每成功一次的成本"。

**6. 上下文隔离到底买到了什么？代价是什么？**
- 买到：质量（噪音少）、成本（中间过程不进主管上下文）、故障面（单点跑偏可隔离、可重跑）；
- 代价：信息传递丢失（压缩会丢细节，需要有意识地保留指针）；目标不一致风险（隔离≠不传约束）；
- 关键动作：**压缩回传**，且保留"可回查指针（路径/来源 id/行号）"与"不确定性说明"；
- 判断标准：主管下一步决策需不需要这条细节 —— 不需要就丢，需要就落盘。

**7. Supervisor / Pipeline / Graph 怎么选？**
- Pipeline：流程稳定、路径可写死 → 最易调试、每步有产物；
- Supervisor：需要动态分发、需要裁决与兜底 → 但主管是瓶颈与上下文瓶颈；
- Graph：需要断点续跑/分支/长任务 → 唯一能从中断处恢复的模式，代价是状态存储与实现复杂度；
- 自由对话式永远不选：跑题、n² 膨胀、无法终止；
- 两角色场景用 `for` 循环即可，不要提前上框架。

**8. 为什么明确不推荐"自由对话式"多智能体？**
- 容易跑题：在无法判定的问题（"什么算更好的文风"）上耗光预算；
- 上下文爆炸：每个 Agent 读别人全部发言，消息数按 n² 涨（实测 5 轮差 10.7 倍）；
- 无法终止：没有停止条件，只能靠外部轮次上限掐断 —— 说明它不是可控系统；
- 替代方案：Supervisor / Pipeline / Graph 三选一。

**9. 任务漂移怎么检测？阈值怎么定？**
- 检测：每轮强制输出 `restated_goal`，与原始目标做重合度比对，低于阈值就打回；
- 阈值定法：先跑 3 轮记录正常复述的分数分布（通常 0.7+），把阈值放在"正常值与漂移值之间的缝里"（常见 0.45–0.6）；
- 副作用收益：目标和约束被反复强调，模型更不容易忘；
- 目标本身要写成可判定的句子，否则再好的检测也救不了。

**10. 多 Agent 系统怎么做可观测？**
- trace 记全链路事件：谁在第几轮做了什么（`worker_start/done`）、契约违规、回退、漂移分数、轮次上限、交付清单；
- 每次运行落盘（`traces/chXX.json`），作为复盘与版比对的唯一依据；
- 有了 trace 才能回答"平均步数从 5.2 降到 3.8"这类可度量的问题；
- 面试里说"我们靠 trace 定位到是 reviewer 意见不可判定导致的循环"，比说"调了调 prompt"值钱得多。

**11. 新增一个 Agent 的完整成本是什么？**
- 契约（六要素）+ 输入/输出校验 + 失败回退函数 + trace 事件 + 提示词 + 评测样本；
- 还要算上：额外的 token（每次都要带系统提示与背景）、额外的延迟（串行则更慢）、额外的故障面；
- 判断句：**这个 Agent 替谁解决了哪一条门槛需求？答不出来就删掉。**

**12. 面试官追问："你的多 Agent 项目效果如何度量？"**
- 先有基线：单 Agent 的成功率/token/延迟（没有基线就没有对比）；
- 指标：任务完成率、契约违规率、平均轮次、每成功一次的成本、P95 延迟；
- 归因：失败样本按四类故障分类计数，看多 Agent 引入了哪一类；
- 结论要么是"值得"（给出数字），要么是"拆回去"（也是合格答案）；
- 兜底句：**"多 Agent 的收益要能被 trace 和评测集证明，否则就是拿成本和故障面换一个架构图。"**
