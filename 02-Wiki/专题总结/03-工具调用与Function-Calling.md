# 专题：工具调用与 Function Calling

> **一句话** · 模型**从不执行代码**：它只输出一句"我要调 `get_order`，参数是 `{"order_id": "DP1002"}`"，执行永远发生在你的进程里；因此参数是模型的输出、等于不可信输入，返回值是你写的、等于模型的全部世界。
>
> **本专题对应：** `docs/第04章 工具调用`、`docs/第05章 ReAct最小Agent-Loop`、`docs/第09章 Skills能力包`（工具与 Skill 的分工）、`docs/第10章 MCP与通信协议`（工具的跨应用复用）
>
> **读完你能回答：**
> 1. 十个 API 该封装成 10 个工具还是 3 个工具？判断依据是什么，会付出什么代价？
> 2. 模型选错工具 / 漏传参数 / 反复调同一个工具——这三类故障分别该改描述、改 schema，还是改返回值？
> 3. 一个会写数据的工具，你要在架构上加哪几道锁才敢让它上线？

---

## 一、本质

上个月有同学在群里问："我明明告诉模型查不到就返回空，它还是编了一个订单号出来。"把工具描述贴出来才看到：失败时工具返回的是 `{"error": "not found"}`，description 里却从没说过这个字段的含义——模型只能猜，猜的结果就是编。

Function Calling 是一条**协议**，不是一项模型能力：请求里带上工具清单（名字 + 描述 + 参数 JSON Schema），模型返回结构化的调用意图（`tool_calls`），你的代码执行它，再把结果作为 `role="tool"` 的消息喂回。模型在这条链路里做了且仅做了两件事：**选哪个工具、填什么参数**——它看不见工具实现、不知道你有没有真的执行、也没有调用栈与异常。**工具清单就是能力边界；参数是模型的输出，按不可信输入处理；工具失败不是异常，是观察结果。本文把这条协议上的工程取舍讲清楚。**

## 二、决策表

### 2.1 什么时候该给工具（什么时候不该给）

| 判断 | 该给工具 | 不该给工具 |
|---|---|---|
| 数据来源 | 实时、私有、外部系统（订单、天气、文件） | 模型知识内、常识问答 |
| 计算 | 精确计算、大数、日期运算 | 简单判断（模型直接做得更好） |
| 副作用 | 需要写入（发消息、建单、改状态） | 只读任务却给了写工具（白送风险） |
| 确定性 | 需要 100% 一致的规则判断 | 可以用 prompt 稳定的语义判断 |
| 成本 | — | 一次工具调用的延迟 < 一次额外模型调用的延迟时，优先工具 |

**边界提醒**：能用代码写死的规则，不要让模型"调用工具去判断"。`if 金额 > 5000` 比 `check_amount_policy(...)` 快、准、免费。

### 2.2 工具粒度：粗粒度 vs 细粒度

| 方案 | 例子 | 优点 | 代价 | 什么时候选 |
|---|---|---|---|---|
| **细粒度**（一个 API 一个工具） | `list_files` / `read_file` / `stat_file` / `grep_file` | 语义单一、参数少、单步可复用 | 轮数多、模型要做更多编排决策、工具数膨胀 | 步骤确实需要模型自由组合（探索型任务） |
| **粗粒度**（一个任务一个工具） | `summarize_directory(path)` | 轮数少、模型少犯错、token 省 | 灵活性差，任务微调就要改工具 | 高频、固定模式的业务动作（报表、查询、开通） |
| **中间态（推荐）** | 一个工具 = 一个**用户意图闭环**，内部编排多步 API | 兼顾轮数与灵活性 | 需要你写内部编排逻辑 | 大多数生产场景的默认选择 |

**该合并的四个信号**：

1. 两个工具名字几乎同义（`search_order` / `query_order`）——**必须合并**，这是选错工具的头号原因。
2. 模型经常连续调用同一组工具（先 `list` 再 `read`，参数还有依赖）——合并成一个工具更省轮数与 token。
3. 参数里有 3 个以上字段永远同时出现——说明它们是一个整体，合成一个对象参数。
4. 同一个工具调用频繁但每次只用一个字段（如 `get_user` 只查名字）——考虑专门提供一个"只取名字"的窄工具。

### 2.3 工具数量：超过阈值就要分层

| 工具数 | 体验 | 对策 |
|---|---|---|
| 1–7 | 选择准确率通常可用 | 直接全量注册 |
| 8–20 | 相似工具开始混淆，schema 消耗上下文明显 | 合并同义工具 + 在描述里写"何时不用" |
| 20–50 | 选错率上升、单次请求的输入 token 被工具定义吃掉几千 | **分层**：先给"工具目录"，模型选定命名空间后再加载该组 schema |
| >50 | 全量注册不可行（仅工具定义就可能占掉数万 token） | **路由**：先用一次轻量分类调用选出候选工具集，再进入 Agent 循环 |

同一个 MCP Server 接三个就是几十个工具，这是 MCP 落地时最常见的现场问题——**在应用侧做工具裁剪，而不是把 Server 提供的全部工具直接转发给模型**（`docs/第10章`）。

### 2.4 危险工具清单（必须加人工确认的那一类）

| 类别 | 例子 | 为什么危险 |
|---|---|---|
| 不可逆写 | `delete_*`、`drop_*`、`refund`、`transfer` | 错了无法撤回 |
| 对外发送 | `send_email`、`post_message`、`publish` | 发出去就收不回，且可能泄露数据 |
| 花钱 | `create_instance`、`call_paid_api` | 模型可能循环调用 |
| 权限提升 | `grant_role`、`set_permission` | 一次越权可能长期存在 |
| 读敏感数据 | `read_env`、`dump_users` | 数据会进上下文、进日志、进第三方推理服务 |

**处理方式**：`requires_confirmation=True` + **把参数原样展示给人看**（不是展示模型的自然语言解释）+ 审计日志记录"谁在什么时候批准了什么参数"。绕过确认路径（"自动模式"）只能用于沙箱环境。

## 三、工程实现要点

### 3.1 `description` 是工具的使用说明书，不是摘要

模型选工具的唯一依据是**名字 + 描述**（schema 只在选定后约束参数）。描述要写全五件事：

```python
TOOLS = [{
    "name": "search_order",
    "description": (
        "按订单号或手机号查询订单状态。\n"
        "何时用：用户询问某个订单的物流、退款、金额等具体状态。\n"
        "何时不用：用户想列出全部订单时用 list_orders；用户只问退款政策时用 get_policy（不需要订单）。\n"
        "返回：{ok, order:{order_id, status, amount, updated_at}}；找不到时 ok=false 且 error.code=NOT_FOUND。\n"
        "注意：order_id 是 DP 开头的 6 位字符串，不是手机号。"
    ),
    "parameters": {
        "type": "object",
        "properties": {
            "order_id": {"type": "string", "pattern": "^DP[0-9]{4}$", "description": "订单号，例如 DP1002"},
            "phone": {"type": "string", "description": "手机号（与 order_id 二选一）"}
        },
        "required": [],
        "additionalProperties": False
    }
}]
```

**三行验证法**（写完描述后自问）：① 模型能不能从描述里判断"什么时候**不该**用它"？② 返回结构的字段名和类型是否写清？③ 失败时它知道该干什么吗？三个都答"是"，这个描述才算合格。

### 3.2 参数 schema：把"靠模型自律"改成"靠结构约束"

| 技巧 | 写法 | 解决的问题 |
|---|---|---|
| `enum` 限值 | `{"type": "string", "enum": ["退款", "换货", "发票"]}` | 模型自由发挥同义词（"退货"） |
| `pattern` 约束格式 | `{"pattern": "^\\d{4}-\\d{2}-\\d{2}$"}` | 日期写成"下周三"、"3/5/2025" |
| 单位进描述 | `"days": {"type": "integer", "description": "天数，1–30"}` | 传 90 或传 "三天" |
| 避免自由文本参数 | 不要出现 `{"type": "string"}` 的 `query` 字段承载全部语义 | 自由文本是幻觉与注入的温床 |
| 二选一显式化 | 用 `anyOf`（服务商支持时）或描述里写清 | 模型两个都传或都不传 |
| `additionalProperties: false` | 严格模式常要求 | 模型塞入不存在的字段 |

**注意**：schema 是**约束模型的输出**，不能替代你的服务端校验。模型可能不遵守（尤其在不支持严格模式的服务商上），所以执行层仍要做一次参数校验——这一次校验是**安全边界**，不是重复劳动。

### 3.3 参数校验：把模型当外网输入

```python
import os, re

ALLOWED_DIRS = [os.path.realpath("./sandbox")]

def safe_read_file(path):
    """路径白名单：模型给的 path 一律当外网输入处理。"""
    p = os.path.realpath(os.path.join("./sandbox", path))
    if not any(p.startswith(d + os.sep) or p == d for d in ALLOWED_DIRS):
        return {"ok": False, "error": {"code": "PERMISSION_DENIED",
                                       "message": "只能读取 sandbox/ 下的文件"}}
    with open(p, encoding="utf-8") as f:
        return {"ok": True, "text": f.read()[:4000], "truncated": True}
```

四条硬规则：**①** 路径做 `realpath` 后做前缀白名单（防 `..` 穿越、防符号链接）；**②** SQL 一律参数化查询，绝不用模型给的字符串拼接；**③** shell 命令不用 `shell=True` 拼接，参数走 argv（模型的参数里可以有空格与分号）；**④** 所有模型传入的 id 先做格式校验（正则）再进业务逻辑，非法直接返回 `INVALID_ARG`。

### 3.4 错误处理：把错误写成"说明书"

```python
def execute_tool(call):
    """永不抛异常：所有失败都变成结构化结果，供模型决策。"""
    name = (call.get("name") or "").strip().lower()          # 名字大小写/空格归一化
    fn = TOOL_REGISTRY.get(name)
    if fn is None:
        return {"ok": False, "error": {"code": "NO_SUCH_TOOL",
                "message": "没有名为 %s 的工具。可用工具：%s" % (name, ", ".join(sorted(TOOL_REGISTRY)))},
                "retryable": False}                          # 不可重试：换工具才对
    try:
        args = json.loads(call.get("arguments") or "{}")      # arguments 是字符串，且可能是坏 JSON
    except ValueError as exc:
        return {"ok": False, "error": {"code": "BAD_JSON", "message": "参数不是合法 JSON：%s" % exc},
                "retryable": True}                            # 可重试：让它重发参数
    try:
        return {"ok": True, "data": fn(**args)}
    except TypeError as exc:                                  # 参数名/数量错
        return {"ok": False, "error": {"code": "BAD_ARGS", "message": str(exc)}, "retryable": True}
    except TimeoutError:
        return {"ok": False, "error": {"code": "TIMEOUT", "message": "工具超时，可换个条件重试"}, "retryable": True}
    except Exception as exc:
        LOG.exception("tool crashed")
        return {"ok": False, "error": {"code": "INTERNAL", "message": "工具内部错误，已上报"}, "retryable": False}
```

**可重试 / 不可重试的判据只有一句话：换个参数重试有没有可能成功？** 资源不存在（`NOT_FOUND`）、无权限（`DENIED`）都不该重试；超时、坏 JSON、临时不可用可以。这个分类要显式写进返回值，模型（和小模型路由）都看得懂。

### 3.5 幂等与副作用

- **只读工具标 `readonly: true`**，在确认策略里可以直接放行；写工具必须走确认或幂等键。
- **幂等键的生成位置在执行层，不在模型**：`request_id = sha1(session_id + tool_name + canonical_args)`。模型重发同样参数的调用时命中同一键，服务端只执行一次。
- **重试前先查状态**："POST 超时"之后正确动作是 `get_status(request_id)`，不是盲目重发。
- **给写工具加 dry-run 模式**：先让模型调用 `preview_refund(order_id)`，确认后再执行——比事后回滚便宜得多。

### 3.6 超时、并发与顺序依赖

| 问题 | 表现 | 处理 |
|---|---|---|
| 单个工具挂死 | 整个 Agent 卡在某一步 | 每个工具独立超时（只读 5s、写 10s、慢查询单独放宽），超时转成 `TIMEOUT` 结果 |
| 串行太慢 | 5 个独立查询 5×2s = 10s | 模型一轮可返回**多个** `tool_calls`，执行层并发跑（`ThreadPoolExecutor`），再一次性回填多条 tool 消息 |
| 并发有依赖 | 模型在同一轮里既 `create_order` 又 `pay_order`，pay 用了还没生成的 id | **拆轮次**：分阶段暴露工具（第 1 阶段只给创建类）；或执行层对同一组调用串行化并检测参数引用 |
| 触发限流 | 并发 20 个请求被服务端 429 | 并发上限（4–8）+ 退避重试 + 把 429 作为 `retryable=True` 的观察结果回灌 |
| 结果顺序 | 模型把第 2 个结果当第 1 个的 | 每条结果通过 `tool_call_id` 与请求一一对应，**顺序无关**，别依赖数组下标 |

### 3.7 大返回值：给模型的是索引，不是全文

- **先裁剪再入上下文**：单条工具结果设上限（如 2000 字符），按**语义边界**截断（行、段落、JSON 结构），并显式标记 `"truncated": true`，同时告诉模型"如何取更多"（分页参数、`doc_id`）。
- **结构化摘要代替原文**：`{"total": 1832, "returned": 20, "items": [...]}` 比 1832 行列表有用得多。
- **资源引用模式**：大对象落盘/入库，上下文里只留 id + 摘要；模型要细节时再调 `read_chunk(doc_id, offset)`。这是长任务 Agent 能在小窗口里干活的关键（`docs/第07章`）。
- **别把"用不到的字段"喂给模型**：内部 API 返回 40 个字段，工具层只保留 5 个与决策相关的——**裁剪本身就是提示工程**。

### 3.8 schema 的单一来源

手写 schema 与实现分开维护，迟早漂移（改了参数名忘记改 schema，模型继续传旧名字）。做法是**从代码生成 schema**：用函数签名 + 类型注解 + docstring 生成 `parameters`（`pydantic` 的 `model_json_schema()`、`inspect.signature` 都能做），或反过来用 schema 生成实现骨架。**同一个工具，只有一份定义。** 这也是 `code/common/tools.py` 里注册表存在的意义。

## 四、横向对比

### 4.1 三种"让模型用工具"的实现路线

| 维度 | 原生 Function Calling | 文本解析（ReAct 文本版） | 代码执行沙箱（Code Interpreter 风格） |
|---|---|---|---|
| 模型输出 | 结构化 `tool_calls` | 自由文本 + 约定格式 | 一段可执行代码（如 Python） |
| 解析成本 | 无（结构化字段） | **高**：正则、格式失败、参数转义 | 无解析，但要做代码沙箱 |
| 可靠性 | 高 | 中（格式失败是常态） | 高（代码由解释器执行） |
| 一轮多调用 | 支持（多个 `tool_calls`） | 难（要约定多行格式） | 天然支持（代码里循环调用） |
| 可移植性 | 各服务商字段有差异 | **最好**（任何模型都能用） | 需要执行环境 |
| 安全风险 | 参数级（校验即可） | 参数级 + 解析歧义 | **执行级**（代码逃逸风险最高） |
| 表达复杂逻辑 | 差（一次一个动作） | 差 | **好**（可以写循环、条件、数据处理） |
| 何时选 | 生产默认 | 自建/开源模型、教学、极简环境 | 数据分析、批量处理、需要中间计算的场景 |

**实践结论**：生产用原生 FC；文本版 ReAct 是理解原理与兼容旧模型的方案（`docs/第05章` 讲过它的五个真实故障）；代码沙箱适合"数据处理"类任务，但要接受最高的隔离要求（容器 + 无网络 + 只读挂载 + 资源限额）。

### 4.2 工具设计的三种粒度对照（同一业务）

任务："客户要查上周订单 DP1002 的物流，如果已签收就告诉签收时间"。

| 设计 | 工具集 | 模型需要几轮 | 风险 |
|---|---|---|---|
| 细粒度 | `get_order` + `get_logistics` + `compare_date` | 3–4 轮 | 中间任一步选错工具就偏；token 累计高 |
| 中粒度（推荐） | `get_order_status(order_id)` 返回状态与签收时间 | 1–2 轮 | 灵活性略降，但覆盖 90% 场景 |
| 粗粒度 | `answer_customer_question(question)` | 1 轮 | 模型失去可控性，等于把业务逻辑交给模型 |

## 五、常见故障与排查

### 故障 1：选错工具（相似工具混淆）

- **现象**：用户问"订单状态"，模型调了 `search_orders`（列表）而不是 `get_order`（单据详情）；或调了 `get_policy`.
- **定位**：trace 里统计"实际调用工具 vs 期望工具"，按工具对（confusion pair）聚合——大多数选错集中在 3–5 组相似工具上。
- **解决**：① **合并同义工具**（最有效）；② 名字带上区分词（`get_order_by_id` / `list_orders_by_user`）；③ 描述里补"何时不用"（"若要查单个订单，用 `get_order`"）；④ 减少工具总数，超过 20 个考虑分层/路由。

### 故障 2：参数漏填 / 类型错 / 名字错

- **现象**：`{"error": "missing 1 required positional argument: 'order_id'"}`、`{"days": "三天"}`、`{"orderId": "DP1002"}`。
- **定位**：打印 `call["arguments"]` **原文**（它是一段字符串，可能本身就不是合法 JSON）。
- **解决**：① `required` 与 `enum` 补齐；② 校验失败的**具体信息**回灌给模型（"`days` 必须是 1–30 的整数，你传的是字符串"）；③ 描述里给一个合法示例值；④ 参数别名做一次兼容映射并记录命中次数。

### 故障 3：反复调用同一个工具（用相同参数）

- **现象**：同一签名调用 4 次，模型每轮都说"我再查一次"。
- **定位**：按签名统计重复次数；重点看**返回给模型的观察结果有没有提供可决策的新信息**。
- **解决**：① 返回值里补上"下一步建议"（"未找到订单 DP1002，可用手机号查询，或确认单号是否有误"）；② 重复第 2 次时注入提示（"相同参数已经调用过且结果相同"）；③ 第 3 次终止（`docs/第05章` 的闸门）；④ 检查工具是不是静默返回了空数据（`ok=true` 但内容为空）。

### 故障 4：工具返回过长撑爆上下文

- **现象**：跑到第 4 轮突然 `context_length_exceeded`；或模型开始忽略早期指令。
- **定位**：逐步打印每轮 `prompt_tokens`，找出"哪一步跳涨"——通常是某个工具返回了全量列表或整篇文档。
- **解决**：① 工具层裁剪（上限 + 语义截断 + `truncated` 标记）；② 只返回决策必要的字段；③ 大对象走 `doc_id` 引用 + 按需分页读取；④ 对高频工具加结果缓存，避免重复拉取。

### 故障 5：工具异常导致整个程序崩溃

- **现象**：第三方 API 抖动时，用户看到 500，而不是"抱歉，查询失败"。
- **定位**：看异常栈是否穿过了 Agent 主循环；确认执行层有没有统一的 `try/except` 兜底。
- **解决**：① 执行层**永不抛异常**，全部转成 `{"ok": false, ...}`；② 超时用独立线程/信号量强制中断；③ 区分"可重试/不可重试"；④ 主循环对 `execute_tool` 的返回值做结构校验（防止工具层自己写坏格式）。

### 故障 6：串行调用慢（用户体验差）

- **现象**：5 个独立查询串行 10 秒，用户以为卡死。
- **定位**：trace 里累加各步耗时，看是否存在"无依赖却串行"的调用序列。
- **解决**：① 让模型在**同一轮**返回多个 `tool_calls`，执行层并发执行；② 提供批量接口（`get_orders(ids=[...])`）把 N 次调用压成 1 次；③ 高频只读结果加缓存；④ 流式输出中间状态（"正在查询物流…"）降低感知延迟。

### 故障 7：并行调用的顺序依赖（最难发现的一类）

- **现象**：模型同一轮里 `create_order` + `pay_order`，`pay_order` 用了占位的假 id，两个都返回成功，但支付落到了别的地方（或失败）。
- **定位**：检查同轮多个 `tool_calls` 之间是否存在**参数引用关系**（一个调用的参数出现在另一个调用的结果里）。
- **解决**：① **分阶段暴露工具**（创建阶段不给支付工具）；② 执行层检测引用并强制串行 + 回灌"请先用第一步的结果再调下一步"；③ 参数校验层拒绝"看起来像 id 但格式不符"的值；④ 对写操作要求幂等键，避免误执行。

### 故障 8：模型不调工具，直接编答案

- **现象**：明明给了 `get_order`，模型却回答"您的订单已发货"（它没查）。
- **定位**：trace 里 `tool_calls` 为空但答案包含具体业务数据。
- **解决**：① 提示词把"必须调用工具"写成完成条件（"回答中出现的任何订单信息必须来自工具结果"）；② 关键路径用 `tool_choice` 强制首次必须调用；③ 收工前加一次轻量检查：答案里的事实是否都能在工具结果中找到；④ 拉高"未调用工具的答案"的失败判定（进评测集）。

### 故障 9：schema 与实现漂移

- **现象**：改了实现（参数改名），线上出现 `TypeError`；或模型按旧 schema 传参，工具静默忽略新参数。
- **定位**：对比 schema 定义与函数签名（可以用脚本自动比对）。
- **解决**：① **从签名/类型生成 schema**，单一来源；② schema 变更走版本号（出现在 trace 里）；③ CI 里加一条"schema 与实现一致性"的测试；④ 工具描述里不要写会变的业务数字（否则每次变了都要改提示）。

### 故障 10：流式响应下 `tool_calls` 被截断

- **现象**：开了流式后，`arguments` 经常解析失败，报 JSON 不完整。
- **定位**：打印每个 chunk 的 `delta.tool_calls` —— 流式下参数是**分片增量**到达的，第一片常常只有 `name`，后续片只有 `arguments` 的片段，多个工具调用用 `index` 区分。
- **解决**：按 `index` 累积拼接 `arguments`，直到 `finish_reason` 出现或流结束再解析；**不要在第一个 chunk 就尝试 `json.loads`**。

## 六、面试要点

**1. Function Calling 的原理是什么？**
骨架：① 请求携带工具清单（名字/描述/参数 schema）；② 模型输出结构化意图（`tool_calls`：名字 + 参数 JSON 字符串），**不执行**；③ 你的代码执行并把结果以 `role="tool"` 消息回填；④ 循环直到模型不再请求工具；⑤ 模型只做"选择 + 填参"，可靠性取决于描述质量与 schema 严格度。

**2. 怎么提升工具调用的准确率？**
骨架：① 描述写清"何时用/何时不用/返回什么"；② 合并同义工具、控制数量（>20 要分层）；③ schema 用 `enum`/`pattern`/`required` 约束；④ 给示例与参数格式说明；⑤ 关键路径 `tool_choice` 强制调用；⑥ 用 trace 统计选错率与参数错误率，按 confusion pair 优化。

**3. 工具太多（50+）怎么办？**
骨架：① 分层：先给工具目录，模型选命名空间后再加载 schema；② 路由：轻量分类器先选候选集；③ 合并同义工具；④ 在应用侧裁剪 MCP Server 暴露的工具；⑤ 全量注册的代价：仅工具定义就可能吃掉数万 token，还会降低选择准确率。

**4. 工具执行失败了，Agent 该怎么处理？**
骨架：① 失败转成结构化观察结果（`ok=false` + `code` + `retryable`）；② 判据："换个参数重试可能成功吗"；③ 错误信息写成说明书，给出下一步建议；④ 重试上限 + 退避 + 预算；⑤ 兜底降级（转人工 / 返回部分结果）。

**5. 怎样设计一个好工具？（ACI 视角）**
骨架：① 名字可被模型理解（动词 + 对象 + 限定）；② 描述包含何时用/何时不用/返回结构/失败语义；③ 参数少而明确，避免自由文本；④ 返回值裁剪且有稳定结构；⑤ 幂等与超时策略；⑥ 错误可分类；⑦ 设计标准是"让模型少做猜测"。

**6. 参数是模型生成的，怎么保证安全？**
骨架：① 参数视为不可信输入，服务端必须二次校验；② 路径白名单（`realpath` + 前缀）；③ SQL 参数化、禁 shell 拼接；④ id 类参数做正则校验；⑤ 危险工具人工确认 + 参数原样展示 + 审计日志；⑥ 最小权限（只读账号、沙箱目录）。

**7. 并行调用的坑有哪些？**
骨架：① 顺序依赖（同一轮里后续调用依赖前面的结果）；② 幂等（重试导致重复写入）；③ 限流（并发被 429）；④ 结果顺序（用 `tool_call_id` 对应，不要按数组下标）；⑤ 成本（并发不省 token，只是省时间）。

**8. 返回值太大怎么处理？**
骨架：① 语义截断 + `truncated` 标记；② 只返回决策必要字段；③ 结构化摘要（total/returned/items）；④ 大对象用 `doc_id` 引用 + 按需分页读取；⑤ 高频结果加缓存；⑥ 把它当成提示工程的一部分：**你给模型看什么，它就只能基于什么思考**。

**9. 原生 Function Calling 与文本 ReAct 怎么选？**
骨架：① 生产默认用原生（结构化、可靠、易并行）；② 文本版用于自建/老模型与教学，格式失败率高、参数转义是常见坑；③ 两者不能在同一循环里混用（消息结构冲突）；④ 原生的短板：模型在决定调工具时常把注意力放在 `tool_calls`，`content`（推理）可能为空——需要显式要求或用单独的推理步骤补。

**10. 幂等性怎么落地？**
骨架：① 幂等键由**执行层**生成（`session + tool + 规范化参数` 的哈希），不依赖模型；② 服务端按幂等键去重；③ 超时后先查状态再决定是否重发；④ 写工具支持 dry-run / preview；⑤ 审计日志记录幂等键，便于对账。

**11. 工具的 schema 怎么维护？**
骨架：① 单一来源（从函数签名/类型生成，或反之以 schema 为准）；② CI 校验一致性；③ schema 变更要有版本号并进 trace；④ 描述里不写易变的业务数字；⑤ 与 MCP/外部 Server 对接时，把远端 schema 做一次规范化（补 `additionalProperties: false`、去掉无关字段）。

**12. 工具调用要观测哪些指标？**
骨架：① 调用成功率（按工具分）；② 选错率（与期望工具对比，做 confusion pair）；③ 参数错误率（缺字段/类型错/坏 JSON）；④ 重复调用率（绕圈信号）；⑤ 平均调用轮数与 P95；⑥ 单工具耗时与超时率；⑦ 危险工具确认通过率。
