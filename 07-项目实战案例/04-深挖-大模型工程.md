# 深挖：大模型工程

> **一句话** · 这条线的核心矛盾是：大模型是一个**你无法测试、无法预测、无法控制成本、还随时会挂**的外部依赖，而工程化的全部工作就是把「一个不可靠的远程调用」改造成「一个可预算、可降级、可归因、可计量的系统组件」——这个项目的 `pkg/llm` 只完成了前一半：它把模型**接进来了**，但没有把它**管起来**。
>
> **读完你能回答：** ① 你的 LLM 调用超时设在哪一层、设多少？429 打过来会发生什么？ ② 一次 5 轮的 Agent 对话花多少 token？为什么必须把输入和输出分开统计？ ③ 你的中文知识库切片是怎么切的？检索效果变好了你怎么知道？

**行号约定：** 相对项目根，格式 `文件:行号`。全文的「这个项目」指 `bitguide-agent-platform-go`。

## 一、本质：把大模型接进生产系统，难在哪

先破除一个幻觉。调用大模型**真的不难**——这个项目的全部 LLM 客户端实现是 236 行（`pkg/llm/openai.go`），其中真正干活的 `Chat` 只有 22 行（`openai.go:52-74`），核心是一次 SDK 调用加一次字段拷贝，写过 HTTP 的人半天能写完。**难的不是「调用」，难的是「调用挂了之后怎么办」，而后者在这个项目里几乎完全没有被回答。**

把大模型当成外部依赖看，它有四处和普通微服务不一样，每一处都在代码里留下了痕迹：

**① 它是一个不可靠的依赖，失败模式比普通服务脏得多。** 普通 RPC 挂掉就三种：连不上、超时、返回错误码。大模型多了几种：连上了但一直不返回、返回 200 但 `choices` 是空数组、返回 200 但 `tool_calls` 里的 arguments 是半截 JSON、返回 429 让你等 3 秒再来、返回 400 因为你上一轮拼进历史的消息协议不合法。这五种在这个项目里**被当成同一种东西处理**：`fmt.Errorf("LLM 调用失败: %w", err)`（`openai.go:66`、`openai.go:105`），或者干脆静默吞掉——`openai.go:69-71` 把空 `choices` 返回成 `("", nil)`，`openai.go:118-126` 把 `json.Unmarshal` 的 error 丢掉。上层 `base.go:320-322` 拿到 error 就返回，循环终止，用户看到「错误: LLM 调用失败: ...」。

**② 它的成本不可控，因为成本单位不在你的代码里。** 大模型的成本是 token，而 token 数量由「历史多长 × 检索回来几段 × 工具描述多啰嗦 × 模型决定思考几轮」四个半可控变量相乘决定。这个项目的 `pkg/llm` 里**没有一处统计 token**——`grep -rn "tokens" pkg/llm/` 只命中两个 `maxTokens` 字段声明（`openai.go:19`、`openai.go:37`），`pkg/log/log.go:346` 的 `LLMResponse(model, tokens)` **全仓零调用者**。而 SDK 返回的 `ChatCompletionResponse.Usage` 就在手边，`openai.go:130-133` 构造 `ChatResponse` 时只取了 `Content` 和 `ToolCalls`——**成本数据一路送到手边，被丢掉了**。

**③ 它的延迟不可预测，而且是长尾的。** 一次非流式的 7B 调用（prompt 2000 token、生成 300 token）：本地 Ollama 5-20 秒，云端 API 2-8 秒，排队就是 30 秒。而这个项目**没有任何超时**：`openai.go:29-35` 建客户端时没设 `HTTPClient`，go-openai 回落到零值 `http.Client`（`Timeout = 0`，永不超时）；`openai.go:42` 的 embedding 客户端就是 `&http.Client{}`。`grep -rn "Timeout" pkg/llm/` **零命中**——全项目唯一一处超时在 `pkg/rag/milvus.go:37`，那是连 Milvus 的 10 秒。调用方传的全是 `context.Background()`（`cmd/stage1/main.go:186`、`cmd/stage2/main.go:228`）。**模型不返回，进程就永远等下去。**

**④ 它的行为无法用单元测试固定。** 同一句 prompt 两次调用结果不同（temperature 未生效，见 2.2），工具调用可能这轮调、下轮不调。做回归的前提是能固定输入和输出分布，而这个项目连 `temperature` 都没传进请求。加上**全仓 `find . -name "*_test.go"` 返回 0 个文件**，这条线上没有任何自动化防线。

结论：**`pkg/llm/openai.go` 是一份「能跑通的 demo」，不是「能上生产的客户端」。** 它的价值在于协议打通、分层做对（见 2.1）；剩下的超时/重试/计量/流式/结构化校验五件事，正是第三节的全部内容。

## 二、这个项目怎么实现的（带行号）

### 2.1 LLM 客户端的分层

三层，职责划分是对的，但每一层都很薄。

**接口层（`pkg/llm/client.go:40-52`）** 定义四个方法：`Chat`、`ChatWithTools`、`Embed`、`EmbedBatch`，覆盖 Agent 平台的全部模型需求。**所有方法第一个参数都是 `context.Context`**——说明作者知道要留取消和超时的接口，只是上游没人用（`cmd/stage1/main.go:186` 传 `context.Background()`）。Agent 只依赖这个接口（`base.go:47` 持有 `llmClient llm.Client`），所以换供应商、加中间层都不用动 Agent。这个抽象是对的。

**实现层（`pkg/llm/openai.go`）** 唯一实现，走 OpenAI 兼容协议。实际意义是：**Ollama 也实现了 `/v1/chat/completions`**，所以 `stage1.yml:40` 的 `baseUrl: http://localhost:11434/v1` 让本地模型和云端模型共用一套代码。`Chat`（`openai.go:52-74`）与 `ChatWithTools`（`openai.go:77-134`）的差别只是请求体里多一个 `Tools` 字段（`openai.go:102`）。

**路由层（`pkg/llm/gateway.go`）** `LLMGateway` 按 `modelRef` 选客户端：

- 缓存是 `sync.Map`（`gateway.go:17`），构造时**预创建**配置里的所有客户端（`gateway.go:31-35`），避免请求路径上建连接。
- `GetClientForModel`（`gateway.go:47-57`）：空 ref 返回默认客户端；命中缓存返回对应客户端；**未知 ref 静默回落默认模型**（`gateway.go:56`）。
- 自己实现 `Client` 接口，四个方法全部委托给默认客户端（`gateway.go:98-118`），所以 `LLMGateway` 可以**直接当 `llm.Client` 传给 Agent**（`cmd/stage2/main.go:100` 就是这么做的）。`gateway.go:98` 的 `var _ Client = (*LLMGateway)(nil)` 是编译期接口断言，好习惯。
- `ResolveLLMGateway`（`gateway.go:122-143`）从 `cfg.Models` 提取多模型配置。

**做得好的地方：** 分层干净、接口最小、网关可当客户端用、有编译期断言。**天花板在哪：** 路由能力**写完了但没被用起来**——`GetClientForAgent`（`gateway.go:60-65`）按 `AgentConfig.ModelRef` 路由，而 `stage3.yml:18` 是 `modelRef: ""`，`stage1.yml:37-43` 连 `models` 段都没有。所以「多模型路由」在默认配置下永远走 `defaultClient` 那一支（`gateway.go:61-62`）。**能力在代码里，配置里是空的**——这是被追问时最容易被戳破的一类「我实现了 X」。正确用法见 3.3 的「模型分级路由」。

### 2.2 一次调用的完整参数（哪些配了、哪些没用）

| 参数 | 项目里配了吗 | 传进请求了吗 | 证据 |
|---|---|---|---|
| `Model` | 配了 | **传了** | `openai.go:100`；`stage1.yml:41` = `qwen2.5` |
| `Messages` | — | **传了** | `openai.go:101` |
| `Tools` | — | **传了** | `openai.go:102` |
| `Temperature` | **配了 0.7** | **没传** | 定义 `config.go:26`；`stage1.yml:42` = 0.7；请求体里没有 |
| `MaxTokens` | **配了 2000/2048** | **没传** | 定义 `config.go:25`；`stage1.yml:43` = 2000、`stage3.yml:11` = 2048；装进结构体 `openai.go:37`；请求体里没有 |
| `Stream` | 没配 | — | `grep -rn "stream" pkg/llm/` 零命中 |
| `ToolChoice` / `ResponseFormat` / `TopP` / `Seed` | 没配 | — | 全仓无 |

`openai.go:99-103` 的请求体只有三个字段：`Model`、`Messages`、`Tools`。

**这不是「配了忘了传」的笔误，是有工程后果的：**

1. **temperature 不受控 → 无法做回归。** 你改了切片参数、改了 prompt，想对比两版效果，但采样温度由服务端默认值决定（Ollama 默认 0.8，OpenAI 默认 1.0），同一 prompt 的两次输出差异可能比你两次改动的差异还大。**没有确定性就没有 A/B。**
2. **maxTokens 不受控 → 输出可能被截断，而且你不知道。** 服务端默认上限普遍远小于你需要的长度（很多网关默认 512 甚至 128）。模型在第三个活动说到一半撞上默认上限，返回 `finish_reason: "length"`——而 `openai.go:112-133` **完全不看 `finish_reason`**，截断的回答被当成完整答案返回给用户（`base.go:325-328`）。这是一个**用户可感知、开发不可见**的 bug 类别。
3. **`tool_choice` 缺失 → 强制工具调用只能靠 prompt。** Skill 场景想让「第一步必须调 `get_weather`」，正解是 `tool_choice` 指定函数名；这个项目只能在 system prompt 里写「你必须调用工具获取准确结果，不要仅凭记忆估算」（`skill_enhancer.go:73`），把确定性交给模型的自觉。

顺带一个同类的「静默失败」：`openai.go:108-110`，`len(resp.Choices) == 0` 时返回 `&ChatResponse{}, nil`——**空响应 + nil error**。上层 `base.go:325-328` 看到 `len(ToolCalls) == 0` 就把空 `Content` 当最终答案返回，用户看到一片空白，没有任何错误提示。更糟的是 `cmd/stage1/main.go:186` 用 `if response == ""` 判断「Skill 未命中」，所以「Skill 命中但模型返回空」会**再触发一次完整的普通对话**——一次请求付两次 LLM 调用。

### 2.3 Embedding 为什么手写 HTTP 而不用 SDK

**这是这条线上最值得讲的取舍，因为它不是「不会用 SDK」，而是「用了 SDK 但故意在一个地方不用」。**

同一个文件里两种做法并存：`Chat` 走 go-openai SDK（`openai.go:29-35` 建 client，`openai.go:61` 调用），`Embed`/`EmbedBatch` 走手写 HTTP（`openai.go:154-236`：`http.NewRequestWithContext` + `json.Marshal` + 自己定义请求/响应结构体 `embeddingRequest`/`embeddingResponse`，`openai.go:136-152`）。

**为什么这个取舍说得通（三条真实理由）：**

1. **Embedding 端点是各家差异最大的地方。** Chat 接口有 `chatml` 事实标准压着，兼容度高；Embedding 是「形似神不似」的重灾区——`data[].index` 顺序不保证、`usage` 字段缺失或名字不同、`object` 取值五花八门。手写解析后只依赖**最小契约**：`data[].embedding` 和 `error.message`（`openai.go:143-152` 只定义这两个字段）。契约面越小，换供应商炸的概率越小。
2. **`Input` 字段要能吃两种类型。** `embeddingRequest.Input` 声明成 `any`（`openai.go:138`），同一个结构体既能发 `"一段文本"` 也能发 `["文本1","文本2"]`。
3. **模型名要完全自由。** 项目用的是 `nomic-embed-text`（`openai.go:39` 硬编码默认值，`stage1.yml:56` 配置化），一个非 OpenAI 模型；手写意味着模型名纯粹是个字符串，不受任何 SDK 类型或白名单约束。

**但这个取舍有一个真实代价，而且项目正好踩中了：手写之后连 HTTP 状态码都不看了。** `openai.go:206-228` 拿到 `resp` 后**没有检查 `resp.StatusCode`**，直接 `io.ReadAll` 再 `json.Unmarshal`。后果：网关返回 401 时响应体不是 JSON，`json.Unmarshal` 失败 → 用户看到的错误是「解析响应失败: invalid character '<' looking for beginning of value」（`openai.go:222`），**而不是「401 未授权」**。排查一个认证问题从 5 秒变成 30 分钟。SDK 在这里恰恰免费帮你做了正确的事：先看状态码、再解析、把错误体包装成可读错误。

**面试口径：** 「Chat 走 SDK、Embedding 手写 HTTP，是有意的。Embedding 端点在各家的兼容度远低于 Chat，手写让我只依赖 `data[].embedding` 这一个最小契约，换供应商不会因为某个可选字段缺失就崩，也能用任意模型名。但手写之后我付出了 SDK 的免费保障——状态码检查、错误体解析——所以我在 `do` 之后补了 `StatusCode != 200` 的分支。**结论是：兼容性诉求用手写，但手写必须自己把 SDK 替你做的事做完。**」**边界：** 如果只用 OpenAI 官方 + 官方模型，手写毫无收益、纯增维护面；这个取舍的前提是「多供应商兼容」，而项目恰好连 `nomic-embed-text` 都要支持，前提成立。

## 三、五个必须知道的工程细节

### 3.1 超时设在哪一层

**现状：全层无超时。** 证据链完整：

- `openai.go:29-35`：`openai.DefaultConfig(cfg.APIKey)` 只设了 APIKey，**没有设 `HTTPClient`**，go-openai 回落到零值 `http.Client`（`Timeout = 0`，永不超时）。
- `openai.go:42`：`httpClient: &http.Client{}`——embedding 客户端更直白。
- `grep -rn "Timeout" pkg/llm/` → **零命中**；`config.go:20-27` 的 `LLMConfig` 里**没有 timeout 字段**，也没法从配置注入。
- 调用方：`cmd/stage1/main.go:186`、`cmd/stage2/main.go:228` 传 `context.Background()`，**没有 deadline、不可取消**。
- 唯一存在的超时是 `pkg/rag/milvus.go:37`：`context.WithTimeout(context.Background(), 10*time.Second)`——连 Milvus 的，不是连 LLM 的。这个对比很刺眼：**连向量库都记得设 10 秒，连模型一次都不设。**

**超时必须分四层设，而且各层数值不同：**

| 层 | 该设多少 | 为什么是这个数 | 项目现状 |
|---|---|---|---|
| 连接建立（Dial） | 1-3s | DNS + TCP + TLS；超过 3 秒说明网络或网关有问题，重试更划算 | 无（零值 `http.Client`，Dial 用默认无超时） |
| 单次 LLM 调用 | 非流式 60-120s；流式首字节 10-30s | 本地 7B 生成 500 token 约 10-25s；云端排队会到 30s+；留 3 倍余量 | **无** |
| 单次工具执行 | 5-30s | `calculator`/`datetime` 是纯计算，1s 都嫌多；外部搜索类 10-30s | **无**（`tool.Tool.Execute` 签名里根本没有 `ctx`，`pkg/tool/tool.go:4-16`——**结构性不可能有超时**） |
| 整个请求 | 120-300s | 这是 ReAct 循环的总预算，循环上限 10 轮（`base.go:296`） | **无** |

**关键设计点：整体预算必须显式设置并向下分配，否则等于没设。** 如果单次 LLM 超时 60s、循环 10 轮，最坏情况是一个请求挂 600 秒（10 分钟）；但如果入口预算是 120s，第 3 轮就会因为预算耗尽而中断。**正确做法是自上而下**：入口 `ctx, cancel := context.WithTimeout(r.Context(), 120*time.Second)`，往下原样传；每层用 `context.WithTimeout(ctx, 层预算)` 但不超过父 ctx 的剩余时间——Go 的 `context` 天然保证这点（子 deadline 晚于父 deadline 时以父为准），这是 Go 在这个问题上最优雅的地方。

**流式的特殊规则（容易答错）：** 一旦上了流式，**不能用 `http.Client.Timeout`**——它计的是「从发出请求到读完整个 body」的时间，会把正常的长生成连接切断。流式要改成 `Transport.ResponseHeaderTimeout`（等响应头的时间）+ 每次调用的 `context` 预算。

**怎么补（最小改动）：**

```go
clientConfig := openai.DefaultConfig(cfg.APIKey)            // openai.go:29-35 附近
clientConfig.HTTPClient = &http.Client{
    Transport: &http.Transport{
        DialContext: (&net.Dialer{Timeout: 3 * time.Second, KeepAlive: 30 * time.Second}).DialContext,
        ResponseHeaderTimeout: 30 * time.Second,   // 流式友好：不限制 body 读取时长
        MaxIdleConnsPerHost:   50,
    },
    // 刻意不设 Timeout：单次调用超时由 per-call context 控制
}
```

配套两处：`config.LLMConfig` 加 `TimeoutMs` 字段；**`tool.Tool.Execute` 签名加 `ctx context.Context`**（这是这个项目所有工具超时的根子——`pkg/tool/tool.go:4-16` 不加这个参数，工具永远无法被取消）；此外 `base.go:300` 之前要用带 deadline 的 `ctx` 替换调用方的 `context.Background()`。

### 3.2 重试：什么错该重试、什么不该

**现状：完全没有重试。** `grep -rni "retry\|backoff\|429" pkg/llm/ pkg/rag/ pkg/agent/base.go` → **零命中**。一次 429 的完整后果链：`openai.go:104-106` 包装成 error → `base.go:320-322` `return "", fmt.Errorf("LLM 调用失败: %w", err)` → `cmd/stage1/main.go:196-199` 打印「错误: LLM 调用失败: ...」并 `continue`。**用户丢掉的是一个已经等了几秒的回答，代价零收益。**

**分类是重试的全部智慧（按状态码）：**

| 错误 | 该重试吗 | 退避策略 | 原因 |
|---|---|---|---|
| 429 Too Many Requests | **该** | 优先看 `Retry-After` 头；没有则基数 2s、最多 3 次 | 明确是「现在不行，等会儿行」。有配额语义，退避基数要**比 5xx 大**，否则重试只会继续吃 429 |
| 500 / 502 / 503 / 504 | **该** | 基数 500ms、×2、最多 3 次 | 服务端瞬时故障 |
| 连接超时 / connection reset | **该** | 同 5xx | 网络抖动；但**这在计费上不幂等**（见下面边界） |
| 400 Bad Request | **不该** | — | 请求本身有问题（消息协议不合法、schema 不合法）。重试 3 次得到 3 次同样的 400，白等 3 倍延迟 |
| 401 / 403 | **不该** | — | 认证/权限。配置问题，**要立刻熔断并告警**，否则每个请求都白跑 |
| 404（模型不存在） | **不该** | — | 配置问题 |
| 422 / `context_length_exceeded` | **不该** | — | 请求太大，必须**改请求**（截断历史、裁 RAG 上下文）后重试，不是原样重试 |
| 工具执行错误 | **不该盲目重试** | — | 这个项目做对了：把错误作为 `role:"tool"` 消息回喂模型让它自愈（`base.go:359-368`）。模型会换参数再试，比在底层无脑重试聪明 |

**指数退避 + 抖动（jitter）的标准形态：** `delay = min(maxDelay, base × 2^attempt) × random(0.5, 1.0)`。**抖动不是可选项**：没有抖动时，多个副本会在同一个 429 之后**在同一时刻**一起重试，形成惊群，把上游从「限流」打成「持续过载」——重试反而让故障更久。

**三条边界，讲出来就是深度：**

1. **重试必须算在超时预算内。** 不能「单次超时 60s × 重试 3 次 = 最坏 180s」，那是在给用户制造新问题。正确做法是重试循环每一轮都检查 `ctx` 剩余时间（`ctx.Err()` / `ctx.Deadline()`），预算不够就直接返回最后一次错误。
2. **重试不是幂等的，因为钱不幂等。** LLM 调用在语义上幂等，但在计费上不幂等：第一次可能已经生成了 500 token 才断在网络上，重试一次就是**付两次钱拿一份结果**。所以重试次数要有上限、要有总耗时预算——而这些「白花的钱」本该被计量，只是项目连正常花费都不统计（见 3.3）。
3. **重试不该写在 LLM 客户端里，该写在网关层。** 因为只有网关知道「这个 `modelRef` 有哪几个候选模型」。真正的生产形态是**重试 + 模型降级 fallback**：主模型连续 429 两次 → 切到备用模型（7B 切 1.5B，或 A 供应商切 B 供应商）→ 成功返回。这个项目的 `LLMGateway`（`gateway.go:15-20`）**已经有全部基础设施**（多模型缓存 + `GetClientForModel` 路由），只差一个「按健康度选客户端」的策略——**这是一个「已有能力、差最后一层」的典型位置，也是最容易讲成亮点的位置。**

### 3.3 成本控制：token 从哪来、怎么省

**现状：零 token 统计。** 三类证据：`pkg/llm/` 里没有 token 计数（`grep "tokens"` 只命中两个 `maxTokens` 字段声明）；`pkg/log/log.go:346` 的 `LLMResponse(model, tokens)` **零调用者**；`pkg/metrics` 的 6 个自定义指标里**没有任何 LLM 指标**（token 数、调用次数、错误率、TTFT 全无）。

#### 3.3.1 先量再说：输入和输出必须分开统计

这不是洁癖，因为**它们的价格差 3-5 倍**（量级参考：输入 $0.15-3 / 1M token，输出 $0.6-15 / 1M token）。只统计「总 token」，你无法知道该优化哪一侧。上层需要的也不是一个总数，是四个数：`input_tokens`、`output_tokens`、`cached_input_tokens`（前缀缓存命中量）、`calls`。这四个数的组合直接决定优化方向——**如果 `input/output` 是 40:1，所有精力都该压在输入侧。**

#### 3.3.2 token 从哪来：把这个项目的输入拆开算

两个估算基准（工程估算，不是精确值）：**中文**在主流 BPE 分词器（Qwen 系列约 150k 词表、OpenAI o200k）上**1 个汉字大约 0.6-1.5 个 token**，工程上按 **1 字 ≈ 1 token** 估（高频词「孩子」「教育」1 token 覆盖 2 个字，生僻字要 1-2 token）；**英文**是 **1 token ≈ 4 字符 ≈ 0.75 个单词**（OpenAI 官方口径）。推论：**同样一段意思，中文的 token 消耗约为英文的 1-1.5 倍，而中文的字符数只有英文的一半**——所以「按字符数估 token」在中文上尤其不准，混排（中文 prompt + 英文工具名 + JSON schema）时必须实测。

现在算这个项目一次调用的输入构成，每一项都能落到代码：

| 组成 | 估算 token | 依据 |
|---|---|---|
| System prompt | ~200 | `stage1.yml:11-23` 的亲子顾问提示词约 200 汉字 |
| **RAG 上下文** | **~2300** | topK=5（`service.go:31`）× 实测平均 chunk 长度 459 字（见 4.2 实测）≈ 2295 字 |
| 工具定义 | ~250 | 2 个内置（`stage1.yml:25-27`：calculator、datetime）+ 2 个 MCP（`mcp-servers/parenting/main.go:137,155`）；后两个的 description 和参数说明都是长句，单个 80+ token |
| 历史对话 | 0 → 5000 | `maxSize=50` 硬编码（`base.go:51` → `memory.NewConversationMemory(50)`），满后约 25 轮对话，每轮约 200 token |
| 当前输入 | ~20 | — |

**然后是这里最关键的一个机制：ReAct 每一轮都把上面全部内容重新发一遍。** `base.go:306-308` 每轮从 `session.Memory.BuildMessages(systemPrompt, userInput)` 重建消息列表，`base.go:316` 每轮重新生成 `toolDefs`，然后 `base.go:319` 把完整消息数组发出去。**没有任何增量发送或缓存复用。**

一次 5 轮（4 次工具调用 + 1 次收尾）的对话，输入累计大约：

```
第 1 轮  system 200 + RAG 2300 + tools 250 + 历史 250 + 输入 20   ≈ 3020
第 2 轮  上一轮 + assistant 消息 60 + tool 结果 40              ≈ 3120
第 3/4/5 轮  每轮各 +100                                        ≈ 3220 / 3320 / 3420
累计输入 ≈ 16,100 token          累计输出 ≈ 400 token
```

**输入 : 输出 ≈ 40 : 1。** 这不是这个项目的特例，是所有 Agent 系统的常态——每一轮都要重发全部上下文。**所以「输入是主战场」不是一句空话，是一个 40 倍的数量级判断。**

#### 3.3.3 怎么省（按收益排序）

**① 前缀缓存（prompt caching）——收益最大、改动最小。** 这个项目的输入前缀在 10 轮循环里**逐字节不变**：system prompt 是 `a.systemPrompt` + RAG 上下文（`base.go:282` 拼接结果），工具定义来自 `tool.GetToolDefinitions()`（`base.go:316`），历史只在末尾追加。这正是前缀缓存的理想形态。各家折扣（量级参考）：OpenAI 对 ≥1024 token 的前缀自动缓存，命中部分按 **0.25-0.5 倍**计价；Anthropic 的 cache read 是 **0.1 倍**（cache write 1.25 倍）；DeepSeek 的 cache hit 也是 **0.1 倍**。按 0.5 倍算，上面 16,100 token 里约 15,000 token（重复的 system + RAG + tools）能省近 40% 的输入成本；按 0.1 倍算能省 80% 以上。**但有个致命前提：前缀必须严格逐字节一致。** 所以「不要在 system prompt 里插当前时间戳」「不要按随机顺序拼 RAG 结果」「不要在工具定义里塞会变的东西」——违反任何一条，缓存命中率归零。这个项目目前是安全的（RAG 按 score 排序、`base.go:273-279` 顺序拼接），但**只要有人为了「让模型知道现在几点」在 system prompt 开头加一行时间，整条前缀缓存就废了**。这是一个值得主动讲给面试官的坑。

**② 历史压缩——这个项目最痛的一处浪费。** `BuildMessages`（`conversation.go:171-213`）把**全部历史**塞进每次都发的消息里，`maxSize=50`（`base.go:51`）满了以后**直接丢最旧一条**（`conversation.go:91-93`），**没有任何摘要**。后果：对话到第 20 轮时，每次 LLM 调用都要带 40 条历史，输入从 3000 token 涨到 8000+，而其中大部分信息已经不重要。**正确做法是分层压缩**：最近 3-5 轮保留全文（模型需要精确的指代消解），更早的用一次小模型调用压成 300 字摘要，以一个 `role:"system"` 消息插在历史开头。有意思的是，**类型定义里已经有 `InteractionTypeSummary = "summary"`（`conversation.go:16`），`BuildMessages` 也已经在处理它（`conversation.go:192-194` 映射成 system 角色）——但全仓没有任何一处产生 summary**。又是一个「管道铺好了，没接水源」。

**③ 模型分级路由——基础设施已就位，配置是空的。** `gateway.go:60-65` 的 `GetClientForAgent` 就是为这件事写的。合理分级：**Skill 匹配用 `qwen2.5:1.5b`**（`pkg/skill/manager.go:190-198` 每条消息做一次 LLM 匹配，是个纯分类任务，7B 完全浪费）、摘要压缩用 1.5b、主对话用 7b、复杂多步推理才升级到 14b/云端。配置现状：`stage1.yml:37-43` 只有单个 `llm` 段，`stage3.yml:18` 的 `modelRef: ""`——**换了模型也没人用得上**。

**④ 工具定义精简。** 工具 description 是每轮重发的固定成本。`mcp-servers/parenting/main.go:138,157` 的两条 description 加参数描述合计约 160 token，4 个工具加起来 ~250 token——单看不多，但乘以「每次对话 5 轮 × 每天 N 次请求」就可观。原则：**描述里只留「什么时候用」和「参数含义」，不要写营销文案**（`dataanalyzer.go:27`、`websearch.go:28` 的描述都长于必要）。

**⑤ 预算熔断——这个项目完全没有，而且容易被误认为有了。** `pkg/gateway/ratelimit.go:27,69` 实现了令牌桶限流（`stage3.yml:97-98`：globalQps 1000、userQps 10）。**但 QPS 限流挡不住成本风暴**：10 个用户各发起一次「带 40 条历史 + 5 段 RAG」的对话，每个请求 8000 token，QPS 只有 0.1，限流器完全不触发，而你已经花掉了 80,000 token。成本熔断需要**三层预算**：单次请求 token 上限（超了直接截断历史并提示）、单用户日预算、全局日预算——后两层超限时**同时打告警**，因为超了通常是代码 bug（比如循环里递归调用了 LLM）而不是用户行为。

**⑥ 隐藏成本：embedding 和重复索引。** 上面全是生成侧，别忘了向量化也要钱。知识库是 4 篇共 20554 字节（实测），按 500 字切片约 20 个 chunk，一次全量索引 = 20 次 embedding（`maxBatchSize=10` 硬编码在 `embedding.go:30`，所以是 2 次 HTTP）。看起来微不足道——**但项目每次启动都重新全量索引，而且不删旧数据**：`LoadDocumentsFromDirForKB`（`service.go:350-392`）不做清理，而 `cmd/stage1/main.go:84`、`cmd/stage2/main.go:81` 每次启动都直接调它。**重启 N 次 = N 倍的向量存储 + N 倍的 embedding 费用 + 每次检索 top-5 里出现重复 chunk**（既浪费 RAG 那 2300 token，又让「命中数」这个指标失去意义）。只有 `LoadKnowledgeBase`（`service.go:293-303`）走对了流程——它先调 `DeleteKnowledgeBase`。

### 3.4 流式输出：它改变的是「感知延迟」而不是「延迟」

**现状：没有流式。** `grep -rni "stream" pkg/llm/ pkg/rag/ pkg/agent/base.go` → **零命中**。全项目唯一提到 stream 的地方是 `pkg/mcp/http_transport.go:54` 的 `Accept: text/event-stream` 头，那是 MCP 协议的事，与 LLM 无关。`Chat`（`openai.go:61`）和 `ChatWithTools`（`openai.go:99`）都用非流式的 `CreateChatCompletion`，`stage3` 的 HTTP handler 也是一次性返回完整字符串。

**先把一句话说准：流式不减少总耗时，一毫秒都不减。** 它改变的是**用户感知到的延迟**。用户感知的不是「回答什么时候结束」，而是「**我什么时候开始拿到东西**」。

具体数字（量级参考）：本地 7B 模型生成 400 token 的回答，总耗时约 8-20 秒。非流式：用户盯着空白等 15 秒，然后一次性蹦出一整段。流式：**首 token 在 0.5-2 秒出现**，之后每秒 20-60 token 稳定输出。总耗时可能都是 15 秒，但一个像「服务器死了」，一个像「对面有人在打字」。业界对人机对话等待容忍度的共识大致是**首反馈 1-2 秒内**，这就是流式的全部价值。

**Agent 场景下，流式有四个普通聊天机器人没有的难点，这才是这条线要讲深的地方：**

**① 工具调用的增量帧必须缓冲，不能边收边解析。** 流式响应里 `tool_calls` 是**分片增量**到达的：第一个 chunk 可能只有 `delta.tool_calls[0].id` 和 `function.name`，之后每个 chunk 带着 `function.arguments` 的一小段字符串（经常是逐字符或几个字符）。**`arguments` 拼起来之前它不是合法 JSON**，`json.Unmarshal` 必然失败。更麻烦的是多个工具调用会交错分片——必须按 `index` 字段把每个工具调用的 `arguments` 各自累积，等收到 `finish_reason == "tool_calls"` 才能解析。对照非流式实现：`openai.go:116-127` 直接拿完整的 `tc.Function.Arguments` 去 unmarshal；改成流式后这段要重写成一个「按 index 聚合的累加器 + 结束时的批量解析」，**这是流式改造里 80% 的代码量所在**。

**② 用户会看到半句话然后卡住，UI 必须为这个状态设计。** 模型在决定调工具之前，经常已经吐了一些文本（「让我帮你查一下成都的天气……」）。流式下这些字**已经到用户屏幕上了**，然后流停住、工具执行 1-3 秒、再继续。如果前端没有「工具执行中」的提示，用户看到的是一句话卡在半截，比什么都不显示更让人怀疑。所以流式 Agent 的正确形态是：文本流 + 显式状态机（`thinking` / `tool_calling:get_weather` / `generating` / `done`），工具执行期间前端要切到「正在查询天气」这类具体状态。

**③ 中间轮次的文本不该原样给用户看。** 这是 Agent 流式里最容易被忽略的设计题。ReAct 循环（`base.go:296-384`）里第 1 到第 N-1 轮的 `Content` 是模型的**思考旁白**（「我需要先查天气」「现在我有天气了，让我算一下年龄」），只有最后一轮的 Content 才是面向用户的答案。流式把每一轮的 Content 都推给用户，回答会充满「内部独白」。三种处理：只流最后一轮（用户又等太久）、流全部但把中间轮次折进可展开的「执行轨迹」面板（业界主流）、或要求模型把旁白放进特定标记里由前端按标记分流。

**④ SSE 带来的工程债要提前说。** 换成 `text/event-stream` 之后：连接要设 keep-alive（中间网关有空闲超时，通常 30-60s，长生成可能撞上）；要处理客户端主动断开——**断连时必须取消上游的 LLM 请求**，否则你还在付钱生成一段没人看的内容，而这正是 `context` 该起作用的地方，可这个项目的调用链传的是 `context.Background()`（`cmd/stage1/main.go:186`），**断连根本传不到模型层**；`http.ResponseWriter` 要每帧 `Flush()`（Go 里要判断是否实现了 `http.Flusher`，因为某些 `ResponseWriter` 不实现）。

**一个连带的观测性问题：** 改成流式后，「一次请求的耗时」这个指标要拆成 **TTFT（首 token 时间）** 和 **总时长** 两个。而现在的 `metrics.ChatDurationSeconds`（`cmd/stage3/main.go:301`）用 `prometheus.DefBuckets`（0.005s 起、10s 封顶），**一次 15 秒的 LLM 生成全部落进最后一个桶，P50 和 P99 无法分辨**——即使有了流式，这个分桶也观察不出任何东西。LLM 场景的桶应该是 `[0.1, 0.3, 0.5, 1, 2, 5, 10, 30, 60]` 这一量级。

**怎么补（Go 侧最小路径）：** go-openai 有 `CreateChatCompletionStream`，返回 `*ChatCompletionStream`，循环 `Recv()` 拿 `ChatCompletionStreamResponse`，累积 `delta.content` 和按 index 聚合的 `delta.tool_calls`。上层需要把 `Chat` 系列改成返回 channel 或接收 `func(chunk) error` 回调——**这是接口层的破坏性改动**（`client.go:40-52` 的签名要动），所以要新加方法（`ChatStream`）而不是改旧方法。

### 3.5 结构化输出的可靠性阶梯

当你要的不是「一段话」而是「一个能被程序消费的结构」时，可靠性从低到高有五个台阶。这个项目停在第 3 级，而且**第 3 级本身还漏了两个关键件**。五级阶梯：**① 纯 prompt 约束**（「请以 JSON 格式返回」）——什么也不保证，模型可能用 json 围栏代码块包起来、加解释文字、换掉字段名；**② JSON mode**（`response_format={"type":"json_object"}`）——保证**语法**合法（一定能 parse），不保证 **schema**（字段名可能错、类型可能错、必填可能缺）；**③ Function Calling**——用 tools 定义结构，保证能解析成参数对象、结构由你的 JSON Schema 定义，但模型仍可能不调用、漏必填、`arguments` 是坏 JSON；**④ 严格 schema**（Structured Outputs / `strict: true`）——服务端约束解码，schema 级别保证（字段、类型、必填、枚举），代价是供应商支持度不一、要求 `additionalProperties:false` + 全部字段 required；**⑤ 校验兜底**——你的业务规则，需要自己写。

**这个项目在第 3 级：** `ChatWithTools` 把 `tools` 数组传给模型（`openai.go:87-97` 转换、`openai.go:102` 发送），工具定义由 `tool.Manager.GetToolDefinitions()` 生成（`manager.go:75-105`）。这是**正确的选择**——用工具调用做结构化输出，比让模型「输出 JSON」可靠得多，而且天然适配 Agent 循环。**但有两个致命的衰减：**

**① `Required` 被丢掉了，模型根本不知道哪些参数必填。**

```go
// pkg/tool/manager.go:82-98 —— 生成的 schema 只有 type 和 description
params[name] = map[string]interface{}{"type": param.Type, "description": param.Description}
//                                                                  ↑ param.Required 没写进去
```

生成的 schema 里有 `type: "object"` 和 `properties`，**唯独没有 `required` 数组**。所以 `Required: true`（`pkg/tool/tool.go` 的 `ParameterDef` 里定义了）**只是装饰，从来没有到达模型**。MCP 侧是同一个问题的另一份实现：`pkg/mcp/adapter.go:36-57` 解析 `InputSchema` 时只取 `properties`，**同样丢掉 `required`**。而 MCP server 那边明明声明得好好的——`mcp-servers/parenting/main.go:150` 里 `"required": []string{"city"}`。**信息在两跳之后被丢干净了。** 后果链：模型不知道 `city` 必填 → 可能只传 `{"days": 2}` → 工具内部断言 `args["city"].(string)` 失败 → 返回「缺少参数 city」→ 模型再试一次（多花一轮的时间和 token）。**这不是模型不行，是 schema 里没告诉它。**

**② `arguments` 的解析错误被静默吞掉。**

```go
// pkg/llm/openai.go:118-126
args := make(map[string]interface{})
if tc.Function.Arguments != "" {
	json.Unmarshal([]byte(tc.Function.Arguments), &args)   // ← 返回的 error 被忽略
}
```

模型给了语法错的 `arguments`（在参数里带引号或换行时确实会），`args` 保持空 map，**你静默地当成「无参数调用」继续往下走**。用户看到的是工具报「缺少参数」，真实原因是「模型输出的 JSON 坏了」。**根因被埋了两层。**

**还缺的两件：** `tool_choice`（无法强制「这一步必须调 `get_weather`」，只能靠 prompt 里写「你必须调用工具」，`skill_enhancer.go:73`）和 `strict: true` / `additionalProperties: false`（没法启用服务端强 schema 校验）。

**第 5 级该怎么写（项目完全没有）：** 校验兜底不是「解析失败就报错」，而是「解析失败就带着错误信息重试一次」——把「你返回的 arguments 不是合法 JSON，原始串是 X，schema 是 Y，请重新输出」作为一条消息回喂（`base.go:359-368` 已经在用这个模式，只是用在了工具执行错误上，没用在校验上），最多重试 1 次，第 2 次失败才向上抛错。**「失败可自愈」和「失败静默吞掉」的区别，就在这一步。**

### 4.2 切片：这个项目做对了什么

**这是全项目最值得讲的一处细节，因为它不显眼，但没有它整个中文 RAG 就是废的。**

**① 用 rune 计数，不是字节计数。** `splitter.go:58` 和 `splitter.go:169` 都是 `utf8.RuneCountInString(para)` —— 所以 `chunkSize=500`（`service.go:29` / `stage1.yml:59`）是 **500 个字符**，不是 500 字节。**为什么这是大是大非：** Go 的 `len(s)` 返回**字节长度**，UTF-8 下一个汉字占 **3 字节**。如果用 `len()`：**（a）** 同样「500」的 chunkSize，中文只能装 166 个字、英文能装 500 个字符——中文文档被切成三倍多的碎片，每片的上下文都不完整，检索命中率直接下降；**（b）更严重的是会切出非法 UTF-8**——按字节 `s[:500]` 切片时切片点落在汉字中间字节上，得到半个汉字，送进 tokenizer 变成替换字符（U+FFFD），向量和原文语义断裂；存进 Milvus 再取出来 `content` 就是乱码。**这是「检索能跑但结果莫名其妙」的经典成因，而且极难排查，因为它不报错。** overlap 同理：`getOverlapText`（`splitter.go:234-240`）取的是 `[]rune(text)[len-50:]`——rune 切片，所以 50 个字符的 overlap 是完整的 50 个汉字。这一段在面试里的价值是：它证明作者知道「Go 的字符串是字节序列，中文处理必须显式按 rune」——一个只有真写过中文文本处理的人才会踩的坑。

**② 全角句读作为句子边界。** `splitter.go:212-221` 的终止符是 `'。' || '？' || '！' || '.' || '?' || '!'`。**为什么这一行是整个 RAG 的生死线：** 句子级切分是长段落降级的**唯一路径**（`splitter.go:92-97`：段落超过 chunkSize 时调 `splitLongParagraph`）。如果这里只认半角 `.?!`，那么——中文没有空格分词、句末是 `。` 不是 `.`，**一篇中文长段落永远切不开**；结果是一个几千字的「超级 chunk」被原样送进 embedding；embedding 模型的有效上下文有限（`nomic-embed-text` 典型在 512 token 量级），超长文本会被截断或平均化，向量变成一个指向「这段大概讲了什么」的模糊点；检索时它对**所有** query 都算出中等相似度——「什么都沾一点，什么都不准」——阈值过滤也救不了，因为它分数不算低；而且这个 chunk 一旦被召回，会把 2300 token 的上下文预算**一个人吃掉**，把其他真正相关的片段挤出 top-5。**所以这一行不是「优化」，是「让中文长文档能被处理」的必要条件。**（对照：`pkg/skill/manager.go:163-173` 的 `keywordMatch` 用 ASCII 空格/逗号/句点分词，对中文描述完全失效——甚至那 6 个分隔符里有两个是重复的（`','` 和 `'.'` 各写了两次，见 `manager.go:165-167` 的原始字节），像是从全角版本改写时留下的痕迹。**同一个仓库里，一处对中文做对了，另一处对中文完全没做。**）

**③ 边界（主动标注，别被问倒）：** **a.** 半角 `.` 参与句子切分会误杀技术文档——小数 `3.14`、版本号 `v1.2.3`、域名 `example.com`、代码块里的点都会被当句末，把完整句子切成三段（对纯中文育儿文档无害，但知识库里若有 API 文档就会碎得很厉害；修法是加「`.` 后面必须是空白或行尾才算句末」的前视判断）。**b.** 只认句内标点、不认 `、；：` 和换行——这个取舍是对的（顿号分号是次级停顿，当 chunk 边界会切得太碎），但**列表项**（`- 第一条建议……` 每行一条、行尾没有句号）会被 `splitParagraphs`（`splitter.go:133-152`）用 `" "` 合并成一整段，然后因为没有句末符而无法进一步切分。**c.** 最后一级没有兜底——如果**单个句子**本身就超过 chunkSize，`splitLongParagraph` 里 `currentChunk.Reset(); currentChunk.WriteString(sent)`（`splitter.go:188-190`）会把这个超长句原样当成一个 chunk 塞进去（`splitter.go:171` 的长度检查只决定「是否换行」，不决定「是否强制切断」），**缺少「超过 chunkSize 就硬切」的最后一档**。**d.** overlap 是纯字符尾巴截断，会把词从中间劈开——「亲子沟通」可能变成「……亲子沟」+「通技巧……」；这是轻微噪声（有 overlap 仍远好于没有），但可以改成语义边界对齐。

**④ 实测：记账 bug 让 11/20 的 chunk 超过了 chunkSize。** 走查报告指出 `currentLength` 有记账 bug（`splitter.go:84-102`）：长段落分支把 `currentLength = 0`（`:98`）但**没有清空 `currentChunk`**（`currentChunk` 里还留着 overlap 文本）——所以下一个段落被追加时，实际内容 = 残留 overlap + 新段落，而 `currentLength` 只从 0 开始计新段落。**块实际长度大于记录长度。** 我用同一套算法（同样的三级降级 + 同样的 rune 计数 + 同样的记账逻辑）在真实知识库上跑了一遍：

| 文件 | chunk 数 | 最长 | 最短 | 平均 | 超过 500 的 |
|---|---|---|---|---|---|
| child_development.md | 4 | 523 | 395 | 456 | 1 |
| communication_skills.md | 5 | 543 | 256 | 463 | 3 |
| emotion_management.md | 6 | 550 | 177 | 471 | 4 |
| parenting_faq.md | 5 | 543 | 340 | 474 | 3 |
| **合计** | **20** | **550** | **177** | **459** | **11 / 20** |

**20 个 chunk 里 11 个超过 500 字符，最长 550（超 10%）。** 所以「chunkSize=500、overlap=50」这个配置**实际没有生效**——真实分布是 177 到 550，波动接近 3 倍。对 RAG 的实际影响是：**chunk 大小不齐 → 每段的向量「信息密度」不一致 → 相似度分数不可比 → 你精心挑的 0.5/0.6 阈值其实是在给一堆不同尺度的东西设一条线。**

### 4.3 检索：topK=5 + 阈值后置过滤的架构问题

**现状：** `topK = 5`（`service.go:31`、`stage1.yml:62`），检索回来后在应用层过滤：

```go
// pkg/rag/service.go:134（Search）/ :267（SearchWithKB）
if result.Score < s.scoreThreshold { continue }
```

**这个架构问题的本质：后置过滤只能让结果变少、变空，永远不能召回到更好的结果。** 拆开看。`store.Search(ctx, queryVector, s.topK)`（`service.go:122`）已经从 Milvus 拿回**恰好 5 条**、也就是全库最相似的 5 条，然后你在应用层把其中低于阈值的丢掉。这意味着：如果真正相关的那条排在第 7，**你没取到它，阈值再松也拿不到**；阈值的作用被限制在「过滤噪声」，而「提升召回」这件事**被 topK 卡死了**；阈值调高则结果变空、调低则噪声进来——**两条路都不通向「更好的检索」**。

**用数字举例。** 假设某个 query 全库的真实相似度分布是：

```
排名:  1     2     3     4     5     6     7     8
分数: 0.58  0.56  0.55  0.53  0.51  0.50  0.49  0.48
```

topK=5 取回前 5 条（**全部 < 0.6**），阈值 0.6 过滤后返回 0 条。然后 `base.go:264-266` 发现 `len(results) == 0`，直接 `return basePrompt`——**Agent 完全不知道有知识库，凭模型自己的记忆回答**。而第 6、7、8 条（0.50/0.49/0.48）里的内容可能正是答案。（如果分布换成 0.68/0.65/0.61/0.55/0.52，同样取 5 条、同样阈值 0.6，返回的是 3 条——**同一个阈值，一次给出 3 条、一次给出 0 条，决定这件事的是运气**。）

**这里还有一个更隐蔽的问题：0 命中时 `return basePrompt` 是最危险的行为。** 一个「知识库里没有答案」的 query，和「检索没检到但知识库里有答案」的 query，在这个项目里**走的是同一条路**——都变成「让模型裸答」。而 RAG 系统里幻觉最高发的场景恰恰就是知识库里没有、但模型「觉得自己知道」的时候。**至少应该区分这两种情况**：检索返回了结果但全被阈值滤掉（说明模型可能知道一些）vs 检索完全没命中（说明库是空的）。前者应该明确告诉模型「检索到低置信度内容」，后者应该明确告知用户「知识库中没有相关信息」。

**正确做法有两条，推荐第一条：**

**① 把阈值下推到 Milvus 的 `range_filter`（架构上正确）**——在 `entity.NewIndexAUTOINDEXSearchParam(10)` 之上加 `WithRangeFilter(float32(threshold))`，让「相似度 < 阈值」的候选**在索引层就被排除**。这样 topK=5 的含义变成「**最多** 5 条、且全部高于阈值」，检索结果要么有 5 条高质量的，要么少于 5 条，而不是「5 条里可能一条都不合格」。**这是量级区别：从「先取后筛」变成「取的时候就筛」。**

**② 先取 topK × 3 再筛到 topK（最小改动）**——把 `service.go:122` 的 `s.topK` 改成 `s.topK * 3`（取 15 条），过滤后再截断到 5 条。改动是一行数字，代价是 Milvus 多返回 10 条、检索耗时略增（AUTOINDEX 在这个量级下影响很小）。不如方案 ① 干净（还是「先取后筛」，只是取多了），但效果一样且不影响其他调用方。

**另一个隐患：nprobe 写死 10，且和 topK 一样小。** `milvus.go:200`（`Search`）和 `milvus.go:366`（`SearchWithFilter`）都是 `entity.NewIndexAUTOINDEXSearchParam(10)`——nprobe=10 表示「在 10 个簇里搜索」。nprobe 小 + topK 小，召回率有天花板；这个参数在百万级向量上是重要的性能/召回权衡旋钮，**应该配置化**。

**还有一处阈值不一致，且没有数据支撑：** `stage1.yml:63` 是 `0.6`，`stage3.yml:78`（以及 stage2）是 `0.5`。同一个知识库、同一个模型、同一个切片配置，两个阈值。走查报告的原话是「不一致且无数据支撑」——追问「为什么是 0.6」时，除了「调出来的」没有别的答案，而**正确回答需要的是评估集（见 4.5）**。

**最后，一个必须说清的诚实话（最能体现你真懂）：** 「在只有 20 个 chunk 的规模下，topK=5 意味着**每次检索取出全库的 25%**。所以现在这个 RAG 里，『检索』实际上几乎不起筛选作用——它更接近『从 20 段里挑 5 段最像的』，而 5 段加起来 2300 token，已经占满了上下文预算。**这个规模下调 topK 和阈值没有任何统计意义，真正的杠杆在文档质量和切片质量上。**」面试官听到这句话会知道：这个人不是照着教程搭了 RAG，是真的看过数据。

### 4.4 引用：为什么这个项目零 citation

**现状：`base.go:273-283` 的上下文组装只拼正文。**

```go
// pkg/agent/base.go:271-282
var contextBuilder string
for i, result := range results {
	if i > 0 { contextBuilder += "\n\n" }
	contextBuilder += result.Content            // ← 只有正文
	clog.Debug("[RAG]", "Doc %d (score: %.2f): %s", i+1, result.Score, truncate(result.Content, 100))
}
return basePrompt + "\n\n以下是与用户问题相关的知识库内容，请参考这些内容回答问题：\n\n" + contextBuilder
```

**没有编号、没有来源、没有分数。** 模型看到的是 5 段无署名的文字，无法说「根据《亲子沟通技巧》第 3 节」，只能把这 5 段嚼碎了用自己的话讲出来——**用户无法验证任何一句话是不是真的来自知识库。**

**最讽刺的一点：`Source` 明明取到了，然后在组装时被丢弃。** `SearchResultItem` 有三个字段 `Content` / `Source` / `Score`（`service.go:100-104`），`Source` 在 `service.go:145-147` 从 metadata 里被正确解析出来，`base.go:278` 的 Debug 日志里甚至还用了它——但 `base.go:277` 那一行只拼了 `result.Content`。**数据一路送到了 `for` 循环里，在最后一句被扔了。** `Score` 也在同一位置被扔（只在 `:278` 的调试日志里出现）。

**死代码：项目其实写好了带引用的 prompt，但没有任何调用点。** `service.go:165-201` 的 `RetrieveAndGenerate` 里有 `fmt.Sprintf("[%d] %s\n", i+1, result.Content)`（`service.go:180`）——完整的编号 `[1] [2] [3]`、上下文头「以下是相关知识库内容」（`service.go:178`）、以及「基于以下知识库内容回答问题。如果知识库中没有相关信息，请如实说明」（`service.go:184`）这个**明确的反幻觉指令**。`grep -rn "RetrieveAndGenerate"` 的结果是**只有定义在 `service.go:165`，全项目零调用点**。所以 Agent 实际走的路径（`base.go` 的 `buildSystemPromptWithRAGBase`）用的是**另一套更简陋的**拼装逻辑，而这套写好的引用模板从没被执行过。

**零 citation 的三个后果：** **① 可信度价值丢掉一半**——RAG 相对于「直接问模型」的核心优势除了准确性还有**可验证性**，用户能点开来源才会信任答案；没有引用，RAG 和微调后的模型在体验上没有区别。**② 幻觉无法归因**——回答错了，你不知道是「检索错了（该有的没检到）」还是「检索对了但模型编了」，而**这两种故障的修法完全不同**（前者改切片/检索，后者改 prompt 或换模型），排查成本从一个日志查询变成一轮完整实验；这是**运维成本**，不是「nice to have」。**③ 合规场景直接不可用**——教育、医疗、金融场景里「答案必须能追溯到出处」是硬要求（这个项目的知识库是亲子教育，`stage1.yml:22` 自己都写了「对于健康问题，明确说明仅供参考」，而**一句免责声明的可信度远不如一个能点开的来源**）。

**还有一个前置缺陷让引用即使加上也不完整：`source` 只是文件名。** `service.go:382` 和 `service.go:471` 都是 `source := filepath.Base(filePath)`——**只有文件名，没有路径**。所以两个不同目录下的同名文件（`docs/v1/faq.md` 和 `docs/v2/faq.md`）会撞成一个 source；用户看到「来源：child_development.md」**翻不到具体是哪一段**；`Chunk.Index` 是有的（`splitter.go:74`）而且被写进了 metadata（`service.go:85`、`service.go:232`），但**从来没有被读出来用过**（`Search` 只解析 `content` 和 `source`，`service.go:142-147`）——「第几段」这个信息在存储里有、在检索结果里丢了。

**怎么补（工作量其实很小，但要讲清代价）：** 第一步改 3 行——`base.go:273-283` 的拼装改成 `contextBuilder += fmt.Sprintf("[%d] (来源: %s, 相关度: %.2f)\n%s", i+1, result.Source, result.Score, result.Content)`；第二步 system prompt 加约束「回答时用 `[编号]` 标注信息来源；如果资料中没有相关信息，明确说明，不要凭记忆补充」；第三步 API 返回体加 `citations` 数组（`{index, source, score, snippet}`），让前端渲染成可点击的来源卡片。**真正的工作量在第三步之后：** （a）校验模型引用的编号必须落在 `1..len(results)` 范围内——模型会引用不存在的 `[6]`，这是必须挡住的；（b）前端要展示来源卡片，涉及 UI 设计；（c）要跳到原文具体位置，metadata 里得存 `file_path + start_offset + end_offset`，**而 splitter 现在只输出 `Index`、不输出字符偏移**（`splitter.go:33-38` 的 `Chunk` 结构体里没有 offset 字段）——这是一个需要改 splitter 接口的改动，也是「引用」从「能看」到「能跳」的门槛所在。

### 4.5 评估：完全没有

**现状：零。** ① **没有 golden set**——`grep -rn` 全项目找不到任何 (query, 期望结果) 的标注数据；② **没有指标**——没有 Recall@k、MRR、NDCG、Context Precision/Recall、A/B 框架；③ **唯一的「评估手段」是两行日志**——`service.go:127` 的 `log.Info("[RAG]", "Raw search returned %d results (threshold: %.2f)")` 和 `service.go:160` 的 `log.Info("[RAG]", "Final filtered results: %d items")`。这两行告诉你「检索返回了几条」，**不告诉你「返回的对不对」**——而条数和质量零相关（4.3 的例子里，返回 0 条和返回 3 条都可能是对的，也可能是错的）。此外 **Rerank 没有**（全项目 grep 零命中），意味着链路里少了一个「用更贵的模型精排 top-20 到 top-3」的召回率提升点；**混合检索（BM25 / 稀疏向量）也没有**（零命中），而纯稠密向量对**专有名词、人名、数字、精确短语**天然弱——用户问「3 岁孩子的语言发展」，稠密向量可能召回一堆讲「幼儿沟通」的段落，真正讲「语言里程碑」的那段因为用词不同被排在后面。

**但比「没做」更重要的是：在这个数据规模上做评估也没有意义。** 知识库是 **4 篇 markdown、20554 字节、9181 个字符、20 个 chunk**（实测，见 4.2 的表）。在 20 个 chunk 上算 Recall@5：分母最大 20、分子最多 5，**任何参数改动带来的指标波动都在噪声范围内**；每个 query 的「正确 chunk」通常只有 1-2 个，标注 30 个 query 只能覆盖 20 个 chunk 的一部分，统计置信度极低；更根本的是 **20 个 chunk 里的 5 个已经占了 25%**，「检索」在这规模下不是筛选，是近似全量投喂（见 4.3 末）。

**所以正确的面试答法是分层的——先承认规模，再讲方法：** 「现在这个知识库只有 20 个 chunk，在这个量级上算 Recall@5 没有统计意义——所以我先做的是**把规模涨上去**，同时把重复索引这个问题修掉（`service.go:350-392` 每次启动重复追加，会让同一个 chunk 在库里有 N 份拷贝，直接污染所有检索指标）。有了 500+ chunk 之后，评估分三层：**第一层，建 golden set**——30-50 个 `(query, 期望命中的 chunk id)` 对，按「知识库有答案」和「知识库没有答案」**两类**分别标，后一类是幻觉高发区，最该测的就是「库里没有时它会不会瞎编」，而现在的实现是把这种情况变成裸答（`base.go:264-266`）。**第二层，算三个指标**——Hit Rate@5（前 5 里有没有期望 chunk）、MRR（第一个正确结果排第几）、Context Precision（送进 prompt 的 5 段里有几段是相关的，**这个直接决定那 2300 token 花得值不值**）。**第三层，归因指标**——检索耗时 P50/P99、平均 score、**被阈值干掉了多少条**（这个数字直接告诉你阈值是不是定错了）、embedding 调用耗时；没有这一层，前面两层只能告诉你「变差了」，不能告诉你「为什么差」。最后是把评估接进 CI：golden set 跑一次成本很低（30 个 query × 20 个 chunk，纯检索不调生成），每次改切片参数或换 embedding 模型都跑一遍，**指标掉了就拦住合并**。」这段回答同时展示三件事：知道当前规模的真实局限、知道评估的完整方法、知道「先修数据质量问题再谈指标」——**这是 4.5 唯一需要背下来的东西。**

## 六、面试要点（12 个高频问题）

### Q1：你怎么控制大模型调用的成本？

**骨架：** ① **先量再说**——输入/输出/缓存命中/调用次数四个数分开统计（`pkg/log/log.go:346` 的 `LLMResponse(model, tokens)` 是死代码，而 SDK 返回的 `Usage` 就在 `openai.go:130-133` 被丢掉）；② **输入是主战场**——一次 5 轮 Agent 对话输入约 16,000 token、输出约 400，**输入:输出 ≈ 40:1**，因为每轮都要重发全部上下文（`base.go:306-308, 316` 每轮重建消息和工具定义）；③ **前缀缓存**——system + RAG + 工具定义在循环里逐字节不变，命中能省 50%（OpenAI 口径）到 90%（Anthropic/DeepSeek 口径）的输入成本，**但前缀必须逐字节一致，所以不能在 system prompt 里插时间戳**；④ **历史压缩**——`maxSize=50`（`base.go:51`）满了直接丢最旧一条（`conversation.go:91-93`），没有任何摘要，而 `InteractionTypeSummary`（`conversation.go:16`）定义了却从没被产生过；⑤ **模型分级路由**——Skill 匹配/摘要用小模型，主对话用大模型（`gateway.go:60-65` 的能力已有，配置里 `modelRef: ""` 是空的）；⑥ **预算熔断**——单次/单用户日/全局日三层，**注意 QPS 限流不等于成本熔断**（`ratelimit.go` 挡不住「低频但超长上下文」）。

### Q2：你们线上超时怎么设的？LLM 挂了会怎样？

**骨架：** ① **分四层**：连接 1-3s、单次 LLM 60-120s、单次工具 5-30s、整体请求 120-300s；② **整体预算必须显式设置且向下分配**，不能「单次 60s × 循环 10 轮 = 最坏 600s」，Go 里子 deadline 超过父 deadline 时以父为准，所以入口设总预算、逐层传递是安全的；③ **流式不能用 `http.Client.Timeout`**（它计的是全程，会切断正常的长生成），要改用 `Transport.ResponseHeaderTimeout` + per-call ctx；④ 这个项目**全层无超时**：`openai.go:29-35` 没设 `HTTPClient`（零值 `http.Client`，Timeout=0），`openai.go:42` 的 embedding 客户端更直白，`grep "Timeout" pkg/llm/` **零命中**，调用方传 `context.Background()`（`cmd/stage1/main.go:186`）——**唯一存在的超时是连 Milvus 的 10 秒**（`milvus.go:37`）；⑤ 结构性问题：`tool.Tool.Execute` 签名里根本没有 `ctx`（`pkg/tool/tool.go:4-16`），**工具超时在类型层面就不可能实现**。

### Q3：什么错该重试、什么不该？重试会不会让问题更糟？

**骨架：** ① **按状态码分类**：429 和 5xx 重试（429 先看 `Retry-After`，退避基数要比 5xx 大）；400/401/403/404/422 一律不重试（请求或配置有问题，重试只是 3 倍延迟 + 3 倍日志噪音）；② **必须加抖动**（`delay = min(max, base × 2^n) × rand(0.5,1.0)`），否则多副本同时重试形成惊群，把限流打成持续过载；③ **重试要算在超时预算内**，否则「重试 3 次 × 60s」给用户造出 3 分钟的新问题；④ **重试在计费上不幂等**——第一次可能已经生成了一半才断，重试就是付两次钱；⑤ **重试应该写在网关层而不是 LLM 客户端**，因为只有网关知道备用模型是谁——`LLMGateway`（`gateway.go:15-20`）已有全部路由基础设施，只差健康度策略；⑥ 现状：**零重试**（`grep -rni "retry\|backoff\|429" pkg/llm/ pkg/rag/` 零命中），一次 429 直接把错误抛给用户（`openai.go:104-106` → `base.go:320-322`）；⑦ 对照：**工具执行失败不该重试，该回喂模型让它自愈**——这一点项目做对了（`base.go:359-368`）。

### Q4：为什么用 Function Calling 而不是让模型输出 JSON？

**骨架：** ① **可靠性阶梯**：prompt 约束 < JSON mode（保证语法，不保证 schema）< Function Calling（结构由你的 schema 定义）< 严格 schema（服务端约束解码）< 校验兜底；② Function Calling 的实质是**把「输出格式」从自然语言约束变成参数契约**，模型在训练时就对齐过这个行为，比「请返回 JSON」可靠一个量级；③ **但 schema 必须完整**——这个项目把 `required` 丢了两遍：`pkg/tool/manager.go:82-98` 只写 `type`/`description`，`pkg/mcp/adapter.go:36-57` 只解析 `properties`，而 MCP server 明明声明了 `"required": ["city"]`（`mcp-servers/parenting/main.go:150`），**信息在两跳后被丢干净**；④ **解析错误不能吞**——`openai.go:118-126` 丢掉了 `json.Unmarshal` 的 error，坏 JSON 被静默当成「无参数调用」，根因被埋两层；⑤ **还缺 `tool_choice`**（无法强制「必须先调某个工具」，只能靠 prompt 里写「你必须调用」，`skill_enhancer.go:73`）；⑥ 校验兜底应该是**带着错误信息重试一次**，而不是直接报错——「失败可自愈」和「失败静默吞掉」的区别就在这一步。

### Q5：中文文档切片要注意什么？

**骨架：** ① **必须按 rune 计数，不能按字节**——`utf8.RuneCountInString`（`splitter.go:58, 169`），这个项目做对了；如果用 `len()`，中文 3 字节/字 → 同样 500 的 chunkSize 中文只能装 166 字（英文的 1/3），**而且按字节切片会把汉字切成两半产生非法 UTF-8** → tokenizer 变成替换字符 → 向量语义断裂 + Milvus 里存的是乱码；② **句子边界必须包含全角标点**——`。？！`（`splitter.go:214`），这是全项目唯一针对中文的专门处理；如果只认 `.?!`，**中文长段落永远切不开**，退化成几千字的超级 chunk → 超过 embedding 有效窗口 → 向量被平均化 → 对所有 query 都中等相似 → 检索准确率崩；③ **overlap 也要按 rune 取**（`splitter.go:234-240` 取 `[]rune` 尾部 50 个）；④ 边界：半角 `.` 会误杀小数/版本号/URL（技术文档要加前视判断）、无标点的列表项切不开、**单个超长句没有硬切兜底**（`splitter.go:188-190` 原样塞进去）；⑤ 实测数据：20 个 chunk 里 11 个超过 500、最长 550——`currentLength` 记账 bug（`splitter.go:84-102` 长段落分支把长度归零但没清空 `currentChunk`）让 chunkSize 实际没生效。

### Q6：RAG 检索不准怎么排查？你怎么知道检索变好了？

**骨架：** ① **先分层定位，别急着调参数**——「没检到」是召回问题（切片太碎/embedding 不适配/纯稠密向量对专有名词弱），「检到了但排在后面」是排序问题（该加 rerank），「检到了但答错」是生成问题（prompt 或模型）；② **召回层**：看 chunk 大小是否均匀、overlap 是否生效、有没有重复索引（`service.go:350-392` 每次启动重复追加，同一 chunk 有 N 份拷贝 → top-5 里可能出现 3 个一样的结果）；③ **排序层**：加 rerank，或用混合检索（BM25 + 向量）补稠密向量对精确词项的短板；④ **评估**：建 30-50 对 golden set，**按「库里有答案/没有答案」两类分开标**（后一类测幻觉），算 Hit Rate@5 / MRR / Context Precision；⑤ **归因指标**：检索耗时、平均 score、**被阈值干掉了多少条**；⑥ 诚实的规模判断：项目只有 20 个 chunk（实测），**topK=5 等于每次取出全库 25%，在这个量级上评估没有统计意义**——先修数据质量问题（重复索引）并把量做上去，再接评估进 CI。

### Q7：topK 和相似度阈值怎么定的？

**骨架：** ① **阈值应该在检索里生效，不是检索后**——这个项目是 `topK=5` 取回来再过滤（`service.go:134, 267`），**后置过滤只能让结果变空，不能提升召回**：真正相关的那条排在第 7 就永远拿不到；② 正确做法两条：把阈值下推成 Milvus 的 `range_filter`（架构上正确，「取的时候就筛」），或者先取 `topK × 3` 再筛到 5（最小改动，一行数字）；③ **数值必须有数据支撑**——stage1 是 0.6（`stage1.yml:63`）、stage2/3 是 0.5（`stage3.yml:78`），同一个库同一个模型两个阈值，追问「为什么是 0.6」只能答「调出来的」；④ **0 命中时的行为最危险**：`base.go:264-266` 直接 `return basePrompt`——「库里有答案但没检到」和「库里没有答案」走同一条路，都变成让模型裸答，**这正是幻觉最高发的场景**；⑤ 别忘 nprobe 这个旋钮（`milvus.go:200, 366` 写死 10），它和 topK 一起决定召回天花板，应该配置化。

### Q8：为什么流式输出这么重要？Agent 场景下流式的难点是什么？

**骨架：** ① **流式一毫秒都不减少总耗时，它改变的是感知延迟**——用户感知的是「什么时候开始拿到东西」：非流式干等 15 秒后一次吐出 vs 流式 1 秒出首字、15 秒吐完；业内对人机对话的首反馈容忍度大致是 1-2 秒；② **难点一：工具调用的增量帧必须缓冲**——`tool_calls` 是分片到达的，`function.arguments` 是逐字符拼的，**拼完之前不是合法 JSON**，而且多个工具调用会交错分片，必须按 `index` 分别聚合到 `finish_reason == "tool_calls"` 才能解析（对照 `openai.go:116-127` 的非流式实现，这段要整个重写）；③ **难点二：用户会看到半句话然后卡住**——模型决定调工具前常已吐出一些文字，前端必须有显式的状态机（thinking / tool_calling / generating）；④ **难点三：中间轮次的文本不该给用户看**——ReAct 里第 1..N-1 轮的 Content 是模型的思考旁白，主流做法是折进可展开的「执行轨迹」；⑤ **难点四：SSE 的工程债**——keep-alive、客户端断连必须取消上游请求（`cmd/stage1/main.go:186` 传的是 `context.Background()`，**断连根本传不到模型层，你还在付钱生成没人看的内容**）、每帧 `Flush()`；⑥ 连带的观测问题：指标要拆成 TTFT 和总时长，而现在的 `ChatDurationSeconds` 用 `DefBuckets`（10s 封顶），**15 秒的生成全落最后一个桶，P50/P99 分不出来**（`cmd/stage3/main.go:301`）。

### Q9：你们为什么不直接用官方 SDK？

**骨架：** ① 这个项目**同时用了两种**：Chat 走 go-openai SDK（`openai.go:29-35, 61`），**Embedding 手写 HTTP**（`openai.go:154-236`）——这是一个有意的取舍，不是「不会用 SDK」；② **手写的理由**：Embedding 端点各家差异最大（`data[].index` 顺序不保证、`usage` 字段名不一），手写后只依赖最小契约（`data[].embedding` + `error.message`，`openai.go:143-152`）；`Input` 声明成 `any`（`openai.go:138`）所以一个结构体既能发 string 也能发数组；模型名完全自由（`nomic-embed-text`）；③ **手写的代价（必须主动说）**：SDK 免费提供的保障全丢了——`openai.go:206-228` **完全不检查 `resp.StatusCode`**，401 会以「解析响应失败: invalid character '<'」的形式暴露，排查认证问题从 5 秒变成 30 分钟；④ 结论：**兼容性诉求用手写，但手写必须自己把 SDK 替你做的事做完**（状态码分支、错误体解析、`Retry-After` 读取）；⑤ 边界：如果只用 OpenAI 官方 + 官方模型，手写零收益、纯增维护面——这个取舍的前提是「多供应商兼容」，而项目要支持 Ollama 本地模型，前提成立。

### Q10：多模型路由和降级你怎么做的？

**骨架：** ① 现状：**基础设施齐了，配置是空的**——`LLMGateway` 有 `sync.Map` 客户端缓存（`gateway.go:17`）、构造时预创建（`gateway.go:31-35`）、按 `modelRef` 路由（`gateway.go:47-57`）、实现 `Client` 接口可直接传给 Agent（`gateway.go:98-118`），但 `stage3.yml:18` 的 `modelRef: ""`、`stage1.yml:37-43` 连 `models` 段都没有 → **永远走默认客户端**；② **未知 ref 静默回落**是隐患（`gateway.go:56`）——配置写错了不报错，只是静默用错模型，应该启动时校验所有 `AgentConfig.ModelRef` 都能解析；③ **分级路由的正确形态**：Skill 匹配（`pkg/skill/manager.go:190-198` 每条消息一次 LLM 调用的纯分类任务）用 1.5b、摘要压缩用 1.5b、主对话用 7b、复杂推理升级到 14b 或云端；④ **降级的正确形态**：主模型连续 429/5xx → 切备用模型；**降级必须记录并可观测**，否则「用户悄悄拿到一个更差的模型」没人知道；⑤ 降级要考虑**质量断层**：小模型可能不遵守工具调用格式，降级后要放宽解析（或对结构化任务不降级）——这是降级策略里最容易被忽略的一条。

### Q11：你的 RAG 为什么没有引用？怎么加？

**骨架：** ① 现状：**零 citation**——`base.go:273-283` 只拼 `Content`，`SearchResultItem.Source` 在 `service.go:145-147` 明明解析出来了、在 `base.go:278` 的调试日志里还用了，**但在拼上下文那一行被丢掉**，`Score` 同样；② **死代码**：`service.go:165-201` 的 `RetrieveAndGenerate` 有完整的 `[1] [2]` 编号模板（`service.go:180`）和反幻觉指令（`service.go:184`），**全项目零调用点**——Agent 走的是 `base.go` 那条更简陋的路径；③ **三个后果**：可信度（用户无法验证）、可归因性（回答错了分不清是检索错还是模型编）、合规（教育/医疗/金融硬要求，而这个项目的知识库正好是亲子教育，涉及健康建议时 `stage1.yml:22` 自己都写了「仅供参考」）；④ **怎么加**：组装带编号+来源+分数（3 行改动）、system prompt 加引用约束、API 返回 `citations` 数组；⑤ **真正的工作量在后面**：校验模型引用的编号在 `1..len(results)` 内（模型会引 `[6]`）、前端来源卡片 UI、**要跳到原文位置得让 splitter 输出 offset**（现在 `Chunk` 只有 `ID/Content/Source/Index`，`splitter.go:33-38`，而且 `Index` 存了 metadata 也从没被读出来用，`service.go:142-147`）；⑥ **前置缺陷**：`source` 只是 `filepath.Base`（`service.go:382`），同名文件会撞，引用粒度只能到文件不能到段。

### Q12：一次 Agent 调用大概多少 token？怎么算的？

**骨架：** ① **基准**：中文大致 **1 字 ≈ 1 token**（BPE 词表上 0.6-1.5，工程估算取 1）；英文 **1 token ≈ 4 字符 ≈ 0.75 词**（OpenAI 官方口径）；**混排必须实测**，不能按字符数推；② **输入构成**（这个项目）：system ~200（`stage1.yml:11-23`）+ **RAG 上下文 ~2300**（topK=5 × 实测平均 459 字）+ 工具定义 ~250（2 内置 + 2 MCP）+ 历史 0→5000（`maxSize=50`，`base.go:51`）；③ **关键机制：ReAct 每轮重发全量上下文**（`base.go:306-308` 重建消息、`base.go:316` 重建工具定义），没有增量；④ **算例**：5 轮对话累计输入 **≈16,000 token**、输出 ≈400 → **输入:输出 ≈ 40:1**；⑤ 结论：**输入是主战场**，所有优化精力压在输入侧；⑥ 现状：**零 token 统计**——`pkg/log/log.go:346` 的 `LLMResponse(model, tokens)` 是死代码，SDK 返回的 `Usage` 在 `openai.go:130-133` 被丢弃，`pkg/metrics` 里没有任何 LLM 指标；⑦ 补的第一步是**把 `Usage` 接出来**（改动 3 行），第二步是分 `input/output/cached/calls` 四个数打点。

---

## 收尾：这条线的三句话

1. **最诚实的自我描述**：一个把 LLM 接进来了、分层做对了、OpenAI 兼容协议打通了（本地 Ollama 和云端同一套代码）的教学实现，**但没有任何一层治理**——无超时、无重试、无流式、无 token 统计、无结构化校验兜底、无评估；`temperature`/`maxTokens` 配了不传，`agent.modelRef` 路由能力写了不用，`LLMResponse` 埋点写了不调。
2. **真正的亮点有三个，都能讲出「为什么」**：① **embedding 手写 HTTP** 而不是用 SDK——为了兼容任意模型名和最小契约，代价是要自己补状态码检查；② **中文切片按 `utf8.RuneCountInString` + 全角句读 `。？！`**——全项目唯一针对中文的专门处理，没有它整个中文 RAG 是废的；③ **`LLMGateway` 的分层**——接口/实现/路由三层干净，网关能直接当客户端用，多模型路由和降级只差最后一层策略。
3. **最容易被问倒的三处**：① 「你的超时设在哪」→ 全层无超时，`tool.Execute` 连 `ctx` 参数都没有，**要补的第一件事是改接口签名**；② 「你怎么知道检索变好了」→ 只有两行日志，20 个 chunk 的规模做评估没有统计意义，**要补的第一件事是修重复索引、把量做上去，再建 golden set**；③ 「token 花在哪」→ 零统计，而 `Usage` 就在手边被丢掉，**要补的第一件事是接出 `Usage` 分四个数打点**。

**一句话记住这条线**：*接进来是半天的工作，管起来是这个项目缺失的全部工作。*
