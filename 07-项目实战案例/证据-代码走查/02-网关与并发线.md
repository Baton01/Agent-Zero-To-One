### 注意：注释与实现不符

`gateway.go:59` 注释写"认证→限流→安全"，但 `GetOrder()` 实际是 **Auth 10 / Security 20 / RateLimit 30**（`auth.go:38-40`、`security.go:57-59`、`ratelimit.go:36-38`）。`distributed.go:70` 注释同样错。

## 二、限流（重点）

### 事实

- **算法**：本地是**令牌桶**（`ratelimit.go:74-127`），分布式是**固定窗口**（`distributed.go:189-198` INCR+EXPIRE）。**两套并存**。
- **限流 key**：本地全局桶（一个实例，`:26-28`）；本地用户桶用 `ctx.UserID`，而 UserID 来自 `apiKey → "default-user"` 的**写死映射**（`main.go:257`）。
- **参数**：`stage3.yml:96-98` → `globalQps: 1000`、`userQps: 10`。桶容量 = 速率（`NewTokenBucketLimiter(globalQPS, globalQPS)`，`:27`），即允许 1 秒突发。

```go
// pkg/gateway/ratelimit.go:95-127
func (l *TokenBucketLimiter) TryAcquire() bool {
	l.refill()                      // 每个请求都进 mutex
	for {
		current := l.tokens.Load()
		if current <= 0 { return false }
		if l.tokens.CompareAndSwap(current, current-1) { return true }
	}
}
func (l *TokenBucketLimiter) refill() {
	l.mu.Lock(); defer l.mu.Unlock()          // ← 全局串行点
	now := time.Now().UnixMilli(); last := l.lastRefill.Load()
	elapsed := now - last
	if elapsed >= 1000 {                       // 整秒量化
		newTokens := (elapsed / 1000) * l.refillRate
		current := l.tokens.Load()
		newCount := current + newTokens
		if newCount > l.capacity { newCount = l.capacity }
		l.tokens.Store(newCount)               // ← 非 CAS 的裸 Store
		l.lastRefill.Store(now)
	}
}
```

### 关键缺陷

**① 每个请求都进全局 mutex**

`refill()` 每次 `TryAcquire` 都 `Lock`，**即使不需要补充**（`:96,111`）。1000 QPS = 1000 次全局互斥/秒。正确做法：只走 atomic/CAS（`lastRefill` 用 CAS 抢，抢到的那个才补令牌），或用 `golang.org/x/time/rate`，或**按用户哈希分片**成 N 个桶降低竞争。

**② lost update 竞态**

`refill` 里 `Load()` → `Store()` 之间没有 CAS → 并发 `TryAcquire` 的 CAS 扣减会被 `Store` 覆盖回去（**多退令牌 = 超发**）。混用 atomic 和 mutex 却把 `tokens` 当临界区外变量，是典型的"以为原子就安全"。

**③ 整秒量化丢余数**

`elapsed/1000` 向下取整 + `lastRefill.Store(now)` → 1.5s 间隔的请求每次只补 1 秒的量，**丢 0.5s**。结果是**限流实际比配置更严**，反直觉。

**④ 用户桶可被绕过 + 内存泄漏**

`userLimiters sync.Map` 从不淘汰（`:17,65-72`），且 `getUserLimiter` 是 **Load 后无条件 `Store`（第 70 行），不是 `LoadOrStore`** → **同一用户的并发首个请求会互相覆盖成"满桶新桶"，直接绕过该用户配额**。同时 sync.Map 无上限增长。

**⑤ 所有用户共用一个桶（致命陷阱）**

所有请求认证后都映射到同一个 `"default-user"`（`main.go:257` + `auth.go:59`）→ **`userQps=10` 才是真正的全平台上限**，`globalQps: 1000` 形同虚设。多实例部署时实际上限 ≈ **10 × 实例数**。

**⑥ 分布式限流实际从不生效**

```go
// pkg/gateway/distributed.go:77-82
if req.UserID != "" {              // ← req.UserID 从未被赋值
```

`req.UserID` 来自 `GatewayRequest.UserID`，HTTP 层从未赋值（`main.go:404-409` 只填 SessionID/AgentID/Message/Token；`auth.go:60` 设置的是 **`ctx.UserID`** 而非 `req.UserID`）。`ChatRequest` 结构体里也根本没有 userId 字段（`main.go:58-63`）。**`DistributedGateway.checkRateLimit` 是死代码。**

**⑦ 固定窗口的 Expire 非原子且错误被丢**

`pkg/redis/client.go:169` 的 `Expire` 返回值被丢弃。一旦 EXPIRE 失败/进程在两次命令间崩溃，**key 永不过期 → 该用户被永久限流**。正确做法是 Lua 脚本或 `SET key 0 EX 1 NX` + `INCR` 合并成一条 EVAL。

**⑧ 降级是 fail-open**（对的设计）

`distributed.go:194-196`：Redis 出错时返回 `true`（放行）。这是"限流不可用优先保业务可用"，但要能说出代价（Redis 挂了等于没限流）。

## 三、认证与安全

### 事实

**认证是静态 apiKey 明文查表**：**无 token 签发、无签名、无过期、无 JWT、无刷新**。

```go
// pkg/gateway/auth.go:42-67
if !f.enabled { return nil }                              // ← 未启用 = 全放行
token := strings.TrimSpace(ctx.Request.Token)
if token == "" && f.defaultToken != "" { token = f.defaultToken }   // 有默认 token 兜底
if token == "" { return ErrorResponse("UNAUTHORIZED", "缺少认证 Token") }
if userID, ok := f.validKeys[token]; ok {                 // map 明文比对
    ctx.UserID = userID; return nil
}
```

未用 `subtle.ConstantTimeCompare`（时间侧信道，理论问题）。stage3 装配处：`main.go:255-259`，`validKeys = {apiKey: "default-user"}`，apiKey **明文写在 YAML**（`stage3.yml:93`）。

**安全过滤防 4 类**（`security.go`）：
1. 长度：`len(message) > maxInputLength`（`:70`，**按字节不是 rune** —— 中文 4000 字节 ≈ 1333 汉字）
2. Prompt 注入：5 条大小写不敏感正则（忽略指令 / 角色切换 / `system:` 前缀 / 越狱词 / 危险命令，`:23-34`）
3. 非法字符：仅 `\x00` 一个（`:84`）
4. 敏感词：朴素 `strings.Contains(lower(input), word)` 线性扫描（`:90-98`）

**日志脱敏做得不错**：`truncate(token, 8)`（`auth.go:65`、`filter.go:118-123`）只打印前 8 位；`gateway.go:66` 只打 `msg_len` 不打消息体；`security.go:78` 只打正则前 40 字符。**未发现明文 token / 完整 prompt 落日志。**

### 关键缺陷

**① 信息泄漏：底层错误直接返回给客户端**

`gateway.go:157` 的 `fmt.Sprintf("Agent 执行失败: %v", err)` → **可能泄漏上游 LLM/MCP 的原始错误（含 URL、模型名、连接信息）**给终端用户。而 `gateway.go:73` 会打印它。

**② 正则黑名单必然可绕**

Unicode 归一化（`ｉｇｎｏｒｅ`）、全角空格、零宽字符、中文同义词（"无视上述要求"）、Base64、拼音。诚实答法：黑名单是**演示级防护**，不是安全边界。

**③ CORS 是 `*` 且允许全部方法**（`main.go:582-584`），生产需收敛。

## 四、会话与并发：Lane（重点）

### 事实

**Lane 是什么**：每个 session 一条"车道"，用 CAS 把 `processing: 0→1` 抢占，保证**同一 session 的请求串行**（`lane.go:33-68`）。

```go
// pkg/gateway/gateway.go:117-131（本地模式）
entered := false
for i := 0; i < 600; i++ {           // 50ms × 600 = 30s
    if lane.TryEnter() { entered = true; break }
    time.Sleep(50 * time.Millisecond)   // ← 忙等轮询，且不看 ctx.Done()
}
if !entered { return ErrorResponse("SYSTEM_BUSY", "系统繁忙，请稍后重试") }
defer lane.Leave()
```

```go
// pkg/gateway/lane.go:52-68
func (l *Lane) TryEnter() bool {
    swapped := l.processing.CompareAndSwap(0, 1)
    if swapped { l.queueSize.Add(1) }      // 注意：成功才 +1，且 Leave 不减
    return swapped
}
func (l *Lane) Leave() { l.processedCount.Add(1); l.processing.Store(0) }
```

**分布式模式**用 **Redis SET NX PX 锁 + 100ms 轮询**（`distributed.go:201-221`）。锁释放用 **Lua compare-and-delete**（`pkg/redis/client.go:145-159`）—— **这个设计是对的**，避免超时后误删别人的锁。

**没有做会话粘性**：全仓 grep `consistent|hashring|ketama` 零命中。多实例下同一会话可能落到任意实例，靠 Redis 锁做**跨实例串行**。

### 关键缺陷

**① 分布式锁没有看门狗续期（最容易被问倒）**

锁 TTL 默认 **60s**（`distributed.go:45-49`、`config.go:94`）。如果一次 LLM 调用要 60s+，**锁会在业务未完成时自动过期，第二个请求进入同一会话 → 两个请求并发读写同一会话**。这是"裸 SETNX 没有 watchdog"的经典漏洞（Redisson 有 watchdog）。

**② 客户端断开会卡满锁 TTL**

```go
// pkg/gateway/distributed.go:99
defer dg.releaseLaneLock(ctx, laneKey, requestID)   // ← 用的是 r.Context()
```

客户端一断开 ctx 被取消 → Lua 脚本调用失败 → **锁不释放，卡满 60s TTL** → 该会话后续请求全部 `LANE_BUSY`。

本地模式更差：轮询**不看 `ctx.Done()`**（对比 `distributed.go:213-215` 有 select），goroutine 会空转 30s。

**③ requestID 跨实例不唯一**

`distributed.go:91` 用 `time.Now().UnixNano()` → 不同机器时钟可能重合，一旦碰撞，A 的 `Unlock` 可能删掉 B 持的锁。应答：UUID 或 `instanceID-nanotime`。

**④ 轮询 vs 阻塞**

50ms/100ms 固定间隔轮询，N 个等待者 = N × 20 QPS 的 Redis 往返；且 50ms 粒度意味着平均额外 25ms 延迟。应答：Redis Pub/Sub 唤醒、阻塞队列，或本地串行 + 一致性哈希把会话钉到实例。

**⑤ 机制命名与实现不符**

`TryEnter` 里 `queueSize.Add(1)` 只在抢到锁时执行且 `Leave` 不减（`lane.go:55`），所以 `GetQueueSize()` 返回的是**累计进入次数**，不是队列长度。

**⑥ Lane 与 sessions 只增不减**

`RemoveLane` 全仓**无调用方**（`lane.go:112`，死代码）；`Gateway.sessions sync.Map`（`gateway.go:31`）只在显式 `ClearSession` 时删除。两者**无 TTL、无上限、无 LRU** → 长跑进程按 sessionID 无限增长。

## 五、Redis 分布式记忆

### 事实

**连接池完全没配**：

```go
// pkg/redis/client.go:25-33
client := redis.NewClient(&redis.Options{
    Addr: cfg.Addr, Password: cfg.Password, DB: cfg.DB,
})
```

全仓没有 `PoolSize` / `MinIdleConns` / `PoolTimeout` / `ConnMaxIdleTime` / `ReadTimeout` / `WriteTimeout`。走 go-redis 默认值：**`PoolSize = 10 * GOMAXPROCS`、`MinIdleConns = 0`、读写超时 3s**。没有 TLS、没有 Sentinel/Cluster、没有熔断。

**key 与存储**：`bitguide:session:{sessionID}`（`memory/distributed.go:52-54`），value 是**整个会话的 JSON 快照**：

```go
// pkg/memory/distributed.go:26-30, 93-105
type sessionData struct {
	Interactions []Interaction         `json:"interactions"`
	Variables    map[string]interface{} `json:"variables"`
}
func (d *DistributedMemory) saveToRedis(sessionID string, mem *ConversationMemory) {
	data := sessionData{Interactions: mem.GetHistory(), Variables: mem.GetVariables()}
	if err := d.redisClient.SetJSON(ctx, d.redisKey(sessionID), data, d.ttl); err != nil { /* 只打日志 */ }
}
```

**全量 JSON `SET`，没有 Hash/List 增量追加、没有压缩、没有分页、没有 value 大小检查。**

**TTL**：有，默认 1 小时（`distributed.go:37-38`）。**但本地 `localCache sync.Map` 永不过期**（`:20`）→ "TTL 不可靠"。

### 关键缺陷

**① 分布式记忆只写不读（最大短板，必须自己先说）**

`DistributedMemory.BuildMessages` / `GetHistory` **没有任何生产调用方**。LLM 上下文来自 `BaseAgent.session.Memory.BuildMessages`（`pkg/agent/base.go:232,306`），而那是**每个实例各自的内存 `sync.Map`**（`base.go:31,388-396`）。

**也就是说 Redis 里的会话记忆目前只写不读** → **换一个实例或重启后 LLM 拿不到历史**。"分布式记忆"在端到端行为上并不成立（数据存了，没接回上下文）。

**② 陈旧缓存回写导致消息丢失**

同实例内：`ConversationMemory` 有 `sync.RWMutex`，单条 append 安全。跨实例：Redis Lane 锁保证了同一会话同一时刻只有一个实例在写，**所以"并发交错"被防住了**；但**陈旧缓存回写**没防 —— A 实例本地缓存停留在旧版本，B 写入新消息后，A 下次请求直接用自己那份旧快照全量覆盖 Redis → **B 的消息丢失**。

**lane 锁只解决并发，不解决缓存失效。** 正确做法：版本号 / `WATCH`+乐观锁 / 写完就 `DEL` 本地缓存 / 把 Redis 当唯一数据源。

**③ Redis 挂了是静默失败**

- 启动时 `Ping` 失败 → 降级为单机模式（`main.go:284-286`），这是唯一的降级。
- 运行时：`GetJSON` 失败被当成"key 不存在"→ **静默新建空会话**（`distributed.go:71-85`，错误被 `else` 吃掉）；`saveToRedis` 失败只打 `clog.Error`（`:102-104`）→ **请求仍成功返回，记忆静默丢失且上层无感知**。
- **Lane 锁路径不是 fail-open**：Redis 不可用时 `acquireLaneLock` 会**轮询满 30 秒**才返回 `LANE_BUSY` → Redis 故障时每个请求挂 30s，**等于自我 DoS**。这与限流的 fail-open 行为**不一致**。

**④ 健康检查撒谎**

`RedisConnected: cfg.Redis.Enabled`（`main.go:334`）读的是**配置开关**，不是 `Ping` 结果 → Redis 挂了 `/health` 依然返回 `"redisConnected": true`。

**⑤ DELETE 会话清不掉 Redis**

HTTP handler 调的是 `gw.ClearSession`（基础版，`main.go:474`），而清 Redis 的逻辑在 `DistributedGateway.ClearSession`（`distributed.go:182-187`）—— **该方法没有任何调用方**。

**⑥ sessionID 不一致**

分布式记忆用 `userID:sessionID`（`distributed.go:85-88`），而 `getOrCreateSession` 用的是原始 `req.SessionID`（`:119`）。stage3 里 UserID 恒空所以没暴露，一旦接入 userId 就会出现"本地会话 map 与 Redis key 不对齐"。

**⑦ 丢取消传播**：`GetOrCreate`/`saveToRedis` 都带 `context.WithTimeout(3s)`（`:67,94`）但用的是 `context.Background()`，**客户端断开后 Redis 调用照跑**。

## 六、etcd 动态配置与热更新

### 事实

**观察者模式**：接口 + 切片回调，**同步调用**，不是 channel。

```go
// pkg/dynamic/listener.go:4-7
type ConfigChangeListener interface{ OnConfigChange(event *ConfigEvent) }

// pkg/dynamic/watcher.go:38-40, 194-198
func (w *ConfigWatcher) AddListener(listener ConfigChangeListener) {
	w.listeners = append(w.listeners, listener)     // ← 无锁！
}
func (w *ConfigWatcher) notifyListeners(event *ConfigEvent) {
	for _, listener := range w.listeners { listener.OnConfigChange(event) }  // 同步、watch 协程内
}
```

```go
// pkg/dynamic/watcher.go:119-142
watchChan := w.client.Watch(w.ctx, prefix, clientv3.WithPrefix())   // ← 没有 WithRev(...)
for {
	select {
	case <-w.ctx.Done(): return
	case watchResp, ok := <-watchChan:
		if !ok { return }
		if watchResp.Err() != nil { clog.Error(...); return }   // ← 直接退出，永不重连
		for _, event := range watchResp.Events { w.handleEvent(event) }
	}
}
```

### 关键缺陷

**① watch 出错后永久退出，静默失效**

`watchResp.Err() != nil` 直接 `return`（`:132-135`）。一旦出现**不可恢复错误（典型是 etcd compaction：`required revision has been compacted`）**，watch 协程永久退出 → **配置热更新静默失效、无人知晓**（没有重启、没有告警、没有降到轮询兜底）。

**这是最容易被追着打的一点。**

**② Get 与 Watch 之间丢事件**

`loadAllConfigs` 拿到 `resp.Header.Revision` 后**丢弃了它**，`Watch` 没带 `WithRev(revision+1)`（`:99-122`）→ 两次调用之间的 PUT/DELETE 不会被感知。

**标准做法**：`Get` 拿 revision → `Watch(..., WithRev(rev+1))`。

**③ watch 回调里做重活**

`notifyListeners` **同步在 watch goroutine 里执行** → `handleAgentConfigChange` → `registry.Register` → `factory.CreateAgentFromConfig`，**可能建立 MCP 连接（网络 IO）**；知识库路径还会启动文档摄取。

后果：watch 循环被阻塞，etcd 事件在后面排队（`WatchQueueSize: 100` 配了但**代码里从未使用**，`config.go:107`），长时间阻塞会顶到 clientv3 的 channel 缓冲上限。另外**没有 panic recover** —— 任何一个监听器 panic 都会杀掉 watch 协程。

**④ 配置零校验**

```go
// pkg/dynamic/manager.go:241-252
func (m *DynamicConfigManager) parseAgentConfig(jsonStr string) *config.AgentConfig {
	var cfg config.AgentConfig
	if err := json.Unmarshal([]byte(jsonStr), &cfg); err != nil { clog.Error(...); return nil }
	return &cfg        // ← 只判断 JSON 合法性，零字段校验
}
```

`temperature: 999`、`maxTokens: -1`、`modelRef` 指向不存在的模型、`systemPrompt` 为空等**都不会被拦**。推**非 JSON** → 打一行 Error 日志，**静默忽略，etcd 里的坏值一直留着**。

**⑤ 手写 Lock/Unlock 而非 defer**

`manager.go:173-217` 的 `handleKnowledgeBaseConfigChange` 有 4 条 return/分支各自 Unlock —— 现在正确，但**任何后续编辑漏掉一次 Unlock 就是整条配置链永久死锁**。

**⑥ 裸 map 的定时炸弹**

`LLMGateway.RegisterModel` 往**裸 map** 写（`pkg/llm/gateway.go:68-75`，无锁），读方 `FormatModelInfo` 在 `:154`。当前读只发生在启动期，**暂不构成 panic**，但混用 `sync.Map`(modelCache) 与裸 map(modelConfigs) 是明显的隐患。

**⑦ key 解析脆弱 + 默认前缀不一致**

`parseKey` 硬编码 `parts[3]/parts[4]`（`event.go:73-84`）—— 多级 key 会解析出错误的 configID 且不报错。`watcher.go:77-79` 默认前缀 `/bitguide/config/`，而 `stage3.yml:58` 用的是 `/bitguide-go/config/`（靠 YAML 显式配置才对齐，**漏配就静默监听不到任何东西**）。

### 做得好的地方

- **热更新的请求侧保证**（这是本项目设计得最好的地方）：Agent 有引用计数，请求期间持有引用，等引用归零才销毁旧实例（`registry.go:154-196` + `gateway.go:99-115`）。**单请求持有 Agent 引用，全程看到同一个 Agent 实例，不会一半旧一半新。** 创建失败还会回滚（`registry.go:181`）。
- `handleEvent` 对同值 PUT 做了幂等跳过（`watcher.go:158-163`）；cache 里的旧值让 UPDATE/DELETE 事件语义完整。
- `DynamicConfigManager` 通过 `SetRAGService/SetLLMGateway/SetSkillManager` 注入依赖，注释特意提醒"必须在 Init() 之前注入"（`main.go:233`）—— 说明踩过坑。

### 但要主动交代三个瑕疵

- **`markForDeletion` 到注册新实例之间有窗口** → 此时进来的请求 `AcquireRequest` 失败 → 短暂 `AGENT_NOT_FOUND`（可用性缺口）。
- **跨配置项无原子快照** → 一个请求可能用到"新模型配置 + 旧 Agent 配置"。
- **知识库是 incremental 灌入向量库**（`manager.go:188-199`）→ 灌入期间查询会看到**部分加载的索引**（没有蓝绿双索引切换）。

## 七、HTTP 服务（cmd/stage3/main.go）

### http.Server 参数：一个都没设

```go
// cmd/stage3/main.go:506-509
server := &http.Server{
	Addr:    fmt.Sprintf(":%d", port),
	Handler: handler,
}
```

`ReadTimeout` / `ReadHeaderTimeout` / `WriteTimeout` / `IdleTimeout` / `MaxHeaderBytes` **全部为零值 = 不限制**。`WriteTimeout=0` + 慢客户端 → slowloris；叠加"本地 Lane 轮询 30s 不看 ctx" → 慢连接可长期占住 goroutine 和会话锁。

### 优雅关闭：有，且链路完整

```go
// cmd/stage3/main.go:512-548
go func() {
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)
	<-sigChan
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	server.Shutdown(ctx)          // 1. 停新请求，等在途请求（最多 10s）
	dynamicManager.Stop()         // 2. 停 etcd watch
	registry.Clear()              // 3. 清 Agent（触发 MCP 断开）
	factory.Shutdown()            // 4. 关工厂
	redisCli.Close()              // 5. 关 Redis
}()
...
log.Fatal(server.ListenAndServe())   // main.go:551
```

**两个瑕疵**：
- `log.Fatal(server.ListenAndServe())`（`:551`）—— `Shutdown` 成功后返回 `http.ErrServerClosed`，`log.Fatal` 会**以退出码 1 结束进程**，K8s 里看起来像崩溃。正确写法是判 `errors.Is(err, http.ErrServerClosed)` 后 `return`。
- 10s 超时到点后 `Shutdown` 强制返回，紧接着 `registry.Clear()`/`redisCli.Close()` **直接掐断还在跑的请求**（比如 LLM 调用 60s）—— 需要更长超时或先摘流量。

### 可观测性

- `/metrics`（Prometheus `promhttp.Handler()`，`:485`）、`/health`（`:322-338`）、`/api/v1/agents`、`/api/v1/chat`、`/api/v1/sessions/`。
- **没有 pprof**（全仓 `pprof` 零命中）。

- `/api/v1/chat` 每次请求都可能触发 `sessionID` 自动生成（`:394-396`）→ 前端不传 sessionID 就等于**每次都新建会话**，Lane 锁形同虚设，且 `sessions` map 每次请求增长一条。
- `json.NewDecoder(r.Body).Decode` **无 body 大小限制**（`:384`）。

### 压测与测试

**没有。** 仓库里**没有任何 `*_test.go`**，没有 wrk/ab/hey 脚本，README 里也没有 QPS 数字。

**被问「你的服务能扛多少并发」时，唯一诚实的回答是"没有压测过"。** 然后可以定性分析瓶颈：请求耗时由 LLM 决定（秒级 IO），受限的不是 Go 的 goroutine 而是 LLM 后端并发；服务端自身**没有任何并发上限**（`globalMaxConcurrent: 100` 配了但代码从不读，`config.go:151`）→ 大流量打进来只会堆积 goroutine 和 LLM 连接。**要能主动说出"缺少并发闸门（semaphore）"这个洞。**
