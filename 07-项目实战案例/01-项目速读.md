## 一、它是什么

BitGuide 是一个教学导向的 Agent 平台：75 个 Go 文件、12,253 行、四个递进阶段，共用同一个 `pkg/`。定位是**教材不是产品**——每个 Stage 只引入一个新概念，所以每条线都做到「能讲清楚原理」，而不是「能扛住线上」。

| 维度 | 事实 | 出处 |
|---|---|---|
| 规模 | 75 个 Go 文件 / 12,253 行；`*_test.go` **0 个** | 仓库全量 `find` 计数 |
| 四个入口 | stage1 205 行 / stage2 395 行 / stage3 676 行 / stage4 252 行 | `cmd/stage{1,2,3,4}/main.go` |
| LLM | go-openai v1.17.9，默认 Ollama `qwen2.5`，embedding `nomic-embed-text` | `go.mod:8`、`cmd/stage1/stage1.yml` |
| 存储 | Milvus（向量）/ etcd（配置）/ Redis（会话 + 锁 + 限流） | `pkg/rag`、`pkg/dynamic`、`pkg/redis` |
| HTTP | 纯 `net/http` + `http.ServeMux`，**无 Gin/Echo** | `cmd/stage3/main.go:319` |
| 依赖 | milvus-sdk-go v2.4.2、go-redis v9、etcd clientv3、Viper | `go.mod:6-8` |
| 定位的代价 | 工作流引擎写完了但没进 README；4 个 REST 接口写了但零调用 | `README.md`（只写 3 个 Stage）、`pkg/workflow/server/handler.go:74-79` |

**「教学项目」这四个字意味着什么**：它是**取舍**，不是缺点，但你必须能把取舍讲成判断，而不是借口。

- **它解释了什么被砍掉了**：没有单元测试、没有压测、没有 RAG 评估、没有 tracing（全仓 `pprof` / OpenTelemetry 零命中），因为这些都不属于「讲清楚一个概念」的必需项。
- **它也解释了为什么有些东西写了一半**：Stage4 的 `pkg/workflow/server` 注册了 4 个路由（`handler.go:74-79`）却没人调用，`WithChannel` 定义了三类实现却零调用点——**写完但没接线**是这个项目的典型形态。
- **它不解释也不该被接受的是**：协议不合规（`tool_call_id` 缺失）、`IsAlive` 恒真、热更新自毁连接——这些不是取舍，是疏漏。**面试时的关键动作是把这两类分开讲**：前者说"我砍的，我知道代价"，后者说"我写错的，我知道为什么、知道怎么改"。

**这张图里最值钱的一句话**：MCP 工具通过 `pkg/mcp/adapter.go` 适配成和内置工具**同一个 `tool.Tool` 接口**，所以 ReAct 循环一行都没改就同时支持本地和远程工具——`base.go:349` 的 `a.toolManager.Get(tc.Name)` 完全不关心工具从哪来。这是全项目结构上最干净的一处。

**第二值钱的一句话**：L4 的六个能力包**彼此不依赖**，都只依赖 L3 定义的接口（`llm.Client`、`tool.Tool`、`rag.Service` 指针）。所以 Stage2 换多模型（`llm/gateway.go:17` 的 `sync.Map` 按 modelRef 缓存客户端）不需要 Agent 改一行。

**四层各自的职责边界**（被问"为什么这么分层"时按这张表答，比背目录结构有用）：

| 层 | 只该做 | 不该做 | 越界的代价（本项目实例） |
|---|---|---|---|
| L1 接入 | 协议转换、参数解析、HTTP 语义 | 业务判断、状态管理 | `main.go:394-396` 每次不传 sessionID 就自动生成 → **Lane 锁形同虚设**，`sessions` map 每请求增长一条 |
| L2 网关 | 横切关注点：身份、限流、串行、可观测 | 直接操作 Agent 内部状态 | `filter.go:46-53` 把 `UserID` 放在 `RequestContext` 里，但下游有人去读 `req.UserID` → 死代码 |
| L3 Agent | 循环控制、会话生命周期、引用计数 | 关心工具/模型从哪来 | 循环里每轮重建 `tools` 数组（`base.go:316`），**不缓存、也不裁剪**（10 轮 = 10 次重复的 Schema 生成） |
| L4 能力 | 单一能力，通过接口暴露 | 反向依赖上层 | `pkg/mcp/adapter.go` 只实现 `tool.Tool`，不认识 Agent → 这是它最干净的地方 |

## 三、四个 Stage 各自引入了什么

| Stage | 定位 | 新增能力 | 关键文件 | 为什么现在才引入 |
|---|---|---|---|---|
| **1** | MVP Agent | ReAct 循环、4 个内置工具、MCP（stdio）、Skill 加载、RAG 检索（Milvus） | `cmd/stage1/main.go:189`、`pkg/agent/base.go:295` | **必须先有一个能跑通的"一次 LLM 调用"**。工具、RAG、Skill 全挂在同一个循环上，循环本身没写对，上面挂什么都是错的 |
| **2** | 通用平台 | 多 Agent（Factory + Registry）、etcd 动态配置 + watch 热更新、引用计数、LLMGateway 多模型路由 | `pkg/agent/registry.go:153-199`、`pkg/dynamic/watcher.go:119-142`、`pkg/llm/gateway.go:17` | Stage1 的 Agent 是构造时就固定的；要"改 prompt 不重启"，才必须引入**配置中心 + 注册表 + 生命周期管理**这一整套。没有热更新需求时，Registry 只是多余的一层 |
| **3** | 企业级服务 | Gateway 三层过滤器（认证/安全/限流）、HTTP API + Web、本地 Lane 串行、Redis 分布式 Lane 锁 + 固定窗口限流 + 分布式记忆、Prometheus | `cmd/stage3/main.go:254-261,319,376`、`pkg/gateway/filter.go:96-106`、`pkg/gateway/distributed.go:94-99` | **并发是 Stage1/2 里根本不存在的问题**——CLI 是单线程的，一个 session 一个用户。只有变成 HTTP 服务、多请求并发之后，"同一 session 的两个请求同时改一份历史"才会真的发生。Lane 是**被问题逼出来的**，不是提前设计的 |
| **4** | 工作流引擎 | 状态图（`__start__`/`__end__` 哨兵）、条件边、checkpoint + interrupt/resume、Supervisor/Router/Loop/SubTaskExecutor 等 8 类节点 | `pkg/workflow/core/{graph,executor,state,channel}.go`、`pkg/workflow/patterns/*.go` | 前三个 Stage 都是**单次请求内的 ReAct**；多步骤、可暂停、可恢复、要人机交互的流程，用 ReAct 表达不了。这是"控制流"和"模型自主决策"的分界线 |

### 每个 Stage 的一句话记忆点 + 最常见的追问

**Stage1 · 一句话**：一个 while 循环加三个出口。
- 循环：`base.go:312-382`，最多 10 轮（`maxIterations := 10`，`:296` 是**局部变量**，不在 config 里）。
- 三个出口：模型不返回 tool_calls（`:325`，正常出口）、跑满 10 轮（`:384`，返回 error）、LLM 报错（`:320-322`，直接返回）。
- **追问「为什么是 10」**：诚实答案是"经验值"。更好的是补一句"它应该是配置项，而且要按模型能力区分——10 轮对 Qwen2.5 偏多，对 GPT-4 级别的模型偏少"。

**Stage2 · 一句话**：把「Agent 是什么」从代码里搬到了 etcd 里。
- 热更新五步：标记旧（`registry.go:176`）→ 建新（`:179`）→ 换 map 指针（`:187-191`）→ 起 goroutine 等引用归零（`:196`）→ 销毁（`:202-214`）。
- **追问「热更新中途的请求怎么办」**：引用计数保证它看到的是同一个旧实例；如果拿到的是已标记的旧 entry，会**刷新到最新 Agent 再 acquire**（`gateway.go:101-108`）；新实例创建失败会**回滚 `marked=0`**（`registry.go:182`）。

**Stage3 · 一句话**：把「一个用户一个进程」变成「多用户一个服务」，于是所有并发问题一次性到账。
- 三层防线：过滤器链（`filter.go:96-106`）→ Lane 串行（`gateway.go:117-131`）→ Redis 锁（`distributed.go:94-99`）。
- **追问「为什么拿 Redis 锁还要本地 Lane」**：本地 Lane 是**同实例内**的低成本串行（CAS，无网络往返），Redis 锁是**跨实例**的兜底。代价是本地模式轮询不看 `ctx.Done()`（`gateway.go:119-124`），客户端断开会空转 30s。

**Stage4 · 一句话**：用约 2000 行 Go 重写了 LangGraph 的核心概念，并**明确不做 superstep**。
- 能跑的闭环：checkpoint + interrupt + resume（`executor.go:83-149`；`InterruptNode` 只打标记存快照，`:23-48`，由 executor 在节点返回后检测 `_interrupted` 并 return，`:59-65`）。
- **追问「你这个 interrupt 是节点内挂起还是 executor 扫状态位」**：**是后者**，协作式的。LangGraph 是节点内动态 `interrupt()` + `Command(resume=...)`。

**四个 Stage 的递进关系可以一句话说完**：
> Stage1 让一个 Agent 能干活 → Stage2 让很多 Agent 能被动态管理 → Stage3 让这些 Agent 能被很多用户同时用 → Stage4 让多个 Agent 按图协作并能中途停下来等人。

**面试官最爱的追问：「为什么 Stage2 不直接上 Gateway？」**
答：因为 Gateway 的价值依赖两个前提——**多用户**和**多实例**。Stage2 是 CLI 单机，Gateway 的认证没有对手方、限流没有维度、Lane 锁没有并发者。提前引入的结果是三个过滤器里两个是空转的，反而看不清它们各自解决什么问题。

## 四、一次请求的完整链路（按 Stage 3 讲）

这条链路是面试画图的底稿。**10 步，每步都能落到行号。**

| # | 环节 | 位置 | 一句话说明 |
|---|---|---|---|
| 1 | CORS 中间件包装 | `cmd/stage3/main.go:580-593`、挂载点 `:505` | 裸函数包装 handler，`Access-Control-Allow-*: *`，生产要收敛 |
| 2 | `http.ServeMux` 路由 | `main.go:319`、各 `HandleFunc` `:341,357,376,441,489` | 手工前缀匹配，在 handler 内部判 `r.Method`；无 Gin/Echo |
| 3 | 解析请求 | `main.go:383-401` | `json.NewDecoder(...).Decode`（**无 body 大小限制**）；sessionID 缺失则自动生成（`:394-396`）；`req.Token = r.Header.Get("X-API-Key")`（`:400`） |
| 4 | 运行期决定单机/分布式 | `main.go:274-304`、调用点 `:413` | `activeProcessFunc` 这个函数变量在启动时按 Redis Ping 结果二选一：`gw.Process` 或 `distGw.Process` |
| 5 | 过滤器链 | `pkg/gateway/filter.go:96-106`；排序 `:82-92` | Auth(**10**) → Security(**20**) → RateLimit(**30**)（注意注释写反了，见 §六） |
| 6 | 分布式限流 | `pkg/gateway/distributed.go:77-82` → `:190-198` | **实际是死代码**：`req.UserID` 从未被赋值，条件恒不成立 |
| 7 | Lane 串行化 | 本地 `gateway.go:117-131`；Redis `distributed.go:94-99` | 本地 CAS 轮询最多 30s；分布式 `SET NX PX` + Lua compare-and-delete 释放（`pkg/redis/client.go:145-159`，这个设计是对的） |
| 8 | 引用计数 + 会话装配 | `gateway.go:99-115`、`distributed.go:124-131` | acquire 失败会**刷新到最新 Agent** 再 acquire；`defer ReleaseRequest()` |
| 9 | Skills 匹配（条件触发） | `gateway.go:135-147`、`distributed.go:138-152` | 只有 `len(agentCfg.SkillRefs) > 0` 才触发；命中则直接 return，**不进 ReAct** |
| 10 | Agent 对话 + 写记忆 | `gateway.go:152`、`distributed.go:156,165-167`、`pkg/agent/base.go:147-179` | `ChatWithSession` → 会话记忆 → 分流：有工具走 `chatWithTools`（`base.go:295`），无工具走 `chatDirectly`（`base.go:225`）；最后把回复写进 Redis（**只写不读**，见 §六） |

**第 9 步到第 10 步之间发生的事（面试最常追问的一段）：**
`ChatWithSession` 先把 user 消息写进会话记忆（`base.go:158`），再进循环。循环里每轮**重新生成工具定义**（`base.go:316` → `pkg/tool/manager.go:75-105`）调 LLM（`base.go:319`）；没有 `tool_calls` 就返回（`:325`，正常出口）；有就顺序执行工具、把结果作为 `role:"tool"` 消息塞回历史（`:377-380`）继续下一轮。**跑满 10 轮返回 error**（`:384`，此时 `:172-174` 直接 return，`:177` 的"写回 assistant 回复"不可达，但 `:158` 已经把 user 消息写进历史了 → 留下一条永远没有回复的 user 消息）。

**链路里有三个"看起来在跑、其实没跑"的点，务必自己先说出来：**

- **埋点写在死代码里**：`pkg/tool/manager.go:108-128` 的 `Manager.Execute`（带日志、带 `metrics.ToolExecuteSuccess`）**在 ReAct 循环里根本没被调用**——`base.go:360` 直接调 `t.Execute`。所以 `ToolCallsTotal` 指标和 `ToolExecuteStart/Success` 日志是死代码（只有 stage4 的 `tool_node.go:46` 用它）。
- **第 6 步的分布式限流**是死代码（条件恒不成立）。
- **第 10 步写的 Redis 记忆**没人读（`DistributedMemory.BuildMessages` 零调用）。

**画这张图的三个锚点**（面试时不用背全部行号，记住这三条就能把图画对）：
1. **横向的分界线在 `RequestContext`**（`filter.go:46-53`）——过滤器链之前是 HTTP 细节，之后是业务逻辑；`UserID` 正是在这里从 `req` 搬到 `ctx` 的，所以下游读错载体就会静默失效。
2. **纵向的分界线在 `tool.Tool` 接口**（`tool.go:4-16`）——L4 的六种能力全都被适配成统一接口，Agent 只认名字不认来源；这也解释了为什么加 MCP 不用改循环。
3. **会话状态有两个副本**：`BaseAgent.sessions`（内存，`base.go:31`）和 Redis（`memory/distributed.go`）——**只有前者真的被 LLM 读到**，这是整张图里最容易被面试官一眼看穿的裂缝。

## 五、核心数据结构速查

| 结构 | 定义位置 | 一句话说明 |
|---|---|---|
| `GatewayRequest` | `pkg/gateway/filter.go:8-14` | SessionID / **UserID** / AgentID / Message / Token。**HTTP 层从不填 UserID**，是坑 8 的根源 |
| `RequestContext` | `pkg/gateway/filter.go:46-53` | 请求在过滤器链里的载体：Request + StartTime + **UserID**（AuthFilter 写入，`auth.go:60`）+ AgentID + Blocked/BlockReason |
| `FilterChain` | `pkg/gateway/filter.go:77-79` | `filters []GatewayFilter`。`NewFilterChain` 先 copy 再排序（`:84-85`），**不改调用方切片**（一个很隐蔽的别名 bug 被避开了） |
| `GatewayFilter` | `pkg/gateway/filter.go:66-74` | 只有三个方法：`GetName`/`GetOrder`/`Process`。**`Process` 返回非 nil 即拦截并终止链** |
| `Lane` | `pkg/gateway/lane.go:36-41` | 会话车道：`processing atomic.Int32`（0=IDLE / 1=PROCESSING）+ queueSize + processedCount。`TryEnter` 是 CAS（`:52-58`），`Leave` 是裸 Store（`:62-65`） |
| `LaneManager` | `pkg/gateway/lane.go:92-94` | `lanes sync.Map`。`RemoveLane`（`:112`）**全项目零调用** → lane 只增不减、无 TTL、无上限 |
| `AgentEntry` | `pkg/agent/registry.go:24-31` | 注册表条目 = Agent + Config + Source + `refCount atomic.Int32` + `marked atomic.Int32`。**热更新安全的核心就是这两个原子量** |
| `AgentConfig` | `pkg/config/config.go:32-54` | etcd 推送的配置形态：ID/Name/Description/ModelRef/SystemPrompt + ToolRefs/SkillRefs/McpServers/KnowledgeBase/Memory。**Description 和 Memory 没进 `configEqual` 的比较**（`registry.go:344-371`） |
| `SessionContext` | `pkg/agent/base.go:36-38` | 只有一个字段 `Memory *ConversationMemory`。存在 `sessions sync.Map` 里（`base.go:31`），**per 实例** |
| `Message`（记忆侧） | `pkg/memory/conversation.go:216-220` | 只有 `Role` + `Content`。`BuildMessages`（`:171-213`）把 `InteractionTypeTool` 映射成 `role:"tool"`——协议不合规的源头之一 |
| `Message`（LLM 侧） | `pkg/llm/client.go:8-11` | 同样只有 `Role` + `Content`，**没有 `ToolCalls`、没有 `ToolCallID`** |

## 六、3 个真亮点 + 3 个真短板

### 亮点 1 · Agent 热更新的引用计数 + 优雅销毁（最值钱的一块）

`AgentEntry` 带 `refCount` + `marked`（`registry.go:24-31`）；热更新流程是「标记旧 → 建新 → 换指针 → 起 goroutine 等引用归零再销毁」（`registry.go:176-196`）；请求侧 `acquire` / `defer release`（`gateway.go:99-115`）——`acquire` 本身是 `marked` 检查 + `refCount.Add(1)` 两步（`registry.go:34-40`），有 TOCTOU 窗口，但窗口极窄且被"刷新到最新 Agent"兜住；**拿到已标记的旧 entry 时会刷新到最新 Agent**（`gateway.go:101-108`）；新实例创建失败会**回滚 `marked=0`**（`registry.go:182`）。
→ 结果是：**一个请求从头到尾看到同一个 Agent 实例，不会一半旧 prompt 一半新 prompt。** 再加上 session 级 Lane 串行（`gateway.go:117-131`），三层加起来是"企业级网关"故事里最实的部分。

### 亮点 2 · MCP 是真协议实现，不是玩具

`Client.initialize`（`client.go:98-131`）完整走 `initialize` → `notifications/initialized` → `tools/list`，协议版本 `2024-11-05`，并且用 `SendNotify`（`client.go:301-315`，注释写明"避免死锁"）发通知——**这是手写 MCP 客户端里少见的正确顺序**。stdio 用换行分隔 JSON（`stdio_transport.go:82-95`），stderr 异步打日志（`:70-76`）；`adapter.go:36-57` 把 MCP 的 `inputSchema` 转成统一 `ParameterDef`，**ReAct 循环零改动同时支持内置和远程工具**（`base.go:349`）。

### 亮点 3 · Skill 与 ReAct 正交，控制权不在 Skill 手里

Skill **没有执行体**——它就是「专业 SystemPrompt + 工具引用 + few-shot」（`skill.go:14-35`）。执行时只做两件事：注入工具、覆盖 system prompt，然后**复用同一个 ReAct 引擎**（`skill_enhancer.go:26-42` → `base.go:185-206`；`ChatWithSkill` 通过参数传 prompt 而不是改字段，注释特意说明了并发安全考虑，`base.go:184`）。`skill.go:6-12` 的注释还引了 Semantic Kernel / Assistants / LangChain 三种主流做法对比。
→ 这个判断是对的：**Skill 不该是"流程脚本"，流程归模型。** 与 Stage4 的 Workflow 形成清晰分工——Workflow 才是显式控制流。

### 短板 1 · 工具调用消息协议不合规（最致命）

`pkg/llm/client.go:8-11` 的 `Message` 没有 `ToolCalls` / `tool_call_id`；`base.go:338-341` 回填 assistant 消息时只带 `content`；`conversation.go:78-83` 把**工具名当内容**存成 `type=tool`，`BuildMessages`（`:195-197`）又映射成孤立的 `role:"tool"`。
→ **Ollama 容忍，OpenAI 官方接口直接 400。** 而且历史里会留一条"没有回复的 user 消息"（见 §四末）与孤立的 tool 消息，越跑越脏。
**被问到怎么答**：「这是我第一版对消息协议理解不到位——我以为 `role:"tool"` 是独立的历史条目，实际它必须紧跟带 `tool_calls` 的 assistant 消息并携带 `tool_call_id`。改法是把 `ToolCalls`/`ToolCallID` 加到结构体、回填时带上，并把工具调用**从会话记忆里剔出去**（它是循环内的中间态，不该落历史）。修法与 diff 在 `08-如果重做一次.md` 坑 1。」

### 短板 2 · LLM 层是裸调用（无超时 / 无重试 / 无流式 / 无成本统计）

`openai.go:29-35` 用 `openai.DefaultConfig` + `NewClientWithConfig`，底层 `http.DefaultClient` **无 Timeout**；embedding 的 `&http.Client{}`（`openai.go:42`）同样无超时；config 里**根本没有 timeout 字段**（`config.go:20-30`）；stage1/2 还传 `context.Background()`（`cmd/stage1/main.go:189`、`cmd/stage2/main.go:348`）。另外 `pkg/log/log.go:346` 有 `LLMResponse(model, tokens)` 但**全仓无调用者** → 没有 token/成本统计；`openai.go:69-71` 的 `if len(resp.Choices) == 0 { return "", nil }` 把空响应当成功，`base.go:325-328` 又把它当最终答案 → **用户看到空白回答且没有任何错误**。
**被问到怎么答**：「LLM 客户端是按『先跑通』写的，只做了 `CreateChatCompletion` 这一件事——**超时、重试、退避、熔断四件套一件都没有**。这在 Stage1 CLI 里看不出来，到 Stage3 变成 HTTP 服务后就变成可用性问题：一次 429 会把错误直接返回用户，而 429 本来最该重试。修法是显式传 `http.Client{Timeout}`、加带抖动的指数退避（只重试 429/5xx），并且**超时值必须小于会话锁 TTL**，否则请求还在重试、锁已经过期。」

### 短板 3 · 分布式记忆只写不读（换实例历史就丢）

`DistributedMemory.BuildMessages`（`memory/distributed.go:135-138`）和 `GetHistory`（`:129-132`）**没有任何生产调用方**；LLM 的上下文来自 `BaseAgent.session.Memory.BuildMessages`（`base.go:232,306`），那是**每个实例各自的内存 `sync.Map`**（`base.go:31,388-398`）。
→ Redis 里的会话记忆**只写不读**：换实例或重启后 LLM 拿不到历史。**"分布式记忆"在端到端行为上并不成立**（数据存了，没接回上下文）。更麻烦的是 `localCache sync.Map`（`:20`）永不过期，跨实例会有"陈旧缓存回写覆盖新消息"的问题——lane 锁只解决并发，**不解决缓存失效**。
**被问到怎么答**：「这是全项目最该先修的一个洞。我写了 `DistributedMemory` 的两级缓存和 Redis 序列化，但**没有把它接进 Agent 的上下文构建路径**——`BuildMessages` 是真的没人调。而且就算接上，本地 `sync.Map` 永不失效，A 实例的旧快照全量覆盖 Redis 会丢掉 B 刚写的消息。正确做法是让 Agent 依赖一个 `MemoryProvider` 接口、Redis 作唯一数据源 + 版本号乐观锁，完整改法见 `08-如果重做一次.md` 坑 10。」

### 补：还有三个"主动说出来会显得成熟"的点

- **MCP 配置是命令执行面**：`McpServers` 由 etcd 推送（`config/config.go:47`、`dynamic/manager.go:120-141`），`command`/`args` 直接进 `exec.CommandContext`（`stdio_transport.go:37`）→ **任何能写 etcd 配置的人都能在 Agent 主机上执行任意命令**，没有命令白名单、没有路径限制。
- **过滤器顺序是安全洞**：顺序是 Auth 10 → Security 20 → RateLimit 30，而注释写的是"认证→限流→安全"（`gateway.go:59`、`distributed.go:70`）→ **被安全规则拒绝的请求不消耗限流令牌**，可用"必被拦"的 payload 无限打满 5 条正则 + `ToLower` 全量扫描（`security.go:23-34,90-98`）→ CPU 打点。
- **没有并发闸门**：`globalMaxConcurrent: 100` 配了但代码从不读（`config.go:151`），`http.Server` 五个超时全为零值（`cmd/stage3/main.go:506-509`）→ 大流量只会堆积 goroutine 和 LLM 连接。

## 七、面试前 10 分钟自检题

**规则：先自己答，答不上来就翻对应的那一篇。别跳过——这 10 道覆盖了面试 80% 的追问。**

1. 四个 Stage 各自解决了什么问题？**为什么第三个 Stage 才引入 Gateway**？（→ 本文 §三）
2. 一次 HTTP 请求从进入到返回，经过哪 10 个环节？中间层里哪一步是**死代码**？（→ §四第 6 步）
3. Agent 热更新时，怎么保证一个在途请求**不会一半用旧 prompt、一半用新 prompt**？引用计数具体在哪两处加/减？（→ 亮点 1）
4. 工具调用消息为什么会 400？`role:"tool"` 消息缺了哪两个东西？（→ 短板 1）
5. `Tool.Execute` 的签名里少了一个什么参数？它导致哪些能力**结构上无法实现**？（→ §五 `Tool` 行）
6. 为什么说「所有用户共用 `default-user` 桶」会让 `globalQps: 1000` 形同虚设？真实上限是多少？（→ `02-网关与并发线.md` §二⑤）
7. 分布式 Lane 锁的 TTL 是多少？如果一次 LLM 调用要 90 秒会发生什么？（→ `08-如果重做一次.md` 坑 9）
8. etcd watch 在什么情况下会**永久退出且没人知道**？为什么会退？怎么修？（→ 坑 11）
9. Stage4 的 channel / `WithChannel` 抽象为什么说是死代码？`NewWorkflowState()` 建出来的 state 挂了几个 channel？（→ 坑 12）
10. 你说「支持并行」——全项目哪一处是真的并发？它有什么缺陷？（→ `03-RAG与工作流线.md` §二 `SubTaskExecutorNode`）

**答完之后自查一遍"四必说"**（这四句在面试里必须主动出现，否则会被追着打）：

- **必说取舍**：「Stage4 我不做 superstep，因为串行执行模型下 channel 的合并时机不存在」——把"没实现"说成"评估后不做"。
- **必说边界**：「这些并发设计全是静态分析，**没有一个是实测数据**」——仓库没有压测脚本、没有 QPS 数字，硬撑一秒就崩。
- **必说未验证**：「这个改动我没编译验证过，本机没有 Go 环境」——比假装验证过安全一百倍。
- **必说教训**：每个短板都要能收在一句话上（如"资源的生命周期 key 必须和实例一致，不能和逻辑名字一致"）。

**最后一句话建议**：这个项目最大的风险不是"有缺陷"，而是"被问到缺陷时露出意外"。上面每一条都是**你以为藏住了、其实面试官一眼能看出来的那种**。主动说，比被问出来强十倍——具体怎么说，看 `08-如果重做一次.md`。
