# 深挖：高并发与分布式

> **一句话** · AI 服务的并发瓶颈在下游（LLM / 向量库）的配额与排队能力，不在 Go 的 goroutine —— 所以"限流、排队、超时"在这个场景里不是性能优化，而是**可用性本身**。

## 一、本质：AI 服务的并发模型和普通 Web 有什么不同

先用利特尔法则（Little's Law）：**并发数 L = 到达率 λ × 停留时间 W**。

| 场景 | 到达率 λ | 单请求耗时 W | 需要的并发承载 L |
|---|---|---|---|
| 普通 Web（查一次 MySQL） | 1000 QPS | 50ms | **50** |
| Agent 对话（3 轮 ReAct + RAG） | 1000 QPS | 10s | **10,000** |

同样 1000 QPS，**Agent 服务需要的驻留并发是普通 Web 的 200 倍**。这不是实现问题，是"秒级 IO 请求"的物理事实：一个请求占用一个 goroutine、一条 HTTP 连接、一份会话上下文、一条到 LLM 的连接，一占就是 5~60 秒（`pkg/agent/base.go:296` 的 ReAct 循环 `maxIterations := 10`，每轮一次 LLM 调用，`base.go:312-322`）。

把这 10,000 并发翻译成资源，才看出差别：goroutine 栈 10,000 × 8KB ≈ **80MB**（还不含堆上的消息体与历史）；**10,000 条客户端连接 + 10,000 条到 LLM 的连接，而容器里 `ulimit -n` 常见值是 1024 → 先在 fd 上撞墙（`EMFILE`），根本到不了 10,000**；输入上限 4000 字节（`cmd/stage3/stage3.yml:102`），10,000 个在途请求 = 40MB 常驻；LLM 客户端是裸 `&http.Client{}`（`pkg/llm/openai.go:42`；go-openai 的 `DefaultConfig` 里也是同款），因此走 `http.DefaultTransport`，其 **`MaxIdleConnsPerHost` 默认是 2** —— 并发一超 2，空闲连接池立刻填满丢弃，每个新请求重开一条 TCP，对远程 HTTPS 端点就是每请求一次 TLS 握手（100~300ms + 一次非对称加密 CPU）。

但真正的瓶颈在这三条之上：

**① 瓶颈不在 CPU，在等待。** Go 里 10,000 个阻塞在 `read` 上的 goroutine 几乎不耗 CPU（调度器把它们挂在 netpoller 上），CPU 曲线会很漂亮而服务已经死了。**你要监控的不是 CPU，是"在途请求数"和"下游队列深度"。**

**② 不能靠加实例线性扩展，因为下游有配额。** 本地 Ollama 有并行推理上限（`OLLAMA_NUM_PARALLEL`，默认 1~4），云端 LLM 有 RPM/TPM 配额，Milvus 有查询并发上限。把实例从 1 个加到 10 个，下游承受的是同样的 10 倍压力 —— 结果是把 LLM 打到限流，所有实例一起 429。

**③ 过载的表现不是"慢"，是"雪崩"。** 普通 Web 过载时延迟上升、吞吐饱和，是个可预期的平台期；Agent 服务过载时延迟被排队推高到几十秒 → 客户端超时 → 重试 → 重试流量叠加在原队列上 → 延迟更高。**这是正反馈**，服务自身不会自救，必须靠外部机制（闸门 + 快速拒绝）打断。

所以后面每一节都在展开这三条：**限流**必须能区分维度（§三）；**排队必须有界**，无限接受请求 ≠ 高并发能力，只等于无限的内存增长（§四、§七）；**超时必须处处存在** —— HTTP 入口、LLM、Redis、锁 TTL，任何一个缺失的超时都会成为雪崩入口（§四、§五、§七）。

> **边界**：`globalQps: 1000` / `userQps: 10`（`stage3.yml:97-98`）在量级判断上是合理的（Agent 的 QPS 本来就该是两位数），这一点比很多"我 QPS 十万"的项目诚实。但下面会看到，这两个数字**在代码里根本没按预期生效**。

## 二、网关的三层过滤器

### 2.1 责任链的实现：20 行的插入排序 + 短路

`pkg/gateway/filter.go` 用 120 行实现了完整的责任链：接口只有三个方法（`filter.go:66-74`，`Process` 返回非 nil 即拦截并终止链）；排序是插入排序（`filter.go:82-92`）；执行链在第一个非 nil 处短路（`filter.go:96-106`）。

```go
// filter.go:82-92  按 Order 升序（插入排序）
for i := 1; i < len(sorted); i++ {
    for j := i; j > 0 && sorted[j].GetOrder() < sorted[j-1].GetOrder(); j-- {
        sorted[j], sorted[j-1] = sorted[j-1], sorted[j] } }
// filter.go:96-106  短路
for _, filter := range fc.filters {
    if resp := filter.Process(ctx); resp != nil { return resp } }
```

**这里做对了：** 注释直接写了为什么用插入排序 ——"过滤器数量少，不需要复杂排序"（`filter.go:83`）。3 个过滤器最多 3 次比较，为它引入 `sort.Slice` 的接口转换是净亏损。**这是一个正确的工程取舍，而且注释解释了取舍**，比"用了某某排序算法"更值得说。另一个加分细节：`NewFilterChain` 先 `copy` 一份再排序（`filter.go:84-85`），**没有修改调用方传入的切片**，避开了一个很隐蔽的别名 bug。

### 2.2 顺序反了的安全问题（必须讲透）

| 过滤器 | Order | 位置 |
|---|---|---|
| AuthFilter | 10 | `auth.go:38-40` |
| SecurityFilter | 20 | `security.go:57-59` |
| RateLimitFilter | 30 | `ratelimit.go:36-38` |

而两处注释都写着"认证 → 限流 → 安全校验"（`gateway.go:59`、`distributed.go:70`）—— **注释与实现相反，且反的方向正是安全方向**。

**机制：被安全拦下的请求不消耗任何限流令牌。** 攻击者只要构造「一定会被 SecurityFilter 拒绝」的 payload，就让请求止步于第 2 层，永远走不到第 3 层的 `TryAcquire()`（`ratelimit.go:47`）—— 限流对你无效。

被拦下之前服务端付出了什么？看 `security.go:61-101` 的检查顺序：① 长度检查 O(1)（`:70`，**注意是按字节不是按 rune**：4000 字节 ≈ 1333 个汉字，中文用户的实际额度是标称的三分之一）；② 5 条正则逐个 `MatchString`（`:23-34, 76-81`，RE2 单条线性无回溯灾难，但每条最多扫 4000 字节 → 最多 2 万字节扫描）；③ `strings.ToLower(message)`（`:91`，**分配一个新的 4000 字节字符串**）；④ 敏感词 4 个 `strings.Contains`（`:92-97`，1.6 万字节扫描）。合计约 **4KB 堆分配 + 3.6 万字节扫描/请求**，单核 5~20µs。听起来不多，关键在于：这条路径**完全不依赖下游**（不用 LLM、不用 Redis），攻击者可以把它打到任意 QPS，CPU 是唯一上限；每个这样的请求都**免费**（零令牌消耗），攻击者成本只有带宽；而真正做事的请求被 `userQps=10` 卡在 10 QPS —— **攻击者与正常用户争抢的不是配额，是 CPU**。

**怎么改：** 限流的用户维度需要 `ctx.UserID`，而 UserID 由认证产生（`auth.go:60`），所以正确顺序是 **Auth(10) → RateLimit(15) → Security(20)**，只把限流上移一位。再进一步：未认证流量不受用户维度约束（`ratelimit.go:53` 的 `ctx.UserID != ""` 条件），所以还需在认证之前加一层 **IP 粗粒度限流**（Order=5）。完整链路：`IP 限流 → 认证 → 用户/租户限流 → 安全过滤`。

### 2.3 统一错误码出口

映射集中在 `mapErrorCodeToHTTP`（`main.go:562-577`），语义基本正确：`UNAUTHORIZED→401`、`PROMPT_INJECTION/INVALID_INPUT/INPUT_TOO_LONG/SENSITIVE_WORD→400`、`TOO_MANY_REQUESTS→429`、`AGENT_NOT_FOUND/NOT_FOUND→404`。**这里做对了：** 错误码是稳定契约（前端不用解析文案），状态码集中映射，响应带 `processingTimeMs`（`main.go:432`），`writeJSON` 统一 Content-Type（`main.go:556-560`）。两个洞：① **`LANE_BUSY` / `SYSTEM_BUSY` 没有映射** → 落到 `default: 500`（`main.go:574-576`）。它们分别是排队超时（`distributed.go:97`）和本地等锁超时（`gateway.go:129`），是**明确的过载信号**，报 500 会让客户端以为请求写错了、让监控统计成服务端 bug —— 应该是 **503 + `Retry-After: 1`**；② **429 没带 `Retry-After` 头** —— 告诉客户端"你被限了"却不告诉它多久后可重试，客户端只能盲目重试，等于自己制造重试风暴。

## 三、限流：令牌桶的两个真 bug（实际是六个）

### 3.1 实现

```go
// ratelimit.go:95-107
func (l *TokenBucketLimiter) TryAcquire() bool {
	l.refill()                                   // ← 每个请求都调用
	for { current := l.tokens.Load()
		if current <= 0 { return false }
		if l.tokens.CompareAndSwap(current, current-1) { return true } } }
// ratelimit.go:110-127
func (l *TokenBucketLimiter) refill() {
	l.mu.Lock(); defer l.mu.Unlock()             // ← 全局串行点，无条件加锁
	now := time.Now().UnixMilli()
	elapsed := now - l.lastRefill.Load()
	if elapsed >= 1000 {                         // ← 整秒量化
		newTokens := (elapsed / 1000) * l.refillRate
		newCount := l.tokens.Load() + newTokens
		if newCount > l.capacity { newCount = l.capacity }
		l.tokens.Store(newCount)                 // ← 非 CAS 的裸 Store
		l.lastRefill.Store(now) } }              // ← 余数丢失
```

桶容量 = 速率（`ratelimit.go:27` 的 `NewTokenBucketLimiter(globalQPS, globalQPS)`），语义是"允许 1 秒突发"；每用户桶同构（`:69`）。参数 `globalQps: 1000`、`userQps: 10`（`stage3.yml:97-98`）。

### 3.2 每个请求都进全局 mutex

`TryAcquire` 无条件调 `refill()`（`:96`），`refill()` 无条件 `Lock`（`:111`），**然后在 99.9% 的调用里算一个减法就退出**（`:118` 的 `elapsed >= 1000` 不成立）。1000 QPS = **1000 次全局互斥/秒，其中约 999 次纯属浪费**。

**先把话说准，否则被追问"1000 次互斥有多贵"就露馅：** Go 的 `sync.Mutex` 无竞争时是一条 CAS（15~25ns），有竞争时走 semaphore 唤醒（0.5~2µs）。1000 次/秒最坏也就 **1~2ms CPU/秒（0.1%~0.2% 单核）**。**在 1000 QPS 下 mutex 本身绝对不是瓶颈** —— 不要编造性能灾难，面试官会算这笔账。真正的代价是三条：① **它把限流器退化成单核组件**，所有核心轮流抢同一条 cache line 的独占权，横向加核完全无效，上限是锁的争用吞吐（现在富余，但这是一条**会随 QPS 增长而封顶的曲线**，修复成本接近零）；② 它是 lost update 这个真 bug 的温床（3.3）；③ 临界区里做的判断（算一个减法）不值得加锁。

**三种做法（按推荐度）：** ① **快路径放锁外** —— 先 `lastRefill.Load()` 判断 `now-last < 1000` 就直接返回，99.9% 的请求零竞争，改动最小；② 用 `golang.org/x/time/rate`，官方实现、`Allow`/`Reserve`/`Wait` 语义齐全、支持 burst 与"允许欠账"（对 AI 服务很有用），而且**它把"补令牌"和"扣令牌"放在同一个临界区里，所以没有 lost update** —— **它不是无锁的，它是正确的，这是关键区别**；③ **分片**：把 userID 哈希到 `N = GOMAXPROCS` 个桶，每桶独立锁，争用降 N 倍，代价是全局限额 = 各片限额之和。

### 3.3 lost update 竞态

`refill` 的 `Load()`（`:120`）→ `Store()`（`:125`）之间**不原子**，而 `tokens` 同时被另一条路径的 CAS 扣减（`:103`）：

```
Goroutine A（refill，持锁）            Goroutine B（TryAcquire，无锁）
  current = Load() → 50
                                       Load()=50 → CAS(50,49) ✅ 实际 49
                                       Load()=49 → CAS(49,48) ✅ 实际 48
  Store(50+10 = 60)                                       ← B 扣掉的 2 个被抹掉
```

**后果：多退令牌 = 限流比配置更松 —— 安全语义上最坏的方向。** **窗口量化**：`Load` 到 `Store` 之间是一次加法、一次比较、一次 Store，十几纳秒，只有 GC STW / 抢占 / 缓存未命中能拉到 µs 级；1000 QPS 下撞上的概率在万分之一量级，**实际影响很小，必须主动承认**。但它的诊断价值远大于实际危害：这是"混用 atomic 和 mutex、却把 `tokens` 当作临界区外变量"的教科书症状 —— 作者的心智模型是"`tokens` 是 `atomic.Int64`，所以对它做任何操作都安全"，而**原子性（单个操作不可分割）不等于隔离性（复合操作不可分割）**。同一段代码用 mutex 保护写入、用 CAS 保护读取，是"一半锁、一半 CAS"，两套机制谁也没保护住谁。**修法只有两个方向，不能取中间**：全 CAS（`CompareAndSwap(current, newCount)` 失败就重读重算），或全锁（把扣减也放进 `mu`，正确但把 3.2 的性能问题变成真问题）。**正解是第一个，或者换成 `x/time/rate`（它选的是"全锁"，但临界区极短且用 `AllowN` 合并了判断与扣减）。**

### 3.4 整秒量化丢余数 → 实际速率低于配置值

`elapsed / 1000` 向下取整（`:119`）+ `lastRefill.Store(now)`（`:126`）→ **亚秒余数被永久丢弃**。设到达间隔 d 秒（d > 1s），每次补 `floor(d) × rate` 并重置时钟，于是 **实际速率 / 配置速率 = floor(d) / d**：

| 到达间隔 d | 1.1s | 1.5s | **1.9s** | 2.9s | 最坏 d→2⁻ |
|---|---|---|---|---|---|
| 实际速率 | 90.9% | 66.7% | **52.6%** | 69.0% | **50%** |

**"限流实际比配置更严"，最坏只有配置值的一半。** 比"更严"更糟的是：**它取决于流量到达模式，不可预测、不可复现、无法解释** —— 压测时（密集请求）速率正常，生产低峰期（稀疏请求）腰斩，而配置写的还是 1000。修法一行：`l.lastRefill.Store(now - elapsed%1000)`。（注意：这条和 3.3 是**方向相反的两个 bug** —— 丢余数更严、lost update 更松，不能互相抵消，也不能只修一个就以为对了。）

### 3.5 用户桶可被绕过 + sync.Map 无限增长

```go
// ratelimit.go:65-72
if v, ok := f.userLimiters.Load(userID); ok { return v.(*TokenBucketLimiter) }
limiter := NewTokenBucketLimiter(f.userQPS, f.userQPS)  // 满桶
f.userLimiters.Store(userID, limiter)                    // ← 无条件 Store，不是 LoadOrStore
```

这是 **check-then-act**：`sync.Map` 的 `Load` 和 `Store` 各自原子，**组合起来不原子**。同一用户的两个并发首请求都 Load miss，各自新建一个**满桶**（`ratelimit.go:89` 的 `tokens.Store(capacity)`），都 Store，后者覆盖前者 —— 配额凭空翻倍；更糟的情况是被覆盖掉的桶**已扣过 500 个令牌**，那 500 次扣减**全部作废**，配额一秒内从 510 变回 10 —— 攻击者只要并发打首请求就能反复把桶重置为满。**对照组就在隔壁文件**：`lane.go:102-109` 的 `GetOrCreateLane` 写的是 `actual, _ := m.lanes.LoadOrStore(...)` 并 `return actual.(*Lane)`（**用返回的实际值**），是正确形式。**同一个项目、同一个模式（sync.Map 做按 key 的惰性构造），一处对一处错** —— 这个对比比单纯指出 bug 有力得多：说明不是"不会"，是"没检查"。

**内存增长**：`userLimiters` 从不淘汰（`:17`，全文件无 `Delete`）。当前 UserID 只有 `"default-user"`（`main.go:257`），**所以现在不漏**；但一旦接入真实多租户（这正是 `apiKey → userId` 映射存在的意义），攻击者用无限多的 apiKey 就能让这个 map 无限增长，且 `sync.Map` 的 `Load` miss 成本随 key 数上升。修法：分片 map + `sync.RWMutex` + LRU 上限，或给用户桶加空闲 TTL。

### 3.6 所有用户共用 default-user 桶（**最致命**）

`main.go:255-259` 传的 `validKeys` 是 `map[string]string{gwConfig.APIKey: "default-user"}` —— 一个 key（`stage3.yml:93` 的 `"bitguide-demo-key"`）映射到常量 `"default-user"`；`auth.go:59-61` 把它写进 `ctx.UserID`。所以：

**`userQps: 10` 就是整个平台的真实吞吐上限，与用户数无关；`globalQps: 1000` 形同虚设。**

执行顺序是全局桶先扣（`ratelimit.go:47-50`，基本不触发）、用户桶后扣（`:53-59`，10 个令牌），有效吞吐 = `min(1000, 10) = 10 QPS`。叠加 §1 的时延公式，**稳态在途请求只有 10 × 10s = 100 个**，第 101 个直接吃 429 —— **没有排队机会，直接拒绝**。多实例更微妙：每个实例一份**本地**桶（`:26-28`），实际上限 ≈ **10 × 实例数** —— **扩容会静默放宽限流策略**：今天 1 个实例限额 10 QPS，明天扩到 4 个就变 40 QPS，配置文件一个字没改，而下游 LLM 会先感受到。修法：① `apiKey → userId` 从业务侧生成（现在写死一个 `default-user` 是为演示）；② **把限流策略从"每实例"提升到"每集群"**（§3.7 的 Redis 固定窗口正是为此存在，但它完全不生效）；③ `apiKey` 从 YAML 明文（`stage3.yml:93`）移入密钥管理，比对用 `subtle.ConstantTimeCompare`（`auth.go:59` 的 map 明文查表有理论上的时间侧信道 —— 要能说清"理论"在哪：Go 的 map 查找时间与哈希冲突路径有关，实测差异极小，所以优先级低）。

### 3.7 分布式限流是死代码

```go
// distributed.go:77-82
if dg.userQPS > 0 && req.UserID != "" {        // ← req.UserID 从未被赋值
```

`req` 是 `*GatewayRequest`，它有 `UserID` 字段（`filter.go:9`），但 HTTP 层是**手工**构造的：`main.go:404-409` 只填 SessionID/AgentID/Message/Token，**没有 UserID**；源头的 `ChatRequest`（`main.go:58-63`）**根本没有 `userId` 字段**；认证设置的是 `ctx.UserID`（`RequestContext.UserID`，`filter.go:49`）而非 `req.UserID`。全仓只有 `/api/v1/chat` 一个入口（`main.go:376`），所以 **`DistributedGateway.checkRateLimit` 永远不会被调用**。

这条推论的价值不在"发现死代码"，而在它**接出的因果链**：**§3.8 那个"固定窗口可能永久限流某个用户"的 bug 现在是埋着的雷 —— 一旦有人为了让 `userId` 生效而给 `ChatRequest` 加一个字段（哪怕只是顺手补全），分布式限流立刻上线，同时 §3.8 立刻生效，用户被永久限流且需人工 `DEL` key 才能恢复。** **bug 的严重性取决于它离被触发的距离** —— 这样讲比"这里有个 bug"的信息量高一个量级。（顺带：`ProcessWithUser`（`distributed.go:174-179`、`gateway.go:165-171`）也无调用方，HTTP 层只调 `activeProcessFunc`，`main.go:413`。）

### 3.8 固定窗口 Expire 非原子 + 错误被丢

```go
// client.go:162-172
count, err := c.client.Incr(ctx, key).Result()
if err != nil { return 0, err }
if count == 1 { c.client.Expire(ctx, key, ttl) }   // ← 返回值被丢弃
```

两条独立命令，中间有窗口：**第 1 条 `INCR` 成功、第 2 条 `EXPIRE` 失败**（连接抖动、Redis 主从切换、进程在这两句之间被 kill）→ **key 存在但没有 TTL**；下一次 `INCR` 返回 2，`count != 1`，**再也不会尝试设置 TTL**（`:168` 的条件）→ 计数只增不减、永远 `> qps` → **该用户被永久限流，恢复需要人工删 key**。而 `Expire` 的错误被静默丢弃（`:169` 没接收返回值），全仓无人感知。**标准修复是一条 Lua 脚本**（Redis 单线程执行 Lua，整段原子）：

```lua
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end
return n
```

**另一个必须主动交代的问题**：固定窗口本身在**窗口边界允许 2 倍突发**（1 QPS 的限额，00:00.999 打 1 个、00:01.001 又打 1 个，两个窗口各计 1，瞬时 2 QPS）。**而本项目同时存在两套算法**：本地令牌桶（`ratelimit.go:74-127`）、分布式固定窗口（`distributed.go:189-198`）—— **同一个用户在两种部署模式下被限制的速率语义不同**（单机能突发 10，分布式边界能突发 20）。修法：统一成 Redis+Lua 令牌桶，或用 GCRA（Redis Cell 的 `CL.THROTTLE` 一条命令）。

### 3.9 降级方向：限流 fail-open 是对的，但和锁路径不一致

`distributed.go:192-196`：Redis 出错返回 `true`（放行）。**fail-open 是对的决定**（限流是保护措施，失效时应优先保业务可用），但要能说出代价：**Redis 挂掉 = 限流完全消失**，而本项目**恰好没有并发闸门**（§7.2）。而 **Lane 锁路径是 fail-closed**（`client.go:137-141`，`TryLock` 出错返回 `false`），且是**最糟的那一种**：`acquireLaneLock` **死等 30 秒**（`distributed.go:203-220`）才返回失败。

**同一份 Redis 依赖、两条路径两种方向，其中一条还会挂 30 秒。** 正确的框架是按"失败会损失什么"决定：限流失效 → 失去保护 → **fail-open**（放行 + 打点告警，现状正确）；会话串行失效 → 数据错乱（两个请求同写一个会话）→ **fail-closed，但必须快速失败（1~2s 内 503）+ 熔断，而不是等 30s**。

**"30 秒"是这一节最需要被算清楚的东西：故障期间的资源占用 = 到达率 × 等待时间。** Redis 挂 30 秒、QPS=100 时：现状是 100 QPS 全部进入等待 → **3000 个请求同时在等 30s → 3000 个 goroutine + 3000 条 HTTP 连接**（服务端没有 `WriteTimeout`，不会主动掐连接）→ 30 秒后集中返回 503 → 客户端集中重试 → 第二波，**故障被延迟放大成自我 DoS**；正确做法是第一个请求用 100ms 发现不可用 → 熔断器打开 → **后续请求 0 延迟直接拒绝**，占用 = 1 个请求。熔断器最小实现：连续 5 次失败后直接拒绝，冷却 1s；冷却后放一个探测请求，成功则关闭，失败则冷却翻倍（1s→2s→…→30s 上限）。**不到 50 行，但它把"每个请求等 30 秒"变成"第一个等 100ms，其余零成本"。**

## 四、会话串行化：Lane（**项目的亮点，也是坑最密的地方**）

### 4.1 为什么需要"同一会话串行"

多轮对话的上下文是**读-改-写**的：`ChatWithSession` 从 `session.Memory` 构建 prompt（`base.go:232`、`base.go:306`），LLM 返回后再 `AddAssistantMessage`（`base.go:204`）。并发两个请求进同一会话：

```
请求 A                      请求 B
BuildMessages → [u1]        BuildMessages → [u1]     ← 都只看到 u1
LLM(u1)                     LLM(u1)
AddAssistant(u1→a1)         AddAssistant(u1→a2)     ← 两个回复都基于 u1
```

`ConversationMemory` 有自己的 `sync.RWMutex`（`conversation.go:38`，`AddInteraction` 在 `:86-97` 加锁），**所以不会数据竞争崩溃、也不会丢消息 —— 但结果是语义错乱**：历史变成 `[u1, a1, a2]`，LLM 下一轮看到"用户只说了一句，助手答了两遍"。**这个区分是本节最重要的一句话：并发安全（race-free）≠ 语义正确（serializable）。** `sync.RWMutex` 保证前者，Lane 是为了后者 —— 先说这句，面试官就知道你不是在背"加锁"两个字。

### 4.2 本地实现：CAS 抢占 + 50ms 轮询

```go
// lane.go:52-68
func (l *Lane) TryEnter() bool {                      // CAS: 0=IDLE → 1=PROCESSING
	swapped := l.processing.CompareAndSwap(0, 1)
	if swapped { l.queueSize.Add(1) }                 // 只在成功时 +1
	return swapped }
func (l *Lane) Leave() { l.processedCount.Add(1); l.processing.Store(0) }
// gateway.go:117-131
for i := 0; i < 600; i++ {                            // 50ms × 600 = 30s 上限
	if lane.TryEnter() { entered = true; break }
	time.Sleep(50 * time.Millisecond) }               // ← 轮询，且不看 ctx.Done()
if !entered { return ErrorResponse("SYSTEM_BUSY", "系统繁忙，请稍后重试") }
defer lane.Leave()
```

**这里做对了：** 用 CAS 而不是 mutex 抢占，语义是"**抢不到就走**"（非阻塞尝试）—— mutex 天生是阻塞语义，要做"试着抢一次、失败就做别的事"得用 `TryLock`；`LaneManager.GetOrCreateLane` 的 `LoadOrStore` + 返回实际值（`lane.go:102-109`）也是对的（对比 §3.5）。

**代价要算清：** ① **固定 50ms 轮询的平均额外延迟是 25ms**（唤醒时刻均匀分布）—— 对秒级 LLM 请求可忽略，这个量级判断是对的；② 等待者每分钟对同一个 `processing` 变量做 20 次 CAS，等待者数量 N 时压力是 **20N 次/秒** —— N=100 时是 2000 次/秒的 CAS 打在一条 cache line 上，**比 §3.2 的 mutex 还贵**（每次 CAS 都是一次 cache line 独占转移）；③ **不看 `ctx.Done()`**（`gateway.go:120-126` 循环体里没有 select）→ 客户端断开后 goroutine 继续空转最多 30 秒，占着一个 goroutine 和一条已死的连接 —— **对比分布式版：它看了 ctx（`distributed.go:213-215` 有 `select { case <-ctx.Done(): }`）。同一件事两种实现，说明本地版是早期版本，后来只补了分布式版**；④ **这不是队列，是争抢**：等待者的唤醒顺序由调度器决定，没有 FIFO 公平性，先到的可能一直输（饥饿）。对"同一用户自己串行发请求"可接受，但本项目的 `sessionID` 是**前端传入的**（`main.go:394-396`，不传就按 `UnixNano` 新建），多个前端共享一个 sessionID 时公平性就是真问题。

**口径要诚实**：`TryEnter` 只在成功时 `queueSize.Add(1)`（`lane.go:55`）且 `Leave` 不减（`:64-68`）→ `GetQueueSize()`（`:81-83`）返回的是**累计进入次数**，不是队列长度；而 `processedCount`（`:65`）也是累计完成数 —— **两个字段语义重复，且名字骗人**。相关死代码：`RemoveLane`（`lane.go:112-114`）与 `GetActiveLaneCount`（`:117-124`）无调用方；`metrics.ActiveLanes`（`pkg/metrics/metrics.go:47-51`）定义后**从未 `Set`** → Grafana 上永远是 0 —— **指标定义了但没打点比没有指标更危险：看板上有线，人会读成"没有并发"，而不是"没有数据"**。

### 4.3 分布式实现：SET NX PX + 100ms 轮询 + Lua 释放

```go
// client.go:136-159
ok, err := c.client.SetNX(ctx, key, requestID, ttl).Result()   // 出错返回 false
script := redis.NewScript(`
	if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1])
	else return 0 end`)                                        // ↓ 只有持有者能删
result, err := script.Run(ctx, c.client, []string{key}, requestID).Int64()
// distributed.go:201-221  ttl 默认 60000ms；maxWait=30s；interval=100ms
for time.Now().Before(deadline) {
	if dg.redisClient.TryLock(ctx, key, requestID, ttl) { return true }
	select { case <-ctx.Done(): return false; case <-time.After(interval): } }
```

**这里做对了（要夸得具体）：** `Unlock` 用 Lua 做 **compare-and-delete** —— 先 `GET` 比对 value 是否等于自己的 `requestID`，相等才 `DEL`。这防住了分布式锁的头号 bug：**持有者处理超时 → 锁自动过期 → 第二个请求拿到锁 → 第一个请求才姗姗来迟地 `DEL`，把第二个请求的锁删掉了**。没有这个比对，锁只是一个"限时占用标记"，可以被任意过期者误删。**这是"见过真实分布式锁长什么样"的代码。**

代价：100ms 固定间隔 → N 个等待者是 **10N 次/秒的 Redis `SET NX` 往返**，而且 `SET NX` 是**写命令**，全部由 Redis 单线程主循环串行执行 —— N=100 时是 1000 次写/秒的纯浪费。更好的是 `Pub/Sub` 唤醒（等待者零轮询）或**会话粘性 + 本地串行**（一致性哈希把会话钉到实例，根本不跨实例竞争 —— 全仓 grep `consistent|hashring|ketama` 零命中，没做）。

### 4.4 没有 watchdog 续期（**最容易被问倒**）

锁 TTL 默认 **60 秒**（`distributed.go:45-49` 兜底 + `config.go:94`）。一次请求要多久？项目没测过（§7.1），但可从代码推：ReAct 最多 10 轮（`base.go:296`），每轮一次 LLM 调用（`base.go:319`），本地 Ollama 7B 单轮几秒到十几秒 → **一次请求几十秒到几分钟，60 秒的 TTL 小于业务时长上界**。

```
T=0    请求 A 拿到锁（TTL 60s），开始 10 轮 ReAct
T=60s  锁自动过期（A 还在跑，它不知道自己已不是持有者）
T=60s+ 请求 B 对同一会话 SET NX 成功 → 两个请求并发进入同一会话  ← Lane 的保护完全失效
T=90s  A 完成，defer releaseLaneLock → Lua 比对失败（value 是 B 的）→ 不解锁 ✅
```

注意最后一行：**A 和 B 并发的那 30 秒里，Lane 存在的全部意义失效了**；`Unlock` 的 Lua 比对恰好保护了 B 的锁不被 A 误删（`client.go:147-153`）—— 但**保护锁 ≠ 保护数据**，A 早已把它的读写交错进 B 的会话。

**Redisson 的 watchdog（面试标准答案，四个要点）：** ① `lock()` 不显式指定 lease time 时默认 TTL 30 秒，同时启动 `ExpirationRenewal` 定时任务；② 定时任务每 `internalLockLeaseTime / 3`（10 秒）执行 Lua：**先校验锁的 value 是不是自己的，是则 `PEXPIRE` 续到 30 秒**，间隔取 TTL/3 留两次容错，解锁时取消任务；③ **续期必须校验持有者身份**，否则会"续别人的锁"；④ 最关键的性质：**续期任务属于持有者进程 —— 进程崩溃 → 续期停止 → 锁在 TTL 内自动释放。所以 TTL 的语义是"持有者失联检测窗口"，不是"业务超时"。** 代价：每个持有者一个后台 goroutine + 每 TTL/3 一次 Redis 命令（持有者数量 ≈ 活跃会话数，通常可接受）。

**修法（三层，缺一不可）：** ① **先给业务一个明确上界** —— 给 LLM 调用加 ctx 超时（比如 90 秒），让"最大执行时间"从"不知道"变成"90 秒"。**没有业务超时，"TTL 该设多少"这个问题是无法回答的**（当前 LLM 客户端完全没有超时：`pkg/llm/openai.go:42` 是光秃秃的 `&http.Client{}`，grep `Timeout` 在 `pkg/llm/` 零命中）；② **TTL ≥ 业务上界 + 余量**（如 120 秒）+ 续期 goroutine（每 40 秒续一次，脚本比对 value）；③ 更强的方案是 **fencing token**（Kleppmann）：每次成功获取锁让 Redis `INCR` 一把单调计数器，把返回值作为 **fence** 交给持有者，写入端**拒绝任何 fence 小于已见最大值的写入** —— 即使"锁过期后两个持有者并发"，**落后者的写入会被拒绝**，用数据侧的单调性最终解决"锁只能尽力而为"。**这套机制正好也能解决 §5.4 的陈旧回写（版本号就是一种 fence）。**

> **边界（主动说）**：本项目没有 watchdog、也没有 fencing —— 必须承认 **"Lane 在'单次会话交互 < 60 秒'的假设下工作正常，超出就会静默失效"，而这个假设我没测量过。**

### 4.5 客户端断开会卡满整个 TTL

`distributed.go:99` 的 `defer dg.releaseLaneLock(ctx, laneKey, requestID)` 用的是 `dg.Process(ctx, ...)` 传进来的 ctx，也就是 HTTP 请求的 `r.Context()`（`main.go:413`）。于是：**客户端断开 → ctx 被 cancel → `Unlock` 里的 `script.Run(ctx, ...)` 立刻返回 `context.Canceled` → `Unlock` 返回 false（`client.go:155-158`）→ 日志只打 Debug（`distributed.go:226`）→ 锁留在 Redis 里直到 60s TTL 到期。** 一个用户刷新页面就能锁死自己的会话 60 秒；后续请求在 `acquireLaneLock` 里等满 30 秒才返回 `LANE_BUSY` → 落到 `default: 500`（§2.3）—— 用户看到"服务器内部错误"，其实是"你自己的会话被你刚才那次刷新锁住了"。

**修法（原则：清理路径绝不能用会被取消的 ctx）：**

```go
defer func() {
	releaseCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 2*time.Second)
	defer cancel()
	dg.releaseLaneLock(releaseCtx, laneKey, requestID) }()
```

`context.WithoutCancel` 是 Go 1.21+ 标准库（`go.mod:3` 声明 `go 1.23.0`，可用）：**保留 ctx 里的 value（trace/日志关联），但剥离取消信号**。顺带说明为什么这不矛盾：解锁是**幂等且短小**的操作（一条 Lua），不需要背压 —— 而这正是 §5.5 里"业务路径用 `Background` 丢取消传播是错的"的对照：**同样的 `context.Background()`，在清理路径上正确，在业务路径上错**（`memory/distributed.go:67,94` 的两个 3 秒超时属于后者）。

### 4.6 requestID 用 UnixNano，跨实例不唯一

`distributed.go:91` 的 `requestID := fmt.Sprintf("%d", time.Now().UnixNano())` 同时是"锁的所有权凭证"和"解锁的比对值"，**锁的正确性完全依赖它的唯一性** —— 一旦 A 和 B 生成相同 requestID，A 的解锁脚本会匹配到 B 的锁并删掉，两个请求同时进入同一会话。`UnixNano` 在多机场景**两条要求都不满足**：① **唯一性** —— NTP 校时（尤其容器启动时的一次性跳变）会让两台机器的纳秒时间戳重合，概率不高但**不是零，而且无法通过测试发现**；② **不可预测性** —— 时间戳可猜，猜中 value 就等于能删别人的锁。修法：UUIDv4，或 **`{instanceID}-{本地单调计数器}`**（`instanceID` 来自 Pod 名或启动时随机串，计数器用 `atomic.Int64`）—— 后者还额外带来**可读**（日志能看出哪个实例持锁）和**零成本**（不引入 UUID 依赖）。

## 五、Redis 与分布式记忆

### 5.1 连接池完全没配

`pkg/redis/client.go:25-33` 的 `redis.NewClient` 只设了 `Addr/Password/DB`（`Config` 结构体只有这三个字段，`:18-22`），全仓没有 `PoolSize` / `MinIdleConns` / `PoolTimeout` / `ConnMaxIdleTime` / `ReadTimeout` / `WriteTimeout` 的任何设置。走 go-redis v9 默认值：**`PoolSize = 10 × GOMAXPROCS`、`MinIdleConns = 0`、读写超时 3s、`PoolTimeout` ≈ 读超时+1s、`ConnMaxIdleTime` 30 分钟**。

**先算清池子该多大（这是这道题的全部价值）** —— 又是利特尔法则，这次算**连接**：**所需连接数 L = 每秒命令数 λ_cmd × 单条命令耗时 W_cmd**。本项目的每请求 Redis 命令数：`SET NX`（抢锁，`distributed.go:208`）= 1；Lua `GET`+`DEL`（放锁，`:225`）= 1；`GET`（读会话，`memory/distributed.go:71`）= 0~1（本地命中则 0）；`SET`（写会话全量 JSON，`:102`）= **1~2**（用户消息 + 助手回复各一次）；`INCR`（分布式限流，`distributed.go:192`）= **0（死代码）**。合计约 **3~5 条**。按 1000 QPS 算 = 5000 命令/秒；同机房往返 0.2~0.5ms → `L = 5000 × 0.0003 ≈ 1.5`。

**结论：默认的 `10 × GOMAXPROCS`（4 核机器上 40）远超需求，所以这个"没配"在当前规模下不是事故** —— 必须诚实说出这一点，再讲两个真正的风险：① **默认值随 GOMAXPROCS 漂移**（`--cpus=2` 的容器里是 20，64 核裸机上是 **640**），而 Redis `maxclients` 默认 10000，多实例 × 640 会顶到上限；更实际的危害是**连接数不影响吞吐** —— Redis 是单线程，把池子从 40 提到 400 只增加 epoll 轮询和内存（server 端每条连接约 10~20KB），不提高任何吞吐，**池子大小由"命令数 × 时延"决定，不是越大越好**；② **`MinIdleConns = 0` + `ConnMaxIdleTime` 未设** —— 前者意味着流量低谷后第一个请求要付一次 TCP 三次握手（同机 ~50µs、跨机 ~0.5ms，可接受但没必要）；后者意味着空闲连接**永不回收**，而上游 NLB / 云防火墙 / 容器网络各有 idle timeout（常见 60~350s），它们会**静默**回收连接，客户端下次复用这条"僵尸连接"时才收到 RST → 偶发 `EOF` / `connection reset by peer`，**这是分布式系统里最经典的"每月一次、无法复现"故障来源**。

```go
redis.NewClient(&redis.Options{
	Addr: ..., Password: ..., DB: ...,
	PoolSize:        2 * 预期并发峰值,   // 或按上面公式算完取整、留 2 倍余量
	MinIdleConns:    PoolSize / 4,      // 预热，消除冷启动握手
	PoolTimeout:     1 * time.Second,   // 池满时快速失败，而不是挂 4s
	ReadTimeout:     1 * time.Second,   // RPC 语义下 3s 太长，会拖长故障时的雪崩
	WriteTimeout:    1 * time.Second,
	ConnMaxIdleTime: 5 * time.Minute,   // 小于上游 idle timeout
	ConnMaxLifetime: 30 * time.Minute,  // 配合下游主从切换，让连接有机会重建
})
```

**还有三个结构层面的缺失，比参数更重要：** ① **没有 TLS 选项**（生产跨网段必须 TLS）；② **没有 Sentinel / Cluster 配置项**（`Config` 只有单个 `Addr`）→ **没有主从切换路径，Redis 是单点** —— 也就是说整个平台的分布式能力建立在一个没有 HA 的 Redis 上；③ **没有熔断器**（§3.9）。

### 5.2 全量 JSON SET vs 增量

`memory/distributed.go:93-105` 的 `saveToRedis` 每次记录一条消息，就把**整个会话快照**（`:97-100` 取 `GetHistory()` 全量 + `GetVariables()`）序列化成 JSON 然后 `SET` 全量覆盖，失败只 `clog.Error`。没有 Hash、没有 List、没有压缩、没有分页、**没有 value 大小检查**。

**算一下成本**：`maxSize = 50`（`stage3.yml:46`），一条中文回复 500 字 ≈ 1.5KB UTF-8 → 50 条历史 ≈ **50~75KB 的 value**；每轮对话至少写两次（`distributed.go:103` 用户消息 + `:166` 助手回复）→ 1000 QPS 下是 **50~75MB/s 的 Redis 写流量**，每次写都是一次 50KB 的分配 + 序列化 + 网络输出。**写入成本是 O(历史长度)，而它本该是 O(1)。**

修法（按性价比）：① **`RPUSH` + `LTRIM` 增量追加** —— 写一条从 `O(N)` 变 `O(1)`，List 两端操作 O(1)，`LTRIM` 让内存有界，**这一条就能把写流量降一到两个数量级**；② **Hash 存储**（`HSET session:{id} msg:{seq} <json>`，元数据放独立 Hash）；③ **value 大小上限检查**（现在完全没有）—— 一条 1MB 的超长回复会让 value 直接到 1MB 级，**Redis 侧不会拦（`proto-max-bulk-len` 默认 512MB），但大 key 的危害在别处：`DEL` 是同步的，删除 1MB 的 value 会阻塞事件循环，AOF rewrite / RDB fork 的 COW 会放大内存** —— 工程经验值是**单 value > 10KB 就要关注，> 1MB 就是大 key**，所以要在写入侧截断而不是指望 Redis 拦；④ 压缩（最后考虑）—— 50KB 中文 JSON 用 zstd 能压到 ~15KB，但换来每次读写的 CPU，**只有网络带宽是瓶颈时才值得**，而这里的瓶颈是命令次数和 value 大小，不是带宽。

### 5.3 只写不读（**最致命的短板，必须主动先说**）

实际用到哪份历史：`base.go:232`（chatDirectly）与 `base.go:306`（chatWithTools）都调 `session.Memory.BuildMessages(...)`，而 `session` 是 `BaseAgent.sessions sync.Map`（`base.go:31`）里的**实例本地**对象。而 `DistributedMemory.BuildMessages`（`memory/distributed.go:135-138`）**全仓没有调用方**（只有定义），`GetHistory`（`:129-132`）同样没有生产调用方。**Redis 里存着完整的会话快照，但从来没有人读它来构造 prompt。** 更微妙的是 `GetOrCreate` 确实会从 Redis 恢复（`distributed.go:71-82`），但那**只在 `RecordUserMessage`/`RecordAssistantResponse` 内部被调用**（`:108-118`）—— 恢复出来的 `ConversationMemory` 只用来"继续往 Redis 写"，**LLM 依然看 `BaseAgent` 那份本地历史**。**同一份对话在两个地方各存一份，只有一份（本地的）被读。**

**端到端后果：** ① **换个实例访问同一会话 → LLM 看不到任何历史**（滚动发布、K8s 重新调度、负载均衡换 Pod、进程重启），用户感觉"AI 失忆了"；② Redis 里的会话数据目前是**纯成本** —— 每请求 1~2 次 50KB 写 + 序列化，换来零收益，**这是最该被裁掉或接回去的代码**。

| 修法 | 做法 | 代价 | 解决什么 |
|---|---|---|---|
| ① Redis 为唯一数据源 | 把 `DistributedMemory.BuildMessages` 通过接口注入 `BaseAgent`；本地只留**短 TTL 读缓存**（1~5s），写时失效本地缓存 | 每请求多一次 Redis 读（~0.3ms，可接受）；读-改-写必须靠 Lane 串行保护（现有锁够用，**前提是 §4.4 的 TTL 问题修掉**） | 换实例/重启后历史不丢 |
| ② **本地为主 + 会话粘性** | 正常路径全走本地（零 Redis 读）；加"会话归属实例"记录（如 `SET session:owner instanceID`），检测到会话不在本实例时才从 Redis 拉 | 需要一致性哈希或归属表 + 会话迁移逻辑 | 历史不丢，**且顺带解决 §5.4 的陈旧回写** |

②更强：它把"跨实例并发写"换成"同一实例写"，从根上消除缓存一致性问题 —— 这正是会话粘性在 Agent 系统里比在 Web 里更值得做的原因（单请求耗时长，跨实例争用窗口也长）。**主动交代的答法：** "我们的分布式记忆只实现了写侧、读侧没接回 LLM 上下文，所以它的实际作用是'会话备份'而不是'分布式会话'。原因是接回读路径时发现需要一个版本/粘性机制来防陈旧回写，那一步没做完。"

### 5.4 陈旧缓存回写导致消息丢失

两级缓存是"本地 `sync.Map`（热）+ Redis（持久化）"（`distributed.go:14-24`），但**本地缓存永不过期**：TTL 只设在 Redis key 上（`:46`），`localCache`（`:20`）没有任何 TTL 或失效逻辑。

```
A 实例：localCache[s1] = V1（历史 10 条）
B 实例：拿到 Lane 锁，写入 V2（历史 12 条）到 Redis
A 实例：再次拿到 Lane 锁，用自己那份 V1 全量 SET → Redis 回到 10 条
        → B 的两条消息永久丢失，且无错误、无日志、无指标
```

**为什么 Lane 锁没救回来？因为锁只保证"同一时刻只有一个写入者"，不保证"写入者手里的数据是最新的"。串行 ≠ 一致。** 这是很多人对分布式锁的误解：锁解决**互斥**（mutual exclusion），缓存一致性解决**可见性**（visibility）—— 两个独立的问题，需要两套机制。修法（按强度）：① **版本号 / 乐观锁**（value 带 `version`，写入用 Lua 比对，冲突则重读重试；**版本号本身就是轻量 fencing token**，能和锁超时问题一起解决）；② **`WATCH` + `MULTI/EXEC`**（Redis 原生乐观锁，go-redis 支持，语义更严谨但实现成本更高）；③ **写完就 `DEL` 本地缓存**（最简单，但退化成"每次请求都从 Redis 读"，等价于 5.3 方案①）；④ **会话粘性**（问题从根上消失）。

### 5.5 Redis 挂了是静默失败（三个层次）

**① 写路径静默丢。** `saveToRedis` 失败只 `clog.Error`（`distributed.go:102-104`），而 `RecordUserMessage`/`RecordAssistantResponse` 没有返回值（`:108-119`）—— 错误在这一层被吞掉，调用方（`distributed.go:103,166`）无从感知 → **请求照样 200 返回，用户以为历史保存了。**

**② 读路径静默降级 + 数据损坏（最狠的一条）。** `memory/distributed.go:71-85` 是 `if err := GetJSON(...); err == nil { 恢复历史 } else { 新建会话 }` —— **「key 不存在」和「查询失败」被合并处理**：Redis 超时、连接被拒、认证失败全部走 `else` → 新建**空会话** → 紧接着 `saveToRedis` 把这个空会话**全量写回 Redis，覆盖掉原来那份完好的数据**（`distributed.go:111`/`:118`）→ **Redis 抖一下 = 用户历史被清空，而且这个清空被持久化。** 这是全项目唯一一处"故障升级为数据损坏"的路径，严重性高于其他所有并发问题。修法：**区分"查不到"和"查失败"** —— `GetJSON` 透传 go-redis 的错误（`client.go:126-132`），所以 `errors.Is(err, redis.Nil)` 可判别：`redis.Nil` 时新建空会话（正常路径），其他错误时**返回错误让上层拒绝这个请求**（fail-closed），**绝不允许在"不确定数据是否存在"的情况下写入**。一行 `errors.Is` 就能封掉这条路径。原则：**永远不要把"没有数据"和"取不到数据"当成同一件事。**

**③ 锁路径 fail-closed 但方式糟糕。** `client.go:137-141` 的 `TryLock` 出错返回 false → `acquireLaneLock` 死等 30 秒（`distributed.go:203-220`），数字已在 §3.9 算过：**Redis 挂 30 秒、100 QPS = 3000 个请求同时挂 30 秒，故障被放大成自我 DoS。**

| 路径 | 出错行为 | 问题 |
|---|---|---|
| 分布式限流（`distributed.go:192-196`） | fail-open（放行） | 方向对，代价是"Redis 挂了等于没限流" |
| 会话读（`distributed.go:71-85`） | **fail-silent**（当成不存在） | **最危险：故障升级为数据损坏** |
| Lane 锁（`distributed.go:203-220`） | fail-closed + **等 30 秒** | 方向对、形态错（应快速失败） |

**正确答案是把三者对齐到一套规则**：读路径 fail-closed（无法保证正确性就拒绝）、写路径要么成功要么显式报错（不能静默丢）、保护性能力 fail-open，**并且所有 fail-closed 路径都必须快速失败 + 熔断**。附带一条：`GetOrCreate`/`saveToRedis` 用 `context.Background() + 3s`（`distributed.go:67,94`）**丢了取消传播** —— 客户端断开了 Redis 调用照跑最多 3 秒，危害不大（有界），但原则是**业务路径用 Background 就丢了背压**。

### 5.6 健康检查撒谎

`main.go:328-337` 的 `RedisConnected: cfg.Redis.Enabled` 读的是**配置开关**，不是 `Ping` 结果 —— Redis 挂了 `/health` 依然返回 `{"status":"UP","redisConnected":true}`。唯一的真实探测是启动时那一次 `Ping`（`main.go:284-286`），**之后再也不探**。后果链：K8s 探针依赖 `/health` → 探针永远成功 → **流量不会被摘掉** → 请求继续打到 Redis 已不可用的实例 → **§5.5 的三条静默失败路径全部命中**。

修法：① `/health` 做**真实**依赖探测，并且**区分 live 和 ready** —— `live`（liveness）：进程活着就 200，只有死锁/永久阻塞才该失败，**绝不能把依赖检查放进 liveness**，否则 Redis 一抖所有实例一起重启，把局部故障放大成全局故障；`ready`（readiness）：Redis `PING` + etcd 一个轻量 `Get`，失败就摘流量、不重启进程。② **探针结果要缓存**（1 秒 TTL）：K8s 每 10 秒一次探针，每次一次 Redis 往返可接受，但没必要在并发探针上各打一次。③ **LLM 不该进探针**：一次真推理太贵，且 LLM 抖动时摘掉所有实例是灾难。

**还有一个反模式要单独说**：`main.go:326-327` 在 `/health` 里 `metrics.ActiveSessions.Set(...)` —— **用健康检查驱动指标采集**，探针频率变了指标就失真（探针停了 Gauge 就永远停在旧值）；而且 `gw.GetStats()`（`gateway.go:260-272`）内部是 `sync.Map.Range` 全量遍历 `sessions` → **O(会话数) 的开销放进了高频探针**，会话数 10 万时每次探针遍历 10 万个 entry。**健康检查应该 O(1) 且无副作用**，指标采集应该独立（定时器或事件驱动）。

### 6.1 观察者模式

接口 + 切片，10 行实现发布-订阅：`listener.go:4-7` 定义 `ConfigChangeListener`；`watcher.go:38-40` 的 `AddListener` 直接 `append`（**无锁**）；`watcher.go:194-198` 的 `notifyListeners` **在 watch goroutine 里同步遍历回调**。**这里做对了：同步回调（而不是 channel）带来天然背压**（慢监听器直接拖慢 watch），但代价是"一个监听器卡住 = 所有人收不到事件"（§6.4 会引爆）。`listeners` 的无锁读写**当前安全**：全仓只有一个监听器（`manager.go:89` 的 `AddListener(m)`），且它发生在 `Start` 之前（`manager.Init()` 里先 `AddListener` 再 `Start`，`manager.go:87-98`；`main.go:239` 调用）—— goroutine 启动提供了 happens-before。**但接口本身没有任何约束**：任何人在 `Start` 之后 `AddListener`（比如加一个审计监听器）就是数据竞争。修法：加 `sync.RWMutex`，或用注释/断言固化"必须在 Start 前注册"。

### 6.2 watch 出错永久退出、静默失效（**最容易被追着打**）

```go
// watcher.go:119-142
watchChan := w.client.Watch(w.ctx, prefix, clientv3.WithPrefix())   // ← 没有 WithRev
for {
	select {
	case <-w.ctx.Done(): return
	case watchResp, ok := <-watchChan:
		if !ok { return }                                  // ← 出口 1：channel 关闭
		if watchResp.Err() != nil {
			clog.Error("[Dynamic]", "监听到配置变更事件失败: %v", watchResp.Err())
			return                                          // ← 出口 2：直接退出，永不重连
		}
		for _, event := range watchResp.Events { w.handleEvent(event) } } }
```

**两个出口都是 `return`，之后什么都没有**：没有重连、没有状态标记、没有指标、没有告警。`Start()` 时打印的"开始监听配置变更"（`watcher.go:90`）是日志里最后一次提到 watch 的地方。**配置热更新从此静默失效，而进程一切正常。**

**为什么 etcd compaction 会让 watch 永久失败（讲清机制）：** etcd 用 MVCC 保留有限个 revision（`--auto-compaction-retention`，服务端默认 1 小时或最近 1000 个 revision，托管服务常配 5~60 分钟）；watch 的语义是"从 revision R 开始把之后的每个变更推给我"，如果客户端**落后得比 compaction 更远**（网络分区、长 GC 停顿、channel 缓冲满导致服务端发送阻塞），那么 R 对应的历史已被删除、**变更无法补发**，etcd 只能返回 `ErrCompacted` 并终止 watcher。**这时唯一正确的做法是从"当前最新 revision"重新做一次全量 `Get`，再用新 revision+1 重新 `Watch`** —— 即 **"重连 + 全量对账"**：配置是**幂等且小**的，全量对账的成本远低于逐事件补偿，且天然覆盖所有丢失场景（不只 compaction）。

**怎么观测（现在一个都没有）：** `bitguide_etcd_watch_alive`（Gauge 0/1，**最重要的一个**，直接暴露静默失效）、`bitguide_etcd_watch_restarts_total`（Counter，突发上升说明 etcd 不稳）、`bitguide_etcd_last_event_timestamp_seconds`（长期不动 = 可疑）、`bitguide_etcd_config_version`（当前 revision，与 etcd 实际值对比能发现落后）。**"静默失效"最危险的不是失效本身，是没有任何观测量**；这四个指标不到 20 行代码，而 `watch_alive` 应该进 **ready** 探针 —— 一个"配置陈旧"的实例和一个"配置正确"的实例对同一请求会给出不同答案，这在多实例部署里是最难排查的 bug。

**自愈实现：** 外层 `for w.ctx.Err() == nil { if err := w.watchOnce(prefix); err != nil { 打点 + 指数退避 100ms→30s 上限 + jitter 防惊群; continue } }`，**重连后必须做全量对账**（`Get` 全量 → 与 `w.cache` diff → 补发差异事件，复用 `handleEvent` 的幂等），否则只是把"永久失效"换成"短期失效"。

### 6.3 Get 与 Watch 之间丢事件（没带 `WithRev(rev+1)`）

`loadAllConfigs`（`watcher.go:95-116`）拿到 `resp, err := w.client.Get(...)` 并用 `resp.Kvs`，**但丢弃了 `resp.Header.Revision`**；`Start` 在它返回后才 `go w.watch(prefix)`（`watcher.go:82-88`）；而 `watch` 里的 `Watch(...)` **没有 `WithRev`**（`:122`）。**窗口**：`Get` 返回时等价于 revision R，从 `Get` 返回到 `Watch` 真正在 etcd 服务端建立订阅，中间隔着一次网络往返 + 客户端处理 + goroutine 调度（毫秒到秒级）—— 这期间发生的 PUT/DELETE 落在 `(R, 当前 rev]` 区间，而**不带 `WithRev` 意味着从"订阅建立那一刻"开始推事件，中间那些变更永远不会被通知到** → **永久性配置漂移**：etcd 里有新配置，进程里没有，而进程会一直"正常"运行下去。

**标准做法（etcd 官方 "watch from revision" 模式）：**

```go
resp, err := cli.Get(ctx, key, clientv3.WithPrefix())
wch := cli.Watch(ctx, key, clientv3.WithPrefix(), clientv3.WithRev(resp.Header.Revision+1))
```

**为什么是 `rev+1` 而不是 `rev`**：`WithRev(rev)` 会把 revision 恰等于 rev 的那个事件重发（若 rev 对应一次写入）→ 重复通知，从 rev+1 开始才是"`Get` 之后的新变更"；更稳的是 rev+1 + 幂等 —— **而本项目恰好有幂等（`handleEvent` 对同值 PUT 跳过，`watcher.go:158-163`），值得夸**：它把"重复事件"从正确性问题降级成性能问题。**边界（避免过度指控）**：`w.cache[key] = value` 在 `loadAllConfigs` 里（`watcher.go:108`）没加锁，但它发生在 watch goroutine 启动**之前**，goroutine start 提供 happens-before，**所以这里没有数据竞争**。

### 6.4 watch 回调里做重活 → 阻塞 watch 循环

`notifyListeners` 同步在 watch goroutine 里执行（`watcher.go:194-198`）→ `OnConfigChange`（`manager.go:101-117`）→ `handleAgentConfigChange`（`manager.go:120-140`）→ `registry.Register/Update` → `factory.CreateAgentFromConfig`。**而它会建 MCP 连接**，`stage3.yml:31-35` 配的是 `command: go` / `args: ["run", "mcp-servers/parenting/main.go"]` —— **`go run` 要现编译再执行，几百毫秒到几秒**。于是：

```
watch 循环停止消费事件 → etcd 事件在 clientv3 的 channel 缓冲里堆积
→ 缓冲满后 etcd 服务端发送被阻塞 → 触发 "server-side buffer full" → watcher 被取消
→ watchResp.Err() != nil → return → §6.2 的永久退出
```

**这是两个 bug 连锁放大的例子（局部设计缺陷 + 无重连 = 永久失效）** —— 讲成一条链比分别讲两个 bug 有价值得多。**只在一个地方做对了**：`handleKnowledgeBaseConfigChange` 里的文档摄取用了 `go func(){...}()` 异步（`manager.go:188-198`），说明作者意识到"索引构建慢"；**但 Agent/MCP 那条更慢的路径反而是同步的**，而且文档摄取是"无界 goroutine + 无重试 + 无对账"，灌失败只 `clog.Warn`（`manager.go:193-197`）。另外 `WatchQueueSize: 100`（`stage3.yml:61`、`config.go:107`）**代码从未读取** —— 用户以为调它就调了缓冲，实际没有。

**修法（四层）：** ① **回调改成"入队 + 独立 worker"**（`select { case w.events <- event: case <-w.ctx.Done(): }`，有界 channel，满了明确拒绝并打点，而不是无限排队）；② 慢操作（建 MCP、灌向量库）全部异步 + 有界 + 幂等对账；③ **`recover()` 包住每个回调** —— 全仓 grep `recover()` **零命中**，所以监听器里任何 panic（比如 §6.5 的裸 map 并发写）都会**让整个进程崩溃**（比"杀掉 watch 协程"更严重：Go 里未 recover 的 panic 终止进程，不只是那个 goroutine）；④ 重连 + 全量对账（§6.2）兜底。

### 6.5 配置零校验

`manager.go:241-252` 的 `parseAgentConfig` 只判 JSON 合法性就 `return &cfg`，**零字段校验**（`handleAgentConfigChange` 只判 `cfg != nil`，`manager.go:127,133`）。能被推上去的坏值及后果：

| 坏值 | 后果 |
|---|---|
| `temperature: 999` | 后端 400，或被截断到合法区间 —— 静默用错参数 |
| `maxTokens: -1` | 未定义行为 |
| `modelRef: "不存在的模型"` | `GetClientForModel` 回落到 `defaultClient` → **静默用了错误的模型** |
| `systemPrompt: ""` | Agent 变成没有角色的裸模型 |
| **`mcpServers: [{transport:"stdio", command:"任意命令", args:[...]}]`** | **见下 —— 最严重** |

**`mcpServers` 是配置注入 = 远程命令执行。** `stage3.yml:31-35` 里 `command` 是 `go`、`args` 是 `["run", ...]` —— 配置文件可以指定任意可执行命令和参数，服务端会 fork 它。**谁有 etcd 的写权限，谁就有在服务端执行任意命令的权限。** 修复顺序：**① etcd RBAC 收紧写权限（首要 —— 这是权限边界问题，不是代码问题）**；② `command` 白名单；③ 写入侧 admission 校验（推送前验证，而不是消费侧丢弃）。

**静默忽略坏值**：`parseAgentConfig` 返回 nil → 被 `if cfg != nil` 跳过 → **etcd 里的坏值一直留着**，下次重启仍读它、仍失败、仍只打一行日志。这里有一个**意外的正确性**值得指出：坏值被忽略 == 保留上一版有效配置（旧 Agent 实例还在），**所以进程不会因为一个坏配置而失效** —— 但要补三件事才完整：**告警**（不能只有日志）、**审计**（谁推的、何时）、**可视**（`/api/v1/agents` 里标注"配置解析失败，使用上一版"）。**"静默忽略"和"显式拒绝并告警"的区别就是能不能发现问题。** 校验清单：`temperature ∈ [0,2]`、`maxTokens > 0` 且 ≤ 模型上限、`modelRef ∈ 已注册模型`（`LLMGateway.ModelRefs()`）、`systemPrompt` 非空、`mcpServers[].command` 白名单、**`ID` 与 etcd key 一致**（`agentID` 来自 key 解析 `event.go:81`，`registry.Register(agentID, cfg)` 用 key 的 ID 而 `cfg.ID` 只出现在日志里 → 会出现"key 是 A、Agent 自报 ID 是 B"的状态，不一致应直接拒绝）。

**两个解析层的问题：** ① **`parseKey` 硬编码 `parts[3]/parts[4]`**（`event.go:73-84`）—— key `/bitguide/config/agents/x` split 后是 `["","bitguide","config","agents","x"]`；多一级的 key（`/bitguide/config/agents/team1/agent1`）会解析出 `configID = "team1"` 且**不报错**，静默把团队目录当成 Agent ID。修法：校验 `len(parts) == 5` + configType 白名单 + 前缀匹配。② **默认前缀不一致**：`watcher.go:77-79` 默认 `/bitguide/config/`，`stage3.yml:58` 用 `/bitguide-go/config/`（靠显式配置对齐）—— **漏配就静默监听不到任何东西**：`Start()` 成功、`loadAllConfigs` 返回 0 条（日志打"加载配置数量: 0"，`watcher.go:114`）、然后 watch 一个空前缀永远没事件，**热更新整体失效但没有任何错误**。修法：默认值改成与部署一致，或干脆要求 `ConfigPrefix` 必填（漏配直接启动失败）—— **默认值的意义是"大多数情况下对"，当它和部署不一致时，默认值就从便利变成了陷阱。**

### 6.6 Agent 热更新的引用计数（**全项目最值得讲的设计**）

**要解决的问题：** 朴素的替换是 `entries[id] = newEntry` 然后立刻 `oldAgent.Close()`，但 `Close()` 会清会话记忆（`base.go:215-221`）、`factory.DestroyAgent` 会断 MCP 连接（`registry.go:137-140`）—— **正在用旧实例的请求会踩到已关闭的资源**（工具调用失败、历史丢失）。这是 Go 里"对象被替换但还有人在用"的经典问题，也是所有热更新系统的第一个坑。

```go
// registry.go:24-40  AgentEntry 带引用计数 + 标记位
refCount atomic.Int32; marked atomic.Int32          // :28-29
func (e *AgentEntry) acquire() bool {
	if e.marked.Load() == 1 { return false }        // ← check
	e.refCount.Add(1); return true }                // ← then act（TOCTOU 窗口）
// registry.go:154-199  doUpdate：标记旧 → 创建新 → 替换 → 异步等旧引用归零
oldEntry.markForDeletion()                                   // :176 阻止新请求 acquire
newAgent, err := r.factory.CreateAgentFromConfig(newConfig)  // :179
if err != nil { oldEntry.marked.Store(0); return false }     // :182 ← 回滚！加分项
r.entries[agentID] = &AgentEntry{Agent: newAgent, ...}       // :187-191
go r.gracefulDestroy(oldEntry, agentID)                      // :196 ← 异步
// registry.go:202-229  gracefulDestroy → waitForRelease
timeout := 5 * time.Second                                   // :218
for time.Now().Before(deadline) { if entry.refCount.Load() <= 0 { return }; time.Sleep(interval) }
clog.Warn("[Agent]", "等待引用计数归零超时 (refCount=%d)，强制销毁", ...)   // :228
```

请求侧（`gateway.go:99-115`、`distributed.go:123-136`）：`AcquireRequest()` 失败就取 `registry.GetEntry` 换最新实例重试，`defer ReleaseRequest()`。

**它解决了什么（要讲成"这是对的"）：** ① **一个请求全程只看到同一个 Agent 实例**（不会前 3 轮旧、后 2 轮新）；② **旧实例的资源在没有请求再用它之后才释放** —— 这是"引用计数 + 延迟销毁"的标准形态，和 `sync.WaitGroup`、`http.Server.Shutdown` 是同一个思想（等计数/在途归零）；③ **创建失败会回滚**（`registry.go:182`）—— **很多人会忘这一步**，忘掉的后果是一次失败的更新（比如 MCP Server 暂时连不上）让这个 Agent **永久不可用**（所有新请求 acquire 都返回 false），而 etcd 里配置是对的、日志里看不出来；**"失败路径要恢复不变量"是热更新系统里最容易漏的一半**；④ 配置未变化时跳过更新（`configEqual`，`:96-99`、`:344-371`），避免重复推送导致实例重建。

**必须自己先说的五个瑕疵：**

**① TOCTOU 窗口：`acquire()` 是 check-then-act。** 若 T1（读 marked = 0）和 T2（`refCount.Add(1)`）之间另一个 goroutine 执行了 `markForDeletion()`，而 `waitForRelease` 在 `:222-227` 读到 `refCount <= 0`（T2 还没执行）→ 判定"没人用了" → **立即销毁旧实例**，而 T2 马上要 +1 并使用它 → **use-after-destroy**。**窗口量化**：`marked.Load()` 在 x86 上是一条普通 `MOV`（~1ns，无锁前缀），`refCount.Add(1)` 是一条 `LOCK XADD`（~15-20ns）→ **窗口 20ns 量级**；Go 的异步抢占只发生在函数入口和循环回边（这里没有），能显著拉宽窗口的只有 GC STW；而 `markForDeletion` 只在配置更新时发生（低频）。**所以实际触发概率极低 —— 必须主动承认。但面试官问的不是"多久触发一次"，而是"你怎么论证它安全"** —— 只要 `acquire` 是"先检查再行动"，安全性就无法论证，无论窗口多窄。

**② 怎么改才严格（三种，按推荐度）：** **方案 A（零窗口，推荐）** —— 把 `marked` 和 `refCount` **打进同一个原子字**：最高位当 dead 标志、低 63 位当计数；`acquire` 用 CAS 循环（`v := state.Load(); if v < 0 { return false }; if state.CompareAndSwap(v, v+1) { return true }`），`markForDeletion` 用 `state.Or(minInt64)` 置位，等待条件变成 `state.Load() == minInt64` —— **一次 CAS 同时完成"检查是否已死"和"计数 +1"，窗口为零**，语义也更清晰。**方案 B（最不容易写错）** —— `sync.RWMutex` 保护 entry 状态：acquire 走 RLock（读 marked + 计数都在读锁内），markForDeletion 走写锁；正确，热路径每次一次 RLock（无竞争约 20ns，可接受）。**方案 C（用时间换正确性）** —— 不销毁：放进延迟销毁队列（`time.AfterFunc(最大请求时长, close)`）或只标记 + 打点 + 留到进程退出清；简单够用，代价是资源晚释放 —— 如果"业务最大时长"有明确上界（§4.4 第一步），这个方案很实用。

**③ 更严重的问题：`waitForRelease` 的超时只有 5 秒。** `timeout := 5 * time.Second`（`:218`），超时后**"强制销毁"**（`:228`），而 LLM 调用经常超过 5 秒（§4.4 论证过可能 60 秒+）→ **"引用计数保护"实际退化成一个 5 秒的宽限期：5 秒之后旧实例被强制关闭，而那个请求还在用它的会话记忆和 MCP 连接。** 这是"**设计对、参数错**"的典型：代码结构完全正确，一个常量让整个机制在真实负载下失效，而且**失效是静默的**（只有一行 Warn）。修法：超时必须 ≥ 业务最大时长上界（给 LLM 加超时后这个数字就确定了，比如 90 秒），或者超时后**只标记不销毁**（打指标 + 告警 + 延迟到进程退出）—— **永远不要"强制销毁还有人在用的对象"；宽限期的下界由业务决定，不能拍一个整数。**

**④ DELETE 路径把等待放进了全局写锁。** `Unregister` 拿 `r.mu.Lock()`（`registry.go:120-124`）后调 `doUnregister`，后者执行 `markForDeletion` + `delete` + **`waitForRelease`（持锁自旋最多 5 秒，每 50ms 轮询一次）**（`:127-144`）。这 5 秒里所有需要注册表读锁的操作全部阻塞，而它们几乎全在请求热路径上：`GetEntry`（`:246-250`，每个新会话调一次 `gateway.go:180`、引用计数续期也调 `gateway.go:102`）、`GetAvailableAgentIDs`（`:285-294`，agentID 为空时的兜底 `gateway.go:85`）、`Size`（`:321-325`，`/health` 每次探针 `gateway.go:269`）、`GetAllAgentInfo`（`:297-318`，`main.go:343`）→ **一次 etcd 的 Agent 删除事件 = 整个网关最多阻塞 5 秒**，1000 QPS 下就是 5000 个请求排在一把锁上，期间 `/health` 探针也会超时（→ K8s 可能重启进程）。**最有说服力的对比：同一个文件里 update 路径是异步的（`go r.gracefulDestroy`，`:196`），delete 路径是同步的（`:135`）—— 这是不一致，不是设计选择。** 修法：`doUnregister` 也改成"标记 + 删除后立刻返回，把等待丢进 goroutine"。

**⑤ `Clear()` 完全不尊重引用计数。** `registry.go:328-341` 标记 → **立即 `Close()`** → 删除，**没有 `waitForRelease`** → 优雅关闭路径上（`main.go:534`）**正在跑的请求被直接掐断**；这和 `main.go:518` 的 `Shutdown` 10 秒超时叠加：`Shutdown` 等 10 秒后强制返回，然后 `Clear()` 无差别关闭所有 Agent，而那些正在跑的 LLM 调用（可能 60 秒）被腰斩。另外 **跨配置项无原子快照**：`handleAgentConfigChange` 与 `handleModelConfigChange` 是两次独立事件、两个独立通知（`manager.go:106-116`）→ 中间进来的请求可能用"新模型配置 + 旧 Agent 配置"；修法是配置版本化 + 请求级快照，或者接受最终一致但**要能说出"为什么两者语义独立、短暂不一致不会坏"**。

> **总结一句给面试用：引用计数这个设计本身是对的，也是全项目最值得拿出来讲的一处。它的全部问题在三个参数/路径上 —— 5 秒超时、DELETE 走同步锁内、acquire 的 20ns TOCTOU 窗口。** 应该主动说"我知道它的边界在哪"，而不是"我做了引用计数所以安全"—— 前者是工程师，后者是简历。

## 七、压测与容量

### 7.1 没有任何压测数据

**事实**：全仓 `find . -name "*_test.go"` → **0 个文件**；grep `wrk|vegeta|hey|k6|ab -n` 在 `*.sh/*.md/*.yml` 里 → **零命中**；`README.md` 没有 QPS 数字（只有一张能力对比表，`README.md:53`）。**为什么这条在面试里最重要**：涉及"高并发"的话题，**第一个可信度锚点是数字**，没有数字时任何"我们支持高并发"都是零信息量 —— 主动说"没测过"是唯一安全的选择，而且会立刻建立可信度，因为它证明你分得清"有代码"和"有证据"。但要给"没测"一个体面的理由并立刻转向定性分析：**这个项目的瓶颈根本不在服务端**（请求耗时由下游 LLM 决定），所以"服务端能扛多少 QPS"单独看没有意义 —— 有意义的数字是"在给定下游配额下，服务端能维持多少并发而不雪崩"（§7.4）。

### 7.2 没有并发闸门

`stage3.yml:89` 配了 `globalMaxConcurrent: 100`，而**全仓 grep 只有 `config.go:151` 这一行定义命中，没有任何读取方**。写了配置、没实现功能 —— **这比"没这个配置"更危险**：运维看到 100 会以为有并发上限，实际不存在。

**没有闸门会怎样（"高并发"最核心的一段机制）：** 到达率超过服务能力时 Go 不会拒绝，它会**无限接受**：每请求一个 goroutine（8KB 栈起步）、一条到 LLM 的连接（`MaxIdleConnsPerHost=2`，§1）、一份请求体 —— 而且 **body 读取没有任何大小限制**：`json.NewDecoder(r.Body).Decode(&req)`（`main.go:384`）直接读，一个 1GB 的 body 会被完整读进内存（修法一行：`r.Body = http.MaxBytesReader(w, r.Body, 1<<20)`）。

假设 LLM 后端只能支撑 **8 路**并发推理、服务端能扛 10,000 个 goroutine、客户端持续打 1000 QPS：

| | 无闸门 | 有闸门（100 并发 + 1s 等待） |
|---|---|---|
| 接受的请求 | 全部（无限） | 前 100 个 |
| 单请求延迟 | 排队到 **1250 秒**（队列无界增长） | 前 100 个保持 10s |
| 第 101+ 个 | 加入队列，同样等几百秒 | **1 秒后 503**，客户端快速重试其他实例 |
| 内存/连接 | 单调增长直到 OOM | 有界（100 × 请求大小） |
| 恢复 | 需要重启 | 自动（队列一缩短就恢复） |

**这就是"闸门不是优化，是可用性"：目标不是让更多请求进来，而是让进来的一定能完成。** 怎么加：① `golang.org/x/sync/semaphore`（`go.mod` 里 `golang.org/x/sync v0.16.0` 已是间接依赖）或 `chan struct{}` 计数信号量；② **带超时的 Acquire**（等 1~2 秒拿不到就 503，不是无限等）；③ **位置：过滤链之后、Agent 调用之前** —— 过滤链很便宜（µs 级），让它先快速拒绝非法/注入请求、不占名额（这也部分缓解 §2.2）；④ **必须在 Lane 之前** —— 反过来的话大量"在等会话"的请求会占满名额，实际在执行的请求反而进不来；⑤ **值怎么定：不是拍脑袋 100，而是由下游倒推** —— `闸门 = min(LLM 后端并发上限, 本机安全承载) × (1 - 余量)`；本地 Ollama 看 `OLLAMA_NUM_PARALLEL`，云端 API 用 RPM/TPM 配额除以单请求平均耗时换算成并发。**这句话是整篇里最能体现工程思维的：闸门大小是从下游倒推出来的，不是配置里写死的。**

### 7.3 `http.Server` 零超时 → slowloris

`main.go:505-509` 的 `&http.Server{Addr, Handler}` 只设了两个字段 → `ReadTimeout`/`ReadHeaderTimeout`/`WriteTimeout`/`IdleTimeout`/`MaxHeaderBytes` **全部零值 = 不限制**：header 可以无限慢发、body 可以无限慢发、keep-alive 永不回收、写响应可以无限慢。

**slowloris 机制：** 攻击者开 N 个连接，每个每隔几秒发一个字节（或发一半就停），服务端为**每个连接**分配一个 goroutine 并阻塞在读取上 —— 连接和 goroutine 被占着不放，直到客户端断开或服务端超时（现在没有超时，所以永不释放）。**攻击者成本近乎零（N 个 socket），服务端成本是 N 个 goroutine + N 个 fd** —— 一台 `ulimit -n` = 1024 的机器，攻击者用几百个连接就能让正常用户连不上（不是 CPU 被打满，是 fd 和连接槽位被占满）。**本项目的叠加放大：** ① 无 `ReadHeaderTimeout` → header 无限慢发；② 无 `IdleTimeout` → keep-alive 永不回收（客户端连接池一直占着服务端槽位）；③ 无 `WriteTimeout` → 慢读客户端（`w.Write` 阻塞在 TCP 发送缓冲）也能占住 goroutine；④ **最关键** —— 请求 ctx 是 `r.Context()`（`main.go:413`），而它**只在客户端断开时取消、没有超时**，所以慢连接不仅能占住 goroutine，**还能占住 Lane 锁和会话**（配合 §4.5，最坏情况下锁死一个会话直到 60 秒 TTL 到期）。

```go
server := &http.Server{
	Addr: ..., Handler: ...,
	ReadHeaderTimeout: 5 * time.Second,    // 只保护 header；正常客户端 < 100ms
	ReadTimeout:       30 * time.Second,   // 覆盖 body；chat 请求体很小（< 100KB）
	WriteTimeout:      0,                  // ← 见下面的取舍
	IdleTimeout:       120 * time.Second,  // keep-alive 空闲回收，要大于客户端复用间隔
	MaxHeaderBytes:    1 << 16,            // 64KB，够用
}
```

**`WriteTimeout` 是唯一需要想清楚的一处**：它和流式输出（SSE）天然冲突 —— 流式回答连续写几十秒，一个固定的 `WriteTimeout` 会在第 N 秒掐断长回答。**正解不是设一个很大的值（那等于没有保护），而是用 `http.ResponseController`（Go 1.20+）在每次写之前 `SetWriteDeadline(now + 30s)`**：把"两次写之间的最大间隔"作为超时，于是**"客户端太慢"和"回答太长"两件事被解耦** —— 前者在 30 秒无进展时被杀，后者可以持续几分钟。这个点很能体现深度，它说明你知道 `WriteTimeout` 为什么不能简单"设大一点"。（`ReadTimeout` 同理：如果以后要支持上传大文件，应该用 `SetReadDeadline` 在单个 handler 里放宽，而不是把全局值调大。）

### 7.4 被问"能扛多少并发"该怎么答

**① 先划边界（止住追问）：** "我们没做过压测，所以我不给数字。"

**② 给一个由下游推导的上界（这是能算的）：** `单实例稳态吞吐 ≈ 下游允许并发 C / 单请求 LLM 轮数 / 单轮耗时`。假设平均 3 轮、每轮 5 秒（本地 Ollama 7B 量级）、C = 100 → `100 / 3 / 5 ≈ 6.7 QPS`。**关键洞察：Agent 服务的 QPS 比普通 Web 低两个数量级，这是架构决定的天花板，不是实现问题。** 顺便自证：本项目配的 `userQps: 10` 和这个量级是同一个数量级 —— **说明作者对量级有直觉**，值得说。

**③ 给"什么会先坏"的排序（比给数字更有说服力）：**

| 顺序 | 先坏的东西 | 依据 |
|---|---|---|
| 1 | LLM 下游（配额/排队） | §1 —— 瓶颈永远在下游 |
| 2 | **服务端自身：goroutine 和连接无界堆积** | §7.2 没有闸门 |
| 3 | Redis 相关路径 | §5.1 无池配置 + §5.5 故障时每请求等 30s |
| 4 | Go 服务本身（slowloris） | §7.3 零超时 |

**④ 主动给改进项和收益：** 加闸门 + 加超时 + 配池子，把"过载时延迟无限增长"变成"过载时快速拒绝"，预计 P99 从"不可预测"变成"有上界（1~2s 拒绝）"。**"说完'我不知道数字'之后要给'我知道瓶颈在哪'" —— 这是从"没测过"到"想清楚了"的关键一步；面试官问这个问题，考的从来不是数字。**

### 7.5 如果要压测，压什么、看什么指标

**压什么：** ① 工具 —— `hey -z 60s -c 100 -m POST -T application/json -D body.json http://localhost:8080/api/v1/chat`，或 `k6`（能自定义指标和分阶段负载）；`wrk` 对 POST + 动态 body 不方便。② **必须先有一个 mock LLM** —— 压真 LLM 测的是 Ollama 的性能（而且不可重复：模型有 KV cache、GPU 有热状态），用一个可控延迟的假 OpenAI 端点（`httptest.Server` 或 `time.Sleep(3s)` 后返回固定 JSON 的小程序），**让瓶颈回到被测服务 —— 这一步是"会不会压测"的分水岭，拿真 LLM 压测的人测出来的是别人的系统**。③ **三个场景**：**稳态容量**（固定并发 10/50/100/200 各跑 60s，看吞吐和延迟在哪里拐，拐点就是容量）；**突发**（0 → 500 并发瞬间拉起，有闸门的正确表现是 503 上升、延迟平稳，没闸门是延迟爆炸）；**依赖故障**（压测中 kill Redis / 停 etcd / 让 mock LLM 返回 500，观察降级是否符合预期 —— 最能暴露 §5.5 和 §3.9 的问题，也最容易被忽略）。

**看什么指标（先看一个具体的可观测性 bug）：** `metrics.go:34-39` 的 `ChatDurationSeconds` 用 `prometheus.DefBuckets`，**最大桶上界是 10 秒**，而真实对话十几到几十秒 → **所有观测落在 `+Inf` 桶里，直方图退化成"只知道有个东西很慢"**；而且它把排队等待 + RAG 检索 + LLM 推理 + 工具调用全混在一个指标里（`Observe` 在 `main.go:417`，包住整个 `activeProcessFunc`）。**在 Agent 服务里"慢"有三种完全不同的原因，混在一个指标里等于没有指标。** 应该拆三个：

| 指标 | 含义 | 桶建议 |
|---|---|---|
| `queue_wait_seconds` | 等 Lane 锁（§4）—— **来源是服务端自身的排队** | 0.001 ~ 10 |
| `llm_ttft_seconds` | 到第一个 token —— **来源是 LLM 负载** | 0.1 ~ 60 |
| `request_total_seconds` | 端到端（以上之和 + 生成时间） | 0.1 ~ 120 |

其他必须看的：**P50/P95/P99**（P99 才是容量决策依据，平均值会让你以为服务很好）**并且必须同时看拒绝率** —— 只报 QPS 不报拒绝率是压测里最常见的作弊：**把闸门调到 1 就能得到"P99 = 5ms"的漂亮数字**；**TTFT**（流式/Agent 场景里这是用户体验的主要指标，和总时长是两件事；本项目是**一次性返回**（`writeJSON`，`main.go:556-560`），用户感知延迟 = 总时长，**没有流式就等于把生成时间全算进等待，这本身是个可提的优化点**）；**Goodput（有效吞吐）** = 成功完成数/秒，而不是"进入系统的请求数" —— 过载时 QPS 可能上升（重试）而 Goodput 下降；**`go_goroutines`**（promhttp 免费赠送，`metrics.go:26` 的注释里写了）—— 过载时单调上升 = **没有背压的直接证据**；**下游配额消耗**（每分钟 LLM 请求/token 数 vs 配额，是"能不能扩容"的真正约束）；**现场诊断**用 `/debug/pprof/goroutine?debug=1` 看 goroutine 卡在哪（**全仓 grep `pprof` 零命中**，加它是 3 行：`import _ "net/http/pprof"` + 一个内部端口），`go tool pprof` 的 **mutex / block profile 能直接定位 §3.2 的锁争用和 §4 的轮询自旋 —— 这是唯一能"看见"锁争用的工具**。

**容量换算的收尾公式（很好背）：`所需实例数 = 峰值 QPS × 平均请求耗时 / (单实例并发上限 × 冗余系数)`**。例：50 QPS × 10s / (100 × 0.7) ≈ **7.1 个实例**。这条公式顺带暴露本项目的一个隐患：每个实例有**自己的本地限流桶**（`ratelimit.go:17,26-28`）和自己的会话 `sync.Map`，**所以实例数一变"实际生效的策略"就变**（§3.6 的"实际限额 ≈ 10 × 实例数"）—— **在多实例部署下，任何"每实例"的状态都会变成"× 实例数"的行为**，这是扩容时最容易忽视的一类 bug。

## 八、面试要点（15 个高频问题）

> 用法：先看骨架，再看括号里的 `文件:行号` —— 那是唯一能让你在被追问时站住的东西。

### Q1：你的限流怎么实现的？多实例下还成立吗？

① 单机令牌桶，桶容量 = 速率（允许 1 秒突发），参数 `globalQps=1000`/`userQps=10`（`ratelimit.go:26-28,84-92`；`stage3.yml:97-98`）；选型理由：能容忍突发、状态量小（令牌数 + 时间戳）、无 Redis 依赖。
② **多实例下不成立** —— 桶是进程内状态（`ratelimit.go:15-17`），N 个实例的实际限额是 N 倍，**扩容会静默放宽策略**。
③ 集中式方案：每请求一次 Redis 往返，用 Lua 把"INCR + 首次 EXPIRE"合并成一条 EVAL（现在的 `IncrWithExpire` 是两条非原子命令，`client.go:162-172`）；**或者本地预分配配额**（实例每次向 Redis 借 100 个令牌，用完再借）—— 把往返从"每请求一次"降到"每 100 个请求一次"，代价是限额有最多 100 的粒度误差。**说出"本地预分配"这个折中是这道题的高分点。**
④ 降级：**fail-open**（`distributed.go:192-196`），限流是保护性能力，失效时优先保业务 —— 但代价是"Redis 挂了 = 限流消失"，此时必须有第二道防线（并发闸门，本项目恰好没有）。

### Q2：令牌桶、漏桶、固定窗口、滑动窗口怎么选？

① 固定窗口最简单，但**边界允许 2 倍突发** —— 本项目分布式侧用的就是它（`distributed.go:189-198`）；滑动窗口（ZSET 存时间戳）精确但内存 O(请求数)，生产常用**滑动窗口计数**（两窗口加权）折中；令牌桶允许突发、平均速率可控；漏桶强制恒定输出（适合保护下游，不适合用户体验）。
② **AI 场景的特殊考量：真正的资源不是"请求数"而是 token 数** —— 一次长 prompt 的 LLM 成本是短 prompt 的 100 倍。所以理想方案是**双维度限流**：请求数（QPS）+ token 数（TPM），后者在请求前后各记一次（预估 + 实际）。**本项目只做了 QPS，这是可以主动提的改进方向。**
③ **不要自己手写**：`x/time/rate` 有 `Allow`/`Reserve`/`WaitN` 三套语义（支持"允许欠账"），且内部临界区完整（`ratelimit.go:110-127` 的 lost update 就是手写的代价）。
④ **但"用库"不是答案的全部** —— 要能说出这个库的临界区为什么没有 lost update：**它把"补令牌"和"扣令牌"放在同一个 `mu` 里。**

### Q3：你怎么保证同一会话的请求不并发？

① 先分清两个问题：**并发安全（race-free）** 靠 `ConversationMemory` 自己的 `sync.RWMutex` 就够（`conversation.go:38,86-97`）；**语义正确（串行化）** 才需要 Lane —— 两个请求各读到同一份历史、各 append，会产出"用户说一句、助手答两遍"的错乱历史（`base.go:232,306,204`）。
② 单机：每 sessionID 一把 CAS 锁（`lane.go:33-68`），抢不到就 50ms 重试、最多 30 秒（`gateway.go:117-131`）。
③ 分布式：Redis `SET NX PX`（TTL 60s）+ 100ms 轮询 + **Lua compare-and-delete 释放**（`distributed.go:201-221`；`client.go:145-159`）—— 这个 Lua 是全项目最正确的分布式代码。
④ **主动交代三个边界**：无 watchdog 续期（TTL < 业务时长时锁提前失效，§4.4）；解锁用 `r.Context()`，客户端断开就卡满 TTL（`distributed.go:99`）；requestID 用 `UnixNano`，跨实例不唯一（`distributed.go:91`）。
⑤ 结论句：**"Lane 在'单次会话交互 < 60 秒'的假设下正确工作，超出会静默失效，而我没测量过这个假设。"**

### Q4：Redis 分布式锁你了解多少？锁过期了怎么办？

① `SET key value NX PX ttl` 一条命令完成"不存在才设置 + 带过期"，天然原子（`client.go:136-142`）。
② **value 必须是唯一标识，解锁必须用 Lua 比对 value 再删**（`client.go:147-153`）—— 核心不是"防误删"而是"**防过期者误删**"。
③ **锁过期 = 业务未完成的必然结果**（TTL 是为了防持有者崩溃后死锁）。三层解法：**业务超时上界 + TTL ≥ 上界**；**watchdog 自动续期**（Redisson：默认 30s TTL、每 TTL/3 用 Lua 校验持有者身份并 `PEXPIRE`；续期任务属于持有者进程，崩溃则续期停止、锁自动释放 → **TTL 的语义是"持有者失联检测窗口"，不是"业务超时"**）；**fencing token**（每次获取锁 `INCR` 一把单调计数器，写入端拒绝比已见最大值小的 fence）—— 最终解决"锁只能尽力而为"，且顺带解决陈旧回写（版本号就是一种 fence）。
④ **锁 ≠ 一致性**：锁保证互斥、不保证可见性 —— 本项目就有锁保护下的陈旧缓存回写丢消息（`memory/distributed.go:20` 本地缓存永不过期 + `:97-104` 全量覆盖写）。
⑤ 加分：讲一句 **Redlock 的争议**（Kleppmann vs antirez）——"单实例 Redis 锁在异步复制的主从切换时会丢锁，所以严格正确的做法是 fencing token；多数业务用单实例 + fencing 就够，不需要 Redlock 的 5 节点" —— 能说出争论的两边比只会背 Redlock 更值钱。

### Q5：锁的 value（requestID）怎么生成？

① 两条要求：**唯一**（否则 A 的解锁脚本会删掉 B 的锁）和**不可预测**（否则猜中 value 就等于能删别人的锁）。
② 本项目用 `time.Now().UnixNano()`（`distributed.go:91`）—— **两条都不满足**：跨机器时钟回拨/漂移时会重合；时间戳可猜。
③ 正解：UUIDv4，或 **`{instanceID}-{本地单调计数器}`**（`instanceID` 来自 Pod 名或启动时随机串，计数器用 `atomic.Int64`）—— 后者额外带来**可读性**（日志能看出哪个实例持锁）和**零成本**（不引入 UUID 依赖）。
④ 顺带：不要把"业务 ID"（比如 sessionID）当 requestID —— 那会让"同一会话的重试"看起来像同一个持有者。

### Q6：Redis 挂了你的服务会怎样？

① **三条路径三种行为、互不一致**（最该主动说的）：限流 fail-open（`distributed.go:192-196`）；会话读 **fail-silent**（`distributed.go:71-85` 把错误当"key 不存在" → 新建空会话 → 紧接的全量写回**覆盖掉原数据**）；Lane 锁 fail-closed 但**每请求等 30 秒**（`distributed.go:203-220`）。
② **最严重的是第二条：故障会升级为数据损坏。** 修法：`errors.Is(err, redis.Nil)` 区分"没有数据"和"取不到数据"，后者返回错误让请求失败 —— **永远不要让"不确定"变成"空"。**
③ **锁路径的 30 秒是自我 DoS**：故障期间占用资源 = 到达率 × 等待时间 → Redis 挂 30 秒、100 QPS = 3000 个请求同时挂 30 秒然后集中重试。正解是快速失败（100ms）+ **熔断器**（连续 5 次失败直接拒绝，冷却 1s，成功则关闭，失败则翻倍到 30s 上限 —— 不到 50 行，把"每请求 30 秒"变成"第一个 100ms，其余零成本"）。
④ 统一规则：**读路径 fail-closed、写路径必须显式报错、保护性能力 fail-open**，所有 fail-closed 都要快速失败 + 熔断。
⑤ 健康检查要真实探测（`main.go:334` 读的是配置开关 `cfg.Redis.Enabled` 而非 `Ping` 结果），并且**放进 ready 而不是 live**（live 失败会重启所有实例，把局部故障放大成全局故障）。

### Q7：你的服务能扛多少并发？

① **诚实开场**："没做过压测，不给数字。"（全仓 0 个测试文件、README 无 QPS 数据）
② **给一个由下游推导的上界**：`吞吐 ≈ 下游并发 / LLM 轮数 / 单轮耗时`，例：100 / 3 / 5 ≈ **6.7 QPS** —— Agent 的 QPS 比 Web 低两个数量级是架构决定的。
③ **给"什么会先坏"的排序**：LLM 下游配额 → **服务端无闸门导致的 goroutine/连接无界堆积**（`globalMaxConcurrent: 100` 配了但从不读，`config.go:151`）→ Redis 路径（无池配置 + 故障等 30s）→ slowloris（`main.go:506-509` 零超时）。
④ 给改进项和收益：闸门 + 超时 + 池配置 → 把"延迟无限增长"变成"快速拒绝（有界）"。
⑤ 收在一句：**"我不知道数字，但我知道瓶颈在哪、下一个该修什么。"**

### Q8：你的服务有超时吗？没有 `WriteTimeout` 会怎样？

① `http.Server` 只有 `Addr` 和 `Handler`（`main.go:506-509`）→ 五个超时相关字段全是零值（不限制）。
② **slowloris**：每连接一个 goroutine 长期阻塞在读取上，攻击者成本近乎零，服务端的 fd 和连接槽位被占满 → 正常用户连不上（不是 CPU 被打满）。
③ 叠加效应：LLM 客户端也**没有任何超时**（`pkg/llm/openai.go:42` 与 go-openai 的 `DefaultConfig` 都是裸 `&http.Client{}`）→ 下游不响应的请求会**永久占用** goroutine + Lane 锁（ctx 是 `r.Context()`，只在客户端断开时取消，`main.go:413`）。
④ 正确配置：`ReadHeaderTimeout=5s`、`ReadTimeout=30s`、`IdleTimeout=120s`、`MaxHeaderBytes=64KB`；**`WriteTimeout` 不能简单设大** —— 它和 SSE 冲突，正解是用 `http.ResponseController.SetWriteDeadline` **每次写前按"两次写之间的最大间隔"设**，把"客户端慢"和"回答长"解耦。
⑤ 顺带：body 无大小限制（`main.go:384`），一行 `http.MaxBytesReader` 修掉。

### Q9：配置热更新怎么做？etcd watch 断了怎么办？

① 观察者模式：`ConfigWatcher`（`watcher.go:38-40,194-198`）+ 同步回调；`DynamicConfigManager` 实现监听器接口按 key 类型分发（`manager.go:87-117`）。
② **现在 watch 出错就永久退出**（两个出口都 `return`，`watcher.go:129-135`）→ **静默失效**。最典型的触发原因是 **etcd compaction**：客户端落后超过服务端保留的 revision（默认 1 小时或 1000 个 rev），历史变更已被删除、**无法补发**，etcd 只能 `ErrCompacted` 并终止 watcher。
③ **正确形态 = 重连循环 + 全量对账**：外层 `for` 包住单次 watch，指数退避 + jitter 防惊群（100ms → 30s 上限）；每次重连后全量 `Get` 与本地 cache diff 补发差异 —— 配置幂等且小，**对账比逐事件补偿便宜得多，且天然覆盖所有丢失场景**。
④ **必须有观测量**：`watch_alive`（Gauge，最重要）、`watch_restarts_total`、`last_event_timestamp`、`config_version`。**静默失效最危险的不是失效，是没有指标。**
⑤ **Get 与 Watch 之间的窗口**：`loadAllConfigs` 丢掉 `resp.Header.Revision`（`watcher.go:99-105`）、`Watch` 没带 `WithRev(rev+1)`（`:122`）→ 两次调用之间的变更永久丢失；标准做法是"Get 拿 rev → `Watch(WithRev(rev+1))`"，而本项目已有幂等（同值 PUT 跳过，`watcher.go:158-163`）可兜住重复。

### Q10：热更新时正在处理的请求怎么办？

① 问题：直接替换 + `Close()` 会让在途请求踩到已断的 MCP 连接和已清的会话。
② **本项目的做法（值得讲）**：`AgentEntry` 带 `refCount` + `marked`（`registry.go:24-31`）；更新路径"标记旧 → 创建新 → **失败则回滚标记**（`:182`）→ 替换 → 异步等引用归零再销毁"（`:154-214`）；请求侧 `AcquireRequest`/`ReleaseRequest`（`gateway.go:99-115`）。效果：**一个请求全程只看到同一个 Agent 实例**，旧实例资源在没人用之后才释放 —— 和 `sync.WaitGroup`、`http.Server.Shutdown` 是同一个思想。
③ **主动交代边界**：`acquire` 是 check-then-act，有 20ns TOCTOU 窗口（`:34-40`），严格修法是把 dead 位和计数打包进**同一个原子字**、一次 CAS 完成"检查 + 计数"；`waitForRelease` 超时只有 **5 秒**（`:218`）而 LLM 调用常超 5 秒 → **保护实际是 5 秒宽限期**，超时后"强制销毁"（`:228`）—— **设计对、参数错**；`Unregister` 在**全局写锁内**等最多 5 秒（`:120-144`）而 `GetEntry` 是每请求必经 → **一次 etcd 删除事件能让整个网关阻塞 5 秒**（对比 update 路径是异步的，`:196`，所以这是不一致而非设计）；`Clear()` 完全不等待（`:328-341`）→ 优雅关闭时掐断在途请求。
④ 修法收口：删除也异步化、超时由业务上界决定（或超时只标记不销毁）、acquire 用单原子字。

### Q11：引用计数的 acquire 和 markForDeletion 怎么保证不打架？

① 现象：`acquire` 是"读 marked → 再 +1"，`markForDeletion` 可以插在两步之间，而销毁侧判断条件是"refCount ≤ 0"（`registry.go:222-227`）→ 可能"计数还是 0 就销毁了"，而那个 +1 马上到来 → use-after-destroy。
② **量化**：窗口 ≈ 20ns（一次普通 load + 一次 `LOCK XADD`），`markForDeletion` 只在配置更新时发生（低频）→ **实际触发概率极低**；但"检查与执行分离"意味着安全性无法论证，这才是问题。
③ **严格解法（零窗口）**：dead 标志和计数放进**同一个 `atomic.Int64`**，最高位 dead、低 63 位计数；`acquire` 用 CAS 循环（读到 dead 位返回 false，否则 CAS 加一），`markForDeletion` 用 `Or(minInt64)` 置位，等待条件变成 `state == minInt64` —— **一次 CAS 同时完成检查和计数**。
④ 备选：`sync.RWMutex` 保护 entry 状态（acquire 走 RLock）—— 正确且最不容易写错，代价是每请求一次 RLock（无竞争约 20ns）。
⑤ 加分句：**"这个模式在 Go 里到处都是 —— `sync.WaitGroup` 的 `Add` 在 `Wait` 之后调用会 panic、`singleflight` 用 mutex 保护状态。通用结论：任何'引用计数 + 失效标志'都必须用一次原子操作完成检查与计数，或用锁把它们包起来。"**

### Q12：会话记忆为什么放 Redis？跨实例怎么保证不丢消息？

① **先坦白最大短板**：`DistributedMemory.BuildMessages`（`memory/distributed.go:135-138`）**没有调用方** —— LLM 上下文来自 `BaseAgent.sessions`（`base.go:31,232,306`）这个**实例本地的 sync.Map**。**所以 Redis 里的会话是"只写不读"的，换实例/重启后 LLM 拿不到历史** —— 写侧做了、读侧没接回去。
② **陈旧缓存回写**：本地 `localCache` 永不过期（`distributed.go:20`，TTL 只设在 Redis key 上），A 实例用旧快照全量 `SET` 会覆盖 B 实例刚写的消息（`:97-104`）。
③ **关键区分：Lane 锁保证互斥、不保证可见性 —— 串行 ≠ 一致。** 锁只解决"同一时刻只有一个写入者"，不解决"写入者手里的数据是否最新"。
④ 修法：版本号 / `WATCH`+`MULTI` 乐观锁（版本号本身就是轻量 fencing token，能同时解决锁过期问题）；写完就 `DEL` 本地缓存（退化成每次都读 Redis）；**会话粘性（一致性哈希把会话钉到实例）—— 从根上消除跨实例并发写**，这在 Agent 系统里比在 Web 里更值得做（单请求耗时长，跨实例争用窗口也长）。
⑤ 全量写 vs 增量：现在每次写 50~75KB 的完整快照（`maxSize=50` × 1.5KB，`distributed.go:93-105`），**写成本 O(历史长度)**；改成 `RPUSH` + `LTRIM` 就是 O(1)，写流量降一到两个数量级。

### Q13：网关里过滤器顺序为什么这么排？限流放最后有什么问题？

① 顺序：Auth(10) → Security(20) → RateLimit(30)（`auth.go:38-40`、`security.go:57-59`、`ratelimit.go:36-38`），**而注释写的是"认证→限流→安全"，与实现相反**（`gateway.go:59`、`distributed.go:70`）。
② **问题：被安全拦下的请求不消耗限流令牌** → 攻击者用"一定被拦"的 payload 无限打 → 走完 5 条正则 + `ToLower` 全量扫描（`security.go:76-97`，4000 字节上限 → 约 4KB 分配 + 3.6 万字节扫描/请求）→ **纯 CPU 打点，且完全绕过限流**。
③ 正确顺序 **Auth(10) → RateLimit(15) → Security(20)**，只把限流上移一位 —— **理由是限流的用户维度需要 `ctx.UserID`，而 UserID 是认证产生的**，不能更靠前。**这一句能证明你是想清楚了而不是背口号。**
④ 再进一步：未认证流量不受用户维度约束（`ratelimit.go:53`）→ 需要**在认证之前加一层 IP 粗粒度限流**（Order=5）。完整链路：`IP 限流 → 认证 → 用户/租户限流 → 安全过滤`。
⑤ 顺便：错误码映射缺 `LANE_BUSY`/`SYSTEM_BUSY` → 落到 `default: 500`（`main.go:574-576`），**过载信号被报成服务端 bug**，应该 503 + `Retry-After`。

### Q14：你们的 Prometheus 指标是怎么设计的？

① 六个业务指标（`metrics.go:33-63`）：请求数、耗时直方图、活跃会话、活跃 Lane、限流拒绝、工具调用 —— 方向对（RED 方法：Rate/Errors/Duration）。
② **三个具体 bug**：`ChatDurationSeconds` 用 `prometheus.DefBuckets`，**最大桶上界 10 秒**而真实对话十几到几十秒 → **全落在 `+Inf`，直方图失效**（`metrics.go:34-39`）；`ActiveLanes`（`:47-51`）定义后**从未 `Set`**，Grafana 上永远 0（**比没有指标更危险，人会读成"没有并发"**）；`/health` 里做指标采集（`main.go:327`）—— **用探针频率驱动指标**，且 `gw.GetStats()` 是 O(会话数) 全量遍历。
③ **LLM 服务的延迟必须拆三个**：`queue_wait`（等 Lane）/ `llm_ttft`（到首 token）/ `total` —— 混成一个就无法回答"用户觉得慢是我们排队还是下游慢"。
④ 加 `pprof`（全仓没有）：`goroutine?debug=1` 看卡点、`block`/`mutex` profile 看锁争用 —— **这是唯一能"看见"锁争用的工具**，而本项目有四处锁争用（§3.2、§4.2、§6.6）。
⑤ 加分：指标要有**基数意识** —— `ToolCallsTotal` 按 `tool_name` 打（`:59-63`），如果工具名来自用户输入或动态配置就是无界基数（cardinality 爆炸）；本项目工具名受控所以没问题，**能主动说"我看过它的基数"就是加分**。

### Q15：你觉得这个项目在高并发上最大的问题是什么？

① **一句话**：**"最缺的不是限流，是'并发闸门 + 处处超时' —— 限流控制的是'接受多少'，闸门和超时控制的是'进来的一定能完成'。这个项目做了前者，几乎没做后者。"**
② **三条证据**：`globalMaxConcurrent: 100` 配了但**代码从不读**（`config.go:151`）→ 过载时 goroutine 和连接无界增长；`http.Server` **零超时**（`main.go:506-509`）+ LLM 客户端**零超时**（`pkg/llm/openai.go:42`）→ slowloris + 慢连接能占住 goroutine、Lane 锁和会话；Redis 故障时**每请求等 30 秒**（`distributed.go:203-220`）而不是快速失败 + 熔断 → **故障被延迟放大成自我 DoS**。
③ **但要说清哪些是对的**（只讲坑像在背别人的 bug 清单）：`Unlock` 的 Lua compare-and-delete（`client.go:145-159`）是正确的分布式锁写法；热更新的引用计数 + 失败回滚（`registry.go:154-214`）是全项目最好的设计；限流的 fail-open 方向对（`distributed.go:192-196`）；错误码映射集中且语义正确（`main.go:562-577`）；优雅关闭链路完整（`main.go:512-548`）。
④ **如果只改三处**：加并发闸门（`x/sync/semaphore` + 1s 超时 → 503）；给 `http.Server` 和 LLM 客户端补超时；给 Redis 加熔断 + 区分 `redis.Nil` 与真实错误。**三处加起来不到 200 行，但把系统从"过载时不可预测"变成"过载时快速失败"。**
⑤ **留印象的最后一句**：**"这个项目的并发问题是'知道的比做到的多' —— 报告里能写出的每个缺陷，配置里几乎都有对应的开关（`globalMaxConcurrent`、`laneLockMs`、`watchQueueSize`），只是代码没接上。这比'不懂'好修，但也提醒我：配置项写进 YAML 的那一刻，就等于承诺它生效了。"**
