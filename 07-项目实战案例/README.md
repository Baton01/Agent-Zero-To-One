# 项目实战案例 · BitGuide Agent Platform

> **这个模块解决什么问题：** 前面的章节教你造 Agent，[[06-模拟面试/README|模拟面试]] 给你练的设施，但**你手里没有一份"标准答案"** —— 一个好项目在面试里到底该被讲成什么样。
>
> **这一份就是那份标准答案。** 拿一个真实的 Go Agent 项目从头拆到源码行号，你会看到：一个项目里哪些东西能写进简历、哪些东西是"看起来实现了"的坑、以及被面试官按住追问时怎么接。
>

## 一、先看一段真实的追问

候选人说：「我做了个 Agent 平台，用 ReAct 循环调工具，网关做了限流。」

面试官问：「循环什么时候停？」

> **候选人：** 模型不调工具了就停。
>
> **面试官：** 还有别的出口吗？
>
> **候选人：** ……还有个最大轮数吧，我设的 10。
>
> **面试官：** 为什么是 10？
>
> **候选人：** 默认值吧，参考别人的。
>
> **面试官：** 那跑满 10 轮之后，历史里留下了什么？用户看到什么？
>
> **候选人：** 这个……应该是报错吧。

到这儿面试官已经把你归类了：**项目是你做的，但你没想过它为什么这么做。**

这一段里没有一道题是难的。三个问题都只有一个特征：**它们问的不是"有没有实现"，而是"你当时怎么想的"。**

`ReAct 循环`、`10 轮上限`、`终止条件` 这些词候选人都会说，但他答不出"为什么是 10"和"跑满之后留下什么" —— 因为那是**抄来的默认值**，不是他的决策。

**面试考的从来不是功能清单，是决策链。** 这个模块就是教你怎么把决策链讲出来。

## 二、为什么拿这个项目当靶子

[[07-项目实战案例/01-项目速读|BitGuide Agent Platform]] 有两个别的教学项目没有的特征：

**第一，它没有用框架。** 没有 LangChain、没有 Eino，网关是纯 `net/http` 手写的，ReAct 循环是手写的 `for` 循环，MCP 客户端是手写的握手。这意味着每一层都留得下**可以讲的实现细节** —— 用了框架的项目，面试官一问"这个能力怎么实现的"，你的答案就只能是"框架帮我做的"。

**第二，它有真实的、没修完的缺陷。** 这是它最值钱的地方。比如：

- 分布式限流那段代码的分支**永远进不去**（`distributed.go:77` 判断的 `req.UserID` 在 HTTP 层从未被赋值），所以简历上写"实现了分布式限流"就是假话；
- MCP 的 `IsAlive()` **恒返回 true**（因为全仓没有一处 `cmd.Wait()`），崩溃检测和自动重连永远不会触发；
- etcd 的 watch 遇到 `compaction` 报错直接 `return`，**永不重连、无告警、无兜底**。

**为什么这类坑比"功能没做"更值得学？** 因为它们**看起来是实现了的** —— 有文件、有函数、有结构体，甚至有注释。你自己读代码时会以为它是好的，简历上也敢写。面试官顺着问一层就穿了。

[[07-项目实战案例/08-如果重做一次|如果重做一次]] 把 12 个这样的坑逐个拆成「现象 → 根因 → 影响半径 → 怎么修 → 代价与风险 → 面试怎么讲」。**这一份是整个模块里最该精读的**：面试里唯一能证明你真懂系统的表达方式，不是"我知道有这么个问题"，而是"我知道它为什么会这样、改了会影响什么"。

## 三、所有结论都挂着源码行号

这个模块里几乎每句技术判断后面都跟着 `pkg/agent/base.go:295` 这样的引用。这不是装饰：

- 面试官追问"你怎么知道的"，你可以直接翻到那一行；
- 你自己复习时，看到行号就知道该去读哪一段；
- 别人（包括 AI）说你的项目有问题时，你能**验证他说的对不对**。

行号下面还有一层托底：[[07-项目实战案例/证据-代码走查/01-Agent与工具线|证据·Agent 与工具线]]、[[07-项目实战案例/证据-代码走查/02-网关与并发线|证据·网关与并发线]]、[[07-项目实战案例/证据-代码走查/03-RAG与工作流线|证据·RAG 与工作流线]] 三份走查把每条结论对应的代码原文列了出来。行号会随代码演进而漂，所以走查里同时写了**函数名和关键语句**，方便重新定位。

## 四、网页上可以直接练（76 道题）

左侧「面试准备 → 项目实战案例」里有三套题库：

| 题库 | 题数 | 什么时候用 |
| --- | --- | --- |
| 完整模拟面试 | 34 | 面试前一天，按真实流程从头走一遍（自我介绍 → 四轮技术 → 反问） |
| 追问预演 | 30 | 简历投出去之前，把每个技术点下面可能被追问的都过一遍 |
| 缺陷应对 | 12 | 面试官指出你项目的问题时，怎么把"被挑错"变成加分项 |

**练法不是看答案，是自己先讲一遍再对照。** 每道题的流程是：先自己开口答（真的说出来，或者写要点）→ 展开参考回答与点评 → 自评「不会 / 半懂 / 掌握」→ 答不上来的进薄弱清单。

「半懂」这个档位是有意留的：**你脑子里有、但嘴上说不出来**，这是最常见也最致命的状态。它和「不会」要补的东西不一样 —— 不会要回去读材料，半懂要练表达（结论 → 依据（带行号）→ 边界，三句话）。

> **一个刻意的设计：**「跳过」按钮会把这道题记成**不会**，而不是不记录。跳过本身就是信息 —— 一道题你不展开、不自评，说明你不想面对它。面试官不会给你跳过的机会。

## 五、这个模块和你自己项目的关系

**你的项目不会是 BitGuide，但你会有同构的问题。** 这套方法论可以直接搬：

1. **把项目过一遍，列出所有"我改过/我选过"的地方** —— 那才是决策，功能列表不是；
2. **对每个决策问三个问题：** 为什么这样选？失败了会怎样？代价是什么？
3. **把结论钉到行号上** —— 没有行号的结论都是"我记得好像是"；
4. **找出至少三个"看起来实现了、其实是死的"地方** —— 主动说出来，比被问穿强一百倍。

第 4 条反直觉但最有用。面试里主动说「我这里其实有个坑，`X` 那条分支进不去，因为 `Y` 没赋值」，传递的信号是**你读过自己的代码、你有判断力**，而不是"你的项目有缺陷"。缺陷人人都有，能看见缺陷的人不多。
