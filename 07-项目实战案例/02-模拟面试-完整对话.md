# 02 · 模拟面试：一场完整的对话

> **这篇是什么：** 一次完整逐轮展开的模拟面试。面试官提问 → 面试者回答 → 追问 → **【点评】**。
> **怎么用：** 不要背答案，去背**结构**。每个「面试者答」都能直接读出声音，每个【点评】告诉你这句话为什么有效、面试官会从哪一刀切进来。
> **最高原则是诚实。** 这个项目有大量未实现、写了一半、以及明确是死代码的部分。文档里所有「这块我没做到」都是**加分项**，所有硬撑都是**失分项**。面试官见过太多背书的人，他们最想听的是「我知道我这里有问题，知道问题在哪，知道怎么改」。

---

## 【开场】自我介绍与项目概述

> **这一轮在考什么：** 能不能在三分钟内让人听懂你在做什么，而不是复述简历。

### Q1 · 面试官的原话问题
> 「先做个自我介绍吧，三分钟，重点讲讲你这个 BitGuide 项目。」
**面试者答：**
「好，我是 XXX，后端开发，主要用 Go。
最近半年我做了一个叫 BitGuide Agent Platform 的项目，教学场景的 AI Agent 平台，大概 75 个文件、12000 行。它的特点是我把它做成了**四个递进的阶段**，每个阶段解决一类工程问题。

Stage1 是单 Agent 的 MVP：一个 ReAct 循环加工具调用加 RAG 检索增强。Stage2 加多 Agent 和 etcd 动态配置——Agent 的 system prompt、模型、挂哪些工具都能在运行时改，不重启。Stage3 把它做成真正的 HTTP 服务，加了企业网关该有的东西：认证、限流、安全过滤、会话串行化，还有 Redis 做跨实例的会话锁和记忆。Stage4 我用大概两千行 Go 重写了一个类似 LangGraph 的工作流引擎，支持状态图、条件路由、checkpoint，还有「跑到一半暂停、人工确认后恢复」这个闭环。一个仓库四个入口，`cmd/stage1` 到 `cmd/stage4`，共用底下的 `pkg/`，四个 yml 各自独立。

我想强调的一点是，这四个阶段不是我照教程抄的，每一层的取舍都是自己踩出来的。比如 Stage1 我根本没想过会话并发，直到写 Stage3 网关才意识到同一个 session 的两个请求会同时改一份历史，才补上 Lane 串行化。所以如果你们问我哪块最有价值，我觉得是**每一层的动机我都能讲清楚**——包括哪些是我有意砍掉的。

代码量不算大，但它是完整的：从 LLM 客户端、工具协议、MCP 客户端到网关过滤器和分布式锁，除了 HTTP 路由和 Redis 客户端，几乎没有第三方框架。」
**【点评】**

- ✅ **答得好的地方**：「75 个文件、12000 行」立刻给出量级。四个 Stage 用「解决什么问题」而不是「用了什么技术」来讲，是工程视角不是考证视角。
- ⚠️ **有风险的地方**：「跑到一半暂停、人工确认后恢复」这句会被追。面试官如果熟悉 LangGraph，下一句就是「你这个 interrupt 是节点内主动挂起，还是 executor 扫状态位？」——**实际是后者**（`executor.go:59-65` 检查 `_interrupted`），要能立刻答出来。
- 💡 **更好的说法**：最后那句自我评价可以换成一个具体钩子：「最容易讲错的是 Stage4，因为它的 yml 里写了 `gateway.enabled: true, port: 8081`，但 `cmd/stage4/main.go` 从来没读过这个段——里面那套 REST 接口我写完了，`pkg/workflow/server/handler.go:74-79` 注册了四个路由，但全项目零调用点，一个都访问不到。」**主动埋钩子，比自夸有效得多。**

### Q2 · 面试官的原话问题
> 「你自己觉得这个项目做得最扎实的是哪块？最心虚的是哪块？」
**面试者答：**
「最扎实的是 Stage3 的**热更新链路**。etcd 推一份新 Agent 配置过来，注册表先把旧实例标记成待删除、拒绝新的 acquire，然后建新实例、替换 map 里的指针；旧实例不立刻销毁，而是起一个 goroutine 等它的引用计数归零再销毁——每个 HTTP 请求进业务逻辑之前都会 acquire 一次、defer release 一次。所以一个请求从头到尾看到的是同一个 Agent 实例，不会「一半用旧 prompt、一半用新 prompt」。创建新实例失败还会把旧的 marked 回滚成 0（`registry.go:181`），不会因为一次坏配置把服务挂死。

最心虚的是**测试和压测**。整个仓库 `*_test.go` 是 0 个文件，没有任何 wrk、hey 脚本，README 里也没有 QPS 数字。所以我今天讲的所有并发相关的设计，**都是代码层面的静态分析，没有一个是实测数据**。这一点我不想含糊。」
**【点评】**

- ✅ **答得好的地方**：承认得干脆。**「没有一个是实测数据」这句话本身就是可信度**——面试官会自动把你前面的技术描述降权一半，但剩下的那一半他会信。反过来，吹一个「单机 3000 QPS」，一句「用什么压的？瓶颈在哪？」就崩了。
- ⚠️ **有风险的地方**：「最心虚的是测试」主动把自己钉在短板上，下一句大概率是「那你为什么没写测试？」——必须准备好这个回答（见第四轮 Q2）。
- 💡 **更好的说法**：加半句防守：「没写测试是我的判断失误。我当时把时间全花在把四条线都打通上，以为『能跑通』比『测得细』重要。现在看这个判断是错的——尤其限流那个 lost update，几行 `go test -race` 就能测出来，我是靠读代码才发现的。」

## 【第一轮】Agent 与工具调用

> **这一轮在考什么：** 你是真的写过一个 Agent 循环，还是只是调了个框架。

### Q1 · 面试官的原话问题
> 「先讲 Agent 这条线。ReAct 循环你具体怎么写的？从头到尾说一遍。」
**面试者答：**
「核心循环在 `pkg/agent/base.go:295` 的 `chatWithTools`。入口先分流：`base.go:164` 判断 `toolManager.Size() > 0`，有工具才走 ReAct，没有就直接 `chatDirectly`（`base.go:225`）——单次 LLM 调用，不循环。

进循环后每轮四件事：
第一，**重建工具定义数组**。`base.go:316` 调 `toolManager.GetToolDefinitions()`。注意是每轮重新生成，不是循环外生成一次——因为工具可能被中间插进来，比如 Skill 增强会往 Agent 里注入工具。

第二，调 LLM。`base.go:319` 把当前消息历史和工具定义一起发过去。
第三，检查模型要不要调工具。`base.go:325`，`len(response.ToolCalls) == 0` 就说明模型直接给了最终答案，返回 `response.Content` 结束。

第四，顺序执行工具。`base.go:344` 是个普通 for：先 `toolManager.Get(tc.Name)` 找工具，找不到就塞一条 `role:"tool"` 的『工具 X 不存在』让模型自己纠正；找到就调 `t.Execute(tc.Arguments)`，结果以 `role:"tool"` 追加进 `currentMessages`，进下一轮。

整个循环单 goroutine 顺序执行，工具之间没有并发。10 轮跑满还没结束就返回 error。」
**【点评】**

- ✅ **答得好的地方**：**四步结构**清晰，每句都带行号。「每轮重建工具定义」这个细节特别值钱——它证明你真读过自己的循环，不是凭印象描述。
- ⚠️ **有风险的地方**：「工具之间没有并发」是给自己挖坑。面试官接「为什么不做并发？」，要能答出根因：**`tool.Tool` 接口的 `Execute(args)` 压根不带 `context.Context`（`pkg/tool/tool.go:14`）**，所以并发做不了取消也做不了超时。这是结构性原因，不是懒。
- 💡 **更好的说法**：结尾补一句：「这个循环有个我当时没意识到、后来才发现的坑——`base.go:306` 每轮都从记忆重建消息，意味着**循环内的工具结果不跨轮持久化**，模型看不到上一轮的工具输出。」**主动埋雷，让面试官顺着你的节奏走。**

---

### Q2 · 面试官的原话问题
> 「循环什么时候停？终止条件有几个？」
**面试者答：**
「三个出口，都在同一个函数里。
第一个是正常出口，`base.go:325`：模型这一轮没有返回 tool_calls，直接返回 `response.Content`。

第二个是循环上界，`base.go:312` 的 `for i := 0; i < maxIterations`，跑满 10 轮后跳出，落到 `base.go:384` 返回 error『工具调用次数超过限制』。

第三个是 LLM 报错，`base.go:320-322`，`ChatWithTools` 返回 err 就 `return "", err`。
这里我想主动说一个问题：**第二个出口是有副作用的**。`base.go:158` 在进循环之前已经把 user 消息写进会话记忆了；而跑满 10 轮时是 `base.go:172` 直接 return error，`base.go:177` 那句『写入 assistant 回复』根本走不到。所以这次对话在历史里会留下一条**永远没有回复的 user 消息**，下一轮请求会把它重新发给模型。这是个真实的脏数据问题，我当时没处理。」
**【点评】**

- ✅ **答得好的地方**：按「行号 + 语义」列清三个终止条件，然后**主动把副作用讲出来**。「悬空 user 消息」走查报告里明确标了，你自己先说，面试官就没有得分点可拿。
- ⚠️ **有风险的地方**：问「那应该怎么写？」时，别只说「加个回滚」。更好的答案是：**把记忆写入推迟到对话成功之后**，或者引入显式的「turn 事务」——user 消息和 assistant 消息要么一起进历史，要么都不进。
- 💡 **更好的说法**：三个出口之后补一句框架感的话：「这三个出口对应 ReAct 的三类失败——模型不收敛、预算耗尽、依赖故障。**第三类应该重试，第一类应该接受，第二类应该降级成『就用手上的信息回答』而不是报错。**」这句会让面试官觉得你是在设计，不是在实现。

---

### Q3 · 面试官的原话问题
> 「为什么是 10 ？这个数字怎么来的？」
**面试者答：**
「诚实说，**它是拍的**。
`base.go:296` 是 `maxIterations := 10`，一个局部变量。不是常量，不在 config 里，yml 里也没有对应字段，改它必须改代码重新编译。

我当时的想法很朴素：复杂一点的查询，比如『先搜最近的股票行情，再算我持仓的收益，再对比一下』，大概会走三到四轮工具调用；10 轮留了两倍多余量。超过 10 轮基本可以判定模型在打转——反复调同一个工具、参数不变，这种情况再给 20 轮也没用。

但这个理由是有问题的。真正决定这个数字的是三件事：一是**工具调用轮次的分布**——如果有 P99 轮次数据，取 P99 加一点余量就行；二是**成本上限**——每轮都是一次完整的 LLM 调用，10 轮意味着最差情况 10 倍 token；三是**用户体验的超时预算**——一轮 3 秒，10 轮就是 30 秒，已经超过很多前端的容忍度。

所以我要改的话，第一步不是调数字，是把它挪进 config 变成可配置；第二步是加**重复调用检测**——连续两轮调同一个工具、参数一样，直接中断。这比一个固定的 10 有用得多。」
**【点评】**

- ✅ **答得好的地方**：先认「拍的」，再讲**三个真正决定这个数字的变量**（轮次分布 / 成本上限 / 超时预算），最后给出比「改配置」更本质的方案。这是把短板答成加分题的标准动作：**承认 → 给正确判据 → 给更好方案**。
- ⚠️ **有风险的地方**：「重复调用检测」这个提议很好，但如果追问「怎么判断参数一样？」，`map[string]interface{}` 不能直接 `==`，要么序列化成 JSON 串比对，要么 `reflect.DeepEqual`。**别提出一个自己实现不了的方案。**
- 💡 **更好的说法**：补一个成本视角的具体量：「按 qwen2.5 这类模型的量级，10 轮最坏情况大概是单轮 token 的 6 到 8 倍，因为每轮都要把完整历史重发一遍。」**说得出倍数，你的成本意识就不是空话。**

### Q4 · 面试官的原话问题
> 「工具调用的消息，你是怎么在 LLM 和你的代码之间传的？assistant 消息要带 tool_calls，这个你怎么处理的？」
**面试者答：**
「**这里有问题，我先说结论：我的消息协议是不合法的，接 OpenAI 官方接口一定会 400。**
根因在数据结构上。`pkg/llm/client.go:8-11` 的 `Message` 只有两个字段，`Role` 和 `Content`——**没有 `ToolCalls`，也没有 `ToolCallID`**。

后果是一整条链上的。`base.go:338-341` 要把模型返回的 tool_calls 作为 assistant 消息追加进历史，但我只能写：

```go
currentMessages = append(currentMessages, llm.Message{
    Role: "assistant", Content: response.Content,   // tool_calls 没带
})
```

而 `base.go:377-380` 追加工具结果时写的是 `Role: "tool"`，**没有 tool_call_id**。
更麻烦的是落库那条路。`pkg/memory/conversation.go:78-83` 的 `AddToolCall` 把**工具名当内容**存成一条 `type=tool` 记录，参数和结果都没存；然后 `conversation.go:195-197` 的 `BuildMessages` 把它映射成 `role:"tool"`。所以只要发生过一次工具调用，**后续任意一轮历史里都会出现一条孤立的 `role:"tool"` 消息**——content 是工具名、没有 tool_call_id、前面也没有对应的 assistant tool_calls。

OpenAI 官方接口对这个是硬校验，直接 400。我一直没炸是因为全程用 Ollama 的兼容端点，它对畸形消息比较宽容，会忽略。
改法很清楚：`Message` 加 `ToolCalls` 和 `ToolCallID` 两个字段；`ChatWithTools` 的返回里本来就有 `tc.ID`（`openai.go:123`），透传下来；回填 assistant 消息时带上 tool_calls，工具结果带上 id；`conversation.go` 的 `AddToolCall` 要么存 params 和 result，要么干脆别往记忆里存工具中间态——**只存 user 和 assistant 就够了**。」
**【点评】**

- ✅ **答得好的地方**：**第一句就认了**，没有铺垫、没有「看情况」。然后按「数据结构 → 循环回填 → 记忆落库」三层拆开，每层都指到行号。这是全场技术含量最高的回答，因为它证明的不只是「我知道有 bug」，而是**你知道一个 bug 在这条链上有几个传播点**。
- ⚠️ **有风险的地方**：面试官很可能追问「Ollama 为什么能容忍？它实现是什么样的？」——超纲，别硬答：「我没看过 Ollama 的前端实现，我只知道行为上它把没有 `tool_call_id` 的 tool 消息当普通上下文，不做配对校验。**这是我的观察，不是我的原理。**」
- 💡 **更好的说法**：收尾加一句工程味的话：「这个问题的本质是我的 `llm.Message` 是**按文本模型设计的**，后来加工具调用时没回头改它，就在中间夹了一层隐式约定。如果重做，我会让 `Message` 直接对齐 OpenAI 的 wire format，不自己发明一个更简单的中间结构——**这一类抽象迟早要还。**」

### Q5 · 面试官的原话问题
> 「工具描述怎么写给模型的？参数 schema 呢，必填参数怎么标？」
**面试者答：**
「工具定义在 `pkg/tool/manager.go:75-105` 的 `GetToolDefinitions` 里生成，标准 OpenAI tools 数组：`type: "function"`，带 name、description、parameters。

**这里有一个我写的时候就知道、但没改的问题：必填参数没有告诉模型。**
`pkg/tool/tool.go:18-23` 的 `ParameterDef` 定义了 `Required bool` 字段，四个内置工具也都认真标了——比如 `websearch.go` 里 `query` 是 `Required: true`。但生成 schema 时（`manager.go:82-98`）我拼的是：

```go
params[name] = map[string]interface{}{
    "type": param.Type, "description": param.Description,
}
```

`param.Required` **没被写进去**，也没生成 JSON Schema 规范里的 `required: [...]` 数组。所以模型完全不知道哪些参数必填，只能从 description 的文字里猜。**`Required: true` 在我代码里实际上是个装饰。**

MCP 那边一样：`pkg/mcp/adapter.go:36-57` 把 MCP 的 `inputSchema` 转成 `ParameterDef` 时只解析了 `properties`，`required` 数组也被丢了。所以不管工具是本地还是远程，模型看到的 schema 都是残缺的。

改起来很简单：`manager.go` 里多生成一个 `required` 数组把 `Required: true` 的参数名收集起来；adapter 那边把 MCP 的 `required` 读出来映射到 `Required`。两处都是十几行。

顺带说一个相关的问题：**参数校验实际上不存在**。没有 JSON Schema 校验器，就是每个工具自己在 Execute 里做类型断言，断言失败返回一个错误 ToolResult。模型给错参数的时候是靠工具自己兜底。」
**【点评】**

- ✅ **答得好的地方**：**「Required: true 在我代码里是个装饰」是本轮金句。** 「本地工具和 MCP 工具都丢了 required」这个横向对比，说明你不是单点排查，是找了一类问题的共性。
- ⚠️ **有风险的地方**：说「参数校验实际上不存在」后，追问会是「那工具执行时参数错了会怎样？」——标准答案是走到 `base.go:361` 的 err 分支，回喂一条 `role:"tool"` 的『工具执行失败』让模型自愈。**这条链路要背熟，因为它是你少数做对的地方。**
- 💡 **更好的说法**：升维一下：「这类问题的共性是我在**每一层都自己发明了一个更简单的中间结构**——`llm.Message` 简化掉 tool_calls，`ParameterDef` 简化掉 JSON Schema。简化在写的时候很爽，代价是**模型看到的东西和你以为它看到的东西不一致**。LLM 工程里这种不一致特别贵，因为调不出来。」

### Q6 · 面试官的原话问题
> 「MCP 这块，你自己写的客户端还是用了别人的库？」
**面试者答：**
「自己写的，全部手写，只用标准库。`pkg/mcp/` 三个文件：`client.go` 是 JSON-RPC 客户端，`stdio_transport.go` 和 `http_transport.go` 是两种 transport，`adapter.go` 把 MCP 工具适配成我自己的 `tool.Tool` 接口。

**握手是完整的**，这点我比较有把握。`client.go:98-131` 的 `initialize`：先发 `initialize` 请求，带 `protocolVersion: "2024-11-05"`、capabilities 声明要 tools、clientInfo；拿到响应记 serverInfo；**然后发 `notifications/initialized` 通知**；最后调 `tools/list` 拿工具列表。顺序和规范一致。

这里有个细节我特意处理过：发 initialized 通知我单独写了一个 `SendNotify`（`client.go:300-315`），不复用 `Send`——因为 `Send` 是「写请求 + 读响应」的同步语义，而 initialized 是个 notification、**不返回响应**。用它发就会阻塞在读响应上，把初始化挂死。这个坑我是踩过才知道的。

transport 抽象在 `transport.go:7-22`，五个方法：Connect / Send / SendNotify / Close / IsAlive。stdio 用 `exec.CommandContext` 起子进程，管道加换行分隔 JSON，这是 MCP stdio 的规范做法。http transport 是 `http.Client{Timeout: 30s}`，但它的 `Connect` 是空实现，而且声明了 `Accept: text/event-stream` **却没有 SSE 解析**（`http_transport.go:54`），直接把 body 丢给 `json.Unmarshal`——真实的 Streamable HTTP MCP Server 返回 SSE 时会解析失败。这条路径我没测过。

还有一点我觉得是这个项目结构上最干净的地方：`adapter.go:12-23` 把 MCP 工具适配成了同一个 `tool.Tool` 接口。所以 ReAct 循环**零改动**地同时支持本地和远程工具——循环里只有 `toolManager.Get(name)` 和 `t.Execute(args)`，它不知道这个工具背后是本地函数还是一个子进程。」
**【点评】**

- ✅ **答得好的地方**：「用 `Send` 发 notification 会阻塞」是**全篇最有说服力的证据**——只有真写过的人才会为一个 notification 单独写方法，也才知道为什么。主动划清「http transport 没测过」的范围，反而显得可信。
- ⚠️ **有风险的地方**：面试官会从 `IsAlive` 追进来（见 Q7）。**不要在这里就把 IsAlive 讲了**，留着让他问——他问出来你答是「你懂」，你不问他先讲是「你心虚」。节奏感也是评分项。
- 💡 **更好的说法**：顺手把命名债交代掉：「`pool.go` 那个结构叫 pool，但它是 per-agent 的连接注册表，`map[agentID]map[serverName]*Client`。没有池大小、没有复用、没有空闲回收、没有后台探活。**同一个 MCP server 被两个 Agent 引用会起两个进程。** 我把名字起大了。」

### Q7 · 面试官的原话问题
> 「你说 MCP 是真实现的。那我问个具体的：你怎么知道一个 MCP server 还活着？」
**面试者答：**
「**这里有一个 bug，而且是那种『写了检测逻辑但永远不会触发』的 bug。**
`pkg/mcp/stdio_transport.go:117-123`：

```go
func (t *StdioTransport) IsAlive() bool {
    if t.cmd == nil || t.cmd.Process == nil { return false }
    return t.cmd.ProcessState == nil
}
```

`ProcessState` **只有在 `Wait()` 被调用之后才会被赋值**。而全仓库找不到任何一处调用 `t.cmd.Wait()`——我一个文件一个文件搜过，零命中。
所以实际行为是：子进程崩溃了、被 Kill 了、或者我主动 Close 了，`ProcessState` 依然是 nil，`IsAlive()` 依然返回 `true`。**崩溃检测和重连逻辑永远不会触发。** Close 之后再调工具，会得到『发送请求失败: file already closed』，而不是触发重连。

修法两步。第一步，起进程之后立刻开一个 goroutine 去 `cmd.Wait()`，把返回的 error 存到一个字段，`IsAlive` 改成读这个字段加一个 atomic 的 exited 标志。第二步更彻底：**主动探活**——MCP 协议里有 `ping` 方法，可以在 GetStatus 或者定时任务里发一个带超时的 ping，比看进程状态可靠，因为**进程活着不代表它还能响应**。

还有个相关的：`Connect` 里用 `exec.CommandContext(ctx, command, args...)`，这个 ctx 是调用方传进来的，它被取消**整个 MCP 子进程会被杀掉**。而且 `Process.Kill()` 只杀直接子进程不杀进程组——command 是 `go run xxx.go` 的话，go run 会再 fork 真正的二进制，Kill 掉 go run 之后那个孙进程就成孤儿了。这两个我都知道该修，没修。」
**【点评】**

- ✅ **答得好的地方**：**「一个文件一个文件搜过 `Wait()`，零命中」** ——这个动作本身就是加分项，说明你不是「记得好像没调」，是「查过」。然后把修法分两步，第二步（主动 ping）比第一步（修正 ProcessState）高一档，展示了你知道「进程活着 ≠ 服务可用」。
- ⚠️ **有风险的地方**：这条 bug 有一个**连锁后果**，面试官如果读过代码一定会问：它会让热更新之后 MCP 工具永久失效。见第四轮 Q3——**这一刀必须提前准备**。
- 💡 **更好的说法**：补一个进程管理常识：「Go 里管子进程，`Wait()` 不只是为了拿退出状态，它还有回收资源的作用——不 Wait 在 Unix 上会留僵尸进程。所以这个 bug 是双重的：既检测不到崩溃，又在漏资源。」

### Q8 · 面试官的原话问题

**【点评】**

- ✅ **答得好的地方**：**「grep 过 `{{`，零命中」** 极有力量——它把「我不知道」变成了「我验证过我不知道」。而且把 Skill 和 Stage4 工作流引擎的**职责边界**讲出来了，这是设计层的表述。
- ⚠️ **有风险的地方**：追问大概率是「Skill 匹配怎么触发的？」答案是两条路径：关键词匹配和 LLM 匹配（`manager.go:126-138`）。**但关键词匹配对中文是失效的**——`keywordMatch`（`manager.go:163-173`）用 ASCII 空格和标点分词，中文 description 没这些分隔符，整段变成一个 token，`strings.Contains` 几乎不可能命中。所以关键词路径**实质上永不命中**，全靠 LLM 匹配，而 LLM 匹配是**每条消息一次额外的 LLM 调用**（`manager.go:197`），延迟和成本都翻倍。**这段要背下来。**
- 💡 **更好的说法**：再补一个更尴尬的自查：「Skill 热更新也是死代码。`manager.go:86-94` 判断文件 mtime 变化就重新加载，但 `skillsModTime` 这个 map 从 `LoadAll` 到 `Register` 都没写过——**判断条件要求它已存在，而它永远不存在，所以这个分支永不命中。改了 SKILL.md 永远不会生效**，只是每次 Get 多一次 `os.Stat`。」

### Q1 · 面试官的原话问题
> 「你的 LLM 客户端怎么封装的？抽象在哪一层？」
**面试者答：**
「接口在 `pkg/llm/client.go:40-52`，四个方法：`Chat`、`ChatWithTools`、`Embed`、`EmbedBatch`。实现分两层：`openai.go` 是具体的 OpenAI 兼容客户端，包了 `go-openai`；上面 `gateway.go` 的 `LLMGateway` 按 `modelRef` 做多模型路由——Agent 配置写 `modelRef: "fast"` 或 `"quality"`，gateway 路由到不同的底层客户端，构造时预创建好，存在一个 `sync.Map` 缓存里（`gateway.go:17, 30-35`）。

- ⚠️ **有风险的地方**：开头可以更硬：「这一层我做对的事只有一件——**把多模型路由做成了对 Agent 透明的装饰器**；做错的事有一堆，最主要的是**所有失败模式都是静默的**。」「一件对、一堆错」的结构会让人更愿意听下去。
- 💡 **更好的说法**：把静默回落和后面的 temperature 串起来：「这两个是同一类病——**配置和运行时的连接靠人肉保证，没有任何机制校验**。」这句话提前埋下，第三轮的 `default-user` 会和它形成一条完整的论证线。

### Q3 · 面试官的原话问题
> 「如果上游 LLM 慢，或者挂了，你的服务会怎么样？」
**面试者答：**
「**没有超时、没有重试、没有熔断、没有降级。四个都没有。**
先说最要命的超时。`openai.go:29-35` 我用的是 `openai.DefaultConfig` 加 `NewClientWithConfig`，底层走 `http.DefaultClient`——**Timeout 是零值，也就是不超时**；embedding 那边我自己建了个 `&http.Client{}`（`openai.go:42`），同样没有 Timeout。config 里也**没有 timeout 字段**，我想配都没地方配。

更上游一层：stage1 和 stage2 传进 Agent 的是 `context.Background()`（`cmd/stage1/main.go:189`、`cmd/stage2/main.go:348`），没有 deadline。Stage3 走 HTTP 请求的 ctx，客户端断开会取消——**但取消只是停止等待，不会告诉上游 LLM 停止生成**，而且因为没有超时，客户端不断开就是无限等。

所以真实行为是：**LLM 端点卡住，我的服务跟着卡住，一个请求占着一个 goroutine 和一条会话 Lane，永远不会自己退出。** 这不是「慢」的问题，是「雪崩」的问题——那个 session 连续来几个请求，Lane 锁会被卡满，其他请求全在 `SYSTEM_BUSY` 上排队。

重试也没有，因为超时都没有，重试的前提就不成立——你不知道该在多久之后重试。
修的顺序应该是：**第一步加 Timeout**，`http.Client{Timeout: 60 * time.Second}` 加 ctx deadline；**第二步加重试**，但要区别对待——网络错误和 5xx 可以重试，4xx 重试是浪费；**第三步才是熔断和降级**。这三步的优先级不能反，**因为『没有超时的重试』是最危险的组合**，它会成倍放大对上游的压力。

还有一个我漏掉的：重试应该只在**单次 LLM 请求**这一层做，**不要在 ReAct 循环那一层做**——循环里前面可能已经执行过工具了，重试会把工具重复执行。」
**【点评】**

- ✅ **答得好的地方**：「**没有超时的重试是最危险的组合**」——这句话一出来，面试官就知道你不是在背四个名词，你理解它们之间的依赖顺序。把「卡住的 goroutine 占住会话 Lane」串起来是**跨模块影响分析**，本轮最高分点。
- ⚠️ **有风险的地方**：说「取消不会告诉上游停止生成」的时候要小心——在 HTTP 层面，ctx 取消实际上会关闭 TCP 连接，**大多数 LLM 服务端会因此中止生成**。更准确的表述是：「取消会关闭连接，服务端大概率会中止；但**取消传播到 MCP 工具那边就被切断了**——`adapter.go:61` 用的是 `context.Background()`，把调用方的 ctx 彻底断了。」
- 💡 **更好的说法**：给一个数字感收尾：「按现在这个实现，一个卡住的请求会占着 goroutine 无限等。goroutine 确实便宜，但**每个卡住的请求背后是一个真实 TCP 连接和一个真实的 LLM 后端 worker，后端那边的并发是有限的**。所以这不是『Go 能扛住』的问题。」

### Q4 · 面试官的原话问题
> 「流式输出做了吗？token 用量和成本怎么统计的？」
**面试者答：**
「**两个都没做。**
流式方面，全仓搜过，唯一一个 `text/event-stream` 出现在 `pkg/mcp/http_transport.go:54`，那是 MCP 的，跟 LLM 无关。LLM 这条路径全是 `CreateChatCompletion` 的非流式调用，等整个回答生成完才返回。用户体感是：发一条消息，白屏等 5 到 30 秒，然后整段话一次性出来。**流式的价值不是快，是感知快**——第一个 token 出来通常只要几百毫秒。

token 统计反过来，是**很小的一件事**——`resp.Usage.PromptTokens / CompletionTokens` 就在响应体里，加起来存一下就行。这个没做纯粹是我漏了，没有借口。」
**【点评】**

- ✅ **答得好的地方**：**「流式输出是感知快，不是真的快」** 是内行话。把流式的成本拆到五层，说明你评估过；然后老实承认 token 统计是漏的——**两件事分开定性：一个是有意识砍的，一个是疏忽**，这种区分度会让面试官觉得你在认真复盘。
- ⚠️ **有风险的地方**：说流式 tool_calls 分片时别说得太细。如果真追问「分片怎么拼？」：按 `index` 聚合，`arguments` 是字符串增量拼接，最后一个 chunk 才完整解析。没把握就说「我知道它有 index 聚合和 arguments 拼接这两个机制，具体实现我没写过」。
- 💡 **更好的说法**：补一个自己没解决的问题：「流式和 Lane 串行化的组合还有一个我没想清楚的——**同一会话要串行，但流式期间这个连接要持有多久？** 用户看两行就关页面，Lane 锁要不要立刻释放？我倾向于流式下用『首 token 后释放锁』，或者干脆放弃这个会话的串行保证，但我没有结论。」**说出一个自己没解决的问题，比给一个假答案更有价值。**

### Q5 · 面试官的原话问题

### Q3 · 面试官的原话问题
> 「限流具体用了什么算法？讲讲实现。」
**面试者答：**
「**有两套，而且它们不一样，这是我先要交代的。** 本地的 `RateLimitFilter` 是**令牌桶**（`pkg/gateway/ratelimit.go:74-127`）；分布式的 `checkRateLimit` 是 **Redis 固定窗口**，`INCR` 加 `EXPIRE`（`distributed.go:189-198`）。两套并存，语义不同。

令牌桶的实现我讲一下，因为**它有两个 bug 是我后来才发现的**。桶的结构是 `tokens atomic.Int64`、`lastRefill atomic.Int64`、`capacity`、`refillRate`，外加一个 `sync.Mutex`。

**第一个问题：`refill()` 每次请求都进全局 mutex**（`:111`），即使根本不需要补令牌。1000 QPS 就是 1000 次全局互斥/秒，这是纯粹的串行点。正确做法是让 `lastRefill` 也用 CAS 抢，**抢到的那个 goroutine 才去补令牌**，抢不到的直接跳过。

**第二个问题更严重：`refill` 里有 lost update**（`:120-126`）：

```go
current := l.tokens.Load()
newCount := current + newTokens
if newCount > l.capacity { newCount = l.capacity }
l.tokens.Store(newCount)      // 裸 Store，不是 CAS
```

`Load` 和 `Store` 之间没有 CAS，而这段时间里并发的 `TryAcquire` 可能已经 CAS 扣掉过令牌——**然后我这一发 `Store` 把它覆盖回去了。多退令牌，等于超发。**

根因是我把 `tokens` 当临界区外的变量在用：我用了 atomic 类型，就以为它是原子的，**但『读-算-写』这个组合不是原子的**。光有 atomic 类型不等于有原子性。
**第三个问题比较反直觉**：`elapsed / 1000` 是整数除法向下取整（`:119`），然后 `lastRefill.Store(now)` 把时间戳直接推到当前。所以两个请求间隔 1.5 秒，我只会补 1 秒的量，**丢掉 0.5 秒**。结果是**限流实际比配置更严**，跟大多数令牌桶实现的偏差方向是相反的。

修法三个：`refill` 改成 CAS 抢 `lastRefill`；令牌数更新改成 CAS 循环；时间量化改成保余数——补完令牌后 `lastRefill` 只加 `(elapsed/1000)*1000` 而不是 `now`。或者更干脆，用 `golang.org/x/time/rate`。」
**【点评】**

- ✅ **答得好的地方**：**「我用了 atomic 类型，就以为它是原子的」** ——这是本轮最值钱的一句，它是一个**可迁移的教训**，面试官会记住。三个 bug 按「性能问题 → 正确性问题 → 语义偏差问题」排序，也是对的结构。
- ⚠️ **有风险的地方**：说「用 `x/time/rate`」后会被问「它怎么解决这些问题的？」——它内部仍然有 mutex，**它是把 `Load-计算-Store` 整段放进锁里，从而消除了 lost update**，取舍是放弃一点性能换正确性。你的问题是**既没换来正确性，也付了锁的代价**。这个对比要能说出来。
- 💡 **更好的说法**：加一句更狠的自评：「这三个里只有第三个（量化丢余数）是设计取舍，前两个是纯粹的错误。**而且它们都是『读一遍代码就能发现、跑 `go test -race` 就能暴露』的类型，我一个都没做**——这又回到我前面说的，零测试这个洞会以各种形式漏出来。」

### Q5 · 面试官的原话问题
> 「同一个会话同时来两个请求会怎么样？你怎么处理的？」
**面试者答：**
「**这里是我这个项目里少数几个我觉得做对了的设计，叫 Lane 会话串行化。**
解决的问题是：同一个 session 的两个请求并发进来，会同时读写同一份 `ConversationMemory`——单条 append 有锁不会崩，但会**交错**：请求 A 读到的历史里没有 B 的消息，两个请求都基于残缺的历史回答，然后两条消息又都写进同一份历史。用户观感是「答非所问」。

Lane 的做法是给每个 session 一条「车道」，用 CAS 抢占（`pkg/gateway/lane.go:52-68`）：

```go
func (l *Lane) TryEnter() bool {
    swapped := l.processing.CompareAndSwap(0, 1)
    if swapped { l.queueSize.Add(1) }
    return swapped
}
func (l *Lane) Leave() { l.processedCount.Add(1); l.processing.Store(0) }
```

网关侧在 `gateway.go:117-131` 轮询抢，抢不到就 50ms 重试，最多 600 次也就是 30 秒，超时返回 `SYSTEM_BUSY`，拿到之后 `defer lane.Leave()`。

分布式模式下语义一样，只是用 **Redis 的 `SET NX PX` 锁**加 100ms 轮询（`distributed.go:201-221`）。锁的释放是 **Lua compare-and-delete**（`pkg/redis/client.go:145-159`）——先比对 value 是不是自己的 requestID，是才 DEL。**这个设计是对的**，它解决了「锁超时自动过期之后，原来那个持有者又把别人的锁删了」这个经典问题。

我没做会话粘性——全仓搜过 consistent hashing、hashring、ketama，零命中。所以同一会话在多实例下可能落到任何一台，靠 Redis 锁做**跨实例串行**。
**但有三个问题我要主动说。一是分布式锁没有看门狗续期**，锁 TTL 是 60 秒（`distributed.go:45-49`），如果一次 LLM 调用要 60 秒以上，**锁会在业务没做完的时候自动过期**，第二个请求进入同一会话 → 两个请求并发读写。**二是轮询是忙等，而且本地模式不看 ctx**——`gateway.go:120-126` 那个循环里只有 `time.Sleep`，没有 `select ctx.Done()`，客户端断开了这个 goroutine 还会空转满 30 秒（分布式那边 `distributed.go:213-215` 有 select ctx，好一点）。**三是 `requestID` 跨实例不唯一**，`distributed.go:91` 用的是 `time.Now().UnixNano()`，两台机器的时钟可能撞车，一旦撞上 A 的 Unlock 有机会删掉 B 的锁——Lua 脚本机制是对的，但我的 requestID 生成有问题，应该用 UUID 或 `instanceID + nanotime`。」
**【点评】**

- ✅ **答得好的地方**：**把 Lane 当「设计」而不是「实现」来讲**——先讲解决什么问题（历史交错），再讲机制（CAS），再讲分布式版本，最后讲 Lua 释放锁是对的。这个顺序会让面试官觉得你有系统思维。主动说「没做会话粘性」也很关键，否则被问到「多实例下同会话怎么办」会显得是漏洞而不是取舍。
- ⚠️ **有风险的地方**：说「Lua 是对的」时**要立刻补上 requestID 的漏洞**，否则面试官会认为你没看出这个破绽。**「机制对、实现有漏」这个双面表述必须连在一起说。**
- 💡 **更好的说法**：给一个更好的方案收尾：「30 秒轮询加 50ms 粒度，在有等待者的时候是 N 乘 20 QPS 的 Redis 往返，而且平均多 25ms 延迟。更好的做法有两个方向：**用一致性哈希把会话钉到实例上，本地串行就够，Redis 锁只作兜底**；或者用 Redis Pub/Sub 唤醒，不要轮询。我选了最土的那个，因为它在功能上是正确的。」

### Q6 · 面试官的原话问题
> 「Redis 那块的分布式锁，详细讲讲加锁和释放。」
**面试者答：**
「加锁是 `TryLock`，一个 `SET NX PX`（`redis/client.go:136-142`）——key 是 `bitguide:lane:{sessionID}`，value 是 requestID，带 TTL。释放是 `Unlock`，我用了 Lua 脚本（`:145-159`）：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1]) else return 0 end
```

它的意义是**只有锁的持有者才能删锁**。不用它的话会有这个问题：请求 A 拿到锁、本该 10 秒释放但它卡了 70 秒；锁在 60 秒时自动过期；请求 B 拿到锁开始干活；A 醒了，一发 DEL 把 B 的锁删了——C 就能进来，B 和 C 并发。Lua 通过比对 value 避免了这个。

**但这个脚本有三处我没做好。第一，没有 watchdog 续期**——这是最根本的，Lua 保证的是『不会误删别人的锁』，**但它不能阻止锁在业务没做完时过期**。60 秒 TTL 到点就没了，不管我有没有做完。正确做法是加看门狗：拿到锁后起一个后台 goroutine，每隔 TTL 的三分之一去检查业务还在不在跑，还在就 `EXPIRE` 续到满 TTL。Redisson 就是这个机制。

**第二，释放锁用的是请求的 ctx。** `distributed.go:99` 的 `defer dg.releaseLaneLock(ctx, laneKey, requestID)`，这个 `ctx` 是 `r.Context()` 传下来的。**客户端一断开 ctx 就被取消，Lua 脚本调用直接失败，锁不释放，卡满 60 秒 TTL**，这个会话的后续所有请求全部 `LANE_BUSY`。修法是用一个独立的、带自己超时的 context，比如 `context.WithTimeout(context.Background(), 3*time.Second)`。

**第三，固定窗口的 `Expire` 非原子而且错误被丢。** `redis/client.go:161-171` 的 `IncrWithExpire` 是 `INCR` 之后再 `Expire`，而 `:169` 的**返回值被丢弃了**。如果 `INCR` 成功但 `EXPIRE` 因为网络抖动、超时或者进程崩溃没执行成功，**这个 key 就没有 TTL，该用户被永久限流**。正确做法是用一条 Lua 脚本把两条命令原子化。

还有一点：**Redis 挂了的时候 Lane 锁路径不是 fail-open 的。** `acquireLaneLock` 在 Redis 不可用时会一直失败重试，**轮询满 30 秒才返回 `LANE_BUSY`**——Redis 故障时每个请求挂 30 秒，**等于自我 DoS**。而同一个文件里的限流 `checkRateLimit`（`distributed.go:194-196`）在 Redis 出错时返回 `true`（放行）。**同一个服务里两个组件对 Redis 故障的行为不一致**，这是我设计时没想清楚的地方。」
**【点评】**

- ✅ **答得好的地方**：三处都指到行号，而且**最后那条「同一服务里两个组件对 Redis 故障行为不一致」是这一轮的最高分点**——它不是找 bug，是发现**设计原则层面的不一致**。面试官会认为这个人有能力做架构评审。顺带把「降级是 fail-open 对的设计，但代价是 Redis 挂了等于没限流」说清楚，也很加分。
- ⚠️ **有风险的地方**：说 `Expire` 被丢弃导致永久限流时**别说得太绝对**——go-redis 的 `Expire` 在 key 已被删时返回 false，正常流程里也可能。严谨的表述是：「**如果 INCR 成功但 EXPIRE 没执行成功**，key 就没有 TTL。这不是必然发生，是一个存在但概率不高的坏路径。」
- 💡 **更好的说法**：补一个更本质的方案：「比 watchdog 更彻底的做法是**放弃分布式锁，用一致性哈希把会话粘到实例**——分布式锁本身是很重的方案，它把一次简单的串行化变成了 N 次 Redis 往返。**能在本地解决的问题，不要用分布式锁解决。**」

### Q7 · 面试官的原话问题
> 「分布式会话记忆怎么做的？跨实例能共享历史吗？」
**面试者答：**
「**我要先给一个让我很尴尬的结论：Redis 里的会话记忆目前只写不读。**
结构是 `DistributedMemory`，key 是 `bitguide:session:{sessionID}`（`pkg/memory/distributed.go:52-54`），value 是**整个会话的 JSON 快照**（`:26-30`），写入是 `saveToRedis`（`:93-105`），**全量 JSON `SET`**，每次覆盖，没有 Hash 或 List 增量追加，没有压缩、没有分页。TTL 默认一小时。

**问题在于 `DistributedMemory.BuildMessages` 和 `GetHistory` 没有任何生产调用方。** LLM 拿到的上下文来自 `BaseAgent.session.Memory.BuildMessages`（`base.go:232, 306`），那是 `BaseAgent` 内部一个**每个实例各自的内存 `sync.Map`**（`base.go:31, 388-396`）。所以端到端的行为是：请求进来写一条到 Redis，响应完再写一条，**但读从来只读本地内存**。换一个实例、或者服务重启，**LLM 拿不到任何历史**。『分布式记忆』这个功能在行为上不成立——**数据存了，没接回上下文**。

**第二个问题：就算接回去了，还有陈旧缓存回写导致的丢消息。** 假设 A 和 B 两个实例，A 的本地缓存停在版本 5。B 处理了一个请求，写了版本 6 到 Redis。然后 A 处理下一个请求——A 用自己版本 5 的快照加上新消息变成 6'，**全量覆盖写回 Redis**，B 那条消息就没了。这里要澄清一点：**Lane 锁防住了并发交错，但防不住这个**——因为这不是并发问题，是**缓存失效**问题。Lane 锁只解决『同时写』，不解决『写旧数据』。

修法三条路，从轻到重：**写完就 `DEL` 本地缓存**，下次读强制回源；**加版本号或者用 Redis 的 `WATCH` 做乐观锁**，版本不匹配就重读重试；**把 Redis 当唯一数据源，本地不缓存**——语义最清晰，但每次请求多一次往返，还要考虑 Redis 挂了的降级。

还有一个相关的问题：**Redis 挂了是静默失败**。`GetJSON` 失败被当成『key 不存在』，**静默新建一个空会话**（`distributed.go:71-85`，错误被 else 吃掉了）；`saveToRedis` 失败只打一行 `clog.Error`（`:102-104`），**请求照样成功返回，记忆丢了上层完全无感知**。而 `/health` 里的 `redisConnected` 读的是 `cfg.Redis.Enabled`（`main.go:334`）——**配置开关，不是 Ping 结果**，所以 Redis 挂了健康检查依然返回 `true`。**『健康检查撒谎』比没有健康检查更危险。**」
**【点评】**

- ✅ **答得好的地方**：**「只写不读」自己先说，不加修饰。** 然后主动区分「并发问题」和「缓存失效问题」——很硬的分布式基础。最后那句「健康检查撒谎比没有健康检查更危险」是可以被面试官记住的句子。
- ⚠️ **有风险的地方**：`ClearSession` 也有同类问题——HTTP handler 调的是基础版 `gw.ClearSession`（`main.go:474`），而清 Redis 的逻辑在 `DistributedGateway.ClearSession`（`distributed.go:182-187`），**那个方法没有任何调用方**，所以 DELETE 会话清不掉 Redis。被问到就直接说。
- 💡 **更好的说法**：给一个更本质的框架：「根因是我**在本地内存和 Redis 之间没有一个明确的『谁是 source of truth』的决定**。两套都写了，读走本地、写走 Redis，等于两套状态同时存在但没有同步协议。**分布式系统里最危险的不是选错，是不选。**」

### Q8 · 面试官的原话问题
> 「etcd 这块，配置热更新怎么做的？」
**面试者答：**
「流程是：`ConfigWatcher` 先 `Get` 一次拿全量配置（`pkg/dynamic/watcher.go:95-122`），然后起 goroutine `Watch` 前缀（`:119-142`），收到事件 `handleEvent`，再 `notifyListeners` 同步通知所有监听器；监听器里的 `DynamicConfigManager` 按 key 类型分发——Agent 配置走 `registry.Register`，知识库配置走文档摄取。

**两个 bug，第二个更严重。**
**第一个：Get 和 Watch 之间会丢事件。** `loadAllConfigs` 拿到了 `resp.Header.Revision` 然后**把它丢掉了**，Watch 的时候是 `clientv3.WithPrefix()`——**没有 `WithRev(...)`**。etcd 的标准做法是 Get 拿 revision N，然后 `Watch(..., WithRev(N+1))`，这样两次调用之间的 PUT 和 DELETE 都不会漏。我现在这个写法，**从 Get 返回到 Watch 真正建立之间落下来的所有配置变更全部丢失**。窗口很小但真实存在，而且丢了之后**没有任何补正机制**。

**第二个：watch 出错之后永久退出，静默失效。** `watcher.go:130-135`：

```go
if watchResp.Err() != nil {
    clog.Error("[Dynamic]", "监听到配置变更事件失败: %v", watchResp.Err())
    return        // ← 直接退出，永不重连
}
```

`WithPrefix` 的 watch 在 etcd 集群做 compaction 之后会返回一个**不可恢复的错误**——典型是 `required revision has been compacted`。这时这个 goroutine 就打一行日志然后 return。**后果是：配置热更新从此静默失效，没有任何人知道。** 没有重启、没有告警、没有降级到轮询兜底。服务看起来一切正常，但 etcd 里改的任何东西都不生效了——**这是最坏的一种故障，因为它不报错**。

修法是标准三件套：**watch 加重连循环**，用带退避的 for 包住，出错就重建；**compaction 错误要先重新 `Get` 一次全量配置再 Watch**，因为 revision 已经不可用了；**加一个健康指标或告警**，让「watch 协程活着」这件事可以被观测。

还有第三个问题顺带说：**`notifyListeners` 是在 watch goroutine 里同步执行的**（`watcher.go:194-198`），而通知链最后会走到 `factory.CreateAgentFromConfig`——那里面会 **fork MCP 子进程并做 JSON-RPC 握手**，是网络 IO。所以 watch 循环会被业务代码阻塞，后面的事件排队。`config.go:107` 我配了 `WatchQueueSize: 100`，**但代码里从来没读过它**。另外这里也没有 panic recover——任何一个监听器 panic，watch 协程就没了。

还有一个更尴尬的：`watcher.go:77-79` 的默认前缀我写的是 `/bitguide/config/`，而 `stage3.yml:58` 配的是 `/bitguide-go/config/`，**两者不一致**，现在是因为 yml 里显式配了才对得上。**漏配一次，watch 会静默监听不到任何东西，而且不报错。**」
**【点评】**

- ✅ **答得好的地方**：**把 compaction 这个具体错误名说出来**，是「我真踩过」的信号。把「静默失效」定性为最坏的故障类型（因为它不报错），是运维视角的判断。顺带发现 `WatchQueueSize` 配了不用、默认前缀和 yml 不一致——**两个「配置当文档写」的同族实例**，和后面第二轮 Q2 形成呼应。
- ⚠️ **有风险的地方**：追问「那你怎么发现 watch 挂了的？」——**正确答案是发现不了**，因为现在没有任何监控。诚实答法：「发现不了。`/health` 不检查 etcd 连通性，也没有 watch 协程的存活指标。**这是个可观测性的洞，不是代码的洞。**」
- 💡 **更好的说法**：给一个可迁移的判断框架：「我数了一下，这个项目里至少五个静默失败——watch 退出、空响应当成功、Redis 静默失败、健康检查读配置、前缀漏配不报错。它们是我最想统一清理的一类债，因为**它们不产生告警，只产生『看起来正常』**。」

### Q9 · 面试官的原话问题
> 「Agent 热替换的时候，正在跑的请求怎么办？我看你有引用计数。」
**面试者答：**
「**这是我这个项目里我觉得设计得最好的一块，我详细讲。**
问题：etcd 推一份新的 Agent 配置过来，如果直接把旧实例销毁换成新的，在途请求会撞两种情况之一——要么用了已关闭的 Agent，要么**一个请求跑到一半 Agent 被换了，前半段用旧 prompt、后半段用新 prompt**。第二种更危险，因为它不报错。

方案是**引用计数加优雅销毁**，分三层。

**第一层是数据结构**（`pkg/agent/registry.go:24-31`）：每个 `AgentEntry` 带一个 `refCount atomic.Int32` 和一个 `marked atomic.Int32`，marked 表示「已被标记待删除」。

**第二层是请求侧**（`gateway.go:99-115`）：每个请求在进业务逻辑之前先 `AcquireRequest()`，`defer ReleaseRequest()`。acquire 的逻辑是（`registry.go:34-40`）：先检查 marked，是 1 就返回 false 拒绝；否则 refCount 加一。

**第三层是替换流程**（`registry.go:154-199` 的 `doUpdate`）：先把旧 entry `markForDeletion` 阻止新请求 acquire，然后创建新实例，成功后替换 map 里的指针，最后**起一个异步 goroutine `gracefulDestroy`**，等旧实例引用计数归零再真正销毁。

所以一个请求从 acquire 到 release 之间，**它拿到的 Agent 实例不会被销毁，全程是同一个实例**，不会出现「一半旧一半新」。

两个细节我觉得做得不错：请求拿到的是已被标记的旧 entry 时，**它会自动刷新到最新 Agent**（`gateway.go:101-108`）；新实例创建失败会**把旧实例的 marked 回滚成 0**（`registry.go:181`），不会因为一次坏配置把服务挂死。

**但有四个问题。一是 `acquire` 有 TOCTOU 窗口**（`registry.go:34-40`）：`if e.marked.Load() == 1 { return false }` 和 `e.refCount.Add(1)` 是两步，中间可以插入 `markForDeletion`，窄窗口下会出现「请求通过了检查，但 marked 已生效，waitForRelease 看到 refCount 是 0 就返回，旧 Agent 被 Close，请求随后在已关闭的 Agent 上跑」。修法是把「检查并自增」合成一个原子操作——用 mutex，或者把两个状态打包成一个 int64 用一次 CAS 完成。

**二是持写锁做重活。** `RegisterWithSource` 和 `doUpdate` 都在**持有写锁时创建 Agent**（`registry.go:91-117, 154-199`），而创建 Agent 会 fork MCP 子进程、做 JSON-RPC 握手。`Unregister` 更狠，在**持写锁时同步等最多 5 秒**（`:120-144` 的 `waitForRelease`，50ms 轮询）。**一次注册或注销期间，整个注册表被阻塞。**

**三是 `configEqual` 漏比字段**（`registry.go:344-371`）：比较了 ID、Name、SystemPrompt、ModelRef、KnowledgeBase、ToolRefs、SkillRefs、McpServers，**但没有比较 Description 和 Memory**。所以只改描述或只改记忆配置的 etcd 推送会被判定『配置未变化，跳过更新』。

**四是 `markForDeletion` 到新实例注册成功之间有窗口**——这个窗口里进来的请求 acquire 会失败，返回 `AGENT_NOT_FOUND`。功能上没错，但是**个可用性缺口**。理想方案应该是**先建新、再原子切换、最后标记旧的**，而不是先标记再建。」
**【点评】**

- ✅ **答得好的地方**：这是唯一一个「我做了设计」而不是「我写了代码」的回答。三层结构拆得非常清楚，两个细节（刷新到最新、失败回滚）证明你考虑过边界情况。然后主动给出四个问题，第四条还给了修正方案——**说明你不只是实现了，还想过更好的实现**。
- ⚠️ **有风险的地方**：TOCTOU 那条要小心措辞。**这不是理论问题，它是可以真实发生的**（虽然窗口很窄）。追问「怎么修」时别只说「加锁」，要说清代价：mutex 会让 acquire 变成串行点（每个请求都要过），而打包成一个 int64 做 CAS 能保持无锁。**两个方案的取舍要能讲。**
- 💡 **更好的说法**：给一个宏观自评：「这四层加起来的价值是——**热更新对用户是无感的**，这个特性在很多 Agent 平台里都是商业卖点。但我实现它的方式是**用轮询和锁去等**，而更优雅的是用 `sync.Cond` 或 channel 做信号。`waitForRelease` 那个 50ms 轮询（`registry.go:217-229`）在引用归零的平均延迟上白多了 25ms，而且完全没必要。」

### Q1 · 面试官的原话问题
> 「你说你做了限流。那我问你，你这个限流在多实例部署下等于没有，你知道吗？」

### Q3 · 面试官的原话问题
> 「你说 MCP 是真实现的。那我顺着问：Agent 热更新之后，这个 Agent 的 MCP 工具还能用吗？」
**面试者答：**
「**不能。而且热更新会把这个 Agent 的 MCP 连接永久搞死。这是我这个项目里最难看的一个 bug，因为它把三处缺陷串成了一条链。**

**第一环：`IsAlive()` 恒真。** `stdio_transport.go:117-123` 判断 `t.cmd.ProcessState == nil`，而全仓没有任何 `Wait()` 调用，所以 `ProcessState` 永远是 nil，`IsAlive()` 永远返回 `true`。

**第二环：热更新会关掉新 Agent 的 MCP 连接。** 创建新 Agent 时 `registry.go:179` 会调 `ConnectAgentServers(agentID)`——注意这个函数是**先关旧连接、再把新 client 存进同一个 agentID key**（`pool.go:33, 55`）。然后 `registry.go:196` 起一个 `go gracefulDestroy(oldEntry, agentID)`，等引用归零后调 `factory.DestroyAgent(agentID)`，走到 `factory.go:174-177` 再到 `pool.DisconnectAgentServers(agentID)`——**关掉的是新 Agent 的 client，因为它存在同一个 key 下面。**

**第三环：因为 `IsAlive()` 恒真，重连永远不触发。** adapter 的重连逻辑（`adapter.go:64-68`）是 `if !a.client.IsAlive() { Reconnect() }`——既然恒真，这个分支永远不进。

**所以端到端行为是：一次 Agent 热更新之后，这个 Agent 的所有 MCP 工具永久失效。** 调用会报 `发送请求失败: file already closed`，而且**不会自愈**。

**还有第四环，我在这条链上埋了一个更糟的：重连失败被静默吞掉。**

```go
// pkg/mcp/adapter.go:64-68
if err := a.client.Reconnect(ctx); err != nil {
}        // ← 空 if 体
```

就算前面三环都修好、重连真触发了，**重连失败是无声的**，然后代码照常往下走调 `CallTool`，拿到一个更难懂的错。

**修的顺序很重要：** 1）**先修 `IsAlive`**——重连机制是后两环的前提，不修它后面全白搭；2）**再修 pool 的 key 设计**——把连接从 per-agentID 改成 per-(agentID, 配置版本)，或者让 `DestroyAgent` 只关**旧的、已被替换的** client 而不是按 agentID 关，更彻底的做法是**连接按 server 复用**（同一个 server 被两个 Agent 引用只起一个进程），这样热更新根本不涉及连接生命周期；3）**最后把空的 if 体补上**，重连失败记 ERROR 并让这次工具调用返回明确错误。

**还有两个同族问题**：`CallTool` 和 `call` 全程无锁（`client.go:156-190, 258-298`），`requestID++` 是**数据竞争**；stdio 下两个 goroutine 同时读写同一对管道会**串响应**——A 的响应被 B 读走。HTTP 下 `t.sessionID` 也是无锁写（`http_transport.go:69-71`）。**因为 Gateway 是多请求并发的，这不是理论问题。**」
**【点评】**

- ✅ **答得好的地方**：**把三处独立缺陷串成一条因果链讲出来**，这是压力面里最强的反击方式——面试官问的是一个点，你给的是一个系统。「修的顺序很重要」这个细节是真正的工程思维：**知道依赖关系，而不是知道知识点**。
- ⚠️ **有风险的地方**：面试官可能压一句「那你这个 MCP 到底是真实现还是玩具？」——**别被激怒，也别退让**。最好的答法：「**协议实现是真的**（握手顺序、transport 抽象、adapter 适配都对），**连接管理是玩具级的**（没有 Wait、没有探活、没有复用、没有并发保护）。这两件事不矛盾——**我写对了协议，写错了生命周期。**」
- 💡 **更好的说法**：补一个安全层面的收尾，主动抛出来显得成熟：「还有一个我要主动说的：`McpServers` 是 etcd 推过来的配置（`config/config.go:47`、`dynamic/manager.go:120-141`），而 `command` 和 `args` 是**直接进 `exec.CommandContext`** 的（`stdio_transport.go:37`）。所以**任何能往 etcd 写配置的人，都能在我的 Agent 主机上执行任意命令**——没有命令白名单、没有路径限制。这个在生产环境是不可接受的。修法是给 command 加白名单、禁止 shell 元字符、最好把 MCP server 容器化隔离。」

我问这个是因为我在自己项目里手写了 embedding 的 HTTP 调用，当时觉得是控制力，后来觉得如果团队有统一网关，那最优解其实是用网关加客户端库，客户端不该自己管模型名的事。**我发现自己做技术决策时缺少一个参照系——我不知道在一个有十个服务的团队里，一个服务应该管多少。我想知道你们这条线是怎么切分的。**」
**【点评】**

- ✅ **答得好的地方**：**这是一个「用具体经验换对方信息」的问题**：不是泛泛问「你们用什么技术栈」，而是带着自己的判断来对齐。一问同时展示三件事：你关心架构分层、你有过真实取舍、你在评估团队的成熟度。最后那句「我缺少一个参照系」把姿态放得很低但很有分量。
- ⚠️ **有风险的地方**：问容错实现容易滑进「面试」的姿势，听起来像在考对方。**避免连续追问细节**，问完就听，不要接「那你们为什么不用 XXX」。
- 💡 **更好的说法**：可以加一层具体动机：「我想知道的是**一个服务该管到哪一层**——比如模型名、超时、重试这些，到底是每个服务自己配，还是收敛到平台层。我猜不同团队答案不一样，但我没有对照过。」

---

### Q2 · 面试官的原话问题
> 「还有别的想问吗？」
**面试者答：**
「第二个，关于我的短板：**你们怎么看『教学项目』背景的候选人？**

我很清楚我这个项目的性质：它有 12000 行、四条完整的技术线、几个我觉得做对了的设计（引用计数热更新、Lane 串行化、MCP 协议实现、工作流引擎的 checkpoint 闭环），但它也有很明显的缺口——**零测试、零压测、零生产流量**。我在真实的生产系统里没见过一个 QPS 数字背后的真实代价。

我知道我会缺的是**从症状反推根因的路径**——我能读懂锁、能看懂 CAS，但我没有『线上 p99 突然涨了三倍，先看什么』这种经验。所以我想知道：**如果我进来，你们会怎么安排我？** 是先让我在成熟模块里做增量、熟悉团队做法，还是直接给我一块需要从零设计的？我两种都能接受，但这个答案会影响我前三个月该把力气花在哪——是『补齐工程规范』还是『快速交付一个东西』。」
**【点评】**

- ✅ **答得好的地方**：**把短板放在问题里问，是最聪明的处理方式。** 一箭三雕：主动展示自知、把「你有没有短板」这个追问提前消解掉、同时打听到入职期望。最后那句「这个答案会影响我前三个月把力气花在哪」——**它把问题从『评价我』变成了『我们一起规划』**，姿态是对的。
- ⚠️ **有风险的地方**：说「零测试、零压测、零生产流量」时**语气要稳**。自嘲或心虚的语气就变成了自我否定。**平铺直叙地说事实，把评价权留给对方。**
- 💡 **更好的说法**：把「缺什么」说得更具体：「我知道我会缺的是**诊断的经验**——不是不会看指标，是**不知道先看哪一个**。我想知道团队里这种经验是怎么传的：有文档、有 review、还是靠带。」

### Q3 · 面试官的原话问题
> 「嗯，你可以再问一个。」
**面试者答：**
「第三个：**团队的 code review 和测试文化是什么样的？具体到——我一个人提 PR，要求里面必须有测试吗？谁来 review？**

我问得很具体，因为它决定了我要怎么改我的习惯。我以前写代码的习惯是先跑通再补测试，然后『补测试』这一步经常被下一个功能挤掉。如果团队的要求是测试必须跟 PR 一起提，那我会从第一天就改；如果实践是核心路径必须有测试、边缘路径靠 review，那我也需要知道边界在哪。

顺便问一个具体的：**你们最近一次因为 review 打回 PR 是什么原因？**」
**【点评】**

- ✅ **答得好的地方**：**问文化的关键是问「具体的、可验证的行为」而不是形容词。** 「有没有测试文化」谁都会问，答案永远是「我们很重视」；但「PR 必须带测试吗、谁 review」是**有确定答案的**。最后那个「最近一次打回 PR 是什么原因」更是把问题从流程问到了事实——**得到的答案真实得多**。同时这个问题再次把「我没写测试」这个短板转化成了「我在主动了解你们的规范」。
- ⚠️ **有风险的地方**：别问成「你们是不是也不写测试」（带预设），也别在对方回答后立刻说「我在我项目里就是没写」——**短板已经交代过了，重复会显得过度自贬。**
- 💡 **更好的说法**：可以再补一层，把规范和你的补课绑起来：「如果要求带测试，我需要提前知道你们用什么框架、覆盖率要求多少——**我想从第一天就按你们的规范写，而不是先按我的习惯写三个月再被纠正。**」

---

### Q4 · 面试官的原话问题
> 「时间差不多了，你还有什么想问的？」
**面试者答：**
「最后一个，关于我自己：**今天这几个环节里，哪一块你印象最差？如果我要补，你建议我先补哪一块？**

我问这个是因为我今天讲了很多我知道的问题，但**我对自己的问题的判断可能是有偏差的**——我可能把力气花在修一个我自己很在意但实际不重要的地方。如果站在你们的角度看，我这个项目最刺眼的是哪一处？

如果你们愿意的话，我想在结果出来之后也问一下我哪块答得最差——**哪怕最后没有过，这个反馈对我下一次也值钱。**」
**【点评】**

- ✅ **答得好的地方**：**这是反问环节里最高价值的一个问题。** 三个理由：它把面试变成了一次反馈对话，姿态是从容的而不是防御的；你能在还有时间的时候**当场修正**——如果他说「最刺眼的是零测试」，你还能补一段话；**能问出这个问题的候选人，通常会让面试官对整场的印象再提一档**，因为它需要你在已经暴露了很多短板之后依然保持稳定的自我价值感。「哪怕没有过，这个反馈也值钱」这句尤其好，它把这句话从策略变成了品格。
- ⚠️ **有风险的地方**：如果面试官真说了很重的话，**不要辩解、不要补答**。就说「这个我记下来了，你说得对」，然后如果还有时间再补一句简短的。**在这个问题里辩解，等于把这个问题的价值全部清空。**
- 💡 **更好的说法**：这个问题的位置可以更早——**如果放在第四轮 Q5 之后、反问一开始就问，你还能在本场里补上一段，价值会翻倍。**

### 哪几轮是加分项

- **【第一轮】Agent 与工具调用 —— 最大加分项。** 把 `tool_call_id` 缺失这条最致命的缺陷自己先说，并且拆成了「数据结构 → 循环回填 → 记忆落库」三层传播路径。**一个能把自己最烂的地方讲成原理的候选人，可信度是全场最高的。**
- **【第三轮】高并发与分布式 —— 第二加分项。** `default-user` 共用桶、安全过滤器顺序、令牌桶 CAS、Redis 锁三缺、分布式记忆只写不读、etcd watch 静默失效、引用计数四问——这一轮几乎把走查报告里的红区全打穿了，而且每处都有行号。
- **【第四轮】压力面 —— 关于「崩不崩」的加分项。** 三道压力问（限流是假的 / 没压测 / MCP 热更新后失效）全部接住，方法都是同一个：**认领 + 拆解 + 给修法**。没有一处狡辩，也没有一处垮掉。

### 哪几轮是失分项

- **【第二轮】大模型工程 —— 最弱的一轮。** 五个问题里四个的答案是「没做」：没超时、没重试、没流式、没 token 统计。虽然「流式是感知快不是真快」「没有超时的重试最危险」两个回答救了场面，但这一轮**信息增量最少**——面试官问的大多是「有没有」，而你回答的多是「没有」。
- **【开场】自我介绍 —— 微小失分。** 「每一层的动机我都能讲清楚」有点空，而且三分钟里没有给一个「最强的单点」作为钩子，导致面试官必须自己找切入点。
- **【反问】—— 不算失分，但顺序可以更好。** Q4（问对方印象最差的地方）非常强，但放在最后有点浪费——**如果早一点问，你还能在本场里补上一段，价值会翻倍。**

### 如果重来一次，只改一件事

**把「我知道」变成「我写了」。** 这一场最有说服力的一句话是「我一个 Go 文件一个 Go 文件 grep 过 `{{`，零命中」——因为它是**一个动作**，不是一个记忆。而整场最弱的部分是第二轮，因为那五个「没做」缺的正是这个动作：**加一个 `http.Client{Timeout: 60s}` 是十分钟的事，统计 token 是半小时的事，把 `Required` 写进 schema 是十几行的事。** 下一版别再攒这些问题——修一个、留一个 `go test`、在 README 里写一个真实的延迟数字。**能让面试官看见的两个小时，比能说出口的二十个小时值钱。**
