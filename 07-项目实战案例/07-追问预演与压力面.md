# 追问预演与压力面：30 个问题的答法

> **一句话** · 面试的胜负不在"你答对了没有"，在"面试官信不信你做过"。所以这 30 道题的答案有一条共同的骨架：**先给结论 → 再给带 file:line 的依据 → 最后主动给边界**。给不出依据的结论是空话，给不出边界的结论是在吹。
>
> **怎么用这份文件：** 不要背。每道题先只看标题，自己答一遍，再对照「30 秒骨架」。**「扣分回答」一定要读** —— 那是最容易脱口而出的话。

**四组题的性质不同，考的东西也不同：**

| 组 | 题数 | 面试官在考什么 | 你的目标 |
|---|---|---|---|
| 第一组：常规追问 | 10 | 你是不是真的理解自己写的东西 | 答得**干净利落 + 有依据**，不啰嗦 |
| 第二组：深水区 | 8 | 你是真做过还是只搭了架子 | 答得**具体到机制**；答不上来的部分诚实说 |
| 第三组：压力面 | 7 | 你扛不扛得住质疑、会不会乱 | **先承认，再分级，再给方案** —— 不辩护、不崩 |
| 第四组：挖坑题 | 5 | 你会不会抢答、有没有分层思维 | **先分层再答**，识别出真正的考点 |

## 第一组：常规追问（10 题）

### Q1 · 为什么用 Go 不用 Java？

**考什么：** 技术选型是判断力还是习惯。注意 README 里写着"本项目是 `bitguide-agent-platform`（Java 版）的 Go 语言实现" —— 否认对标就是撒谎。

**30 秒骨架：**
1. **结论：** 这是 Java 版的 Go 重写，选 Go 是三个具体理由，不是"Go 更简洁"。
2. **依据：**
   - **并发模型匹配业务形状** —— 网关是纯 IO 密集（LLM 秒级、Redis、Milvus），Go 的 goroutine 让它天然一请求一协程（`pkg/gateway/gateway.go:66-160`），不需要线程池调参；
   - **单二进制 + 子进程管理** —— MCP stdio transport 要 `exec.CommandContext` 起子进程并接管 stdin/stdout（`pkg/mcp/stdio_transport.go:37,84-94`），Go 的 `os/exec` + 管道 + 协程读 stderr（`:70-76`）在这块极其顺手；
   - **标准库够用** —— `net/http` + `http.ServeMux` 直接起网关（`cmd/stage3/main.go:319`），零 web 框架依赖。
3. **边界：** 代价是没有 Java 侧的成熟 Agent 生态（LangChain4j / Spring AI）；JDK 21 的虚拟线程在并发模型上已经抹平了大部分差距，Go 剩下的优势主要在"单二进制部署 + 子进程管理"。

**加分点：** 主动说"如果目标是团队协作和生态复用，Java 可能是更好的选择；我这个项目选 Go 是因为要把 MCP 子进程和向量库客户端都手写一遍，Go 在这两块的样板代码更少。"

**扣分回答：** "Go 性能好"或"Go 更简洁"。下一句必然是"哪块性能好、好多少"，你答不出 —— 而且这个项目的瓶颈根本不在语言。

### Q2 · 为什么自己写网关不用 Gin？

**考什么：** 标准库功底 + 会不会为选型找借口。这题的陷阱是"标准库更好"这个结论本身不成立。

**30 秒骨架：**
1. **结论：** 需求只有 5 个前缀路由 + 一条自定义中间件链，标准库够用 —— 但这是**规模判断**，不是"标准库更好"。
2. **依据：** 路由是手工前缀匹配，handler 内部判 `r.Method`（`cmd/stage3/main.go:319-497`）；中间件是自研过滤器链、带显式 order（`pkg/gateway/filter.go:96-106`）。
3. **边界：** 手工前缀匹配有真实代价 —— **没有路径参数**（`/api/v1/sessions/` 得手工切字符串，`main.go:441-482`）、**没有内置 Recovery**（中间件 panic 会直接炸连接）、**没有自动绑定**。路由一复杂就该换。

**加分点：** 自研链反而带来了 Gin 没有的东西：过滤器有显式优先级和短路语义（Auth 10 / Security 20 / RateLimit 30），错误码到 HTTP 状态码集中映射且语义正确（`main.go:562-577`，`TOO_MANY_REQUESTS→429`、`PROMPT_INJECTION→400`）。

**扣分回答：** "Gin 太重了"。Gin 不重 —— 这个回答会立刻暴露你没做过选型对比。

### Q3 · MCP 和 Function Calling 是什么关系？

**考什么：** 两个概念是不是真的分清。混答的人很多，所以这题是很好的筛选器。

**30 秒骨架：**
1. **结论：** 不是竞争关系，是**两层**。Function Calling 解决"模型怎么表达调用意图"（模型 ↔ 你的程序）；MCP 解决"你的程序怎么发现和调用外部工具"（你的程序 ↔ 工具服务）。
2. **依据：** 项目里两条链路共存 —— FC 走 `base.go:316` 每轮重建 tools 数组 + `chatWithTools`；MCP 走 `client.go:98-131` 的 `initialize` → `notifications/initialized` → `tools/list` 握手。**接起来的地方是 adapter**（`pkg/mcp/adapter.go:12-23`）：把 MCP 的 `inputSchema` 归一成内部 `tool.Tool` 接口，于是 MCP 工具和内置工具在 ReAct 循环里长得完全一样，循环零改动。
3. **边界：** MCP 的增量价值在**工具发现**（`tools/list`），不在工具调用 —— 调一个 HTTP API 本来就不难。我的实现是 2024-11-05 版本，**HTTP transport 声明接受 SSE 但没解析**（`http_transport.go:57-59` 带 `Accept: text/event-stream`，body 却直接交给 `json.Unmarshal`，`client.go:279`），真实的 Streamable HTTP Server 会解析失败。

**加分点：** 说出"如果没有 MCP，工具接入的成本不在调用，在**发现和描述**：每个工具都要手写 schema 定义和文档。MCP 把这一步标准化了。"

**扣分回答：** "MCP 就是 Function Calling 的一种实现"。概念混淆，后面所有相关问题都会跟着崩。

### Q4 · 你的 Agent 循环怎么终止？跑不完怎么办？

**考什么：** 有没有想过"模型不听话"的情况。

**30 秒骨架：**
1. **结论：** 三个出口，语义不同 —— 这是刻意的设计。
2. **依据（`pkg/agent/base.go:295-384`）：** ① 模型不返回 `tool_calls` → 正常出口，返回 `response.Content`（`:325`）；② 跑满 `maxIterations = 10` → 返回 error（`:384`）；③ LLM 调用报错 → 直接返回 error（`:320-322`）。分流在 `:164-170`，只有 `toolManager.Size() > 0` 才走 ReAct。
3. **边界：** 出口②和③**不能混**：③是基础设施故障（可重试），②是预算耗尽（模型死循环或任务太大，应该降级返回已完成部分或转人工），都不该直接 500。而且出口②有个实现缺陷：`base.go:158` 已经把 user 消息写进记忆了，而 `:177` 的"写回 assistant 回复"因 `:172-174` 提前 return 而不可达 → **历史里留下一条永远没有回复的 user 消息**，下一轮会被重发。

**加分点：** 主动说 `maxIterations` 是**局部变量**（`base.go:296`），不是常量、不在 config 里 —— 被问"为什么是 10"只能答"经验值"，这是我知道的设计缺陷。

**扣分回答：** "跑满 10 轮就返回错误" 然后停在这里 —— 面试官接着问"那用户看到什么"，你答不出降级方案。

### Q5 · RAG 的检索结果怎么进 prompt 的？

**考什么：** 有没有真看过自己拼 prompt 那段代码。这题是"citation 缺失"的入口。

**30 秒骨架：**
1. **结论：** 直接拼进 **system prompt，没有编号、没有 source、没有 score**。
2. **依据（`pkg/agent/base.go:273-283`）：** 循环拼 `result.Content`，块间加 `\n\n`，最后接在 basePrompt 后面，附一句"以下是与用户问题相关的知识库内容，请参考这些内容回答问题"。`SearchResultItem.Source` 被取到了但**直接丢弃**（`:273-279`）。
3. **边界：** 项目里其实有一套 `[1] [2]` 编号的 prompt 模板（`pkg/rag/service.go:165-201`），但**全项目无任何调用点**，是死代码。所以 citation 实际是零 —— 这是整个 RAG 链路最大的设计缺陷，因为**引用是 RAG 可信度的唯一抓手**。而且 `source` 本身也只是 `filepath.Base(file)`（`:382`），两个同名文件不同目录会撞。

**加分点：** 主动说第二个设计问题：阈值是 **topK 之后的后置过滤**（`service.go:134,267`）—— **阈值不能提升召回，只能让结果变空**。top-5 全低于阈值时返回 0 条，而不是"再多取几条"。正确做法是把阈值传进 Milvus 做 `range_filter`，或先取 topK×3 再筛。

**扣分回答：** "有引用，模型会标注来源"。代码里没有，打开一看就穿。

### Q6 · Skill 和 Tool 有什么区别？

**考什么：** 是不是把两个概念混着用 —— 这在 Agent 工程里是很常见的糊涂点。

**30 秒骨架：**
1. **结论：** Tool 有 `Execute`，**被模型调用**；Skill **没有执行体**，它是一段专业 system prompt + 工具白名单 + few-shot（`pkg/skill/skill.go:14-35`）。
2. **依据：** Skill 执行时是"注入工具 → 用 Skill 的 prompt 覆盖 system prompt → 复用同一个 ReAct 引擎"（`skill_enhancer.go:26-42` → `base.go:195`）。这个设计判断是对的：**流程控制权留在 ReAct 循环里，Skill 只改变模型的"专业身份"和"可用工具集"**。代码注释（`skill.go:6-12`）还引了 Semantic Kernel / Assistants / LangChain 三种主流做法做对比。
3. **边界：** 三个真实缺陷：① `SKILL.md` 里的 `{{city}}` / `{{user_input}}` **没有任何模板渲染代码**（全仓 Go 代码 grep `{{` 零命中），那整段是原样进 system prompt 的，`tool: get_weather city: "{{city}}"` 只是给模型看的文字提示 —— **被问"变量怎么注入"答"有模板引擎"就是致命失分**；② `MatchSkills` 的中文关键词匹配完全失效（`manager.go:163-173` 用 ASCII 空格/逗号分词，中文描述整段变成一个 token），加 skill 的 `Name` 是英文（`parenting-activity-advice`）、`examples` 为空 → **关键词路径实质上永不命中，`MatchSkills` 是装饰**；③ `injectTools` 直接往共享 Agent 的 toolManager 里注册工具、**不撤销**（`skill_enhancer.go:45-63`）→ Skill 声明的工具会永久污染该 Agent 后续所有普通对话。

**加分点：** 主动说 Skill 与 Tool 的边界是"**谁拥有控制权**"：Tool 是模型的选择，Skill 是人的预设。模板渲染缺失这件事说明我当时把 `SKILL.md` 当成了"给人看的文档"而不是"给程序解析的配置"。

**扣分回答：** "Skill 是更复杂的 Tool" —— 概念不清，接下来问"那为什么还要分两个概念"就完了。

### Q7 · 你在这个项目里用了哪些设计模式？

**考什么：** 会不会背模式名词。**这题的正确答法是"只讲真的用了的，并说出它解决了什么"。**

**30 秒骨架：**
1. **结论：** 四个是结构性的、三个是局部的。
2. **依据：**
   - **策略/接口隔离**：`llm.Client` 接口（`pkg/llm/client.go:40-52`）有 `openai.go` 具体实现和 `gateway.go` 多模型路由实现，后者自己实现 `Client` 接口委托默认模型（`gateway.go:98-118`）→ 可直接当 `llm.Client` 传给 Agent（`cmd/stage2/main.go:100`）；
   - **适配器**：`pkg/mcp/adapter.go:12-23` 把 MCP 工具适配成 `tool.Tool`，**这是全项目结构上最干净的一处**；
   - **观察者**：`pkg/dynamic/listener.go:4-7` 的 `ConfigChangeListener` + `watcher.go:38-40,194-198` 的回调切片，是 etcd 配置变更的传播机制（但注意是**同步调用、无锁 append**）；
   - **工厂**：`pkg/tool/factory.go:211-218` 的 `GetToolFactories` 让每个 Agent 拿**新实例**、`pkg/agent/factory.go:101-137` 的 `CreateAgentFromConfig` 七步装配；
   - **责任链**：`pkg/gateway/filter.go:96-106` 的过滤器链，带 order 排序 + 短路；
   - **状态机**：checkpoint 的 running/paused/completed/failed 四态（`pkg/workflow/checkpoint/checkpoint.go:6-12`）+ `Resume` 校验状态（`executor.go:95`）；
   - **模板方法/管道**：工作流图的节点-边执行。
3. **边界：** **没有用单例、没有 DI 容器** —— 依赖是显式注入的，`DynamicConfigManager` 还要注释提醒"必须在 `Init()` 之前注入"（`cmd/stage3/main.go:233`），说明显式注入是踩过坑才收敛的写法。

**加分点：** 主动说"适配器那处是我唯一觉得自己做对了架构的地方：MCP 工具和内置工具的来源完全不同（一个本地函数、一个跨进程 JSON-RPC），但上层 ReAct 循环完全不需要知道自己拿的是哪种。"

**扣分回答：** 罗列十几个模式名词。面试官会挑一个问"在哪个文件"，答不出的那个就是你的破绽。

### Q8 · 多 Agent 是怎么路由的？

**考什么：** 是不是把"多 Agent"想成了"智能调度"。这个项目的真实答案是**它没有智能路由**。

**30 秒骨架：**
1. **结论：** 三种，**都不是智能路由**。Stage2 没有 supervisor。
2. **依据：** ① CLI 手动 `/switch`；② Gateway 按 `req.AgentID` 取，缺失就"取第一个可用 Agent"（`gateway.go:68-78`）；③ 单 Agent 内部的 Skill 匹配（`pkg/skill/manager.go:126-138`）。
3. **边界：** 真正带"分派"味道的东西在 Stage4 工作流里，但也不是 LLM 规划：`SupervisorNode`（`patterns/supervisor_node.go:26-41`）调的是普通 Go 回调 `PlannerFn`，demo 里就是个硬编码两项闭包（`cmd/stage4/main.go:228-235`），而且**只把第一个子任务写进 `current_sub_task`**。`RouterNode`（`router_node.go:21-33`）在 demo 里 `RouterFn` **恒返回 `"default"`**（`main.go:104-106`）→ router-demo 是个恒等路由。

**加分点：** 主动说"我没有实现 LLM 规划式路由，因为当时判断这属于编排层的能力，应该由工作流引擎承担，而不是让 Agent 自己决定找谁 —— 混在一起会让两个抽象都变脏。"

**扣分回答：** "有 supervisor 做智能分派"。代码里 Stage2 没有 supervisor 这个词，Stage4 的那个还是硬编码 planner。

### Q9 · 为什么 embedding 不用 `go-openai` 的 SDK？

**考什么：** 会不会为"手写"找借口。手写通常意味着丢了东西。

**30 秒骨架：**
1. **结论：** 为了兼容**任意非 OpenAI 命名的模型名**。
2. **依据：** chat 侧用的是 `go-openai v1.17.9`（`go.mod`），embedding 侧手写 HTTP POST 到 `/v1/embeddings`（`pkg/llm/openai.go:155-236`），因为项目用的模型是 `nomic-embed-text`（`pkg/rag/embedding.go:22-24`），而 SDK 对模型名有约束。
3. **边界：** 代价是**丢了 SDK 的重试、超时、错误分类** —— 而且我手写的那个 client 是 `httpClient: &http.Client{}`（`openai.go:42`），**连 Timeout 都没设**。这是净损失，不是"更灵活"。

**加分点：** 说出策略边界："我的原则是**只在 SDK 不支持的端点上手写，不整体替代 SDK**。chat 侧继续用 SDK，就是为了保住它的错误处理。"

**扣分回答：** "手写更灵活、可控"。面试官接着问"你丢掉了什么"，答不出就是没有取舍意识。

### Q10 · etcd 在项目里承担什么角色？为什么不用 Nacos/Consul？

**考什么：** 知不知道这个组件为什么在这里。

**30 秒骨架：**
1. **结论：** etcd 在这个项目里是**配置分发 + 变更通知**，不是服务发现。
2. **依据：** `pkg/dynamic/watcher.go` 的 `ConfigWatcher` 监听固定前缀（`/bitguide-go/config/`，`stage3.yml:58`），变更推给 `ConfigChangeListener` 回调 → `DynamicConfigManager` 解析 → `registry.Register` 触发热更新（`manager.go:120-141`）。**没有服务注册、没有健康探测、没有节点列表。**
3. **边界：** 选 etcd 的理由主要是"它同时是 K8s 的数据源"，本地起一个容器就有；Nacos 生态更靠 Java 侧，Consul 的多数据中心更重。**但我的用法其实只需要一个支持 watch 的 KV 存储** —— 这个需求甚至 Redis Pub/Sub 都能覆盖（只是没有 revision 语义）。

**加分点：** 主动说 key 解析的脆弱点：`parseKey` 硬编码 `parts[3]/parts[4]`（`event.go:73-84`），多级 key 会解析出错误的 configID **且不报错**；而且 `watcher.go:77-79` 的默认前缀 `/bitguide/config/` 和 `stage3.yml:58` 的 `/bitguide-go/config/` **不一致，靠 YAML 显式配置才对齐 —— 漏配就静默监听不到任何东西**。

**扣分回答：** "etcd 是服务发现的标准方案"。在这个项目里它不做服务发现，这么答说明你没读自己代码。

## 第二组：深水区（8 题）

> **这一组的意义：** 答不上来不是"扣分"，是"判定你没真做过"。所以每题的边界部分比结论部分更重要 —— **说不清机制时，诚实说"这里我没想透"比编一个机制强**。

### Q11 · 引用计数的 TOCTOU 窗口在哪？

**考什么：** 你写的引用计数是不是只是"看起来安全"。

**30 秒骨架：**
1. **结论：** 在 `acquire()` 里 —— `marked.Load() == 1` 的检查和 `refCount.Add(1)` 之间是可插入的。
2. **依据（`pkg/agent/registry.go:34-40`）：**
   写法是两步：`if e.marked.Load() == 1 { return false }` 然后 `e.refCount.Add(1)` —— **检查与自增是两个独立的原子操作，中间可插入 `markForDeletion`**。
   失败路径：请求通过检查 → `markForDeletion` 生效 → `waitForRelease` 看到 0（因为请求还没自增）返回 → 旧 Agent 被 `Close()` → 请求随后在**已关闭的 Agent** 上跑。
3. **边界：** 窗口很窄但真实。**修法不是加锁**（`AcquireRequest` 在请求热路径上，加锁会把注册表变成串行点），而是把两个状态**打包进一个原子量**：用一个 `atomic.Int64`，高位当 marked 标志、低位当计数，`acquire` 用一个 CAS 循环完成"检查 + 自增"。或者用 `atomic.Pointer` 指向不可变状态。

**加分点：** 主动说 `waitForRelease` 用的是 **50ms 轮询**（`registry.go:217-229`），而正确做法是 `sync.Cond` 或 channel —— **轮询既增加延迟又浪费 CPU，而且它和 TOCTOU 是同一个根因：把"状态查询"和"状态变更"分成了两步。**

**扣分回答：** "用了 atomic 就线程安全了"。`atomic` 只保证单个操作原子，不保证复合操作 —— 这句话说出来就暴露了并发短板。

### Q12 · etcd watch 遇到 compaction 之后，你怎么知道它死了？

**考什么：** 这是本项目最容易一枪打穿的点。**正确答案是"我不知道，因为我的实现里它静默失效"。**

**30 秒骨架：**
1. **结论：** **不会知道。** 这是我的实现里最严重的可靠性缺陷。
2. **依据（`pkg/dynamic/watcher.go:119-142`）：** watch 循环里 `if watchResp.Err() != nil { clog.Error(...); return }` —— **直接退出，永不重连、无重启、无告警、无降级轮询**。一旦出现 `required revision has been compacted`（etcd 默认 compaction 间隔 5 分钟，长跑进程一定会遇到），**配置热更新静默失效**，而外部完全看不出来：进程活着、HTTP 正常、日志里只有一行 Error。
3. **边界：** 修法有三层：① 识别 `rpc error: code = OutOfRange` 后用**当前 revision 重建 watcher** + 指数退避；② 重连动作暴露一个 Prometheus 计数器，让"曾断开过"在面板上可见；③ 兜底加一个低频全量 `Get` 轮询，防止 watch 类错误的漏掉。**另外还有一个更隐蔽的洞：`loadAllConfigs` 拿到了 `resp.Header.Revision` 但丢弃了它（`:99-122`），`Watch` 没带 `WithRev(revision+1)` → Get 与 Watch 之间发生的 PUT/DELETE 永远不会被感知。** 标准做法就是 `Get` 拿 revision → `Watch(..., WithRev(rev+1))`。

**加分点：** 主动把两条一起说（compaction 静默退出 + Get/Watch 事件窗口）—— 它们体现的是同一件事：**我当时的关注点在"变更能被收到"，没在"永久收不到怎么办"。**

**扣分回答：** "etcd 会自动重连"。clientv3 的 Watch channel 在不可恢复错误上会关闭，**不会**自动重建 —— 答这句等于没看过客户端文档。

### Q13 · 锁没有 watchdog 会怎样？

**考什么：** 分布式锁的最小正确实现里，TTL 与续期的关系。

**30 秒骨架：**
1. **结论：** **业务超过 TTL 时锁自动过期，第二个请求进入同一会话，两个请求并发读写同一份会话。** 这是"裸 SETNX 没有 watchdog"的经典漏洞。
2. **依据：** TTL 默认 **60s**（`pkg/gateway/distributed.go:45-49`、`config.go:94`）。一次 LLM 调用超过 60s 完全可能（长上下文 + 慢模型），此时 `SET NX PX 60000` 到期自动释放，后来的请求拿到锁进入 —— 前一个请求还在写会话记忆。Redisson 的 watchdog 就是为这件事存在的（默认 lockWatchdogTimeout 30s，按 1/3 周期续期）。
3. **边界：** 续期本身也有代价和风险：①续期 goroutine 崩溃或 GC 停顿会导致续期失败，所以业务侧必须做**锁有效性校验**（比如写会话前再取一次锁校验 value）；②续期的前提是"业务还在跑"，**不能无限续期**，需要一个绝对上限；③更彻底的方向是**放弃锁**，改用版本号/`WATCH` 乐观锁让写操作自己检测冲突。

**加分点：** 主动说第二处锁的问题：`defer dg.releaseLaneLock(ctx, laneKey, requestID)`（`distributed.go:99`）**用的是 `r.Context()`** —— 客户端一断开 ctx 被取消 → Lua 脚本调用失败 → **锁不释放，卡满 60s TTL** → 该会话后续请求全部 `LANE_BUSY`。修法是 `context.WithoutCancel(ctx)` 或独立的清理 ctx。

**扣分回答：** "锁有 TTL 就够了，不会死锁"。**是的不会死锁，会数据错乱** —— TTL 解决死锁，不解决互斥性丢失。

### Q15 · MCP 的 `IsAlive` 怎么判断进程存活？

**考什么：** 你有没有真的想过"子进程死了我怎么知道"。

**30 秒骨架：**
1. **结论：** **我的实现恒返回 true —— 崩溃检测和重连逻辑永远不触发。**
2. **依据（`pkg/mcp/stdio_transport.go:117-123`）：**
   判的是 `t.cmd.ProcessState == nil`，而 **`ProcessState` 只有 `Wait()` 之后才非 nil**。
   **全仓没有一处调用 `t.cmd.Wait()`** → 进程崩溃、被 Kill、被 Close 之后 `IsAlive()` 一律返回 `true`。`Close()` 之后再调用工具会得到 `发送请求失败: file already closed`。
3. **边界：** 正确做法有两条：① 起一个 goroutine 阻塞在 `cmd.Wait()`，返回即表示进程已退出（同时顺手回收僵尸进程）；② 在读 stdout 的 goroutine 里感知 EOF 并标记连接失效。**两条都要做** —— `Wait()` 回收资源，EOF 感知提前量。而且这个洞还有一个放大效应：`adapter.go:64-68` 的重连逻辑本身就写错了 ——
   空的 if 体 —— **重连失败无声吞掉，然后照常 `CallTool`**。

**加分点：** 主动把两个 bug 的**组合效应**说出来：因为 `IsAlive` 恒真，所以 adapter 不会重连；**而一旦真的重连失败，错误也被静默吞掉**。更糟的是热更新会顺手杀掉新 Agent 的 MCP 连接（`registry.go:179` 用同一个 agentID key 覆盖新 client，`:196` 的 `gracefulDestroy` 最终调到 `pool.DisconnectAgentServers(agentID)` 关掉的是**新** client）→ **热更新后该 Agent 的所有 MCP 工具永久失效**。

**扣分回答：** "会检测进程状态，死了就重连"。代码里这个检测恒真，等于没有。

### Q16 · 你的分布式锁 `requestID` 用 `UnixNano`，会有什么问题？

**考什么：** 分布式唯一性意识。

**30 秒骨架：**
1. **结论：** **跨实例不唯一，碰撞时会误删他人的锁。**
2. **依据（`pkg/gateway/distributed.go:91`）：** `requestID := fmt.Sprintf("%d", time.Now().UnixNano())`。不同机器的**时钟可能重合**（NTP 同步的系统时钟精度有限，容器环境尤其），一旦两个实例在同一纳秒生成 ID，A 的 `Unlock` 就可能满足 Lua 脚本的 value 比对条件、删掉 B 持的锁。
3. **边界：** 修法很简单：**UUID**，或者 `instanceID + "-" + nanotime`（instanceID 启动时生成一次）。**但要注意这不是"改成 UUID 就完事了"** —— 它还暴露一个更深的问题：`requestID` 是锁的持有凭证，它应该跟"这次锁获取"绑定，而不是跟"这个进程"绑定。更严谨的做法是把凭证存进一个结构体，释放时校验结构体而不是字符串。

**加分点：** 主动说 Lua 释放那部分**做对了**："`pkg/redis/client.go:145-159` 的释放是 Lua compare-and-delete，避免了超时后误删他人锁 —— 这个设计是对的，问题只出在**凭证生成**这一环。"

**扣分回答：** "纳秒级不会重复"。单机可能，跨机不一定 —— 而且面试官问的就是跨机。

### Q17 · 分布式记忆里，陈旧缓存回写会怎样？

**考什么：** 缓存一致性 —— 这是"分布式"三个字里最容易漏的一环。

**30 秒骨架：**
1. **结论：** **会丢消息。** Lane 锁只解决并发，**不解决缓存失效**。
2. **依据：** 同实例内 `ConversationMemory` 有 `sync.RWMutex`，单条 append 安全；跨实例有 Redis Lane 锁保证同一会话同一时刻只有一个实例在写 —— **所以"并发交错"被防住了**。但**陈旧缓存回写**没防：A 实例本地缓存停留在旧版本 → B 写入新消息 → A 下次请求直接用自己那份**旧快照全量覆盖** Redis（`memory/distributed.go:93-105` 的 `saveToRedis` 是全量 `SET`）→ **B 的消息丢失**。
3. **边界：** 正确做法有四种，各有代价：① 版本号 / `WATCH` + 乐观锁（要改写入协议）；② 写完就 `DEL` 本地缓存，下次强制回源（增加 Redis 读）；③ **把 Redis 当唯一数据源，本地不缓存**（最简单也最可靠，代价是每轮多一次 Redis 往返）；④ 只追加不改写（用 Redis List 做 append-only，避免全量覆盖）。**我会选 ③ 或 ④** —— 因为这个场景下本地缓存的收益（省一次 Redis 往返）远小于数据丢失的代价。

**加分点：** 主动补最根本的那条：**这套记忆只写不读。** `DistributedMemory.BuildMessages` / `GetHistory` 没有任何生产调用方，LLM 上下文来自 `BaseAgent.session.Memory.BuildMessages`（`pkg/agent/base.go:232,306`），那是每实例各自的内存 `sync.Map` → **换实例或重启后 LLM 拿不到历史**。"分布式记忆"在端到端行为上并不成立。

**扣分回答：** "有 Lane 锁所以不会有并发问题"。**锁解决并发，不解决一致性** —— 这个区分答不出来就是没做过分市式状态管理。

### Q18 · 工作流的 checkpoint 只留一份快照，怎么支持断点续跑和回放？

**考什么：** 会不会把"有 checkpoint"当成"有 checkpoint 机制"。

**30 秒骨架：**
1. **结论：** **断点续跑支持，回放不支持。** 这是两个不同的能力。
2. **依据：** checkpoint 结构是 `{ExecutionID, CurrentNodeID, StateData, CreatedAt, Status}`（`checkpoint.go:6-12`），Redis 里存两个 key：`bitguide:workflow:checkpoint:`（String，整个 Checkpoint 的 JSON，`Set(..., 0)` **永不过期**）和 `bitguide:workflow:checkpoints`（Hash: execID → status）。**同一个 key 覆盖写** → 每个 execution **只保留一份最新快照，没有历史、无法回放**。而 `Resume`（`executor.go:83-149`）要求 `cp.Status == "paused"`（`:95`），从 checkpoint 重建 state、清 `_interrupted`、并入 userInput，然后 `resolveNextNode(cp.CurrentNodeID, state)`（`:115`）—— **从暂停节点的下一条边继续，不会重跑中断节点**。
3. **边界：** 要支持回放需要三件事：① key 带 revision/step，存成链（`checkpoint:{execID}:{step}`）；② 记录每步的输入快照和节点 ID；③ 加一个 `fork(step)` API。**对比 LangGraph：它有 thread_id + checkpoint_id、每步快照成链、支持 time travel 和分支回放 —— 我这里只有最新一份，这是能力差距不是实现差距。**

**加分点：** 主动说另外三处相关缺陷：① `ExecutionID` 用 `UnixNano()%1e8`（`executor.go:191-193`）—— **只有 8 位十进制，约 0.1 秒就会重复**，并发下极易撞 ID，而它是 checkpoint 的主键；② `Checkpoint.CreatedAt` **从未被赋值**（`:180-185` 和 `interrupt_node.go:34-39` 都没设）→ `/status` 返回的 `createdAt` 永远是 `0001-01-01T00:00:00Z`（`handler.go:186`）；③ Redis checkpoint 无 TTL + 每步全量 state JSON → **长会话存储无界增长**。

**扣分回答：** "有 checkpoint 就能恢复"。面试官接着问"那能回到第 3 步重跑吗"，答案是"不能" —— 而你刚才的说法暗示能。

### Q21 · "你这不是抄 LangGraph 吗？"

**考什么：** 抗质疑 + 你到底是"抄"还是"复刻并理解"。

**30 秒骨架：**

2. **依据 —— 先列像的地方（不否认）：** `__start__`/`__end__` 哨兵节点（`core/graph.go:11-14`）、nodes + edges 图、条件边 router、Channel ≈ reducer（`core/channel.go:4-6`）、checkpointer + interrupt/resume 的形态、Supervisor/Router/Loop 这些 prebuilt 模式、state 当共享黑板 —— **这些形态就是 LangGraph 的。**
3. **边界 —— 再说差的地方（这些是我自己的实现决定）：** ① **执行模型**：LangGraph 是 Pregel 风格 superstep、同超步内节点并行、channel 带版本号合并、有 join/barrier；**我的是单线程 while 循环，一次一个节点，没有超步概念**（`executor.go:12` 的注释自己写着 serial execution）；② **channel 是装饰**：LangGraph 的 channel 就是运行时数据结构，我的三条 channel 实现**从没被任何 state 实例挂载过**，全是死代码；③ **checkpoint 只留一份**，没有历史、无法回放；④ **interrupt 是协作式的** —— 节点必须主动 `Set("_interrupted", true)`，由 executor 在节点返回后检查，而 LangGraph 是节点内动态 `interrupt()` + `Command(resume=...)`。

**加分点：** 说出复刻的真实收益："**抄完之后我才知道 LangGraph 为什么需要 superstep 和 channel 版本号。** 在串行执行下，channel 确实只是装饰；只有当你允许同超步内两个节点并行写同一个 key 时，合并语义才成为必需。**这个概念在读文档时是看不出必要性的。** 我的定位就是复刻核心概念、理解机制 —— 如果目标是生产使用，我会直接用 LangGraph。"

**扣分回答：** "我自己想的，不是抄的"。哨兵节点名字都一模一样，否认就是自曝 —— 而且比抄更糟，因为你还撒了谎。

## 第四组：挖坑题（5 题）

### Q26 · "你这个 Agent 支持并发吗？"

**考什么：** **其实在问会话串行。** 直接答"支持"就掉坑了 —— 因为 Agent 实例本身并不保证并发安全。

**30 秒骨架：**
1. **先分层：** "要分两层答：**Agent 实例本身不保证并发安全；串行性是由 Gateway 层的 Lane 提供的。**"
2. **依据：** Lane 是每 session 一条车道，用 CAS 抢占（`lane.go:33-68` 的 `CompareAndSwap(0,1)`），Gateway 侧最多等 30s（`gateway.go:117-131` 的 600 × 50ms）→ **session 内串行、session 间并行**。
3. **边界 —— 主动说出那个竞态：** `getOrCreateSession`（`base.go:388-398`）是 **Load 后 Store 的非原子操作** → **并发首次请求会创建两个 `SessionContext`，后写覆盖前者，丢掉一个请求的上下文**。也就是说我的串行化保护的是"已有 session 的请求"，**首次并发请求这道门是漏的**。

**加分点：** 主动说清 Lane 的两个实现缺陷：① `TryEnter` 里 `queueSize.Add(1)` **只在抢到锁时执行，且 `Leave` 不减**（`lane.go:55`）→ `GetQueueSize()` 返回的是**累计进入次数**，不是队列长度 —— **命名与实现不符**；② 本地模式的轮询**不看 `ctx.Done()`**（`gateway.go:119`），客户端断开后 goroutine 会空转 30s。

**扣分回答：** "支持，网关是多请求并发的。" —— 字面对了，但你漏掉了 Agent 内部的会话竞态，而这才是他要听的。

### Q27 · "Redis 里存的是什么？"

**考什么：** **其实在问序列化格式与缓存一致性。** 只答"存会话记忆"就浪费了这道题。

**30 秒骨架：**
1. **直答结构：** 一个 key 存**整个会话的 JSON 快照**。key 是 `bitguide:session:{sessionID}`（`memory/distributed.go:52-54`），value 是 `{interactions, variables}`（`:26-30`），TTL 默认 1 小时（`:37-38`）。
2. **再答写策略：** **全量 `SET`，没有 Hash/List 增量追加、没有压缩、没有分页、没有 value 大小检查**（`saveToRedis`，`memory/distributed.go:93-105`）。
3. **边界 —— 主动递到一致性和可用性：**
   - **只写不读**：`BuildMessages`/`GetHistory` 无生产调用方，LLM 上下文来自每实例内存 `sync.Map` → **换实例/重启就丢历史**；
   - **陈旧缓存回写会丢消息**：Lane 锁防住了并发交错，但 A 实例用旧快照全量覆盖 Redis 会抹掉 B 的消息 —— **锁解决并发，不解决缓存失效**；
   - **Redis 挂了是静默失败**：`GetJSON` 失败被当成"key 不存在"→ 静默新建空会话（`distributed.go:71-85`，错误被 `else` 吃掉）；`saveToRedis` 失败只打 `clog.Error`（`:102-104`）→ **请求仍成功返回，记忆静默丢失且上层无感知**；
   - **分布式记忆和本地会话的 key 不一致**：分布式用 `userID:sessionID`（`distributed.go:85-88`），`getOrCreateSession` 用原始 `req.SessionID`（`:119`）→ **一旦接入 userId 就会出现"本地会话 map 与 Redis key 不对齐"**（stage3 里 UserID 恒空所以还没暴露）。

**加分点：** 主动补两个 Redis 客户端层的事实："**连接池完全没配** —— `redis.NewClient` 只填了 Addr/Password/DB（`pkg/redis/client.go:25-33`），PoolSize/MinIdleConns/超时全部走默认值，没有 TLS、没有 Sentinel/Cluster、没有熔断。" 和 "`Expire` 的返回值被丢弃（`client.go:169`），一旦 EXPIRE 失败或进程在 INCR 与 EXPIRE 之间崩溃，**key 永不过期 → 该用户被永久限流**。正确做法是把 INCR + EXPIRE 合并成一条 Lua/EVAL。"

**扣分回答：** "存会话历史。" —— 面试官接下来每个追问都会落在你没提的那几个点上。

### Q28 · "你的服务支持水平扩展吗？"

**考什么：** **其实在问无状态性与会话粘性。** 答"支持，无状态"是最危险的答案 —— 这个服务**有状态**。

**30 秒骨架：**
1. **先给结论（诚实）：** "**部分支持，但我得说清哪部分是有状态的。**"
2. **依据 —— 两处状态：**
   - **会话记忆**：生产路径上是每实例内存 `sync.Map`（`pkg/agent/base.go:31,388-396`）→ **同一会话换实例就丢历史**（Redis 那份没接回上下文）；
   - **Lane**：本地模式是进程内 CAS（`lane.go:33-68`）→ 同一会话落到不同实例时**本地 Lock 只覆盖单实例**，要靠 Redis 锁补（`distributed.go:201-221`）。
3. **边界：** 所以现状是：**能多实例部署，但同一会话的行为不一致**（历史可能丢、锁可能跨实例）。另外还有两个纯工程问题：① `Gateway.sessions sync.Map`（`gateway.go:31`）只在显式 `ClearSession` 时删，`RemoveLane`（`lane.go:112`）**全仓无调用方** → **两者无 TTL、无上限、无 LRU，长跑进程按 sessionID 无限增长**；② `/api/v1/chat` 每次请求都可能自动生成 sessionID（`main.go:394-396`）→ 前端不传就等于每次新建会话，**Lane 锁形同虚设**且 sessions map 每请求增长一条。

**加分点：** 给出正确的扩展路线，并说清代价："要么**无状态化**（把会话状态外置到 Redis/DB，每实例不缓存），要么**会话粘性**（一致性哈希把会话钉到实例，落地本地锁）。我倾向无状态化 —— 因为它让扩缩容变成无脑操作，代价是每轮多一次 Redis 往返和一个必须解决的缓存一致性问题。**一致性哈希的代价更隐蔽：扩缩容时会话迁移会打乱在途请求。**"

**扣分回答：** "支持，没有状态"。事实相反，而且这个谎**在面试官问到"那会话历史存哪"时会立刻破**。

### Q29 · "你的 Agent 是无状态的吧？"

**考什么：** **其实在问 session 生命周期与内存泄漏。** 这题是 Q28 的变体，但重点不同 —— 它盯的是"资源会不会一直涨"。

**30 秒骨架：**
1. **结论：** "**Agent 对象本身可以认为无状态（配置 + 无状态工具），但 Agent 持有的会话容器是有状态的，而且它现在没有回收机制。**"
2. **依据：** `BaseAgent` 里挂着 `sessions`（一个 `sync.Map`，`base.go:31,388-396`），每个 session 是一个 `SessionContext`（含 `ConversationMemory`）。`getOrCreateSession` 只创建不回收。
3. **边界 —— 四处只增不减：**
   - `BaseAgent.sessions`：无 TTL、无上限、无 LRU；
   - `Gateway.sessions sync.Map`：只在显式 `ClearSession` 时删（`gateway.go:31`）；
   - `LaneManager` 的 lanes：`RemoveLane`（`lane.go:112`）**全仓无调用方**（死代码）；
   - `userLimiters sync.Map`（`ratelimit.go:17,65-72`）：**从不淘汰**，且有 bug —— `getUserLimiter` 是 **Load 后无条件 `Store`，不是 `LoadOrStore`** → **同一用户的并发首个请求会互相覆盖成"满桶新桶"，直接绕过该用户配额**。
   
   **叠加的效果：长跑进程会按 sessionID / userID 无限增长；而 `ClearSession` 这条路本身还有 bug —— HTTP handler 调的是基础版 `gw.ClearSession`（`main.go:474`），清 Redis 的逻辑在 `DistributedGateway.ClearSession`（`distributed.go:182-187`），而它没有任何调用方 → DELETE 会话清不掉 Redis。**

**加分点：** 说出正确的回收设计："会话生命周期应该由**最后活动时间 + TTL** 驱动，配一个后台清理（比如每 5 分钟扫一遍超过 30 分钟未活动的 session）。用 `sync.Map` 是为了读多写少的并发，但它**不支持按时间淘汰** —— 需要额外的 `lastAccess` 记录和定期扫描，或者用带 TTL 的缓存库（如 `ristretto`/`freecache`）。"

**扣分回答：** "无状态"。然后面试官问"那用户的会话存在哪"，你说"内存里"，他就知道你前面那句是随口说的。

### Q30 · "你这个工作流引擎支持循环吧？"

**考什么：** **其实在问环检测。** 而且这里有个陷阱：项目里**有一个叫 `LoopNode` 的东西**，答"支持，有 LoopNode"就掉进去了。

**30 秒骨架：**
1. **先分层（这句是这题的关键）：** "要分清两种'循环'：**图上的环**，和**一个封装好的循环节点**。我只有后者，**图上零环检测**。"
2. **依据（分两点说）：**
   - **图上没有环检测**：无 visited 集合、无最大步数，**`A→B→A` 会无限循环**。`Build()`（`core/graph.go:70-75`）只校验"至少一个节点" —— 不校验 Start 边、不校验边指向的节点是否存在（运行时才报，`executor.go:42-44`）、不校验可达性。

3. **边界：** 而且这个 `LoopNode` 还有个语义陷阱：`ShouldContinue` 是**前置判断** → **初值 false 时 body 一次都不执行**（do-while 的直觉会写错）。另外它在 8 个 demo 里**零使用**（唯一被 demo 用到的 6 类节点里不含它）。

**加分点：** 主动说出路由的另一个隐蔽问题："多条边时 `resolveNextNode`（`executor.go:159-174`）返回**第一条 `ResolveTarget` 非空**的边，而 `SimpleEdge.ResolveTarget` **恒返回非空 `To`**（`edge.go:16`）→ **边的注册顺序决定语义**。混合挂静态边 + 条件边时，**静态边永远赢，条件边可能永远轮不到** —— 这是个静默的语义 bug，代码不报错，只是不按你写的走。"

**扣分回答：** "支持，有 LoopNode。" —— 面试官接着问"A→B→A 会怎样"，答"会一直循环"，那"支持循环"这个说法就变成了"支持死循环"。

## 附：三条通用应急法则

面试里遇到没准备的问题时，用这三条而不是硬编：

| 法则 | 怎么说 | 为什么有效 |
|---|---|---|
| **把结论降级成条件句** | 不说"是这样"，说"**在我的实现里是这样，如果换成 X 场景就不成立**" | 你不需要知道所有情况，只需要知道边界在哪 —— 而边界是你一定知道的 |
| **把不会的换成"我知道它的代价"** | "**我选了 A 没选 B，B 的代价是 C**" | 判断力比知识更难伪装，也更能加分 |
| **主动交出一处未修的缺陷** | "同一块代码里我还知道有个问题没解决：……" | 编简历的人不敢说自己有洞。**这是成本最低的真实性证明** |

**最后一条，也是最重要的：** 上面 30 道题里，**凡是"结论是我没做/我不知道"的题，都不是失分项**。失分的永远是那三种回答：**编一个机制**、**用"教学项目"当挡箭牌**、**把没做的说成做了**。这个项目有 75 个文件、12,253 行真代码、20 多个能在面试里讲透的技术点 —— **你完全不需要编。**
